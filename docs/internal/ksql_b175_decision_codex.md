# 推奨: 案1 — 今は実装せず、案Aで止める

B175 の EXPLAIN 注記は、B173 にも別リリースにも載せないことを推奨します。

理由は次の4点です。

1. 現時点の露出は小さいです。実測上、踏めば `INSERT`/対象フィールド更新で 6/8 と高確率ですが、推奨 R18 は読取・ゲートを先に行い、書込を最後にしています（`docs/ksql_batch_recipes.md:820-841`）。起票も探索由来であり（`docs/internal/ksql_b175_klike_index_lag_issue.md:7`）、提示された運用事実では障害報告・該当資産ともゼロです。

2. 案Aは現在、単なる注意書き以上に具体的です。新値の取りこぼし、旧値の偽陽性、第一回避策の「書込を最後」、`LIKE` の `maxRecords` リスクまで既に説明しています（`docs/ksql_language_reference.md:1138-1146`）。既知利用者がいない現状では、追加の EXPLAIN 注記による限界便益は小さいです。

3. EXPLAIN 注記は保護ではありません。実行を止めず、通常実行だけの利用者には届かず、MCP の単文 EXPLAIN は共通バッチ計画を通りません（`src/mcp/tools.ts:705-730`）。それに対して、完全な論理アプリ同一性まで扱うには15位置引数の共通関数（`src/execute.ts:12637-12652`）から CLI・MCP・flow・engine-library へ binding を配管する必要があります（`docs/internal/ksql_b175_klike_index_lag_explain_spec.md:238-284`）。

4. 決定的に、R1の対象範囲には現コードとの齟齬があります。R1は後続の SELECT スコープだけを検出します（`docs/internal/ksql_b175_klike_index_lag_explain_spec.md:37-42,136-147`）が、現コードでは通常親 `UPDATE` / `DELETE` の WHERE と APPLY 複数親 `UPDATE` でも `KLIKE` が許可されています（`src/core/klikeValidation.ts:68-109`、`src/core/__tests__/klikeValidation.test.ts:65-71`、`docs/ksql_language_reference.md:1153-1155`）。一方、レシピ文書の「全 DML で使用不可」は古い記述です（`docs/ksql_batch_recipes.md:797-802`）。

したがって、危険形は「後続の読取文」だけとは限りません。先行書込後の `UPDATE/DELETE ... WHERE ... KLIKE ...` も同じ索引を使うため、対象の見逃しや旧値による過剰更新・削除が起こり得ます。これはコードからの推論であり、連続 DML と `NOT KLIKE` の実機挙動は要確認です。今の R1を実装すると、助言機能自体に重要な見逃しを固定してしまいます。

## 安く塞げる別の手

製品内で、文書より安くかつ正確に穴を塞ぐ手は現状ありません。

- 既存静的検証は文単位です。`validateKlikeStatement` は単一 `Statement` を検査するだけで、先行文との書込順やフィールド交差を持ちません（`src/core/klikeValidation.ts:24-34`）。ここへ単純な全面拒否を足すと、別フィールド更新や即時削除など実測上無害な形まで拒否します。
- `VALIDATE ONLY` も解決になりません。対象取得そのものが `KLIKE` 索引に依存するため、索引ラグによる欠落を正解集合と比較できません。通常親DMLで `KLIKE` が許可される事実も変わりません（`docs/ksql_language_reference.md:1155`）。
- 既存EXPLAIN行へ無条件に「索引ラグ」を追記する方法は安いですが、先行書込のない通常のKLIKEにも毎回出て警告疲れを生みます。B140では、常時出る警告の隣に別警告が流れることが実運用で確認されています（`docs/internal/ksql_b140_cte_groupby_total_order_issue.md:168-176`）。
- レシピ面ではR18がすでに書込最後なので、追加変更は不要です（`docs/ksql_batch_recipes.md:820-841`）。

どうしても即時の機械的ガードが必要なら、kSQL本体ではなく、該当資産を持つ側のCIで「最初のmutation以降にKLIKEを置かない」という保守的lintを置くのが最安です。R18と一致し、app bindingもフォーム定義も不要です。ただし ksql-flow にlint挿入点があるかは未調査のため要確認です。

## 判断を覆す条件

次のいずれかが観測されたら、案3「B173とは別リリースで実装」へ変更します。B173同梱には戻しません。

1. 実資産または障害報告で、書込後KLIKEによる取りこぼし・旧値偽陽性・誤更新・誤削除が1件でも確認された。
2. リポジトリまたは推奨レシピに、書込後のKLIKE読取/DMLを必要とする実例が入った。
3. B143案Aまたは `/flow` の `StatementResult.warnings` 配管に着手し、共通警告基盤へ相乗りできる状態になった。
4. 先行書込後の `UPDATE/DELETE ... KLIKE/NOT KLIKE` を実機測定し、対象範囲と結果方向を確定できた。
5. 本番規模・高負荷環境でも再現する、またはラグが3秒を大きく超える事例が観測された。
6. kintone公式が索引の非同期反映を契約として文書化した。
7. 逆に、複数環境・負荷条件で即時同期化されたことが確認された場合は、実装再開ではなく案A文書自体の再検証を行う。

結論として、今は「作らない」が正しいです。R1は費用対効果だけでなく、現行DML能力を見落とした対象範囲の問題があるため、そのまま実装候補として保持すべきではありません。この調査ではファイル変更・コード変更・git操作は行っていません。
