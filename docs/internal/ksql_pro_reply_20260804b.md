# 本文（送付版）

## 【返信】レシピ集を読ませていただきました — 1 件訂正と、取り込みのご報告

## 1. 訂正 — `DATE_ADD` は使えます

レシピ集に「`DATE_ADD` / `DATE_SUB` / `INTERVAL` は**非対応**（検証済み）」とありますが、
**`DATE_ADD` は使えます。**引数の形が違うだけでした。

```sql
DATE_ADD(受注予定日, INTERVAL 1 MONTH)   -- ParseError（MySQL の書き方）
DATE_ADD(受注予定日, 1, 'MONTH')         -- OK（kSQL の書き方）
```

- 単位は `YEAR` / `MONTH` / `DAY` の 3 つで、大文字小文字は問いません
- **`DATE_SUB` が無いのは事実です。**減算は負数で書きます（`DATE_ADD(期限日, -1, 'MONTH')`）
- `INTERVAL` 構文も非対応です

**前月・前年の判定を `YEAR(列) * 12 + MONTH(列)` の数値演算で書かれている箇所（D2）は、
そのままでも正しく動きます**ので、無理に書き換える必要はありません。ただ「使えない」と
思われたままだと選択肢が狭まるので、お知らせします。

## 2. レシピ集から 1 つ取り込みました

**「フルスキャンになる書き方 → 回避形」の対応表**を、こちらの言語リファレンス §6
（WHERE の押し下げ）へ取り込みました。次のリリースに載ります。

こちらには型 × 演算子の網羅表（実装から生成）はあったのですが、**書き換えの指針が
散在**していて、「で、どう書けばいいのか」に一息で答えられていませんでした。
そちらの表はその穴をそのまま埋める形になっていました。ありがとうございます。

**全 6 行はこちらでも実測してから載せています。**

## 3. ただし JOIN の行だけ、効果を限定して書きました

`売上 >= 5000000` → `売上 > 4999999` の書き換えですが、**押し下がるのは主表だけ**です。

```
売上 >= 5000000  →  主表 fetch: ALL          / 結合先 fetch: ALL
売上 > 4999999   →  主表 fetch: PREFILTERED  / 結合先 fetch: ALL   ← 結合先は変わらない
```

レシピ集の「実測 30 → 15 件」は主表側の取得件数だと理解しています。
**結合先のアプリは全件のまま**なので、「JOIN 全体が軽くなる」と読まれると
期待とずれるかもしれません。表現をご確認いただければ。

## 4. 未知の値の扱い — こちらの文書にも入れました

「**知らない区分を軽い側へ寄せない**」という方針、そのとおりだと思います。
理由（新しい重い区分が入ったときに全件取得を安全と誤って見せる）ごと、こちらの
engine ライブラリ文書へ書き足しました。次に別の利用者が来たときにも効きます。
