## 1. 実装の範囲

**R1 §2〜§8 を実装する。**

**中心は R1 §3 の案 C**＝**`SELECT` の出力値と入力フィールドを別の名前空間で保持する。**

> **`SELECT` 句の別名は、同じ `SELECT` 句の他の式からは見えない。**

## 2. **必ず守ること**

1. **`HAVING` と通常 `ORDER BY` の別名解決は維持する**（R1 §4.2）。
   **これが本件でいちばん難しいところ**＝**`SELECT` 式からは見えなくしつつ、
   `HAVING` / `ORDER BY` からは見えたままにする。**
   **Claude が実測した基準値**（v3.57.0・APP4228）＝
   ```
   SELECT 製品名, SUM(個数) AS 個数 FROM APP4228 GROUP BY 製品名
   HAVING 個数 >= 20000 ORDER BY 個数 DESC
     → 牛乳 29351 / 食パン 23429
   ```
   **修正後も同じであること。**
2. **新しいエラー・警告・reason code を作らない**（R1 §4.3）。**本件は成功 SQL の値修正**
3. **落としてはいけない SQL**（R1 §4.2）＝`SELECT 商品, SUM(数量) AS 数量 … GROUP BY 商品`。
   **自然で無害な形**である
4. **内部保存先を source 列として露出しない**（R1 §3.3）＝
   `SELECT *` / `alias.*` / `_p.*` / `DISTINCT` の入力列 / CTE の公開 `columns` /
   公開 `SelectResult.rows` / `columns`。
   **予約 prefix を使うなら、利用者が同名フィールドを作っても到達できないこと**
5. **公開型に必須プロパティを足さない**（BYO クライアントが壊れる）
6. **ウィンドウ関数も対象**（R1 §8.1）。**集計も `GROUP BY` も無い素の `SELECT` で起きる**
   （起票 §9・Claude の実測）

## 3. **直る形（Claude の実測・v3.57.0）**

**すべて「別名を衝突させたとき」の現行値。修正後は右の値になること。**

| SQL の骨子 | 現行（誤り） | 修正後 |
|---|---|---|
| `DATE_FORMAT(日付,'%Y-%m') AS 年月, SUM(個数) AS 日付` | `年月 = ""` | `年月 = "2025-08"` |
| `個数 * 2 AS 倍, SUM(個数) AS 個数`（`GROUP BY 製品名, 個数`） | `倍 = 2584` | `倍 = 1292` |
| `製品名 \|\| '-x' AS 名札, SUM(個数) AS 製品名` | `名札 = "23429-x"` | `名札 = "食パン-x"` |
| `CASE WHEN 個数 > 100 … AS 区分, SUM(個数) AS 個数` | `区分 = "大"` | `区分 = "小"` |
| `個数 * 2 AS 倍, ROW_NUMBER() OVER (…) AS 個数` | `倍 = 2, 4, 6` | `倍 = 1292, 1412, 796` |

**グループが 1 件だと現行でも偶然合う**ので、**受入は必ず 2 件以上のグループで書くこと。**
