# B121 `HAVING` の集計比較が文字列比較になり、誤った行集合を返す

- 起票: 2026-08-05
- ステータス: ✅ **完了（v3.44.0 でリリース）**（2026-08-05・npm publish 済み・**MCP 実機で確認**＝`HAVING COUNT(*) > 10` が 0 行）。`HAVING` の直接参照に集計の比較型を引き渡して修正。**8 集計で「直接参照 = 別名参照」を突き合わせ全一致。差し戻し 0 回。**
- 出典: [B119/B120 のレビュー 3 回目](ksql_b119_b120_review_2.md) の追加検証中に発見（`ksql-analytics` で実測）
- 関連: [B119](ksql_b119_aggregate_string_function_arg_issue.md) / [B120](ksql_b120_aggregate_position_diagnostics_issue.md)
  ＝**同族（集計値が文字列として比較される）**。B117・B118 から続く「静かに間違う」系
- **既存の欠陥**: `git stash` で変更を退避した HEAD でも完全に同じ結果になることを確認済み。
  B119/B120 の実装とは無関係

## 1. 症状（実測 2026-08-05・v3.43.0・dev / APP4149）

対象データ: 20 レコード / 10 社。件数の最大は 5、`SUM(売上)` は 0 〜 20,700,000。

| SQL | 期待 | 実測 | 文字列比較なら |
|---|---:|---:|---|
| `GROUP BY 会社名 HAVING COUNT(*) > 10` | **0 行** | **5 行** | `"5" > "10"` → `'5'>'1'` → true。件数 2/3/5 の社が通る |
| `GROUP BY 会社名 HAVING AVG(売上) > 9` | **8 行** | **0 行** | `"4140000" > "9"` → `'4'<'9'` → false。全社が落ちる |
| `GROUP BY 会社名 HAVING SUM(売上) >= 9050000` | **4 行** | **1 行** | `"20700000" >= "9050000"` → `'2'<'9'` → false |
| `GROUP BY 会社名 HAVING SUM(売上) > 9` | **8 行** | **1 行** | 先頭が `'9'` の 9,050,000 だけが通る |

**4 例すべてがコードポイント順の比較と一致する。** 過大にも過小にも振れる。

### 再現

```
ksql --profile dev -e "SELECT 会社名, COUNT(*) AS c FROM APP4149 GROUP BY 会社名 HAVING COUNT(*) > 10"
→ 5 行（0 行が正しい）
```

## 1.5 壊れているのは**直接参照だけ**。別名参照は正しい（2026-08-05 追記）

同じ条件を SELECT の別名で書くと**数値比較で正しく動く**。

| 形 | 期待 | 実測 |
|---|---:|---:|
| `SELECT ... SUM(売上) AS s ... HAVING s > 9`（**別名**） | 8 行 | **8 行** ○ |
| `SELECT ... SUM(売上) AS s ... HAVING SUM(売上) > 9`（**直接**） | 8 行 | **1 行** ✗ |
| `SELECT ... COUNT(*) AS c ... HAVING c > 10`（**別名**） | 0 行 | **0 行** ○ |
| `SELECT ... COUNT(*) AS c ... HAVING COUNT(*) > 10`（**直接**） | 0 行 | **5 行** ✗ |

**別名参照の経路が、そのまま正解の参照実装になる。** 直接参照の経路が
同じ型情報を使うようにすればよい。修正範囲もこの経路に限定される。

## 2. なぜ今まで見つからなかったか

**桁数が揃っていれば文字列比較でも正しい答えになる。** 言語リファレンス §9 の例はどちらも偶然一致する。

```sql
HAVING COUNT(*) >= 5          -- 件数が 1 桁どうしなら一致する
HAVING SUM(金額) > 1000000    -- 8 桁 vs 7 桁で '2' > '1' となり、たまたま正しい
```

誤るのは**比較の両辺で桁数が異なり、かつ先頭の桁の大小が数値の大小と逆になる**場合。
実データではごく普通に起きる（上の 4 例はどれも作為的な値ではない）。

既存テストが通っているのも同じ理由と考えられる。**テストの値を桁違いにすれば落ちるはず。**

## 3. 影響

- `HAVING` は「一定件数以上のグループだけ」「一定金額以上の取引先だけ」という
  **分析の定番の絞り込み**。誤った行集合がそのままレポートの数字になる
- 過小（0 行）に振れた場合は「該当なし」と読まれ、過大に振れた場合は
  「条件を満たしていない行」が混ざる。**どちらもエラーは出ない**
- **B120 修正後は不整合が表面化する**。同じ SQL の中で
  `CASE WHEN SUM(売上) > 9 THEN ...`（B120 修正で数値比較・正しい）と
  `HAVING SUM(売上) > 9`（文字列比較・誤り）が**食い違う**。
  B120 と同じ版でリリースするのが望ましい

## 4. 原因の見立て

集計値が行に**文字列として** materialize され、`HAVING` の評価がその文字列をそのまま
比較していると見られる（B120 の CASE 条件と同じ構図）。

B120 の修正では、CASE 条件に集計の比較型（`COUNT`/`SUM`/`AVG`/統計 = 数値、
`GROUP_CONCAT`/`MODE` = 文字列、`MIN`/`MAX` = 引数の型に追従）を引き渡すことで解決した。
**`HAVING` にも同じ型情報を渡せばよいはず**で、B120 の実装がそのまま参考になる。

## 5. 受入条件

APP4149（20 件 / 10 社）で:

1. `HAVING COUNT(*) > 10` → **0 行**
2. `HAVING AVG(売上) > 9` → **8 行**
3. `HAVING SUM(売上) >= 9050000` → **4 行**
4. `HAVING SUM(売上) > 9` → **8 行**
5. `MIN` / `MAX` は引数の型に追従（数値フィールドなら数値比較、文字列フィールドなら文字列比較）
6. `GROUP_CONCAT` / `MODE` は文字列比較のまま
7. **回帰**: `HAVING COUNT(*) >= 3`、`HAVING GROUPING(会社名) = 1`、
   `HAVING SUM(CASE WHEN ... END) > n`、SELECT の別名参照（`HAVING 売上合計 > 0`）が従来どおり
8. **テストは桁違いの境界で書く。** 桁が揃った値では文字列比較でも通るため検出力がない

## 6. 併せて直すこと

[B120 の文書](ksql_b120_aggregate_position_diagnostics_issue.md) §2 に
「`HAVING SUM(売上) > 0` → 10 行（正しい）」と書いたが、**正しくは 8 行**
（`SUM(売上)` が 0 の 2 社は条件を満たさない）。本件の調査で判明したため訂正済み。
B120 §2 の主張（SELECT に無い集計は無言で 0 行）自体は変わらない。
