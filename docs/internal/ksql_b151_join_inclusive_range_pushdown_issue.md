# B151 JOIN の `<=` / `>=` が全件取得になる（kintone が受ける条件の JS 判定落ち）

- 起票: 2026-08-07（オーナー依頼「起票して対応」＝方向確定・着手指示済み）
- ステータス: 📝 **起票・方向確定（案 A＝widening 正規化）・仕様 R1 作成へ**
- 関連: [B76 Phase A](ksql_b76_join_pushdown_phase_a_spec.md)（strict 限定の判断元）／
  [B84](ksql_b84_pushdown_visibility_spec.md)（可視化・2 機構の区別）／
  [B126]（選択系 `=` の正規化＝本件と同じ「正規化してから分類」の型）

## 1. 症状（実測・v3.59.0・APP4228/4229）

| 経路 | SQL | 結果 |
|---|---|---|
| 単一表 | `WHERE 個数 <= 100` | **EXACT**（`kintone query: 個数 <= 100`）＝問題なし |
| **JOIN** | `WHERE t.個数 <= 100` | **`join pushdown not applied: UNSAFE_RELATION`・JOIN 側 fetch: ALL**＝全件取得後に JS 判定 |
| JOIN（対照） | `WHERE t.個数 < 100` | `pushdown applied`・`relation: superset`・PREFILTERED |

**kintone のクエリ構文は数値の `<=` / `>=` を受け付ける**（公式ドキュメントの演算子表）。
落ちているのは kintone 側ではなく、**kSQL の JOIN prefilter の安全証明**
（B76 Phase A「IEEE-754 境界のため inclusive は不可」＝境界ちょうどを含む比較は、
10 進厳密比較（kintone）と binary64（ローカル）の丸めで境界直近の行が欠落し得る）。

## 2. 対応の方向（案 A 採用・オーナー指示）

**案 A＝widening 正規化**: 安全整数リテラル L に対し、エンジンが

```
x <= L  →  x < L+1
x >= L  →  x > L-1
```

へ正規化してから既存の分類器（strict `<` / `>`・superset）に乗せる。

- **安全性の証明が既存のリリース済み経路に帰着する**のが要点＝strict の境界安全性
  （10 進で境界以下の値は binary64 で境界を超えない）と空セル・再評価の意味論を
  そのまま継承し、**新しい証明を持ち込まない**
- 手動の書き換え（`売上 >= 5000000` → `売上 > 4999999`）は言語リファレンスに実測付きで
  文書化済み＝**「人に書き換えを案内している形は、エンジンが自動でやれる」**（B126 と同じ判断）
- superset なので取得後の再評価で正確性は従来どおり担保。**結果は変わらず取得量だけ減る**
- L±1 が安全整数を外れる境界（`<= 9007199254740991` 等）は正規化せず従来どおり（fail-closed）

### 検討対象（codex が証明可能性をコードから列挙して Phase を切る）

- 非整数リテラル（`<= 100.5` → `< 101` などの整数境界への widening）
- `$id` / レコード番号顔の経路との整合（`$id` は既に inclusive 可＝対象外）
- DATE / DATETIME / TIME の範囲・`!=`・TEXT `in` 等は**空セル意味論の新規証明が要るため本件の対象外**
  （B76 の「やらないこと」を維持。実需が出たら別途）

### 採らなかった案

- **案 B＝厳密 10 進比較の新設**（B76 対象外リスト）: 大型で、日次の実害（取得量）には過剰
- **案 C＝文書化のみ**: 書き換えは案内済みだが、「最初に書かれる形」は `<=` / `>=`（B124 の物差し）
