# B151 JOIN の `<=` / `>=` が全件取得になる（kintone が受ける条件の JS 判定落ち）

- 起票: 2026-08-07（オーナー依頼「起票して対応」）
- ステータス: 📝 **方向転換（2026-08-07・§2.6）＝widening ではなく「そのまま押し下げ」。
  意味論一致を実測で確認済み・仕様依頼を書き直して R1 作成へ**（widening 前提の初回 R1 は
  レビュー前に前提が覆ったため未保存のまま破棄。参照しないこと）
- 関連: [B76 Phase A](ksql_b76_join_pushdown_phase_a_spec.md)（strict 限定の判断元）／
  [B84](ksql_b84_pushdown_visibility_spec.md)（可視化・2 機構の区別）／
  [B126]（選択系 `=` の正規化＝本件と同じ「正規化してから分類」の型）

## 1. 症状（実測・v3.59.0・APP4228/4229）

| 経路 | SQL | 結果 |
|---|---|---|
| 単一表 | `WHERE 個数 <= 100` | **EXACT**（`kintone query: 個数 <= 100`）＝問題なし |
| **JOIN** | `WHERE t.個数 <= 100` | **`join pushdown not applied: UNSAFE_RELATION`・JOIN 側 fetch: ALL**＝全件取得後に JS 判定 |
| JOIN（対照） | `WHERE t.個数 < 100` | `pushdown applied`・`relation: superset`・PREFILTERED |

**kintone のクエリ構文は数値の `<=` / `>=` を受け付ける**（公式ドキュメントの演算子表）。
落ちているのは kintone 側ではなく、**kSQL の JOIN prefilter の安全証明**
（B76 Phase A「IEEE-754 境界のため inclusive は不可」＝境界ちょうどを含む比較は、
10 進厳密比較（kintone）と binary64（ローカル）の丸めで境界直近の行が欠落し得る）。

## 2. 対応の方向（案 A 採用・オーナー指示）

**案 A＝widening 正規化**: 安全整数リテラル L に対し、エンジンが

```
x <= L  →  x < L+1
x >= L  →  x > L-1
```

へ正規化してから既存の分類器（strict `<` / `>`・superset）に乗せる。

- **安全性の証明が既存のリリース済み経路に帰着する**のが要点＝strict の境界安全性
  （10 進で境界以下の値は binary64 で境界を超えない）と空セル・再評価の意味論を
  そのまま継承し、**新しい証明を持ち込まない**
- 手動の書き換え（`売上 >= 5000000` → `売上 > 4999999`）は言語リファレンスに実測付きで
  文書化済み＝**「人に書き換えを案内している形は、エンジンが自動でやれる」**（B126 と同じ判断）
- superset なので取得後の再評価で正確性は従来どおり担保。**結果は変わらず取得量だけ減る**
- L±1 が安全整数を外れる境界（`<= 9007199254740991` 等）は正規化せず従来どおり（fail-closed）

### 検討対象（codex が証明可能性をコードから列挙して Phase を切る）

- 非整数リテラル（`<= 100.5` → `< 101` などの整数境界への widening）
- `$id` / レコード番号顔の経路との整合（`$id` は既に inclusive 可＝対象外）
- DATE / DATETIME / TIME の範囲・`!=`・TEXT `in` 等は**空セル意味論の新規証明が要るため本件の対象外**
  （B76 の「やらないこと」を維持。実需が出たら別途）

### 採らなかった案

- **案 B＝厳密 10 進比較の新設**（B76 対象外リスト）: 大型で、日次の実害（取得量）には過剰
- **案 C＝文書化のみ**: 書き換えは案内済みだが、「最初に書かれる形」は `<=` / `>=`（B124 の物差し）

## 2.5 前提の実測（2026-08-07・オーナーの問い「小数の桁落ちが問題なのか？」への検証）

**kintone の数値精度はアプリ設定「数値や計算の精度」（`numberPrecision`）で決まる**ことを、
APP4228 への書き込み実験（検証レコードは削除済み）と一般設定 API で確認した。

- APP4228 は既定値＝**全体 16 桁・小数部 4 桁・HALF_EVEN**。実測と一致:
  整数 12 桁（=16−4）は受理・13 桁は拒否（`CB_VA01`）／`0.1234567890123456789` は
  **保存時に `0.1235` へ丸め**（受理はされるが精度は設定で落ちる）
- **設定は全体 30 桁・小数部 10 桁まで広げられる**ため、binary64（有効 15〜16 桁）で
  区別できない値を格納できるアプリは設定次第で実在する。**既定の 16 桁でも**
  境界密度が ulp を下回る領域（例: `999999999999.9999` と `1000000000000`）があり、
  IEEE-754 前提の危険は**既定設定でも到達可能**
- **リテラルの渡し方は無関係**＝kSQL は元々条件を文字列クエリとして kintone へそのまま送る。
  問題は送信側ではなく、**取得後のローカル再評価（binary64）と kintone（10 進）の境界一致**
- **案 A（整数境界への widening）はこの精度問題に依存しない**＝`L±1` は安全整数で
  binary64 厳密表現でき、「10 進で境界以上の値は binary64 で境界を下回らない」証明が
  アプリの precision 設定に依らず成立する
- 将来の別案として、**アプリの `numberPrecision` を読み「このアプリは binary64 安全」と
  証明して inclusive を直接押し下げる**拡張があり得る（metadata 取得が増える。本件の対象外）

## 2.6 方向転換（2026-08-07・オーナーの追及「そのまま送ればよいのでは」が正しかった）

**案 A（widening）は不要**。オーナーの連続した問いを実測で追った結果、
**現行エンジンのローカル数値比較は kintone と同じ 10 進厳密意味論**であることを確認した。

1. **比較実装**＝`src/core/scalarCompare.ts` の `numberKey` が `parseExactDecimal` で
   10 進厳密比較（band 2）。binary64 ではない
2. **実測（境界すれすれ）**＝格納値 `999999999999.9999`・リテラル `999999999999.99985`
   （binary64 では同値に丸まる組）で、`<=` / `>=` とも
   **押し下げ経路・FULL_SCAN 強制経路・算術経由の 3 経路すべて同じ結果**（0 行 / 1 行が一致）
3. **実測（空セル）**＝空の数値セルは **kintone・ローカルとも「最小値」扱いで両方向一致**
   （`< 100` は両者とも空セルを含む／`>= -5` は両者とも除外）
4. したがって **B76 Phase A の「IEEE-754 境界のため inclusive 不可」は現行実装では
   前提が成立していない**（当時の binary64 比較を前提にした判断が、10 進比較器の導入で
   静かに無効化されたと推定。導入版の特定は仕様作成時に codex がコード履歴から行う）

**新しい方向＝`<=` / `>=` を JOIN prefilter でそのまま押し下げる**（widening なし・正規化なし）。
安全性の根拠は「ローカルと kintone の数値比較意味論が一致している」ことの証明
（B78 の local contract と同じ形式）。同じ根拠で **strict `<` / `>` の安全整数リテラル制限の
解除・`!=` の解禁も検討対象**になる（空セル・非数リテラルの端の意味論を仕様で列挙すること）。

なお §2.5 の「既定の 16 桁でも危険域がある」という記述は **binary64 ローカル評価を前提とした
誤り**だった（前提ごと覆ったため、本節が正）。

## 2.7 原理の整理（2026-08-07・オーナーの問い「単一表と同じでよいのでは」への回答）

**押し下げの正しさの条件（取得集合 ⊇ ローカルが欲しい行＋再評価）は単一表と JOIN で同一**であり、
**値の意味論の一致が要る点にも差はない**。JOIN に本質的に固有な制約は次の 3 つだけ:

1. **部分条件の切り出し**（AND の葉単位の superset 証明・OR/NOT の下は構造的に不可・所有権解決）
2. **外部結合の非保存側**（絞ると NULL 展開の意味が変わる。型と無関係）
3. **複数アプリへの分配**（alias・非修飾フィールドの所有解決）

**型×演算子で JOIN だけ絞る理由は、原理上は「意味論が本当に違う組」だけ**＝
CALC（表示書式で値形式が変わる）・RECORD_NUMBER（アプリコード付き形式）・
LIKE（v2.0.0 の意図的な JS 統一）・kintone が演算子自体を受けない組。
それ以外の ✕ は「証明できた組だけ開けた」B76 の歴史的残差であり、
**同じ一致証明の枠組みで型ごとに順次開けるのが後続 Phase の方向**
（DATE / TIME / DATETIME の範囲・ユーザー系 `in`・TEXT の `!=` / `in` が候補。
各々、空セル方向・値表現・正規化の実測証明を条件とする）。
