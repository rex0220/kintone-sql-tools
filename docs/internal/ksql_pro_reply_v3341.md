# 本文（送付版）

## 【返信】§3 はご指摘のとおりです — **こちらの限界の書き方が誤っていました**

**「再起動したら、クライアント側も繋ぎ直してください」と書きましたが、足りませんでした。**

**`instructions` が文脈に入るのは、MCP の接続時ではなく会話の開始時です。**
**正しい規則は「繋ぎ直す」ではなく「新しい会話を始める」**でした。

---

## 1. **こちらでも同じことが起きていました**

**v3.34.1 を publish して VSCode を再読み込みしたあとも、
その時点で進行中だったセッションの文脈は、版数行の無い本文のままでした。**

**そのセッションからは、自分がリリースした版を確かめられませんでした。**

**§3 の観測は、実クライアント 2 つで一致しています。**
とくに**「同じ瞬間に 2 つの会話が違う本文を見る／サーバーもプロセスも 1 つ」**という切り分けは、
**原因を接続ではなく会話に確定させるもの**で、こちらの推測だけでは出せませんでした。

---

## 2. 直しました

| | |
|---|---|
| `CHANGELOG.md` の v3.34.1 使い方 | 「再起動する」→ **「再起動したうえで、新しい会話を始める」** |
| `release/README.txt` | 「繋ぎ直してください」→ **「新しい会話を始めてください」** |

**どちらにも「古い会話では古い版が見えるだけなので、誤って新しいと思い込むことはない」**
を併記しました（§3.1 のご指摘）。

**GitHub Release の本文も同じ内容へ直しています。**

---

## 3. §3.1 の整理はそのまま採らせていただきました

**失敗の向きが安全側**——**古い版が見えるので「まだ更新されていない」と読め、
再更新へ倒れる。誤って新しいと思い込むことはない**——という整理です。

**逆向きが起きるのは、新しい版で会話を始めたあとに、その会話の中で古い版へ戻して
再起動した場合だけ**というのも、そのとおりです。

**これは課題の優先度にも効きます。**
**「疑わなくても気づける」ようにする案**（プロセスの版とディスクの版を突き合わせて
ずれていたら知らせる）を保留にしていましたが、**急ぐ理由がないことの根拠が 1 つ増えました。**

---

## 4. §3.2 について

**「挙動が変わらない版差は測れない」**——**カナリアの本質的な限界**だと思います。

今回の 3.34.0 → 3.34.1 がまさにそれで、**挙動が同じである以上、
どんなクエリを流しても版は判別できません。**
**版を知る手段は、版そのものを聞く以外にありません。**

---

## 5. 一連のやり取りについて

**こちらの誤りも同じ数ありました。**

- 「2026-07-28 に対応した SDK が存在しない」——**package が分割されていただけ**
- 「版数を返す標準の手段が無い」——**`_meta` という標準があった**
- 「`_meta` があるから解決済み」——**実クライアントには届かなかった**
- 「繋ぎ直せばよい」——**会話単位だった**（今回）

**いずれも、測った範囲の外に答えがありました。**
**そちらの報告が無ければ、どれも気づいていません。**

**とくに今回の §3 は、「動いている」という報告に添えて限界の反証まで出していただいたものです。**
**助かりました。**
