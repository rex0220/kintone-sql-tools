# B115 CLI テストが開発者のシェル環境変数に依存して緑赤する

- 起票: 2026-08-04
- ステータス: ✅ **完了（運用で回す・2026-08-04 オーナー判断）**＝README「ローカル開発」に記述。実装・テストは変更しない
- 出典: B114 第 1 段の実装レビュー中に発見（2026-08-04）。**B114 の回帰ではない**
- 関連: `src/cli/__tests__/logicalExecution.test.ts` / `src/node/runtime.ts:292-297`

## 1. 症状（実測 2026-08-04）

**`logicalExecution.test.ts` の 2 件が、リポジトリの状態と無関係に、実行するシェルの
環境変数で緑にも赤にもなる。**

```
そのまま実行                                  → 2 failed / 9 passed
KSQL_USERNAME・KSQL_PASSWORD 等を外して実行     → 11 passed
```

- **B114 を退避した HEAD でも同じ 2 件が落ちる**＝コード変更が原因ではない
- v3.39.0 のリリースゲート（2026-08-02）は全 green だった＝**その後に環境変数が
  設定されただけで、リポジトリは何も変わっていない**

## 2. 原因

対象テストは **`tokenMap` だけを書いた設定**（`auth` も `username` / `password` も無い）を
一時ファイルに作り、アプリごとに正しい API トークンで振り分けられることを検証する。

認証の解決は **CLI 引数 → 環境変数 → 設定ファイル**の順で、`auto` は
「ユーザー名とパスワードが揃っていれば `userpass`、無ければ `token`」である
（`src/node/runtime.ts:292-297`）。

```ts
const username = envString("KSQL_USERNAME") ?? profile.username ?? null;
const auth = authReq === "auto" ? (hasUserPass ? "userpass" : "token") : authReq;
```

したがって開発者のシェルに `KSQL_USERNAME` / `KSQL_PASSWORD` があると、
テストの設定は `tokenMap` しか持たないのに **`userpass` が選ばれ、
`X-Cybozu-API-Token` が付かない**。実測の失敗（トークンが `null`）と一致する。

**優先順位そのものは仕様どおり**（環境変数が設定ファイルより優先）。
**問題はテストが環境を遮断していないこと**だが、遮断するかどうかは §3 の判断による。

## 3. 方針（2026-08-04 オーナー判断）

**しくみは変えない。運用として記述する。**

テスト側に環境変数の隔離機構を足すことも検討したが、**採らない**。
認証の優先順位（CLI 引数 → 環境変数 → 設定ファイル）は**仕様どおり**であり、
テストは実際の CLI をそのまま駆動している。隔離機構は「正しい挙動をテストのために
覆う」形になり、テスト群への適用と保守も要る。

**やること**＝`README.md` の「ローカル開発」に、**テスト実行時は `KSQL_*` を外す**ことと、
**落ちたらまず `env | grep KSQL_` を見る**ことを書く。実装・テストは変更しない。

### 3.1 対象（実測 2026-08-04）

実装が読む環境変数は **`KSQL_*` が 32 個**あり、認証系は一部にすぎない。

```
KSQL_CONFIG / KSQL_PROFILE / KSQL_BASE_URL / KSQL_TOKEN / KSQL_TOKEN_MAP /
KSQL_AUTH / KSQL_USERNAME / KSQL_PASSWORD / KSQL_MAX_RECORDS / KSQL_ALLOW_DML /
KSQL_YES / KSQL_OUTPUT / KSQL_TIMEOUT / …（計 32）
```

**`KSQL_CONFIG`（設定ファイルのパス）や `KSQL_PROFILE` が残っていれば、テストは
別の設定を読んで通ったり落ちたりする。**認証系だけの問題ではない。
**`KINTONE_*` は kSQL が読んでいない**（このマシンにあるものは kintone MCP サーバー用）。

### 3.2 再検討の条件

- **同じ誤認が再発したとき**（今回は B114 のレビューで「B114 が壊した」と誤認しかけた）
- **開発者が増えたとき**——口伝と記述だけでは追いつかなくなる。そのときは
  `npm test` 側で `KSQL_*` を落とす形（テスト群へ個別適用しない中央 1 箇所）を検討する

## 4. 優先度

**中で起票したが、記述で閉じた。** 危険の本体は「**開発者の環境によっては赤が常態化し、
「またあれか」で無視されるようになる**」ことで、今回も B114 のレビューで「B114 が壊した」と
誤認しかけた。**その危険は、原因と確認手順が書かれていれば大きく下がる**（今回いちばん
時間を食ったのは切り分けであって、修正ではない）。

## 5. 確認していない論点（本件とは別）

**設定ファイルに `tokenMap` があるとき、環境変数のパスワード認証を優先するのが
妥当かどうかは確認していない。** 優先順位（env > config）自体は一貫しているが、
「アプリごとのトークンを明示している設定」を環境変数が黙って上書きする形が
利用者の期待に合うかは別途の検討事項。**必要になったら測ってから判断する。**
