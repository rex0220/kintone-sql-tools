前回（[Claude Desktop に「会社別に売上を集計して」と頼むと kSQL MCP は何をするのか](https://qiita.com/rex0220/items/60f5ee4b22fb2f90dada)）では、AI が自然言語の依頼からアプリ構造を辿り、売上の在処を突き止めて段階的に集計する過程を追いました。そのとき AI は **「集計関数の引数に `CASE` は書けない」** という当時の制約にぶつかり、`SUM(CASE WHEN …)` を避けて **会社別集計と会社×フェーズ別集計を別々に取得し、後から統合** していました。

その制約は **v3.16.0（機能追加 B64）で解消** しました。本記事では、同じ「会社別に売上等の集計を」という依頼が、**条件付き集計 `SUM(CASE WHEN … END)` を使って、会社別表は 1 クエリ、全体サマリを加えても 2 クエリに収まる** ようになったことを、実データで示します。

対象は、会社名・商談フェーズ・売上を持つ案件アプリ APP4149 の 20 件です。前回記事を未読でも、以下ではこの 3 項目を会社別・フェーズ別に集計していると捉えれば読み進められます。

# 何が変わったか（B64）

kSQL では従来、集計関数の引数に書けるのは **フィールド・数値・算術式・関数呼び出し** までで、`CASE` 式は `ParseError` になっていました。

```sql
-- v3.15.0 まで: ParseError（算術式のオペランドに CASE は書けない）
SELECT SUM(CASE WHEN 商談フェーズ = '受注' THEN 売上 END) FROM APP4149
```

v3.16.0 からは、全 12 集計関数（`SUM` / `COUNT` / `AVG` / `MIN` / `MAX` / `GROUP_CONCAT` / 統計集約 / `MODE`）の引数に **`CASE` 式・`||` 連結・スカラー変数 `@var`** を書けます。SQL の定番イディオムである **条件付き集計（conditional aggregation）** がそのまま書けるようになりました。

```sql
-- v3.16.0 以降: そのまま通る
SELECT SUM(CASE WHEN 商談フェーズ = '受注' THEN 売上 ELSE 0 END) AS 受注済み売上
FROM APP4149
```

比較式そのもの（`SUM(売上 > 0)` など）は、kSQL に真偽値型が無いため引き続き非対応で、`CASE` で値を明示するよう案内されます。既存の算術式引数の挙動は変わりません（SemVer は minor）。

# 対応前 → 対応後の比較

## 対応前（v3.15.0・前回記事）

AI は「集計内 `CASE` は不可」と判断し、粒度を変えた **4 本のクエリ** を積み上げて、最後に人間が読める 1 枚の表に統合していました。

| # | 目的 | SQL（要約） |
|---|---|---|
| Q1 | 全体像 | `SELECT COUNT(*), SUM(売上), COUNT(DISTINCT 会社名) FROM APP4149` |
| Q2 | フェーズ別 | `SELECT 商談フェーズ, COUNT(*), SUM(売上) FROM APP4149 GROUP BY 商談フェーズ` |
| Q3 | 会社別 | `SELECT 会社名, COUNT(*), SUM(売上) AS 売上合計, ROUND(AVG(売上)) FROM APP4149 GROUP BY 会社名 ORDER BY 売上合計 DESC` |
| Q4 | 受注済み売上 | `SELECT 会社名, 商談フェーズ, COUNT(*), SUM(売上) FROM APP4149 GROUP BY 会社名, 商談フェーズ` |

「受注済み売上」は Q4（会社×フェーズ）のフェーズ＝受注の行を、AI が Q3（会社別）の結果へ後処理で統合して作っていました。

## 対応後（v3.16.0）

同じ「会社別・売上合計・受注済み売上・平均売上」の表が、**1 クエリ** で出ます。

```sql
SELECT
  会社名,
  COUNT(*) AS 案件数,
  SUM(売上) AS 売上合計,
  SUM(CASE WHEN 商談フェーズ = '受注' THEN 売上 ELSE 0 END) AS 受注済み売上,
  ROUND(AVG(売上)) AS 平均売上
FROM APP4149
GROUP BY 会社名
ORDER BY 売上合計 DESC
```

# 横持ち（ピボット）は B64 の本命

条件付き集計がいちばん効くのは、**カテゴリ別の値を列として横に並べる（ピボット）** 用途です。会社ごとにフェーズ別の売上を横持ちにすると、AI が段階集計で組み立てていた内訳が 1 クエリで出ます。

```sql
SELECT
  会社名,
  SUM(CASE WHEN 商談フェーズ = '受注'   THEN 売上 ELSE 0 END) AS 受注,
  SUM(CASE WHEN 商談フェーズ = '提案中' THEN 売上 ELSE 0 END) AS 提案中,
  SUM(CASE WHEN 商談フェーズ = '内示'   THEN 売上 ELSE 0 END) AS 内示,
  SUM(売上) AS 合計
FROM APP4149
GROUP BY 会社名
ORDER BY 合計 DESC
```

実行結果（実データ）:

| 会社名 | 受注 | 提案中 | 内示 | 合計 |
|---|--:|--:|--:|--:|
| 株式会社サイボウズ商事 | 8,100,000 | 12,600,000 | 0 | 20,700,000 |
| 株式会社キントーンシステムズ | 9,300,000 | 0 | 6,250,000 | 15,550,000 |
| 株式会社倉本インターナショナル | 7,100,000 | 0 | 6,500,000 | 13,600,000 |
| 篠村食品株式会社 | 4,200,000 | 4,850,000 | 0 | 9,050,000 |
| 株式会社テクノロジーサービス | 0 | 7,200,000 | 0 | 7,200,000 |
| 株式会社橘川ケミカル | 6,700,000 | 0 | 0 | 6,700,000 |

列ごとに合計すると、受注 40,800,000 / 提案中 28,250,000 / 内示 12,750,000、3 列の合計は 81,800,000 となり、前回記事のフェーズ別内訳と総売上に一致します。従来は AI がこの内訳を **会社×フェーズの縦持ち集計（Q4）から読み替えて** 作っていました。

# `COUNT(CASE …)` で条件付き件数も

`COUNT` に `CASE` を渡すと、**条件に一致した件数** を数えられます（`ELSE` を省略した `CASE` の非一致は `NULL` になり、`COUNT` は数えません）。全体サマリも 1 クエリで出ます。

```sql
SELECT
  COUNT(*) AS 総件数,
  SUM(売上) AS 総売上,
  SUM(CASE WHEN 商談フェーズ = '受注' THEN 売上 ELSE 0 END) AS 受注売上,
  COUNT(CASE WHEN 商談フェーズ = '受注'   THEN 1 END) AS 受注件数,
  COUNT(CASE WHEN 商談フェーズ = '提案中' THEN 1 END) AS 提案中件数,
  COUNT(CASE WHEN 商談フェーズ = '内示'   THEN 1 END) AS 内示件数
FROM APP4149
```

実行結果: 総件数 20 / 総売上 81,800,000 / 受注売上 40,800,000 / 受注件数 8 / 提案中件数 6 / 内示件数 2。

`COUNT(CASE WHEN p THEN 1 END)` は「条件に一致した件数」、`SUM(CASE WHEN p THEN 1 ELSE 0 END)` も同じ件数になります。`ELSE 0` を付けると非一致の行も 0 として集計に入る、という SQL 標準どおりの区別です。

# できること・できないこと

- **できる**: `SUM` / `COUNT` / `AVG` / `MIN` / `MAX` / `GROUP_CONCAT` / 統計集約 / `MODE` の引数に `CASE` 式・`||` 連結・スカラー変数 `@var`。`SUM((CASE …))` のように括弧で包んでも可。`HAVING SUM(CASE …) > n` も同じ書き方で通る。
- **できない（設計）**: 比較式そのものを集計値にする形（`SUM(売上 > 0)` など）。kSQL に真偽値型が無いためで、`SUM(CASE WHEN 売上 > 0 THEN 1 ELSE 0 END)` のように `CASE` で値を明示する。サブクエリ・集計の入れ子（`SUM(SUM(x))`）も従来どおり不可。
- **変わらない**: 既存の算術式引数（`SUM(売上)` / `SUM(ROUND(売上))` など）の結果・挙動。B64 は新しい書き方を追加し、既存の有効な集計 SQL の構文・挙動は変更しない設計です。

`CASE` の分岐が返す値の型（数値か文字列か）は `MIN` / `MAX` / `MODE` の比較順に反映され、条件にどのフィールドを使っても取得対象として正しく読み込まれます。混在・不明な型は安全側で文字列（コードポイント順）として扱います。

# AI はどうやって「書けるようになった」と気づくのか

前回、AI は `ksql_docs` で当時の方言仕様を確認し、標準 SQL では一般的な `SUM(CASE WHEN …)` を決め打ちせず、「集計内 `CASE` は不可」と **正しく** 判断していました。では今回、同じ AI が「今度は書ける」と認識を切り替えたのは、何を根拠にしているのでしょうか。

ポイントは、**AI は記憶や標準 SQL の常識で決め打ちしていない** ことです。kSQL MCP は、初めて使う文形式を `ksql_docs` で確認し、実行前には具体的な SQL を `ksql_validate` で検証して、**構文を発明しない** よう AI を促す設計になっています（サーバーの instructions で行動規範として与えています）。

認識を切り替えた実体は、**`ksql_validate` の応答そのものが変わったこと** です。まったく同じ SQL が、バージョンによって違う結果を返します。

```text
SELECT SUM(CASE WHEN 商談フェーズ='受注' THEN 売上 END) FROM APP4149

v3.15.0 → ParseError（算術式のオペランドに CASE は書けない）
v3.16.0 → ok（受理）
```

AI はこの `ok` を見て「構文・静的検証を通る書き方だ」と判断します（データ依存の実行時エラーまで保証するものではありません）。逆に比較式 `SUM(売上 > 0)` は v3.16.0 でも `ParseError` を返し、しかも **「CASE で値を明示してください。例: SUM(CASE WHEN amount > 0 THEN 1 ELSE 0 END)」** という誘導つきのエラーになるので、AI はそのまま正しい書き方へ乗り換えられます。

この「認識の切り替え」が成立するには、実は 2 つの更新が必要でした。

1. **本体（パーサ／エンジン）の変更（B64）** — `SUM(CASE WHEN …)` を実際に受理するようにした。これが無ければ validate は `ok` を返しません。
2. **デプロイ済み MCP サーバーの更新とクライアントの繋ぎ直し** — npm publish で `v3.16.0` を配布し、VSCode（や Claude Desktop）を再読み込みして新しいサーバーに接続し直す。クライアントが古いサーバーに繋いだままだと、AI は今も `ParseError` を見て「不可」と判断します（＝前回の記事の世界のまま）。

つまり、ドキュメントは書き方を知る入口ですが、方言の受理範囲はバージョンで変わります。接続中のサーバーがその SQL を今受理するかは、**その場の `ksql_validate` の応答が最も確実な根拠**です。言語リファレンスに構文が記載されていても、古い MCP サーバーへ接続したままなら validate は `ParseError` を返します。逆に、ドキュメントだけを読んで未検証の構文を実行せず、最後に validate で接続先の実装と一致していることを確かめるのが、この検証ループです。

これは姉妹記事の [AI は独自 SQL の構文を「発明」する](https://qiita.com/rex0220/items/4d9fc0ed48ebd5b32a7b) や [validate では捕まらない誤り](https://qiita.com/rex0220/items/7f229c87a20f2d45777c) と同じ構図です。ドキュメントや記憶に頼りきると方言で外すが、**「使う前に validate で確かめる」** という一手が、バージョンアップで広がった表現力にも AI を自然に追従させています。

# まとめ

- 前回、AI が「集計内 `CASE` は不可」と判断して **4 本のクエリに分けて統合** していた集計が、v3.16.0（B64）では **`SUM(CASE WHEN … END)` で 1〜2 クエリ** に収まる。
- とくに **会社 × フェーズの横持ちピボット** は条件付き集計の本命で、内訳表を 1 クエリで直接作れる。
- 比較式は引き続き `CASE` で明示する。既存の集計の挙動は不変（新しい書き方の追加のみ）。
- AI が「書けるようになった」と気づく最終的な根拠は、**その場の `ksql_validate` の応答**。本体の B64 対応に加え、MCP サーバーを新版に更新してクライアントを繋ぎ直すことで、AI の認識が切り替わる。

kSQL MCP は「SQL を書ける AI に kintone を触らせる」ためのツールですが、AI の書き方は、方言側の表現力が上がると自然に短くシンプルになっていきます。前回は制約を賢く回避する過程が見どころでしたが、今回はその回避が **そもそも要らなくなった** という更新でした。
