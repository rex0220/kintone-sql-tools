## 1. 対象（SQL:2023 SQL/PGQ）

既存テーブルを**ノード（VERTEX TABLES）/エッジ（EDGE TABLES）**として `CREATE PROPERTY GRAPH` で定義し、`GRAPH_TABLE(g MATCH <パターン> COLUMNS(...))` でアスキーアート記法の経路パターンを問い合わせる。

```sql
MATCH (a:Account)-[t:transfer]->(b:Account)              -- 1ホップ
MATCH (a)-[t1]->(b)-[t2]->(c)-[t3]->(a)                  -- 3ホップ循環（マネロン検出）
MATCH (a:Account)-[:transfer]->{1,3}(b:Account)          -- 可変長 1〜3 ホップ（到達可能性）
```

## 2. kintone/kSQL への適合

kintone は**関係が濃い**（ルックアップ・関連レコード・マスタ/明細・承認ルート・組織図・BOM・振込/フロー履歴）。ノード＝アプリ、エッジ＝2 つの外部キー（`Transfers.from_account`/`to_account` → `Accounts.account_id`）を持つアプリ、と自然に対応する。グラフパターンは kintone の実データと相性が良い。

## 3. 現状 kSQL で「できる/できない」（グラフ機能が埋める隙間）

| クエリ | 現状 kSQL | SQL/PGQ |
|---|---|---|
| 1ホップ結合 | JOIN（**単一等値のみ**）で可 | `MATCH (a)-[t]->(b)` |
| 固定 N ホップ | 連鎖 JOIN で**冗長だが可能な場合あり**（各 JOIN 単一等値・派生テーブル無し・自己結合の別名） | `MATCH (a)-[t1]->(b)-[t2]->(c)...` で 1 行 |
| 循環（→(a) で戻る） | 連鎖 JOIN＋等値条件で**理論上可だが極めて冗長**・派生テーブル制約で難 | `-[t3]->(a)` 1 行 |
| **可変長 `{1,3}`・到達可能性** | **不能**（`WITH RECURSIVE` なし・再帰/推移閉包を表現できない） | `-[:transfer]->{1,3}` |

→ **最大の固有価値＝可変長経路・到達可能性・循環検出**（現状 kSQL で表現不能 or 極めて冗長）。関係が濃い kintone で「不能→可能」を作る。

## 4. 実装の障害・コスト

1. **kintone にグラフエンジン/プッシュダウンなし**：全て**クライアント側**（該当アプリのノード/エッジを全件取得→JS でグラフ構築→パターン照合/走査）。kSQL の既存「全件取得して JS 処理」モデルの延長だが、**グラフ走査は JOIN より重い**。
2. **性能・データ量が本体リスク**：可変長走査は**組合せ爆発**し得る。振込ログのような大アプリでは全ノード/エッジ取得（500件/ページ・大規模は Cursor）＋メモリ内 BFS/DFS が高コスト。**境界（最大ノード/エッジ数・最大パス長）と fail-closed（無音の打ち切りをしない＝B1/B30 の原則）が必須**。
3. **実装規模が最大級**：`MATCH` の**新しい副言語**（ノード/エッジ/方向/ラベル/量指定子 `{m,n}`）＋プロパティグラフ定義＋**グラフ実行エンジン**（パターン照合・走査・COLUMNS 射影）。kSQL がこれまで検討した中で**最も大きい**（新クエリ文法＋グラフ計算基盤）。
4. **標準は新しい**：SQL/PGQ は SQL:2023 策定・主要 RDBMS のネイティブ完全実装は限定的（Oracle 先行）。標準自体は安定だが先進的。

## 5. 確定すべき設計論点

- **グラフ定義**：`CREATE PROPERTY GRAPH`（永続・保存クエリ的に定義を保持）か、`GRAPH_TABLE` 内**インライン定義**か。ノード/エッジのアプリ対応（KEY フィールド・SOURCE/DESTINATION KEY・LABEL・PROPERTIES）。論理アプリ参照（LAPP_）との整合。
- **MATCH サブセット**：v1 は固定長のみか・可変長 `{m,n}` を上限付きで入れるか・方向（`->`/`<-`/`-`）・複数ラベル・パターン内 WHERE。
- **取得/実行戦略**：関与アプリを**一時テーブル同様に全件実体化**→メモリ内グラフ。取得は既存 fetch（Cursor 含む）を流用。ノード/エッジ数の上限（`tempTableMaxRows` 相当）。
- **性能ガード**：最大ノード/エッジ・最大パス長・訪問数上限・**超過は fail-closed（planning/実行エラー）**。無音の部分結果を返さない。
- **SELECT 統合**：`FROM GRAPH_TABLE(...)` を既存 SELECT の FROM として扱う・COLUMNS の射影・後続 WHERE/ORDER BY/集約との合成。
- **面**：全面（CLI/MCP/プラグイン）で同一（engine 側・全件取得の既存モデル）。ただしプラグインの大規模走査は UX 上の注意。

## 6. 段階案（フェーズ分割）

- **Phase 1（MVP・固定長）**：`CREATE PROPERTY GRAPH`（or インライン）＋`GRAPH_TABLE MATCH` の**固定長パターン**（1〜数ホップ・循環 `->(a)`）＋COLUMNS。**連鎖 JOIN の簡潔化＋循環検出**を提供。境界・fail-closed 必須。→ 「循環検出（マネロン等）」の看板ユースケースをカバー。
- **Phase 2（可変長・到達可能性）**：`{m,n}` 上限付き走査（reachability）。**最大の固有価値だが最も重い**（走査・爆発対策）。
- **対象外/後回し**：上限なし可変長・最短経路・複雑な量指定子・巨大グラフ・書込み系（グラフ更新）。

## 7. 実需確認（2026-07-19・ユーザー回答）

1. **ユースケース**：**BOM/部品構成**・**取引フロー/循環検出**に関心（ただし「**まだ具体需要はない**」＝探索的）。
2. **規模**：**小（数千件以下）**。→ **全件取得＋メモリ走査が余裕**。**評価の最大リスク（性能・可変長の爆発）がほぼ消える**。
3. **固定長 vs 可変長**：**両方・段階的**（Phase1 固定長→Phase2 可変長）。BOM は本質的に可変長（Phase2）だが循環検出は Phase1 で可。
4. **面**：**CLI・プラグイン・MCP の全面**。→ グラフエンジンは**取得済みレコードへの純計算（engine 側）**なので、**面ごとの配管が不要で全面が自然に動く**（IMPORT と違い面依存プラグインが要らない＝大きな利点）。

### 判断への含意（2 大リスクが両方緩和）
- **性能リスク → 小規模で消える**：数千件なら全件取得＋メモリグラフは快適。可変長の爆発も小グラフでは実害小。
- **面リスク → engine 側で不要**：全面同一・配管なし（IMPORT の loader capability のような面別実装が不要）。
- **残るコスト＝実装規模**：新 `MATCH` 副言語＋グラフ実行エンジン。**正しさ/実現性のリスクではなく工数**（小規模・engine 側なので難所は減る）。
- **弱点＝需要が探索的**（具体業務での需要は未確定）。

## 8. 総合評価・提言

| 項目 | 評価 |
|---|---|
| 固有価値 | **高**：可変長/到達可能性/循環は現状**不能**。関係が濃い kintone で「不能→可能」。差別化大。 |
| 実装コスト | **最大級**：新 MATCH 副言語＋グラフ実行エンジン。 |
| 性能リスク | **高**：クライアント側全件取得＋メモリ走査・可変長は爆発。境界と fail-closed 必須。 |
| 標準成熟度 | 新しい（Oracle 先行）が安定。 |

**提言**：価値は高いが**規模・性能リスクが大きい単独テーマ**。着手するなら、
1. **§7 の実需確認**（多ホップ/循環/到達可能性の具体需要・対象グラフ規模）を先に。
2. 進めるなら**フェーズ分割で Phase 1（固定長・循環検出）を境界付き MVP** に。可変長（Phase 2）は性能設計を本体として別途。
3. **性能ガード（最大ノード/エッジ/パス長・fail-closed）を第一級の設計要件**に（kSQL の無音打ち切り禁止と整合）。
4. 固定長の一部は現状の連鎖 JOIN で代替可・**可変長/到達可能性には代替がない**ため、そこに実需があるかが着手判断の分かれ目。

**結論**：**条件付きで魅力的だが大規模**。

### §7 回答後の更新（2 大リスク緩和）
- 対象規模が**小（数千件以下）**＝**性能リスクがほぼ消滅**、全面 engine 側＝**面配管不要**。→ 評価当初より**技術的に一段リスクが下がった**（残るは実装工数）。
- ただし**需要は探索的**（BOM/循環に関心・具体業務需要は未確定）。BOM は本質的に可変長（Phase2）、循環検出は Phase1。

**提言（更新）**：小規模・engine 側で**Phase1（固定長 MATCH＋循環検出・境界付き）は技術的に無理のない MVP**。ただし需要が探索的で実装が大きいので、
- **(A)** Phase1 の仕様（R1）を書いて**スコープ/工数を具体化**し、実装可否を判断（＝設計は進めるが実装は需要と工数を見て決める）。
- **(B)** 具体需要（実業務での多ホップ/循環/BOM）が出るまで**評価のまま保留**。

engine 側・小規模で難所が少ないため、**(A)（Phase1 の仕様化まで）を進めて実装判断の材料にする**のが妥当。可変長（Phase2・BOM 本命）は性能設計を本体に別途。
