# B91 MCP にプラグイン互換モードを追加する（環境変数）

- 起票: 2026-07-29
- ステータス: ❌ **クローズ（Pro が取り下げ・2026-07-29）**。→ [確認文](ksql_pro_inquiry_b91_20260729.md) / §11
- 出典: [Pro からの連絡 2026-07-29](../../../ksql-dashboard-pro/docs/internal/kSQLエンジンへの連絡-20260729-送付版.md) 依頼③（継続）
- 関連: [B89 explainQuery バッチ](ksql_b89_library_explain_batch_issue.md) / [B68](ksql_b68_engine_library_readonly_impl_plan.md)

## 1. 依頼内容

環境変数（例 `KSQL_PLUGIN_MODE=1`）で、`ksql_validate` / `ksql_explain` / `ksql_query` に
**`runQuery` と同じ許可リスト**を適用してほしい。

**ツール引数ではなく環境変数**を希望する理由は、**引数だと AI が渡し忘れる**ため。
環境変数なら `.mcp.json` に探索用と互換モード用の 2 エントリを登録して併存できる。

## 2. 解きたい問題

**AI が MCP で書いた SQL が、CLI / MCP 専用構文を含んでいても MCP 上では通ってしまう。**
それをプラグイン（Pro のペイン）へ持っていくと動かない。

## 3. Pro が優先度を下げた理由

**設定画面の構文チェックが `explainQuery`（＝プラグインの guard 経路）を通す**ため、
CLI / MCP 専用構文は**ペインを開いた時点で既に弾かれる**。

本件が埋めるのは
**「AI が MCP で書いた SQL が、設定画面を開くまで誤りと分からない」という時間差だけ**である。

## 4. B89 との関係

> **B89 が実現すると本件の価値も上がる。**
> B89 でバッチが検証できるようになれば、互換モードでも同じ判定が返せるため（Pro 談）。

**先に B89 を片付けるべき**で、本件を単独で進める理由は無い。

## 5. 検討事項

- **環境変数という形が妥当か。**MCP サーバーの設定は `.mcp.json` に集約されており、
  プロファイル指定は既にツール引数（`profile`）で行っている。
  **面ごとの許可集合を環境変数で切り替える前例が無い**
- **「`runQuery` と同じ許可リスト」の定義。**B68 で `isReadOnlyStatement()` へ一本化済みなので、
  参照先は明確。ただし **`runQuery` は行を返す文に限られる**（`isRowReturningReadOnlyStatement`）ため、
  Pro が実際に欲しいのが `runQuery` 相当か `runBatch` 相当かを確認する必要がある
  （**Pro は `runBatch` を採用済み**なので、後者の可能性が高い）
  → **【Pro 回答 2026-07-29】`runBatch` 相当が正しい。**「こちらの書き間違いでした」と訂正あり。
  **`runQuery` に揃えると `CREATE TEMP TABLE` や `SET` が弾かれ、互換モードのほうが本番より狭くなるという逆転が起きる**（Pro 談）。
- **モードが増えることの保守コスト。**MCP の許可集合が 2 通りになると、
  B68 で作った parity テストの対象も 2 通りになる

## 6. 規模

**未見積もり。**§5 の残り 2 点（環境変数という形・parity テストの保守コスト）を確定してから。
**許可集合は `runBatch` 相当で確定済み。**B89 の完了後に再評価する。

## 7. 優先度の根拠

**Pro 自身が優先度を下げており、代替手段（設定画面が弾く）が機能している。**
埋まるのは時間差だけで、**誤った結果が出る類ではない。**

**B89 の完了後に、Pro が実際に欲しい許可集合を確認してから再評価する。**

## 8. 再評価（2026-07-29・v3.33.0 時点）

**保留の条件だった「B89 の完了」が満たされたので測り直した。**

### 8.1 受理集合の差は **5 形だけ**（実測）

**両方のガードに同じ SQL を通した。**手で数えていない。

| 形 | MCP `ksql_query` | engine lib `runBatch` |
|---|---|---|
| `SELECT` / `WITH` / `UNION` / `SHOW APPS` / `DESCRIBE` | ✅ | ✅ |
| `CREATE TEMP TABLE` / `SET` / `ASSERT` / 先頭 `VALIDATE` | ✅ | ✅ |
| `EXPLAIN SELECT` | ✅ | ✅ |
| **`EXPLAIN UPDATE` / `DELETE` / `INSERT` / `UPSERT`** | ✅ | ❌ |
| **`UPDATE` / `INSERT` / `UPSERT ... VALIDATE ONLY`** | ✅ | ❌ |
| **`IMPORT`** | ✅ | ❌ |
| `UPDATE` / `DELETE`（書き込み） | ❌ | ❌ |

**差は 5 形。すべて「DML 型だが書き込まない検証系」である。**
**書き込む DML は両方が拒否する**ので、**危険な差ではない。**

### 8.2 **この差は意図的である**（偶然のずれではない）

- **engine ライブラリは「read-only が契約」**であり、**文の型で切っている**
  （書き込むかどうかではなく `isDmlType`）。**B89 が `EXPLAIN <DML>` を塞いだのは、
  まさにこの線を引き直したから**である（v3.31.0）
- **MCP は対話的な道具**であり、**「DML を実行前に検証する」ことが中核の使い方**
  （`ksql_validate` → `VALIDATE ONLY` → `ksql_mutate` という手順を server instructions が案内している）

**つまり「MCP を engine ライブラリに合わせる」は、MCP の意図的な機能を取り上げることになる。**
**互換モードが「純加法」ではないことを意味する。**

### 8.3 B89 は本件の価値を**上げていない**（起票時の見込みと逆）

起票時は「B89 が実現すると本件の価値も上がる」（Pro 談）としていた。

**実際には B89 は `runBatch` を**厳しく**した**（`EXPLAIN <DML>` を拒否）。
**差は縮まらず、1 形増えた。**

### 8.4 Pro の用途で踏むか

**踏みにくい。**

| 差分の形 | ダッシュボードのペインで書くか |
|---|---|
| `IMPORT` | **書かない**（inline sources が要る） |
| `EXPLAIN <DML>` | **書かない** |
| `UPDATE / INSERT / UPSERT ... VALIDATE ONLY` | **考えにくい**。データ品質ペインは**先頭 `VALIDATE APPn`** で書け、**それは両方が受理する** |

**Pro が本当に困る形は、実質的に残っていない。**

## 9. 案 D（推奨）— **モードではなく `ksql_validate` の応答に可搬性を出す**

**Pro が env var を望んだ理由は「引数だと AI が渡し忘れる」だった。**
**応答フィールドなら渡し忘れが原理的に起きない。**

`ksql_validate` は**既に同じ形のフラグを返している。**

```ts
canRunWithQueryTool: analysis.isReadOnlyBatch,
requiresMutationTool: analysis.containsDml,
```

**ここへ 1 つ足すだけで済む**（名前は要検討）。

```ts
canRunWithEngineLibrary: <runBatch の受理集合に収まるか>,
```

### 9.1 案 A（環境変数モード）より優れている点

| | 案 A（env var モード） | **案 D（可搬性フラグ）** |
|---|---|---|
| AI の渡し忘れ | 起きない（env var） | **起きない**（応答） |
| MCP の機能 | **取り上げる**（検証系が使えなくなる） | **そのまま** |
| 許可集合 | **2 通りになる** | **1 通りのまま** |
| B68 の parity テスト | **対象が 2 倍** | **不変** |
| `.mcp.json` | **2 エントリ登録が必要** | **不要** |
| 気づくタイミング | 実行時に弾かれる | **`ksql_validate` の時点**（より早い） |

**案 D のほうが早く気づける。**`ksql_validate` は**実行前に呼ぶ**ものであり、
**MCP の server instructions が「実行前に `ksql_validate` を使え」と案内している。**

### 9.2 案 D の注意点

- **判定を新規に書かないこと。**`assertRunBatchStatement` を**そのまま呼ぶ**
  （B97 の教訓＝新しい判定は silent wrong result の温床）
- **engine ライブラリの内部関数を MCP から参照する形になる。**
  **bundle-guard（engine bundle に MCP を混ぜない）と逆方向なので、依存の向きを確認すること**
- **公開面の変更**＝`ksql_validate` の応答に純加法。**MCP の tool 出力は snapshot 対象か要確認**

### 9.3 規模（暫定）

**0.5 人日**と見る。§9.2 の依存の向きが問題なければ浅い。

## 11. クローズ（2026-07-29・Pro が取り下げ）

**Pro が SQL 資産 83 本を機械的に監査し、該当 0 本だった。**

| 形 | 該当 |
|---|---:|
| `IMPORT CSV` / `IMPORT JSON` | **0 本** |
| DML の `VALIDATE ONLY` | **0 本** |
| `EXPLAIN <DML>` | **0 本** |
| 書き込む DML | **0 本** |
| （参考）先頭 `VALIDATE APPn`＝両方が受理 | 1 本 |
| （参考）`CREATE TEMP TABLE`＝両方が受理 | 2 本 |

対象: サンプル設定 JSON のペイン SQL / レシピ集・Qiita 記事・設定ファイル仕様・
AI 設定オーサリング手順の SQL コードブロック / 組み込みテンプレート。

### 11.1 **構造的に踏みにくい**（Pro の整理）

> **5 形はすべて「書き込みを伴う作業の下準備」**です。
> ダッシュボードのペインは**画面に何かを表示する**ためのもので、
> **書き込みの検証結果を表示したい場面が（データ品質ペインを除いて）ありません。**
> そのデータ品質ペインも、先頭 `VALIDATE` という**両方が受理する書き方**が用意されています。
> **つまり構造的に踏みにくい**のであって、たまたま踏んでいないわけではない。

### 11.2 決め手は §2（互換モードが純加法にならない）

> **依頼したときのこちらの前提が間違っていました。**
> 「MCP を engine ライブラリに合わせる」ことを**純粋な絞り込み**だと思っていましたが、
> **MCP の中核機能を削ることだった**わけです。

### 11.3 【申し送り】案 D を実装する場合の穴（Pro §2.1・要望ではなく参考）

**`ksql_validate` を呼ばずに `ksql_query` を直接叩く経路が残る。**

> MCP の案内は「実行前に `ksql_validate`」ですが、`ksql_query` は単体でも動くため、
> **AI が検証を飛ばすと受け取れません。**
> **同じフィールドを `ksql_query` / `ksql_explain` の応答にも載せる**と、この経路も塞がります。
> **「渡し忘れ」が「呼び忘れ」に形を変えただけ**なので。

**この指摘は正しい。**§9 の案 D を実装するなら、**`ksql_validate` だけでは足りない。**

### 11.4 再提起の条件

**AI が書いた SQL がペインで動かなかった実例が出たら。**
そのときは**モードではなく `ksql_validate` のフラグ**で、とのこと。

**Pro は監査を機械的に回せる形にしており、SQL 資産が増えたときに定期的に測り直す。**
