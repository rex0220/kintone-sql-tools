# B144 サブテーブル仮想テーブルの `EXPLAIN` が、実行しない押し下げを表示する

- 状態: 🐞 **起票・原因特定まで完了。修正は未着手**（2026-08-06）
- 種別: 課題（`EXPLAIN` が実行と食い違う）
- 優先: **中**（`EXPLAIN` の契約が破れており、`maxRecords` の見積りが外れる）
- 発見: 利用者からの指摘（`SELECT COUNT(*) FROM APP4233$テーブル` が全件取得になるのに記載が無い）

## 1. 何が起きているか

**`EXPLAIN` は親項目条件を押し下げると表示するが、実行は押し下げない。**

実測（v3.54.4・APP4233＝親 14 レコード / 明細 24 行）:

| クエリ | `EXPLAIN` | 実行（`maxRecords=3`） |
|---|---|---|
| `SELECT $id FROM APP4233 WHERE $id IN (1,2)` | `EXACT` / `$id in (1,2)` | **成功**（2 件） |
| `SELECT _pid FROM APP4233$テーブル WHERE _p.$id IN (1,2)` | **`EXACT` / `$id in (1,2)`** | **`FetchAllLimitError`** |
| `SELECT _pid FROM APP4233$テーブル WHERE _p.数値 = 100` | **`EXACT` / `数値 = 100`** | **`FetchAllLimitError`** |
| `SELECT COUNT(*) FROM APP4233$テーブル WHERE _pid = 1` | `ALL` / `(全件取得)` | 全件取得（**一致**） |

**`_p.<親項目>` の形だけが食い違う。** `EXPLAIN` は `fetch: EXACT` と表示するのに、
**実行は親レコードを全件取得する**（`maxRecords=20` にすると同じクエリが 5 行返る＝
14 レコードを取りに行っている）。

`_pid`（システム列）は `EXPLAIN` も `ALL` と表示するので**一致している**
（ただし押し下げられるはずの情報を捨てている。→ §4）。

## 2. なぜ重いか

**`EXPLAIN` の存在意義が「実行前に取得量を知る」ことなので、そこが外れると使えない。**

- **`maxRecords` の見積りが外れる。** `EXACT` を見て「2 件しか取らない」と判断すると、
  実際は全件取得で上限エラーになる
- **依頼元（`ksql-analytics`）は「実行前に `ksql_explain` まで通す」運用**
  （→ [B143](ksql_b143_explain_warnings_issue.md)）。**この形をそのまま踏む**
- **`EXPLAIN` は「安全側に倒す」と文書で宣言している**
  （「分類に迷いがある場合は、より多く取得する側を表示します」）。
  **本件はその逆で、実際より少なく表示している**

**結果は正しい**（取得後にローカル評価するため）。**外れるのは取得量の予測だけ。**

## 3. 原因

[`src/execute.ts`](../../src/execute.ts) の `fetchTableRecordsForFullScan`。

```ts
// サブテーブル仮想テーブルは親レコードを取得して展開する
const parentQuery = isMainTable ? "" : "";
```

**三項演算子の両辺が空文字**で、**サブテーブル経路は query を組み立てていない**。
親テーブル経路（同じ関数の上側）は `selectToFetchAllParams` と押し下げ条件から
query を作っているので、**片側だけが未実装のまま残っている**。

`git log -L` で追うと**初版（公開リポジトリ作成時）から同じ形**で、
**途中で壊れたのではなく、最初から placeholder**だった。

**`EXPLAIN` 側は別経路で計画を組む**ため、押し下げ可能と判定して表示している。
**「計画を作る側」と「実行する側」が別実装で、後者だけが取り残されている。**

## 4. 案

- **案 A＝実行側を計画に合わせる**（`parentQuery` を実際に組み立てる）。
  **`EXPLAIN` の表示が正しくなり、取得量も減る。** 本命。
  **確認が要る**＝`stmt.where` には `_pid` / `_rid` / `_idx` / サブテーブル項目の条件も
  混ざるので、**親アプリの query へ変換してよい leaf だけ**を選ぶ必要がある
  （`_p.<親項目>` と、`_pid` → `$id` は安全。**サブテーブル項目の条件は行単位なので
  親の絞り込みには使えるが superset**）。
- **案 B＝`EXPLAIN` を実行に合わせる**（サブテーブルでは常に `ALL` と表示）。
  **安価で、少なくとも嘘はつかなくなる**。取得量は減らない。
- **案 C＝案 B を先に出し、案 A を別途**。**`EXPLAIN` の契約破れだけ先に止める**。

**見立て＝案 C。** `EXPLAIN` が実際より少なく表示するのは
**「安全側に倒す」という明文の契約に反する**ので、**そこだけ先に直す価値がある**。
案 A は取得量が減る改善で、**変換してよい leaf の選別**という設計が要る。

**`_pid` → `$id` の押し下げ**（§1 の 4 行目）も案 A に含める。
**特定の親レコードの明細だけを見る形は素直に書かれるはず**で、
現状は 1 レコードぶんが欲しいだけでも全件取得になる。

## 5. 文書側（v3.54.5 で対応予定・未リリース）

利用者の指摘そのもの＝**サブテーブルの `COUNT(*)` が全件取得になることが書かれていなかった**。

- §19 の冒頭に対比つきで明示した（`COUNT(*)` だけでも `WHERE` があっても全件取得）
- `fetch:` の `COUNT_ONLY` の行に「**サブテーブル仮想テーブルの `COUNT(*)` はこれになりません**」を追記

**`totalCount` は親レコードの件数**で、**サブテーブル行を数える手段が API に無い**。
**行はレコードを取得してから展開する**ため、件数を知るだけでも全件が要る。
**この事実自体は案 A でも変わらない**（`WHERE` で親を絞れる場合に取得量が減るだけ）。

## 6. 次に開くとき必要なもの

- **`EXPLAIN` 側でサブテーブルの計画を組んでいる箇所**（実行側と別実装になっている位置）
- **`stmt.where` から親 query へ変換してよい leaf の判定**（既存の
  `whereToKintone` / 押し下げ判定を再利用できるか）
- サブテーブル項目の条件を **superset prefilter** として使えるか
  （使えるなら `relation: superset` で表示する）
