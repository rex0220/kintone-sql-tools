# 本文（送付版）

## 【返信】K-87 — 仕組みは開けられます。ただし**論理名は ASCII 限定**で、例の日本語名は使えません

**ご依頼の筋は良いです。**挙げられた懸念 3 点は、エンジンの解決機構が既に満たしています。

| ご懸念 | エンジンの機構 |
|---|---|
| 文字列リテラル内の誤置換 | **起きません**。解決は字句認識つきの前処理で、`'文字列'`（`''` エスケープ対応）・バッククォート識別子・コメントを読み飛ばします |
| エラー表示が物理番号になる | **併記です**＝`LAPP_ORDERS -> APP1234@prod` の形で論理名と物理番号を両方出します |
| 字句規則の二重管理 | **エンジン側に一本化できます** |

**ただし 1 点、実測して分かった重要な事実があります。**

## 1. ⚠ **論理名は ASCII 限定です — 例に書かれた日本語名は現行構文で使えません**

**名前規則＝`[A-Z][A-Z0-9_]{0,63}`・大小文字を区別しない・ASCII のみ**です
（言語リファレンス §1「CLI / MCP 拡張: 論理アプリ参照」に記載）。

**ご依頼の例をそのまま実測しました。**

```
SELECT * FROM LAPP_TEST      → PARSE_ERROR（現行の engine ライブラリ。想定どおり）
SELECT * FROM LAPP_案件管理  → PARSE_ERROR（「案」が名前の開始文字ではないため、
                                論理トークンとして認識されません）
```

**つまり「受け口を開けるだけ」では、`LAPP_案件管理` は動きません。**
**`LAPP_ANKEN` のような ASCII 名に寄せていただく必要があります。**

**一方、そちらのフォールバック（テキスト置換）は日本語名を扱えます。**
**ここが今回の判断の分かれ目です。**

### 1.1 お聞きしたいこと

**ASCII の論理名で足りますか。**

| そちらの要件 | こちらの対応 |
|---|---|
| **ASCII 名で足りる** | **受け口の追加は現実的**です（案 A・下記 §3） |
| **日本語名が必須** | **構文拡張を含む別の大きさの課題**になります（CLI / MCP も同時に広げるため。名前の文字種・正規化・識別子境界の設計が要ります） |

**設定 UI で論理名を入力させる際の利用者体験**（日本語アプリ名をそのまま
論理名にしたいか、英字コードを振らせるか）が判断材料になると思います。

---

## 2. ご質問への答え（すべて実測）

1. **未定義の論理名** → `ArgumentError` の分類で、**名前を含む文言**です。
   `logical app LAPP_ORDERS@dev is not defined.` の形なので、構文チェックにそのまま出せます
2. **文字種** → **§1 のとおり ASCII `[A-Z][A-Z0-9_]{0,63}`・大小無視・日本語不可**。
   記載場所は言語リファレンス §1「CLI / MCP 拡張: 論理アプリ参照 `LAPP_<NAME>`」です
3. **表示** → 診断は**併記**（`LAPP_ORDERS -> APP1234@prod`）。engine ライブラリへ
   対応する場合も同じ形を配線する想定です。`EXPLAIN` の計画本文は解決後の物理番号ですが、
   併記の対応表が付きます
4. **渡し方** → **バッチ単位のオプション（`variables` と同じ渡し方）で問題ありません**。
   ご提案の `logicalApps: Record<string, number>` の形が自然です

### 2.1 実装する場合の補足

- **`@profile` 構文（`LAPP_ORDERS@prod`）はブラウザに profile の概念が無いため、
  明確なエラーで拒否する**想定です。マッピングは渡された 1 面だけです
- 解決機構は Node 層にあるため、**ブラウザ bundle へ入れる分離作業**が発生します
  （公開 package のゼロ依存は維持します）
