# B106 テストスイートの監査 — 無駄・重複・意味のないテストを整理できるか

- 起票: 2026-07-31
- ステータス: ❌ **クローズ（整理しない・2026-07-31 オーナー判断）**＝**測った結果、消してよいものが実質ゼロ**
- 出典: オーナーの問い「テスト件数が多くなっている。無駄なテスト、重複したテスト、意味のないテストを整理できるか？」
- 関連: [B104 構文ブロックの乖離検知（クローズ）](ksql_b104_syntax_block_drift_issue.md)（同じ「測って価値を判断した」形）

## 1. 問い

**jest の報告が 5,052 件（201 suites）まで増えた。整理できるか。**

## 2. 静的監査（2026-07-31 実測）

### 2.1 件数の内訳 — **数字の約半分はパラメータ行**

| | |
|---|---|
| 書かれた `test()` / `it()` ブロック | **2,376 個** |
| jest が報告する件数 | 5,052 件 |
| 差分 約 2,600 件 | **`test.each` のパラメータ行の展開**（132 ファイルで使用） |

**パラメータ行は同じコードを表のデータで回すだけで、記述・保守コストは 1 行分。**
**5,052 という数字自体が、実態より大きく見えている。**

### 2.2 定番の「無駄」はゼロ

| 検査 | 結果 |
|---|---|
| `skip` / `xit` / `xdescribe` / `only` | **0** |
| 同一ファイル内の同名重複タイトル | **0** |
| ファイルを跨ぐ同名タイトル | **4**（lexer / parser など層が違う別契約。重複ではない） |
| 同じ SQL 文字列の共有 | 最大 11 ファイルだが **fixture の共有**で、検査内容は層ごとに別 |

### 2.3 規模と増加ペース

| | |
|---|---|
| テストコード | 56,097 行（201 ファイル） |
| 実装コード | 47,963 行 |
| 比率 | **1.17 倍**（fail-closed を旨とするエンジンとして過大ではない） |
| 増加 | v3.31.0 → v3.35.0 で **+64 記述**（1 リリースあたり約 13） |
| B 番号付きファイル | **66 / 201**＝**過去の決定を固定する回帰契約** |

## 3. 実行時間

**開発者が体験する `npm test` は壁時計 約 50 秒＋subprocess e2e 約 19 秒。**

**重い suite の順位**（3 回の計測で安定。**絶対値は計測方法の汚染があり順位のみ信頼**——
うち 2 回はフル実行が重なって競合し、素の `npx jest` は `npm test` より大きく出る）:

| 順位 | suite | 重い理由 |
|---|---|---|
| 1 | `evalFunc.surrogate`（2 位の約 2 倍） | **総当たり性質検査**＝サロゲートペア入り文字列 × 全開始位置 × 全長を参照実装と突き合わせ |
| 2–5 | `mcp/tools`・`metadataTools`・`docsResources` | **実際に MCP サーバーを組み立てて繋ぐ**統合テスト |
| 上位常連 | `execute`・`executeBatch`・`explain`・B 番号統合系 | エンジンのフルパイプライン実行 |

**「無駄に重い」ものは見つからなかった。重い理由がすべて説明できる。**

## 4. 判断 — **整理しない**

- **消してよいもの（dead・重複・無意味）が実質ゼロ**だった
- **整理で得られるのは「数字が小さくなること」だけ**で、失うのは決定の記録。
  この repo ではテストが仕様書を兼ねる（B65 allowlist・語数予算・B94/B97/B98 の fail-closed 契約…）
- **実行時間を縮めたい場合も削除は効かない。**効くのは surrogate の総当たりを
  普段サンプル・リリース時フル網羅に分けることだが、**「網羅が常時走っている」保証を失う**。
  サロゲート境界は実際に踏んできた領域であり、壁時計 約 70 秒はこの安全網の対価として妥当

## 5. 再起票の条件

1. **実行時間が開発を妨げる水準になったとき**（目安: `npm test` の壁時計が数分に達する）
   → まず surrogate と MCP 統合系の分割を検討する
2. **本物の重複の実例が出たとき**（同じ層で同じ契約を 2 箇所が固定している、が具体で示せたとき）
3. **mutation 監査に費用を払う判断をしたとき**＝「このテストを消して実装に変異を入れても
   他が捕まえるか」を機械で確かめる。安全に削る唯一の方法だが、費用が大きい

## 6. 対象外

| | 理由 |
|---|---|
| `test.each` の行数削減 | **1 行 = 1 ケースで既に最小**。表を削るのは網羅を削ること |
| 層を跨ぐ「見た目の重複」の統合 | **層ごとに別契約**（lexer / parser / capability / execute / EXPLAIN / smoke）。統合すると壊れた層が分からなくなる |
| snapshot 22 件 | 意図的な検知装置。B81 と同じ扱い |
