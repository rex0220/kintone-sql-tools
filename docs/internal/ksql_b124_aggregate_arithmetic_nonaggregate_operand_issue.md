# B124 集計算術式に非集計オペランド（`GROUP BY` 列・`@変数`）を書けない

- 起票: 2026-08-05
- ステータス: 📝 **評価（方向判断待ち）**。**実測で射程が広がった**＝`GROUP BY` 列だけでなく **`@変数` も拒否**される。新しい表現力ではなく**標準 SQL 互換と書きやすさ**が価値で、既存の回避策（`SUM(a * 単価)`）は**グループ内一定なら厳密に等価**。段階案 A1（`@変数`）/ A2（`GROUP BY` キー）に分割可能
- 出典: `ksql-analytics` の在庫分析セッションで AI が遭遇（2026-08-05）。在庫金額 = 現在庫 × 仕入価格 を素直に書いて `ParseError`
- 関連: [B120](ksql_b120_aggregate_position_diagnostics_issue.md)（位置・トークン診断。**これが効いて 1 回で直せた**）/
  [B122](ksql_b122_having_aggregate_expression_issue.md)（`HAVING` の集計式。**同じ式を `HAVING` に書く経路**）/
  [B64](ksql_b64_aggregate_case_expression_spec.md)（集計引数の `CASE`）/
  集計算術式 alias 消失バグ（`parseAggregateColumn` の `AS` 非消費ヘルパー化。**同じ関数を触る**）

## 1. 症状（実測 2026-08-05・v3.44.0・MCP `ksql_validate`）

集計算術式のオペランドは**集計関数・数値リテラル・括弧・単項マイナス**のみ。それ以外は `ParseError`。

| SQL（`... FROM APP4229 GROUP BY 分類`） | 結果 |
|---|---|
| `SUM(仕入価格) * 2 AS a` | ✅ 通る |
| `SUM(仕入価格) * 分類 AS a` | ❌ `集計算術式には集計関数または数値が必要です（位置 23、トークン: 「分類」）` |
| `SET @r = 2; ... SUM(仕入価格) * @r AS a` | ❌ `集計算術式には集計関数または数値が必要です（位置 35、トークン: 「@r」）` |

**`@変数` も拒否される**のは起票時に想定していなかった点。`@変数` は**グループ内で一定であることが構造から保証される**ので、グループキー判定を要しない最も安全な部分集合。

### 出典での形

```sql
-- 書きたかった形（GROUP BY に m.仕入価格 を含んでいる）
SUM(t.個数_在庫計算用) * m.仕入価格 AS 在庫金額
→ ParseError: 集計算術式には集計関数または数値が必要です（位置 144、トークン: 「m」）

-- 回避した形
SUM(t.個数_在庫計算用 * m.仕入価格) AS 在庫金額
```

## 2. なぜ重いか / 重くないか

**重くない理由（先に書く）**:

- **エラーで止まる。** 誤った値は返していない
- **回避策が厳密に等価。** `m.仕入価格` が `GROUP BY` キーならグループ内で定数なので、
  `SUM(a) * 単価` と `SUM(a * 単価)` は同じ値になる。**新しい表現力は増えない**
- B120 の位置・トークン診断が効き、出典セッションでも**1 回で直せている**

**それでも起票する理由**:

- **標準 SQL では当然書ける形**で、経験のある利用者ほど先にこちらを書く
- **`GROUP BY` に含めているのに拒否される**ため、利用者から見ると理由が分からない
  （「集計と非集計は混ぜられない」の一般則は知っていても、グループキーは例外のはず、と考える）
- **制約が言語リファレンスに 1 行も書かれていない**（§8 を grep しても該当なし）。
  エラーは「何が」を教えるが「なぜ」と「どう書くか」を教えない
- `@変数` の拒否は**回避策が自明でない**（`SUM(a * @r)` は書けるが、
  `COUNT(*) * @r` は `SUM(@r)` に読み替える必要があり、直感的でない）

## 3. 原因（特定済み）

```ts
// src/parser/parser.ts — 集計算術式の一次式: 集計関数 / 数値リテラル / 括弧
private parseAggPrimary(): AggOperand {
  if (this.consume(TokenKind.LPAREN)) { ... }          // 括弧
  if (this.peek().kind === TokenKind.MINUS) { ... }    // 単項マイナス
  if (this.peek().kind === TokenKind.NUMBER) { ... }   // 数値リテラル
  const aggFunc = this.tryAggregateFunc();
  if (aggFunc !== null) return this.parseAggregateRef(aggFunc);
  throw new ParseError("集計算術式には集計関数または数値が必要です", this.peek());
}
```

意図的な fail-closed（非集計列を混ぜると意味が定義できないため）で、**バグではなく仕様**。
問題は**安全な部分集合まで一律に落としている**こと。

## 4. 対応案

### 案 A1: `@変数` を許可する（安い・独立して出荷可）

`@変数` は文の実行前に解決されるスカラーで、**グループ内で一定であることが構造から保証**される。
グループキー判定も機能従属性の解析も要らない。`parseAggPrimary` に変数トークンを 1 つ足すだけ。

### 案 A2: `GROUP BY` キーであるフィールド参照を許可する（本命）

`SUM(a) * m.仕入価格` を、`m.仕入価格` が**その SELECT の `GROUP BY` キーに含まれる場合に限り**許可する。

- **fail-closed を維持する**: `GROUP BY` に無いフィールドは**従来どおり拒否**。
  機能従属性（主キーだから一意に決まる等）の推論は**しない**——推論を入れると
  「静かに間違う」帯域が広がる
- **`GROUP BY` が無い SELECT では常に拒否**（グループが 1 つでもキーが無いため）
- 評価はグループ出力時。グループキーの値はその時点で確定している
- **空セルは既存規則どおり 0**（`LEFT JOIN` の null 拡張で 0 になるのは現状と同じ）

### 案 C（どの案でも必須）: 言語リファレンス §8 に制約と回避形を書く

現在どこにも書かれていない。案 B を選ぶ場合はこれが唯一の対応になる。

```markdown
集計を含む算術式の被演算子は、集計関数か数値リテラルだけです。
`GROUP BY` に含まれる列でも直接は掛けられません（`SUM(a) * 単価` は不可）。
グループ内で値が一定なら `SUM(a * 単価)` と内側に入れてください（結果は同じです）。
```

### 案 B: 何もしない（案 C の文書追記のみ）

`SUM(a * 単価)` が厳密に等価である以上、これも合理的な選択。

**見立て**: **まず案 C（文書 2 行）**。次に **A1（`@変数`）は安いので単独出荷してよい**。
**A2 は「標準 SQL 互換」以上の価値が無い**ため、実需（他 RDB からの移植で実際に困った例）が
出てからが妥当。**A2 の費用は実装よりも受入条件側**にある（§5 の回帰 1・2）。

## 5. 受入条件（A1 / A2 を実装する場合）

| SQL | 期待 |
|---|---|
| `SET @r = 2; SELECT 分類, SUM(仕入価格) * @r FROM APP4229 GROUP BY 分類` | ✅ A1 |
| `SELECT 分類, SUM(仕入価格) * 分類 FROM APP4229 GROUP BY 分類` | ✅ A2（分類は `GROUP BY` キー） |
| `SELECT 分類, SUM(仕入価格) * 製品名 FROM APP4229 GROUP BY 分類` | ❌ **ParseError / 静的エラー**（`GROUP BY` に無い） |
| `SELECT SUM(仕入価格) * 分類 FROM APP4229`（`GROUP BY` なし） | ❌ エラー |
| `SELECT m.仕入価格, SUM(t.個数_在庫計算用) * m.仕入価格 FROM ... GROUP BY m.仕入価格` | ✅ かつ `SUM(t.個数_在庫計算用 * m.仕入価格)` と**同値**であること |

**回帰（必須）**:

1. **alias が落ちないこと。** `SUM(a) * 単価 AS x` / `SUM(a) - SUM(b) AS diff` /
   `SUM(a) AS x - SUM(b)`（= ParseError のまま）。**`parseAggregateColumn` の `AS` 非消費ヘルパーを触る**ため、
   集計算術式 alias 消失バグの回帰をすべて再実行する
2. **`HAVING` から同じ式を書いたときの挙動を決めること。** B122 で `HAVING` の集計式が評価できるようになったので、
   `HAVING SUM(a) * 単価 > 100` が**通るのか静的に拒否されるのか**を受入条件で固定する
   （曖昧なまま出すと「別名なら通る / 直接なら 0 行」の再来になる）
3. `ORDER BY` の alias 参照・`UNION`・CTE 経由で同じ式が壊れないこと
4. **既存の拒否が緩まないこと**: `SUM(売上 > 0)` / `SUM(SUM(x))` / `MODE(DISTINCT ...)`

## 6. スコープ外

- 機能従属性の推論（主キーだから決まる、ルックアップだから決まる等）。**入れない**
- スカラーサブクエリをオペランドにする形（`SUM(a) * (SELECT ...)`）。別途評価
- ウィンドウ関数との併用（→ [B125](ksql_b125_aggregate_window_function_issue.md)）
