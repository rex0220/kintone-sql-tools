# 本文（送付版）

## 【返信】K-6 — v3.39.0 で入れました。形だけ 1 つ変えさせてください

**先に、リリースに直接効く実測を 1 つ。**

## 1. 「日時フィールドでは使えない」という制限は、書かなくて大丈夫です

ご指摘の実害（終端の取りこぼし）は、**engine 側の変更なしに解決できます**。
上限を **RFC3339** で渡してください。実データで測りました（全 20 件・最終作成 `2026-07-14T06:04:00Z`）:

```
作成日時 <= '2026-07-14'             → 18 件   ← ご指摘のとおり取りこぼす
作成日時 <= '2026-07-14T23:59:59Z'   → 20 件   ← 正しい
```

**RFC3339 文字列は `variables` 経由でもそのまま `EXACT_PUSHDOWN` で通ります**（EXPLAIN で確認）。
日時フィールド用のプリセットだけ `T23:59:59Z` を付けて解決すれば、**現 MVP のまま
日付フィールドと同じように扱えます。**

## 2. ご依頼の前提が 1 つだけ違っていました

「現行でも `NOW()` / `TODAY()` は既定値に書ける、の拡張」という点です。

```
DECLARE @period = THIS_MONTH();   → ParseError（相対日付関数は DECLARE 右辺で使えません）
DECLARE @period = TODAY();        → 通ります。ただし別物です
```

**`TODAY()` は綴りが同じで意味が 2 つあり、位置で決まります。**

| 書き方 | 実際の kintone クエリ |
|---|---|
| `WHERE 受注予定日 = TODAY()` | `受注予定日 = TODAY()`（**kintone サーバー評価**） |
| `DECLARE @p = TODAY(); WHERE 受注予定日 = @p` | `受注予定日 = "2026-08-02"`（**クライアント評価のリテラル**） |

つまり既定値に `TODAY()` と書くと、**静かに実行ホストの時計・タイムゾーン基準**になります。
ご相談の拡張の出発点ではなく、こちらが文書化すべき既存の罠でした。**v3.39.0 で
言語リファレンスへ明記しました**（日時フィールドの境界を RFC3339 で書くことも同様です）。

## 3. 形 — ご提案の後者（値の型注釈）を採りました

**「値が関数になる」形は採っていません。**

```sql
DECLARE @period RELATIVE_DATE = THIS_MONTH();
SELECT ... FROM APP4149 WHERE 受注予定日 = @period;
-- variables: { period: "THIS_YEAR()" }
```

**理由は注入安全性ではなく、DML の fail-open です。**
ホワイトリストの安全性についてのご認識は正しいのですが、値束縛の保証は
「**値は決して code にならない**」ことで、暗黙解釈はこれを壊します。具体的には:

```sql
DELETE FROM APPn WHERE 日付 = @period   -- 注入値ひとつで「単日削除」が「年間削除」になりうる
```

`PRIMARY_ORGANIZATION()` を DML で拒否したのと同じ形です。宣言する形にしたので、

- **SQL を読めば `@period` が関数トークンを持つと分かります**（隠れモードなし）
- ホワイトリスト外の値は **kintone API を呼ぶ前に名前入りエラー**（fail-closed）
- **既存 SQL は 1 つも意味が変わりません**——ご懸念の「`'THIS_MONTH()'` という文字列を
  検索したい利用者との衝突」が消えます
- DML では拒否します（そちらは read-only ライブラリなので影響はありません）

グローバルなフラグは採りません。同じ SQL がフラグで意味を変えるのは、B107 で
「定義済みのときだけ解決」を却下したのと同じ形になるためです。

## 4. 進め方 — **v3.39.0 で入りました**

**「実需を見てから」と書きかけたのですが、設計が固まったのでそのまま実装しました。**

```
npm i @rex0220/kintone-sql-tools@3.39.0
```

```sql
DECLARE @period RELATIVE_DATE = THIS_MONTH();
SELECT ... FROM APP4149 WHERE 受注予定日 = @period;
-- variables: { period: "THIS_YEAR()" } → 受注予定日 = THIS_YEAR() として押し下げ
```

- **単一変数形が使えます。**プリセットは `FROM_TODAY(-1, MONTHS)` のようなローリング窓も可
- **2 変数形も従来どおり動きます。**移行は任意で、利用者の学び直しは発生しません
- ただし **§1 のとおり「日時フィールド不可」の記載だけは落として**ください
  （単一変数形に移れば相対日付関数が日時フィールドの境界を正しく包含しますし、
  2 変数形のままでも RFC3339 で解決します）
- **ホワイトリスト外の値は kintone API を呼ぶ前に名前入りエラー**です。
  そちらの構文チェック（`explainQuery`）にそのまま出せます

## 5. 別件のご報告 — EXPLAIN の表示に欠陥がありました（B112・こちらの取り落とし）

**そちらの実行計画ボタンが踏んでいたはずです。JOIN を使うペイン SQL でご確認ください。**

```
修正前  app:  LAPP_案件管理 -> APP4149 AS a (900000000)     ← 内部 ID が残っていた
        JOIN: LAPP_検証アプリ -> APP4148 AS c (900000001)
```

**別名（`AS a`）や JOIN のある形だけ、括弧内に内部の仮想 ID が残っていました。**
B108 / B109 で塞いだはずの契約の残りで、**こちらが仕様を書くときに「経路」だけを列挙し、
出力の形を列挙していなかった**ことが原因です。範囲の取り落としは 2 度目で、申し訳ありません。

- **v3.38.0 の新しい問題ではありません**（v1.13.x 以来の既存欠陥です）
- **表示のみ**で、結果・計画の中身・押し下げ判定には影響しません
- CLI / MCP では物理アプリの profile が二重に出る症状（`APP4149@dev@dev`）も同じ原因です
- **B112 として起票し、v3.39.0 で直しました**（上の取り込みに含まれます）

```
修正後  app:  LAPP_案件管理 -> APP4149 AS a
```

自前の凡例を畳んでいただいた直後にこういう報告になってしまい恐縮です。
**v3.39.0 を取り込んでいただければ、JOIN を含むペインでも論理名だけが出ます。**
