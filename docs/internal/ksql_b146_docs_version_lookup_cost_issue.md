  高いのは費用だけ**。**依頼元も「1 回なら許容範囲」「急ぎではありません」**と書いている
- 種別: 改善（観測性の費用）
- 優先: **中**（[B101](ksql_b101_mcp_stale_process_version_issue.md) の引き出しを**習慣にできるか**が懸かる）

## 1. 何が起きているか

**v3.56.3 で「探しに行ける場所」を作ったが、そこへ行く費用を測っていなかった。**

**実測**（v3.56.3・`release/ksql-mcp.js` を stdio で起動し `ksql_docs` を引数なしで呼ぶ）

| | |
|---|---|
| 索引の応答 | **6,821 バイト / 178 行** |
| **欲しい版の行** | **144 バイト** |
| **比** | **47 倍** |

**依頼元の見積り（約 3.5KB）より重い。**

### 1.1 依頼元の指摘

> **当方の規約は「目次を丸ごと読み込まない」**（`ksql_docs` は該当セクションのみ）なので、
> **版の確認だけが規約の例外**という形になりました。1 回なら許容範囲ですが、
> **「疑ったら引く」を習慣にすると、疑うたびに 3.5KB 積み上がります。**

**引き出しを習慣にしてほしいのに、引く費用が相手の規約違反を強いていた。**

**索引の先頭に置く判断そのものには依頼元も賛成**している
（**探しに行った人が最初に当たる場所**であるため）。**問題は費用だけ。**

## 2. あわせて判明したこと — **`instructions` の陳腐化は想定より重い**

**依頼元のセッションで同時に測った 3 つ。**

| 見たもの | 出た版 |
|---|---|
| `ksql_docs`（引数なし）の 1 行目 | **3.56.3** ✅ |
| `ksql.js --version`（CLI） | 3.56.3 |
| **セッション開始時の `instructions`** | **3.46.0** ❌ |

**10 版ぶん古い。** その間に MCP は少なくとも 10 回差し替わっており、
**同じセッションの中で v3.47.0〜v3.56.3 の挙動を実測してきた**という。

**B101 §7 は「会話の開始時に 1 回」、§8 は「押し付けは探しに行く人に届かない」と書いた。
どちらも正しいが、どれくらい古くなるかを書いていなかった。**

**書き方を改める**——**「接続時のみ」ではなく「セッション中の再読み込みは反映されない」。
長いセッションほど確実に古い。**

**こちらのセッションでも同じことが起きた**（v3.56.3 のリリース当日）＝
**`instructions` は 3.56.2、`ksql_docs` は 3.56.3。正しいのは引き出し側だった。**
**新機能が最初に自分自身を捕まえた。**

## 3. 案

- **案 A＝`ksql_docs {"section":"version"}` で版の行だけを返す**（依頼元の提案）。
  **索引の先頭行と同じ文字列を使う**ので二重管理にならない。**本命**
- 案 B＝索引そのものを軽くする。**別の利用者（章を探す人）の役に立たなくなる**ので採らない
- 案 C＝何もしない。**1 回なら許容範囲**だが、**習慣にはできない**

**見立て＝案 A。** **索引の先頭にも残す**（探しに行った人が最初に当たる場所）。

**「版数は文書ではない」という B101 §4 の反対は、ここでさらに弱くなる**——
**`ksql_docs` は「この MCP について尋ねる口」として使われているのが実態**である。

## 4. 実装の中身（一度書いて、戻した）

- **`KSQL_DOCS_SECTION_KEYS` と `VALID_KEY_HINT` にも載せる**＝

## 6. **着手しない理由と、着手する合図**

**一度実装したが、リリースせずに戻した。**

**賛成材料が弱い**——

- **47 倍は比であって、実数は 6.8KB。1 回なら何でもない**
- **「習慣にすると積み上がる」はもっともらしい議論であって、観測ではない。**
  **依頼元も「1 回なら許容範囲」「急ぎではありません」と書いている**
- **B101 が解いた問題（版を確かめられない）は解けている。**本件は**それを安くする別の話**

**反対材料のほうが具体的だった**——

- **固定テストを 2 本壊した**（§4）。**あれは手を止めさせるためにある装置**で、実際に止まった。
  **止まった理由を「通すために直す」で処理しかけた**
- **同日に 5 版出していた。**publish は毎回オーナーの操作（2FA）で、
  **この 5 本目がいちばん証拠が薄い**
- **口を増やすこと自体の費用**（オーナー指摘・§6.1）

### 6.1 **口を増やすこと自体の費用**（オーナー指摘）

**バイト数では案 A は小さい。効くのは別の軸だった。**

| 増やすもの | いつ費用が出るか |
|---|---|
| **tool を 1 本**（案 C の `ksql_version`） | **全セッション**。スキーマが毎回文脈に載る |
| **節キーを 1 本**（案 A） | **索引を引いた人だけ**。1 行 |

**案 C を「tool 枠を毎セッション消費する」として落としたのは正しかった。**
**しかし案 A にも、量ではない形で同じ費用がある。**

**`version` は文書ではない。** `ksql_docs` に非文書を載せた瞬間、
**この tool の契約が「文書 + その他」になる。**
**次に「安く置く場所が欲しい」ものが出たとき、また同じ理由でここへ来る。**

**[B101](ksql_b101_mcp_stale_process_version_issue.md) §4 の「版数は文書ではない」はこれを言っていた。
こちらは 2 回とも「もう越えた」で片づけた。**

**越えたのは索引の先頭 1 行**であり、**あれは「このサーバーは何か」を尋ねる
呼び出しの答え**として筋が通る。**節キーを増やすのは、そこから一段進んで
契約を変える**——**同じ判断ではなかった。**

**したがって、再開するとしても案 A をそのまま採らない。**
**「文書ではないものを `ksql_docs` に載せてよいか」を先に決める。**
決め方次第では、**`ksql_docs` ではなく別の場所**（`_meta` は §2ter で落ちるので、
**既存 tool の返り値に混ぜる**か、**案 B の自己検出**）になる。

**着手する合図**

1. **依頼元が「費用のせいで版の確認を省いた」と報告したとき**
2. **同じ取り違え（別プロセスの版を測る）がもう一度起きたとき**
3. **他の理由で MCP を触る版があり、ついでに入れられるとき**

**ただし合図が出ても、§6.1 の「文書ではないものを載せてよいか」を先に決める。**
**「ついでに入れられる」は、契約を変えてよい理由にならない。**

**B101 案 B（陳腐化の自己検出）へ進む条件は変わらない**＝
**`ksql_docs` で引いても取り違えが起きたら。** そのとき初めて
**押し付け・引き出しの両方が効かない**ことになる。

## 7. 手順の反省

**測ってから実装し、実装してから起票した。**
**起票が最後になると、案の比較が事後の正当化になりやすい。**
**実際、起票を求められて初めて「必要か」を考え直し、結論が逆になった。**

**実装が小さくても、案を並べる時点で 1 度手を止める。**
