## この文書の目的

本書は、kSQL を差分型の夜間バッチに利用するために、今後追加する機能・追加しない機能・実装順を決定する。個別機能の完全な構文仕様は別紙（各仕様案）に分離しており、本書だけで実装できる完全仕様ではない。

顧客マスタ差分更新バッチ（ステータス駆動・冪等・リラン前提）の設計と、その後の検討（API 制限・大量レコードの適用限界・現行機能での代替可否）を反映した改訂版。

**検討の結論**: 当初 8 案 → 採用 2 案 + 依存機能 1 件 + ランタイム内部改善 1 件に絞り込み。「現行 SQL で書けるもの」はドキュメント整備、「大量レコードで初めて必要になるもの」は連携方式の見直しが先、「リカバリー手順を複線化するもの」は設計原則違反、という判断基準で削った。

## 採用機能

### 事前検証エラー行の隔離・継続（Phase 3・価値最大）（`ON ERROR SKIP INTO #err REJECT LIMIT n`）

「1 件の不良データで夜間バッチ全体が停止する」問題の解消。**kSQL でバッチを組む決め手を最も増やす機能**（TS に逃げる理由の筆頭を消す）。

> **定義（隔離対象の限定）**: 本機能が隔離するのは、kSQL が **API 送信前にローカルで判定できる検証エラーに限る**。kintone API 実行時のエラー（権限・競合・一意制約衝突・プラグイン/JS による保存拒否等）を行単位で隔離する機能ではなく、API レベルの失敗は従来通り全体停止（fail-fast）する。

- スコープはローカル事前検証（Tier 0）のみ: フィールド定義から判定できる必須・型・範囲・選択肢・キー空値・ソース内キー重複を、書き込み前に全行検証して隔離。**正常パスの API 発行数は現状と完全同一**
- kintone バルク API（100 件 all-or-nothing）へレコード単位 API で対抗しない
- `REJECT LIMIT n` は**隔離された行数**に適用（1 行に複数エラーがあっても 1 行と数える）。n 行までは許容し n+1 行目で超過。**超過時も全行検証を完了してから書き込みゼロで停止**し、`#err` は参照可能（結果が決定的になる）
- 同じ検証エンジンを VALIDATE ONLY モード（書き込みゼロでエラー一覧のみ）として公開 — 取り下げた DRY RUN の固有価値をここに吸収
- **非保証範囲**: VALIDATE ONLY / 事前検証の通過は、kintone API による書き込み成功を保証しない（条件付き必須・カスタマイズ JS の制約・実行時点の権限や競合はローカルで判定不能）

### バッチ変数（Phase 1）（`SET @var` / `DECLARE @param`）

時刻固定・バッチ ID・保存クエリのパラメータ化を一つの機構で解決。実装コスト小・静的検査（validate で未定義参照検出）込み。

- `SET @now = NOW()` で時刻固定 → **NOW() のセマンティクス変更が不要**で後方互換問題なし
- `DECLARE`（外部注入可）と `SET`（内部のみ）の分離で、注入面をクエリ作成者が制御。値バインドでインジェクション構造的に不能
- 保存クエリが初めてパラメータ化可能になる（MCP / CLI から params 注入）
- `@batch_id` を全書き込みに付与 → 事後検証が完全一致になり、機能 4（実行ログ）の紐付けキーにもなる

### 内部改善: HTTP 層の透過リトライ（構文なし・429 のみ）

当初提案していた `RETRY n BACKOFF` 構文は取り下げ、ランタイム内部の HTTP クライアント層でのレート制限（429）バックオフのみに縮小する。

- **429 に限定する根拠**: 現時点で、安全性と効果をともに説明できる自動再試行対象は 429 のみ。レート制限はバッチ自身のリクエストレートが原因（自己誘発性）でジョブ全体リランでは同じ地点で再発しやすく、プロセス内バックオフが有効に働く。未実行保証もあるため文の種類を問わず安全
- **ネットワークエラーは対象外**: 外因性（回線・kintone 側障害）であり、多くの場合リトライは失敗検知を遅らせるだけで、正しい対処はジョブ全体リラン。また「送信前」を確実に判別できる範囲は狭く（接続リセット等は送信後＝結果不明の可能性）、安全な部分集合として切り出す価値が小さい
- **5xx・タイムアウトも対象外**: 処理結果を確定できない場合がある（kintone 側でコミット後に応答が失われた可能性）ため fail-fast し、ジョブ全体リランに委ねる

### 依存機能: UPDATE ... FROM

B11 v1（v2.12.0）で SET 値の他テーブル参照と `target.$id = source.key` は実装済み。ただしB12の `#err` はUPSERT入力列だけを保持し、差分アプリの `$id` を持たない。エラーメッセージを書き戻す看板ユースケースには `target.業務キー = source.業務キー` が必要なため、B11 v1.1をB12-Bの前に実装する。B12-A `VALIDATE ONLY` は書き戻し非依存なので先行できる。

**複数マッチはエラーに固定する**: FROM 句の結合結果が更新対象 1 行につき複数行になった場合、DML 実行前にエラーとする。「先勝ち」は行順・取得順に依存して結果の決定性を失い、不正な結合条件やデータ重複を静かに隠すため採用しない（本バッチ設計の原則「冪等・リラン可能・判断分岐なし」と整合させる）。1 行化が必要な場合は利用者側で集約してから結合する。

```sql
-- B11 v1.1。差分アプリ = APP4220
CREATE TEMP TABLE #err_summary AS
SELECT 顧客コード, MIN($err_message) AS エラー内容
FROM #err GROUP BY 顧客コード;

UPDATE APP4220 SET 処理ステータス = 'エラー', エラー内容 = e.エラー内容
FROM #err_summary e WHERE APP4220.顧客コード = e.顧客コード;
```

## 取り下げ・保留の理由（検討経緯）

### ステートメント単位リトライ（取り下げ・HTTP 層へ縮小）

1. **リトライ安全性がエラー種別 × 文の種類の組み合わせで変わる**: 5xx/タイムアウトは結果不明のため、INSERT 系のリトライは二重登録リスクがあり、運用者に影響箇所の特定とマニュアル判断を強いる。夜間無人バッチに最も不向きな性質
2. **設計原則との矛盾**: 本バッチ設計の核心は「全ケースで先頭からのリランが唯一のリカバリー手順（判断分岐なし）」。バッチ内部に第二のリカバリー機構を持ち込むとこの一本道が壊れる
3. 差分型夜間バッチではジョブ全体リランのコストは数分であり、部分リトライによる節約効果が実質ない
4. リトライで結果が変わるのは自己誘発性の 429（レート制限）のみ。外因性のネットワークエラーはジョブ全体リランが正しい対処であり、リトライ対象から除外。HTTP クライアント層の 429 バックオフのみ残す（前掲）

### DRY RUN（取り下げ）

影響件数・inserts/updates 内訳・変更前後プレビューは**現行機能で取得できる**ため独立機能にしない。

```sql
-- 事前ゲートパターン（読み取り専用・現行機能のみ）
CREATE TEMP TABLE #tgt AS SELECT ... FROM APP_差分 WHERE 処理ステータス = '未処理';
SELECT COUNT(*) AS inserts FROM #tgt t LEFT JOIN APP_マスタ m ON t.キー = m.キー WHERE m.キー IS NULL;
SELECT COUNT(*) AS updates FROM #tgt t INNER JOIN APP_マスタ m ON t.キー = m.キー;
ASSERT (SELECT COUNT(*) FROM #tgt) BETWEEN 1 AND 10000;   -- 想定外件数なら書き込み前に停止
```

固有価値のうち検証エラープレビューは エラー行隔離の VALIDATE ONLY に吸収。「DML 文からのミラークエリ自動導出」（手書きミラーとの乖離バグ防止）のみ将来課題として残し、まずレシピ集のドキュメント整備で対応。

### ONLY CHANGED（保留）

1. 最大の効能である全件洗い替え型の書き込み削減は、**そもそも連携方式を差分型に直すべきケース**であり、機能で救う領域ではない
2. 推奨する差分型バッチでは投入行が元々変更行のみで、効果はリラン時（希少イベント・当日差分のみ）の「更新日時を汚さない」に限定される
3. 仕様の複雑さが最重量級: 読み取り戦略（`キー in` は in 句の値数=実質クエリ長に律速され 500 件/req は成立しない / マスタ全読みカーソルとの自動選択）、型別正規化、文字列（1行）の先頭 64 文字比較問題
4. 検証エンジン・比較エンジンの土台（エラー行隔離・レシピ集）が先。需要立証後に再評価

### 実行ログ自動記録・スナップショット退避・チャンク実行（保留）

- 実行ログ: バッチ変数の `@batch_id` + 現行 INSERT で運用可能になるため、まず変数で様子を見る
- スナップショット退避: 現行でも `CREATE TEMP TABLE #before AS SELECT ...` を DML 前に挟み結果に含めれば近い効果が得られる（レシピ化）
- チャンク実行: 対象となる数十万件級は本方式の適用限界の外側（下記）

## 適用限界（ドキュメントに明記すべき指針）

kSQL バッチの想定スケールと、超えた場合の判断:

| 実行あたり処理件数 | 判断 |
|---|---|
| 〜数千件（差分型の日次バッチ） | 本設計の主戦場。差分を効率的に抽出でき書き込みを 100 件単位でまとめられる典型ケースでは、API 消費は 1 日上限（10,000 req/アプリ）のごく一部（例: 差分 2,000 件 → 読み取り 4 req + 書き込み 20 req + ステータス更新 20 req ≒ 上限の 0.5%） |
| 〜数万件 | 成立。tempTableMaxRows 調整または日付範囲での分割実行が必要 |
| 数十万件〜 | **機能追加で解く領域ではない**。インメモリモデル・API 上限・実行時間の 3 制約が同時に立つ。上流での差分抽出（CDC 化）、洗い替え方式の廃止、または kintone をシステム・オブ・レコードにしない、を先に検討する |

判断基準は総レコード数ではなく**「日次の実変更件数が API 制限と実行時間に収まるか」**。マスタ 10 万件でも日次差分が数百件なら何の問題もない。

## 推奨実装ロードマップ（コスト×効果評価）

| 施策 | コスト | 効果 | 費用対効果 |
|---|---|---|---|
| レシピ集 | 極小（文書のみ） | 中: 現行機能の価値を顕在化 | ◎ |
| バッチ変数 | 小〜中 | 大: バッチ外にも効く汎用機能 | ◎ |
| UPDATE ... FROM v1 | 中 | 大: 転記処理は頻出ニーズ | **実装済み** |
| UPDATE ... FROM v1.1 | 中 | 大: B12エラー書き戻しの前提 | ○ |
| エラー行隔離 | 大（型別検証エンジン） | 大: ただしバッチ用途に集中 | ○ |
| 429 バックオフ | 極小 | **ほぼゼロ**（下記） | 機会的 |

- **Phase 0（即着手）**: レシピ集。リスクゼロ・即効
- **Phase 1**: バッチ変数。`SET` のみ先行（パーサー+評価器で閉じる）→ `DECLARE` + 外部パラメータ（MCP/CLI インターフェース変更を伴う）は後続。保存クエリのパラメータ化は候補中最大の汎用リターン
- **Phase 2（完了）**: UPDATE ... FROM v1（`$id` 結合）。複数マッチは DML 実行前エラーに固定
- **Phase 3-A**: **VALIDATE ONLY を先行リリース**。書き込みセマンティクスに触れず、B11にも依存しない
- **Phase 3-B**: B11 v1.1（業務キー結合）。`#err` から差分アプリへの書き戻しを成立させる
- **Phase 3-C**: `ON ERROR SKIP INTO #err`。検証エンジンは保留中の ONLY CHANGED・将来の DRY RUN 復活の土台にもなる

**429 バックオフの格下げ理由**: kintone にはリクエスト毎秒のスロットリングがなく、制限は同時アクセス数（100/ドメイン）と 1 日 10,000 req/アプリ（即遮断なし）のみ。kSQL の並列度は fetchParallel 最大 10 で、想定する夜間単独実行では 429 が発生する可能性は低い。日中実行・他連携との同居ドメインへの保険と位置づけ、HTTP クライアント改修の機会があれば同梱する「機会的改善」とする。

方針: **小さく確実なものから出し、最大の投資（検証エンジン）は VALIDATE ONLY で需要検証してから**。
