# kSQL 仕様案：ONLY CHANGED（UPSERT の変更行スキップ）

- 出典: 設計メモ `ksql-batch/kSQL仕様案_ONLY-CHANGED変更行スキップ.md`（2026-07-16 に repo へ移設）
- ステータス: **⏸ 保留**（差分型では効果がリラン時限定・実装コスト重）。エラー行隔離（B12）の検証エンジンが先。需要立証後に再評価。台帳 [ksql_issue_tracker.md](../ksql_issue_tracker.md) §3。

> **ステータス: 保留**
> 差分型バッチでは投入行が元々変更行に限定され、効果は主にリラン時の監査情報保護（更新日時・Webhook を汚さない）に限られる。一方、実装には既存レコード取得戦略・フィールド型別正規化・長文キー対応など大きなコストを要する。まずバッチ変数、UPDATE ... FROM、Tier 0 事前検証（VALIDATE ONLY → ON ERROR SKIP）を優先し、実際のリラン運用で無変更更新が問題化した場合に再評価する。詳細は「kSQL改善案_バッチ処理機能.md」参照。

## 1. 目的

UPSERT は値が既存レコードと同一でも書き込みが発生し、(1) 更新日時・更新者が動いて監査情報を汚す、(2) 更新日時トリガーの後続処理や Webhook が誤発火する、(3) 書き込み API（100 件/リクエスト）を無駄に消費する、という副作用がある。
既存レコードと**実際に値が異なる行だけ**を書き込むことで、リラン時の書き込みゼロ（真の冪等性）と API 発行数の削減を実現する。

## 2. 構文

```sql
UPSERT INTO <app> (<col1>, <col2>, ...) SELECT ...
  ON DUPLICATE (<key>)
  [ONLY CHANGED [(<比較列>, ...)]] ;
```

- `ONLY CHANGED` … キー一致の既存レコードと比較し、**書き込み対象列がすべて同値なら UPDATE をスキップ**。INSERT（キー不在）は常に実行
- 比較列リスト省略時は**書き込み対象列すべて**を比較（既定・推奨）
- 比較列を明示した場合はその列のみで判定（例: 更新元システムのタイムスタンプ列だけで判定し、比較コストを下げる）
- 句を付けない既存 SQL の挙動は不変（後方互換）

## 3. 実行セマンティクス

```
1. ソース確定（スナップショット）
2. キー値で既存レコードを取得（500件/リクエストの読み取り。キー IN (...) をチャンク分割）
3. 行分類:
   - キー不在        → INSERT 対象
   - キー一致・値差異 → UPDATE 対象
   - キー一致・全同値 → スキップ（unchanged）
4. INSERT/UPDATE 対象のみ従来通りバルク書き込み
5. 結果メタデータ: { inserts, updates, unchanged }
```

### コスト特性（重要）

`upsert: true` の REST API は事前読み取り不要だが、ONLY CHANGED は**既存値の読み取りが追加で必要**になる。読み取り戦略は 2 通りあり、ランタイムが自動選択する。

| 戦略 | 読み取り方法 | 読み取りコスト | 向くケース |
|---|---|---|---|
| A: キー絞り込み | `キー in (...)` をチャンク分割 | ceil(N/チャンク) | 投入 N ≪ マスタ M |
| B: マスタ全読み | キー + 比較列のみカーソル取得 | ceil(M/500) | 全件洗い替え型、N ≒ M |

- **戦略 A の注意**: 500 は取得レスポンスの上限であり、リクエスト側は in 句の値数に律速される。in の値数上限は公式に未文書化のため（実質はクエリ文字列長。GET の URL 長制限は X-HTTP-Method-Override で回避）、安全既定値は 100 キー/クエリとし、この場合読み取りは書き込みと同数の ceil(N/100)。キー長が短ければ設定で引き上げ可能とする（要実測）
- **戦略 B** は in 句制約と無関係に確実に 500 件/リクエスト。選択基準の目安: `ceil(M/500) < ceil(N/100)` なら B
- 読み取りは更新日時・Webhook を動かさない。差分バッチの実態は「リラン時・再送時に大半が同値」なので、**リランで書き込みゼロになる価値が読み取りコストを上回る**
- 全件洗い替え型バッチでは劇的に効く: 変更 1% なら書き込みが 1/100（読み取りは戦略 B で ceil(M/500)）
- `dmlMaxRows` は inserts + updates のみカウント（unchanged は含めない)

## 4. 同値判定ルール（フィールド型別の正規化）

kintone の値表現ゆれを吸収するため、単純文字列比較ではなく型別正規化後に比較する。NULL 同士は同値（`IS NOT DISTINCT FROM` 意味論）。

| フィールド型 | 正規化・比較規則 |
|---|---|
| 文字列一行/複数行、リンク | 完全一致。空文字と NULL は同値扱い |
| 数値 | 数値として比較（"1.0" = "1"、"" と NULL は同値） |
| 日付/時刻/日時 | ISO 正規化後に比較（日時は UTC 換算） |
| ドロップダウン/ラジオ | 完全一致 |
| チェックボックス/複数選択 | **集合比較（順序不問）** |
| ユーザー/組織/グループ選択 | code の集合比較 |
| 添付ファイル・テーブル | 比較対象外（列指定時は静的エラー。将来拡張） |

境界ケースは `ksql_explain` / DRY RUN で判定結果を確認できるようにする（§6）。

## 5. 利用例（顧客マスタ差分更新バッチ）

```sql
UPSERT INTO APP_顧客マスタ (顧客コード, 顧客名, 住所, 電話番号)
SELECT 顧客コード, 顧客名, 住所, 電話番号 FROM #tgt
ON DUPLICATE (顧客コード) ONLY CHANGED;
```

- 正常リラン時: 前回適用済みの行はすべて unchanged → **マスタの更新日時が一切動かない**。「リランしたら全顧客の更新日時が今日になった」という監査上の事故が構造的に消える
- ON ERROR SKIP と併用時の評価順: エラー検証（Tier 0）→ 同値判定 → 書き込み。`#err` 隔離行は比較対象にしない

## 6. 関連機能との統合

- **結果メタデータ**: mutate 結果に `unchanged` を追加。「全件 unchanged = リラン成功・変更なし」を呼び出し側が機械判定できる
- **事前ゲートレシピとの関係**: inserts / updates の件数内訳は現行 SQL（LEFT JOIN + COUNT）で取得可能（改善案の事前ゲートパターン参照）。本仕様の比較エンジンが提供する固有価値は「値レベルの unchanged 判定」のみであり、この点も保留判断の根拠の一つ
- **ハッシュ最適化（将来）**: 比較列の正規化値ハッシュをマスタ側の隠し列（または専用フィールド）に保持すれば、既存値の読み取りをハッシュ列 1 列に減らせる（Data Vault の HASHDIFF 方式）。初期実装では不要

## 7. 参考事例

| 製品/手法 | 機能 | 本仕様への採用点 |
|---|---|---|
| MySQL | `INSERT ... ON DUPLICATE KEY UPDATE` は全列同値なら更新せず affected rows = 0 | 「同値ならエンジンが書かない」という先例そのもの。affected rows で挿入/更新/無変更を区別する慣行 |
| PostgreSQL | `suppress_redundant_updates_trigger()`（組み込みトリガー）、`ON CONFLICT DO UPDATE ... WHERE target IS DISTINCT FROM excluded` イディオム | 無変更 UPDATE 抑止が公式機能として存在する需要の立証。NULL 安全比較（IS DISTINCT FROM）の意味論 |
| SQL Server / Oracle | `MERGE ... WHEN MATCHED AND (t.col <> s.col OR ...) THEN UPDATE` イディオム | 「MATCHED かつ差異あり」を分ける 3 分類（insert / update / unchanged）の構造 |
| dbt | snapshot の `check` 戦略（check_cols 指定列の比較で変更検出） | 比較列を明示指定するオプションの先例 |
| Data Vault / DWH | HASHDIFF（比較列の正規化ハッシュで変更検出） | ハッシュ最適化（§6 将来拡張）の設計 |

RDB ではエンジンが行を直接比較できるため追加コストほぼゼロだが、kSQL では読み取り API が必要になる。**無変更行の比率が十分高く、更新日時・Webhook 等の副作用抑制に価値がある場合**、追加読み取りと引き換えに書き込みを削減する設計は有利になり得る。逆に、差分型の通常実行のように投入行の大半が実変更である場合は、追加読み取りが純粋なコスト増になる（本仕様を保留とする根拠の一つ）。

## 8. 制限事項

1. 従来 UPSERT と同様に排他制御は行わず、読み取り後から書き込みまでの間の他者更新は検知しない。事前比較を追加するため比較時点と書き込み時点の間隔は従来より生じるが、初期仕様では revision 条件による競合検出は行わない
2. 添付ファイル・テーブルフィールドは比較対象外（初期実装）
3. キー IN 検索のクエリ文字列長制限により、キーのチャンクサイズは値長に応じて動的調整が必要（実装詳細）。in の値数上限は公式未文書化のため保守的な既定値から始める
4. 比較列に計算フィールド等の書き込み不可列は指定不可（静的エラー）
5. **文字列（1行）の `=` / `in` 比較は先頭 64 文字のみで判定**される kintone 仕様のため、64 文字超のキーでは戦略 A（キー絞り込み）で誤マッチの可能性がある。キーが 64 文字超の場合は戦略 B に強制フォールバックし、比較はローカルで全文字実施する
