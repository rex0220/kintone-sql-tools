## 1. 何が起きているか

**説明文を直したのに、その下の例が古いまま残る。** 同じ形で 3 回起きた。

| # | 版 | 説明文 | 取り残された例 |
|---|---|---|---|
| B136 | v3.49.0 | `DESCRIBE` の列を 7 列に変更 | 言語リファレンスの列表が旧いまま |
| R16 | v3.53.0 | B140-C で CTE 経路の警告文を直した | レシピ R16 の注記が「レコード番号など」のまま |

**3 件とも、説明は正しく、例だけが間違っていた。** 読み手は例を写すので、直した説明は届かない。

## 2. 本件の具体

[言語リファレンス](../ksql_language_reference.md) の `NULLIF` の注記は、
「空文字が NULL 相当のため `Number('') = 0` となり、結局ゼロ除算で `NaN` になる」
と原因を正しく説明したうえで、対処として次を ○ として挙げていた。

```sql
SELECT CASE WHEN 金額 = 0 THEN '' ELSE 1000 / 金額 END AS 単価 FROM APP100
```

**この ○ が、まさに説明した理由で NaN を出す。** 空文字は**算術では 0 になるが比較では 0 と等しくない**ため、
空セルの行は `ELSE` へ落ちて `1000 / ''` になる。

実測（APP4229 × APP4228・`LEFT JOIN` で一致しない行が空セル）:

```
ほうじ茶    出庫数=""   旧ガード=NaN   新ガード=""
ライ麦パン  出庫数=""   旧ガード=NaN   新ガード=""
トマト缶    出庫数=1147 旧ガード=0.871…  新ガード=0.871…（変化なし）
```

本物の 0（`仕入価格 - 仕入価格`）は新旧どちらのガードも捕まえる。**差は空セルだけ。**

修正＝`CASE WHEN 金額 = '' OR 金額 = 0 THEN ''`。除数が空になり得る場面
（`LEFT JOIN` で一致しなかった行・`LAG` / `LEAD` の端の行・`NULLIF` の結果）を注記に列挙した。

**発見の経緯**＝依頼元（`ksql-analytics`）が R16 の `LAG` 先頭行で `= 0` ガードが効かないと報告し、
「他にも同じ形が無いか」を探して当たった。**依頼元は R16 しか見ていない**。

## 3. なぜ機械で防げていないか

- B136 は[列表の同期テスト](../../src/__tests__/b136DocsColumnParity.test.ts)で塞いだが、**これは列名という機械が照合できる対象だったから**成立した。
- 本件のような「例の SQL が期待どおりの値を返すか」は、**実行しないと分からない**。
- [`docs:check`](../../scripts/docs-check.mjs) はリンクと台帳の構造しか見ておらず、**SQL は文字列として素通りする**。

## 3.5 射程は公開文書の外にも伸びていた（2026-08-06 追記）

**依頼元の `docs/06-ksql-tips.md` に、同じ ○ がそのまま写っていた。**

```sql
-- 依頼元の旧記述（言語リファレンスの ○ と同型）
SELECT CASE WHEN 金額 = 0 THEN '' ELSE 1000 / 金額 END AS 単価 FROM APP100
```

**依頼元は踏んでいない**（除数が 3 箇所ともに集計経路だったため）。
ただし**踏まなかったのは運**で、R17 型の表で「1 件あたり」「回転率」を出した時点で踏む。

**エンジンの文書の例は、下流のドキュメントへ複製される。**
再発防止を設計するとき、**直す対象は自分の文書だけでは終わらない**（複製先へ連絡が要る）。

## 4. 案

- **案 A＝文書の SQL を実行するテスト**。掲載 SQL に期待値を添えて実行し照合する。
  **障害＝ネットワークが要る**ため既存の単体テスト（228 suites・オフライン）には入れられない。
  別系統（`mcp:verify` のような実機系）に置くことになる。実データへの依存も設計が要る。
- **案 B＝実行可能な例だけ機械抽出し、固定のスタブアプリに対して実行する**。
  ネットワーク不要にできるが、**スタブの整備が本体**になる。
- **案 C＝運用ルールのみ**（公開する SQL は必ず実行してから載せる）。
  **現に守れておらず 3 回起きている**ので、これ単独では弱い。
- **案 D＝説明文を変更したら同じ節の例を必ず読み直す**、をレビュー観点として明文化。
  費用ゼロだが、**B136 のときも同じことを言って再発している**。

- **案 E＝新規に追加・変更する例だけを実行必須にする**（依頼元の提案・2026-08-06）。
  **既存の例を全部潰すより費用対効果が高い**という主張で、根拠は
  **今回の 3 件がいずれも「後から気づいた既存の例」ではなく、書いた時点で実行していれば分かったもの**だという点。
  `= 0` の ○ は**1 回実行すれば `NaN` が出る**。

**見立て＝案 E を採る（2026-08-06 に案 B から変更）。**

案 B（すべての例を実行可能に書き換える）を降ろした理由は依頼元の指摘が正しいため＝
**`APP100` のような架空アプリは読みやすさのために選ばれており、
実在アプリへ置き換えると今度は「読み手の環境で再現しない例」になる。**
費用が大きいだけでなく、**文書として悪くなる**。

**案 E で残る弱点＝機械で強制できない**（案 C と同じ弱さを持つ）。
ただし案 C が「全部の例を実行してから載せる」だったのに対し、
案 E は**変更した節の例だけ**なので、守れる大きさになっている。
**次に破れたらここへ追記して、機械化の費用と比べ直す。**
