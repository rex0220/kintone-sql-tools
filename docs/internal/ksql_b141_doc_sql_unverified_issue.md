- 優先: 中

## 1. 何が起きているか

**説明文を直したのに、その下の例が古いまま残る。** 同じ形で 3 回起きた。

| # | 版 | 説明文 | 取り残された例 |
|---|---|---|---|
| B136 | v3.49.0 | `DESCRIBE` の列を 7 列に変更 | 言語リファレンスの列表が旧いまま |
| R16 | v3.53.0 | B140-C で CTE 経路の警告文を直した | レシピ R16 の注記が「レコード番号など」のまま |
| 本件 | v3.53.0 | `NULLIF` のゼロ除算ガードが効かない理由を説明 | その 3 行下の ○ の例が空セルを見ていない |

**3 件とも、説明は正しく、例だけが間違っていた。** 読み手は例を写すので、直した説明は届かない。

**追記（2026-08-07・6 件目）**: 言語リファレンス §6 の「選択系の `=` は押し下がりません。
`IN (...)` を使用してください」と書き換え表の `確度 = 'A'` → 全件取得 の行が、
**v3.47.0（B126・`=` を `IN` へ自動正規化）から 12 版のあいだ古いまま**だった。オーナー指摘で発覚。
**実測（v3.59.0）**＝`= '出庫'` は `EXACT`（`pushdown normalized:` 行付き）・`= ''` は `ALL` のまま・
`IN ('')` は `EXACT` → 散文を現行挙動へ書き換え、表の行は空文字判定の書き換えへ差し替えた（PR #323）。
**今回は 4 件目・5 件目（値の表）と違い、散文＋手書きの書き換え表＝機械照合の対象外**で起きた。
「残る穴＝散文」の判断どおりの場所で出ている。**なお v3.47.0 の CHANGELOG 自体は正しく、
言語リファレンスだけが取り残された**＝「挙動を変えた版で言語リファレンスを grep する」が
運用として要る（B126 なら「押し下が」で当たった）。

**続報（同日）**: この修正の際、B84 の押し下げ表（機械照合済み）に引きずられ、
「JOIN prefilter には正規化が掛からない」と**誤った一文を書いた**。オーナーの表見直し依頼
→ 実測（JOIN でも `pushdown normalized:` が出て `relation: exact`）で同日中に発覚。
**原因＝パリティテストが正規化前の分類器を生で呼んでおり、表が「観測可能な挙動」ではなく
「内部関数の生の挙動」を固定していた**。生成器を「正規化 → 分類」の観測順へ直し、
表 3 行（単一値選択系の `=` / `!=`）を ○ へ反転した。
**学び＝機械照合は「何と照合するか」で正しさが決まる。内部関数と照合した表は、
機械照合済みでも利用者の観測と食い違い得る。文書の照合先は公開面（EXPLAIN・実行結果）に近いほど良い。**

## 2. 本件の具体

[言語リファレンス](../ksql_language_reference.md) の `NULLIF` の注記は、
「空文字が NULL 相当のため `Number('') = 0` となり、結局ゼロ除算で `NaN` になる」
と原因を正しく説明したうえで、対処として次を ○ として挙げていた。

```sql
SELECT CASE WHEN 金額 = 0 THEN '' ELSE 1000 / 金額 END AS 単価 FROM APP100
```

**この ○ が、まさに説明した理由で NaN を出す。** 空文字は**算術では 0 になるが比較では 0 と等しくない**ため、
空セルの行は `ELSE` へ落ちて `1000 / ''` になる。

実測（APP4229 × APP4228・`LEFT JOIN` で一致しない行が空セル）:

```
ほうじ茶    出庫数=""   旧ガード=NaN   新ガード=""
ライ麦パン  出庫数=""   旧ガード=NaN   新ガード=""
トマト缶    出庫数=1147 旧ガード=0.871…  新ガード=0.871…（変化なし）
```

本物の 0（`仕入価格 - 仕入価格`）は新旧どちらのガードも捕まえる。**差は空セルだけ。**

修正＝`CASE WHEN 金額 = '' OR 金額 = 0 THEN ''`。除数が空になり得る場面
（`LEFT JOIN` で一致しなかった行・`LAG` / `LEAD` の端の行・`NULLIF` の結果）を注記に列挙した。

**発見の経緯**＝依頼元（`ksql-analytics`）が R16 の `LAG` 先頭行で `= 0` ガードが効かないと報告し、
「他にも同じ形が無いか」を探して当たった。**依頼元は R16 しか見ていない**。

## 3. なぜ機械で防げていないか

- B136 は[列表の同期テスト](../../src/__tests__/b136DocsColumnParity.test.ts)で塞いだが、**これは列名という機械が照合できる対象だったから**成立した。
- 本件のような「例の SQL が期待どおりの値を返すか」は、**実行しないと分からない**。
- [`docs:check`](../../scripts/docs-check.mjs) はリンクと台帳の構造しか見ておらず、**SQL は文字列として素通りする**。

## 3.6 4 回目＝同じリリースサイクル内で、同じ文書の中が矛盾した（2026-08-06）

**案 E（新規・変更分だけ実行必須）を決めた直後に、4 回目が起きた。**

v3.54.0 で `MIN` / `MAX` の空集合を `0` から空文字へ変えたとき、
**同じ言語リファレンスの中に、古い値を書いた表が残った。**

| 場所 | `MIN` / `MAX` の空集合 |
|---|---|
| 除数ガードの表 | **`0`** ← 古い |
| 集計関数の節（同じ文書） | 空文字 ← 正しい |

**しかも除数ガードの表は、その 1 つ前のリリースで自分が書いたもの。**
**依頼元が読んで指摘してくれるまで気づいていない。**

**案 E では止まらなかった。** 案 E は「**追加・変更した例を実行する**」だが、
今回壊れたのは**変更していない別の節**で、実行対象に入らない。

### だから機械化した

**この形は機械で照合できる。** 文書の表と、エンジンの実際の戻り値を突き合わせればよい。
[`b141EmptyAggregateDocsParity.test.ts`](../../src/__tests__/b141EmptyAggregateDocsParity.test.ts)
を追加した（[B136 の列名パリティ](../../src/__tests__/b136DocsColumnParity.test.ts) と同じ形）。

- 言語リファレンスの「集計する値が 1 つも無いときの戻り値」の表を解析する
- 各関数を空入力で実行し、表の値と一致することを確かめる
- **エンジンが対応する集計関数がすべて表に載っていること**も確かめる（関数を足したら落ちる）

**表を機械が読める形に揃えた**＝「統計集約」という散文を `VAR_POP` / `VAR_SAMP` /
`STDDEV_POP` / `STDDEV_SAMP` へ展開し、`GROUP_CONCAT` を追加した。
**文書としても正確になった**（以前は `GROUP_CONCAT` の空集合が書かれていなかった）。

**表を一時的に `0` へ改変して、テストが落ちることを確認済み。**

### 学び

**「実行してから載せる」は、書いた瞬間の正しさしか守らない。**
**挙動を変えたときに古くなる文書は、実行では見つからない。**
機械照合が要るのは**例の SQL ではなく、挙動を写した表**のほうだった。

**残る穴**＝機械照合できるのは「値の表」だけ。**散文で書かれた挙動の説明は依然として守れない**
（§3.5 の下流への複製も同じ）。→ **下流への複製には §3.7 の刻印が効く。**

## 3.65 5 回目＝機械照合が「もう 1 つの表」を素通りさせた（2026-08-06）

**v3.54.1 で入れたパリティテストは、マーカー 1 つ分の表しか見ていなかった。**

`§8` には**空集合の戻り値を書いた表が 2 つ**ある。

| 表 | v3.54.1 時点 |
|---|---|
| 「集計する値が 1 つも無いときの戻り値」（v3.54.0 で追加） | 正しい・**照合対象** |
| 「### 0 件時の挙動」（以前からある） | **`SUM` / `AVG` / `MAX` / `MIN` → `0`** のまま・**照合対象外** |

**後者は 5 回目の取り残し**で、しかも**同じ節の中**にある。
**依頼元が `ksql_docs` 経由で読んで指摘するまで気づいていない。**

**機械化そのものが、防ごうとした穴と同じ形をしていた**＝
「1 か所を直して、同じことを書いた別の場所が残る」。

### 直した形

**「値が無いとき」列を持つ表を、文書全体から自動で見つけて全部照合する**ようにした。

- 列見出しが `値が無いとき` / `0 件時の値` に一致する表を検出する
- **表を新しく足しても、その列名を使う限り自動で検査対象になる**
- 関数名はバッククォート断片の先頭識別子から拾う（`` `COUNT(*)` `` → `COUNT`）

**強化したテストが、直す前の文書で落ちることを確認してから直した**
（`Expected: "集計 | 0 件時の値 / MAX=0"` / `Received: "… MAX="`）。

### 学び

**「機械照合を入れた」は「その照合が網羅している」を意味しない。**
**照合の網の張り方が、対象を列挙する形（マーカー・許可リスト）だと、
同じ取り残しがメタレベルで再発する。** 網は**構造から導出**する
（「この列名を持つ表すべて」）ほうが良い。

## 3.7 案 F＝挙動を写した表に「実測した版」を刻む（依頼元の提案・採用済み）

**依頼元は自分の文書で既にこれをやっており、今回それがそのまま効いた。**

```
**どこから除数が来たかで結果が変わる**（実測・2026-08-06・v3.54.1）。
```

v3.54.0 の連絡を受けたとき、依頼元の表には `v3.53.0` と刻まれており、
**「この表は v3.53.0 時点の観測である＝挙動が変わった今は再確認が要る」と機械的に判定できた。**

**なぜ下流複製に効くか。**

- **複製先が自分で staleness を検出できる**（`grep 'v3\.5[0-9]'` で洗い出せる）
- **こちらが複製先を把握する必要がない**（連絡の網羅性に依存しない）
- **費用はほぼゼロ**（表を書くときに 1 行足すだけ）

**今回の 4 回目も、刻印があれば気づけた**＝除数ガードの表に `v3.53.0` と刻まれていれば、
v3.54.0 で挙動を変えたときに**刻印と実装の差**で拾えた。刻印が無かったため、
**こちらでも依頼元でも気づけなかった**。

**採用**＝挙動を写した表に `（実測・vX.Y.Z）` を刻む。まず 2 つに入れた
（除数ガードの表・空集合の戻り値の表）。**機械照合が入った表には冗長だが、
複製された先では刻印だけが手がかりになる**ので残す。

**パリティテストのマーカーは刻印を含めない形にした**（刻印を更新しただけで落ちないように）。

## 3.8 「値の表」を書くときは測る形を固定する（依頼元の指摘）

**依頼元の `CLAUDE.md` 鉄則 9（こちらが書いた分）に不整合があった。**

`fetch` の値を 4 行並べた表で、**最終行だけ `SELECT COUNT(*)` で測っていた**。

| 書き方 | 旧記載 | 同じ `GROUP BY` の形で測り直し |
|---|---|---|
| `入出庫区分 = '出庫'`（RADIO_BUTTON） | PREFILTERED | PREFILTERED |
| `入出庫区分 = '廃棄'`（定義に無い値） | ALL | ALL |
| `担当者 = 'rex0220'`（USER_SELECT） | ALL | ALL |
| `担当者 IN ('rex0220')` | **COUNT_ONLY** | **PREFILTERED** |

**`SELECT COUNT(*)` は押し下げが効いていても `COUNT_ONLY` になる**（走査しないため）。
**同じ列に並ぶと「`IN` は `=` と別物の何か」に見える。**
押し下げの有無という論点では 4 行とも正しく、結論も変わらないが、**表としては誤読を招く**。

**言語リファレンスの `fetch:` の節に、形で値が変わることと実測例を追記した**（v3.54.2）。
**分類表そのものは定義表なので混在の問題は無い**が、
**「同じ `WHERE` でも形で変わる」がどこにも書かれていなかった**。

## 4. 案

- **案 A＝文書の SQL を実行するテスト**。掲載 SQL に期待値を添えて実行し照合する。
  **障害＝ネットワークが要る**ため既存の単体テスト（228 suites・オフライン）には入れられない。
  別系統（`mcp:verify` のような実機系）に置くことになる。実データへの依存も設計が要る。
- **案 B＝実行可能な例だけ機械抽出し、固定のスタブアプリに対して実行する**。
  ネットワーク不要にできるが、**スタブの整備が本体**になる。
- **案 C＝運用ルールのみ**（公開する SQL は必ず実行してから載せる）。
  **現に守れておらず 3 回起きている**ので、これ単独では弱い。
- **案 D＝説明文を変更したら同じ節の例を必ず読み直す**、をレビュー観点として明文化。
  費用ゼロだが、**B136 のときも同じことを言って再発している**。

- **案 E＝新規に追加・変更する例だけを実行必須にする**（依頼元の提案・2026-08-06）。
  **既存の例を全部潰すより費用対効果が高い**という主張で、根拠は
  **今回の 3 件がいずれも「後から気づいた既存の例」ではなく、書いた時点で実行していれば分かったもの**だという点。
  `= 0` の ○ は**1 回実行すれば `NaN` が出る**。

**見立て＝案 E を採る（2026-08-06 に案 B から変更）。**

案 B（すべての例を実行可能に書き換える）を降ろした理由は依頼元の指摘が正しいため＝
**`APP100` のような架空アプリは読みやすさのために選ばれており、
実在アプリへ置き換えると今度は「読み手の環境で再現しない例」になる。**
費用が大きいだけでなく、**文書として悪くなる**。

**案 E で残る弱点＝機械で強制できない**（案 C と同じ弱さを持つ）。
ただし案 C が「全部の例を実行してから載せる」だったのに対し、
案 E は**変更した節の例だけ**なので、守れる大きさになっている。
**次に破れたらここへ追記して、機械化の費用と比べ直す。**

## 5. 次に開くとき必要なもの

- 文書中の SQL ブロックの本数と、うち実行可能な形（実在アプリ・実在フィールド）の本数
- `mcp:verify` に実機系のテストを足す場合の所要時間（現行の smoke / dual-era / pack の実測値）
