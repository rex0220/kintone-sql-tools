## 1. v3.29.0 の変更（engine ライブラリ）

**純加法です。**既存 API の型も挙動も変わらず、いま動いているコードはそのまま動きます。

### 1.1 `runQuery()` で既存レコード監査の `VALIDATE` が使えます

```js
const r = await runQuery("VALIDATE APP100", { client });
r.validateStats;  // { errorRecords: 3, errorCount: 5 } ← そのまま KPI に使えます
r.rows;           // 診断行（$id / $err_field / $err_code / $err_message / $err_value ほか計 9 列）
```

`validateStats` は **`VALIDATE` のときだけ載る任意フィールド**です。通常の `SELECT` には付きません。
**集計は済んだ状態で返る**ので、エラー件数の KPI は追加処理なしで出せます。
`$err_code` 別の内訳グラフは `rows` を集計してください。

### 1.2 `runBatch()` で複文と一時テーブルが使えます

```js
const r = await runBatch(
  "CREATE TEMP TABLE #cur AS SELECT ... FROM APP100 WHERE 受注日 = THIS_MONTH();" +
  "SELECT 担当者, SUM(受注金額) FROM #cur GROUP BY 担当者",
  { client }
);
r.results;  // 各要素は runQuery と同じ QueryResult
```

`CREATE` / `DROP TEMP TABLE`、`SET` / `DECLARE`、`ASSERT` に対応します。
`variables` で `DECLARE` へ外部から値を渡せるので、**クエリのパラメータ化**にも使えます。

引数の形は `runQuery` / `explainQuery` と同じ **`(sql, options)`** です。

### 1.3 失敗時は throw します（`ok` を見る実装は不要です）

**文が1つでも失敗したらエラーになり、部分結果は返しません。**
エラーから `statementIndex` / `statementType` が読めます。

```js
try {
  await runBatch(sql, { client });
} catch (e) {
  e.code;            // 既存の code 体系のまま（EXECUTION_ERROR など）
  e.statementIndex;  // 0-based
  e.statementType;   // "ASSERT" など
}
```

理由は、**プログラム API では部分結果が黙ってアプリケーションロジックへ流れ込むほうが危険**
だからです（v3.27.0 の外部結合と同じ判断）。

> 実装途中では `ok: false` と部分結果を返す形にしていましたが、
> **`ok` を見落とすと途中までの結果を完全なものとして描画してしまう**ため、
> throw する契約に改めました。`ok` フィールドはありません。

### 1.4 一時テーブルの上限は公開契約です

| 項目 | 値 |
|---|---|
| `tempTableMaxRows` | 既定 **10,000 行**（`options` で変更可） |
| 同時に存在できる表 | **最大 16**（`DROP TEMP TABLE` で枠が空きます） |
| 超過時 | **`onLimitReached: "truncate"` を指定してもエラー** |
| 実体化先 | **利用者ブラウザのプロセス内メモリ** |

**実体化先がブラウザである点が MCP との違い**です。上限は型定義にも書いてあります。

## 2. ⚠ 一時テーブルを JOIN の入力にすると server-only 関数が使えません

**ご返信の用途（複数アプリ JOIN の整理）に直結するのでご注意ください。**

相対日付・`TODAY()` / `NOW()` / `LOGINUSER()` は、
**入力に一時テーブルが1つでも含まれる文では使えません。**

**特に見落としやすい点＝関数を物理アプリ側に置いても拒否されます。**
「一時テーブルの列に関数を使わなければよい」ではありません。

```sql
-- ✅ 物理アプリを触っている間に絞る（JOIN したまま一時テーブルにできます）
CREATE TEMP TABLE #当月 AS
  SELECT d.顧客No AS k, d.売上, c.業種
  FROM APP100 d INNER JOIN APP200 c ON d.顧客No = c.顧客No
  WHERE d.受注日 = THIS_MONTH();

SELECT 業種, SUM(売上) FROM #当月 GROUP BY 業種;

-- ❌ 実体化してから絞る
CREATE TEMP TABLE #x AS SELECT ... FROM APP100;
SELECT ... FROM #x a JOIN APP200 c ON ... WHERE a.受注日 = THIS_MONTH();
```

**絞ってから実体化するほうが、ブラウザのメモリに載る行数も減ります。**
「絞り込みは物理アプリを触っている間に済ませる」と覚えていただければ大丈夫です。

なお **2つの物理アプリを直接 JOIN できる場合は、そちらのほうが強い**です
（両アプリへ別々に押し下がります）。一時テーブルは**構造の整理**のための道具とお考えください。

## 3. MCP と library の構文差をテストで固定しました

**生成 AI が MCP で SQL を作り、ダッシュボードが library で実行する**という使い方を伺い、
**両面の差は「AI が検証して通した SQL が本番で落ちる」事故になる**と理解しました。

そこで **MCP が read-only として受理する文は library でも受理する**ことを、
共通のテストで固定しました。**例外は `IMPORT` / `APPLY` / DML `VALIDATE ONLY` の3つだけ**
（いずれも書き込みを前提とした文）で、**どちらの関数（`runQuery` / `runBatch`）が受理するかまで**
固定しています。

**今後、片方の面にだけ文型が増えることは起きません。**

## 4. 確認依頼①「JOIN 内の数値フィールド比較が押し下がりません」

**意図した仕様です。ただし原因は JOIN ではなく演算子でした。**

| 述語 | 単一表 | JOIN |
|---|---|---|
| `売上 >= 5000000`（**非厳密**） | ✅ | **❌ 押し下げなし** |
| `売上 > 5000000`（厳密） | ✅ | ✅ |
| `売上 = 5000000` | ✅ | ✅ |
| `$id <= 3000` | ✅ | ✅ |

**一般の数値フィールドは `=` と厳密比較（`<` `>`）のみ**押し下げます。
`>=` / `<=` を除いているのは **IEEE-754 の境界**が理由です。
非厳密比較は境界値そのものが結果に含まれるため、表現の差で行が欠ける可能性があります。
**`$id` / レコード番号は正準な整数領域として扱えるので全比較演算子が使えます。**

### 「v3.25 以前と入れ替わった」という点について

**入れ替わってはいません。**旧実装を確認したところ、**Phase A 以前から一般の数値は厳密比較のみ**で、
`$id` だけが5演算子すべてを扱っていました。

以前「JOIN で押し下がるのは `$id` と数値のみ」と見えたのは、**当時 DATE / TEXT が
押し下がらなかった**ためで、数値の演算子範囲は変わっていません。

**回避策**: `>= 5000000` は `> 4999999` と書けば押し下がります（整数値の場合）。

## 5. 確認依頼②「選択系フィールドの `=` は押し下げ対象外か」

**そのとおりです。kintone のクエリ文法に由来します。**

kintone のクエリでは、**ドロップダウン / ラジオボタン / チェックボックス / 複数選択は
`in` / `not in` しか受け付けません**（公式のクエリ仕様）。
`=` は kintone のクエリとして**表現できない**ため、押し下げようがありません。

**言語リファレンスに明記しました**（v3.29.0）。`in` を推奨する旨も書いています。
レシピ集に追加された「選択系は `in` のほうが速い」という設計原則は、そのままで正しいです。

> なお、押し下げ可否の**全体表**を公開文書に載せる件は課題として登録しました。
> 現状は相対日付・KLIKE・JOIN の各節に分散していて横断的に読めません。
> **実装から自動生成する方式**を検討しています（手書きだと実装とずれるため）。
> Pro 側でレシピ集に実測表を作っていただいた状態は、本来こちらが解消すべきものでした。
