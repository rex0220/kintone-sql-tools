# B103 作業ツリーの行末で doc テストが落ちる

- 起票: 2026-07-30
- ステータス: ✅ **完了（v3.36.0 でリリース）**（2026-07-31）＝**案 A＋B の両方を実装**。文書を CRLF へ転ばせて 3 テストとも通ることを確認済み
- 出典: `KORDER BY` の文書修正中に踏んだ（2026-07-30）
- 関連: [B84 押し下げ表の生成・照合](../ksql_issue_tracker.md)

## 1. 実際に起きたこと

**`docs/ksql_language_reference.md` を編集したら `b84PushdownDocs.test.ts` が落ちた。**
**差分表示は上下の行が同一に見えるのに一致しない**——行末の違いだった。

```
編集前（作業ファイルが LF）  → pass
編集で CRLF に転ぶ           → fail
LF へ戻す                     → pass
```

**このテストは公開文書の表を、実装から生成した表と文字列比較する**（[B84](../ksql_issue_tracker.md)）。
**生成側は `\n` で組み立てるため、読み込む側が CRLF だと必ず一致しない。**

## 2. 測定（2026-07-30）

### 2.1 作業ツリーの行末はばらばら

```
git ls-files --eol
  515 件  i/lf w/crlf     ← index は LF、作業ファイルは CRLF
  130 件  i/lf w/lf
   80 件  i/lf w/mixed    ← 混在
    7 件  binary
```

**index は全ファイル LF で揃っている。作業ツリーだけが割れている。**

### 2.2 原因

| | |
|---|---|
| `core.autocrlf` | **`true`**（checkout で LF → CRLF に変換される） |
| `.gitattributes` | **無い**（eol を固定していない） |
| 書き込む側 | **ツールによって違う**。こちらの編集スクリプトは `\n` で書き、エディタ系は CRLF で書く |

**80 件の「混在」は、同じファイルを別々のツールが編集した跡である。**

### 2.3 影響を受けるテスト

**`docs/` を直接読むテストは 3 つ。いずれも行末を正規化していない。**

| テスト | CRLF で落ちるか |
|---|---|
| `b84PushdownDocs.test.ts` | **落ちる**（表全体を文字列比較するため） |
| `b67RelativeDateDocs.test.ts` | 落ちない（`toContain` で 1 行ずつ見るため） |
| `docsResources.test.ts` | 落ちない（同上） |

**落ちるのは 1 つだけだが、落ち方が分かりにくい。**
**差分が目視で同一に見えるため、原因にたどり着くまで時間がかかる。**

> **`scripts/version-sync-guard.mjs:102` も `docs/ksql_language_reference.md` を読む。**
> **こちらは版数文字列の検索なので行末に依存しない。**

## 3. なぜ今まで表面化しなかったか

**この文書を書き換えるのが、ほぼ常に `\n` で書くスクリプトだったため。**
**その結果、作業ファイルが偶然 LF に保たれていた。**

**新規 clone した Windows 環境では、checkout の時点で CRLF になる。**
**そこでは最初から落ちるはずである**（未確認）。

## 4. 案

### 案 A: `.gitattributes` で eol を固定する（**根本**）

```
* text=auto eol=lf
```

- **checkout が常に LF で書く。**作業ツリーの割れが消える
- **80 件の「混在」も解消する**
- **index は既に全 LF なので、コミット内容は変わらない**
- **作業ツリーの 595 件（CRLF 515 ＋ 混在 80）が書き換わる**——
  **git の差分には出ないが、エディタによっては一度リロードが要る**

### 案 B: doc を読むテストで正規化する（**対症・零リスク**）

```ts
readFileSync(path, "utf8").replace(/\r\n/g, "\n")
```

- **3 テストに 1 行ずつ**。影響範囲がゼロ
- **落ちている 1 件は直る**
- **作業ツリーの割れは残る。**別の場所で同じことが起きうる

### 案 C: 何もしない

- **踏むのは文書を編集したときだけ**で、原因が分かっていれば戻せる
- **次に踏んだ人は同じ時間を使う**

## 5. 現時点の見立て

**案 A ＋案 B の両方を推す。優先度は 低。**

- **案 A が根本**——`.gitattributes` が無いことが割れの原因である
- **案 B も要る**——**`.gitattributes` を持たない古い作業ツリーでも通るようにする**ため。
  テストは「文書の内容」を検査しているのであって、行末を検査しているのではない
- **優先度が 低 なのは、製品の挙動に影響しないため。**踏むのは開発時だけである

**次に開くときに必要なもの**

1. **新規 clone した Windows 環境で `b84PushdownDocs.test.ts` が実際に落ちるか**
   ＝**§3 の推測の確認。案 A の緊急度がこれで決まる**
2. **案 A を入れたときに、`prod/js/desktop.js` などの生成物の差分が出ないか**

## 6. 対象外

| | 理由 |
|---|---|
| **`core.autocrlf` の変更を利用者に求める** | **リポジトリ側で決めるべき**。各自の設定に依存させない |
| **生成物の行末統一** | **`.gitattributes` の効果として付いてくる**。単独では扱わない |
| **文書の内容そのもの** | 別の話 |
