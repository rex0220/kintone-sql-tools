# B142 集計する値が無いとき、`MIN` / `MAX` の戻り値が経路で割れる

- 状態: 📝 **起票・射程の実測まで完了。方向は案 A で確定、着手は未**（2026-08-06）
- 種別: 課題（静かに間違う）
- 優先: 中
- 発見: B141 の検証中（依頼元の「集計を通した値は空にならない」を裏取りしていて出た）

## 1. 実測（v3.53.0・APP4228 / APP4229）

**「集計する値が 1 つも無い」という同じ状況で、経路によって `"0"` と `""` に割れる。**

| 経路 | `MIN` / `MAX` | `SUM` / `AVG` | `COUNT` |
|---|---|---|---|
| **0 行のスカラー集計**（`WHERE` が全部落ちる） | **`"0"`** | `0` | `0` |
| **全行が空の値**（`CASE` に `ELSE` が無い） | **`"0"`** | `0` | `0` |
| **`LEFT JOIN` で一致しないグループ** | **`""`** | `0` | `0` |

```sql
-- 0 行のスカラー集計 → "0"（長さ 1 の文字列。= '' は偽）
SELECT MIN(製品名), LENGTH(MIN(製品名)) FROM APP4228 WHERE 製品名 = '存在しない製品'
--  "0" / "1"

-- 全行が空の値 → "0"（1,000 行すべて空。COUNT は 0）
SELECT MIN(CASE WHEN 個数 > 999999 THEN 個数 END), COUNT(*) FROM APP4228
--  "0" / "1000"

-- LEFT JOIN 不一致 → ""
SELECT m.製品名, MIN(s.出庫数), MIN(s.初日), MIN(s.製品名)
FROM APP4229 m LEFT JOIN #一部 s ON m.製品名 = s.製品名 GROUP BY m.製品名
--  ほうじ茶 / "" / "" / ""
```

**`SUM` / `AVG` / `COUNT` は三経路とも `0` で一貫している。割れているのは `MIN` / `MAX` だけ。**

### 型は関係ない

0 行のスカラー集計は**どの型でも `"0"`** を返す。

```sql
SELECT MIN(日付), MIN(作成日時), MIN(入出庫区分), MIN(レコード番号), MIN(個数_在庫計算用)
FROM APP4228 WHERE 製品名 = '存在しない製品'
--  すべて "0"（DATE / CREATED_TIME / RADIO_BUTTON / RECORD_NUMBER / CALC）
```

対象行があれば正しく動く（`MIN(製品名)` = `"ほうじ茶"` / `MAX(製品名)` = `"食パン"`）。
**値が無いときだけ**の挙動。

## 2. 標準 SQL との関係

`GROUP BY` の無い集計は対象行が 0 でも必ず 1 行を返し、その値が規定されている。

| 集計 | 標準 SQL | 主要実装 |
|---|---|---|
| `COUNT(*)` / `COUNT(式)` | `0` | MySQL / PostgreSQL / SQL Server / Oracle とも `0` |
| `SUM` / `AVG` / `MIN` / `MAX` | **`NULL`** | 4 実装とも `NULL`。**方言差は無い** |

**標準では `MIN` / `MAX` の戻り値は引数の型に依存しない。** 数値でもテキストでも日付でも `NULL`。
また**標準では `NULL` が伝播するので `NaN` は起きない**（`1000 / NULL` は `NULL`）。
kSQL で [B141](ksql_b141_doc_sql_unverified_issue.md) の一連の罠が起きるのは、
**NULL が無く、空文字と `0` が場面ごとに行き来する**ため。

## 3. なぜ問題か

**同じ状況が経路で違う値になる**こと自体が問題。利用者は経路を意識しない。

**静かに間違う。** エラーも警告も出ず、`"0"` が製品名として下流へ流れる。

```sql
SET @最古 = (SELECT MIN(製品名) FROM APP4228 WHERE 分類 = @分類);
-- 該当が無いと @最古 は "0"。空判定 (= '') をすり抜ける
SELECT * FROM APP4229 WHERE 製品名 = @最古;   -- 0 件だが「該当なし」だと判定できない
```

**[B119〜B122](../ksql_issue_archive.md) と同じ系列**＝止まらず、結果だけが違う。

**`MIN(日付)` が `"0"` になるのはとくに悪い**。日付として解釈できない値が日付列の位置に出る。

## 4. 方向＝案 A（`MIN` / `MAX` は値が無ければ空文字）

**`LEFT JOIN` の経路が既に `""` を返している。** そこへ他の 2 経路を揃える。

**これは新しい約束事の導入ではなく、kSQL 自身の既存の挙動への統一**である点が重要。

- **`SUM` / `AVG` / `COUNT` は変えない**（三経路とも `0` で一貫しており、変える理由が無い）
- したがって
  [言語リファレンスの「集計を通した値は該当が無いと `0`」という案内](../ksql_language_reference.md)は
  **そのまま維持できる**（`MIN` / `MAX` の `""` は除数に使う形ではない）
- **型ごとに既定値を分ける必要も無い**。標準 SQL も型に依存しない

### 検討して降ろした案

- **案 A′＝全集計を空文字に**（標準の `NULL` に最も近い）。
  **`SUM` が `0` を返す前提が全滅する**うえ、B141 で出したばかりの案内も撤回になる。
  得られるのは「合計が本当に 0」と「行が無かった」の区別だけで、代償が釣り合わない。
  **この区別が要る場面では `COUNT` を併記すればよい**（`COUNT` は三経路とも正しく `0`）。
- **案 A″＝テキスト列だけ空文字に**。**実測で型は無関係と分かったので不要**になった
  （日付・時刻・選択肢・レコード番号・計算フィールドすべてが `"0"`）。
- **案 B＝文書化のみ**。**経路で割れている状態を文書で説明することになり、読み手に経路の判別を強いる**。
- 案 C＝何もしない。

## 4.5 調査結果＝`""` は意図した実装、`0` の根拠は誤り（2026-08-06）

**`LEFT JOIN` 経路の `""` は副作用ではなく、設計された挙動だった。**

`5e14418`（2026-07-17「canonical typed comparison semantics」）で導入され、
コメントが残っている。

```
// 各行で arg を評価する。MIN/MAX は空セルも canonical band の値として保持する。
if (raw === undefined || (raw === "" && func !== "MIN" && func !== "MAX")) return null;
```

**`ORDER BY` と一致することも実測で確認した。**

```sql
SELECT m.製品名, s.出庫数 FROM APP4229 m LEFT JOIN #一部 s ON ... ORDER BY s.出庫数 LIMIT 3
--  ライ麦パン ""  /  ほうじ茶 ""  /  バター "558"
```

**空は並びの先頭に来る。`MIN` の `""` はその 1 行目そのもの**で、
`MIN` / `MAX` は「値の集合の最小・最大」ではなく**「kSQL 自身の並びの先頭・末尾」**として定義されている。
[言語リファレンス](../ksql_language_reference.md) にも
「選択された空セルは canonical empty band の候補」と明記があり、テストでも固定されている
（`process.test.ts` の `MIN / MAX: 文字列型の DISTINCT・空文字・修飾フィールドを扱う`、
`b64AggregateScalarArg.test.ts` の `B64-E04/E05/E06: MIN/MAX は非一致NULL・選択空セル・明示空文字を区別する`）。

**「空」は内部で 3 種類に分かれている。**

| 種類 | 例 | `MIN` / `MAX` |
|---|---|---|
| **非一致 NULL** | `CASE` に `ELSE` が無く条件に外れた行 | **スキップ**（値として数えない） |
| **選択された空セル** | 実データの空セル・`LEFT JOIN` の不一致 | **保持**（並びの先頭） |
| **明示した空文字** | `ELSE ''` | **保持** |

これが「`CASE` 版は `"0"`・`LEFT JOIN` 版は `""`」の理由。**前者は値が 0 個、後者は空という値が 1 個。**

### `0` の側

`return 0` も意図的だが、**根拠として書かれている理由が事実と違う**。

```
// GROUP BY なし集計は入力 0 行でも 1 行返す（SQL 標準準拠。COUNT=0、SUM/AVG/MIN/MAX は
// 全値空グループと同じ 0 — 空集合だけ NULL にすると ksql 内の既存規約と不整合になる）。
```

**「全値空グループと同じ 0」が `MIN` / `MAX` については成り立たない。**
実測でも既存テストでも、**全値空グループの `MIN` / `MAX` は `""`**（`0` ではない）。
`SUM` / `AVG` については正しい。

**さらに `MODE` は空集合で `""` を返す**（同じ関数の 1 つ上の行）。
**比較系の集計で `0` を返すのは `MIN` / `MAX` だけ**で、揃えるべき先ははっきりしている。

```ts
if (func === "MODE")            { if (strValues.length === 0) return "";  ... }
if (func === "MIN" || "MAX")    { if (comparableValues.length === 0) return 0; ... }  // ← ここ
```

### 費用（実装後に訂正）

**「固定する既存テストは無い」と書いたが誤りだった。2 本あった。**
（`B64-E09` だけを見て判断した。`空入力` という語と `mn` / `mx` という別名を使うテストを
grep が拾えていない。**「無い」の確認は grep ではなく実行で取るべきだった**）

| テスト | 旧 | 新 |
|---|---|---|
| `process.test.ts` `空入力 + GROUP BY なし: 全集計関数が 0 を返す` | `mn` = `mx` = `"0"` | `""`（`COUNT` / `SUM` / `AVG` は `0` のまま） |
| `execute.test.ts` `UPDATE SET スカラーサブクエリ — 0 件集計は 0 に解決される（v1.12.0）` | 書き込む値 `"0"` | `""` |

**2 本目は DML の挙動変更**なので独立して扱う（→ §4.6）。

### 4.6 DML への波及＝書き込む値が変わる

```sql
UPDATE APP88 SET 上限費用 = (SELECT MAX(合計費用) FROM APP88) WHERE 確度 IN ('80%')
```

サブクエリが **0 件のとき、NUMBER 列へ書き込む値が `0` から空へ変わる。**

**これは意図した変更**＝該当が 1 件も無いときに「最大値は 0」と書き込むのは事実に反し、
**`0` という実在しない値がレコードに残る**。標準 SQL の `MAX(空集合)` = `NULL` に対応し、
kSQL の NULL 相当は空文字。

**ただし利用者から見れば挙動が変わる。**

- **必須フィールドが対象なら、これまで通っていた `UPDATE` が失敗するようになる**
  （空を書けないため）。**静かに `0` を書くより、止まるほうが正しい**が、移行案内が要る
- 既に `0` が書き込まれているレコードは**そのまま**（遡って直らない）
- **`SUM` / `AVG` / `COUNT` は変わらない**ので、集計を代入する大半の形は影響を受けない

## 5. 着手前に要るもの

**§4.5 で 3 点とも解消した。** 残るのは実装のみ。

- ~~`"0"` の出どころ~~ → `process.ts` の `MIN` / `MAX` 分岐の `comparableValues.length === 0` で `return 0`
- ~~既存テストの有無~~ → **無い**（`B64-E09` は空入力を `COUNT` / `SUM` / `MODE` でだけ固定）
- ~~`""` は意図か副作用か~~ → **意図**（`5e14418`・`ORDER BY` と一致・文書化済み・テストで固定）

実需は未確認。**依頼元も踏んでいない**（除数が集計経路のみで、`MIN` / `MAX` の空集合を使っていない）。

### 実装するときの範囲

- `process.ts` の `MIN` / `MAX` 分岐＝`return 0` を `return ""` へ
- 新規テスト＝空入力の `MIN` / `MAX`、全値空グループとの一致、`MODE` との一致
- **ウィンドウ版の `MIN` / `MAX`（`OVER`）にも同じ分岐があるか確認**
- 文書＝空集合の戻り値を関数ごとに表で示す（`COUNT` = `0` / `SUM` `AVG` = `0` /
  `MIN` `MAX` `MODE` = `''`）
