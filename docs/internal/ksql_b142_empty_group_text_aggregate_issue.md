# B142 0 行の集計が、テキスト列でも `0` を返す

- 状態: 📝 **起票のみ**（2026-08-06）
- 種別: 課題（静かに間違う）
- 優先: 中
- 発見: B141 の検証中（依頼元の「集計を通した値は空にならない」を裏取りしていて出た）

## 1. 実測

```sql
SELECT MIN(製品名) AS t, LENGTH(MIN(製品名)) AS 長さ,
  CASE WHEN MIN(製品名) = '' THEN '空' ELSE '空でない' END AS 判定
FROM APP4228 WHERE 製品名 = '存在しない製品'
```

```
t="0"  長さ="1"  判定="空でない"
```

**`MIN(製品名)` が、1 文字の文字列 `"0"` を返す。** 空文字ではない。

対象行がある場合は正しく動く。

```
MIN(製品名)="ほうじ茶"  MAX(製品名)="食パン"  COUNT(*)=905
```

**0 行のときだけ**の挙動。数値列でも同じ（`SUM` / `MIN` / `MAX` / `AVG` が `0`）。

| 集計 | 0 行のとき（kSQL） | MySQL |
|---|---|---|
| `COUNT(*)` / `COUNT(col)` | `0` | `0` |
| `SUM` / `AVG` / `MIN` / `MAX`（数値列） | `0` | `NULL` |
| `MIN` / `MAX`（テキスト列） | **`"0"`** | `NULL` |

## 2. なぜ問題か

**数値列の `0` は妥当**（kintone に NULL が無く、空セルが `0` として算術に入る現行の設計と一貫する）。
**テキスト列の `"0"` は、その一貫性から外れている。** kSQL の NULL 相当は空文字なので、
**期待される値は `""`**。数値側の既定がテキスト集計へ漏れているように見える。

**静かに間違う。** エラーも警告も出ず、`"0"` が製品名として下流へ流れる。

```sql
SET @最古 = (SELECT MIN(製品名) FROM APP4228 WHERE 分類 = @分類);
-- 該当が無いと @最古 は "0"。空判定 (= '' / IS NULL) をすり抜ける
SELECT * FROM APP4229 WHERE 製品名 = @最古;   -- 0 件だが「該当なし」だと判定できない
```

**B119〜B122 と同じ系列**＝止まらず、結果だけが違う。

## 3. 射程（未確認）

- `MIN` / `MAX` 以外にテキストを取る集計があるか（`GROUP_CONCAT` 相当は無い）
- 日付・時刻・選択肢型の 0 行集計は何を返すか
- `GROUP BY` 付きで**グループ自体が生まれない**場合は行が出ないので該当しない。
  **該当するのは `GROUP BY` の無い集計と、`LEFT JOIN` 越しの集計**
- [B141 で書いた「集計を通した値は空にならない」という案内](../ksql_language_reference.md)は
  **本件があっても崩れない**（`"0"` も空ではない）。ただし
  **「集計は必ず 0 を返す」と読まれるとテキスト列で誤解になる**

## 4. 案

- **案 A＝テキスト列の 0 行集計は空文字を返す**。型ごとに既定値を分ける。
  **懸念＝既存の挙動が変わる**。`MIN(テキスト)` の結果を `= 0` で判定している利用者がいれば壊れる
  （**そんな書き方をする理由が無いので実害は薄いと見ている**が、要確認）
- **案 B＝文書化のみ**。0 行集計の戻り値を型ごとに表で示す
- **案 C＝何もしない**

**見立て＝案 A + 案 B。** ただし**実需は未確認**で、依頼元も踏んでいない。
**先に射程（§3）を測ってから**方向を決める。

## 5. 次に開くとき必要なもの

- `MIN` / `MAX` の実装で既定値がどこから来ているか（型情報を持っているか）
- 既存テストで 0 行集計の戻り値を照合しているものの有無
