# B84 どの述語が押し下がるかが公開ドキュメントに無い

- 起票: 2026-07-27
- ステータス: ✅ **リリース済み（v3.30.0・2026-07-28）**。案 B（テストで生成・照合）で実装。
- 出典: Pro（ksql-dashboard-pro）返信 2026-07-27 の「確認させていただきたい 2 点」
- 関連: [B76 Phase A spec](ksql_b76_join_pushdown_phase_a_spec.md) / [B83 MCP カタログ drift](ksql_b83_mcp_validate_columns_docs_issue.md) / [B74 相対日付 docs 是正](ksql_b74_relative_date_docs_accuracy_issue.md)

## 1. 事象

Pro から**2 つの質問**が来た。**どちらも「押し下がるかどうか」が公開文書に無い**ことに起因する。

### 1.1 質問①「JOIN 内の数値フィールド比較が押し下がらない」

```sql
-- 単一表: 押し下がる
SELECT COUNT(*) FROM APP4149 WHERE 売上 >= 5000000

-- JOIN: 押し下がらない（全件取得）
SELECT COUNT(*) FROM APP4149 d JOIN APP4148 c ON d.顧客No_ = c.顧客No
WHERE d.売上 >= 5000000
```

Pro は「**意図した仕様か、あるいは見落としか**」と尋ねてきた。

**実機で切り分けた結果＝意図した仕様。**演算子の違いだった。

| 述語 | 単一表 | JOIN |
|---|---|---|
| `案件No >= 5`（**非厳密**） | ✅ | **❌ 全件取得** |
| `案件No > 5`（厳密） | ✅ | ✅ |
| `案件No = 5` | ✅ | ✅ |
| `$id <= 3000` | ✅ | ✅ |

根拠は Phase A spec §5.2 にある。

> `NUMBER … * strict `<` / `>` かつ右辺が安全整数。**IEEE-754 境界のため inclusive は不可**`

§0.3.6-3 でも「一般 NUMBER は `=` と strict `<`/`>` 安全整数だけ S。**`>=`/`<=` は U**」と明記され、
非スコープとしても列挙されている。

**Pro の「v3.25 以前と入れ替わった」という見立ては誤解。**
旧抽出器 `isNumericCandidate`（`wherePredicatePushdown.ts`）を確認したところ、
**Phase A 以前から一般 NUMBER は厳密のみ**で、`$id` だけが 5 演算子すべてを扱っていた
（`isSafeIdComparison`）。数値の演算子範囲は変わっていない。

### 1.2 質問②「選択系フィールドの `=` は押し下げ対象外か」

```sql
SELECT COUNT(*) FROM APP4148 WHERE 顧客ランク = 'A'    -- 全件取得（215 件）
SELECT COUNT(*) FROM APP4148 WHERE 顧客ランク in ('A') -- 押し下げ（59 件）
```

**そのとおりで、kintone 側の制約に由来する。**
kintone のクエリ文法では**ドロップダウン・ラジオ・チェックボックス・複数選択は
`in` / `not in` しか受け付けない**（公式表で確認済み）。`=` は kintone クエリとして
**表現できない**ので押し下げようがない。

Pro は**「そうであれば言語リファレンスに明記いただけると助かります」と明示的に依頼**している。

## 2. 原因＝「押し下がるか」が利用者から見えない

**結果は常に正しいので不具合ではない。**しかし**取得件数が数倍変わる**（Pro の実測で 3.6 倍）。

- 公開文書には**押し下げの可否表が無い**
- `EXPLAIN` を読めば分かるが、**読み方を知っている利用者に限られる**
- 結果が正しいため**気づく契機が無い**。遅いだけで動いてしまう

**Pro は自前でレシピ集に実測表を作った。**利用者に実測させている状態であり、
**エンジン側が正を出すべき情報**である。

## 3. 対応案

### 3.1 公開すべき内容

| 区分 | 内容 |
|---|---|
| **単一表** | WHERE 全体を exact に直列化できれば型を問わず押し下がる |
| **JOIN** | 型 × 演算子の可否表。**NUMBER は `=` と strict `<` / `>` のみ**、`$id` は全比較演算子 |
| **選択系** | **`=` は押し下げ不可**（kintone のクエリ文法が `in` / `not in` のみ）。`in` を推奨 |
| **関数付き** | `DATE_FORMAT(field, ...)` のようにフィールドを関数で包むと押し下げ不可 |

### 3.2 置き場所

言語リファレンスに**押し下げの節を新設**するのが素直。
現状は相対日付・KLIKE・JOIN の各節に分散しており、**横断的に読めない**。

### 3.3 生成できないか

Phase A の matrix（§5.2）は**実装のデータ構造**であり、
`classifyJoinPushdownLeaf` の分類と対応する。**表を実装から生成できれば drift しない**
（B60 が statement templates と function catalog で採っている方式）。

手書きすると B74 / B83 と同じ drift を起こす。**生成を優先して検討すること。**

## 4. 規模

- 手書きで表を追加するだけなら **0.5 人日**
- 実装から生成する場合 **1〜1.5 人日**
- **公開挙動の変更なし**

## 5. 優先度の根拠

**利用者からの明示要望があり、実害（取得件数の差）も実測されている。**
B68 Step 5 で言語リファレンスに触れるので、**同時に入れると追加コストが小さい**。

ただし §3.3 の生成方式を採るなら独立した作業になる。
