# B63 — プラグイン面での SQL 構文・関数の説明表示（評価）

- ステータス: 📝 **【A: 評価・方向判断】起票（2026-07-22）**。プラグインの SQL 入力画面から、kSQL の構文骨格・関数・解説をその場で参照できるようにする案。仕様前・実需/UI 方針の確認待ち。
- 種別: 機能（面 UX）
- 優先: 中
- 関連: [B55 `ksql_docs`](ksql_b55_mcp_docs_tool_fallback_issue.md) / [B60 MCP Statement syntax catalog](ksql_b60_mcp_syntax_hints_issue.md) / [B50 MCP discoverability](ksql_b50_mcp_discoverability_spec.md)

## 1. 背景・課題

プラグイン利用者が kSQL を書くとき、**構文・関数の説明が画面内にない**。kSQL は標準 SQL と異なる方言（LIKE=JS 意味論・JOIN 単一等値・派生テーブル非対応・`UPSERT … ON DUPLICATE` 必須・`CHECK` の評価行が文種別・`ON ERROR SKIP INTO #err` はバッチ専用・`KLIKE`/`KORDER BY`・`@variables` など）で、標準 SQL の一般知識では正しく書けない。

現状、構文・関数の一次情報は次の面にしかない。

- リポジトリの言語リファレンス（`docs/ksql_language_reference.md`）・レシピ・Qiita 記事 → **プラグイン画面の外**
- MCP の `ksql_docs`（B55）・server instructions の構文カタログ（B60） → **AI/MCP クライアント向け**。プラグインを手で使う利用者には届かない

つまり「AI には構文カタログを届けたが（B60）、**人がプラグインで手書きするときの導線がない**」。これは B55/B60 と同じ問題（機能名・意味論はあるが、書くその場に骨格が無い）の**プラグイン面版**。

## 2. 固有価値

- プラグインの SQL 入力画面から、**構文骨格・関数一覧・解説をその場で参照**できる（画面遷移や外部ドキュメント検索なしで方言差を確認）。
- 既存の**機械同期済みカタログを再利用**できる: B60 の `STATEMENT_SYNTAX_CATALOG`（18 文型の骨格・句順・併用規則）と B55 の関数カタログ（scalar/aggregate/window/contextual/alias）・言語リファレンス章。**新たな説明文を二重管理しない**のが要点。
- API 不要・オフライン（ビルド埋め込み）で完結。プラグインの SQL 実行とは独立した read-only の参照 UI。

## 3. 設計案（たたき台）

- **データソース**: 既存カタログをビルド時にプラグインバンドルへ埋め込む。
  - 構文: `src/mcp/statementSyntaxCatalog.ts` の family 骨格（B60）。
  - 関数: B55 の関数カタログ（scalar 46 / aggregate 12 / window / contextual / alias）と各説明。
  - 解説章: 言語リファレンスの章別 markdown（B50/B55 の `ksql://` セクション語彙と同一）。
  - **drift guard に乗せる**: 表示内容は catalog⇔parser⇔fixture の既存 drift guard（B55/B60）の下流に置き、実装とズレたら CI で落とす。
- **UI**: SQL 入力ヘッダー付近に「構文ヘルプ」ボタン → モーダル or サイドパネル。カテゴリ（文型 / 関数 / 演算子・方言注意）＋インクリメンタル検索。日本語表示。
- **スコープ段階案**:
  - Phase1: 文型骨格一覧（B60 の 18 family）＋方言注意（LIKE/JOIN/派生テーブル/CHECK 評価行/バッチ専用句）。
  - Phase2: 関数カタログ（名前・シグネチャ・一行説明・例）。
  - Phase3: 言語リファレンス章のインライン閲覧（`ksql_docs` 相当を面内に）。

## 4. 論点

- **表示範囲**: 骨格だけで足りるか、関数・章まで面内に持つか（バンドルサイズと保守コストのトレードオフ）。
- **データ供給**: ビルド埋め込み（オフライン・drift guard 可）か、リンクアウト（Qiita/リポジトリ）併用か。Phase1 は埋め込みで小さく。
- **UI 形態**: モーダル / サイドパネル / 入力補完のツールチップ。まずは非侵襲なモーダルが安全。
- **保守**: 説明文の出所を既存カタログに限定し、プラグイン専用の説明を新規に増やさない（増やすと drift 源になる）。
- **プラグイン制約**: desktop.js は EXPLAIN エンジンをバンドルする都合があり（論理アプリ非対応など既知の面差）、表示専用機能は SQL 実行経路に影響しないよう分離する。
