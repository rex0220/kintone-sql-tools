## 1. ⚠ 破壊的変更（B86）— 引用符の付け忘れがエラーになります

**存在しない列を参照する SQL が、エラーになります。**

```sql
-- 従来: 977 件（全件）が返っていた。エラーも警告も無し
WITH A AS (SHOW APPS) SELECT * FROM A WHERE アプリ名 LIKE 顧客

-- v3.30.0: 取得前にエラー
--   ArgumentError: unknown field code(s): 顧客 (A)
```

### なぜ全件が返っていたか

**裸の識別子は列参照として解釈されます**（実在列なら列同士の比較として正しく動きます）。
存在しない列は**空文字として評価**されるため、

| 演算子 | 従来の挙動 |
|---|---|
| `LIKE` | **全件一致**（空パターンは任意の文字列に含まれる） |
| `=` | 0 件 |
| **`INSERT ... SELECT`** | **空文字レコードを実際に書き込む** |

### Pro 側でご確認いただきたいこと

**レシピ・テンプレート・AI が生成した SQL に、引用符の無い文字列リテラルが無いか**を
ご確認ください。該当すると v3.30.0 でエラーになります。

```sql
WHERE アプリ名 LIKE 顧客     -- ❌
WHERE アプリ名 LIKE '顧客'   -- ✅
```

**現在成功して見えるクエリは実際には誤った結果を返している**ため、
エラー化によって正しい結果が失われることはありません
（v3.25.0・v3.27.0 と同じ判断基準です）。

**対象は実体化ソース**（CTE・一時テーブル・`SHOW APPS` / `DESCRIBE`・サブクエリ・
`UNION` 枝・混在 JOIN）です。**物理アプリ単独の SELECT は従来どおり**で、元からエラーでした。

なお**混在 JOIN では物理アプリ側の不存在列も**同じ検査で拒否するようになりました
（従来は物理側の検証まで迂回していました）。**検査に失敗した場合、取得も書き込みも行いません。**

## 2. 確認依頼③への回答 — **原因はご推測と違いました**

**「`ReadonlyFieldInfo` に制約を渡す口が無い＝契約上の限界」というご推測は、外れています。**
調べたところ**パイプラインは制約を素通ししていました。**

| `getFields` の返り値 | 検出 |
|---|---|
| `{ code, label, fieldType, minLength: "3", required: true }` | **2 件検出** |
| `{ code, label, fieldType }` | 0 件 |

**真因は型が宣言していなかったこと**です。`optionOrder` だけ宣言され、
`minLength` / `maxLength` / `minValue` / `maxValue` / `required` がありませんでした。
**TypeScript は余剰プロパティを拒否する**ので、**渡そうとしても止められる**状態でした。

### ⚠ `createReadonlyKintoneClient` をお使いなら、既に検証できているはずです

同関数は `/k/v1/app/form/fields.json` を読み、**実行時には制約を返していました**
（型だけが狭められていた）。

**0 件だったということは、自前クライアントをお使いではないでしょうか。**
その場合、`getFields` の返り値に制約を含めれば**それだけで文字数・必須・上下限が検証されます**。

**メタデータの取得量は増えません。**同じ `fields.json` を既に取得しているためです。
ご懸念いただいたコスト増は発生しません。

### v3.30.0 での対応

**型に宣言しました**（純加法）。

```ts
interface ReadonlyFieldInfo {
  // ...既存
  required?: boolean;
  minLength?: string; maxLength?: string;
  minValue?: string;  maxValue?: string;
}
```

**さらに、検証範囲を開示するようにしました。**

```js
r.validateStats.constraintMetadata;
// { present: ["choice"], absent: ["required", "length", "range"] }
```

ご要望は「`warnings` に載るだけでも」でしたが、**警告ではなく開示**にしています。
理由は、**制約が 1 つも無いアプリが実在する**ためです
（弊社検証環境の 1 アプリは 21 項目すべて制約なしでした）。
そこで警告を出すと誤警告になり、**無視される警告は無いのと同じ**になります。

また**ライブラリは「アプリに制約が無い」と「クライアントが落としている」を
原理的に区別できません。**そこで推測をやめ、**渡されたメタデータの事実だけ**を返しています。

**「0 件でした」より「選択肢だけ検証して 0 件でした」のほうが、誤った安心を与えません。**
`present` / `absent` をペインの注記にお使いいただけます。

## 3. `SUM($err_count)` のご指摘 — こちらの案内が誤りでした

前回「`$err_code` 別の内訳グラフは `rows` を集計してください」と書きましたが、
**`COUNT(*)` では `validateStats.errorCount` と一致しません。**ご指摘のとおりです。

**言語リファレンスと engine ライブラリ利用ガイドの両方へ、`SUM($err_count)` を使う旨と、
KPI と棒グラフで合計が食い違う例を明記しました。**

---

## 4. 押し下げ可否表を公開しました（B84）

**言語リファレンスに JOIN の型 × 演算子表を追加しました。**

**実装から生成して照合**しているので、実装とずれません
（分類器のソースを走査し、表と一致しなければテストが落ちます）。

表が説明するのは**「alias 付き物理 APP だけを入力にする INNER JOIN で、
1 つのフィールドを 1 つのリテラルと比較する単一の条件」**だけです。
**単一表・`$id`・server-only 関数・`KLIKE` は別の規則**である旨も明記しました。

「単一表では押し下がるのに JOIN では」というご質問は、**まさにこの 2 機構の差**でした。

レシピ集からの参照切り替え、よろしければお願いします。

MCP の説明が `fixed five diagnostic columns` となっていましたが、**実際は 9 列**でした。
**`SUMMARY` を付けた場合が 5 列**で、2 形あることを明記しました。

## 6. ご質問への回答 — parity テストの範囲

> テスト固定は**受理可否**の担保であって**結果の一致**は対象外、という理解で合っていますか。

**合っています。**「MCP が read-only として受理する文は library でも受理する」ことだけを
固定しており、**同じ文が同じ結果を返すことは対象外**です。

**今回の確認依頼③は、まさにその隙間**でした。
「結果の一致」の機械的な固定は、**両面が同じメタデータを持つ前提**が要るため、
今回の修正を見てから検討します。
