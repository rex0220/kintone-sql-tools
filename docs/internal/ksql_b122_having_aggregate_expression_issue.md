# B122 `HAVING` に集計を式でくるんで直接書くと、無言で 0 行になる

- 起票: 2026-08-05
- ステータス: 🐞 **未着手（優先 高）**（2026-08-05）。**エラーを出さずに 0 行を返す。**
  利用者からは「条件を満たすグループが無かった」と区別がつかない。
- 出典: [B121](ksql_b121_having_numeric_comparison_issue.md) の完了後、
  「集計と別名で処理が分かれる構文が他にもないか」を洗っていて発見（`ksql-analytics` で実測）
- 関連: [B121](ksql_b121_having_numeric_comparison_issue.md)（`HAVING` の直接参照・**同じ構図の残り**）/
  [B120](ksql_b120_aggregate_position_diagnostics_issue.md) §2（`HAVING` の無言 0 行）/
  B119・B117・B118（「静かに間違う」系）
- **既存の欠陥**: B119/B120/B121 適用前（`94a8cd4`）でも同一結果。今回の実装とは無関係

## 1. 症状（実測 2026-08-05・APP4149・20 件 / 10 社）

**同じ条件を別名で書けば正しく、直接書くと 0 行**になる。別名側の値が正しい答え。

| `HAVING` に書いた式 | 直接参照 | 別名参照 |
|---|---:|---:|
| `SUM(売上) - 0 > 9` | **0 行** | 8 行 |
| `SUM(売上) * 1 > 9` | **0 行** | 8 行 |
| `SUM(売上) - SUM(売上) > -1` | **0 行** | 10 行 |
| `COUNT(*) + 0 > 1` | **0 行** | 5 行 |
| `ROUND(AVG(売上), 0) > 9` | **0 行** | 8 行 |
| `SUM(CASE WHEN 売上 > 0 THEN 売上 ELSE 0 END) > 9` | 8 行 | 8 行 ○ |

### 境界

`HAVING` の直接参照で**評価されるのは次の 2 つだけ**。

- 素の集計（`SUM(x)` / `COUNT(*)` / `AVG(x)` …）— B121 で数値比較も直った
- 集計の**引数**としての `CASE`（`SUM(CASE ... END)`・B64）

**集計を算術式（`- 0` / `* 1` / 集計どうしの演算）やスカラー関数（`ROUND(...)`）でくるむと、
評価対象から外れて無言で 0 行**になる。`SELECT` に同じ式を別名付きで置いても、
素の `SUM(売上)` を併記しても直らない。

### 再現

```
ksql --profile dev -e "SELECT 会社名, SUM(売上) - 0 AS d FROM APP4149 GROUP BY 会社名 HAVING SUM(売上) - 0 > 9"
→ 0 行（別名 d で書けば 8 行）
```

## 2. なぜ重いか

- **エラーが出ない。** 0 行は「該当なし」と読まれ、レポートに「対象 0 件」と載る
- `HAVING SUM(a) - SUM(b) > 0`（差額が正のグループだけ）、
  `HAVING ROUND(AVG(x), 0) >= n`（丸めた平均で絞る）は**分析で普通に書く形**
- 標準 SQL では当然書ける形なので、経験のある利用者ほど疑わない
- **B121 を直した直後だけに、同じ `HAVING` の中で挙動が分かれる**状態になっている
  （`HAVING SUM(x) > 9` は正しく、`HAVING SUM(x) - 0 > 9` は 0 行）

## 3. 原因の見立て

`HAVING` の直接参照は、SELECT 側で materialize 済みの集計を**合成名で引く**方式と見られる
（§9 の「同じ集計が SELECT 列にも存在する場合に限り評価できます」がこの実装を指す）。
式でくるむと合成名が一致せず、値が引けないまま条件が偽になっている。

- B121 で入れた比較型の引き渡しと**同じ場所**が起点になるはず
- 別名参照の経路は式でも正しく動く＝**そちらが参照実装**（B121 と同じ構図）
- `SUM(CASE ... END)` が通るのは、外側が集計そのもの（合成名が作れる）ため

## 4. 対応案

**案 A（推奨）**: `HAVING` の直接参照で、集計を含む**算術式・スカラー関数**も評価できるようにする。
別名参照が既に解決している経路（SELECT の式評価器）へ委譲するのが素直。
§9 の規則（SELECT に無い集計は追加計算しない）は維持し、
**SELECT に同じ式または構成要素の集計がある場合に評価できる**ようにする。

**案 B（最低限）**: 評価できない形を**取得前にエラー**にし、対処（別名を付けて参照する）を案内する。
静かに間違うのは消えるが、標準 SQL で書ける形が書けないままになる。
[B120](ksql_b120_aggregate_position_diagnostics_issue.md) §2 の②と同じ扱いになるため、**まとめて実装するのが安い**。

## 5. 受入条件

APP4149（20 件 / 10 社）で、**直接参照と別名参照が一致すること**。

| SQL | 期待 |
|---|---:|
| `HAVING SUM(売上) - 0 > 9` | 8 行 |
| `HAVING SUM(売上) * 1 > 9` | 8 行 |
| `HAVING SUM(売上) - SUM(売上) > -1` | 10 行 |
| `HAVING COUNT(*) + 0 > 1` | 5 行 |
| `HAVING ROUND(AVG(売上), 0) > 9` | 8 行 |

6. **回帰**: `HAVING SUM(CASE ... END) > 9` = 8 行（現状も正しい）
7. **回帰**: B121 の 4 点（`COUNT(*) > 10` = 0 / `AVG(売上) > 9` = 8 /
   `SUM(売上) >= 9050000` = 4 / `SUM(売上) > 9` = 8）
8. **回帰**: B119・B120 の受入と、`HAVING COUNT(*) >= 3` / `GROUPING(会社名) = 1` / 別名参照
9. **比較は数値で行うこと**（B121 と同じく桁違いの境界で検証する。
   桁が揃った値では文字列比較でも通り、検出力が無い）

## 6. 調査済み: 他の経路は問題なし

「集計と別名で処理が分かれる構文」を洗った結果、**静かに食い違うのは本件だけ**だった。

| 経路 | 結果 |
|---|---|
| `ORDER BY` の直接参照（`ORDER BY SUM(x)`） | ParseError＝そもそも書けない（別名は正常） |
| CTE 経由の `WHERE` / `ORDER BY` | 正常（数値比較・数値順） |
| 一時テーブル経由の `WHERE` / `ORDER BY` | 正常 |
| スカラーサブクエリ比較（`売上 > (SELECT AVG(売上) …)`） | 正常（リテラル閾値と一致） |
| CTE を `JOIN` のキーにする | 正常 |
| `IN (SELECT MAX(…))` | 正常 |
| `CASE` の中の集計算術式 | ParseError（静かに間違わない） |
| `UNION` + `ORDER BY` 別名 | `ORDER_KEY_UNRESOLVED`（既知の制限・別件） |
