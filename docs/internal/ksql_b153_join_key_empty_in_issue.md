# B153 結合キー押し下げ（`in` 経路）が空キーの JOIN 一致を取り漏らし得る

- 起票: 2026-08-07（B150 仕様レビュー中に発見・既存問題）
- ステータス: ✅ **v3.61.0 でリリース（2026-08-07・B150 と同梱・publish 済み・実機確認済み）**
- 実測（2026-08-07・v3.60.0）: **kintone は `製品名 in ("")`・`個数 in ("")` をそのまま受理**
  （EXPLAIN で押し下げ確認・エラーなし。選択系の `in ("")` は従来から公式の未選択検索）。
  → 修正＝空キーを捨てず `in` リストへ `""` を含める（受理が未確認の型はフォールバック）。
  **結果が変わる正しさ修正**（欠落していた空=空一致が現れる）として CHANGELOG で区別する
- 関連: [B150](ksql_b150_cte_join_date_pushdown_issue.md)（範囲経路は空値でフォールバックし本問題を回避する設計）

## 1. 何が起き得るか

- **kSQL の JOIN ローカル評価器は空=空を一致とみなす**（実測＝CTE 間 JOIN で
  `'' = ''` が 1 件成立。v3.60.0）
- 一方、結合キー押し下げの `in` 経路（`tryFetchJoinRecordsBySourceKeys`）は
  **キー値を trim して空文字を捨て、非空キー 0 件なら JOIN 先を取得せず空配列を返す**
- したがって、**ソース側に空キー行があり、物理側にも空キー行がある**場合:
  - 混在: `in` リストに `""` が入らず、物理側の空キー行が取得されない → **空=空の一致が欠落**
  - 全て空: 取得ゼロへ短絡 → 同様に欠落

## 2. 実害の評価

- 実データでは未観測（APP4228 の空 `製品名` は 0 件）。**結合キーが空の行を意図的に
  突き合わせる設計は稀**で優先度は低い
- kintone は TEXT / 選択系の `in ("")` を受け付ける（未選択検索の公式手段）ため、
  **修正案＝空キーを捨てずに `in` リストへ `""` を含める**（受ける型に限る）が素直。
  受けない型は範囲経路（B150）と同じフォールバック
