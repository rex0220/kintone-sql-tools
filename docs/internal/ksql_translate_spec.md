## 0. 要約

**`TRANSLATE(x, from, to)` — `from` の各文字を `to` の対応位置の文字へ 1 対 1 で置換する。**

```sql
TRANSLATE(会社名,
  '啞焰鷗摑麴噓俠頰軀俱繫姸鹼嚙攢𠮟繡蔣醬蟬搔瘦驒簞塡顚禱瀆吞囊剝潑醱屛幷麵萊屢沪蠟',
  '唖焔鴎掴麹嘘侠頬躯倶繋妍鹸噛攅叱繍蒋醤蝉掻痩騨箪填顛祷涜呑嚢剥溌醗屏并麺莱屡濾蝋')
```

- **主要 RDB 4 つのうち 3 つにある**（Oracle / PostgreSQL / SQL Server 2017+。MySQL のみ無し）。新規発明ではない（§4）。
- **`REGEXP_REPLACE`（B20）とは守備範囲が重ならず補完的**。`TRANSLATE` は 1 文字→1 文字、`REGEXP_REPLACE` は 1 パターン→1 文字列（§3）。
- **コードポイント整列が必須。** 素朴なコードユニット整列だと、実データ 40 字のうち **25 字が誤変換**される（§2）。

---

## 1. 実需（実在の用途）

### 1.1 Shift_JIS(CP932) で保存できない漢字の変換

**cli-kintone の CSV 出力は Shift_JIS。表外漢字字体表 1022 字のうち 40 字が CP932 に無く、出力でエラーになる。**

同じ問題を [rex0220 計算式プラグイン](https://qiita.com/rex0220/items/9db98b2cf027b686e0b5) が既に解決している。そこでは `LET` / `ARRAY_FOR` / `REPLACEALL` / `SUBSTR` を組み合わせ、**40 字を 1 文字ずつループで置換**している。

**kSQL にはループ（`ARRAY_FOR`）が無い**ため、同じ構成は取れない。`TRANSLATE` なら**関数 1 回**で書ける。

**変換表（記事より）:**

| | |
|---|---|
| 変換元 | `啞焰鷗摑麴噓俠頰軀俱繫姸鹼嚙攢𠮟繡蔣醬蟬搔瘦驒簞塡顚禱瀆吞囊剝潑醱屛幷麵萊屢沪蠟` |
| 変換先 | `唖焔鴎掴麹嘘侠頬躯倶繋妍鹸噛攅叱繍蒋醤蝉掻痩騨箪填顛祷涜呑嚢剥溌醗屏并麺莱屡濾蝋` |

### 1.2 全角英数 → 半角

```sql
TRANSLATE(コード, 'ＡＢＣ…Ｚａｂｃ…ｚ０１２３４５６７８９', 'ABC…Zabc…z0123456789')
```

**B20 §4.5.3 で「正規表現では原理的に解けない」とした用途**。正規表現は文字の写像ができない。

### 1.3 記号・区切りの正規化

```sql
TRANSLATE(住所, '－―ー‐（）　', '--- () ')
```

## 2. コードポイント整列が必須（実データで実測）

**§1.1 の変換表は、UTF-16 では変換元と変換先の長さが一致しない。**

```
変換元  LENGTH(UTF-16) = 41   LENGTH_CHAR(コードポイント) = 40
変換先  LENGTH(UTF-16) = 40   LENGTH_CHAR(コードポイント) = 40
```

原因は **`𠮟`（U+20B9F）がサロゲートペア＝2 コードユニット**であること（`𠮟` は 2010 年に常用漢字表へ追加された正式な表記。B23 §1.1）。

**素朴なコードユニット整列で実装すると、`𠮟` 以降の対応が全部ズレる（実測）:**

```
'𠮟る'            → コードポイント整列: '叱る'  ✓
                     コードユニット整列: '𠮟る'  ✗（変換されない）
'𠮟責と嚙み合わせ'  → コードポイント整列: '叱責と噛み合わせ'  ✓
                     コードユニット整列: '𠮟責と噛み合わせ'  ✗
'屢々沪過して蠟燭'  → コードポイント整列: '屡々濾過して蝋燭'  ✓
                     コードユニット整列: '濾々蝋過して燭'    ✗（全く別の字になる）
```

> **実データ 40 字のうち 25 字が誤変換される。**

**コードポイント整列（`[...from]` / `[...to]`）なら 40 字すべてが正しく変換される**（実測確認済み）。

### 2.1 これは計算式プラグインが既に通った道

記事のバージョン差:

> **Ver.60 以前**: 「`𠮟` は `SUBSTR` で切ると 2 文字になる」ため、`𠮟` だけ別の `REPLACEALL` で処理していた
> **Ver.61 以降**: サロゲートペアを一様に扱えるため、40 字を同じループで処理できる

**kSQL は現在 Ver.60 の位置にいる。** `SUBSTRING('𠮟る', 1, 1)` は孤立サロゲートを返す（[B22](ksql_surrogate_pair_split_issue.md)）。**B22 が Ver.61 相当の修正**にあたる。

## 3. `REGEXP_REPLACE`（B20）との守備範囲

**重ならない。補完的である。**

| 用途 | `TRANSLATE` | `REGEXP_REPLACE`（B20） |
|---|---|---|
| **1 文字 → 1 文字**（S-JIS 40 字・全角英数→半角） | **できる**（1 回） | できない（40 回必要・写像を書けない） |
| **1 パターン → 1 文字列**（`（株）`→`株式会社`） | できない（1 対多） | **できる** |
| 文字クラスの除去（`[^0-9]`） | できない（列挙不能） | **できる** |
| 書式検証 | できない | **できる** |

### 3.1 `TRANSLATE` にできないこと

| 用途 | 理由 |
|---|---|
| **半角カナ → 全角** | `ﾎﾞ`（2 文字）→ `ボ`（1 文字）＝ **2 対 1 は写像ではない**。`REPLACE` で濁点・半濁点の組を先に処理してから `TRANSLATE` するのが定石（他 RDB でも同じ） |
| `（株）` → `株式会社` | 1 対多。`REGEXP_REPLACE` の領分 |

**リファレンスに「`TRANSLATE` は 1 文字 → 1 文字専用」と明記する。**

## 4. 主要 RDB の実装

| | `TRANSLATE` | 長さ不一致のとき |
|---|---|---|
| **Oracle** | `TRANSLATE(expr, from_string, to_string)` | **`to` に対応が無い文字は削除される** |
| **PostgreSQL** | `translate(string, from, to)` | **同上（削除）** |
| **SQL Server** | `TRANSLATE(inputString, characters, translations)`（**2017 で追加**） | **エラー** |
| MySQL | **無し** | — |

**4 つのうち 3 つにある。新規発明ではない。**

> **B20 §4.5.3 の「`TRANSLATE` 相当が要るが kSQL にも無く、MySQL にも無い（Oracle にはある）」という記述は不正確だった**（Oracle だけの独自機能であるかのように読める）。**PostgreSQL と SQL Server 2017 にもある**。B20 側を訂正する（§8）。

### 4.1 長さ不一致の扱い: **エラー（SQL Server 方式）を採用**

Oracle / PostgreSQL は `to` が短いとき**対応の無い文字を黙って削除する**。これは「文字を消す」用途（`translate(x, '-（） ', '')`）に使える一方、**書き間違いが静かなデータ欠損になる**。

**kSQL は SQL Server 方式（エラー）を採る。** 理由:

- kSQL は一貫して **fail-closed・入力を捨てない**方針（B1 の `truncate` 禁止、B16 の `GROUP_CONCAT` が暗黙に切り捨てない、B19 の `GREATEST` が `'007'` の桁揃えを保持）。**黙って文字を消す**のはこの方針に真っ向から反する
- **40 字の変換表を手で書く**のが主用途であり、**長さ不一致はほぼ確実にタイプミス**。エラーにする方が親切
- 「文字を消す」用途は `REPLACE` / `REGEXP_REPLACE`（B20）で書ける

```
TRANSLATE(x, 'abc', 'AB')
→ ArgumentError: TRANSLATE の from と to は同じ文字数である必要があります（from=3, to=2）
```

**エラーメッセージは「文字数」（＝コードポイント）で言うこと。** UTF-16 の数を出すと `𠮟` を含む表で利用者が混乱する。

### 4.2 `from` に重複がある場合

Oracle / PostgreSQL とも**最初の出現が優先**。kSQL も同じ（前例に従う）。リファレンスに明記する。

## 5. B23（`LENGTH_CHAR`）との関係

**同じ「コードポイント単位で文字を扱う」土台の上にある。**

```
B23  LENGTH_CHAR(x)          = [...x].length
B24  TRANSLATE(x, from, to)  = [...from] / [...to] で整列し [...x] を写像
```

**B24 は B23 を機能として必要としない**（`LENGTH_CHAR` を呼ぶわけではない）が、**同じ設計判断（コードポイント整列）を共有する**ため、**まとめて 1 リリースにすると筋が通る**。

**B22（切り出しの修正）とは判断軸が違う。** 切り出し（`LEFT`/`SUBSTRING`）は「kintone の上限に収める」用途があるため **UTF-16 のまま**にする（B22 §3.1）。**「数える・写像する」はコードポイント、「切り出す」は UTF-16** という切り分けをリファレンスで説明する。

## 6. 実装

| ファイル | 変更 |
|---|---|
| `src/lexer/tokens.ts` | `TRANSLATE` を予約語へ追加 |
| `src/types/ast.ts` | `StringFuncName` へ追加 |
| `src/parser/parser.ts` | `tryStringFuncName` のマップへ追加。`FUNC_CALL_PREFIX_KINDS` へも追加 |
| `src/engine/evalFunc.ts` | 評価。arity は **3 固定** |

```ts
case "TRANSLATE": {
  assertArity("TRANSLATE", args, 3, 3);
  const from = [...args[1]], to = [...args[2]];
  if (from.length !== to.length) throw new Error(
    `ArgumentError: TRANSLATE の from と to は同じ文字数である必要があります（from=${from.length}, to=${to.length}）。`
  );
  const map = new Map<string, string>();
  from.forEach((ch, i) => { if (!map.has(ch)) map.set(ch, to[i]); });  // 重複は最初が優先
  return [...args[0]].map((ch) => map.get(ch) ?? ch).join("");
}
```

**`[...str]` を使うこと**（`str.split("")` や添字ループはサロゲートペアを割る）。

### 6.1 性能

`from` / `to` は**行ごとに評価される**（フィールド参照や式も取れるため）。40 字の `Map` を毎行構築すると FULL_SCAN で無駄が出る。

**`evalWhere.ts:345` の `likeRegexCache` と同型のキャッシュを検討する**（キー = `from + " " + to`・上限 200・超過で `clear()`）。**ただし v1 では必須としない** — 40 字の `Map` 構築は軽く、まず正しさを優先する。**codex の判断に委ねる**（測ってから入れる）。

### 6.2 予約語

`TRANSLATE` は新しい予約語。同名フィールドはバッククォート（`` `TRANSLATE` ``）で参照する。B19 で 8 語追加した際、バッククォート回避が全経路（SELECT / WHERE / GROUP BY / ORDER BY）で機能することを実機確認済み。

### 6.3 SemVer

**minor**。追加のみで既存の挙動は不変。

## 9. 受入条件

- [ ] **記事の実データで動く**: §1.1 の 40 字表で `TRANSLATE('𠮟責と嚙み合わせ', FROM, TO)` = `'叱責と噛み合わせ'`
- [ ] **40 字すべて**: `[...FROM]` の各字を単独で変換し、`[...TO]` の対応字と一致する（**40 件の全数テスト**）
- [ ] **コードポイント整列であることの証拠**: `TRANSLATE('屢々沪過して蠟燭', FROM, TO)` = `'屡々濾過して蝋燭'`（**コードユニット整列だと `'濾々蝋過して燭'` になる**＝§2 の実測。この 1 本が実装の正しさを決める）
- [ ] **長さ不一致はエラー**: `TRANSLATE('x', 'abc', 'AB')` が `ArgumentError`。**メッセージは文字数（コードポイント）で言う**
- [ ] **サロゲートを含む表で長さ判定が正しい**: `TRANSLATE('x', '𠮟', '叱')` は**通る**（UTF-16 では 2 vs 1 だがコードポイントでは 1 vs 1）
- [ ] **重複は最初が優先**: `TRANSLATE('a', 'aa', 'XY')` = `'X'`
- [ ] **非対象文字は素通し**: `TRANSLATE('普通の日本語', FROM, TO)` = `'普通の日本語'`
- [ ] **空文字**: `TRANSLATE('', FROM, TO)` = `''`／`TRANSLATE('abc', '', '')` = `'abc'`
- [ ] **サロゲートを割らない**: 結果に孤立サロゲートが出ない（`from` に無いサロゲート文字は素通しされる）
- [ ] arity 違反が `ArgumentError`
- [ ] 予約語: `` SELECT `TRANSLATE` FROM APP100 `` が FIELD 参照になる。素の `SELECT TRANSLATE FROM APP100` は `ParseError`
- [ ] SELECT 列 / WHERE / HAVING / `CREATE TEMP TABLE … AS SELECT` / CTE で動く
- [ ] **`from` / `to` が式でも動く**: `TRANSLATE(x, CONCAT('a','b'), 'AB')`（B19 の `DATE_ADD(x,1,CONCAT('MON','TH'))` と同型。**長さ検証も実行時であること**）
