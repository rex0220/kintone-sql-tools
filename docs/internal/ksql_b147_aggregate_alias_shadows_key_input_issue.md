# B147 集計の別名がキー式の入力フィールドを上書きし、キー列が静かに空になる

- 起票: 2026-08-06
- 状態: 📋 **仕様 R1・Claude レビュー済み（指摘 0 件・実装着手可）**（2026-08-07）→ [R1](ksql_b147_aggregate_alias_shadows_key_input_spec.md)。
  **ウィンドウ関数の別名でも起きる**（§9。**集計も `GROUP BY` も無い素の `SELECT` で再現**）。
  **影響範囲**＝
  **式の種類で症状が変わる**（空／違う数値／違う文字列／**反転した分類**）。
  **直し方の原則は [B148 R3 §3.1](ksql_b148_bare_column_group_by_spec_r3.md) と同じ**
- 種別: 課題（**静かに間違う**）
- 優先: **高**（**エラーも警告も出ず、値が空になる**。手がかりが無い）
- 発見: [B140](ksql_b140_cte_groupby_total_order_issue.md) の対応案を codex に出させ、
  その中の「post-group alias 衝突」の指摘を実測して確認した
- 関連: [B119〜B122](../ksql_issue_archive.md)（静かに間違う系列）／
  [B145](ksql_b145_describe_subtable_field_issue.md)（空が返る）

## 1. 実測（v3.56.3・APP4228）

**集計の別名を、別の列の式が参照しているフィールド名にすると、その列が空になる。**

```sql
SELECT DATE_FORMAT(日付,'%Y-%m') AS 年月, SUM(個数) AS 合計 FROM APP4228 GROUP BY 年月
  → 年月="2025-08" 合計="6685"    ✅ 正しい

SELECT DATE_FORMAT(日付,'%Y-%m') AS 年月, SUM(個数) AS 日付 FROM APP4228 GROUP BY 年月
  → 年月=""       日付="6685"    ❌ 年月 が全行空
```

**違いは集計の別名だけ。** `合計` → `日付` にしただけで `年月` が壊れる。

- **エラーも警告も出ない**（`warnings: []`）
- **集計値は正しい**（`6685` は両方で同じ）
- **壊れるのはキー列だけ**
- **CTE は無関係。素の `SELECT` でも起きる**（CTE でも同じ）

### 1.1 出力名は衝突していない

**`年月` と `日付` は別の名前**なので、
[B145 の重複出力名](ksql_b145_describe_subtable_field_issue.md)のように列が潰れる形とは違う。
**列は 2 本とも出ており、片方の中身だけが空**になる。**手がかりが何も無い。**

## 2. 原因（codex のコード読解・未検証）

**集計値はグループ行へ「別名」で書き込まれる。**

- 集計 alias の書き込み: `src/engine/process.ts:416-431`
- 最終 projection はその後: `src/engine/process.ts:2021-2028`

**したがって、`SUM(個数) AS 日付` はグループ行の `日付` を集計値で上書きする。**
**その後 `DATE_FORMAT(日付,'%Y-%m')` を投影で再評価すると、
`日付` は既に数値（合計）なので日付として解釈できず空になる。**

**グループの作成そのものは正しい**（集計値が合っているのがその証拠）。
**壊れるのは「グループ化した後に、キー式をもう一度評価している」ところ。**

> **codex はこれを B140 の「候補キーを証明する際の危険」として挙げた。**
> **実測すると、候補キー以前に現に誤った値を返していた。**

## 3. なぜ重いか

**`SELECT ..., SUM(x) AS <元の列名>` は自然に書かれる形である。**

```sql
SELECT 商品, SUM(数量) AS 数量 FROM APP100 GROUP BY 商品
```

「合計を元の列名で出す」は普通の書き方で、**多くの場合は壊れない**
（`商品` は素のフィールドで、`数量` を参照する式ではないため）。

**壊れるのは、同じ SELECT の別の列が、上書きされたフィールドを式で参照しているとき**だけ。
**だから滅多に出ないが、出たときに気づけない。**

**B119〜B122 と同じ形**＝**条件が揃ったときだけ静かに間違う**ので、長く残る。

## 4. 影響範囲（2026-08-06 に一部を測った）

**測っている途中で[別の欠陥 B148](ksql_b148_bare_column_group_by_issue.md) が出た。**
**B148（非集計・非キー列が先頭行の値を返す）は本件とは独立**で、**そちらのほうが踏みやすい**。
**区別は B148 §5 に書いた。**

### 測って分かったこと

- **`GROUP BY <その列自身>` なら算術式は正しい**
  （`SELECT 個数, 個数*2 AS 倍 … GROUP BY 個数` → `646 / 1292` で正しい）。
  **キーとして解決できていれば壊れない**
- **壊れるのは投影時に再評価される経路**という §2 の見立てと整合する
  （B148 は先頭行の値を返すのに対し、**本件は空**＝先頭行の評価ですらない）

### まだ測っていないこと

1. **数値どうしの上書き**＝`DATE_FORMAT` は空になったが、
   **算術式なら空にならず「違う値」になる可能性がある**（空より悪い）。**最優先**
2. `CASE` / `CONCAT` / 文字列関数でも同じか
3. **`HAVING` / `ORDER BY` / ウィンドウ**でも同じ上書きを踏むか
4. **ウィンドウ関数の別名**でも同じことが起きるか（`OVER` の別名も同じ経路か）
5. **DML の `SET` 側**に波及するか（`UPDATE ... SET x = (SELECT ...)`）

## 5. 案（未検討）

- **案 A＝投影でキー式を再評価しない**（グループ化時に評価した値を持ち回る）。
  **筋が良さそうだが、評価回数が変わるので影響範囲の確認が要る**
- **案 B＝集計の別名がフィールドコードと衝突したらエラー**。
  **破壊的**（今まで通っていた `SUM(数量) AS 数量` が落ちる。しかも大半は無害）
- **案 C＝衝突しても元のフィールド値を壊さない**（書き込み先を分ける）。
  **案 A に近いが、投影の仕組みを変えずに済む可能性**
- 案 D＝警告を出す。**静かに間違うのは止まるが、値は誤ったまま**

**見立ては未定。§4 の影響範囲を測ってから決める。**

## 6. B140 との関係

**B140 の Phase 1 では、この衝突を「候補キーを作らない条件」として除外する必要がある**
（codex の指摘どおり）。**ただし本件はそれとは独立に、今すでに誤った値を返している。**
**B140 を進めるかどうかに関わらず、本件は単独で扱う。**

## 8. 影響範囲の実測（2026-08-07・v3.57.0・APP4228）

**§4 の未測項目を測った。式の種類ごとに症状が違い、`DATE_FORMAT` の「空になる」はいちばん良い方だった。**

### 8.1 症状の一覧

| 式の種類 | 別名を衝突させたとき | 衝突させないとき |
|---|---|---|
| **日付関数** `DATE_FORMAT(日付,'%Y-%m')` | **空になる** | `2025-08` |
| **算術** `個数 * 2` | **2584**（＝2 × 合計） | **1292**（＝2 × キー） |
| **文字列連結** `製品名 \|\| '-x'` | **`23429-x`**（合計を連結） | `食パン-x` |
| **`CASE`** `CASE WHEN 個数 > 100 …` | **`大`**（合計 783 で判定） | **`小`**（キー 27 で判定） |

**起票時の見立て（「数値どうしの上書きなら空にならず違う値になる可能性があり、そのほうが悪い」）は当たった。**
**しかも `CASE` は分類が反転する**——**「小」を「大」と言う**ので、**数値より悪い。**

### 8.2 **グループが 1 件だと偶然合う**

```
SELECT 製品名, 個数 * 2 AS 倍, SUM(個数) AS 個数 FROM APP4228 GROUP BY 製品名, 個数
  食パン   倍 2584  個数 1292   ← 2 件のグループ。誤り（正しくは 1292）
  牛乳     倍 1412  個数 706    ← 1 件のグループ。偶然一致
```

**1 件のグループでは `SUM` がキーと等しい**ため、**誤りが出ない。**
**集約が実際に集約したときだけ壊れる**ので、**小さなデータで試すと正しく見える。**

### 8.3 影響しないもの

| | |
|---|---|
| **`ORDER BY` の別名解決** | `SELECT 製品名, SUM(個数) AS 個数 … ORDER BY 個数` は合計で並ぶ。**§8 の契約どおり**（`ORDER BY` は別名優先）で、本件ではない |
| **CTE の下流** | `WITH m AS (… SUM(個数) AS 個数) SELECT 個数 * 2 FROM m` は正しい（46858 = 2 × 23429）。**下流では衝突が起きない** |

### 8.4 まとめ

**本件は「集計の別名が、同じ `SELECT` 句の他の式から見えてしまう」ことが原因**で、
**症状は式の種類で決まる**（空・違う数値・違う文字列・**反転した分類**）。

**[B148 R3 §3.1](ksql_b148_bare_column_group_by_spec_r3.md) の原則がそのまま直し方になる。**

> **標準 SQL では、`SELECT` 句の別名は同じ `SELECT` 句の他の式からは見えない。**

**残る未測**＝`HAVING` / ウィンドウ関数の別名 / DML の `SET` 側。
**ただし原因が投影時の上書きだと分かった以上、直せば全部に効く見込み。**

## 9. **ウィンドウ関数の別名でも起きる**（2026-08-07・実測）

**表題と §1 は「集計の別名」と書いたが、範囲が広い。**

```
SELECT 個数 * 2 AS 倍, ROW_NUMBER() OVER (ORDER BY $id) AS 個数 FROM APP4228
  → 倍 = 2, 4, 6          ← 2 × 行番号（誤り）

SELECT 個数, 個数 * 2 AS 倍, ROW_NUMBER() OVER (ORDER BY $id) AS 順 FROM APP4228
  → 倍 = 1292, 1412, 796  ← 2 × 個数（正）
```

**集計も `GROUP BY` も無い素の `SELECT` で起きる。**
**「集計したときだけの話」ではない。**

**正確な言い方**＝**`SELECT` の出力別名が、同じ `SELECT` 句の他の式が参照する
入力フィールド名と衝突すると、その式が出力値のほうを読む。**

**[仕様 R1](ksql_b147_aggregate_alias_shadows_key_input_spec.md) は §8.1 に
「window materialized 値と source 値の分離」を入れており、この範囲を含んでいる。**
