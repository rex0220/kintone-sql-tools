# B100 完全入力エラーの語順 — 対処が最後の 5 文目にあり、小さい表示領域で読めない

- 起票: 2026-07-29
- ステータス: 📝 **評価（優先 低）**
- 出典: [Pro の報告 v3.34.0 §3](../../../ksql-dashboard-pro/docs/internal/kSQLエンジンへの報告-v3340.md)。
  **Pro は「現状のままで結構です」と明記している**。こちらで測ったところ**射程が B98 より広かった**ため起票する
- 関連: [B98](ksql_b98_join_truncated_right_null_issue.md) / [B97](ksql_b97_incomplete_aggregate_failclosed_issue.md) /
  [B90](ksql_b90_variable_arithmetic_issue.md) / [B86](ksql_b86_materialized_unknown_column_issue.md)

## 1. 何が起きているか

**完全入力を理由に止まるエラーは、どれも 5 文で、対処が 5 文目にある。**

```
外部結合の正しい結果には完全な候補集合が必要です。          ← ① 理由
complete input reason: OUTER_JOIN_NON_PRESERVED（APP4148）。 ← ② 内部識別子
onLimit=truncateは使用できません。                          ← ③ 方針
取得件数が上限（20 件）を超えました。                        ← ④ 事実
WHERE 句で絞り込むか、maxRecords を引き上げてください。       ← ⑤ 対処
```

**Pro はこれをダッシュボードのペイン内に表示する。**
**小さいペインは高さ 3 行程度で、先頭の 1〜2 文しか見えない。**
**その範囲に対処（⑤）が入らない。**

## 2. 測定（2026-07-29）

**B98 だけの問題ではない。完全入力を理由に止まる 9 つの形すべてが同じ語順である。**

| 形 | 文字数 | 文数 | 対処が始まる位置 |
|---|---:|---:|---:|
| `AGGREGATE`（集計） | 137 | 5 | 101 |
| `GROUP_BY` | 140 | 5 | 104 |
| `DISTINCT` | 143 | 5 | 107 |
| `GROUPING_SETS`（小計・総計） | 144 | 5 | 108 |
| `DML` + 集計 | 142 | 5 | 106 |
| `LOCAL_ORDER` | 145 | 5 | 109 |
| `STATISTICAL_AGGREGATE` | 151 | 5 | 115 |
| 集計 + 並び（`クエリの正しい結果`） | 151 | 5 | 115 |
| **`OUTER_JOIN_NON_PRESERVED`（B98）** | **163** | **5** | **127** |

**B98 が一族で最長。**理由は 2 つある。

1. `OUTER_JOIN_NON_PRESERVED` が**最も長い識別子**である
2. **アプリ番号が付く**（他の形は付かない）

**内部識別子の露出も 9 形すべて**であり、B98 で始まったものではない。

## 3. 文面の組み立て方

**前半（①②③）と後半（④⑤）が別の場所で作られ、連結されている。**

| 部位 | 場所 |
|---|---|
| ① 理由 + ② 識別子 | [`completeInputErrorPrefix`](../../src/execute.ts)（`execute.ts:2927`） |
| ③ 方針 | [`throwCompleteInputError`](../../src/execute.ts)（`execute.ts:2963`） |
| ④ 事実 + ⑤ 対処 | [`FetchAllLimitError`](../../src/api/fetchAll.ts) の本文（`fetchAll.ts:105`） |

**B98 だけは別経路**で、`execute.ts:5010` 付近が同じ並びを直接組み立てている。

> **つまり語順を変えるには、連結の順序そのものを変える必要がある。**
> **前半を後ろへ回す形になるため、`FetchAllLimitError.message` の先頭が変わる。**

## 4. 論点

### 4.1 誰のための文面か

**この文面は 2 つの読者を同時に相手にしている。**

| 読者 | 要るもの |
|---|---|
| **利用者**（ペインを見ている人） | **④事実 → ⑤対処**。**なぜ止まったかは後でよい** |
| **開発者 / AI クライアント** | **②識別子**。どの規則で止まったかを機械的に判別したい |

**現在の語順は後者に最適化されている。**

### 4.2 変えると壊れるもの

- **`message` の先頭を照合しているテスト・smoke**（数は要調査）
- **Pro を含む利用者側の文言照合**——ただし **Pro は `FetchAllLimitError` という型で判定できる**と明言している
- **エラー文の snapshot**

### 4.3 やらない選択も妥当である

**Pro は「Pro 側で短い文言に差し替えることもできる。エンジン側で変えていただく必要はありません」と書いている。**
**型（`FetchAllLimitError`）と識別子（`complete input reason:`）が取れる以上、
表示の都合は利用者側で吸収できる**という判断であり、筋が通っている。

**この課題を進める根拠は「Pro が困っているから」ではない。**
**エンジンが返す既定の文面が、既定のまま使うと読めない形になっている**という点にある。

## 5. 案

### 案 A: 語順を入れ替える（④⑤①②③）

```
取得件数が上限（20 件）を超えました。WHERE 句で絞り込むか、maxRecords を引き上げてください。
外部結合の正しい結果には完全な候補集合が必要です。onLimit=truncateは使用できません。
complete input reason: OUTER_JOIN_NON_PRESERVED（APP4148）。
```

- **対処が 1 文目に来る。**識別子は末尾に残る
- **`message` の先頭が全形で変わる**——影響範囲が最も大きい

### 案 B: 識別子を末尾へ回すだけ（①③④⑤②）

- **②だけを移す。**先頭の「なぜ止まったか」は残る
- **対処は 4 文目**のままで、**1〜2 文しか見えないなら依然読めない**
- **効果が小さい**

### 案 C: 何もしない

- **Pro の言うとおり、型で判定して利用者側で差し替える**
- **エンジンの既定文面は読みにくいまま残る**

### 案 D: 構造化して渡す

- `FetchAllLimitError` に `reasons` / `maxRecords` / `appIds` を**プロパティとして持たせる**
- **文面は変えない。**利用者が自分で組み立てられるようにする
- **公開型の追加**になるため、任意プロパティで純加法にする（[B95](ksql_b95_truncation_visibility_issue.md) と同じ形）
- **表示の都合を利用者側で吸収する道を、文言照合なしで開く**

## 6. 現時点の見立て

**案 D と案 A の組み合わせが素直だが、優先度は低い。**

- **誤った結果を返す問題ではない**——止まるべきときに止まっており、正しさは損なわれていない
- **Pro は対応不要と明言している**
- **他に実需のある課題がある**

**次にこのファイルを開くときに必要なもの**＝
**`message` の先頭を照合しているテスト・smoke の実数**（案 A の費用がこれで決まる）。

## 7. 対象外

| | 理由 |
|---|---|
| **識別子そのものを消す** | **開発者と AI クライアントが規則を判別する手段**。消すと B97 / B98 の設計意図が伝わらない |
| **文面の多言語化** | 別の話。ここでは扱わない |
| **打ち切り以外のエラー全般の語順** | **完全入力の一族に限る**。広げると際限がない |
