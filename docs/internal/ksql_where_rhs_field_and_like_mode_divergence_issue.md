## ① WHERE 右辺のフィールド/関数比較で文字列が壊れる

### 再現(ローカル検証済み)

```sql
-- 数値化できない文字列フィールドを自分自身と比較。本来 = は一致・!= は不一致
SELECT レコード番号 FROM APP123 WHERE 文字列 = 文字列   -- 値が非数値なら 不一致(false)
SELECT レコード番号 FROM APP123 WHERE 文字列 != 文字列  -- 値が非数値なら 一致(true)

-- 数値フィールド同士は "偶然" 正しく動く
SELECT レコード番号 FROM APP123 WHERE 金額 = 金額       -- 正しく true
```

検証: `row = { 文字列: "りんご" }` に対し `文字列 = 文字列` → `false`、`文字列 != 文字列` → `true`。
数値フィールド(`金額 = 金額`, `row.金額 = "1000"`)は `true` になる。

**「常に壊れる」ではなく、数値化不能な一般文字列で原則破綻する。** 破綻するかどうかは値の中身に依存する(下記「例外/境界」)。

#### 例外/境界(誤結果の条件)

右辺だけが `Number()` を通り `String(Number(...))` で正規化されるため、**左辺の生値と右辺の正規化表現が一致するかどうか**で結果が決まる。

| 値の例 | 左辺(生) | 右辺(`String(Number(v))`) | `v = v` の結果 |
|--------|----------|---------------------------|----------------|
| `"りんご"`(非数値) | `"りんご"` | `"NaN"` | **不一致(バグ)** |
| `"1000"`(正準な数値文字列) | `"1000"` | `"1000"` | 一致(偶然正しい) |
| `"01"`(先頭ゼロ) | `"01"` | `"1"` | **不一致(バグ)** |
| `"1.0"`(小数末尾ゼロ) | `"1.0"` | `"1"` | **不一致(バグ)** |
| `"1e3"`(指数表記) | `"1e3"` | `"1000"` | **不一致(バグ)** |
| `"NaN"`(文字列として) | `"NaN"` | `"NaN"` | 一致(偶然正しい) |
| `""`(空=NULL 相当) | `""` | `String(Number(""))`=`"0"` | **不一致** |

つまり誤結果は「非数値文字列」だけでなく「**正準形でない数値文字列**(先頭ゼロ・小数末尾ゼロ・指数表記等)」でも起きる。逆に偶然一致するケース(正準数値・文字列 `"NaN"`)もあるため、症状は「原則破綻・一部すり抜け」。

JOIN 突き合わせ(`WHERE cb.担当者 != cm.担当者_コンサル`)も同じ経路。担当者名が非数値で完全一致する行まで「不一致」と判定され、本来除外すべき一致行が結果に混入する(「全件出る」わけではなく、非数値一致行が不当に残る)。

### 原因(コード裏取り済み)

右辺のフィールド参照は、独立した「フィールド値」型を持たず**算術式(`ARITH_VALUE`)として構文解析され**、評価時に**数値へ強制変換**される。数値化不能な文字列は `"NaN"` に、数値化可能でも非正準な文字列は正準表現に化けるため(上の境界表)、左辺の生文字列と一致しなくなる。

1. パーサ: `parseSqlValue`([src/parser/parser.ts:1489](../../src/parser/parser.ts#L1489))。右辺の裸の識別子は `IDENT` 分岐([:1541-1552](../../src/parser/parser.ts#L1541-L1552))で `parseArithAddSub()` に流れ、単一フィールドでも `{ type: "ARITH_VALUE", expr: { type: "FIELD_REF", field } }` になる。右辺に「文字列としてのフィールド参照」型が存在しない。
   - 実測 AST: `right = {"type":"ARITH_VALUE","expr":{"type":"FIELD_REF","field":"文字列"}}`
2. モード判定: `hasWhereFunc`([src/converter/selectToKintone.ts:84](../../src/converter/selectToKintone.ts#L84))が `right.type === "ARITH_VALUE"` を検出し **FULL_SCAN** にルーティング(SIMPLE 変換は `convertValue` の `ARITH_VALUE` 分岐([whereToKintone.ts:179-180](../../src/converter/whereToKintone.ts#L179-L180))で例外を投げるので、必ず JS 評価側に回る)。
3. JS 評価: `resolveValue` の `ARITH_VALUE` 分岐([src/engine/evalWhere.ts:182](../../src/engine/evalWhere.ts#L182))が `String(evalArithExpr(value.expr, row))`。
4. `evalArithExpr` の `FIELD_REF`([src/engine/evalFunc.ts:21](../../src/engine/evalFunc.ts#L21))が `Number(resolveFieldRef(...))`。文字列フィールド `"りんご"` → `Number("りんご")` = `NaN` → `String(NaN)` = `"NaN"`。
5. 比較: `evalOp` の `=`([src/engine/evalWhere.ts:120](../../src/engine/evalWhere.ts#L120))は `leftStr === rightStr`。左辺 `"りんご"` vs 右辺 `"NaN"` → 常に不一致。`!=`([:121-122](../../src/engine/evalWhere.ts#L121-L122))は逆に常に一致。

数値フィールドが「動く」のは、左辺は `resolveField` の生文字列のまま・右辺だけが数値化されるが、kintone の数値フィールド値は通常**正準表現**(先頭ゼロや末尾ゼロを持たない)で格納されるため、右辺の `String(Number(...))` 正規化後と偶然一致するから。あくまで偶然で、`= 金額`(正準数値)は動くが `= 文字列`(非数値・非正準数値)は壊れる、という不整合が生じる。

REPLACE 等の文字列関数を右辺に置いた場合も同じ経路(`ARITH_VALUE` 内 `STRING_FUNC` → `Number(evalStringFunc(...))`, [evalFunc.ts:22](../../src/engine/evalFunc.ts#L22))で文字列結果が数値化され破綻する。

### 修正方針(案)

右辺の値を、左辺(`FieldValue`)と同様に**文字列ドメインで解決する経路**へ分離する。

- 案 A(推奨): 右辺の裸フィールド/文字列関数を `ARITH_VALUE` に畳み込まず、`resolveField` と同じ文字列解決を通す専用の右辺型(例: `FIELD_VALUE` / `FUNC_VALUE`)を導入し、右辺も文字列ドメインで解決する。
- 案 B(軽微だが不完全): `resolveValue` の `ARITH_VALUE` 評価で、式が単一 `FIELD_REF` / `STRING_FUNC` のときは `Number()` を通さず文字列として解決する。算術演算(`金額 * 1.1`)は従来通り数値。ただし「右辺 = 純粋な文字列演算」と「算術式」を式構造から見分ける必要があり、`FUNC_FIELD` を数値関数(LENGTH 等)と文字列関数(REPLACE 等)で仕分ける判定が要る。

> **注意: 等値比較の仕様を先に確定する必要がある。** 現行 `evalOp`([evalWhere.ts:114-127](../../src/engine/evalWhere.ts#L114-L127))の「数値化可能なら数値比較」判定([:114-117](../../src/engine/evalWhere.ts#L114-L117))が使われるのは `>` / `<` / `>=` / `<=` **のみ**で、`=` / `!=` は**常に文字列表現の一致比較**([:120-122](../../src/engine/evalWhere.ts#L120-L122))。したがって右辺を素直に文字列解決するだけで `文字列 = 文字列` は直るが、`"01" = "1"` / `"1.0" = "1"` / `"1000" = "1e3"` を等値とみなすか(数値正規化して比較するか、文字列としてそのまま比較するか)は**別途仕様決定が要る**。左辺(`resolveField`)は元々文字列を返すため、右辺も文字列解決に揃えれば `=`/`!=` の現行「文字列一致」意味論と自然に整合する — 数値正準化まで踏み込むと `>`/`<` と `=` の数値扱いを統一する広い設計判断になるので、スコープを分けて決める。

### 追加テスト観点(修正時)

- `文字列 = 文字列`(自己一致)→ 全件、`!=` → 0 件
- `金額 = 金額`(数値)→ 従来どおり全件(回帰防止)
- `a.担当者 = b.担当者`(JOIN 文字列突き合わせ)の一致/不一致
- 右辺 `REPLACE(...)` 等の文字列関数比較
- 右辺算術式 `税込 = 金額 * 1.1` が数値比較のまま壊れないこと(回帰防止)

## ② LIKE が SIMPLE と FULL_SCAN で異なる結果になる

### 再現(ローカル検証済み)

値 `"てすと２０"` のレコードに対して:

```sql
-- SIMPLE(kintone が評価): 部分一致で 1 件ヒット
SELECT レコード番号 FROM APP123 WHERE 文字列 LIKE 'すと%'

-- FULL_SCAN(JS が評価。無害な関数条件でモードが切り替わる): 0 件
SELECT レコード番号 FROM APP123 WHERE 文字列 LIKE 'すと%' AND LENGTH(別) >= 0
```

検証:
- SIMPLE 側は kintone クエリ `文字列 like "すと%"` を**そのまま送出**(`resolveSelectMode` → `SIMPLE`)。kintone の `like` は前方一致ではなく**部分一致(contains)**で、`%` をワイルドカードとして解釈しない(利用者の実アプリ観測で 1 件)。
- FULL_SCAN 側(`LENGTH(...)` で `hasWhereFunc` → FULL_SCAN)は JS の `matchLike` が `%`→`.*`・先頭末尾 `^…$` アンカーで「すとで**始まる**」と解釈 → `"てすと２０"` は 0 件(`false`、検証済み)。

つまり **同一 SQL でも、JOIN / DISTINCT / GROUP BY / WHERE 関数の有無で実行モードが切り替わると LIKE の結果が変わる**。

### 原因(コード裏取り済み)

LIKE のワイルドカード意味論を、2 経路で**片方しか実装していない**。

- SIMPLE(kintone 送出): `whereToKintone` はパターン文字列をクォートするだけ([convertString, whereToKintone.ts:192-196](../../src/converter/whereToKintone.ts#L192-L196))で、`%`/`_` を**無変換のまま**渡す。演算子は `like`([convertOp:84](../../src/converter/whereToKintone.ts#L84))。kintone 側は SQL ワイルドカードを解釈せず部分一致する。
- FULL_SCAN(JS 評価): `matchLike`([src/engine/evalWhere.ts:242-269](../../src/engine/evalWhere.ts#L242-L269))は
  - ワイルドカードなし → `value.includes(pattern)`(FULL_SCAN では contains=`includes` として評価。kintone 側との厳密な同義性は未確認 → 「未確認/追加調査事項」)
  - `%`/`_` あり → `%`→`.*`, `_`→`.`, **`^…$` でアンカー**した正規表現(標準 SQL の前方/後方一致)

ドキュメント言語リファレンス §6([docs/ksql_language_reference.md:595-612](../ksql_language_reference.md#L595-L612))は `LIKE '田%'`＝「田で始まる」/`'A__'`＝「A＋任意2文字」と**標準 SQL ワイルドカード**を明記しているが、これは FULL_SCAN(JS)側の挙動であり、SIMPLE(kintone)側は満たさない。両者が食い違うため結果がモード依存になる。

なお「ワイルドカードなし LIKE = 部分一致」は**今回の再現ケースでは一致**したが、両経路が一般に同義とは限らない(下記「未確認/追加調査事項」)。今回コードで確実に食い違うのは **`%`/`_` を含むパターン**である。

#### 未確認/追加調査事項(kintone 側の検索意味論)

FULL_SCAN のワイルドカードなし判定は単純な `String.prototype.includes`([evalWhere.ts:245-246](../../src/engine/evalWhere.ts#L245-L246))だが、kintone の `like` は**単語(トークン)検索**であり `includes` と厳密に同義ではない。[kintone REST API 仕様](https://cybozu.dev/ja/kintone/docs/rest-api/records/get-records/)にも文字列検索が単語単位であること、LIKE 検索に**10万件での打ち切り**があることが記載されている。したがって不一致の範囲は `%`/`_` に留まらず、以下が SIMPLE/FULL_SCAN で乖離しうる。要追加調査。
- トークン分割境界(部分語・区切り文字をまたぐ検索が `includes` と一致するか)
- kintone クエリで使用できない/特別扱いされる記号
- 大文字小文字・全角半角・かな正規化などの照合規則
- 検索対象件数の上限(10万件打ち切り)による欠落

これらは「ワイルドカードなしなら安全」という前提を崩すため、②の統一方針(後述)を検討する前に kintone 実 API での挙動確認が要る。

### 論点: どちらの意味論に寄せるか

ドキュメントは標準 SQL ワイルドカード(FULL_SCAN 側)を正としている。一方 kintone API は `like` にワイルドカードを持たない。整合させる方向は 2 つ:

- 方向 A(ドキュメント準拠 = 標準 SQL 意味論に統一): SIMPLE 経路で SQL LIKE を kintone へ**そのまま送れない**ことを前提に、`%`/`_` を含む LIKE は
  - **a)【推奨・当面】FULL_SCAN に強制ルーティングする** — 最小変更で不一致を確実に解消できる。`%`/`_` を含む LIKE を `hasWhereFunc` 相当のモード判定に追加すればよい(全件取得コストは伴う)。
  - b)【将来の最適化案】前方一致 `'田%'` 等を kintone で表現可能な形へ限定変換し、表現不能なパターン(中間 `%`, `_`, 複数ワイルドカード)だけ FULL_SCAN にフォールバック。「kintone で粗くフィルタ → JS で厳密判定」の 2 段構え。
    - **未証明の安全性: b) は現状推奨できない。** kintone の単語検索が JS 側の厳密判定候補を**必ず包含する保証がない**(上記「kintone 側の検索意味論」)。粗いフィルタで**偽陰性(取りこぼし)**が出れば、後段の JS 評価では復元できず結果が欠落する。
    - **実行計画の不足**: 現行 FULL_SCAN は WHERE に変換不能要素が 1 つでもあれば WHERE 全体を push せず全件取得する設計([selectToKintone.ts:161](../../src/converter/selectToKintone.ts#L161))。b) には「安全に push できる述語」と「JS で再評価する述語」を分解し後段で再結合する**新しいハイブリッド実行計画**が必要で、A-a とは規模が違う。着手前に包含性の証明(または保守的な包含条件の限定)が前提。
- 方向 B(kintone 準拠 = contains に統一): `%`/`_` を**特別扱いせず**リテラル部分一致に統一し、ドキュメント §6 を「LIKE は常に部分一致。`%`/`_` はワイルドカードではない」と書き換える。挙動は単純化するが、標準 SQL 期待から乖離し既存利用者の破壊的変更になりうる。

**推奨**: **A-a(ワイルドカード付き LIKE を一律 FULL_SCAN)を第一候補**とし、A-b は kintone 単語検索の包含性を確認できた後の将来最適化に回す。いずれにせよ「同一 SQL がモードで結果を変えない」ことを不変条件に据える。

### 追加テスト観点(修正時)

- (A-a 適用後)ワイルドカード付き LIKE(`'すと%'` 等)が**確実に FULL_SCAN へルーティングされる**こと — SIMPLE で kintone へ生パターンが送られないこと
- FULL_SCAN の `matchLike` が言語仕様(§6)どおり評価すること(前方 `'田%'` / 後方 `'%田'` / 中間 `'%田%'` / 単一文字 `'A__'`)
- ワイルドカードなし `'会社'`(=部分一致)の回帰
- モード切替トリガ(`JOIN` / `DISTINCT` / `GROUP BY` / `WHERE 関数`)を足しても LIKE 結果が不変であること

## 共通の根本テーマ

両問題の同根は「**SQL の意味論と、バックエンド(kintone)/評価器(JS)の意味論が食い違っている**」こと。ただし食い違いの現れ方は別物なので混同しない。

- ① は **モード間の不一致ではない**。右辺フィールド参照は `ARITH_VALUE` として構文解析され、`hasWhereFunc` により**常に FULL_SCAN へ送られる**([selectToKintone.ts:84](../../src/converter/selectToKintone.ts#L84))。直接原因は「AST 上で右辺文字列フィールドを表す型が無く `ARITH_VALUE` に潰れる」ことと「評価器が右辺を `Number()` 強制する」ことで、SIMPLE/FULL_SCAN の分岐とは無関係。
- ② は **SIMPLE(kintone)と FULL_SCAN(JS)の分岐そのもの**。同じ LIKE がモードで別結果になる。

したがって設計上の不変条件は 2 本立て。
1. (①向け)**AST の値表現と評価器の型ドメインを SQL 意味論に合わせる** — 右辺も左辺と同じ文字列解決を通し、数値/文字列の扱いを比較演算子の仕様として一貫させる。
2. (②向け)**実行モードが結果集合を変えない** — SIMPLE と FULL_SCAN は同じ SQL に対し同じ結果を返す。LIKE/比較/値解決の意味論を 1 箇所に集約し、kintone へ push する条件は「JS 評価と一致することが保証できる範囲」に限定する。

## 影響・優先度

- ① は**サイレントな誤結果**(エラーにならず、値によって一致行の欠落／不一致行の混入が起きる)。JOIN の突き合わせが壊れるため実害が大きい。**優先度: 高**。
- ② はモード依存の**不一致**。ワイルドカード付き LIKE を使い、かつ JOIN/関数等でモードが切り替わる場合に顕在化。**優先度: 中〜高**(データ抽出の正しさに関わる)。
