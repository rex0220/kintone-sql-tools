## 1. 依頼の要旨

書込 DML（INSERT / UPDATE / DELETE / UPSERT の書込フェーズ）を kintone の `bulkRequest`（1 リクエストに最大 20 サブリクエスト）で束ねる。XL 実測で **UPDATE 100,000 件 = 1,000 チャンク = 44.6 分**（2.67 秒/チャンク）となり、書込が所要時間の支配項と確定したため起票された。期待効果は書込 HTTP リクエスト数が最大 1/20（1,000 → 50）で、**44.6 分 → 数分規模**。

## 2. 実測・検算（v3.72.0 実装・2026-08-25）

### 2.1 エンジン側の現状（静的・確定）

| 項目 | 実測 |
|---|---|
| `bulkRequest` の実装 | **無い**。`src/` 内の出現は EXPLAIN の注記 1 行だけ（[execute.ts:12855](../../src/execute.ts#L12855)「`reference: bulkRequest は未実装。書込サブリクエスト数は HTTP 書込回数と同じ`」）。クライアント 3 面のいずれにも `/k/v1/bulkRequest.json` を叩く口が無い |

| EXPLAIN 出力 | 書込 DML で `write: N 回（… 100 件/HTTP リクエスト）` + 上記 reference 行を出す。**文字列を固定するテストがある**（[b168Stage5ExecutionExplain.test.ts:82](../../src/__tests__/b168Stage5ExecutionExplain.test.ts#L82)） |

→ **17 箇所の書込ループを個別に束ねる形にはできない**（`bulkRequest` は複数アプリ・複数 API を 1 リクエストに混ぜる形なので、呼び出し側ごとの改修ではなく**リクエスト計画層の新設**になる）。2026-07-10 の M5 評価「価値は高いがリクエスト計画変換層の新設が必要で重い」（[proposals §2.2](ksql_batch_enhancement_proposals.md)）は**現在も正しい**。

### 2.2 依頼書 論点 3 の前提は誤り — **効くのは時間であって API 回数ではない**

依頼書は「`bulkRequest` 1 回は API 1 回だが kintone 側の負荷は大きい」としているが、**日次 API リクエスト数の観点では誤り**。

[kintone REST API の共通仕様](https://cybozu.dev/ja/kintone/docs/rest-api/overview/kintone-rest-api-overview/)は **1 アプリあたりスタンダード 10,000 件 / ワイド 100,000 件**の日次上限を定め、その**カウント対象外リストに `bulkRequest` 自体を挙げている**。封筒を数えないための除外であり、**内包サブリクエストは個別に計上される**と読むのが自然（サブリクエストも対象外なら日次上限を無制限に迂回できてしまう）。

| 指標 | B174（bulkRequest） | [B173](ksql_b173_native_upsert_update_key_issue.md)（native upsert） |
|---|---|---|
| 1 日の API リクエスト数 | **減らない**（XL の UPDATE は 1,000 のまま） | 減る |
| HTTP ラウンドトリップ数・同時接続数 | 減る（1,000 → 50） | 減る |
| 所要時間 | **§4 の実測次第** | 減る（GET 200 回分） |
| 失敗時のロールバック粒度 | 100 件 → **2,000 件へ粗くなる** | 100 件のまま |

→ **受入基準 1 の「書込リクエストが約 50 回に束ねられ」は HTTP 回数としては正しいが、日次カウントは 1,000 のまま**。依頼元へは [F-7 の回答 §9](../../../ksql-flow/docs/kSQLエンジンからの回答-20260825-F7-upsert-updateKey.md) で訂正済み（先方も `scale-notes.md` に日次カウント併記を予定）。**こちらの `docs/flow_dialect1_engine_task.md` §2.8 の記述も同じ誤りだったので訂正済み。**

### 2.3 依頼書の中核前提「往復レイテンシ支配」は**未測定**

依頼書は「往復レイテンシ支配のため 44.6 分 → 数分規模」と見込むが、**この前提を測ったデータが無い**。

- 依頼元の実測は **2.67 秒 / 100 件チャンク（UPDATE）**
- B173 の実機測定（APP4253・3 フィールドの軽量アプリ）では **100 件混在 upsert が 617ms**

桁は同じだが 4 倍の開きがあり、**この差はレコードの重さ（フィールド数・ペイロード量）に由来する＝サーバ側処理時間の成分が大きい**ことを示唆する。依頼書自身も「同一データ量でも UPDATE は DELETE の約 5.6 倍/チャンク（送信ペイロード差）」と観測しており、**これは往復レイテンシではなくペイロード処理が効いている証拠**。

**`bulkRequest` がサブリクエストをサーバ側で逐次処理するなら、束ねても所要時間はほとんど縮まない。** 縮むのは往復回数分（1,000 往復 → 50 往復）だけで、1 往復のレイテンシが仮に 100ms なら 100 秒しか減らず、44.6 分に対しては誤差。

→ **ここが採否を決める唯一の点。**（[[pro-request-measure-first]]＝依頼は形まで指定して来るが、実装前に測ると前提が覆る）

## 3. 設計上の論点

### 3.1 原子性（依頼書 論点 1）

`bulkRequest` は**いずれかのサブリクエストが失敗すると以降は実行されず全体がロールバックする**（公式明記）。20 × 100 = **最大 2,000 件が all-or-nothing** になる。

依頼書は「冪等リラン前提の kSQL Flow にはむしろ好都合」とするが、**エラー行の特定粒度**は確実に粗くなる。`results[]` は失敗したサブリクエストにだけエラーが入り、**それ以外は `{}`（空オブジェクト）**が返る仕様なので、「どのサブリクエストで落ちたか」は判るが「そのサブリクエスト内のどの行か」はレスポンスからは判らない（現行の 100 件 PUT と同じ粒度）。

### 3.2 適用範囲（依頼書 論点 2）

opt-in か既定か。**既定 ON は採らない見立て**＝失敗時のロールバック粒度が 20 倍になるのは、確認ダイアログや件数ガードを持つ CLI / プラグイン面の前提を変える。B173 と同じく **opt-in（既定 OFF）** が素直。

### 3.3 **B173 と `onChunkWritten` の設計が競合する**（依頼書が見ていない点）

B173 の仕様 R2 は、`onChunkWritten` を **native の 1 リクエストにつき 1 回・`operation: "UPSERT"`・`records` は当該リクエストの件数**と定めた（[仕様 R2 §9](ksql_b173_native_upsert_spec.md)）。依頼元は**チャンク数 = 100 件単位という前提でチェックポイント頻度と進捗表示を組んでいる**と明言しており、**分割通知は不可**という制約もそこから来ている。

`bulkRequest` を入れると **1 通知 = 最大 2,000 件**になり、この前提が崩れる。`lastKeyValue`（ソース順の最終キー）の意味も、2,000 件分飛ぶことになる。

→ **B174 を検討するときは、依頼元のチェックポイント設計との再調整が必須。B173 を先に出す**（B173 は先方の現行前提を壊さない）。

### 3.4 レート制限（依頼書 論点 3）

同時接続数は 1 ドメイン 100。`bulkRequest` は 1 接続で 20 サブリクエスト分の処理をさせるため、**同時接続数の消費は減るがサーバ負荷は変わらない**。429 の挙動が変わる可能性は依頼書のとおり未知（現検証では 429 発生ゼロ）。

## 4. 保留解除時に最初にやること（今は実施しない）

**所要時間を実測して採否を決める。** 同一アプリ・同一ペイロードで次を比較する。

- 100 件 × 20 回の逐次 PUT
- 2,000 件を `bulkRequest`（20 サブリクエスト × 100 件）1 回
- レコードの重さを 2 水準（軽量・実業務相当）測ると、依頼元の 2.67 秒/チャンクとの対応が付く
- **20 分の 1 に近づくなら価値がある。ほとんど変わらないなら ❌ クローズ**

**この測定は保留解除の前提であって、保留のまま先行して測ることはしない**（測ると「効果あり」と出たときに着手圧力が生まれ、保留の判断が実質的に覆るため）。

価値ありと出た場合も、着手は **B173 のリリース後**で、`onChunkWritten` の再調整を依頼元と合意してから（§3.3）。

## 5. 保留の理由（オーナー判断 2026-08-25）

**⏸ 保留＝実装しない。** 理由は 3 つ。

1. **効果が未測定**（§2.3）。依頼書が挙げた 44.6 分は事実だが、**その原因が往復回数だという前提は測られていない**。ペイロード処理が支配的なら束ねても縮まない
2. **費用が大きい**（§2.1）。17 箇所の書込ループの上に**リクエスト計画層を新設**する。2026-07-10 の M5 評価「重い」は今も有効
3. **依頼元の既存前提と衝突する**（§3.3）。`onChunkWritten` のチェックポイント粒度が 100 件 → 最大 2,000 件になり、依頼元の進捗表示と再開設計の再調整が要る。**B173 が先方の現行前提を壊さないのと対照的**

加えて、**依頼元には回避策が既にある**（会社名 `IN` によるバッチ分割。依頼書 §背景の注記のとおり、XL でも機能している）。[[demand-measured-by-first-written-form]] の「回避策の存在は優先度を下げる理由にならない」は**最初に書かれる形が通るか**という方言の穴の話であり、**本件は機能が成立したうえでの速度改善**なので当てはまらない。

### 5.1 保留を解く条件

次のいずれかが起きたら再評価する。

- **依頼元から「44.6 分が運用のブロッカーである」という具体的な実害の報告**が出る（現在は「時間短縮のみが目的・優先度中」との自己申告）
- **往復レイテンシ支配であることを示す実測**が依頼元またはこちらで得られる（§4）
- B173 が出たあとで、依頼元が `onChunkWritten` の粒度変更を受け入れられる設計に移行する
- 書込経路に別件でリクエスト計画層を入れる機会が生じ、**費用 2 が実質的に下がる**

## 6. 決着 — 依頼元の A/B 実測（2026-08-25 受領）

[返信](../../../ksql-flow/docs/kSQLエンジンへの返信-20260825-F5-AB実測.md)で、§4 に書いた比較を**当日そのままの設計で実測**して返してきた（エンジン非経由・kintone REST 直叩き）。

- 対象: SFA パック案件管理アプリ（ルックアップ `会社名` を含む 20 フィールド超）の **2,000 件**の `詳細`（文字列 1 行）UPDATE ＝ **2.67 秒/チャンクのベースラインと同一条件**
- ウォームアップ 1 回（計測外）→ A/B 交互 3 セット

| セット | A（100 件 × 20 回の逐次 PUT） | B（2,000 件を bulkRequest 1 回） |
|---|---|---|
| 1 | 56.7 秒（2.84 秒/チャンク） | 48.2 秒 |
| 2 | 49.8 秒（2.49 秒/チャンク） | 47.6 秒 |
| 3 | 40.5 秒（2.02 秒/チャンク） | 11.8 秒 |
| **中央値** | **49.8 秒** | **47.6 秒（B/A = 96%）** |

- A の秒/チャンク（2.02〜2.84）はスケール検証のベースライン 2.67 と整合＝**同じワークロード級であることが確認された**
- **B は中央値で A の 96%。1/20 には遠く及ばない**＝§2.3 の推測（サーバ側処理時間が支配的・サブリクエストは逐次処理）が実測で裏付けられた
- 依頼元の注記: B の 3 回目だけ 11.8 秒に振れた（1/3 回）。**仮に速い側が真値でも A 比 24% で 1/20 に届かず、再現性も無い**ため中央値で判断するのが妥当、との判断に同意する

**依頼元は「保留（実質クローズ）に同意」「再評価条件 §5.1 のうち 2（往復支配の実測）は逆方向で確定したため、残るは 4（別件でリクエスト計画層が入る機会）のみが現実的なトリガー」**と回答。→ **❌ クローズ**とする。

### 6.1 §7（回避策の運用負担）への回答

- 会社名 `IN` のバッチ分割方式は**機能面のブロッカーになっていない**（こちらの認識どおり）
- **運用負担も実質なし**＝分割はジェネレータが自動生成しており手書きの煩雑さがなく、失敗時の再開も冪等リラン（`--resume`）で完結
- **44.6 分は検証用の合成ワークロードで、実運用の SLA を圧迫している事実はない**。§5.1 の条件 1 に該当する事象が生じたら具体を添えて再起票する、とのこと

→ **別課題の起票も不要**と確定。

### 6.2 この決着から得た運用上の学び

**「効果が未測定」を理由に保留し、測り方だけ渡して返したのが正しく働いた。** こちらで先行して測らなかったこと（§4 の但し書き）も含めて、費用ゼロで結論が出た。
