# 課題: 範囲比較の厳密 10 進化（`<=`/`>=` 数値プレフィルタの前提・案B）

- 作成日: 2026-07-15
- ステータス: **保留確定（2026-07-15・ユーザー判断で 16 桁クラス数値アプリは当面対象外）。③の Number.isSafeInteger ゲートで 16 桁超リテラルは押し下げないため実害は低。残る乖離は「16 桁アプリの FULL_SCAN 範囲比較の丸め」のみ**
- 発見経緯: 述語分割 ③（[ksql_numeric_predicate_pushdown_spec.md](ksql_numeric_predicate_pushdown_spec.md) R2）で、一般 NUMBER フィールドの `<=`/`>=` 押し下げが IEEE-754 の境界丸めで超集合性を壊すため案A から除外。これを可能にするには JS の範囲比較を厳密 10 進にする必要がある。
- 分担: Claude=設計/観点、Codex=実装/テスト

## 背景

`scalarCompare`（[src/core/scalarCompare.ts](../../src/core/scalarCompare.ts)）の範囲比較は `Number()` を通す（IEEE-754）。桁の大きい整数や高精度小数は double へ丸められ、kintone（10 進）と結果がずれる。例:

- `Number("9007199254740993") === Number("9007199254740992")`
- `Number("0.99999999999999999") === 1`

このため一般 NUMBER フィールドの `<=`/`>=` を kintone に押し下げると、JS で真の行を kintone が除外して**結果が欠落**し得る（③で対象外にした理由）。

## この課題で扱うこと

**JS の範囲比較（`< > <= >=`）を厳密 10 進にする**（整数は `BigInt`、小数は 10 進の桁比較等）。これにより:

- FULL_SCAN の大整数・高精度小数の比較が**正確**になる（②の空セルと同種の「SIMPLE/FULL_SCAN 一致」改善）。
- ③の数値プレフィルタで **`<=`/`>=` も超集合性 OK** になり押し下げ可能になる。

## 設計で定義が必要な比較意味論（要仕様レビュー）

単なる最適化追加ではなく **`scalarCompare` の言語意味論を IEEE-754 から厳密 10 進へ変更**するため、次をすべて定義する:

- **符号**（正/負）と **負のゼロ**（`-0` と `0`）
- **小数**（`123.45`）と **末尾ゼロ**（`1.10` と `1.1`）
- **指数表記**（`1e2`, `1.5E-3`）の正規化
- **非有限値**（`Infinity`/`-Infinity`/`NaN` に解決される経路）の扱い
- **空文字との比較**（②の −∞ 規則との整合。空左辺は現状 `< /<=`→true・`> />=`→false）
- **非数値文字列**（テキストフィールド）の範囲比較（現行の文字列比較を維持するか）
- `=` / `!=` は現行の文字列比較を維持（変更しない）

## 影響範囲

- `scalarCompare` を使う全経路（WHERE / HAVING / CASE WHEN / サブテーブル UPDATE・DELETE・REORDER / ASSERT / BETWEEN）＝ ② と同じ広さ。既存の丸め挙動に依存するテストの見直しが必要。
- 変更後、③の抽出器で `<=`/`>=` を一般 NUMBER の押し下げ対象へ追加できる（別 PR）。

## 位置づけ・優先度

- **v2.2.0 には含めない**（②直後にもう一段モード意味論を触る影響が大きい）。独立した設計レビューを通す。
- 優先度: 中（`<=`/`>=` の押し下げ実需と、大整数/高精度小数を扱うアプリの有無で判断）。
