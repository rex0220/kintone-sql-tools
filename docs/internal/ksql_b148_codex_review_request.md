## 2. 特に見てほしい点（コードで真偽が決まるもの）

### 2.1 【最優先】`GROUP BY` との対応づけ（R1 §3）

**R1 は「名前一致で済ませない」と書いたが、具体的な判定方法を書いていない。**

- **`GROUP BY` の解決結果と「同じ実体を指す」ことを、どう判定すればよいか。**
  `plainGroupByPlan` の `PHYSICAL` / `ALIAS_SAFE` / `EXPRESSION` をそのまま使えるか
- **`SELECT` 句の列参照側**は、どの段階で「どのフィールドか」に解決されているか。
  **`GROUP BY` 側と同じ解決規則を通っているか**（通っていないなら、そこが穴）
- **§8 の解決順（同名フィールド優先 → 無ければ SELECT 別名）**を、
  **`SELECT` 句側の判定でも同じように適用しないと食い違う**のではないか

### 2.2 【最優先】式の一致（R1 §3・§5-2）

`GROUP BY DATE_FORMAT(日付,'%Y-%m')` に対し `SELECT DATE_FORMAT(日付,'%Y-%m')` を許すために、
**式の同一性をどう判定するか。**

- **AST の構造比較で足りるか。** 空白・リテラルの表記ゆれ・関数の別名（`SUBSTR`→`SUBSTRING`）で
  同じ式が別物と判定されないか
- **緩すぎると偽陰性**（違う式を同じとみなして誤った値を通す）、
  **厳しすぎると既存クエリを落とす**。**どちらに倒すべきか**
- **別名経由（`AS 年月 … GROUP BY 年月`）に限定して式の一致を諦める**選択肢はどうか。
  **それで主用途は守れるか**

### 2.3 適用範囲の穴

- **CTE・一時テーブルの中の `SELECT`** でも同じ判定が効くか。
  **効かないなら、`WITH m AS (SELECT 製品名, 個数, SUM(個数) … GROUP BY 製品名) SELECT * FROM m` で穴が残る**
- **JOIN を含む場合**の列解決（修飾名・同名フィールド）
- **サブクエリ**（スカラーサブクエリ・`IN` の中）
- **`UNION` の各 arm**
- **DML の `SELECT` 部**（`INSERT ... SELECT` / `UPDATE ... FROM`）
- **`ROLLUP` / `CUBE` / `GROUPING SETS`** のとき、grouping item は物理フィールドのみという
  既存契約と整合するか。**`GROUPING()` の引数**はどう扱うか

### 2.4 「集計を含むクエリ」の判定（R1 §2）

- **`SELECT` / `HAVING` のどちらかに集計関数があるか、`GROUP BY` があるとき**——これで過不足ないか
- **ウィンドウ関数は集計ではない**（`SUM(x) OVER (...)`）。**混同すると素の SELECT を壊す**。
  現行の AST でウィンドウと集計は区別できているか
- **`ORDER BY` にだけ集計がある形**（`SELECT 製品名 FROM t ORDER BY COUNT(*)`）は存在するか

### 2.5 エラーを出す位置（R1 §4.4）

- **「レコード取得前」に判定できるか。** フォーム定義（`getFields`）は要るか、要らないか
- **`EXPLAIN` / `ksql_validate` でも同じエラーになるか。**
  **依頼元は実行前に `ksql_explain` まで通す運用**なので、ここで出ないと意味が薄い
- **プラグイン（`prod/js/desktop.js`）は EXPLAIN エンジンをバンドルする**ので、
  **文言変更が波及する**。影響を確認してほしい

### 2.6 受入条件の穴（R1 §4）

- **R1 §4.1（通り続けるもの）に、落としてはいけない形の抜けが無いか**
- **R1 §4.2（エラーになるもの）に、偽陰性を止める adversarial case が足りているか**
- **受入が「内部実装」を要求していないか。** 観測可能な形（公開 API の結果・エラー文）で書けているか

### 2.7 `$id` / `レコード番号` での `GROUP BY`（R1 §5-5）

**標準 SQL は一意キーへの関数従属を認める**ので、`GROUP BY レコード番号` なら他の列を許してよい。
**R1 は Phase 1 で許さないと決めた。**

- **この判断で落ちる現実的なクエリはあるか**
- **後から許す側へ広げるのは、非破壊で可能か**（一度エラーにしたものを通すのは非破壊のはず）
