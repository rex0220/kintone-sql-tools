## 1. 何が成り立たないか

依頼文 ⑤ が例に挙げた APP4228 の 2 フィールドを実測しました。

| フィールド | 型 | 実体 | **3 フラグ** |
|---|---|---|---|
| `製品名` | SINGLE_LINE_TEXT | **ルックアップ**（APP4229 を引く） | `ルックアップ = YES` |
| `仕入先` | SINGLE_LINE_TEXT | **ルックアップのコピー先**（`fieldMappings` の宛先） | **3 つとも空** |

**`仕入先` は「型だけでは分からない何かが付いている」のに、3 フラグでは何も立ちません。**
素の文字列と区別が付かないままです。

つまり **「3 つとも空だから `ksql_app_metadata` は要らない」とは判断できません。**
`required` / 長さ制約なども同様に見えません。

### しかも kSQL は既にその区別を持っています

内部の正規化は `writable` という値を持っており、**ルックアップのコピー先を既に区別しています**
（`formFieldInfo.ts:72,86-97`）。**出していないだけ**です。

## 2. 確認したいこと

### Q1. 3 つのままでよいですか（目的を狭めることになります）

**3 つに絞る案（こちらの推奨）。** 目的を
「**lookup / unique / 計算式の有無を直接示す**」に狭め、
「1 ビットで metadata の要否を判断できる」という**完全性の主張は取り下げます**。

それでも価値があると考える理由は、**この 3 つが JOIN の正しさ・名寄せキーの可否・
数値の意味に直結し、外したときの誤りが静かに通る**ためです
（⑤ の実例＝ルックアップを素の文字列と誤認して「結合キーが無い」と書いた、がまさにこれです）。

### Q2. 第 4 のフラグ `書込不可`（ルックアップのコピー先）は要りますか

**実装コストはほぼゼロ**です（`writable` を出すだけ）。

ただし足すと**「3 つで打ち止め」という停止規則が消えます。**
次は `required`、その次は `maxLength` と続き、**`ksql_app_metadata` との境界が無くなります。**
**そちらの運用で `書込不可` が効く場面があるか**を教えてください。

- **効く場面がある** → 4 つにして、停止規則を「**書き込み可否と、値の由来（lookup / calc）と、キー適性（unique）**」と定義し直します
- **無い** → 3 つで止めます（実需が出たら再起票）

### Q3. そもそも `describe` にまだ需要がありますか

⑤ の時点では「カタログ作成に `describe` を使っていた」ことが前提でした。
その後、**そちらの鉄則 6 / 10 は「取得は `ksql_app_metadata` で行う。`describe` では足りない」**
に変わっています（当方が v3.47.0/v3.48.0 の反映時に更新しました）。

依頼文にも書かれています。

> それでも **`describe` は軽くて手が伸びる**ので、構造的な対策にはなっていない。

**こちらで測れる範囲では、そちらの `sql/` と `scripts/` に `DESCRIBE` は 1 件もありません**
（2026-08-06 時点）。ただし**その場限りの MCP 呼び出しはファイルに残らない**ので、
実際の使用頻度は分かりません。

**そこで確認です。鉄則 6 を入れた後、`describe` を実際に使う場面は残っていますか。**

- **残っている**（型だけ手早く見るとき等）→ 予定どおり実装します
- **ほぼ使わなくなった** → **優先度を下げます。** 使わない面を厚くしても効きません

**「計算できるか」ではなく「実際にそう書かれるか」で測りたい**ためです
（B124 で判断を誤った反省です）。

## 3. 併せてお知らせ（実装したら影響が出ます）

### 3.1 `SELECT *` の列が 3 → 6 になります

```
WITH d AS (DESCRIBE APP1) SELECT * FROM d      -- 3 列 → 6 列
```

**列を厳密に固定している利用者には破壊的です**（CSV ヘッダ・列数検査・UNION の位置対応など）。
3 列だけ必要なら**名指ししてください**。

```
SELECT フィールドコード, ラベル, タイプ FROM d
```

**そちらの `sql/` に `DESCRIBE` を使っているものがあれば教えてください。**

### 3.2 文書の列名が実装と食い違っていました（B136）

`ksql://language-reference` の `SHOW APPS` / `DESCRIBE` の例が**そのままでは動きません**。

```
WITH フィールド AS (DESC APP4228) SELECT * FROM フィールド WHERE type = 'NUMBER'
→ ArgumentError: unknown field code(s): type
```

文書は `name` / `fieldCode` / `label` / `type`、実装は `アプリID` / `アプリ名` / `説明` /
`フィールドコード` / `ラベル` / `タイプ` です。**該当 6 行。**

**そちらの「エージェントは文章より例を写す」という指摘（B129 の返信 §4）が、
そのままこちらに跳ね返りました。** DESCRIBE 分は B130 で、`SHOW APPS` 分と
再発防止は B136 で直します。**この誤記で実害を踏んでいたら教えてください。**
