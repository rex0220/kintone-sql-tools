## 1. 実測（2026-08-25・APP4253）

### 1.1 索引反映ラグ（**本件の中身**）

`key_text`（文字列 1 行）へ 2 件（`KSQL-FLOW-TEST-C200` と `ABC_DEF`）を POST した**直後**に `like` を撃ち、待ち時間を変えて 3 回繰り返した。

| 書込からの待ち | `KSQL` | `FLOW` | `TEST` | `C200` | `KSQL-FLOW-TEST-C` | `KSQL-FLOW-TEST-C200` | `ABC` | `ABC_DEF` |
|---|---|---|---|---|---|---|---|---|
| **0ms** | **×** | ○ | ○ | ○ | × | ○ | × | ○ |
| 3,000ms | ○ | ○ | ○ | ○ | × | ○ | × | ○ |
| 10,000ms | ○ | ○ | ○ | ○ | × | ○ | × | ○ |

- **待ち 0ms のときだけ `KSQL` が外れた**（3,000ms 以降は安定して ○）
- **外れるトークンは実行ごとに違う**。同じ形の先行実測では `TEST` と `C200` が外れ、`KSQL` は当たっていた
- → **書込直後の `like` は結果が不安定。エラーは出ず、件数が減るだけ**

### 1.2 **隣の経路の切り分け — ラグは `like` の全文索引だけ**（影響範囲の確定）

[[check-sibling-path-when-fixing]] に従い、押し下げされる他の述語も同条件で測った。1 件 POST した**直後**に 4 通りで引き、3 秒後に `like` を再確認。これを 8 回。

| 回 | 直後 `=` | 直後 `in` | 直後 `like` | 直後 `$id > 0` | 3 秒後 `like` |
|---|---|---|---|---|---|
| 1 | ○ | ○ | **×** | ○ | ○ |
| 2 | ○ | ○ | **×** | ○ | ○ |
| 3 | ○ | ○ | ○ | ○ | ○ |
| 4 | ○ | ○ | **×** | ○ | ○ |
| 5 | ○ | ○ | ○ | ○ | ○ |
| 6 | ○ | ○ | **×** | ○ | ○ |
| 7 | ○ | ○ | **×** | ○ | ○ |
| 8 | ○ | ○ | **×** | ○ | ○ |
| **取りこぼし** | **0/8** | **0/8** | **6/8** | **0/8** | 0/8 |

- **完全一致（`=`）・`IN`・`$id` は 8 回とも即時に反映された**＝レコード本体の可視性は遅れない。**ラグは `like` が使う全文検索索引に固有**
- **`like` は直後に 8 回中 6 回外した**＝**踏めば高確率で外す**。まれな競合ではない
- → **影響範囲は `KLIKE` に限定される**。テキストの `=` / `IN` 押し下げ（[選択系 IN 押し下げ](ksql_selection_in_pushdown_spec.md) 系）と `$id` 押し下げは**無傷**。`LIKE` は JS 評価（全件取得後にクライアント判定）なので**元から影響を受けない**

### 1.3 一致規則（副産物・依頼元の指摘は正しかった）

索引が落ち着いた状態で測ると、規則は一貫していた。

| 値 | 検索 | 結果 |
|---|---|---|
| `FOO BAR` | `FOO` / `BAR` | ○（空白で分割された各語） |
| `FOO BAR` | `OO` | ×（語の一部） |
| `X-Y` | `X` / `Y` / `X-Y` | ○ |
| `P-Q-R` | `P` / `Q` / `R` / `P-Q` | ○ |
| `ABCDEF` | `ABC` / `BCD` | ×（語の一部） |
| `ABCDEF` | `ABCDEF` | ○ |
| **`ALPHA_BETA`** | **`ALPHA` / `BETA`** | **×** |
| **`ALPHA_BETA`** | **`ALPHA_BETA`** | **○** |
| `KSQL-FLOW-TEST-C200` | `KSQL-FLOW-TEST-C` | ×（末尾トークン `C` が `C200` と一致しない） |

→ **`-`（ハイフン）と空白はトークンを分割するが、`_`（アンダースコア）は分割しない**。一致はトークン単位で、語の一部では当たらない。**依頼元の説明（ハイフンで分割され `C` が `C200` に一致しない）は正しい。**

### 1.4 影響範囲（確定）

> **【訂正 2026-08-25】この節の初版は「`KLIKE` は全 DML で使用不可」を前提にしていたが誤り。** 根拠にした [`ksql_batch_recipes.md`](../ksql_batch_recipes.md) の記述が **v3.10.0（B5）で解禁されたのに更新されていなかった**（訂正済み）。**言語リファレンスの `KLIKE` 節は正しかった**（「通常（APPLY なし）の親 `UPDATE` / `DELETE`、および APPLY 複数親 `UPDATE` の親 WHERE で使用できます」）。実装も許可している（[klikeValidation.ts:79-103](../../src/core/klikeValidation.ts#L79)・`src/core/__tests__/klikeValidation.test.ts:64-71` が `UPDATE … WHERE 件名 KLIKE …` と `DELETE … WHERE 件名 NOT KLIKE …` を許可で固定）。**指摘は codex（B175 方針判断の依頼時）。** 古い文書が実際に判断を誤らせた実例として [B141](ksql_b141_doc_sql_unverified_issue.md) にも記録する。**これにより本件の深刻度が上がる**（下表）。

| 経路 | 影響 | 根拠 |
|---|---|---|
| **`KLIKE` を含む親 DML**（通常の `UPDATE` / `DELETE` の WHERE・APPLY 複数親 `UPDATE` の親 WHERE） | **該当する。しかも読取より重い** | 親 DML は**WHERE 全体を kintone クエリへ exact 変換して対象を解決する**（言語リファレンス `KLIKE` 節）＝**§1.1 / §1.2 で測ったのと同じ索引経路**。したがって索引ラグにより **①対象を取りこぼして更新／削除しそこねる ②旧値に当たって本来対象外のレコードを更新／削除する**（旧値ヒットは 4/8）。**読取の件数ズレではなく誤った書込になる** |
| エンジン内部の読取（DML の対象取得・UPSERT のキー照合・APPLY の既存値取得） | **なし** | いずれも `=` / `IN` / `$id` を使う（§1.2 で無影響と実測）。**ただし `KLIKE` を書いた親 DML は上行のとおり別**  |
| テキスト `=` / `IN` 押し下げ | **なし** | §1.2 で 8/8 即時 |
| `$id` 押し下げ | **なし** | §1.2 で 8/8 即時 |
| `LIKE`（JS 評価） | **なし** | 全件取得後にクライアント判定するため索引を使わない |
| **同一バッチで「書込文 → `KLIKE` を含む SELECT / ASSERT」** | 該当（結果件数が狂う） | §1.1 / §1.2 |

**踏む条件は狭いが、踏んだときの確率は高い**（直後は 8 回中 6 回）。

**推奨レシピは踏まない形になっている** — dialect 1 の定石 [R18](../ksql_batch_recipes.md)（月次同期ジョブ）は `ASSERT`（読）→ `CREATE TEMP`（読）→ `EXIT` → `UPSERT`（書）で、**書込が最後の文**。定石に従う限り露出しない。

**危ないのは「書込後の検証」を書いたとき。** これは自然に書きたくなる形であり、しかも `ASSERT` で書くと fail-open になる（§2.1）。

## 2. なぜ問題か

### 2.1 fail-open である

`KLIKE` が索引ラグで取りこぼしても、**エラーにならず結果件数が減るだけ**。[B171](../ksql_release_history.md)（ASSERT の辞書順比較が fail-open だった件）と同じ形＝**止まるべきときに止まらず、静かに違う答えを返す**。

とくに危険なのは次の形。

```sql
-- dialect 1 のバッチ（書いてから検索する）
UPSERT INTO APP100 (コード, 区分) VALUES (...) ON DUPLICATE (コード);
SELECT * FROM APP100 WHERE 区分 KLIKE '要確認';   -- ← 直前に書いた行が入らないことがある
```

`ASSERT` の件数ゲートを `KLIKE` で書いていると、**ゲートが素通りする**。

### 2.2 dialect 1 はこの形を推奨している

`KLIKE` は「大規模アプリでも高速」として言語リファレンスが積極的に勧めており（`LIKE` は FULL_SCAN で取得上限に当たりやすいため）、**書込を含むバッチで使われる前提**がある。踏む条件が揃っている。

### 2.3 ただしエンジンのバグではない

kintone の検索索引の性質であり、`LIKE`（JS 評価・全件取得後にクライアント判定）では起きない。**エンジンにできるのは、正しく知らせることと、避け方を示すこと。**

### 4.2.1 `warning` か `EXPLAIN` 注記か — **到達面を測って結論が変わった**

**比較:**

| | `warning` | **`EXPLAIN` 注記** |
|---|---|---|
| 出るタイミング | **実行時**＝取りこぼしが起きたその時 | **実行前**＝まだ文順を直せる |
| `/flow` に届くか | **今は届かない**（型に置き場が無い） | **届く**（`plan` に 1 行） |
