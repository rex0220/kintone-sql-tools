# B175 `KLIKE` の索引反映ラグ — 書込直後の検索が静かに取りこぼす

- 状態: 📝 **起票済み・案 A（文書）実施済み／案 B（静的 warning）は B173 リリース同梱を提案中**（2026-08-25）＝**fail-open の穴**。書込直後に `KLIKE` で検索すると、**索引が追いつかず一致するはずのレコードが返らないことがある**。エラーにならず件数が減るだけなので気づけない。**エンジンの不具合ではなく kintone の検索索引の性質**だが、**dialect 1 のバッチは「書いて → 検索する」形を推奨しているため踏みやすい**
- 種別: 課題（正しさ／文書）
- 優先: **中**（結果が静かに変わる。**踏む条件は狭いが踏めば高確率で外す**〔直後は 8 回中 6 回〕。回避は容易＝`LIKE` を使う・書込を最後に置く）
- 影響範囲: **`KLIKE` に限定**（§1.4 で確定）。テキスト `=` / `IN` 押し下げ・`$id` 押し下げ・`LIKE`（JS 評価）・エンジン内部の読取は**すべて無影響と実測**
- 発見の経緯: [ksql-flow の F-5 返信 §3](../../../ksql-flow/docs/kSQLエンジンへの返信-20260825-F5-AB実測.md)の副次メモ（「`like "KSQL-FLOW-TEST-C"` は語単位マッチのため `KSQL-FLOW-TEST-C200` に当たらない」）を**既知かどうか確かめに行って、別の穴が出た**
- 関連: [KLIKE 仕様](ksql_klike_native_search_spec.md)／[LIKE を JS 判定のみに統一](ksql_like_js_default_optin_pushdown_spec.md)／[文字列の扱い（横断仕様）](ksql_string_semantics.md)

## 1. 実測（2026-08-25・APP4253）

### 1.1 索引反映ラグ（**本件の中身**）

`key_text`（文字列 1 行）へ 2 件（`KSQL-FLOW-TEST-C200` と `ABC_DEF`）を POST した**直後**に `like` を撃ち、待ち時間を変えて 3 回繰り返した。

| 書込からの待ち | `KSQL` | `FLOW` | `TEST` | `C200` | `KSQL-FLOW-TEST-C` | `KSQL-FLOW-TEST-C200` | `ABC` | `ABC_DEF` |
|---|---|---|---|---|---|---|---|---|
| **0ms** | **×** | ○ | ○ | ○ | × | ○ | × | ○ |
| 3,000ms | ○ | ○ | ○ | ○ | × | ○ | × | ○ |
| 10,000ms | ○ | ○ | ○ | ○ | × | ○ | × | ○ |

- **待ち 0ms のときだけ `KSQL` が外れた**（3,000ms 以降は安定して ○）
- **外れるトークンは実行ごとに違う**。同じ形の先行実測では `TEST` と `C200` が外れ、`KSQL` は当たっていた
- → **書込直後の `like` は結果が不安定。エラーは出ず、件数が減るだけ**

### 1.2 **隣の経路の切り分け — ラグは `like` の全文索引だけ**（影響範囲の確定）

[[check-sibling-path-when-fixing]] に従い、押し下げされる他の述語も同条件で測った。1 件 POST した**直後**に 4 通りで引き、3 秒後に `like` を再確認。これを 8 回。

| 回 | 直後 `=` | 直後 `in` | 直後 `like` | 直後 `$id > 0` | 3 秒後 `like` |
|---|---|---|---|---|---|
| 1 | ○ | ○ | **×** | ○ | ○ |
| 2 | ○ | ○ | **×** | ○ | ○ |
| 3 | ○ | ○ | ○ | ○ | ○ |
| 4 | ○ | ○ | **×** | ○ | ○ |
| 5 | ○ | ○ | ○ | ○ | ○ |
| 6 | ○ | ○ | **×** | ○ | ○ |
| 7 | ○ | ○ | **×** | ○ | ○ |
| 8 | ○ | ○ | **×** | ○ | ○ |
| **取りこぼし** | **0/8** | **0/8** | **6/8** | **0/8** | 0/8 |

- **完全一致（`=`）・`IN`・`$id` は 8 回とも即時に反映された**＝レコード本体の可視性は遅れない。**ラグは `like` が使う全文検索索引に固有**
- **`like` は直後に 8 回中 6 回外した**＝**踏めば高確率で外す**。まれな競合ではない
- → **影響範囲は `KLIKE` に限定される**。テキストの `=` / `IN` 押し下げ（[選択系 IN 押し下げ](ksql_selection_in_pushdown_spec.md) 系）と `$id` 押し下げは**無傷**。`LIKE` は JS 評価（全件取得後にクライアント判定）なので**元から影響を受けない**

### 1.3 一致規則（副産物・依頼元の指摘は正しかった）

索引が落ち着いた状態で測ると、規則は一貫していた。

| 値 | 検索 | 結果 |
|---|---|---|
| `FOO BAR` | `FOO` / `BAR` | ○（空白で分割された各語） |
| `FOO BAR` | `OO` | ×（語の一部） |
| `X-Y` | `X` / `Y` / `X-Y` | ○ |
| `P-Q-R` | `P` / `Q` / `R` / `P-Q` | ○ |
| `ABCDEF` | `ABC` / `BCD` | ×（語の一部） |
| `ABCDEF` | `ABCDEF` | ○ |
| **`ALPHA_BETA`** | **`ALPHA` / `BETA`** | **×** |
| **`ALPHA_BETA`** | **`ALPHA_BETA`** | **○** |
| `KSQL-FLOW-TEST-C200` | `KSQL-FLOW-TEST-C` | ×（末尾トークン `C` が `C200` と一致しない） |

→ **`-`（ハイフン）と空白はトークンを分割するが、`_`（アンダースコア）は分割しない**。一致はトークン単位で、語の一部では当たらない。**依頼元の説明（ハイフンで分割され `C` が `C200` に一致しない）は正しい。**

### 1.4 影響範囲（確定）

| 経路 | 影響 | 根拠 |
|---|---|---|
| **エンジン内部の読取** | **なし** | `KLIKE` は**全 DML で静的に使用不可**（[batch_recipes](../ksql_batch_recipes.md) の注記どおり）。DML の対象取得・UPSERT のキー照合・APPLY の既存値取得はいずれも `=` / `IN` / `$id` を使う（§1.2 で無影響と実測） |
| テキスト `=` / `IN` 押し下げ | **なし** | §1.2 で 8/8 即時 |
| `$id` 押し下げ | **なし** | §1.2 で 8/8 即時 |
| `LIKE`（JS 評価） | **なし** | 全件取得後にクライアント判定するため索引を使わない |
| **同一バッチで「書込文 → `KLIKE` を含む SELECT / ASSERT」** | **これだけが該当** | §1.1 / §1.2 |

**踏む条件は狭いが、踏んだときの確率は高い**（直後は 8 回中 6 回）。

**推奨レシピは踏まない形になっている** — dialect 1 の定石 [R18](../ksql_batch_recipes.md)（月次同期ジョブ）は `ASSERT`（読）→ `CREATE TEMP`（読）→ `EXIT` → `UPSERT`（書）で、**書込が最後の文**。定石に従う限り露出しない。

**危ないのは「書込後の検証」を書いたとき。** これは自然に書きたくなる形であり、しかも `ASSERT` で書くと fail-open になる（§2.1）。

## 2. なぜ問題か

### 2.1 fail-open である

`KLIKE` が索引ラグで取りこぼしても、**エラーにならず結果件数が減るだけ**。[B171](../ksql_release_history.md)（ASSERT の辞書順比較が fail-open だった件）と同じ形＝**止まるべきときに止まらず、静かに違う答えを返す**。

とくに危険なのは次の形。

```sql
-- dialect 1 のバッチ（書いてから検索する）
UPSERT INTO APP100 (コード, 区分) VALUES (...) ON DUPLICATE (コード);
SELECT * FROM APP100 WHERE 区分 KLIKE '要確認';   -- ← 直前に書いた行が入らないことがある
```

`ASSERT` の件数ゲートを `KLIKE` で書いていると、**ゲートが素通りする**。

### 2.2 dialect 1 はこの形を推奨している

`KLIKE` は「大規模アプリでも高速」として言語リファレンスが積極的に勧めており（`LIKE` は FULL_SCAN で取得上限に当たりやすいため）、**書込を含むバッチで使われる前提**がある。踏む条件が揃っている。

### 2.3 ただしエンジンのバグではない

kintone の検索索引の性質であり、`LIKE`（JS 評価・全件取得後にクライアント判定）では起きない。**エンジンにできるのは、正しく知らせることと、避け方を示すこと。**

## 4. 対策と時期

### 4.1 案 A（文書のみ）— **実施済み**（2026-08-25・エンジン不変）

- `KLIKE` 節に**書込直後は取りこぼし得る**旨と、`LIKE` を使う回避策を追加
- 一致規則の表に実測行 3 つを追加（現行の表は**空白区切りの例しかなく、記号の扱いが読み取れなかった**）。値はすべて §1.3 の実測（[B141](ksql_b141_doc_sql_unverified_issue.md) の教訓＝挙動を写した表は実測に基づかせる）
- **ラグの秒数は書かない**（§5 のとおり上限が未測。数字を約束しない）

**文書だけでは「既に書かれた SQL」を救えない**ため、案 B の判断が要る。

### 4.2 案 B（静的 warning）— **B173 のリリースに同梱するのが妥当**

判定条件は**静的に決まり、追加 API も要らない**:

> 同一バッチ内で、**書込文（INSERT / UPDATE / DELETE / UPSERT / IMPORT）より後**に、**同じ appId** を読む `KLIKE` を含む文がある

**誤検知が小さい**理由＝この形は実際に危険であり（書込フィールドが KLIKE の対象フィールドと違っても、レコードの再索引が走るため無関係とは言えない）、`KLIKE` は特定アプリの SELECT にしか書けないので条件が絞れる。[B140](ksql_b140_cte_groupby_total_order_issue.md) の警告疲れ（条件が広すぎて常時出る）とは形が違う。

**時期を B173 と同じリリースにする理由**:

1. **単独リリースを切る価値がない**（[B116](ksql_b116_pending_doc_changes_issue.md) の運用＝文書・小改修は次の機能リリースに同梱）
2. B173 で `/flow` の**書込経路とバッチ文列を触る**ため、文列を見る検査を足す文脈が既にある
3. 文書（案 A）は**これから書く人**にしか効かない。**既に書かれたバッチ**を救えるのは検査だけ

### 4.2.1 `warning` か `EXPLAIN` 注記か — **到達面を測って結論が変わった**

当初の見立ては「`warning`（fail-open を静かに残すより、うるさい方が安全側）」だった。**到達面を調べたら、`warning` は肝心の `/flow` に今日届かないことが分かった**ので、**`EXPLAIN` 注記を先に入れる**へ改める。

**実測（到達面）:**

| 事実 | 根拠 |
|---|---|
| **`/flow` の `StatementResult` に `warnings` が無い** | [flow-library/publicTypes.ts:258-270](../../src/flow-library/publicTypes.ts#L258)＝`index` / `type` / `status` / `kind` / `result?: unknown` / `tempTable` / `rowCount` / `error` / `skippedReason` / `metrics` のみ |
| **batch 経路にしか警告がマージされない** | `dialect1Warnings` を SELECT 結果へ merge するのも（[execute.ts:1720-1729](../../src/execute.ts#L1720)）、バッチ全体の `warnings` を返すのも（[同 :1763](../../src/execute.ts#L1763)）**`executeBatch` だけ**。`/flow` の managed 経路（[同 :1950](../../src/execute.ts#L1950)）は `statementOutcome` をそのまま展開するだけで**警告を付けない** |
| **`ExplainScriptResult` には注記を置ける** | [publicTypes.ts:121-124](../../src/flow-library/publicTypes.ts#L121)＝`statements: Array<{ index; type; plan: string[] }>`。**`plan` は文字列配列なので 1 行足すのは純加法**で、公開型の変更が要らない |
| **EXPLAIN に助言行を出す前例がある** | [execute.ts:12855](../../src/execute.ts#L12855) の `reference: bulkRequest は未実装…`。**同じ関数に足すだけ** |

**比較:**

| | `warning` | **`EXPLAIN` 注記** |
|---|---|---|
| 出るタイミング | **実行時**＝取りこぼしが起きたその時 | **実行前**＝まだ文順を直せる |
| `/flow` に届くか | **今は届かない**（型に置き場が無い） | **届く**（`plan` に 1 行） |
| CLI / MCP に届くか | 届く（batch envelope の `warnings`） | 届く（EXPLAIN 出力） |
| 機械判定 | 可（型を足せば） | 不可（`plan` の文字列） |
| 公開型の変更 | **要る**（`StatementResult` に `warnings` を純加法で追加） | **不要** |
| [B143](ksql_b143_explain_warnings_issue.md) との関係 | **B143 の穴をそのまま踏む**＝依頼元は「実行前に `explainScript` まで通す」運用なので、EXPLAIN が warnings を返さない限り**実行するまで気づけない** | **B143 を迂回する**（EXPLAIN 自体に載せるので B143 の解決を待たない） |
| 判定に要る情報 | 文列のみ | 文列のみ（**B143 の window 警告と違いフォーム定義が要らない**＝EXPLAIN 経路で確実に出せる） |

**結論＝2 段階にする。**

1. **まず `EXPLAIN` 注記**（B173 のリリースに同梱）。公開型を変えず、依頼元に今日届き、**実行前**に出る。B143 の解決を待たない
2. **`warning` は追って**。ただし先に **`/flow` の `StatementResult` に `warnings` を足す**（純加法）か、**B143 案 A（EXPLAIN も `warnings` を返す）**のどちらかが要る。**単独で `warning` だけ入れても `/flow` には届かない**

**B143 への波及**: 本件は「**フォーム定義を要さず文列だけで決まる警告**」なので、B143 案 A（EXPLAIN も warnings を返す）の**着手前確認「EXPLAIN 経路に resolver があるか」に引っかからない**。B143 が案 A を採るなら、**本件がその最初の実例になり得る**（B143 の見立て「resolver が既にあれば安い、無ければ見送り」に対して、resolver 不要な警告が 1 つある、という材料）。
