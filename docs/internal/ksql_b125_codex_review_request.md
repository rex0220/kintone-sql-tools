## 3. 特に見てほしい点

**この 6 点は、コードを読めば真偽が決まるもの**なので重点的に確認してほしい。
仕様が「既にこうなっている」と書いていることが、実際にそうなっているかの照合。

### 3.1 `evalAggregate` の切り出しは本当に安全か（最重要）

仕様 §6.2 は、`evalAggregate`（`src/engine/process.ts` 532 行付近）の
「行 → 値 / スキップ」のループ（546〜567 行付近）を
`aggregateRowValues(func, arg, rows): (string | null)[]` として切り出し、
**通常集計とウィンドウ集計で共有する**としている。

- この切り出しで**12 集計すべての挙動が本当に不変か**。
  とくに `MIN` / `MAX` が空文字を残す分岐、統計集計の `Number` 化と例外、
  `DISTINCT` の適用単位（文字列単位 / 数値同値単位）との順序関係
- `null` を「スキップ」の表現に使うことで、**値そのものが `null` / 空文字である場合と
  区別できなくなる箇所**が無いか
- 切り出し後に `evalAggregate` 側で**二重にスキップ判定をしてしまう**設計になっていないか

### 3.2 増分計算は既存の集計と同値か

仕様 §6.2 は `SUM` / `COUNT` / `AVG` / `MIN` / `MAX` を**増分で累積**する（O(N)）としている。

- `AVG` を「和と件数を持って割る」形にしたとき、既存 `evalAggregate` の `AVG` と
  **浮動小数の誤差まで含めて一致する**か（加算順序が同じかどうか）
- `MIN` / `MAX` を走査中に保持する形で、既存の比較規則
  （`resolveAggregateArgSemantics` → 数値順 / コードポイント順 / 選択肢定義順）と
  **同じ結果になる**か。とくに空セルが候補に残る `MIN` / `MAX` の扱い
- 全行がスキップされたパーティションで、既存 `evalAggregate` と同じ値になるか

### 3.3 `applyWindow` の同順検出は `RANGE` に流用できるか

仕様 §6.1 / §6.3 は、既存の `sortedResult.compare(sorted[i-1], sorted[i]) !== 0`
（`RANK` 用の同順境界検出）が **`RANGE` フレームにそのまま使える**と主張している。

- この `compare` は `OVER (ORDER BY ...)` の**キーだけ**で比較しているか。
  それ以外（安定ソートのための行 index など）が混ざっていれば、
  同順グループの判定が壊れる
- §6.3 の「`ROWS` で累積 → 同順グループの末尾値を書き戻す」で `RANGE` が正しく出るか

### 3.4 パーサの先読みは成立するか

仕様 §5.1 は「集計関数の引数を読み終えた直後に `OVER` を先読みする」としている。

- 集計列を読む経路は複数ある（単独集計列 / 集計算術式 / `CASE` の中 / `HAVING` / `ORDER BY`）。
  **`OVER` の先読みを入れるべき箇所は本当に 1 箇所か**
- `SUM(a) OVER (...) * 2` のような「ウィンドウ結果を算術式に入れる」形は
  仕様で触れていない。**現状どう落ちるか**、Phase 1 で拒否するなら
  どこで拒否されるか
- 併用チェック（`parser.ts` 1176〜1180 行）で、集計ウィンドウ列が
  `hasAggregate` に**入らない**という仕様 §5.3 の主張は正しいか
  （`selectColumnHasAggregate` の実装を確認）

### 3.5 `WindowColumn` をユニオンにする影響

仕様 §4 は `WindowColumn` を `RankingWindowColumn | AggregateWindowColumn` の
判別ユニオンに変える。

- **`WINDOW_COL` を参照している箇所を全部列挙**してほしい（仕様は 13 ファイルと書いている）。
  数と場所が合っているか
- 各箇所で `window.func` を直接読んでいるものはどれか。
  `isRankingWindow` で絞る必要がある箇所の**具体的なリスト**
- `windowKind` を optional（省略時 = RANKING）にする案で、
  **型として穴が無いか**（`AggregateWindowColumn` が `func` を持たないことによる問題）

### 3.6 既存契約との齟齬

- 言語リファレンス §10.1 の記述（`SELECT DISTINCT` 併用不可・`KORDER BY` 併用不可・
  `OVER (ORDER BY ...)` から同一 SELECT の alias 参照不可）が、
  **集計ウィンドウにもそのまま当てはまるか**。当てはまらないものがあれば指摘してほしい
- v1 仕様 §5 の「DISTINCT のキー生成でウィンドウ列は未対応」が、
  Phase 1 で新たな穴にならないか

**根拠のないコメントは書かないでほしい。** 「〜かもしれない」ではなく、
**該当コードを引用して**「こうなっているので、こうなる」と書いてほしい。
確認できなかった項目は「未確認」と明記してくれればよい。
