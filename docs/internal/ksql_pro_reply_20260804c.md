# 本文（送付版）

## 【返信】K-112 — ご報告が正しかったです。v3.42.0 で丸めるよう直しました

```
npm i @rex0220/kintone-sql-tools@3.42.0
```

**こちらでも実測し、報告いただいた 5 例すべてが一致しました。**
訂正の直後にこちらの欠陥を見つけていただく形になり、恐縮です。ありがとうございます。

## 1. 原因

`applyDateAdd` が **JavaScript の `Date` の正規化をそのまま漏らしていました。**

```ts
dt.setUTCMonth(dt.getUTCMonth() + n);   // 2026-01-31 に +1 → 「2026 年 2 月 31 日」→ 3 月 3 日
```

ご推測どおりです。**設計された挙動ではなく副産物**でした。

## 2. 案 1（月末へ丸める）を採りました

「破壊的変更だから現状維持」は採りませんでした。理由は 4 つです。

1. **いまの出力は擁護できる意味論ではない**——往復しても戻らず、`1/31 +1ヶ月` と
   `3/31 -1ヶ月` が同じ日になり、順序も壊れる
2. **主要な SQL エンジンはすべて丸める**（MySQL / PostgreSQL / Oracle）
3. **静かに間違う形**である。ご指摘のとおり締め日が月末の業務がそのまま踏み、
   エラーにならないので気づけない。**こちらは同種の「静かな誤り」を fail-closed で
   潰してきた**ので、ここだけ残すのは一貫しません
4. **壊れるのは「今日ちがう月の日付を返している」ケースだけ**＝それに依存している
   利用者は、バグに依存していることになります

```
修正前  DATE_ADD('2026-01-31', 1, 'MONTH') → 2026-03-03
修正後  DATE_ADD('2026-01-31', 1, 'MONTH') → 2026-02-28
```

**丸めが起きないケースと `DAY` 単位の結果は完全に不変**です。

## 3. 「月の比較には使わない」という回避は、撤回して構いません

そちらの文書に**当面「月の比較には使わない」**と書かれるとのことでしたが、
**v3.42.0 では `DATE_ADD` を月の計算に普通にお使いいただけます。**

`YEAR(列) * 12 + MONTH(列)` の数値演算（D2）も**引き続き正しく動く**ので、
急いで書き換える必要はありません。どちらでも構いません。

## 4. 1 点だけ、仕様として残したこと

**丸めが起きた場合、往復は元へ戻りません。**

```
DATE_ADD(DATE_ADD('2026-01-31', 1, 'MONTH'), -1, 'MONTH')  →  2026-01-28
```

`1/31` → `2/28` → `1/28` です。**MySQL も同じ**で、丸めの性質上避けられません。
リファレンスに明記し、テストでも意図として固定しました。後から「往復が戻らない」と
見えたときに、**バグではなく仕様**だと分かるようにしてあります。

## 5. あわせて文書を 4 件

- **押し下がる形への書き換え表**（そちらのレシピ集から取り込んだもの）
- **日時フィールドの境界は半開区間**（`>= 開始日 AND < 終了日の翌日`）を推奨へ
- **`CURRENT_DATE()` は実行環境のローカルタイムゾーン**で評価される旨
- 未知の `fetch` 値を「軽い側」へ寄せない旨
