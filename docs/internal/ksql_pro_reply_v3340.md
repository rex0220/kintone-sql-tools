## 1. 挙げていただいた 2 本は、v3.34.0 で両方ともエラーになりました

**同じアプリ・同じ `maxRecords` で実行しました。**

まず件数です。

```
APP4149（案件） =  20 件
APP4148（顧客） = 215 件
```

**結果です。**

| 試した形 | `maxRecords` | Pro の報告 | こちらの実測（v3.34.0） |
|---|---:|---|---|
| `APP4149 d LEFT JOIN APP4148 c` | 20 | 行 + 警告 | **エラー**（`OUTER_JOIN_NON_PRESERVED（APP4148）`） |
| `APP4149 d RIGHT JOIN APP4148 c` | 10 | 行 + 警告 | **エラー**（`OUTER_JOIN_NON_PRESERVED（APP4149）`） |

```sql
SELECT d.案件名, c.会社名 FROM APP4149 d LEFT JOIN APP4148 c ON d.顧客No_ = c.顧客No
-- maxRecords=20 / truncate
-- → FetchAllLimitError: complete input reason: OUTER_JOIN_NON_PRESERVED（APP4148）
```

### 1.1 **「保持側の打ち切り」は、このデータでは起こりません**

**`APP4149` は 20 件ちょうど**です。
**`maxRecords=20` では上限を超えないので、保持側は打ち切られません。**

**打ち切られていたのは保持されない側（`APP4148` の 215 件）**です。
**そして「行 + 警告」は、まさに v3.33.0 の挙動**です。

```
v3.33.0 → 保持されない側が打ち切られても、警告だけで行を返す  ← B98 で直した形
v3.34.0 → エラー
```

**こちらの推測ですが、3.34.0 へ差し替える前の測定ではないでしょうか。**
`vendor/` の tgz と、テストが実際に読んでいる版をご確認ください。
（§2 の 3 行目に「v3.33.0 の判定」と注記されていたので、
**同じ環境で 1〜2 行目も測られた可能性がある**と考えました。）

## 2. **結合キーによる絞り込みは、外部結合では行われません**

**「結合キーで絞り込まれるため、保持されない側が独立して上限に達しない」**
というご説明は、**外部結合では成り立ちません。**

**結合キーの押し下げは `INNER JOIN` だけが対象です。**
**1 つでも外部結合が混じると、押し下げの計画そのものを作りません。**

そのため **`APP4148` の 215 件は、`APP4149` の内容と無関係に、独立して上限へ達します。**
上の実測がそれです。

### 2.1 **保持側だけを打ち切る形は、こう作れます**

**保持側を大きいほうにしてください。**

```sql
SELECT c.会社名, d.案件名 FROM APP4148 c LEFT JOIN APP4149 d ON c.顧客No = d.顧客No_
-- maxRecords=50 / truncate
-- → 58 行 + 警告「取得上限（50 件）に達したため、50 件で打ち切って表示しています。」
```

**保持側 215 件 > 50 で打ち切られ、保持されない側 20 件 < 50 は打ち切られない**——
**この並びのときだけ、従来どおり警告付きで返ります。**

## 3. §1 の結論は変わりません。ただし見積もりは変わります

**出荷物に外部結合がゼロである以上、Pro の出荷物への影響はありません。**
**`INNER JOIN` の結果一致まで実機で確認いただいた点も、そのとおりです。**

変わるのは **「利用者が自分で書く SQL」の頻度の見積もり**です。

**「こちらの SFA パックのデータ形では自然には起きない」ではなく、
むしろ SFA パックのデータで、既定に近い `maxRecords` ですぐ起きます。**
顧客アプリが 215 件ある以上、**顧客側を保持しない外部結合は上限に掛かりやすい**からです。

**利用者向けの案内としては、「起きにくい」ではなく
「外部結合を書くなら `maxRecords` を候補集合より大きくする」**が実態に合います。

## 4. §3 のエラー文について — **ご指摘のほうが射程が広いです**

**「現状のままで結構です」とのことでしたが、測ってみました。**

**対処が最後に来るのは B98 だけではありません。完全入力を理由に止まる 9 つの形すべてです。**

| | 文字数 | 対処が始まる位置 |
|---|---:|---:|
| `AGGREGATE`（集計） | 137 | 101 |
| `GROUP_BY` | 140 | 104 |
| `DISTINCT` | 143 | 107 |
| `GROUPING_SETS`（小計・総計） | 144 | 108 |
| `LOCAL_ORDER` | 145 | 109 |
| 統計集約 / 集計＋並び | 151 | 115 |
| **`OUTER_JOIN_NON_PRESERVED`（B98）** | **163** | **127** |

**どれも 5 文で、対処は 5 文目**です。
**「先頭の 1〜2 文しか見えない」なら、一族のどれでも対処は読めません。**

**B98 は一族で最長**です。理由は `OUTER_JOIN_NON_PRESERVED` が最も長い識別子で、
**さらにアプリ番号が付く**ためです。

**内部識別子の露出も 9 つすべて**で、B98 で新しく始まったものではありません
（`complete input reason: AGGREGATE` などの形で以前から出ています）。

**つまりご指摘は「B98 の文面」ではなく「このエラー一族の語順」の問題**です。
**[B100](ksql_b100_failclosed_message_order_issue.md) として起票しました。優先度は 低 と判断しています**——**誤った結果を返す問題ではなく、止まるべきときに止まっている**ためです。
**Pro 側で短い文言に差し替える対応を止める必要はありません。**
エンジン側で語順を変える場合も、**`FetchAllLimitError` という型と、
`complete input reason:` に続く識別子は残す**方向で考えます。
