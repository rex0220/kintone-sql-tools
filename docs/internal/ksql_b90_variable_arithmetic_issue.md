# B90 変数を算術式に直接書けない（関数で包めば動く）

- 起票: 2026-07-29
- ステータス: ✅ **リリース済み（v3.31.0・2026-07-29）**（案 (a) で対応）
- 出典: [Pro からの連絡 2026-07-29](../../../ksql-dashboard-pro/docs/internal/kSQLエンジンへの連絡-20260729-送付版.md) 依頼②
- 関連: [バッチ変数 Phase 1a](../../../..) / [B89 explainQuery バッチ](ksql_b89_library_explain_batch_issue.md)

## 1. 事象（実機で再現・2026-07-29）

```sql
CREATE TEMP TABLE #g AS SELECT 案件No, 顧客No FROM APP4147 LIMIT 5;
SET @total = (SELECT SUM(顧客No) FROM #g);

SELECT 案件No, (顧客No * 100) / @total AS 構成比 FROM #g;
-- → ParseError: 算術式のオペランドには識別子・数値・括弧式を指定してください（位置 133、トークン: 「@total」）

SELECT 案件No, ROUND(顧客No * 100 / @total, 1) AS 構成比 FROM #g;
-- → ✅ 5.9 / 23.5 / 17.6 / 35.3 / 17.6
```

**関数引数の中なら変数が算術に参加できるのに、直接書くと通らない。**

## 2. 原因＝式文法が 2 系統ある

| 文法 | 使われる場所 | `@var` |
|---|---|---|
| `SCALAR_*`（[parser.ts:1568](../../src/parser/parser.ts#L1568)） | 関数引数・`SET` の右辺 | ✅ 受理 |
| **`ARITH*`**（[parser.ts:1693-1707](../../src/parser/parser.ts#L1693)） | **SELECT 列の算術** | ❌ 未対応 |

`parseArithPrimary` が受けるのは `(expr)` / 単項符号 / 文字列・数値関数 / `NUMBER` /
`IDENT`・`BIDENT` だけで、`TokenKind.VARIABLE` の分岐が無い。

## 3. なぜ Pro が困るか

**構成比（全体比 %）はダッシュボードで最も要望の多い列の 1 つ。**
Pro は従来これを「SQL では出せない」と文書化しており、
**`runBatch` の採用でようやく書けるようになった**という経緯がある。

利用者への説明が **「`ROUND()` で包んでください。理由は文法上の都合です」**となり、
納得しづらい形になっている。

## 4. 実現性＝**案 (a) は現実的**

**変数は実行前に解決され、評価器や押し下げ分類器へは届かない。**

[`resolveBatchVariableReferences`](../../src/execute.ts#L1975) は
**木全体を汎用に走査**して `{ type: "VARIABLE", name }` をリテラルへ置き換える。
配列・オブジェクトを問わず辿るため、**算術木の中に置いても同じように解決される。**

```ts
if (obj["type"] === "VARIABLE" && typeof obj["name"] === "string") {
  const value = variables.get(obj["name"]);
  ...
}
```

したがって、**パーサが算術中に変数ノードを出せるようにすれば、
下流は解決済みのリテラルしか見ない。**押し下げの安全性に触れずに済む。

**配列変数の誤用も既に塞がれている**（`array variable @x can only be used as IN @x`）。

### 4.1 コスト＝`ArithNode` 型の波及

`ArithNode` に変数を足すと**全消費側へ波及する**。
TypeScript が漏れを検出してくれるので**安全側だが、作業量はそれなり**である。

**波及先が「解決前に走るか」を1件ずつ確認する必要がある。**
`buildBatchExplainPlans` は `resolveBatchVariableReferences` を計画前に呼んでいるが、
**同種の経路が他に無いことを機械的に確かめる**のが本課題の中核になる。

### 4.2 バッチ外での扱い

変数はバッチにしか存在しない。
**単文で算術中に `@x` を書いた場合は、従来どおり明確なエラー**になる。
**実測した文言は `ParseError: variable @x is not defined before statement 1.`**
（`collectVariableRefs` が拾うため追加実装は不要）。

## 5. 案

### 5.1 案 (a) — 直接算術を許可する（Pro の希望・推奨）

§4 のとおり実現可能。**Pro の説明が「文法上の都合」でなくなる。**

### 5.2 案 (b) — 言語リファレンスに制約を明記する

「変数を算術に使う場合は関数で包む」と §25 に書く。**0.25 人日**で済み、
Pro のレシピ集からそこを参照できる。

**(a) を採るなら (b) は不要**（書く内容が無くなる）。

> **【オーナー決定 2026-07-29】(a) を採用。**Pro へもその旨を伝え済み。
> Pro からは「(b) の文書化ではなく (a) で受けていただけたのは想定以上」との返答。

## 6. 規模

- 調査（`ArithNode` 消費側の棚卸しと「解決前に走る経路」の確認）: 0.25〜0.5 人日
- 実装（パーサ＋型の拡張）: 0.5 人日
- テスト（解決前に評価する経路が無いことの機械的確認・単文での明確なエラー）: 0.25〜0.5 人日

**合計 1.0〜1.5 人日。SemVer=minor（純加法＝従来 ParseError だったものが通る）。**

案 (b) のみなら 0.25 人日。

## 7. 優先度の根拠

**回避策がある**（`ROUND()` で包む）ため B89 より低い。
一方で **B89 と同じリリースに載せる価値はある**＝どちらも
**`runBatch` 採用によって顕在化した使い勝手の欠落**で、Pro のレシピ集の更新も 1 回で済む。

> Pro は「現時点で非対応（今後のフェーズ）」の一覧に
> 「SELECT 列の一般式としての新しい変数展開」とあることを把握したうえで、
> **構成比という具体的な用途があることの共有**として送っている。
