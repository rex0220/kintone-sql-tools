## 1. 新しい決定（オーナー判断 2026-08-07・変更しない）

**R1-2 は案 a を採用する＝生成系列列を含むウィンドウ `ORDER BY` では全順序警告を抑止する。**

- 対象は**全順序の証明に依存する警告の両方**＝既定フレーム（`RANGE`）の同順警告（B127）と
  `LAG` / `LEAD` の全順序警告。生成列は構築により厳密単調で同順が存在しないため、
  どちらの警告も前提を失う
- **抑止条件は既存の `$id` / レコード番号の証明規則と同じ形に限定する**＝
  ウィンドウが評価する行集合の中で生成列の一意性が保たれている場合だけ。
  **JOIN・`UNION`・サブテーブル展開などで生成列の値が複製され得る経路では従来どおり警告を出す**。
  既存実装の「証明できないときは警告を出す」原則を崩さない。
  具体的な判定条件（どの AST 形なら証明できるか）はコードを読んで列挙すること
- **受入条件に両方向を入れる**＝
  ①生成 CTE を直接読むウィンドウ（レビュー M4 / M5 相当）は **`warnings` が空配列**、
  ②生成系列を JOIN した後の行に対するウィンドウで一意性が証明できない形は
  **従来の警告文がそのまま出る**（期待警告文を明記する）
- これは B140 で閉じた「集約キーからの一意性証明」の再開ではない
  （あちらは推論、こちらは構成による保証）。仕様にもこの区別を明記する

## 2. レビュー指摘の反映（R1-1・R1-3〜R1-6）

[レビュー](ksql_b149_codex_review_1.md)の該当節を正とする。要点:

- **R1-1【Must】** `DECLARE` の例を全て実構文へ＝**`DECLARE @start = 1;` 形**。
  `DEFAULT` キーワードは存在しない（実測: ParseError）。
  **変数名は英字または `_` で始まる名前のみ**（実測: `@開始` は LexError）。
  §2.4・§12.10 X7・§15.8 のほか、**全文を機械的に確認**すること
- **R1-3【Medium】** **`ksql_validate`（静的検証）の契約を表で明記**＝
  リテラル引数で静的に決まるもの（型不一致・step 0・`FROM` 直置き・引数個数・上限超過）は
  validate 段でエラー、変数を含む場合は実行時（変数解決後）判定、の線引き。
  既存の AST-only / schema-aware 二段階（B148 R3 §が前例）に合わせる
- **R1-4【Medium】** **相対日付変数（`TODAY()` 等で定義した `DECLARE` 変数）を
  日付系列の引数として許可する**（実行時に具体日付へ解決された値で判定する）。
  仕様に明記し、`DECLARE @today = TODAY(); ... GENERATE_SERIES(@from, @today) ...` 形の
  受入条件を 1 本入れる。日次 0 埋めの実需は「今日を終端」が最初に書かれる形のため
- **R1-5【Low】** 保存クエリとの関係を明記＝read-only 分類が新文型を **read-only** として
  扱うこと（分類漏れだと v3.48.0 の read-only 複文保存クエリで使えない）。
  §15 の surface 列挙に `ksql_run_saved_query` 経路を追加
- **R1-6【Low】** step の `+` 符号（`+1` / `'+1 day'`）の可否をどちらかに決めて明記
  （どちらでもよいが、整数 step と日付 step で一貫させ、拒否するなら診断文を書く）
