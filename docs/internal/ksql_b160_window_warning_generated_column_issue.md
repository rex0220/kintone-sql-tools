# B160 全順序警告の「無視してよい条件」が 0 埋め（生成列 ORDER BY）を判定できない

- 起票: 2026-08-08（[依頼元の B128 Phase 2 意見 §3](../../../ksql-analytics/docs/internal/kSQLエンジンへの意見-20260808-B128Phase2再開ライン.md)・v3.59.0 返信でも既出・実測裏取り済み）
- ステータス: 📝 **起票（表示/文言・優先 低。ただし B128 2a に着手するなら前提＝優先繰り上げ）**
- 関連: [B140](ksql_b140_cte_groupby_total_order_issue.md)（「無視してよい条件」の導入元・v3.58.0）／
  [B149 §警告抑止](ksql_b149_generate_series_issue.md)（v3.59.0 免除＝生成列の直接読みのみ）

## 1. 実測（2026-08-08・v3.62.0）

0 埋めは必ず JOIN を経るため、v3.59.0 の免除（生成列を**直接**読むウィンドウ）が効かず、
全順序警告が付く:

```sql
WITH s AS (GENERATE_SERIES(...) AS 日付),
     d AS (SELECT s.日付 AS 日付, SUM(t.個数) AS 出庫 FROM s LEFT JOIN APP4228 t ON s.日付 = t.日付 GROUP BY s.日付)
SELECT 日付, SUM(出庫) OVER (ORDER BY 日付) FROM d
→ warnings: 既定フレーム（RANGE）…（B140 の一文つき）
```

## 2. 問題は「警告が出ること」ではなく「一文で判定できないこと」

B140 の免除文言＝**「元の集約のキーをすべて `ORDER BY` に含めているなら無視して構いません」**。

- 上の形（集約 CTE 経由）は `日付` が集約キーなので**文字どおり当てはまる**
- しかし**非集約の 0 埋め**（JOIN 結果へ直接ウィンドウ・`ORDER BY` は生成列）には
  集約が無く、**一文が判定を与えない**。読み手は「当てはまるのか、当てはまらないが
  安全なのか」を文面から読めない（依頼元の指摘・2 度目）

## 3. なぜ B128 2a の前提になるか

2a（移動フレーム）の標準的な書き方＝「0 埋め＋`ROWS n PRECEDING`」は**例外なくこの警告付き**になる。
「無視してよいと言えない警告が、新機能の標準形に必ず付く」状態で出すべきでない（依頼元順位 3）。

## 4. 案

- **案 A（文言）**＝免除文言に「`GENERATE_SERIES` の生成列で並べている場合も、系列は
  厳密単調なので同順は生じません（JOIN で行が増える形を除く）」級の一文を足す——
  ただし **JOIN で同一日付に複数行が出る形では同順が実際に生じる**ので、無条件には書けない。
  正確な条件の言語化が本体
- **案 B（機構）**＝v3.59.0 の構成保証（厳密単調）を「生成列がソートキーで、
  JOIN 後もパーティション内で一意が保証できる形」まで広げて警告自体を抑止——
  B140 で見送った「推論による証明」に近づくため線引きが難しい
- 見立て＝**案 A を 2a 着手時の同梱条件**とし、単独では急がない（依頼元も急ぎなしと明言）
