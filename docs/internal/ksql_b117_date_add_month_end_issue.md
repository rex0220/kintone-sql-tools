# B117 `DATE_ADD` の月・年加算が月末で翌月へ繰り上がる

- 起票: 2026-08-04
- ステータス: ✅ **完了（v3.42.0 でリリース）**（2026-08-04・受入 §4.3 を新規ビルドの MCP で実測確認。codex の停止 0 回）＝仕様は §4
- 出典: [Pro の報告 2026-08-04c](../../../ksql-dashboard-pro/docs/internal/kSQLエンジンへの連絡-20260804c-送付版.md)（K-112）。
  **こちらの実測で完全に一致を確認済み**
- 関連: `src/engine/evalFunc.ts:624-640`（`applyDateAdd`）/ `LAST_DAY()`

## 1. 症状（実測 2026-08-04・こちらで再現）

```
DATE_ADD('2026-01-31',  1, 'MONTH') → 2026-03-03   （期待 2026-02-28）
DATE_ADD('2026-03-31', -1, 'MONTH') → 2026-03-03   ← 上と同じ日になる
DATE_ADD('2026-05-31',  1, 'MONTH') → 2026-07-01   （期待 2026-06-30）
DATE_ADD('2026-02-28',  1, 'MONTH') → 2026-03-28   （正常）
DATE_ADD('2024-02-29',  1, 'YEAR')  → 2025-03-01   （期待 2025-02-28）
DATE_ADD('2026-01-31',  1, 'DAY')   → 2026-02-01   （DAY は影響なし）
```

**壊れている性質**

- **往復しても戻らない**（`1/31 +1ヶ月` と `3/31 -1ヶ月` が同じ `2026-03-03`）
- **順序が直感と食い違う**
- **エラーにならない**＝もっともらしい日付が返るため、**気づく手段がない**

## 2. 原因

`applyDateAdd`（`src/engine/evalFunc.ts:633`）が **JavaScript の `Date` の正規化を
そのまま漏らしている**。

```ts
case "MONTH": dt.setUTCMonth(dt.getUTCMonth() + n); break;
```

`2026-01-31` に 1 か月足すと「2026 年 2 月 31 日」となり、`Date` がこれを
`2026-03-03` へ正規化する。**設計された挙動ではなく副産物。**

## 3. 判断（2026-08-04 オーナー決定＝案 1）

**月末へ丸める（clamp）。**「破壊的変更だから現状維持」は採らない。

1. **いまの出力は擁護できる意味論ではない**（§1 の壊れている性質）
2. **主要な SQL エンジンはすべて丸める**（MySQL `DATE_ADD` / PostgreSQL `+ interval` /
   Oracle `ADD_MONTHS`）。`DATE_ADD` と書く利用者はその意味論を期待する
3. **静かに間違う形**＝締め日が月末の業務がそのまま踏む。
   本プロジェクトは同種の静かな誤りを fail-closed で潰してきた（B97 / B98 / B102）ので、
   ここだけ残すのは一貫しない
4. **壊れるのは「今日ちがう月の日付を返している」ケースだけ**＝それに依存する利用者は
   バグに依存している

## 4. 仕様

### 4.1 変更点

**`YEAR` / `MONTH` の加減算で、結果の日が対象月に存在しない場合は対象月の末日へ丸める。**

```
DATE_ADD('2026-01-31',  1, 'MONTH') → 2026-02-28
DATE_ADD('2026-03-31', -1, 'MONTH') → 2026-02-28
DATE_ADD('2026-05-31',  1, 'MONTH') → 2026-06-30
DATE_ADD('2024-02-29',  1, 'YEAR')  → 2025-02-28
DATE_ADD('2024-01-31', 13, 'MONTH') → 2025-02-28   （うるう年でない年の 2 月）
DATE_ADD('2023-02-28',  1, 'YEAR')  → 2024-02-28   （丸め不要。日を保つ）
```

- **`DAY` は現状のまま**（日数加算に丸めの概念はない）
- **丸めが起きない場合の結果は完全に不変**（例 `2026-02-28 +1ヶ月` → `2026-03-28`）
- 単位の検証（`YEAR` / `MONTH` / `DAY` 以外は `ArgumentError`）は不変
- 入力が日時文字列の場合の扱い・出力形式（`YYYY-MM-DD`）は不変
- **`LAST_DAY()` の挙動は変えない**（丸めの実装に使ってよい）

### 4.2 やらないこと

- `DATE_SUB` の追加（引き続き負数で書く）
- `INTERVAL` 構文の対応
- 押し下げ・`WHERE` での扱いの変更（`DATE_ADD` はクライアント評価のまま）
- 丸めの有無を切り替えるオプション（**同じ SQL の意味が設定で変わる形は採らない**。B107 の判断と同じ）

### 4.3 受入条件

1. §4.1 の 6 例がすべて期待どおり
2. **往復が戻る**＝`DATE_ADD(DATE_ADD(d, 1, 'MONTH'), -1, 'MONTH')` が、
   丸めが起きた場合を除いて元へ戻る（**丸めが起きた場合は戻らないことを明記して固定**。
   `1/31 → 2/28 → 1/28`。これは MySQL も同じで、丸めの性質上避けられない）
3. `DAY` の結果が完全に不変
4. 丸めが起きないケースの結果が完全に不変
5. 既存テスト全 green・snapshot 22 不変・語数予算 exact 不変・declaration snapshot 差分 0

## 5. リリース

**minor＋移行案内**（B86 / B89 / B98 の前例）。移行案内には
**「月末の日付を `DATE_ADD` で送っていた結果が変わる（今までが誤り）」**ことと、
**変わるのは月末だけ**であることを書く。

## 6. 優先度

**高。** 誤った結果を静かに返す種類の欠陥で、**締め日が月末の業務が対象**。
修正は小さい（`applyDateAdd` の 2 分岐）。
