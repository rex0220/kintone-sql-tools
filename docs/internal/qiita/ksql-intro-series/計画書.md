## 1. 方針転換の理由と読者像

v1 は「SQL 未経験の kintone 担当者が AI の書いた SQL を読めるようになる」を狙ったが、
10 本かけて SELECT の基礎を追う構成は**業務で使うまでの距離が遠い**。
kintone に SQL を持ち込んで得をするのは、すでに SQL を書ける人が「kintone には JOIN も GROUP BY も無い」「REST は 500 件ずつ」
「一括更新に dry-run が無い」で困っている場面なので、そこへ直接届ける。

- 読者像: **SQL を書ける開発者**（kintone のカスタマイズ・プラグイン開発・データ連携・運用スクリプトを書く人。DB 経験があり kintone は浅くてもよい）
- 到達点: 手元の業務課題を kSQL で 1 文〜1 バッチに落とし、`EXPLAIN` で何が kintone に飛ぶかを読み、CLI・保存クエリ・Flow・ダッシュボードのどれかで運用に載せられる
- 書かないこと: SELECT / WHERE / GROUP BY の意味。標準 SQL との**差分だけ**を書く
- 主張の接続: AI エージェント記事の「宣言的で検証可能なインターフェース」を、人間の開発者にとっての生産性の話として言い直す
