# B88 0 行の `SELECT *` が列を失い、空の日だけバッチが落ちる（B2 残スコープ）

- 起票: 2026-07-28
- ステータス: ✅ **リリース済み（v3.31.0・2026-07-29）**
- 出典: [B86](ksql_b86_materialized_unknown_column_issue.md) §8.7 の残る限界を正式起票したもの
- 前史: **B2 は v2.11.0 でパイプライン伝播として解決済み**。本課題は当時 §3.6 で意図的に対象外とした**連鎖の起点**にあたる
- 関連: [B2 仕様（v2.11.0）](ksql_empty_select_wildcard_pipeline_spec.md) / [B87 キャッシュ無効化](ksql_b87_field_metadata_cache_staleness_issue.md) / [B86](ksql_b86_materialized_unknown_column_issue.md)

## 0. なぜ今あらためて起票するか

**残スコープが台帳に無く、B86 の付記と v2.11.0 仕様書 §3.6 に散在していた。**
「着手可能な候補」として参照され続けていたが、**台帳を見ても存在しない**状態だった。
B87 とセットで扱う必要があるため、行を立てて追跡可能にする。

## 1. 事象

**0 行なのは正しいが、列名まで消える。**

```sql
CREATE TEMP TABLE #e AS SELECT * FROM APP300;   -- APP300 は 0 件
SELECT * FROM #e
-- → columns=[]   rows=0
```

実害は 2 つの形で出る（いずれも実測）。

```
INSERT INTO APP200 (備考) SELECT * FROM #e
→ SELECT の列数（0）と INSERT のフィールド数（1）が一致しません

SELECT * FROM #f f2 INNER JOIN APP200 b ON f2.レコード番号 = b.レコード番号
→ ArgumentError: column schema is unavailable for materialized JOIN source #f
```

**「差分バッチの空日だけ落ちる」**という、最も気づきにくい壊れ方をする。
データがある日は動き、0 件の日だけ止まる。

## 2. 原因＝起点が 1 箇所

**波及先が多いので広い問題に見えるが、原因は 1 つ。**

| 形 | `columns` | `getFields` 呼び出し |
|---|---|---|
| 明示列で実体化 → `SELECT *` | ✅ `["レコード番号","件名"]` | あり |
| **実アプリ 0 行の bare `SELECT *`** | ❌ `[]` | **なし** |
| 実アプリ 1 行以上の `SELECT *` | ✅ 3 列 | なし |

**0 行の `SELECT * FROM APP` が起点**で、そこで列が失われ temp・CTE・JOIN・`INSERT ... SELECT` へ伝播する。

**v2.11.0 のパイプライン伝播は正しく動いている**（明示列で実体化すれば 0 行でも列が残る）。
**起点に列が無いので運ぶものが無い**だけである。

**注目点＝このケースで `getFields` は一度も呼ばれていない。**
列の情報はアプリ定義として取得可能なのに取りに行っていない。**できないのではなく、していない**（B86 と同じ構図）。

## 3. v2.11.0 で見送った判断と、条件の変化

[v2.11.0 仕様書 §3.6](ksql_empty_select_wildcard_pipeline_spec.md) で案イ（`getFields` で解決）を検討のうえ
**案ア＝対象外**を選んでいる。理由は 2 つ。

1. 実害は temp/CTE 経由で、実アプリ直 `SELECT *` を空ソース DML に使う実需は薄い
2. **0 行のためだけに `getFields` の追加 API を撃つのは費用対効果が低い**

**どちらも B86（v3.30.0）で条件が変わった。**

- **2 について**＝B86 は実行前に物理アプリの `getFields` を取得して列を検証する。
  **列名を書いた SQL では既に取得済み**で、追加コストが出るのは「`WHERE` も無い純粋な `SELECT *`」だけになった
- **1 について**＝B86 が JOIN 利用を error にしたため、従来は黙って進んでいた形が明示的に止まるようになった

## 4. 【実測・2026-07-28】列順は一致する（懸念①の解消）

**最大の懸念は「0 行のときだけ列順が変わり `INSERT ... SELECT` が列を取り違える」ことだった。**
実 kintone で `SELECT *`（1 行以上）の列順と `getFields` の順序を突き合わせた。

| アプリ | `getFields` | `SELECT *` | 保持列の相対順 |
|---|---:|---:|---|
| APP4147 活動履歴 | 21 | 18 | ✅ 完全一致 |
| APP452 交通費申請（テーブル・プロセス有） | 30 | 27 | ✅ 完全一致 |
| APP424 請求書２（テーブル 2 本） | 24 | 16 | ✅ 完全一致 |
| APP423 日付チェック | 31 | 25 | ✅ 完全一致 |
| **APP423（項目を後から追加）** | **33** | **27** | ✅ **完全一致** |

### 4.1 後から追加した項目は末尾に付かない

**「追加＝末尾」という素朴な想定は外れる。**APP423 に 2 項目を追加した結果:

```
fields.json … レコード番号, 更新者, ステータス, ユーザー選択, 期間開始,
              ★B2確認A, カテゴリー, ★B2確認B, B日付, A日付, …
                6番目            8番目
```

**それでも `SELECT *` は同じ位置に出す。**

```
SELECT *    … レコード番号, 更新者, ユーザー選択, 期間開始,
              ★B2確認A, ★B2確認B, B日付, A日付, …
```

**予測不能な途中位置まで両者が一致する**ため、順序は作成順でもレイアウト順でもなく、
`fields.json` と `records.json` が**同じ内部順序を共有している**と考えるのが妥当である。

> 検証は APP423 へ項目を追加・デプロイ → 確認 → 削除・デプロイで**元の定義へ復元済み**。

### 4.2 除外規則も確定

| 種別 | `SELECT *` | 備考 |
|---|---|---|
| `CATEGORY` | 除外 | 4/4 |
| `REFERENCE_TABLE` | 除外 | APP4147 で 2 本とも |
| **サブテーブルの子フィールド** | 除外 | **`SUBTABLE` 本体は列として残る**（JSON 文字列） |
| **`STATUS` / `STATUS_ASSIGNEE`** | **プロセス設定に依存** | 型では決まらない |

**`STATUS` は型では決まらない**ため `status.json` の取得が必要。推測せず実測した。

| アプリ | `status.json` | `SELECT *` の ステータス |
|---|---|---|
| APP452 | `enable: true` | ✅ 含まれる |
| APP4147 | `enable: false` | ❌ 含まれない |
| APP424 | `enable: false` | ❌ 含まれない |

## 5. 残る決めごと＝`$id` / `$revision`

**両者は `getFields` に存在しないため位置を導出できない。**

| アプリ | `$id` | `$revision` の位置 |
|---|---|---|
| APP4147 | 末尾 | 作成者 の直後 |
| APP424 | 末尾 | 作成者 の直後 |
| APP452 | 末尾 | **ドロップダウン の直後** |
| APP423 | 末尾 | ドロップダウン の直後 |

**`$id` は 4/4 で末尾だが、`$revision` は規則が見つからない。**

**実害は位置ではなく列数**である。0 行のときにこの 2 列を欠くと、
`INSERT ... SELECT` の列数チェックが**データのある日と無い日で違う数を見る**。

**推奨＝末尾に 2 列として足す。**位置のずれは `SELECT *` を `INSERT` のソースにする用途では
影響しない（`$id`/`$revision` は書き込めない）。**列数が合うことのほうが重要**である。

## 6. 対象外（本課題でも直さない）

- **JOIN を伴う 0 行 `SELECT *`** — 複数ソースの列合成順が行に依存し、0 行では確定不能
- **単独 `SELECT _p.*`（`PARENT_WILDCARD`）0 行** — 同上
- **混在 `SELECT *, extra` の `*` 分** — 1 行以上でも `*` は `columns` に寄与しない現行仕様に合わせる

## 7. B87 が前提条件

**B87 を直さずに着手してはならない。**

[B87](ksql_b87_field_metadata_cache_staleness_issue.md) により `getFields` は**プロセス生存期間で古いまま**になる。
その状態で 0 行スキーマを作ると:

| | 列の出所 | 追加項目 |
|---|---|---|
| データがある日 | レコード（常に最新） | 含む |
| データが無い日 | **キャッシュ（古い）** | **含まない** |

**本課題が避けようとしている「空の日だけ違う」を、本課題の修正が作り出す。**

## 8. 規模

- 実装（`getFields` ＋ `status.json` から 0 行スキーマを構成・JOIN なし単一ソース限定）: 0.5〜1.0 人日
- テスト（§4.2 の除外規則・§5 の列数・1 行以上との一致を実測で固定）: 0.25〜0.5 人日

**合計 0.75〜1.5 人日。SemVer=minor（0 行時に列が増える方向のみ・1 行以上は不変）。**

**`status.json` の追加取得**が要る分、当初見積もりの上限寄りを見ておく。

## 9. 優先度の根拠

**silent wrong result ではない**（B86 が JOIN 経路を error 化済み・DML は列数エラー）ため緊急性は低い。
一方で **「0 件の日だけ落ちる」は運用で最も気づきにくい**形であり、差分バッチのレシピが該当する。

**懸念だった列順が実測で消えた**ため、着手すれば確実に片付く見通しが立っている。
**B87 と合わせて 1.75〜3.5 人日で、0 行に起因する不具合が完全に消える。**

## 10. 【Pro 回答 2026-07-29】現状は実害なし。ただし**採用直前**だった

**Pro が心当たりを確認した結果**（v3.30.0 で実測）。

| SQL | 0 行時の列 |
|---|---|
| `SELECT * FROM APPn WHERE …` | **columns = 0（列名が消える）** |
| `SELECT $id, 案件名, 売上 FROM APPn WHERE …` | columns = 3 ✅ |
| `SELECT 商談フェーズ, COUNT(*) … GROUP BY …` | columns = 2 ✅ |

**現時点で実害が無い理由**＝テンプレート 12 種・レシピ集・出荷サンプルは**すべて明示列**で
`SELECT *` を使っておらず、現行ペインは `runQuery` の単文のみで 0 行なら「データなし」を表示するだけ。

### ただし `runBatch` 採用後は当たっていた

```sql
CREATE TEMP TABLE #当月 AS SELECT * FROM APPn WHERE 日付 = THIS_MONTH();
SELECT … FROM #当月 t JOIN APPm c ON …;
```

**まさに K-33 で採用を決めた経路**であり、Pro から
**「採用直前に直していただけたことになります」**との評価。

> **「データがある日は動き、0 件の日だけ落ちる」——利用者がこれを踏むと原因にたどり着けません。**（Pro 談）
