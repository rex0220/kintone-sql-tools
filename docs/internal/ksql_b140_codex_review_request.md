## 特に見てほしい点（コードで真偽が決まるもの）

### 1. 【最優先】`GROUP BY` キーで一意と言い切れるか

R1 §2.1。**これが崩れると偽陰性（本当は同順があるのに警告を出さない）を作る。**

- **`GROUP BY k` の結果が `k` について一意である**ことは、現行の実装で保証されているか
  （`grouping.ts` のグループキー構築を確認してほしい）
- **空文字・空セルの扱い**でキーが衝突する形は無いか
  （B128 の実装で `\x00` 区切りの合成キーを使っていたはず）
- **`ROLLUP` / `CUBE` / `GROUPING SETS` を除外する**判断（§2.3）は十分か。
  **除外し忘れると小計行と実データが衝突する**
- **`UNION` を含む CTE を除外する**判断（§2.4）は十分か

### 2. CTE 定義へ到達できるか

R1 §3.1・§5-3。現行 `canProveTotalWindowOrder` は `stmt` しか受けない。

- **警告を出す時点で `WithStatement` の CTE 定義に手が届くか。** 呼び出し元の文脈を確認してほしい
- **届かないなら、どこから渡すのが最小か**
- **CTE の列メタ（`materializedMetaBySelectResult` など）に
  「この列は `GROUP BY` キーだった」を持たせる案**と比べてどちらが素直か

### 3. `context` の意味

R1 §3.2。現行は `context !== "DIRECT"` で即座に false。

- **`DIRECT` / `DERIVED` はそれぞれどの経路で渡されるか**
- **CTE の本体で窓を使う場合**と**CTE を読む SELECT で窓を使う場合**の区別はどうなっているか
- R1 の「`DERIVED` でも証明できるようにする」は**安全か**

### 4. キーの対応づけ

R1 §2.1。「出力列名で取る」としている。

- **`GROUP BY` が SELECT の別名を参照する形**（`AS 年月 ... GROUP BY 年月`）で、
  **下流から見える列名と `GROUP BY` キーの対応**は取れるか
- **`GROUP BY` に物理フィールドを直接書き、SELECT で別名を付ける形**はあるか。あるなら対応は取れるか
- **修飾名**（`m.k`）が絡む形で取り違えないか

### 5. 一時テーブル（§5-1）

`CREATE TEMP TABLE #t AS SELECT ... GROUP BY k` を同じ方法で扱えるか。
**扱えるなら本 Phase に入れるべきか、分けるべきか。**

### 6. 受入条件の穴

R1 §4。**偽陰性を作らないことが最重要。**

- §4.2（警告が残ること）に**足りない形**が無いか
- **`ORDER BY` が `GROUP BY` キーを全部含むかの判定**を、
  受入で**観測可能な形**に落とせているか

### 7. 採らなかった案（R1 §6）

**実行時にタイの有無を見る案**を「同じクエリが日によって警告を出したり出さなかったりする」
という理由で採らなかった。**この判断は妥当か。** 別の理由で採るべき／採らないべきなら指摘してほしい。
