# 評価: B20 正規表現関数を「ユーザー責任」前提で提供する場合の再評価

## 0. 結論の要約

**方針決定（2026-07-18・ユーザー指示）: 案 A（全 4 面解禁・opt-in・暴走とホスト依存はユーザー責任）で進める。** 本書は案 A を採る場合に文書・実装で明示すべき残リスクと、その実測根拠を示す。

- **ReDoS（暴走）は可用性リスク**で「重い JOIN」「maxRecords 引き上げ」と同族＝利用者が引き受け可能。ただし codex レビューで当初の断定を 2 点訂正: ①「他ユーザーへ波及しない」は MCP（同一プロセスの全リクエストを巻き込む）・プラグイン（同タブの未保存編集も失う）では言い過ぎ ②**ホスト依存の結果差は SELECT-based DML の書き戻し経路で保存データへ波及し得る**（暴走はデータ非破壊だが、ホスト差はそうでない）
- 案 A が引き受けるリスクは 2 軸: **暴走（可用性・§2.1 で 31 文字 7 秒の指数カーブ実測）** と **ホスト依存（受理・結果差・§2.2）**。後者は最新ブラウザ前提でも `\p{}` 1 点ではなく Unicode 版差・Node18 の新構文 SyntaxError 差など複数軸が残る
- **R3 の単純化**: 案 A は正規表現を**通常の関数として出荷し、`--allow-regexp` のような opt-in ゲートは設けない**。理由＝kSQL のゲートは「データ破壊（DML）」専用で、**重い読み取り・ローカル計算（未制約 JOIN・大量 maxRecords）はゲートしていない**（§4.1 でコード確認）。ReDoS は後者と同じ可用性リスクのカテゴリなので、正規表現だけにゲートを課すのは設計の一貫性を欠く。要件は「**関数の注意としての警告（文書＋任意の lint）**」に移る（§5）。案 B（CLI/MCP 限定）・案 C（worker 中断化）は §6 に記録として残す

## 1. 前提の変更が変えるもの・変えないもの

| ⛔ の根拠（R4） | ユーザー責任前提での再評価 |
|---|---|
| ① ReDoS を安全部分集合で塞げない（`^a?ⁿaⁿb$` が指数時間・曖昧 NFA は構文検出不能） | **ブロック理由から「告知＋opt-in」へ格下げ可能**。影響は実行者自身のタブ/プロセスに限定され、kintone サーバー・他ユーザー・データへ波及しない（実測: 1 行 14 秒級のパターンでも kintone API は呼ばれない＝ローカル評価） |
| ② kSQL のタイムアウトは同期 RegExp を中断できない（execute.ts の deadline は文間判定・Promise race） | **変わらない事実**。他 RDB（MySQL `regexp_time_limit`・PostgreSQL cancel）は**中断機構を持った上で**提供しており、kSQL がユーザー責任で出す場合は「暴走したら止められない」点で他 RDB より一段リスクが高い。この差は文書で明示する義務がある |
| ③ ホスト依存（native RegExp の解釈がエンジン依存・Safari 旧版の後読み等）で 4 面同一にできない | **ユーザー責任では解消しない別軸の問題**。緩和: フラグ設計は R2 で確定済み（`i`/`m`/`s` のみ・`u` 強制・`v` 拒否）でエンジン版依存の入口は狭い。**CLI/MCP 限定なら Node 単一エンジンとなり問題自体が消える** |
| ④ CLI/MCP 限定は 4 面一貫性を捨てるため既定案にしない | **再解釈の余地あり**。4 面一貫性原則が守るのは「**同じ SQL が静かに違う結果になる**」こと（v2.0.0 の LIKE モード不一致）。**機能の有無差（未対応面では明示エラー）は fail-closed であり別物**。前例=論理アプリ参照 `LAPP_` はプラグイン非対応（明示） |

## 2. リスクの具体化（本評価で実測・2026-07-18・Node v8 13.6）

### 2.1 暴走する事例（catastrophic backtracking）

**パターン `/^(a+)+$/` に「マッチしない入力」（末尾に非 `a`）を与えると、入力長に対して指数関数的に時間が伸びる**。これは「量化グループの中に量化」があると、失敗を確定するために膨大なバックトラックが起きるためで、正規表現の教科書的な暴走例。

| 入力 | 実測時間 |
|---|---:|
| `a`×20 ＋ `!`（21 文字） | 57 ms |
| `a`×24 ＋ `!`（25 文字） | 111 ms |
| `a`×26 ＋ `!`（27 文字） | 445 ms |
| `a`×28 ＋ `!`（29 文字） | **1,787 ms** |
| `a`×30 ＋ `!`（31 文字） | **7,161 ms** |

1 文字増えるごとにほぼ倍増する（26→28 で 4 倍・28→30 で 4 倍）。**わずか 31 文字の入力で 1 行あたり 7 秒**であり、FULL_SCAN で数千行に適用すれば数時間規模で固まる。（測定は Node V8 13.6・単発計測の代表値で、CPU・ウォームアップで絶対値は変動する。指数傾向が要点。codex 再測でも同オーダー〔a×30 で約 9.6 秒〕を確認）

**実務で書きがちな形でも起きる**: `/^(\d+)*$/`（「数字列の繰り返し」のつもり）に `1`×28＋`x` を与えると **1,816 ms**。`(a+)+` のような明らかに危険な形でなくても、**ネストした量化子は普通のバリデーション用途で書いてしまう**。

**面ごとの帰結（B20 仕様 §4 の整理と一致）:**

- **プラグイン**: 同期 RegExp の実行中はタブが完全に固まる（描画・操作不能）。kSQL のタイムアウトは同期実行を中断できない（`execute.ts` の deadline は文間判定・Promise race）。回復手段は**タブの強制終了のみ**。kintone のアプリ画面上で起きるため体験は「kintone が壊れた」に見える
- **CLI**: `Ctrl+C` で即回復
- **MCP**: リクエストがハングし、サーバープロセスの再起動が必要（同一プロセスの他リクエストも巻き込む）

案 A はこの freeze・ハングを**パターンを書いた利用者の責任**として引き受ける。

### 2.2 ホスト依存で結果が異なる事例（最新版前提でリスクは小さい）

`new RegExp` を呼ぶ以上、パターンの解釈は**実行時のホストエンジン任せ**になる（esbuild の target は正規表現の意味を変換しない）。プラグイン＝利用者のブラウザ、CLI/MCP＝Node。

**前提: kintone の動作環境はモダンブラウザの最新版**（[kintone 動作環境](https://jp.cybozu.help/general/ja/admin/list_systemrequirements.html)は Chrome/Edge/Firefox/Safari の最新版を要件とする）。この前提が §2.2 のリスクを大きく縮小する。

かつて面差を生んだ機能は、最新版では**全エンジンが対応済み**で、SyntaxError 系の割れは実質消える（本評価の Node V8 13.6 でも全て OK を実測）:

| 機能 | 最新版での対応 | 旧版で割れていた点（最新版前提では非該当） |
|---|---|---|
| 後読み `(?<=[0-9])円` | Chrome/Firefox/Safari 16.4+/Node 全対応 | Safari 16.4 未満は SyntaxError |
| `v` フラグ（集合演算・ES2024） | 最新版で対応 | 古い環境で SyntaxError |
| 名前付きキャプチャ後方参照 | 全対応 | 旧環境で SyntaxError |

**最新版前提でも面差は `\p{}` だけではない**（codex レビューで訂正）。少なくとも次が残る:

- **`\p{}` の Unicode バージョン差**: `\p{Script=Han}` などの一致集合はエンジン内蔵の Unicode 版に依存。直近追加された文字で静かな結果差が理論上あり得る（SyntaxError でなく結果が変わるため検知しづらい）
- **`u+i` の case folding も Unicode 版依存**: 大文字小文字同一視は `CaseFolding.txt` に依存するため、`\p{}` を使わなくても `\w`・`\b`・`i` フラグ一致がエンジン版で変わり得る
- **新構文の SyntaxError 差（Node 側）**: CLI/MCP 成果物は **Node 18 target**（`build-cli.mjs`/`build-mcp.mjs`）。インライン修飾子 `(?i:…)` 等の 2025 年新構文は最新ブラウザでは通っても **Node 18 の V8 では SyntaxError** になり、`v` フラグ拒否ではパターン本文の新構文を塞げない。**「最新版だから面差なし」はブラウザ間の話で、Node 版との差は残る**

ただし実務影響は限定的: 通常の日本語業務データ（既存の漢字・かな・記号）は版差の影響を受けず、新構文は意図的に書いた場合に限られる。

**訂正した結論**: ホスト依存は「軽微だが `\p{}` 1 点」ではなく「**軽微だが複数軸（Unicode 版差・Node 版の新構文差）**」。案 A の要件は「暴走」1 本でなく「**暴走（可用性）＋受理・結果差（ホスト依存）**」の 2 軸になる。ただしどちらも案 A の方針（ユーザー責任・通常関数として出荷）を覆すものではなく、**要件は文書明示の対象が増える**という形で反映する（§5）。**ホスト差はデータへ波及する**（§2.3・§5）ため注記だけでは不十分な場合がある点に注意。

### 2.3 リスクの波及範囲（codex レビューで精緻化）

**軸ごとに波及が違う。「データ非破壊」を無条件の前提にはできない**（当初の断定を訂正）:

- **ReDoS（暴走）＝可用性のみ**: FULL_SCAN は先に GET でレコードを取得するが、**同期暴走中は後続の JS 処理・書き込み API へ進めない**（GET は呼ばれる点は正確に記す）。単一文経路では正規表現評価が完了しない限りその文の PUT/POST に到達しないため、暴走単体では保存データを壊さない
- **ホスト依存（結果差）＝データへ波及し得る**: B20 仕様 §5.4 の正式経路（正規表現結果を temp へ入れ `UPDATE … FROM` で書き戻す）では、**エンジン差で `REGEXP_REPLACE` の結果や `REGEXP_LIKE` の対象集合が変われば、その異なる結果が PUT される**。confirm 後に `putRecords`/`postRecords` へ進む（execute.ts:3754 付近）。したがってホスト差は「表示だけ」でなく保存データの差になり得る
- **複文バッチ**: 暴走文より前に成功した DML は既に確定済みで、途中状態が残り得る（非アトミック）
- **波及範囲**: プラグイン＝当該タブ（**同じ kintone タブの未保存レコード編集・未保存 SQL も失われる**）。**MCP＝同一プロセス/接続の全リクエストを巻き込む**（stdio 単一イベントループ・mcp/index.ts）。「実行者自身に閉じる」とまでは言えない（未制約 JOIN も同じだが、正規表現でも同じく波及する事実は明記する）

### 2.4 既存 LIKE への影響（範囲を限定して記す）

- B20 実装は **LIKE の RegExp 生成規則を変えない**（機械生成・メタ文字 escape 済み・入れ子量化子を作らない＝evalWhere.ts:415 付近で確認）。この意味で B20 は既存 LIKE を悪化させない
- ただし**「既存 LIKE は暴走しない」という安全根拠にはできない**: `%a%a%…%b` は `^.*a.*a…$` となり、入れ子量化子なしでもワイルドカード数に対して組合せ的にバックトラックする（実測: ワイルドカード 8/10/12 で約 1/13/133ms と急増）。B20 の有無に関わらず LIKE も同じカテゴリのリスクを持つ＝これは「正規表現だけが特別に危険ではない」ことの傍証でもある

## 4. 採用: 案 A（全 4 面解禁・ユーザー責任）— opt-in ゲートは付けない

方針決定どおり案 A で進める。**R3 で方針を単純化: 正規表現は通常の関数として出荷し、`--allow-regexp` のような opt-in ゲートは設けない。** 理由は「既存の設計との一貫性」である。

### 4.1 ReDoS は未制約 JOIN と同じカテゴリ（コードで確認）

kSQL の opt-in ゲートは `--allow-dml`・`--allow-without-where` の 2 つだけで、**いずれもデータ破壊（書き込み）を守るためのもの**である（`cli/index.ts:310,312`）。一方、**重い読み取り・ローカル計算にはゲートが一切ない**:

- **JOIN にゲートなし**: ローカル JOIN は `process.ts` の同期 for ループ。`3000 × 3000` の直積なら 900 万行を同期処理し、プラグインではタブが固まり得る（**ReDoS と同じ同期 CPU 暴走で、やはり中断できない**）
- `maxRecords`（プラグイン既定 3000・CLI/MCP 500・エンジン 10000）は**取得件数を抑えるだけ**で、取得後のローカル計算量の爆発は止めない
- FULL_SCAN・大量 `maxRecords` も同様にゲートなし

> **ReDoS は「未制約 JOIN を書いた」「maxRecords を上げすぎた」と同じ可用性リスクのカテゴリである。** kSQL はこのカテゴリをゲートせず、書き込み（データ破壊）だけをゲートしてきた。正規表現だけに opt-in を課すのは、この確立した設計方針と矛盾する（＝書き込みでない操作に初めてゲートを付ける前例になる）。

### 4.2 したがって正規表現は「通常の関数」として出す

1. **暴走はデータを壊さない・ホスト差は要注意**（§2.3）。ReDoS は可用性リスクで未制約 JOIN と同じ扱いが一貫している。ただしホスト依存の結果差は DML 書き戻しで保存データに影響し得るため、そこは §5 で書き戻し時の注意を課す
2. **ゲートの代わりに文書で警告する** — 重い JOIN や大量取得をリファレンスの「適用限界」で注意喚起しているのと同じ方式。正規表現には「ReDoS の可能性・中断不能・プラグインでは freeze」を関数の注意として明記する（§5）
3. **4 面すべてで提供**する（B19 の他関数と同じ）。実需 22 パターン（書式検証・`[^0-9]` 除去等）を CLI/MCP/プラグインで使える
4. 旧「安全部分集合」判定器は**保証でなく警告（lint）として転用**: 危険形（ネスト量化子等）を検出したら「実行時間が爆発する可能性があります」と警告しつつ実行は許す。プロトタイプは 22 パターン全 pass 済みで誤警告は少ない見込み。**これは opt-in の代替ではなく、JOIN にはない「書いた時点で気づける」おまけ**

### 4.3 唯一残す慎重さ

正規表現に固有なのは「31 文字の入力で 7 秒」という**入力長あたりの深刻度**（JOIN は行数に対して多項式、ReDoS は入力長に対して指数）。ただしこれは**程度の差**であり、kSQL が他の同期爆発（大直積 JOIN）をゲートしない以上、正規表現だけをゲートする根拠にはならない。**深刻度の差は「文書での警告の強さ」で扱い、ゲートでは扱わない。**

## 5. 案 A 採用時の再開・出荷条件（B20 仕様 §12 の差し替え案）

**警告（ゲートは設けない・§4.1）**

- [ ] **opt-in ゲートを付けない**: 未制約 JOIN・大量 maxRecords と同じ扱いとし、正規表現は通常の関数として既定で使える。DML の `--allow-dml` はデータ破壊専用であり、可用性リスクへは流用しない
- [ ] **暴走の明示（§2.1）**: リファレンスの関数説明と「適用限界」に「正規表現は ReDoS の可能性があり、暴走すると kSQL では中断できない。**プラグインではタブが固まり強制終了が必要**・CLI は Ctrl+C・MCP はプロセス再起動」を記載（重い JOIN の注意喚起と同じ場所・同じ方式）
- [ ] **ホスト依存の明示（§2.2・複数軸）**: 「正規表現の結果は実行環境（ブラウザ／Node）とその版に依存し得る（`\p{}`・`u+i` の case folding の Unicode 版差・Node18 の新構文 SyntaxError 差）。同じ SQL でも面で結果が変わる場合がある」を記載
- [ ] **ホスト差 × DML 書き戻しの注意（§2.3・codex P1-2）**: 正規表現結果を `UPDATE … FROM` 等で書き戻す場合、ホスト差が保存データの差になり得る。書き戻し経路のリファレンスに「環境依存の結果を書き戻す点」を明記する（暴走のデータ非破壊と分けて書く）
- [ ] **MCP・プラグインの波及の明示（§2.3・codex P1-1/P2-2）**: MCP は同一プロセスの全リクエストを巻き込むこと、プラグインの強制終了は同タブの未保存レコード編集・未保存 SQL を失うことを注意喚起（未制約 JOIN と同じ波及だが正規表現でも起きる事実を明記）
- [ ] **警告 lint（任意・v1 に含めるかは実装判断）**: 危険パターン判定（ベストエフォート・保証しないことを文言に含む）。ゲートの代替ではなく「書いた時点で気づける」補助。出荷判定に安全性の証明を要求しない（＝旧⛔基準の破棄を明文化）。**lint 自体がパターン長に対し線形または明示上限内で、対象 RegExp を実行しないこと**（codex P3-2・lint が新たな DoS 面にならない）

**機能仕様（R2/R4 確定分の踏襲）**

- [ ] 命名・文字単位・フラグ: `REGEXP_LIKE`/`REGEXP_REPLACE`/`REGEXP_SUBSTR`・`i`/`m`/`s` のみ・`u` 強制・`v` 拒否・予約語 3 語・SemVer=minor
- [ ] EXPLAIN と実行が同じ可否を返す（各面で一致）
