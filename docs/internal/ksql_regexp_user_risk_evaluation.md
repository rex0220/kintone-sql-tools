# 評価: B20 正規表現関数を「ユーザー責任」前提で提供する場合の再評価

- ステータス: **評価 R2・案 A 方針決定（2026-07-18・ユーザー指示）・codex レビュー中。B20 仕様 §12 の差し替えは codex 承認後。**

## 0. 結論の要約

**方針決定（2026-07-18・ユーザー指示）: 案 A（全 4 面解禁・opt-in・暴走とホスト依存はユーザー責任）で進める。** 本書は案 A を採る場合に文書・実装で明示すべき残リスクと、その実測根拠を示す。

- ReDoS は**可用性のリスクであり、データの正しさを壊さない** — 「重い JOIN」「maxRecords 引き上げ」と同族の、利用者が引き受け可能な性質。ユーザー責任への基準差し替えは成立する
- 案 A が引き受けるリスクは実質 1 つ（暴走）に絞られる:
  - **暴走（ReDoS）＝主リスク**: プラグインでは中断不能でタブごと freeze する。CLI は Ctrl+C・MCP はプロセス再起動で回復。§2.1 で入力 31 文字が 7.2 秒に達する指数カーブを実測
  - **ホスト依存＝軽微**: **kintone 動作環境はモダンブラウザ最新版が前提**のため、後読み・`v` フラグ等の SyntaxError 系の面差は消える。残るのは `\p{}` の Unicode バージョン差（直近追加文字の一致差）のみで、通常の業務データには影響しない注意事項レベル（§2.2）
- 案 A はこれらを**利用者の責任**として引き受けるため、要件は「防ぐ」ではなく「**明示同意（opt-in）と暴走リスクの警告**」に移る（§5）。案 B（CLI/MCP 限定）・案 C（worker 中断化）は §6 に記録として残す

## 1. 前提の変更が変えるもの・変えないもの

| ⛔ の根拠（R4） | ユーザー責任前提での再評価 |
|---|---|
| ① ReDoS を安全部分集合で塞げない（`^a?ⁿaⁿb$` が指数時間・曖昧 NFA は構文検出不能） | **ブロック理由から「告知＋opt-in」へ格下げ可能**。影響は実行者自身のタブ/プロセスに限定され、kintone サーバー・他ユーザー・データへ波及しない（実測: 1 行 14 秒級のパターンでも kintone API は呼ばれない＝ローカル評価） |
| ② kSQL のタイムアウトは同期 RegExp を中断できない（execute.ts の deadline は文間判定・Promise race） | **変わらない事実**。他 RDB（MySQL `regexp_time_limit`・PostgreSQL cancel）は**中断機構を持った上で**提供しており、kSQL がユーザー責任で出す場合は「暴走したら止められない」点で他 RDB より一段リスクが高い。この差は文書で明示する義務がある |
| ③ ホスト依存（native RegExp の解釈がエンジン依存・Safari 旧版の後読み等）で 4 面同一にできない | **ユーザー責任では解消しない別軸の問題**。緩和: フラグ設計は R2 で確定済み（`i`/`m`/`s` のみ・`u` 強制・`v` 拒否）でエンジン版依存の入口は狭い。**CLI/MCP 限定なら Node 単一エンジンとなり問題自体が消える** |
| ④ CLI/MCP 限定は 4 面一貫性を捨てるため既定案にしない | **再解釈の余地あり**。4 面一貫性原則が守るのは「**同じ SQL が静かに違う結果になる**」こと（v2.0.0 の LIKE モード不一致）。**機能の有無差（未対応面では明示エラー）は fail-closed であり別物**。前例=論理アプリ参照 `LAPP_` はプラグイン非対応（明示） |

## 2. リスクの具体化（本評価で実測・2026-07-18・Node v8 13.6）

### 2.1 暴走する事例（catastrophic backtracking）

**パターン `/^(a+)+$/` に「マッチしない入力」（末尾に非 `a`）を与えると、入力長に対して指数関数的に時間が伸びる**。これは「量化グループの中に量化」があると、失敗を確定するために膨大なバックトラックが起きるためで、正規表現の教科書的な暴走例。

| 入力 | 実測時間 |
|---|---:|
| `a`×20 ＋ `!`（21 文字） | 57 ms |
| `a`×24 ＋ `!`（25 文字） | 111 ms |
| `a`×26 ＋ `!`（27 文字） | 445 ms |
| `a`×28 ＋ `!`（29 文字） | **1,787 ms** |
| `a`×30 ＋ `!`（31 文字） | **7,161 ms** |

1 文字増えるごとにほぼ倍増する（26→28 で 4 倍・28→30 で 4 倍）。**わずか 31 文字の入力で 1 行あたり 7 秒**であり、FULL_SCAN で数千行に適用すれば数時間規模で固まる。

**実務で書きがちな形でも起きる**: `/^(\d+)*$/`（「数字列の繰り返し」のつもり）に `1`×28＋`x` を与えると **1,816 ms**。`(a+)+` のような明らかに危険な形でなくても、**ネストした量化子は普通のバリデーション用途で書いてしまう**。

**面ごとの帰結（B20 仕様 §4 の整理と一致）:**

- **プラグイン**: 同期 RegExp の実行中はタブが完全に固まる（描画・操作不能）。kSQL のタイムアウトは同期実行を中断できない（`execute.ts` の deadline は文間判定・Promise race）。回復手段は**タブの強制終了のみ**。kintone のアプリ画面上で起きるため体験は「kintone が壊れた」に見える
- **CLI**: `Ctrl+C` で即回復
- **MCP**: リクエストがハングし、サーバープロセスの再起動が必要（同一プロセスの他リクエストも巻き込む）

案 A はこの freeze・ハングを**パターンを書いた利用者の責任**として引き受ける。

### 2.2 ホスト依存で結果が異なる事例（最新版前提でリスクは小さい）

`new RegExp` を呼ぶ以上、パターンの解釈は**実行時のホストエンジン任せ**になる（esbuild の target は正規表現の意味を変換しない）。プラグイン＝利用者のブラウザ、CLI/MCP＝Node。

**前提: kintone の動作環境はモダンブラウザの最新版**（[kintone 動作環境](https://jp.cybozu.help/general/ja/admin/list_systemrequirements.html)は Chrome/Edge/Firefox/Safari の最新版を要件とする）。この前提が §2.2 のリスクを大きく縮小する。

かつて面差を生んだ機能は、最新版では**全エンジンが対応済み**で、SyntaxError 系の割れは実質消える（本評価の Node V8 13.6 でも全て OK を実測）:

| 機能 | 最新版での対応 | 旧版で割れていた点（最新版前提では非該当） |
|---|---|---|
| 後読み `(?<=[0-9])円` | Chrome/Firefox/Safari 16.4+/Node 全対応 | Safari 16.4 未満は SyntaxError |
| `v` フラグ（集合演算・ES2024） | 最新版で対応 | 古い環境で SyntaxError |
| 名前付きキャプチャ後方参照 | 全対応 | 旧環境で SyntaxError |

**最新版前提でも残る唯一の面差は `\p{}` の Unicode バージョン差**である。`\p{Script=Han}` などの一致集合は**エンジンが内蔵する Unicode の版**に依存し、各ブラウザ・Node のリリース時期で版が僅かに異なる。**ごく最近 Unicode に追加された文字**が、一方のエンジンでは一致し他方では一致しない、という静かな結果差が理論上あり得る（SyntaxError でなく結果が変わるため検知しづらい）。

ただし実務影響は小さい:

- 対象は「直近数年で Unicode に追加された文字」に限られ、通常の日本語業務データ（既存の漢字・かな・記号）はどのエンジンの版でも一致集合が同じ
- 案 A のフラグ設計（R2 確定）で `v` 拒否・`u` 強制のため、`\p{}` を使うのは意図的に書いた場合に限られる

**結論**: 最新版前提のもとでは、ホスト依存は「案 A の出荷を左右するリスク」ではなく「`\p{}` を使う場合の軽微な注意事項」に格下げできる。リファレンスに「`\p{}` を含むパターンの一致は実行環境の Unicode 版に依存する場合がある」と 1 行注記すれば足りる（§5）。**主リスクは §2.1 の暴走（可用性）の方**であり、そちらが案 A の要件の中心になる。

### 2.3 データは壊れない・既存機能は無傷

- ReDoS・ホスト依存とも**書き込み前のローカル評価**で起きる。暴走中も kintone API は呼ばれず、サーバー・他ユーザー・保存済みデータへ波及しない（可用性のみのリスク）
- 機械生成の LIKE 用 RegExp は全 escape 済みで、入れ子量化子が構文的に作れない（既存機能への影響なし）

## 3. 案の比較

| 案 | 内容 | 残リスク | 評価 |
|---|---|---|---|
| **A: 全 4 面解禁＋opt-in** | `--allow-regexp` / profile / MCP ツール入力 / プラグイン⚙オプション。危険パターンのベストエフォート警告（保証しない） | プラグインのタブ freeze・ホスト依存の結果差 | ユーザー責任の趣旨には最も忠実だが、freeze の回復コストと「kintone が固まった」という見え方は opt-in の同意で相殺しきれない |
| **B: CLI/MCP 限定＋opt-in（推奨・v1）** | 上記ゲート＋プラグインは明示 ParseError（「プラグインでは利用できません」）。警告 lint 同梱 | MCP プロセスのハング（再起動で回復・文書化） | freeze を根絶しつつ、実需の主戦場（cli-kintone CSV 連携・品質チェック・バッチ）は CLI/MCP でカバー。Node 単一エンジンで**ホスト依存問題も同時に消える**。`LAPP_` の前例に整合 |
| **C: worker 実行で中断可能化** | Node `worker_threads` / プラグイン Web Worker ＋ `terminate()` で timeout 化 → freeze 自体を解消して全面解禁 | 実装コスト大。プラグインの Blob worker が kintone 環境（CSP）で動くかは**未検証**。行評価のバッチ転送設計が必要 | **v2 の有力路線**。案 B で出して需要と運用実績を見てから、worker 化でプラグイン解禁を判断するのが段階的 |

## 4. 採用: 案 A（全 4 面解禁・opt-in・ユーザー責任）

方針決定どおり案 A で進める。案 A を成立させる根拠と、それゆえ**必須になる明示義務**は次のとおり。

1. **データは壊れない**（§2.3）。暴走・ホスト依存はいずれも可用性・結果差のリスクで、書き込み済みデータや他ユーザーへ波及しない。利用者が引き受け可能
2. **4 面すべてで提供**する。実需（B20 仕様 §1 の 22 パターン）は CLI/MCP のバッチ・連携が主だが、プラグイン画面での書式チェック等も想定し得るため面を絞らない
3. 案 A で引き受ける代わりに、**「防げない 2 リスクを利用者が知った上で opt-in する」構造**を要件にする。すなわち §5 の opt-in ゲート・freeze 明示・ホスト依存明示が**必須**（案 B なら面の限定で消せたリスクを、案 A は文書と同意で引き受けるため、これらは省略不可）
4. 旧「安全部分集合」判定器は**保証でなく警告（lint）として転用**: 危険形（ネスト量化子等）を検出したら「このパターンは実行時間が爆発する可能性があります」と警告しつつ実行は許す。プロトタイプは 22 パターン全 pass 済みで誤警告は少ない見込み

## 5. 案 A 採用時の再開・出荷条件（B20 仕様 §12 の差し替え案）

**opt-in と警告（案 A の必須要件）**

- [ ] **opt-in ゲート**: 既定 off。CLI `--allow-regexp` / env / profile / MCP ツール入力 / **プラグイン⚙オプション**。`--allow-dml` と同型の明示同意。off 時は ParseError で案内し、有効化の副作用（下記 2 リスク）を文言で示す
- [ ] **暴走の明示（§2.1）**: リファレンスとゲート有効化時の案内に「暴走した正規表現は kSQL では中断できない。**プラグインではタブが固まり強制終了が必要**・CLI は Ctrl+C・MCP はプロセス再起動」を記載
- [ ] **ホスト依存の注記（§2.2・軽微）**: kintone 動作環境（最新版）前提では SyntaxError 系の面差は無いが、「`\p{}` を含むパターンの一致は実行環境の Unicode 版に依存する場合がある」を 1 行注記（主リスクは暴走であり、この項目は暴走明示ほど重くない）
- [ ] **警告 lint**: 危険パターン判定（ベストエフォート・保証しないことを文言に含む）。警告は補助で、出荷判定に安全性の証明を要求しない（＝旧⛔基準の破棄を明文化）

**機能仕様（R2/R4 確定分の踏襲）**

- [ ] 命名・文字単位・フラグ: `REGEXP_LIKE`/`REGEXP_REPLACE`/`REGEXP_SUBSTR`・`i`/`m`/`s` のみ・`u` 強制・`v` 拒否・予約語 3 語・SemVer=minor
- [ ] EXPLAIN と実行が同じ可否を返す（ゲート off・各面で一致）
- [ ] パターンがリテラル・式・フィールドのいずれでも同じ opt-in 制限を受ける（B19 `DATE_ADD` と同型で**実行時**評価）
- [ ] 戻り意味型・空文字・置換参照・DML/FULL_SCAN 契約を R4 の型規則と整合させる

**検証**

- [ ] 実需 22 パターンの適合性 corpus が **CLI / MCP / Chromium / Firefox で一致**（案 A は 4 面提供のため 4 面確認が要る。CI で回せないブラウザ面は実機 smoke）
- [ ] 危険パターンの警告発火テスト（§2.1 の `(a+)+`・`(\d+)*` 系）
- [ ] MCP のハング挙動・プラグインの freeze→強制終了を各 1 回実機で観測し復旧手順を文書化（安全な小規模で挙動確認・長時間ハングは再現しない）
- [ ] ホスト依存の実例を Chromium/Firefox で 1 つ観測（後読みか `\p{}` の結果差・注意喚起の裏取り）

## 6. 記録（不採用案）

- **案 B（CLI/MCP 限定）**: プラグイン freeze とホスト依存を面の限定で構造的に消せたが、方針決定で 4 面提供（案 A）を採ったため不採用。プラグインでの利用要望が将来 freeze 問題で撤回検討になった場合の後退先として記録に残す
- **案 C（worker 実行で中断可能化）**: Node `worker_threads` / プラグイン Web Worker ＋ `terminate()` で freeze 自体を解消する路線。実装コスト大・プラグインの Blob worker が kintone CSP 下で動くか未検証。**案 A 出荷後、freeze の運用被害が実際に問題化したら v2 として起票**する
