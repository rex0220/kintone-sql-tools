# 評価: B20 正規表現関数を「ユーザー責任」前提で提供する場合の再評価

- 作成日: 2026-07-18
- 位置づけ: [B20 仕様 R4](ksql_regexp_function_spec.md) は「kSQL が ReDoS を防げないなら出荷しない」という**安全保証基準**で ⛔ とした。本書は「**正規表現の暴走はパターンを書いた利用者の責任**」へ基準を差し替えた場合に何が変わるかを評価する。
- ステータス: **評価 R1・codex レビュー前。B20 の ⛔ 判定は本評価の承認まで変更しない。**
- 分担: Claude=仕様/観点、Codex=実装/テスト
- 台帳: [ksql_issue_tracker.md](../ksql_issue_tracker.md)

## 0. 結論の要約

**ユーザー責任前提なら B20 は出荷可能になる。ただし全面解禁（案 A）ではなく、v1 は CLI/MCP 限定＋opt-in ゲート（案 B）を推奨する。**

- ReDoS は**可用性のリスクであり、データの正しさを壊さない** — 「重い JOIN」「maxRecords 引き上げ」と同族の、利用者が引き受け可能な性質。ユーザー責任への基準差し替えは成立する
- ただし**プラグインだけは質が違う**: 同期 RegExp は中断不能で、暴走すると kintone のページごとブラウザタブが固まり、回復手段がタブ強制終了しかない。CLI（Ctrl+C）/ MCP（プロセス再起動）と回復コストが桁違い
- **ホスト依存（4 面で結果が割れ得る）はユーザー責任では解消しない**。CLI/MCP 限定にすればこの問題も同時に消える（Node のみ＝単一エンジン）

## 1. 前提の変更が変えるもの・変えないもの

| ⛔ の根拠（R4） | ユーザー責任前提での再評価 |
|---|---|
| ① ReDoS を安全部分集合で塞げない（`^a?ⁿaⁿb$` が指数時間・曖昧 NFA は構文検出不能） | **ブロック理由から「告知＋opt-in」へ格下げ可能**。影響は実行者自身のタブ/プロセスに限定され、kintone サーバー・他ユーザー・データへ波及しない（実測: 1 行 14 秒級のパターンでも kintone API は呼ばれない＝ローカル評価） |
| ② kSQL のタイムアウトは同期 RegExp を中断できない（execute.ts の deadline は文間判定・Promise race） | **変わらない事実**。他 RDB（MySQL `regexp_time_limit`・PostgreSQL cancel）は**中断機構を持った上で**提供しており、kSQL がユーザー責任で出す場合は「暴走したら止められない」点で他 RDB より一段リスクが高い。この差は文書で明示する義務がある |
| ③ ホスト依存（native RegExp の解釈がエンジン依存・Safari 旧版の後読み等）で 4 面同一にできない | **ユーザー責任では解消しない別軸の問題**。緩和: フラグ設計は R2 で確定済み（`i`/`m`/`s` のみ・`u` 強制・`v` 拒否）でエンジン版依存の入口は狭い。**CLI/MCP 限定なら Node 単一エンジンとなり問題自体が消える** |
| ④ CLI/MCP 限定は 4 面一貫性を捨てるため既定案にしない | **再解釈の余地あり**。4 面一貫性原則が守るのは「**同じ SQL が静かに違う結果になる**」こと（v2.0.0 の LIKE モード不一致）。**機能の有無差（未対応面では明示エラー）は fail-closed であり別物**。前例=論理アプリ参照 `LAPP_` はプラグイン非対応（明示） |

## 2. リスクの具体化（実測ベース・B20 仕様 §4 より）

- 危険パターン `(a+)+` 型: 入力 29 文字で **1 行 14 秒**・1 文字ごとに倍。FULL_SCAN 1 万行なら約 39 時間
- **プラグイン**: 実行中はタブが完全に固まる（描画・操作不能）。回復＝タブ強制終了。kintone のアプリ画面上で起きるため体験としては「kintone が壊れた」に見える
- **CLI**: Ctrl+C で即回復。**MCP**: リクエストがハングしサーバープロセスの再起動が必要（他リクエストも巻き込む）
- 機械生成の LIKE 用 RegExp は全 escape 済みで安全（既存機能への影響なし）

## 3. 案の比較

| 案 | 内容 | 残リスク | 評価 |
|---|---|---|---|
| **A: 全 4 面解禁＋opt-in** | `--allow-regexp` / profile / MCP ツール入力 / プラグイン⚙オプション。危険パターンのベストエフォート警告（保証しない） | プラグインのタブ freeze・ホスト依存の結果差 | ユーザー責任の趣旨には最も忠実だが、freeze の回復コストと「kintone が固まった」という見え方は opt-in の同意で相殺しきれない |
| **B: CLI/MCP 限定＋opt-in（推奨・v1）** | 上記ゲート＋プラグインは明示 ParseError（「プラグインでは利用できません」）。警告 lint 同梱 | MCP プロセスのハング（再起動で回復・文書化） | freeze を根絶しつつ、実需の主戦場（cli-kintone CSV 連携・品質チェック・バッチ）は CLI/MCP でカバー。Node 単一エンジンで**ホスト依存問題も同時に消える**。`LAPP_` の前例に整合 |
| **C: worker 実行で中断可能化** | Node `worker_threads` / プラグイン Web Worker ＋ `terminate()` で timeout 化 → freeze 自体を解消して全面解禁 | 実装コスト大。プラグインの Blob worker が kintone 環境（CSP）で動くかは**未検証**。行評価のバッチ転送設計が必要 | **v2 の有力路線**。案 B で出して需要と運用実績を見てから、worker 化でプラグイン解禁を判断するのが段階的 |

## 4. 推奨: 案 B（CLI/MCP 限定・opt-in・v1）

1. **最悪の害（ブラウザ freeze）を構造的に排除**した上でユーザー責任を成立させる。「止められる面」（Ctrl+C・プロセス再起動）だけに限定すれば、暴走は「重いクエリを書いた」と同じ運用問題に収まる
2. 実需（B20 仕様 §1 の 22 パターン: 書式検証・`[^0-9]` 除去・範囲検出・空白圧縮）は**すべて CLI/MCP のバッチ・連携文脈**で発生する。プラグイン画面で正規表現が要る実需は薄い
3. Node 単一エンジンになるため、**⛔ 根拠③（ホスト依存）が対象外になる** — ユーザー責任で消せない唯一の技術問題を、面の限定が消す
4. 旧「安全部分集合」判定器は**保証でなく警告（lint）として転用**する: 危険形を検出したら「このパターンは実行時間が爆発する可能性があります」と警告しつつ実行は許す（プロトタイプは 22 パターン全 pass 済みで誤警告は少ない見込み）

## 5. 案 B 採用時の再開・出荷条件（B20 仕様 §12 の差し替え案）

- [ ] **opt-in ゲート**: 既定 off。CLI `--allow-regexp` / env / profile / MCP ツール入力。`--allow-dml` と同型の明示同意。off 時は ParseError で案内
- [ ] **プラグインは明示拒否**（parse または planning・黙って無視しない・文言で CLI/MCP を案内）
- [ ] **警告 lint**: 危険パターン判定（ベストエフォート・保証しないことを文言に含む）。警告はあくまで補助で、出荷判定に安全性の証明を要求しない（＝旧基準の破棄を明文化）
- [ ] **中断不能の明示**: リファレンスに「暴走した正規表現は kSQL では中断できない。CLI は Ctrl+C・MCP はプロセス再起動」を記載
- [ ] フラグ・命名・文字単位は R2/R4 確定分を踏襲（`REGEXP_LIKE`/`REGEXP_REPLACE`/`REGEXP_SUBSTR`・`i`/`m`/`s`・`u` 強制・予約語 3 語・SemVer=minor）
- [ ] EXPLAIN と実行が同じ可否を返す（ゲート off・プラグイン面でも一致）
- [ ] 実需 22 パターンの適合性 corpus（CLI/MCP で一致）・危険パターンの警告発火テスト
- [ ] MCP のハング挙動を実機で 1 回観測し、復旧手順を文書化（安全な小規模パターンで挙動確認・実際の長時間ハングは再現しない）

## 6. 判断を仰ぐ点

1. 案 B（CLI/MCP 限定）で進めてよいか。それとも案 A（プラグイン含む全面・freeze はユーザー責任）か
2. 警告 lint を v1 に含めるか（含めない最小構成も可能。その場合は文書警告のみ）
3. プラグイン解禁（案 C の worker 化）を将来課題として台帳に分離起票するか
