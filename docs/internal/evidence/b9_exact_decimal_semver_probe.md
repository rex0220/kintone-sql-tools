# B9 実機記録: SemVer 判定（v3.2.0 vs B9・major 確定）

- 実施日時: 2026-07-18
- 実施者: Claude（実機・dev・APP4221）
- 目的: 実装計画 §8 の SemVer 判定。公開 v3.2.0 と B9(working tree) を同じ保存データで比較

## 方法

- APP4221 は numberPrecision=digits16/decimalPlaces4（整数12桁＋小数4桁＝16有効桁）。整数16桁は保存不可のため、**16有効桁の範囲で binary64 が衝突するペア**を使用
- 投入値: `999999999999.9992`（$id 91）/ `999999999999.9991`（$id 92）。`Number('…9991')===Number('…9992')` が **true**（binary64 衝突）だが kintone は文字列で区別して保存（読み返しで .9992/.9991 を確認）
- v3.2.0 は release worktree（tag v3.2.0）から `build:cli`・B9 は working tree ビルド。同一 config・同一 SQL で比較

## 結果（決定的差）

| 経路 | SQL | v3.2.0 | B9 |
|---|---|---|---|
| WHERE `= .9991` | `… WHERE 金額 = 999999999999.9991` | $id 92 | $id 92（この等値は偶然一致） |
| **MIN / MAX** | `SELECT MIN(金額), MAX(金額)` | min=**.9992**・max=.9992（**MIN が誤り＝2値を同値扱い**） | min=.9991・max=.9992（正しい） |
| **ORDER BY 金額 ASC, $id ASC** | | `91(.9992), 92(.9991)`（**逆順**） | `92(.9991), 91(.9992)`（正しい昇順） |

v3.2.0 は 2 値を binary64 で同値扱いするため、MIN が数学的に誤った代表値を返し、ORDER BY も区別できず $id 順（.9992 が先）になる。B9 は厳密比較で正しい結果を返す。

## 判定: **major**

公開済み v3.2.0 と同じ SQL・同じ保存データで **MIN/MAX 値と ORDER BY の非同値グループ順が変わる**ことを実測（計画 §8.3 の major 条件）。したがって:

- **B9 は v3.3.0（minor バンドル）では出せない**
- B9 を単独 major（v4.0.0）とし、B29・B20 を別 minor に切り直す版構成の再計画が必要
- テストレコードは削除済み（`DELETE … WHERE タイトル='B9SV'`）・v3.2.0 worktree 撤去済み
