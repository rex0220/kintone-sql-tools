# 本文（送付版）

## 【確認】依頼③（MCP のプラグイン互換モード）を再評価しました

**保留の条件にしていた B89 が出荷されたので、測り直しました。**

**結果として、当初ご提案いただいた形（環境変数でのモード切り替え）とは
別の案をお勧めしたいと考えています。**判断材料を先にお出しします。

---

## 1. 受理集合の差は **5 形だけ**でした

**MCP と engine ライブラリの両方のガードに、同じ SQL を通して測りました。**

| 形 | MCP `ksql_query` | engine lib `runBatch` |
|---|---|---|
| `SELECT` / `WITH` / `UNION` / `SHOW APPS` / `DESCRIBE` | ✅ | ✅ |
| `CREATE TEMP TABLE` / `SET` / `ASSERT` / 先頭 `VALIDATE` | ✅ | ✅ |
| `EXPLAIN SELECT` | ✅ | ✅ |
| **`EXPLAIN UPDATE` / `DELETE` / `INSERT` / `UPSERT`** | ✅ | ❌ |
| **`UPDATE` / `INSERT` / `UPSERT ... VALIDATE ONLY`** | ✅ | ❌ |
| **`IMPORT`** | ✅ | ❌ |
| `UPDATE` / `DELETE`（書き込み） | ❌ | ❌ |

**差は 5 形で、すべて「DML 型だが書き込まない検証系」です。**
**書き込む DML は両方が拒否します。**

---

## 2. この差は**意図的**でした（偶然のずれではありません）

測ってみて分かったのですが、**この 5 形は「たまたまずれた」のではなく、
2 つの面の性格の違いがそのまま出たもの**でした。

| | 性格 | 判定 |
|---|---|---|
| **engine ライブラリ** | **read-only が契約** | **文の型**で切る（書き込むかどうかではない） |
| **MCP** | **対話的な道具** | **DML を実行前に検証する**ことが中核の使い方 |

**B89 で `EXPLAIN <DML>` を拒否するようにしたのは、まさにこの線を引き直したから**です。

MCP のほうは、server instructions が
**「DML の前に `ksql_query` の `VALIDATE ONLY` と `ksql_app_metadata` を使い、それから `ksql_mutate`」**
という手順を案内しています。**`VALIDATE ONLY` は MCP の中核機能**です。

**したがって「MCP を engine ライブラリに合わせる」は、
MCP の意図的な機能を取り上げることになります。**
**互換モードが「純加法」にならない**、というのが再評価で分かった一番大きな点です。

### 2.1 B89 は差を縮めませんでした（こちらの見込みも外れていました）

起票時、**「B89 が実現すると本件の価値も上がる」**と伺い、
**こちらもそう書いて保留していました。**

**実際には B89 は `runBatch` を厳しくした**（`EXPLAIN <DML>` を拒否）ので、
**差は縮まらず 1 形増えました。**

---

## 3. ご提案 — モードではなく `ksql_validate` の応答に出す

**そちらが環境変数を望まれた理由は「引数だと AI が渡し忘れる」でした。**
**応答フィールドなら、渡し忘れが原理的に起きません。**

`ksql_validate` は**既に同じ形のフラグを返しています。**

```json
{
  "canRunWithQueryTool": true,
  "requiresMutationTool": false
}
```

**ここへ 1 つ足す形です**（名前は仮）。

```json
{
  "canRunWithEngineLibrary": false,
  "engineLibraryBlockedBy": ["VALIDATE_ONLY_DML"]
}
```

### 3.1 モードより優れていると考える点

| | 環境変数モード | **`ksql_validate` のフラグ** |
|---|---|---|
| AI の渡し忘れ | 起きない | **起きない** |
| MCP の機能 | **`VALIDATE ONLY` が使えなくなる** | **そのまま** |
| `.mcp.json` | **2 エントリの登録が必要** | **不要** |
| 気づくタイミング | 実行して弾かれたとき | **`ksql_validate` の時点** |

**最後の行が実用上は一番大きい**と考えています。
MCP の案内は**「実行前に `ksql_validate` を使う」**なので、
**AI は普通に使っていれば実行前に受け取ります。**

### 3.2 こちら側の維持コストについても

**モードを作ると MCP の許可集合が 2 通りになり、
面ごとの一致を確かめているテストの対象も 2 倍になります。**
**許可集合が 1 通りのままであることは、ずれが生まれない**という点でも効きます。

## 4. 伺いたいこと

**そちらしか知らないことなので、教えてください。**

1. **実際に踏んだ形はありますか。**
   §1 の 5 形（`IMPORT` / `EXPLAIN <DML>` / DML の `VALIDATE ONLY`）のうち、
   **AI が書いた SQL をペインへ持っていって動かなかった、という実例**があれば教えてください。
   **こちらの想定では踏みにくい**と見ています
   （`IMPORT` は inline sources が要る／データ品質のペインは**先頭 `VALIDATE APPn` で書けて、
   それは両方が受理する**）。**この想定が外れていれば、優先度が変わります。**

2. **`ksql_validate` のフラグで足りますか。**
   足りない場合、**どの場面で足りないか**を教えてください。

3. **そもそも今も必要ですか。**
   設定画面の構文チェックが `explainQuery` を通す、というそちらの整理は今も有効です。
   **埋まるのが「設定画面を開くまでの時間差」だけであれば、
   見送るという判断もあり得る**と考えています。

**急ぎません。**M6 の受け入れテストのほうが先だと考えています。
