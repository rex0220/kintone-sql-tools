# B145 `DESCRIBE` が明細項目を親項目と区別せずに返し、親から SELECT すると静かに空になる

- 状態: 🐞 **起票・実測まで完了。修正は未着手**（2026-08-06）
- 種別: 課題（静かに間違う）
- 優先: **中**（`DESCRIBE` を読んで書いた SQL が、エラーも警告も無く全行空になる）
- 出典: [ksql-analytics の返信 §3](../../../ksql-analytics/docs/internal/kSQLエンジンへの返信-20260806-v3550.md)
  （「`DESCRIBE` は親と子の列を混ぜて返す」）

## 1. 実測（v3.55.0・APP4233）

**`DESCRIBE` は明細項目を親項目と同じ形で返す。区別する列が無い。**

```
WITH d AS (DESCRIBE APP4233)
SELECT フィールドコード, タイプ, ルックアップ, コピー元, 重複禁止, 計算式 FROM d
WHERE フィールドコード IN ('数値_0', '文字列__1行__2', 'テーブル', '数値')
```

| フィールドコード | タイプ | ルックアップ | コピー元 | 重複禁止 | 計算式 |
|---|---|---|---|---|---|
| `テーブル` | SUBTABLE | | | | |
| `文字列__1行__2` | SINGLE_LINE_TEXT | | | | |
| `数値_0` | NUMBER | | | | |
| `数値` | NUMBER | | YES | | |

**`文字列__1行__2` と `数値_0` は `テーブル` の中の項目**だが、
**親項目の `数値` と見分けが付かない。**

### 親から SELECT すると、エラーも警告も無く空になる

```
SELECT $id, 数値_0, 文字列__1行__2 FROM APP4233 LIMIT 5
  → 全行とも 数値_0="" 文字列__1行__2=""（警告なし・エラーなし）

SELECT _pid, 数値_0, 文字列__1行__2 FROM APP4233$テーブル WHERE _pid = 1
  → 5/3, 3/2, 2/5（実際には値がある）
```

**依頼元は「落ちる」と報告してきたが、実際は落ちない。空が返る。**
**報告より悪い。**

### 逃げ道が無い

```
DESCRIBE APP4233$テーブル
  → ParseError: DESCRIBE はサブテーブル仮想テーブル名を受け付けません
```

**「どの項目がサブテーブルの中か」を問い合わせる手段が無い。**

## 2. なぜ重いか

**[B130](../ksql_issue_archive.md) とまったく同じ形。** B130 は
「`DESCRIBE` の型だけではルックアップか素の文字列か分からず、
**推測がしばしば当たるので外れたときだけ静かに間違う**」ことへの対処として
「値の由来」4 列を足した。**本件は同じ失敗をより大きな結果で起こす。**

**踏む流れ:**

1. `DESCRIBE APP100` を読む
2. `数量` という項目を見つける
3. `SELECT 商品名, 数量 FROM APP100` と書く
4. **全行が空。エラーも警告も出ない**
5. 「データが入っていない」と結論する

**B119〜B122・B134 と同じ「静かに間違う」系列**で、
**エージェントが `DESCRIBE` を読んで SQL を書く**という kSQL の主用途に直撃する。

## 3. 案

- **案 A＝`DESCRIBE` に `サブテーブル` 列を足す**（該当時にサブテーブルのフィールドコード）。
  B130 と同じ形。**`SELECT *` の列数が 7 → 8 に増える破壊的変更**（B130 は 3 → 7 だった）。
  `DESCRIBE_COLUMNS` 定数と[列表の同期テスト](../../src/__tests__/b136DocsColumnParity.test.ts)も更新する
- **案 B＝親から明細項目を SELECT したら警告を出す**。
  「`数量` は `テーブル` の中の項目です。`APP100$テーブル` から選んでください」。
  **列は増えないが、`DESCRIBE` を読んだ時点では気づけない**（書いて実行するまで分からない）
- **案 C＝`DESCRIBE APPn$テーブル` を受け付ける**。
  **問い合わせる手段はできるが、`DESCRIBE APPn` を読んだ人は依然として混同する**
- 案 D＝文書化のみ

**見立て＝案 A + 案 B。** **案 A だけでは「読んだのに気づかなかった」を防げず、
案 B だけでは「読んだ時点で分かる」にならない。**
B130 が列を足して解決した前例があり、**同じ利用者（エージェント）が同じ読み方をする**。

**案 C は案 A の後で判断**（`DESCRIBE APPn` に列があれば、そちらで足りる可能性が高い）。

## 4. 破壊的変更の扱い

**`SELECT *` の列数が変わる**ため、B130 と同じ移行案内が要る。

```
移行  WITH d AS (DESCRIBE APP100) SELECT フィールドコード, ラベル, タイプ FROM d
```

**B130 のときは 3 → 7 で、そのときの案内文がそのまま使える。**

## 5. 次に開くとき必要なもの

- `formFieldInfo` の `inSubtable` / `subtableCode` は既にあるので、**DESCRIBE の射影に足すだけ**か確認
- `DESCRIBE_COLUMNS` 定数・言語リファレンス §14 の列表・
  [同期テスト](../../src/__tests__/b136DocsColumnParity.test.ts)の 3 点同期
- 案 B の警告を出す位置（`SELECT` の列解決時に `inSubtable` を見られるか）
- **警告か エラーか**＝親から明細項目を選ぶのは**ほぼ確実に誤り**なので、
  エラーのほうが正しい可能性がある。**ただし破壊的**なので、まず警告で観測する
