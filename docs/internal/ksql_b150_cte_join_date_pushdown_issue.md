# B150 CTE と物理アプリの JOIN 押し下げが DATE キーで kintone の生エラーになる

- 起票: 2026-08-07（B149 の実機確認中に発見）
- ステータス: 📝 **起票（評価前）**
- 関連: [B149](ksql_b149_generate_series_issue.md)（露出を増やす側）

## 1. 何が起きるか（実測）

```sql
WITH s AS (GENERATE_SERIES('2025-08-04', '2025-08-06') AS 日付)
SELECT s.日付, t.個数 FROM s INNER JOIN APP4228 AS t ON s.日付 = t.日付
--  kintone API error 400: GAIA_IQ03
--  「日付フィールドのフィールドタイプには演算子inを使用できません。」
```

CTE→物理アプリの JOIN は、CTE 側のキー値を `in (...)` として kintone へ押し下げる。
**kintone の DATE フィールドは `in` を受け付けない**ため、生の API エラーで落ちる。

**既存経路である**＝v3.58.0（`GENERATE_SERIES` 以前）で手書き系列
（`SELECT '2025-08-04' AS 日付 UNION ALL ...`）でも同一エラーを実測済み。
**B149 の回帰ではない**が、**日付系列を直接 JOIN する形は B149 で「最初に書かれる形」になった**
（露出が増える）。

## 2. 問題の分解

1. **kSQL の診断ではなく kintone の生エラー**が返る。v3.25.0 系の整理
   （型に合わない演算子は `WHERE_OPERATOR_INVALID_FOR_FIELD_TYPE` で取得前に拒否）は
   `WHERE` 経路の話で、**JOIN 押し下げ経路には同種の検査が無い**——
   「経路ごとに検査が揃っていない」形（B145/B148 と同族）
2. 回避形は存在する＝**物理アプリ側を CTE で集約してから CTE 間 JOIN**
   （0 埋めレシピはこの形なので実害を受けない）。ただし回避策の存在は優先度を下げる理由にならない

## 3. 案

| 案 | 内容 |
|---|---|
| A | `in` を受けない型（DATE 等）は JOIN 押し下げをやめ、全件取得へフォールバック（結果は正しくなるが取得量が増える） |
| B | 取得前に専用診断で拒否し、集約 CTE 経由の回避形を案内する |
| C | 文書化のみ（言語リファレンス §7 に制限として明記） |
| **D（2026-08-07 追記・推奨）** | **`in` の代わりにキー値の min/max で `>= min AND <= max` の範囲 prefilter（superset）を送る**。v3.60.0（B152）で日付・日時の範囲押し下げが開放されたため実装可能になった。JOIN の突合が最終判定なので superset で正確。日付系列との JOIN では系列がほぼ連続のため実質 exact 相当の絞り込み。範囲も受けない型（複数行等）は案 A のフォールバック |

**本件は「値が不正なら kintone エラーで構わない」（v3.60.0 の原則）とはクラスが違う**＝
あちらは利用者の値の問題、こちらは**エンジンが自動生成するクエリが型の受けない演算子を
選ぶ問題**（`NATIVE_OPERATORS` の知識を結合キー押し下げ側が参照していない）。
**推奨＝案 D ＋ 範囲も不可の型は案 A**。
