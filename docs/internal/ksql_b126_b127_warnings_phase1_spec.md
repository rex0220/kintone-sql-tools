## 2. B126 正規化（案 A）

### 2.0 どこで行うか（**R4 で確定・最重要**）

**`classifyWhereCapability` の中では行わない。** 同関数は capability しか返さず、
converter・JOIN planner・COUNT・KORDER・ローカル再評価は**別途 `stmt.where` を読む**ため、
分類関数内で書き換えても**分類結果と実際に使われる述語が分離する**。

→ **schema resolver（フォーム定義・`optionOrder` が揃った後）の位置に、純粋な正規化 API を置く。**

```
normalizeChoiceEquality(where, resolveField)
  -> { normalizedWhere: WhereExpr, rewrites: ChoiceEqualityRewrite[] }
```

- **実行と `EXPLAIN` は同じ API の結果を使う**（これが一致の担保）
- 以降の capability 分類・converter・JOIN prefilter・COUNT / KORDER 判定・
  **ローカル再評価**は、すべて `normalizedWhere` を見る
- `rewrites` は `EXPLAIN` の表示（§2.6）にのみ使う

### 2.1 条件（各 `BINARY` leaf ごとに、**すべて**満たすときだけ正規化する）

> **WHERE 全体の capability で判定しない。** `AND` の中の 1 つだけが residual のとき、
> 全体は `SUPERSET_PREFILTER` になるため、全体で見ると正規化が漏れる。**leaf 単位で判定する。**

1. `BINARY` leaf であり、左辺がフィールド参照・右辺が文字列リテラルである
2. `operator` が **`=` または `!=`**（R4 で `!=` を追加・§2.5）
3. `fieldType` が **`LOCAL_SCALAR_TYPES` に属する**（＝単一値。`IN` への書き換えが等価）
4. `nativeWhereOperatorsForType(fieldType)` が `in` を含む
5. **`optionOrder` が取得できており、リテラルがそのキーに実在する**
6. リテラルが**空文字でない**

**1 つでも欠けたら正規化しない**（＝従来どおり residual）。fail-closed。

### 2.2 なぜ結果が変わらないか

- **kSQL は押し下げ後も元の `WHERE` をローカルで再評価する**（§0）。
  したがって押し下げは「どの候補を取りに行くか」だけを変え、**返る行は変わらない**
- 条件 3（単一値）により `in ("X")` の集合は `= 'X'` と**完全に一致**する
  （複数値なら overlap になるので条件 3 が必須）

### 2.3 条件 5 が無いと壊れるもの（**実測**）

| SQL | 現状 | 条件 5 が無い正規化 |
|---|---|---|
| `= '出庫'`（実在） | 0 件でない結果 | 同じ結果（押し下げが効くだけ） |
| **`= '存在しない値'`（実在しない）** | **0 行・正常終了** | **`GAIA_IQ10` エラー** |

**動いていたクエリがエラーになる。** これは既存の文書化された挙動
（`IN` に定義外の値を渡すと `GAIA_IQ10`）に自動で載せてしまうため。
**条件 5 で実在を確かめ、実在しなければ正規化しない**＝従来どおり 0 行。

### 2.4 正規化は「利用者が `IN` と書いた場合と同じ経路」に載せる

正規化後の述語は、**利用者が最初から `IN ('X')` と書いた場合の AST と同一**にする。
これにより下流（単一表 / JOIN prefilter / `COUNT_TOTAL_COUNT` / `KORDER` 等）に
**分岐を 1 つも足さない**。`IN` が押し下がる場所では押し下がり、押し下がらない場所では
押し下がらない。

> **R2 で未確定だった「JOIN で `IN` が押し下がる条件」を調べる必要が無くなる。**
> 警告なら「絞れます」と断定してよいかを型ごと・経路ごとに確定する必要があったが、
> 正規化は**`IN` の挙動をそのまま継承する**だけなので、新しい約束をしない。

### 2.5 `!=` も対象にする（R3 から訂正）

R3 は「`not in` は空セル次第で部分集合になり得る」として Phase 2 に送ったが、**根拠が誤っていた**。

- 言語リファレンス: **「選択系の空／未設定セルは `IN ('')` に一致し、`NOT IN ('')` で除外されます」**
  （`ksql_language_reference.md:1077-1085`）。非空の `X` に対する `NOT IN ('X')` は未選択行を**含む**
- ローカル評価は `NOT_IN` を `IN` の論理補集合として実装（`evalWhere.ts:145-160`）。
  単一値型は `values.has(leftStr)` で、未選択は `leftStr === ""` なので `NOT IN ('X')` は true
- 既存の FULL_SCAN safe prefilter と JOIN prefilter は **`IN` と `NOT_IN` を同じ gate** で扱い、
  実在する非空選択肢なら**両方を `exact`** としている
- **実データで一致を確認**（APP4228・`!= '出庫'` = 95 / `NOT IN ('出庫')` = 95）

> **未確認**: 未選択行が存在するデータでの実機比較（APP4228 の `入出庫区分` は必須のため
> 未選択行が無い）。上の結論はリポジトリの公開契約・既存 optimizer の扱い・
> ローカル評価の実装に基づく。**受入で未選択行を含むケースを必ず置く**（§4.1）。

### 2.6 観測可能性

`EXPLAIN` の `kintone query:` に `入出庫区分 in ("出庫")` が出る。
利用者が書いた SQL と食い違って見えるので、**正規化した事実を 1 行出す**。

```
  pushdown normalized: 入出庫区分 = '出庫' -> 入出庫区分 in ("出庫")
```

## 3. B127 ウィンドウ既定フレームの警告（R2 から変更なし）

### 3.1 検出

集計ウィンドウ列（`windowKind === "AGGREGATE"`）で `orderBy.length > 0` かつ
`frame.source === "DEFAULT"`。

### 3.2 抑止（**すべて**満たすときだけ）

1. `ORDER BY` キーに `$id` または `RECORD_NUMBER` 型が含まれる
2. **単一の物理アプリを入力とし `JOIN` を含まない**
3. **サブテーブル仮想テーブルを入力にしていない**
4. **CTE / 一時テーブル / `UNION` を経ていない**

> ウィンドウは **JOIN 後の行**を評価するため、1:N の JOIN やサブテーブル展開では
> **同じ `$id` が複数回現れる**。JOIN planner 自身が `RECORD_NUMBER` を `$id` と同じ
> canonical domain と証明できないとして fail-closed にしている。
> **証明できないときは抑止しない**（警告を出す）。

### 3.3 文面

```
累積 は既定フレーム（RANGE）で評価されます。ORDER BY の値が同じ行はすべて同じ値になります。
行ごとの値が必要なら ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW を明示するか、
ORDER BY にレコード番号などのタイブレークキーを足してください。
```

alias を含める。ウィンドウ列 1 つにつき 1 行。**`UNION` / 実体化 CTE では
子 SELECT の警告を親へ集約する**（レビュー指摘 8）。

## 4. 受入条件

### 4.1 B126 正規化（**最重要は「壊れないこと」**）

| SQL | 期待 |
|---|---|
| **`WHERE 入出庫区分 = '存在しない値'`** | **エラーにならず 0 行**（現状維持）★正規化しないこと |
| `WHERE 入出庫区分 = '出庫'` | 押し下がる。**行数・各行の値が正規化前と完全一致** |
| 同上 | **`IN ('出庫')` と書いた場合と `EXPLAIN` の計画が完全一致**（`kintone query` / `mode` / `fetch` / `reason` / COUNT・KORDER 判定を含む。**これが効果と正しさの両方の証拠**） |
| **`WHERE 入出庫区分 != '出庫'`** | **正規化する**（R4）。`NOT IN ('出庫')` と書いた場合と計画が一致し、行数・値が正規化前と一致 |
| **未選択行があるデータでの `!= 'X'`** | **未選択行が結果に含まれる**（正規化前と一致）★§2.5 の未確認を潰す |
| `WHERE 入出庫区分 = ''`（空文字） | **正規化しない**（条件 6） |
| **`WHERE 入出庫区分 = '出庫' AND $id > 100`** | **`=` の leaf だけが正規化される**（§2.1・leaf 単位） |
| `WHERE 担当者 = 'user1'`（USER_SELECT・複数値） | **正規化しない**（条件 3） |
| `WHERE チェック = 'A'`（CHECK_BOX） | 従来どおり `UNSUPPORTED` エラー |
| `WHERE 製品名 = '牛乳'`（SINGLE_LINE_TEXT） | 従来どおり（元から `=` が押し下がる） |
| `optionOrder` が取れない列（CTE 由来など） | **正規化しない**（条件 5） |
| JOIN を含む文で選択系 `=` | **`IN` と書いた場合と同じ挙動**（§2.4。押し下がるかは `IN` に従う） |
| `COUNT(*)` で選択系 `=` | 同上 |

### 4.2 B127 警告

| SQL | 期待 |
|---|---|
| `SUM(x) OVER (PARTITION BY p ORDER BY 日付)`（単一表） | 警告 1 行 |
| `... ORDER BY 日付, レコード番号`（単一表・JOIN なし） | 警告なし |
| **同じ形で JOIN を含む** | **警告あり**（抑止しない） |
| サブテーブル / CTE / `UNION` を経る | 警告あり |
| `... ROWS BETWEEN ...` / `... RANGE BETWEEN ...`（明示） | 警告なし |
| `ORDER BY` なし / 順位系 | 警告なし |

### 4.3 非変更性（**R4 で訂正**）

**「結果」は変わらない。「計画」は変わってよい（変わるのが目的）。**

| 対象 | 期待 |
|---|---|
| 行数・各行の値・列名と順序 | **修正前後で完全一致**（これが唯一の非変更性） |
| `EXPLAIN` の計画（`mode` / `fetch` / `reason` / `kintone query` / COUNT・KORDER） | **変わってよい。** ただし**`IN` / `NOT IN` と書いた場合と完全一致**すること |
| 既存警告 2 件（打ち切り・検索中断） | 従来どおり出る |
| `ksql_validate` | 不変（フォーム定義を読まない） |

> **R3 は「`EXPLAIN` は `kintone query` 以外一致」としていたが誤り。**
> 正規化が効けば `mode`（FULL_SCAN → 押し下げあり）・`fetch`・`reason` から
> COUNT / KORDER の適用判定まで変わる。**それが B126 の効果そのもの。**
> 代わりに「**`IN` と書いた場合と一致する**」を固定すれば、効果と正しさを同時に押さえられる。
>
> **`metrics.fetchedRows` の厳密減少は受入にしない。** Cursor 経路を数えず、
> 減らない形（全件が条件に一致する等）もあるため、効果の証明にならない。
