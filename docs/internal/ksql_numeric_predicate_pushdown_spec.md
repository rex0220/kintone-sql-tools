## 0. スコープ（今回入れる / 入れない）

- **入れる**: **NUMBER フィールド**の押し下げ。演算子は **`=` と strict `<` / `>`**（右辺が安全整数の整数リテラル）。型メタ（`FieldTypeMap`）で NUMBER を確定したリーフのみ。`$id`（第0段）は `= < > <= >=` をそのまま維持（安全整数ドメイン）。
- **今回は入れない（案B・別課題）**: 一般 NUMBER フィールドの **`<=` / `>=`**（境界丸めで超集合性が壊れる＝§4。厳密 10 進比較の導入が前提）。
- **入れない（v2.2.0 対象外・別途）**: 日時・テキスト・選択系（`in`）。`!=`/`<>`/`NOT IN`・否定・`IS NULL`・`KINTONE_FUNC` 右辺（②の −∞ は左辺空のみで、右辺 `TODAY()` 等は評価時点差があり不可）。OR/NOT/EXISTS サブツリー。

## 1. 前提（②で解決済みの点）

- 空の数値セルは JS でも **−∞ 相当**（`< /<=` で含む・`> />=` で除外）になり、**SIMPLE と一致**（[scalarCompare.ts](../../src/core/scalarCompare.ts)）。よって空セルは範囲押し下げの超集合性を壊さない。
- 残る安全性の焦点は **(A) 型の確定**（右辺型近似は不可）と **(B) IEEE-754 精度**（§4）。

## 2. 正しさ（超集合性・②を踏まえた再確認）

押し下げる述語 `P` について「kintone の P 集合 ⊇ JS の P 集合」（[親仕様 §2](ksql_like_predicate_pushdown_spec.md)）。数値について:

- **`=`**: JS は文字列比較（`leftStr === rightStr`・[scalarCompare.ts](../../src/core/scalarCompare.ts)）、kintone は数値一致。record 文字列が一致すれば数値も一致 → **JS 一致 ⟹ kintone 一致**（kintone は書式差を吸収して広い方向）→ 超集合性 OK。**IEEE-754 の影響なし**（`=` は Number 化しない）。
- **strict `<` / `>`**: ②で空セル（−∞）は一致。境界が排他的なため丸めがあっても超集合性を保つ（§4）。右辺は安全整数リテラルに限定。
- **`<=` / `>=`**: 境界が包含的で、丸めにより超集合性が壊れる（§4 の反例）。**案 A では押し下げない**。
- **同値性は打ち切りなし前提**（親仕様 §2.1）。`truncate` 時は保証外。

## 3. 型メタ連携（(A)・実装の主眼）

### 3.1 抽出器 `extractSafePushdownLeaves` に型判定を追加

現行シグネチャ（[wherePredicatePushdown.ts](../../src/core/optimization/wherePredicatePushdown.ts)）は既に `fieldTypes?: ReadonlyMap<string, string>` を持つ。これを**使用**する:

- リーフ `field <op> literal` の採否:
  - `field` が **`$id`** → 従来どおり静的に押し下げ（型メタ不要）。
  - それ以外 → **`fieldTypes.get(unqualifiedFieldCode) === "NUMBER"`** かつ 演算子・右辺が数値プレフィルタ条件（§3.3）を満たすときのみ押し下げ。
  - `fieldTypes` が **未指定 / 空 / 当該フィールド未登録（型不明）** → **押し下げない**（[P2-2] メタ「空」＝非押し下げ）。
- **フィールドコードの解決**: JOIN 時は `tableAlias` 一致の明示フィールド、単一テーブルは非修飾も可（第0段の `isTargetIdField` と同じ規則を数値フィールドへ一般化）。型メタの参照キーは**非修飾フィールドコード**（`FieldTypeMap` はアプリ単位のため）。

### 3.2 抽出器は同期・純粋のまま／実行側が型メタを事前取得（[Medium]）

`extractMainSafePushdown`（[execute.ts:1044](../../src/execute.ts#L1044)）は **実行経路だけでなく同期の `buildSelectPlan`（EXPLAIN・[:3185](../../src/execute.ts#L3185)）からも呼ばれる**。そのまま async 化すると EXPLAIN が壊れる。**抽出器は同期・純粋関数のまま**にし、`fieldTypes` を引数で受ける（現行シグネチャどおり）:

- **実行時（`executeFullScanSelect`）**: サブクエリ解決の後・フェッチ開始前に、**必要なアプリの型メタだけ**を `getFieldTypeMap` で取得（フェッチとは別に await）。取得した `fieldTypes` を `extractMainSafePushdown` / JOIN 抽出へ渡す。
- **型メタ取得の限定（[Medium]）**: **一般フィールド（`$id` 以外）の数値比較候補が WHERE に存在するテーブル/アプリだけ**取得する。候補が `$id` だけ、または押し下げ候補なしのクエリでは `getFieldTypeMap` を**呼ばない**（数値押し下げと無関係な既存クエリに新たな API 呼び出し・失敗点を増やさない。現行の「システムフィールドのみなら `getFields` を省略」＝[execute.ts:1044 周辺](../../src/execute.ts#L1044) と同じ思想）。
- **EXPLAIN（`buildSelectPlan`）**: 型メタを持たない**別の同期「候補抽出」**を使う（§5）。`$id` は確定、一般 NUMBER 候補は「候補」表示。
- **メタ取得失敗（`getFields` reject）は既存どおり例外伝播**（[getFieldsCached](../../src/execute.ts#L1834) の await がそのまま throw）。押し下げなしで続行はしない。
- **サブテーブル仮想テーブル・CTE ソースは対象外**（第0段の `subtableCode`/`cteName` ガードを踏襲）。

### 3.3 押し下げ可の条件（数値・すべて満たす）

- 左辺が **NUMBER フィールド（型メタ確定）** または **`$id`**。
- 右辺が `NUMBER` リテラル（`STRING`/`IN_LIST`/`KINTONE_FUNC` は不可）。
- 演算子（§4 で確定）:
  - **`$id`**: `= < > <= >=`（安全整数ドメイン・ゲート免除）。
  - **一般 NUMBER フィールド**: **`=`（ゲート不要）** と **strict `<` / `>`（右辺が `Number.isSafeInteger` の整数リテラル）** のみ。**`<=`/`>=`・`!=`/`<>` は不可**。

## 4. IEEE-754 精度の扱い（(B)・要判断の核心）

**問題**: JS の範囲比較は `Number()` を通す（[scalarCompare.ts](../../src/core/scalarCompare.ts)）。kintone は 10 進で比較する。押し下げた範囲条件で **kintone が除外した行を JS では真と判定**し得るが、その行は fetch されないため**結果から落ちる（超集合性違反）**。

**発生条件（R2 で訂正・[High]）**: 「2^53 近傍のみ」は**誤り**。**小さい安全整数の境界でも、高精度小数のフィールド値が境界へ丸められると破綻する**。

- 反例（`>=`）: `L = 1`, `V = 0.99999999999999999`。`Number(V) === 1`。JS: `V >= 1` → **true**、kintone: `0.999… >= 1` → **false**。JS で残る行を kintone プレフィルタが除外 → **超集合性違反**。
- 反例（`<=`）: `L = 1`, `V = 1.00000000000000001`。`Number(V) === 1`。JS: `V <= 1` → **true**、kintone: **false** → 違反。

**演算子ごとの安全性（`L` を厳密表現可能な安全整数とする）**:

| 演算子 | 安全性 | 理由 |
|---|---|---|
| `=` | **安全（ゲート不要）** | JS は文字列比較。数値リテラルはパース時に JS number へ正規化され、JS 比較も kintone 変換も同じ正規化値を文字列化する（[parser.ts:1626](../../src/parser/parser.ts#L1626)）。精度非依存 |
| `<` / `>`（strict） | **安全（`L`＝厳密表現可能な安全整数）** | 境界が排他的。`V` が `L` へ丸まる場合、JS は `L < L`/`L > L` ＝ false で境界を含めない。kintone が余分に含める分は JS 再評価が捨てるので無害 |
| `<=` / `>=` | **案 A では不可** | 境界が包含的。`V` が境界の**除外側から** `L` へ丸まると（上の反例）、JS が含め kintone が除外 → 違反 |

**対策 — 2 案**:

- **案 A（今回の v2.2.0 スコープ）**: 押し下げるのは **`=`（ゲート不要）と strict `<`/`>`（右辺が `Number.isSafeInteger` の整数リテラル）だけ**。`<=`/`>=`、および安全整数でない/高精度小数のリテラルは**押し下げない**（JS 全評価に委ねる）。これで残余リスクなし。
- **案 B（`<=`/`>=` を含める・別課題）**: `scalarCompare` の範囲比較を**厳密 10 進**にする（整数は `BigInt`、小数は 10 進文字列比較）。JS が kintone と一致し、`<=`/`>=` を含む全範囲が押し下げ可能になる。**副次効果**で FULL_SCAN の大整数比較自体が正確に（②と同種のモード一致改善）。比較器の変更が大きく、既存の丸め挙動に依存するテストの見直しが要る。

→ **③（v2.2.0）は案 A**（`=`・strict `<`/`>`）。`<=`/`>=` の押し下げが必要なら**案 B を別課題**として切り出す。

> **`$id` の扱い（[Low]）**: `$id`（レコード番号）は**常に正の安全整数**でフィールド値に小数・巨大値がないため、上の丸め問題が起きない。よって `$id` は**第0段のまま `= < > <= >=` を維持**（精度ゲート免除）。**ゲートは一般 NUMBER フィールドの範囲にのみ適用**する。

## 5. EXPLAIN（型メタが要るため候補表示）

`executeExplain` は同期・kintone 非アクセス（[execute.ts:3147](../../src/execute.ts#L3147)）。no-API の EXPLAIN が分かるのは「**一般フィールド＋数値リテラルの組み合わせ**」までで、**実際に NUMBER 型かは判定できない**（[Medium]）。よって**確定計画と候補を別行に分離**する（`kintone query` 行に混ぜると「実際に押し下がる計画」と誤認される）:

```
  kintone query:      $id >= 1000
  pushdown candidate: 金額 > 1000（実行時の型確認待ち）
```

- `kintone query`: **確定押し下げ**（`$id` の肯定比較など、型メタ不要で確定できるもの）。
- `pushdown candidate`: 一般フィールド × 数値リテラル × 押し下げ可能演算子（`=`・strict `<`/`>`）の**候補**。実行時に型メタで NUMBER を確認して初めて押し下げる。
- EXPLAIN の **no-API 契約は維持**（型メタ取得のための API を EXPLAIN では呼ばない）。

## 6. 受入・実機テスト（打ち切りなし前提で 押し下げ後 == 全件 JS 評価）

- **単体（抽出器 × 型メタ）**: `fieldTypes` に `金額:NUMBER` を与えたとき、`金額 = 100`・`金額 > 1000`・`金額 < 1000`（strict・安全整数）を押し下げる／**`金額 >= 1000`・`金額 <= 1000` は押し下げない**（案A 対象外）／`金額 != 100`・`金額 > 1.5`（非安全整数）・テキストや型不明フィールドは押し下げない／`fieldTypes` 空・未指定は非押し下げ。`$id >= 1000`・`$id <= 1000` は押し下げる（ゲート免除）。
- **[High] 丸め反例の単体**: `compareScalarValues` レベルで `"0.99999999999999999" >= "1"` → JS true（＝押し下げ不可の根拠）、`"1.00000000000000001" <= "1"` → JS true を固定し、`>=`/`<=` を一般 NUMBER で押し下げないことの妥当性を明示。
- **超集合性（結合・書き込み API モック・打ち切りなし前提）**: `金額 > -1 AND … LIKE …`（無エイリアス／エイリアス／JOIN）で押し下げ結果 == 全件 JS 評価。**空セル（−∞）・0・負値**を含めて一致。
- **`=` の一致**: `金額 = 0`（空セルは偽）・書式差（record `"100"` と リテラル `100`）で一致。
- **メタ失敗**: `getFields` reject で実行がエラー（押し下げなしで続行しない）。**型メタ取得の限定**: 押し下げ候補が `$id` だけ / なしのクエリで `getFieldTypeMap`（getFields）を呼ばないこと。
- **EXPLAIN**: 一般 NUMBER 候補が `pushdown candidate` 行に出て `kintone query` には出ない、`$id` は `kintone query` に確定表示。
- **回帰**: 第0段（`$id`）・②（空セル −∞）・既存 SIMPLE/FULL_SCAN が不変。

## 7. 効果評価・段階

| 観点 | 評価 |
|---|---|
| 効果 | LIKE ＋ 数値 `=`/`<`/`>` の併記クエリで取得件数を削減（②で空セル安全性が担保）。`<=`/`>=` は案 B 導入まで対象外のため効果は限定的（`>` で代替できない小数境界の「以上/以下」は残る） |
| 実装コスト | 中。抽出器の型判定追加は小、実行側の型メタ事前取得＋候補限定が主。EXPLAIN の候補抽出/表示追加。案 A ゲート（`isSafeInteger`＋strict のみ）は小 |
| 正しさリスク | 低〜中。型メタで NUMBER 確定・②で空セル一致・案 A は `=`/strict のみで丸め違反を原理回避。実機超集合性テストで担保 |
| 残余 | 案 A では `<=`/`>=` を出せない（実用上の制約）。全範囲が要るなら案 B（厳密 10 進） |

## 8. 結論（推奨）

- **③（v2.2.0）= NUMBER フィールドの `=` と strict `<` / `>`（安全整数リテラル）を型メタ確定のうえ押し下げ**。②で空セルが −∞ に揃ったことが前提。
- **v2.2.0 は案 A（`=`・strict `<` / `>`）を採用する。一般 NUMBER フィールドの `<=` / `>=` と厳密 10 進比較は別課題**とし、実需と比較意味論の仕様を独立して検討する（[ksql_exact_decimal_compare_issue.md](./ksql_exact_decimal_compare_issue.md)）。`<=`/`>=` を押し下げなくても FULL_SCAN で正しく実行されるため機能欠落にはならない（③は最適化）。
- **抽出器は同期・純粋のまま**、実行側が（数値候補のあるアプリに限り）型メタを事前取得して渡す。EXPLAIN は同期の候補抽出で `pushdown candidate` を別行表示。
- `$id` は安全整数ドメインのため第0段の `= < > <= >=` を維持（ゲート免除）。
- 日時・テキスト・選択系は v2.2.0 に含めない。
- 実装後、①②③をまとめて **v2.2.0** で一括検証・リリース（CHANGELOG「未リリース」を最後に確定）。
