# 仕様案: 型メタ付き数値プレフィルタ（述語分割 ③）

- 作成日: 2026-07-15
- ステータス: **仕様案（レビュー前）**
- 分担: Claude=仕様/観点、Codex=実装/テスト
- 位置づけ: v2.2.0 バンドルの構成要素③。①第0段（`$id` プレフィルタ・安全化＝`5c987e0`）／②空セル −∞（`1c73828`）に続く。**②完了により数値範囲の空セル挙動が SIMPLE と一致した**ため、数値フィールドの範囲比較を安全に押し下げられる前提が整った。
- 親仕様: [ksql_like_predicate_pushdown_spec.md](ksql_like_predicate_pushdown_spec.md)（R3）。本書は「第1段（数値）」の詳細。
- 関連コード: `src/core/optimization/wherePredicatePushdown.ts`（`extractSafePushdownLeaves`）、`src/execute.ts`（`extractMainSafePushdown` / `executeFullScanSelect` / `getFieldTypeMap`）、`src/core/scalarCompare.ts`（②の比較器）

## 0. スコープ（今回入れる / 入れない）

- **入れる**: **NUMBER フィールド**の押し下げ。**範囲比較 `< > <= >=`** と **`=`**。型メタ（`FieldTypeMap`）で NUMBER を確定したリーフのみ。`$id`（第0段）はそのまま維持。
- **入れない（v2.2.0 対象外・別途）**: 日時・テキスト・選択系（`in`）。`!=`/`<>`/`NOT IN`・否定・`IS NULL`・`KINTONE_FUNC` 右辺（②の −∞ は左辺空のみで、右辺 `TODAY()` 等は評価時点差があり不可）。OR/NOT/EXISTS サブツリー。

## 1. 前提（②で解決済みの点）

- 空の数値セルは JS でも **−∞ 相当**（`< /<=` で含む・`> />=` で除外）になり、**SIMPLE と一致**（[scalarCompare.ts](../../src/core/scalarCompare.ts)）。よって空セルは範囲押し下げの超集合性を壊さない。
- 残る安全性の焦点は **(A) 型の確定**（右辺型近似は不可）と **(B) IEEE-754 精度**（§4）。

## 2. 正しさ（超集合性・②を踏まえた再確認）

押し下げる述語 `P` について「kintone の P 集合 ⊇ JS の P 集合」（[親仕様 §2](ksql_like_predicate_pushdown_spec.md)）。数値について:

- **`=`**: JS は文字列比較（`leftStr === rightStr`・[scalarCompare.ts](../../src/core/scalarCompare.ts)）、kintone は数値一致。record 文字列が一致すれば数値も一致 → **JS 一致 ⟹ kintone 一致**（kintone は書式差を吸収して広い方向）→ 超集合性 OK。**IEEE-754 の影響なし**（`=` は Number 化しない）。
- **範囲 `< > <= >=`**: ②で空セルは一致。有限の通常値も kintone（10 進）と JS（`Number`）で一致。**例外は桁の大きい整数**（§4）。
- **同値性は打ち切りなし前提**（親仕様 §2.1）。`truncate` 時は保証外。

## 3. 型メタ連携（(A)・実装の主眼）

### 3.1 抽出器 `extractSafePushdownLeaves` に型判定を追加

現行シグネチャ（[wherePredicatePushdown.ts](../../src/core/optimization/wherePredicatePushdown.ts)）は既に `fieldTypes?: ReadonlyMap<string, string>` を持つ。これを**使用**する:

- リーフ `field <op> literal` の採否:
  - `field` が **`$id`** → 従来どおり静的に押し下げ（型メタ不要）。
  - それ以外 → **`fieldTypes.get(unqualifiedFieldCode) === "NUMBER"`** かつ 演算子・右辺が数値プレフィルタ条件（§3.3）を満たすときのみ押し下げ。
  - `fieldTypes` が **未指定 / 空 / 当該フィールド未登録（型不明）** → **押し下げない**（[P2-2] メタ「空」＝非押し下げ）。
- **フィールドコードの解決**: JOIN 時は `tableAlias` 一致の明示フィールド、単一テーブルは非修飾も可（第0段の `isTargetIdField` と同じ規則を数値フィールドへ一般化）。型メタの参照キーは**非修飾フィールドコード**（`FieldTypeMap` はアプリ単位のため）。

### 3.2 `extractMainSafePushdown` / JOIN 経路の async 化

型メタ取得（`getFieldTypeMap`・async）が必要になるため:

- `extractMainSafePushdown(stmt)` を **async 化**（`getFieldTypeMap(stmt.from.appId, client, cacheContext)` を await して `fieldTypes` を渡す）。JOIN なしはメインアプリのみ、JOIN ありは**各テーブルのアプリごと**に型メタを取得して該当テーブルの押し下げに使う。
- `executeFullScanSelect`（[execute.ts:1076-](../../src/execute.ts#L1076)）は既に async。サブクエリ解決の後（フェッチ開始前）に型メタを取得して押し下げ条件を計算する。**型メタ取得はフェッチと並列化可**（`Promise.all`）だが、押し下げクエリ確定にはメタが要るのでフェッチ開始前に await。
- **メタ取得失敗（`getFields` reject）は既存どおり例外伝播**（[getFieldsCached](../../src/execute.ts#L1834) の await がそのまま throw）。押し下げなしで続行はしない（[P2-2]）。
- **サブテーブル仮想テーブル・CTE ソースは対象外**（第0段の `subtableCode`/`cteName` ガードを踏襲）。

### 3.3 押し下げ可の条件（数値・すべて満たす）

- 左辺が NUMBER フィールド（型メタ確定）または `$id`。
- 演算子が `= < > <= >=`（**`!=`/`<>` は不可**）。
- 右辺が `NUMBER` リテラル（`STRING`/`IN_LIST`/`KINTONE_FUNC` は不可）。
- 範囲演算子は §4 の **数値ドメイン・ゲート**を満たす（`=` は対象外＝常に可）。

## 4. IEEE-754 精度の扱い（(B)・要判断の核心）

**問題**: JS の範囲比較は `Number()` を通す（[scalarCompare.ts](../../src/core/scalarCompare.ts)）。桁の大きい整数は同一の double へ丸められる。例: `Number("9007199254740993") === Number("9007199254740992")`（ともに `9007199254740992`）。kintone が 10 進で比較すれば別値。押し下げた範囲条件で **kintone が除外した行を JS では真と判定**し得るが、その行は fetch されないため**結果から落ちる（超集合性違反）**。

**発生条件（精密化）**: 右辺リテラル `L` と フィールド値 `V` の**両方が 2^53 近傍**（丸めの ULP 内）でのみ起こる。`L` が安全整数域から十分内側で、`V` も通常桁なら発生しない。`=` は文字列比較のため**影響なし**。

**対策（範囲演算子のみ）— 2 案**:

- **案 A（安全ドメイン・ゲート／今回推奨）**: 範囲の右辺リテラルが**安全整数**（`Number.isSafeInteger(Number(rightStr))`）で、かつ**桁・精度が double で厳密表現できる**場合のみ押し下げる。境界（`|L|` が 2^53 近傍・高精度小数）は押し下げず JS 全評価に委ねる。**残余リスク**: 2^53 近傍の小数フィールド値が `L` の半 ULP 内にある極端ケース。実務データでは稀。境界テスト（§6）で監視し、該当時は非押し下げ側へ倒す。
- **案 B（正確 10 進比較／将来）**: `scalarCompare` の範囲比較を**厳密**にする（整数は `BigInt`、小数は 10 進文字列比較）。JS が kintone と一致し、押し下げが常に安全。**副次効果**として FULL_SCAN の大整数比較自体が正確になる（②と同種のモード一致改善）。ただし比較器の変更が大きく、既存の丸め挙動に依存するテストの見直しが要る。

→ **③では案 A（安全整数ゲート）で開始**。`=` はゲート不要。案 B（正確比較）は「大整数の厳密性」が要る場合の**別課題**として切り出す（本課題スコープ外）。

## 5. EXPLAIN（型メタが要るため候補表示）

`executeExplain` は同期・kintone 非アクセス（[execute.ts:3147](../../src/execute.ts#L3147)）。型メタは async のため EXPLAIN では**確定できない**（親仕様 §4.4 の決定を踏襲）:

- `$id` の押し下げは従来どおり**確定表示**。
- NUMBER フィールドの範囲/`=` は「**押し下げ候補（実行時に型を確認して確定）**」と表示（実際の押し下げは実行時に型メタで確定）。
- EXPLAIN の no-API 契約は維持（型メタ取得のための API を EXPLAIN では呼ばない）。

## 6. 受入・実機テスト（打ち切りなし前提で 押し下げ後 == 全件 JS 評価）

- **単体（抽出器 × 型メタ）**: `fieldTypes` に `金額:NUMBER` を与えたとき、`金額 >= 1000`・`金額 = 100` を押し下げる／`金額 != 100`・テキストや型不明フィールドは押し下げない／`fieldTypes` 空は非押し下げ。
- **超集合性（結合・書き込み API モック）**: `金額 >= -1000000 AND … LIKE …`（無エイリアス／エイリアス／JOIN）で押し下げ結果 == 全件 JS 評価。**空セル（−∞）・0・負値**を含めて一致。
- **`=` の一致**: `金額 = 0`（空セルは偽）・書式差（record `"100"` と リテラル `100`）で一致。
- **IEEE-754 境界（実機・案 A のゲート確認）**: 2^53 近傍の値（例 `9007199254740993`）を持つレコードで、`金額 <= 9007199254740992` が**押し下げられない**こと（安全整数外リテラルはゲートで除外）＝ JS 全評価で kintone と一致。小さいリテラルでは押し下げても一致。
- **メタ失敗**: `getFields` reject で実行がエラー（押し下げなしで続行しない）。
- **EXPLAIN**: NUMBER 述語が「押し下げ候補」表示、`$id` は確定表示。
- **回帰**: 第0段（`$id`）・②（空セル −∞）・既存 SIMPLE/FULL_SCAN が不変。

## 7. 効果評価・段階

| 観点 | 評価 |
|---|---|
| 効果 | LIKE ＋ 数値範囲/等値 の併記クエリで取得件数を削減（②で空セル安全性が担保され、数値が押し下げ可能に）。大規模アプリで実用的 |
| 実装コスト | 中。抽出器の型判定追加は小、`extractMainSafePushdown`/JOIN の async 化＋型メタ結線が主。案 A ゲートは小 |
| 正しさリスク | 中。型メタで NUMBER 確定・②で空セル一致・案 A ゲートで大整数を回避。実機超集合性テストで担保 |
| 残余 | 案 A の 2^53 近傍・小数の極端ケース（稀）。厳密性が要るなら案 B（別課題） |

## 8. 結論（推奨）

- **③ = NUMBER フィールドの範囲＋`=` を型メタ確定のうえ押し下げ**。②で空セルが −∞ に揃ったことが前提。
- **IEEE-754 は案 A（安全整数ゲート）で開始**、`=` はゲート不要（文字列比較で精度非依存）。正確 10 進比較（案 B）は別課題。
- 日時・テキスト・選択系は v2.2.0 に含めない（親仕様の段階に従い後続）。
- 実装後、①②③をまとめて **v2.2.0** で一括検証・リリース（CHANGELOG「未リリース」を最後に確定）。
