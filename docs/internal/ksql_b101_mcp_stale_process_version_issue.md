# B101 常駐 MCP プロセスが古い版のまま答えても、利用者に分からない

- 起票: 2026-07-29
- ステータス: 📝 **評価＝R3。案 A' を推す**（§2ter）＝**標準の `_meta` は実クライアント 2 つで読めなかった**。**`instructions` なら両 era・両クライアントに届く**
- 出典: [Pro の報告 v3.34.0(2 通目)](../../../ksql-dashboard-pro/docs/internal/kSQLエンジンへの報告-v3340b.md)。
  **Pro 側は再起動という運用で解決済み**。**エンジン側に観測手段が無い**点をこちらの課題として起票する
- 関連: [B100](ksql_b100_failclosed_message_order_issue.md) / [B98](ksql_b98_join_truncated_right_null_issue.md)
- Pro への連絡: [返信(2 通目)](ksql_pro_reply_v3340b.md)（送付済み） → [Pro の報告(3 通目)](../../../ksql-dashboard-pro/docs/internal/kSQLエンジンへの報告-v3340c.md)＝**`_meta` は届かないと判明**（§2ter）

## 1. 実際に起きたこと

**Pro は v3.34.0 の検証結果として「B98 が再現しない」と報告した。**
**その測定はすべて v3.33.0 の挙動だった。**

```
1. エディター再起動 → MCP サーバーが 3.33.0 を読み込んで常駐
2. package.json を 3.34.0 へ差し替え、npm install    ← ディスクは 3.34.0
3. その MCP 経由で測定                                ← プロセス内は 3.33.0
```

**`npm install` はディスクを置き換えるが、常駐プロセスが読み込み済みのモジュールは差し替わらない。**

**代償**

- **誤った検証結果が返ってきた**（`LEFT` / `RIGHT` とも「行 + 警告」）
- **「実機確認済み」とされた `INNER JOIN` の結果一致も、取り直しになった**
- **往復が 1 回増えた**

**気づけたのは、こちらが同じアプリで測り直して食い違いを見つけたからである。**
**Pro 側からは、測定が古い版のものだと分かる手がかりが無かった。**

## 2. 測定 — **版数を返す tool も resource も無い**

| 面 | 版数 |
|---|---|
| `serverInfo.version`（`initialize` / `server/discover`） | **ある**（`src/mcp/index.ts:132`） |
| **13 tools のいずれか** | **無い** |
| **4 resources のいずれか** | **無い** |
| **`ksql_docs`（引数なし＝「このサーバーは何か」を尋ねる呼び出し）** | **無い** |

**`SERVER_VERSION` の参照箇所は `src/mcp/index.ts:132` の 1 つだけ**である。

> **`serverInfo.version` は handshake にしか出ない。**
> **AI クライアントはこれを利用者へ提示しない**ため、
> **利用者が「どの版が答えたか」を確かめる手段が実質的に無い。**

## 2bis. **【R2 訂正】MCP 標準の作法が既にある**（2026-07-29 実測）

**§2 の「版数を返す手段が無い」は、tool / resource の出力についてのみ正しい。**
**プロトコルには標準の仕組みがあり、こちらは既にそれを満たしていた。**

### 2bis.1 仕組み

**`_meta['io.modelcontextprotocol/serverInfo']`**（spec PR #3002）。
**「servers SHOULD identify themselves on every response」**——
**全 result に `{name, version}` を押す**というもの。

**SDK の 2026-era codec が `Server` の identity を使って自動で押す。**
**こちら側のコードは 1 行も要らない。**

- **2025 era（v1）は一切押さない**——*never-stamp guarantee*。仕様上の設計であって欠落ではない
- **handler が自分で値を入れた場合はそちらが勝つ**

### 2bis.2 実測

```
era = modern
v2 tools/list             → {"name":"ksql-mcp","version":"3.34.0"}
v2 resources/list         → {"name":"ksql-mcp","version":"3.34.0"}
v2 tools/call ksql_docs   → {"name":"ksql-mcp","version":"3.34.0"}
v1 tools/list             → null
v1 tools/call ksql_docs   → null
v1 serverInfo (handshake) → {"name":"ksql-mcp","version":"3.34.0"}
```

> **[B99](ksql_b99_mcp_spec_2026_07_28_issue.md) の v2 移行で、v2 クライアントには既に版数が毎回届いている。**
> **§2 を書いた時点では、この標準を確かめていなかった。**

### 2bis.3 **それでも残る穴**

| | |
|---|---|
| **v1 クライアントには届かない** | **仕様どおり**。こちらでは変えられない |
| **`_meta` は機械可読であって、人に見える場所ではない** | **クライアントが提示しなければ利用者は気づかない**。Pro の事故はこれでも防げない |

**つまり「診断できるようにする」は標準の側で解決済みであり、
残っているのは「利用者が疑わなくても気づける」ようにする話だけ**である。

## 2ter. **【R3】`_meta` は実クライアントで読めない**（2026-07-29）

**§2bis で「v2 なら毎回届いている」と書いたが、届く先はクライアントの内部までである。**
**利用者や AI に渡る前に落ちる。**

### 2ter.1 実クライアント 2 つで確認

| クライアント | `_meta` が読めるか |
|---|---|
| **Pro のクライアント** | **読めない**（[報告 3 通目](../../../ksql-dashboard-pro/docs/internal/kSQLエンジンへの報告-v3340c.md)）。ツール結果の中身だけが届く |
| **Claude Code** | **読めない**。`ksql_query` の結果は `{"ok":true,"type":"SELECT",...}` だけで封筒は見えない |

> **§5 の未調査項目③「主要な MCP クライアントが `_meta` を利用者へ提示するか」の答えは、
> 少なくとも 2 つで「否」**である。

**§2bis の「Pro が自分で読みに行けば確実に分かる」は誤りだった。**
**読める立場のクライアントにしか当てはまらない。**

### 2ter.2 Pro が採った回避策

**(1) 更新したら MCP を再起動する**（既定の手順にした）
**(2) 版に固有の識別子を `grep` で数える**——**ただしディスクの版であって、プロセスの版ではない**。
**今回の取り違えはこれでは防げなかった**
**(3) カナリアクエリを 1 本流す**——**プロセスの版を測る唯一の方法**

```sql
SELECT d.案件名, c.業種 FROM APP4149 d LEFT JOIN APP4148 c ON d.顧客No_ = c.顧客No
-- maxRecords=20 / truncate
-- 3.34.0 → FetchAllLimitError   3.33.0 → 行 + 警告
```

**(3) は正しいが高くつく。**実データが要り、**版ごとに作り直す**必要がある。

## 3. これは誰の問題か

**運用の問題でもある。**Pro は再起動で解決し、その手順を把握した。

**同時にエンジン側の観測性の問題でもある。**

- **毎リリース・全 MCP 利用者に再発する**（`node_modules` から起動する構成は普通）
- **失敗が沈黙する。**古い版は古い版として正しく動くので、エラーも警告も出ない
- **誤った結論が「実機確認済み」として流通する**

**こちらの測定も同じ経路に依存している。**
**B98 の実機確認は、たまたま publish 後に VSCode を再読み込みしていたから正しかった。**

## 4. 案

### 案 A: 版数を開示する（**取り下げ・R2**）

**初版は「`ksql_docs` の出力に版数を 1 行足す」と書いた。取り下げる。**

- **MCP 標準に `_meta['io.modelcontextprotocol/serverInfo']` があり、v2 では既に全 result に載っている**（§2bis）
- **独自に出力へ埋めるのは、標準がある場所に別の作法を足すことになる**
- **`ksql_docs` の出力を固定しているテスト 5・smoke 4 を、得るものなく揺らす**

> **教訓＝「版数を返す手段が無い」を、自分の tool / resource だけ見て結論づけた。**
> **プロトコル側を先に見ていれば、案として書く必要が無かった。**
> **[B99](ksql_b99_mcp_spec_2026_07_28_issue.md) R2 と同じ形の誤り**——**「正しく調べた」と「正しいものを調べた」は別**。

### 案 A': **`instructions` に版数を載せる**（**R3・推し**）

**`KSQL_MCP_INSTRUCTIONS` に版数を 1 語入れる。**

**`_meta` が落ちるクライアントにも届く。**
**`instructions` は AI の文脈にそのまま入るためである**
（Claude Code の文脈に `KSQL_MCP_INSTRUCTIONS` が入っていることを確認済み）。

| | |
|---|---|
| **到達性** | **`_meta` を落とすクライアントにも届く**（実クライアント 2 つで確認） |
| **測る対象** | **常駐プロセスが接続時に返す**＝**ディスクではなく動いているコードの版**。Pro のカナリア (3) と同じものを測る |
| **era** | **v1 の `initialize` と v2 の `server/discover` の両方**に載る（`_meta` は v2 のみ） |
| **費用** | **語数予算は total 548 / prose 290（上限 320）**。**版数は 1 語**で収まり、**語数は版が変わっても不変** |
| **固定しているテスト** | `instructions` は `includes(key)` で見られているだけ。**exact 固定は語数予算の `toEqual({total:548,...})` 1 箇所**で、これは意図的な検知装置 |

- **カナリアクエリが要らなくなる。**実データも、版ごとの作り直しも不要
- **限界＝接続時に 1 回配られるだけ。**セッション中にサーバーを再起動しても、
  AI の文脈は古い `instructions` を持ったまま
- **`ksql_docs` に混ぜる案（取り下げ済み）との違い**＝
  **`ksql_docs` は文書を返す tool で、版数は文書ではない**。
  **`instructions` は「このサーバーは何者か」を伝える場所**なので、版数が入るのは筋が通る

### 案 B: 陳腐化を自己検出する（**失敗そのものを潰す**）

**起動時に焼き込んだ `SERVER_VERSION` と、ディスク上の `package.json` の版を突き合わせる。**

```
プロセス内 3.33.0  ≠  ディスク 3.34.0  → 「サーバーを再起動してください」
```

- **起動時の検査では意味が無い**——起動時点では一致している。
  **tool 呼び出しのたびに（mtime で握って）検査する**必要がある
- **これは Pro の事故を実際に防ぐ。**利用者が疑う必要が無い
- **費用は案 A より大きい**〔ディスク I/O の追加／`dist-mcp` 単体配布（MCPB・`release/ksql-mcp.js`）では
  隣に `package.json` が無い経路がある／どこに出すか（stderr か tool 結果か）の判断〕
- **単体配布の経路では検査できない**ので、**「検査できないときは黙る」**必要がある

### 案 C: 何もしない

- **Pro は解決済み。**運用手順の問題として扱う
- **次の利用者が同じ穴に落ちる**

## 5. 現時点の見立て（R3）

**案 A' を推す。優先度は 低 のままだが、費用が小さく、実害が確認されている。**

**R2 では「診断は標準の側で解決済み」と考えた。それが崩れた。**
**`_meta` は実クライアント 2 つで読めず、届く先はクライアントの内部までだった**（§2ter）。

| 案 | 判断 |
|---|---|
| **案 A'（`instructions` に版数）** | **推す。**`_meta` が落ちる経路にも届き、**プロセスの版**を測る。**1 語** |
| 案 A（`ksql_docs` に版数） | **取り下げのまま。**文書を返す tool に版数は載せない |
| 案 B（陳腐化の自己検出） | **保留。**唯一「疑わなくても気づける」案だが、費用が大きい。**案 A' の後で要否を判断する** |
| 案 C（何もしない） | **Pro はカナリアで凌いでいる**が、**実データと版ごとの作り直しが要る** |

**優先度を 低 に据え置く理由は変わらない。**
**誤った結果を返す問題ではなく、古い版は古い版として正しく動いている。**

**次にこのファイルを開くときに必要なもの**

1. **案 A' を採るなら**——`instructions` のどこに置くか（先頭 1 行を推す）と、
   **語数予算の `toEqual` 更新**（total 548 → 549 前後）
2. **案 B へ進むなら**——**`dist-mcp/ksql-mcp.js` が単体で置かれる経路の一覧**
   （MCPB・`release/`・その他）＝**「検査できない」と判断すべき条件がこれで決まる**
3. **~~主要な MCP クライアントが `_meta` を利用者へ提示するか~~ → 済**。**2 つとも「否」**（§2ter）

## 6. 対象外

| | 理由 |
|---|---|
| **サーバーの自動再起動** | **MCP サーバーは client が起動する。**自分で再起動する立場にない |
| **CLI・engine ライブラリ** | **常駐しない**ので、この失敗は起きない |
| **プラグイン** | ブラウザで読み込むため対象外 |
| **依存の版ずれ一般** | **こちらが焼き込んだ版と、こちらが置いた版のずれ**に限る |
| **`_meta` への独自キー追加** | **標準の `io.modelcontextprotocol/serverInfo` がある**（§2bis）。増やさない |
