## 1. 提案

SQL 標準の **`WITH RECURSIVE`（再帰 CTE・SQL:1999）** と **`CYCLE` 句（循環検出・SQL:2016）** を kSQL に導入する候補。

```sql
-- 例: 部品表（BOM）の親→子を再帰展開（到達可能性）
WITH RECURSIVE 部品展開 AS (
  SELECT 部品ID, 子部品ID, 1 AS 深さ FROM APP100 WHERE 部品ID = 'P001'   -- seed（非再帰項）
  UNION ALL
  SELECT c.部品ID, c.子部品ID, r.深さ + 1                                 -- 再帰項（自己参照）
  FROM APP100 c JOIN 部品展開 r ON c.部品ID = r.子部品ID
)
CYCLE 部品ID SET is_cycle TO 'Y' DEFAULT 'N'                              -- 循環検出（無限ループ防止）
SELECT * FROM 部品展開;
```

## 2. 何を解決するか（固有価値）

評価当時の kSQL は**再帰・推移閉包を表現できなかった**（〜v3.65.0。**B53 Phase1 で解消＝v3.66.0**）。JOIN は単一等値・派生テーブルなし・再帰 CTE なしのため、次が**不能 or 極めて冗長**:

- **階層の展開**: 組織図、部品表（BOM）、カテゴリツリーの親↔子の全展開。
- **可変長経路・到達可能性**: 「A から到達できる全ノード」「N ホップ以内」。
- **循環検出**: 送金経路のループ（マネロン）、参照の循環。

関係が濃い kintone（アプリ間の外部キー参照が多い）で「**不能→可能**」を作る点は B40 と同じ。

## 3. B40（プロパティグラフ）との関係（重要）

**B53 と B40 は同じ用途（到達可能性・循環検出・可変長経路）に対する別アプローチ**であり、**どちらを採るかの判断が必要**（両方は過剰）。

| 観点 | B53 WITH RECURSIVE | B40 プロパティグラフ（GRAPH_TABLE MATCH） |
|---|---|---|
| 標準 | SQL:1999/2016・**広く普及**（PostgreSQL/Oracle/SQL Server/MySQL8） | SQL:2023・**新しい**（Oracle 先行） |
| 学習コスト | SQL 利用者に馴染み・**低め** | 新 MATCH 副言語・高め |
| 既存資産の再利用 | **既存 CTE 機構の拡張**（B51/B52 で実体化 CTE が堅牢化済み）＋UNION ALL | 新 FROM ソース＋型付き副言語＋パターン評価器（新規大） |
| 表現 | 一般の再帰関係（階層・グラフ両方） | グラフパターン（ノード/エッジ）に特化・可読性高 |
| 循環検出 | **CYCLE 句**（明示・標準） | パターンで `->(a)` 戻り＋境界 |
| 実装規模 | 反復 fixpoint 実行エンジン新設（中〜大） | 最大級（B40 評価: 19〜31 人日） |

**示唆**: B53 は **SQL 標準で馴染みがあり、v3.11.0 で堅牢化した CTE 機構を土台にできる**分、B40 より学習コスト・実装の見通しが良い可能性がある。B40 の看板価値（可変長・到達可能性・循環検出）を、より標準的な構文で提供できる。**着手前に B40 と併せて「どちらの方向か」を判断する**。

## 4. 実現可能性・技術課題

kintone にサーバ側再帰はない（他の全機能同様クライアント側）。再帰 CTE は**反復実行**になる:

1. **seed（非再帰項）を実行** → 作業集合。
2. **再帰項を作業集合に対して繰り返し適用**（自己参照）し、新規行を蓄積 → 新規行が出なくなる（fixpoint）まで。
3. 各反復＝クライアント側 fetch/JOIN。

主要課題:

- **終了保証（最重要）**: 循環データで CYCLE も深さ上限も無いと**無限ループ**。→ **CYCLE 句 or 最大深さ/最大行の境界を必須にし、超過は fail-closed でエラー**（B40 と同じ「爆発は有界 fail-closed」）。10 万件打ち切り（KLIKE 系）と同じ思想。
- **性能**: 各反復が fetch/JOIN のため、深さ N で N ラウンド。関係が濃いと行が急増。**境界（深さ・総行数）と EXPLAIN での可視化**が要る。実件数は事前に読めない（B40 と同じ制約）。
- **UNION ALL / 自己参照のパース**: 再帰項が CTE 自身を参照する AST・非再帰項/再帰項の分離・列数/型の整合。
- **CYCLE 句の範囲**: SQL:2016 の完全形（`CYCLE col SET mark TO x DEFAULT y USING path`）は複雑。v1 は**「循環を検出したら打ち切る」最小サブセット**（mark 列生成・path 列は任意）で十分か検討。
- **実行エンジン**: 現状 CTE は単一パス実体化（B51/B52 で堅牢化）。再帰は**反復 fixpoint**の新経路。既存の実体化・JOIN・UNION 資産を反復で回す設計。
- **LAPP/プラグイン等の面**: B40 同様、面ごとの制約（プラグインの取得上限・打ち切り検出）を確認。

## 5. API 発行回数の評価（重要）

再帰 CTE はクライアント側の反復実行になるため、**API 発行回数は実行戦略に強く依存する**。kSQL の現行 JOIN は「結合先アプリを全件取得してメモリ結合」する（実測: `LEFT JOIN APP730` が 618,525 件を全件取得しようとして取得上限に達した）。この性質を再帰でどう扱うかが API 回数を決める。

記号: 参照アプリ 1 つの総レコード数 `R`、ページサイズ `P`（既定 500）、再帰の深さ `D`、各深さの frontier（作業集合の一致キー数）`Fᵢ`、`in` 1 クエリの値上限 `L`。

### 5.1 戦略と API 回数

| 戦略 | API 回数（目安） | 取得データ量 | 備考 |
|---|---|---|---|
| **A: naïve（各反復で結合先を全件取得）** | `D × ⌈R/P⌉` | 深さ×全件（同じアプリを毎反復 re-fetch） | **最悪**。深さに比例して同じアプリを何度も取得。採用しない |
| **B: アプリ 1 回取得＋メモリ反復（推奨・v1）** | `⌈R/P⌉`（アプリごと1回） | 全件 1 回 | 再帰項が参照するアプリを**最初に 1 回だけ取得**して実体化し、以降の反復はメモリ内。**深さに依存しない**。一時テーブル/CTE 実体化（B51/B52 で堅牢化）と同じ。R が maxRecords 内である必要 |
| **C: 深さごとの targeted `IN` クエリ** | `Σᵢ ⌈Fᵢ/min(P,L)⌉`（深さ×frontier ページ） | frontier 分のみ（少ない） | 各深さで `WHERE key IN (frontier)` を発行。**取得データは最小**だが**往復（API 回数）が増える**。frontier が小さい木（BOM 等）で有利・大規模/広ファンアウトで往復増 |

### 5.2 判断

- **v1 は戦略 B（アプリ 1 回取得＋メモリ反復）を基本**とする。理由: ①API 回数が**深さに依存せず** `Σ アプリごと ⌈R/P⌉` に収まり見積り可能 ②B51/B52 で堅牢化した実体化 CTE/JOIN 資産をそのまま反復で回せる ③実装が単純。制約: 参照アプリ全件が `maxRecords` 内に収まること（超過は fail-closed）。
- **戦略 B の目安件数**: 参照アプリのソース件数 `R` が `maxRecords` 内であること。**エンジン既定 `maxRecords = 10,000`**（`fetchAll` の `MAX_RECORDS_DEFAULT`。CLI/MCP 既定は 500・`--max-records`/`maxRecords` で変更）。→ **既定では「~1 万件」が目安**。ただしハードキャップではなく、`maxRecords` を上げれば 1 万件超も取得可能（`fetchAll` は offset 1 万到達でカーソル方式へ切替）で、実質的な制約は**メモリと時間**。API 回数は `⌈R/P⌉`（R=1 万・P=500 で 20 回、R=10 万で 200 回＋カーソル）。
  - メモリは `R`（実体化したアプリ）＋**蓄積される再帰結果**。結果集合は §4 の必須境界（深さ/総行）で別途上限が付く。
  - 再帰項が**複数アプリを参照**する場合は、**各アプリが個別に `maxRecords` 内**である必要がある。
  - **1 万件を大きく超える／全件取得が非現実的**なアプリは戦略 C（深さごと `IN` で frontier 分だけ取得）へ。
- **大規模アプリ（全件取得が非現実的）向けに戦略 C を将来オプション**とする。API 往復と取得量のトレードオフ（往復多いが取得少ない）。frontier が小さいケースで有効。
- **戦略 A は不採用**（同一アプリの深さ回 re-fetch は無駄）。

### 5.3 他の観点

- **並列/レート**: 取得は既存の `--fetch-parallel`（1〜10）・`--max-concurrent`（プロセス全体）に従う。反復間は逐次（前反復の frontier に依存）だが、各反復内の取得は並列化可能。
- **打ち切り（10 万件）**: 再帰項の取得は通常クエリ（`=`/`in`）が主で KLIKE 系の 10 万件打ち切りとは別。ただし戦略 B は「全件取得」なので `maxRecords` 上限に達すれば fail-closed（不完全な母集合で反復しない）。これは終了保証（§4）と同じく**正しさのための fail-closed**。
- **B40 との比較**: B40（プロパティグラフ）も同じ関連アプリをクライアント側で読むため、**API 発行回数の本質は同等**（同じデータを読む）。差は構文と評価器であって取得回数ではない。したがって「API コスト」は方向判断（B53 vs B40）の決め手にはならず、**両者とも戦略 B（アプリ実体化）＋境界 fail-closed が前提**になる。

### 5.4 EXPLAIN への反映

EXPLAIN で **①各参照アプリの取得回数見積り（`⌈R/P⌉`）②反復の深さ上限③戦略（B: 実体化 / C: 深さ別 IN）④総行/深さ境界と fail-closed** を表示し、実行前に API コストと終了性を可視化する（実件数は事前に読めないため見積りと境界を示す）。

## 6. スコープ案（段階）

- **Phase 1（MVP）**: `WITH RECURSIVE name AS (seed UNION ALL 再帰項)` の**単一再帰 CTE**＋**必須の深さ/行境界**＋**CYCLE の最小形（循環打ち切り＋mark 列）**。単一等値 JOIN で自己参照。EXPLAIN に反復・境界・fail-closed を表示。
- **Phase 2**: 複数再帰 CTE・`UNION`（重複排除）・CYCLE の path 列・`SEARCH` 句（順序）等。
