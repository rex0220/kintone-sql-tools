# B53 — WITH RECURSIVE / CYCLE 句（再帰 CTE）評価

- 起票日: 2026-07-21
- ステータス: **起票（評価・仕様前・優先度未確定）**
- 種別: 改善（新機能・大型候補）
- 効果種別: 機能
- 関連: **B40 プロパティグラフ**（同じ用途＝到達可能性/循環検出の別アプローチ・[ksql_property_graph_evaluation.md](ksql_property_graph_evaluation.md)）／B51・B52（CTE 経路の正しさ修正・v3.11.0 で実体化 CTE が堅牢化）

## 1. 提案

SQL 標準の **`WITH RECURSIVE`（再帰 CTE・SQL:1999）** と **`CYCLE` 句（循環検出・SQL:2016）** を kSQL に導入する候補。

```sql
-- 例: 部品表（BOM）の親→子を再帰展開（到達可能性）
WITH RECURSIVE 部品展開 AS (
  SELECT 部品ID, 子部品ID, 1 AS 深さ FROM APP100 WHERE 部品ID = 'P001'   -- seed（非再帰項）
  UNION ALL
  SELECT c.部品ID, c.子部品ID, r.深さ + 1                                 -- 再帰項（自己参照）
  FROM APP100 c JOIN 部品展開 r ON c.部品ID = r.子部品ID
)
CYCLE 部品ID SET is_cycle TO 'Y' DEFAULT 'N'                              -- 循環検出（無限ループ防止）
SELECT * FROM 部品展開;
```

## 2. 何を解決するか（固有価値）

現状 kSQL は**再帰・推移閉包を表現できない**（言語リファレンス「再帰 CTE 非対応」・§22）。JOIN は単一等値・派生テーブルなし・再帰 CTE なしのため、次が**不能 or 極めて冗長**:

- **階層の展開**: 組織図、部品表（BOM）、カテゴリツリーの親↔子の全展開。
- **可変長経路・到達可能性**: 「A から到達できる全ノード」「N ホップ以内」。
- **循環検出**: 送金経路のループ（マネロン）、参照の循環。

関係が濃い kintone（アプリ間の外部キー参照が多い）で「**不能→可能**」を作る点は B40 と同じ。

## 3. B40（プロパティグラフ）との関係（重要）

**B53 と B40 は同じ用途（到達可能性・循環検出・可変長経路）に対する別アプローチ**であり、**どちらを採るかの判断が必要**（両方は過剰）。

| 観点 | B53 WITH RECURSIVE | B40 プロパティグラフ（GRAPH_TABLE MATCH） |
|---|---|---|
| 標準 | SQL:1999/2016・**広く普及**（PostgreSQL/Oracle/SQL Server/MySQL8） | SQL:2023・**新しい**（Oracle 先行） |
| 学習コスト | SQL 利用者に馴染み・**低め** | 新 MATCH 副言語・高め |
| 既存資産の再利用 | **既存 CTE 機構の拡張**（B51/B52 で実体化 CTE が堅牢化済み）＋UNION ALL | 新 FROM ソース＋型付き副言語＋パターン評価器（新規大） |
| 表現 | 一般の再帰関係（階層・グラフ両方） | グラフパターン（ノード/エッジ）に特化・可読性高 |
| 循環検出 | **CYCLE 句**（明示・標準） | パターンで `->(a)` 戻り＋境界 |
| 実装規模 | 反復 fixpoint 実行エンジン新設（中〜大） | 最大級（B40 評価: 19〜31 人日） |

**示唆**: B53 は **SQL 標準で馴染みがあり、v3.11.0 で堅牢化した CTE 機構を土台にできる**分、B40 より学習コスト・実装の見通しが良い可能性がある。B40 の看板価値（可変長・到達可能性・循環検出）を、より標準的な構文で提供できる。**着手前に B40 と併せて「どちらの方向か」を判断する**。

## 4. 実現可能性・技術課題

kintone にサーバ側再帰はない（他の全機能同様クライアント側）。再帰 CTE は**反復実行**になる:

1. **seed（非再帰項）を実行** → 作業集合。
2. **再帰項を作業集合に対して繰り返し適用**（自己参照）し、新規行を蓄積 → 新規行が出なくなる（fixpoint）まで。
3. 各反復＝クライアント側 fetch/JOIN。

主要課題:

- **終了保証（最重要）**: 循環データで CYCLE も深さ上限も無いと**無限ループ**。→ **CYCLE 句 or 最大深さ/最大行の境界を必須にし、超過は fail-closed でエラー**（B40 と同じ「爆発は有界 fail-closed」）。10 万件打ち切り（KLIKE 系）と同じ思想。
- **性能**: 各反復が fetch/JOIN のため、深さ N で N ラウンド。関係が濃いと行が急増。**境界（深さ・総行数）と EXPLAIN での可視化**が要る。実件数は事前に読めない（B40 と同じ制約）。
- **UNION ALL / 自己参照のパース**: 再帰項が CTE 自身を参照する AST・非再帰項/再帰項の分離・列数/型の整合。
- **CYCLE 句の範囲**: SQL:2016 の完全形（`CYCLE col SET mark TO x DEFAULT y USING path`）は複雑。v1 は**「循環を検出したら打ち切る」最小サブセット**（mark 列生成・path 列は任意）で十分か検討。
- **実行エンジン**: 現状 CTE は単一パス実体化（B51/B52 で堅牢化）。再帰は**反復 fixpoint**の新経路。既存の実体化・JOIN・UNION 資産を反復で回す設計。
- **LAPP/プラグイン等の面**: B40 同様、面ごとの制約（プラグインの取得上限・打ち切り検出）を確認。

## 5. スコープ案（段階）

- **Phase 1（MVP）**: `WITH RECURSIVE name AS (seed UNION ALL 再帰項)` の**単一再帰 CTE**＋**必須の深さ/行境界**＋**CYCLE の最小形（循環打ち切り＋mark 列）**。単一等値 JOIN で自己参照。EXPLAIN に反復・境界・fail-closed を表示。
- **Phase 2**: 複数再帰 CTE・`UNION`（重複排除）・CYCLE の path 列・`SEARCH` 句（順序）等。
