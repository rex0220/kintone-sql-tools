## 1. 問題の事実（起点・変更しない）

1. kSQL の JOIN は**空キーどうしが一致する**（B153 で意図的にそう修正した。単一表・CTE・一時テーブル共通）。
2. 階層データの定番設計に「ルート＝親コード空」がある。再帰項の JOIN
   （例: `b.parent_code = e.item_code`）で frontier に空値が 1 つ入ると、
   **毎反復、空親の全行（＝ルート群）と結合して森全体を再展開**する。
3. 帰結は 2 種類あり、両方を規定する必要がある:
   - 展開が膨らんで 3 絶対上限に当たる＝**止まるが、エラーの顔が無関係**（「上限超過」であって「空キー」ではない）。
   - **小さいデータでは上限に当たらず、静かに誤った集計が返る**。こちらが重い
     （B119-B122 と同族の「静かに間違う」）。

## 2. 検討する案（すべて帰結を書き、1 つを推奨する）

- **案 a**: 再帰項の JOIN キーに限り「空キーは一致しない」を既定にする。
  ＝B153 の決定を再帰スコープで反転する。単一表 JOIN と挙動が割れることの説明費用、
  「空で終端」という自然な停止（PG の NULL 非一致と同型）が得られる利点、
  逆に「空を意図的にキーとして使う」データを黙って落とす危険を評価する。
- **案 b**: 意味論は現行のまま、**planning/実行時警告**（B140 と同じ「結果の一部としての warnings」）。
  source 実体化後に JOIN キー列の空値有無は検査できるはず＝実行前に出せるかも評価する。
- **案 c**: frontier または source の再帰 JOIN キーに空値を検出した時点で **fail-closed エラー**。
  正しさは守るが、空キーが「終端の表現」として実在するデータを一律に止める費用を評価する。
- **案 d**: 何もしない＋3 絶対上限の超過エラー文言に空キーのヒントを足す。
  §1-3 の「静かに間違う」側を防げない事実を明記する。

評価には次を含める: ①seed 側の空キー（`WHERE` で除外可能）と再帰項側の区別
②`CYCLE` 列が空値のときの path 判定への影響 ③B153 との整合の説明方法
④各案の受入テスト形（空キールート・空キー葉・空キーを正当に使う対照）
⑤EXPLAIN/警告の表示。
