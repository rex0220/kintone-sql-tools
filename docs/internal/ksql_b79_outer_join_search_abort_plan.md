# B79 実装計画 — 外部結合＋検索打ち切りを fail-closed にする

- 作成: 2026-07-27（Claude 起草）
- ステータス: 📝 **計画（未着手）**。実装は codex、レビューは Claude。
- 課題: [B79 issue](ksql_b79_outer_join_search_abort_issue.md)（オーナー決定＝案 A）
- リリース: **B80 と同一リリース**

## 0. 前提（オーナー決定）

**外部結合で `searchAborted` が起きたら fail-closed（エラー）とする。**
判断基準は B78 と同じ＝**現在成功して見えるクエリは実際には誤った値を返しているので、
エラー化しても正しい結果を失わない**。

## 0.1 【要判断】案 B（警告文の是正）は不要になる

課題文書 §4 は「案 B の警告文是正はいずれの案でも必要」としていたが、
**これは A / B / C を代替案として比較していたときの記述**である。
**案 A を実装すると前提が変わる。**

### 現行の警告文

```
検索が 10 万件で打ち切られ、結果が欠落した可能性があります。
```

### 案 A 実装後に残る警告経路

| ケース | 打ち切り時の性質 | 「欠落」という表現 |
|---|---|---|
| 外部結合 | **エラーになる**（警告経路から消える） | — |
| INNER JOIN | 行の欠落（返る行は正しい） | **正確** |
| 単一表 | 行の欠落 | **正確** |

**誤値を返す経路が消えるため、警告文は正確になる。**
したがって**案 B の是正は必須ではなくなる**。

### 推奨

**案 B は実施しない。** 理由:

- 正確な文言を「より丁寧に」書き換えるのは B79 の目的ではない
- 集計（`SUM` 等）が部分データで計算される点も「結果が欠落」から利用者が推測できる
- 変更しないほうが、本リリースのメッセージ（「外部結合の誤値を止めた」）が明確になる

**ただしオーナー決定は「案 B も併せて実施」だった。**
本計画は案 B を**スコープ外**として起草しているので、
**案 B を実施するか否かの判断をお願いしたい。**
実施する場合は、何を伝える文言にするかを決めてから着手する。

## 1. スコープ

### 対象

- **文中に外部結合（`LEFT JOIN` / `RIGHT JOIN`）を含む SELECT 系文**で
  `searchAborted: true` を受け取ったら `SearchAbortedError` を投げる

### 対象外（挙動を変えない）

- **INNER JOIN のみの文**（行の欠落であり警告で足りる）
- **単一表**（同上）
- DML（既に fail-closed）
- B72 の local 相対日付経路（既に fail-closed）
- **案 B の警告文是正**（§0.1・要判断）

## 2. 実装方針

### 2.1 判定は「外部結合の有無」に直接紐づける

現行の fail-closed 判定は**文の種別**で行っている。

```ts
// src/execute.ts:734 付近（単文）
const guardedClient = wrapClientWithSearchAbort(
  countedClient, collector, !isSelectLikeStatement(stmt)
);
// src/execute.ts:1492 付近（バッチ）も同型
```

ここに**「文が外部結合を含むか」**を加える。

> **B76 Phase A の失敗を繰り返さないこと。**
> B76 は `"joinPlan" in pushdownPlan` という **plan オブジェクトの存在**で判定したため、
> 押し下げが1件も起きていないクエリまでエラーにした。
> **判定は AST 上の外部結合の有無という意味的な条件に直接紐づけること。**

### 2.2 スコープは「文全体」

**トップレベルの `joins` だけを見てはいけない。**
CTE 本体・一時テーブル source・`UNION` の枝・入れ子 SELECT の中に外部結合があれば、
そこで打ち切りが起きたときに同じ誤値が生じる。

**AST を再帰的に走査して外部結合の有無を判定すること。**
既存の walker（例: `relativeDatePushdownGuard.ts` の `collectStatement`）の
走査パターンが参考になる。

### 2.3 既存の fail-closed 経路と競合させない

`wrapClientWithSearchAbort` は複数箇所で呼ばれる（単文・バッチ・B72 local）。
**二重ラップや、既に fail-closed の経路を warning へ緩めることがないよう確認すること。**

## 3. Step

| Step | 内容 | 見積 |
|---|---|---:|
| 1 | 外部結合検出（AST 再帰走査）＋ fail-closed 判定への配線＋単体テスト。**同一 merge** | 0.5〜0.75 人日 |
| 2 | 回帰テスト（下記 §4）・EXPLAIN 表示の確認 | 0.25〜0.5 人日 |
| 3 | docs・CHANGELOG（B80 と合わせて1リリース分） | B80 と共有 |

**Step 1 は検出と配線を分けない。**検出だけ入れて配線しないと、
フラグが黙って無視される状態になる（B75 の `inheritedForbidden` 回帰）。

## 4. 受入条件

| # | 条件 |
|---|---|
| 1 | **`LEFT JOIN` ＋ 打ち切り → `SearchAbortedError`**（部分 rows を返さない） |
| 2 | **`RIGHT JOIN` ＋ 打ち切り → 同上** |
| 3 | **`INNER JOIN` ＋ 打ち切り → 従来どおり警告＋部分結果**（変更なし） |
| 4 | **単一表 ＋ 打ち切り → 従来どおり警告＋部分結果**（変更なし） |
| 5 | **CTE 本体 / 一時テーブル source / `UNION` 枝 / 入れ子 SELECT の外部結合**でも fail-closed |
| 6 | 打ち切りが起きない外部結合クエリは**従来どおり正常に結果を返す**（過剰拒否しない） |
| 7 | DML・B72 local の既存 fail-closed に回帰なし |
| 8 | `npm test` 全件 green・snapshot 差分は意図したものだけ |

**6 が重要。** 外部結合というだけでエラーにしてはいけない。
**打ち切りが実際に起きたときだけ**である。

## 5. テストの必須要件

- **モックは実際の応答形状を再現**すること（B71 の教訓）
- **要求された `fields` だけを返すモック**
- **`searchAborted: true` を返すのは特定のアプリだけ**にしたケースも用意し、
  どちら側の打ち切りでも fail-closed になることを確認する

## 6. 見積もり

**0.75〜1.25 人日**（Step 1: 0.5〜0.75、Step 2: 0.25〜0.5）。
docs・CHANGELOG・リリース準備は B80 と共有。

## 7. 過去の教訓（実装時に必ず反映）

- **B76**: 「plan の存在」のような間接的条件で判定しない。**意味的な条件に直接紐づける**
- **B76**: INNER のみ fail-closed にして危険度と逆向きになり撤回した。**対象は外部結合のみ**
- **B75**: フラグや引数が黙って無視される状態を作らない
- **B72**: 根拠を書けない制約を足さない。**打ち切りが起きていないのに拒否しない**
- **B71**: モックは実際の応答形状を再現する
