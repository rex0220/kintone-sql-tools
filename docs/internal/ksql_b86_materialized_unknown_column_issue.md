# B86 実体化ソースで存在しない列参照が検証されず、LIKE で全件が返る

- 起票: 2026-07-28
- ステータス: 📝 **評価・起票（優先 高／silent wrong result）**。未着手。
- 出典: オーナーによる検証 2026-07-28
- 関連: [B78 ユーザー系 `=` が黙って0件](ksql_b78_user_field_loginuser_issue.md) / [B79 外部結合の誤値](ksql_b79_outer_join_search_abort_issue.md) / [where-rhs-field-like-fix（v1.14.0）]

## 1. 事象

```sql
WITH A AS (SHOW APPS)
SELECT * FROM A
WHERE アプリ名 LIKE 顧客        -- 引用符なし
```

**977 件（全件）が返る。**エラーも警告も出ない。

正しく書けば動く。

| SQL | 結果 |
|---|---:|
| `WHERE アプリ名 LIKE '顧客'`（引用符あり） | **44 件** ✅ |
| `WHERE アプリ名 LIKE 顧客`（引用符なし） | **977 件**（全件） ❌ |

## 2. 原因＝実体化ソースで列の実在が検証されない

**裸の識別子は列参照として解釈される**（v1.14.0 で右辺フィールド比較を実装済み。仕様どおり）。
実在列を指定すれば正しく列同士の比較になる。

```sql
WHERE アプリ名 LIKE 説明   -- 690 件。列同士の LIKE として正常に動作
```

問題は**存在しない列を指定したときに黙って空文字へ解決される**ことである。

| 演算子 | 存在しない列を右辺に置いた結果 |
|---|---|
| `LIKE` | **全件一致**（空パターンは任意の文字列に含まれる） |
| `=` | **0 件**（空文字との等値） |

**`LIKE` が最悪の方向**である。`=` は取りこぼす（0 件）が、`LIKE` は**絞ったつもりで全件返す**。

## 3. スコープ＝物理アプリは守られているが実体化ソースは素通し

| ソース | 存在しない列の参照 |
|---|---|
| **物理アプリ** | ✅ **拒否**＝`ArgumentError: unknown field code(s): ZZZ存在しない列 (APP4147)` |
| CTE（`SHOW APPS` 由来） | ❌ 素通し |
| CTE（物理アプリ由来） | ❌ 素通し |
| 一時テーブル | ❌ 素通し |

**実体化された結果は列名の集合が確定している**（`columns` を持つ）ので、
**検証できないのではなく、検証していない**。

実測（`APP4147` の 18 件を CTE / 一時テーブルへ実体化し、存在しない列で `LIKE`）:

```
CTE over APP    : 18 件（全件・対照と同じ）
一時テーブル     : 18 件（全件・対照と同じ）
一時テーブル対照 : 18 件
```

## 4. 影響

**silent wrong result。**利用者は「絞り込んだ」と思っているのに全件を得る。

- **引用符の付け忘れという最も起きやすいミス**で発生する
- **エラーも警告も出ない**
- 件数が多いほど気づきにくい（977 件のうち該当 44 件でも「多いな」で済ませてしまう）
- **ダッシュボードや集計に載せると、母集団が違うまま数字が出る**

B78（ユーザー系 `=` が黙って 0 件）・B79（外部結合で誤った値）と同系列で、
このプロジェクトが一貫して最優先で潰してきた類である。

**物理アプリでは既に拒否している**ため、**面ごとの不整合**でもある。
同じ SQL が、ソースが物理アプリか実体化結果かで**エラーになったりならなかったりする**。

## 5. 対応案

### 5.1 案 A（推奨）— 実体化ソースでも列の実在を検証する

CTE / 一時テーブル / `SHOW APPS` / `DESCRIBE` の結果は**列名の集合が確定している**。
物理アプリと同じく `unknown field code(s)` で**取得前に拒否**する。

- **物理アプリと同じ挙動に揃う**＝面ごとの不整合が消える
- **fail-closed** の設計思想と一致する

**破壊的変更**である。現在「たまたま動いていた」クエリがエラーになる。
ただし**そのクエリは誤った結果を返していた**ので、B78・B79 と同じ判断基準で正当化できる。

### 5.2 案 B — 空文字への解決をやめる

存在しない列を空文字にせず、**照合不能**として扱う。
ただし「存在しない列＝空」は他の経路でも前提になっている可能性があり、**影響範囲が読めない**。
案 A のほうが局所的である。

### 5.3 検討事項

- **サブクエリ・`UNION` の枝**でも同じか要確認
- **列別名**（`SELECT x AS y`）を使った場合の解決順序
- 物理アプリ側の検証が**どこで行われているか**を確認し、同じ機構を実体化ソースへ適用できるか

## 7. 優先度の根拠

**引用符の付け忘れという最頻のミスが、黙って全件を返す形で顕在化する。**
物理アプリでは既に守られているので、**実装の穴であって設計判断ではない**。
