# B86 実体化ソースで存在しない列参照が検証されず、LIKE で全件が返る

- 起票: 2026-07-28
- ステータス: ✅ **リリース済み（v3.30.0・2026-07-28）**。破壊的変更（誤った結果を返していたもの）。デプロイ済み MCP で実機確認済み。
- 出典: オーナーによる検証 2026-07-28
- 関連: [B78 ユーザー系 `=` が黙って0件](ksql_b78_user_field_loginuser_issue.md) / [B79 外部結合の誤値](ksql_b79_outer_join_search_abort_issue.md) / [where-rhs-field-like-fix（v1.14.0）]

## 1. 事象

```sql
WITH A AS (SHOW APPS)
SELECT * FROM A
WHERE アプリ名 LIKE 顧客        -- 引用符なし
```

**977 件（全件）が返る。**エラーも警告も出ない。

正しく書けば動く。

| SQL | 結果 |
|---|---:|
| `WHERE アプリ名 LIKE '顧客'`（引用符あり） | **44 件** ✅ |
| `WHERE アプリ名 LIKE 顧客`（引用符なし） | **977 件**（全件） ❌ |

## 2. 原因＝実体化ソースで列の実在が検証されない

**裸の識別子は列参照として解釈される**（v1.14.0 で右辺フィールド比較を実装済み。仕様どおり）。
実在列を指定すれば正しく列同士の比較になる。

```sql
WHERE アプリ名 LIKE 説明   -- 690 件。列同士の LIKE として正常に動作
```

問題は**存在しない列を指定したときに黙って空文字へ解決される**ことである。

| 演算子 | 存在しない列を右辺に置いた結果 |
|---|---|
| `LIKE` | **全件一致**（空パターンは任意の文字列に含まれる） |
| `=` | **0 件**（空文字との等値） |

**`LIKE` が最悪の方向**である。`=` は取りこぼす（0 件）が、`LIKE` は**絞ったつもりで全件返す**。

## 3. スコープ＝物理アプリは守られているが実体化ソースは素通し

| ソース | 存在しない列の参照 |
|---|---|
| **物理アプリ** | ✅ **拒否**＝`ArgumentError: unknown field code(s): ZZZ存在しない列 (APP4147)` |
| CTE（`SHOW APPS` 由来） | ❌ 素通し |
| CTE（物理アプリ由来） | ❌ 素通し |
| 一時テーブル | ❌ 素通し |

**実体化された結果は列名の集合が確定している**（`columns` を持つ）ので、
**検証できないのではなく、検証していない**。

実測（`APP4147` の 18 件を CTE / 一時テーブルへ実体化し、存在しない列で `LIKE`）:

```
CTE over APP    : 18 件（全件・対照と同じ）
一時テーブル     : 18 件（全件・対照と同じ）
一時テーブル対照 : 18 件
```

## 4. 影響

**silent wrong result。**利用者は「絞り込んだ」と思っているのに全件を得る。

- **引用符の付け忘れという最も起きやすいミス**で発生する
- **エラーも警告も出ない**
- 件数が多いほど気づきにくい（977 件のうち該当 44 件でも「多いな」で済ませてしまう）
- **ダッシュボードや集計に載せると、母集団が違うまま数字が出る**

B78（ユーザー系 `=` が黙って 0 件）・B79（外部結合で誤った値）と同系列で、
このプロジェクトが一貫して最優先で潰してきた類である。

**物理アプリでは既に拒否している**ため、**面ごとの不整合**でもある。
同じ SQL が、ソースが物理アプリか実体化結果かで**エラーになったりならなかったりする**。

## 5. 対応案

### 5.1 案 A（推奨）— 実体化ソースでも列の実在を検証する

CTE / 一時テーブル / `SHOW APPS` / `DESCRIBE` の結果は**列名の集合が確定している**。
物理アプリと同じく `unknown field code(s)` で**取得前に拒否**する。

- **物理アプリと同じ挙動に揃う**＝面ごとの不整合が消える
- **fail-closed** の設計思想と一致する

**破壊的変更**である。現在「たまたま動いていた」クエリがエラーになる。
ただし**そのクエリは誤った結果を返していた**ので、B78・B79 と同じ判断基準で正当化できる。

### 5.2 案 B — 空文字への解決をやめる

存在しない列を空文字にせず、**照合不能**として扱う。
ただし「存在しない列＝空」は他の経路でも前提になっている可能性があり、**影響範囲が読めない**。
案 A のほうが局所的である。

### 5.3 検討事項

- **サブクエリ・`UNION` の枝**でも同じか要確認
- **列別名**（`SELECT x AS y`）を使った場合の解決順序
- 物理アプリ側の検証が**どこで行われているか**を確認し、同じ機構を実体化ソースへ適用できるか

## 6. 規模

- 調査（検証位置の特定・スコープ確定）: 0.25〜0.5 人日
- 実装（案 A）: 0.5〜1.0 人日
- 破壊的変更の移行案内（CHANGELOG・言語リファレンス・`release/README.txt` の3箇所）: 0.25

**合計 1.0〜1.75 人日。SemVer=minor（破壊的変更を含むが、誤った結果を返していたもの）。**

## 7. 優先度の根拠

**引用符の付け忘れという最頻のミスが、黙って全件を返す形で顕在化する。**
物理アプリでは既に守られているので、**実装の穴であって設計判断ではない**。

## 8. 【2026-07-28 調査】想定より深刻だった＝**書き込みまで届く**

### 8.1 silent wrong write を実測で確認

起票時は**読み取りの誤り**として扱っていたが、調査で**書き込みに届く経路**が見つかった。
モッククライアントで POST 呼び出しを観測して確認した（実書き込みはしていない）。

```sql
CREATE TEMP TABLE #t AS SELECT 件名 FROM APP100;
INSERT INTO APP100 (件名) SELECT 存在しない列 FROM #t
```

```
ok=true / statuses=success,success / POST 1 回
records: [{"件名":{"value":""}}, {"件名":{"value":""}}]
```

**成功し、空文字レコードを実際に書き込む。**エラーも警告も出ない。
**利用者は列をコピーしたつもりで、空白を書き込んでいる。**

> **B79（誤った値を読む）より深刻である。**読みは再実行できるが、**書き込みは戻せない**。

### 8.2 混在 JOIN では物理アプリ側の検証も迂回する

実体化ソースと物理アプリを JOIN すると、**物理アプリ側の不存在列検証まで効かなくなる**。
穴は起票時に把握していたより**広い**。

### 8.3 スコープ実測（codex）

CTE（`SHOW APPS` / `DESCRIBE` / 物理アプリ由来）・一時テーブル・**各種サブクエリ**・
**`UNION` 両枝**・**列別名**・**混在 JOIN** で素通しを確認。
`FROM (SELECT ...)` 派生表は**構文未対応**のため対象外。

### 8.4 検証位置

**`executeQueryWithCte()` の実行ディスパッチ前**が最適。
実体化済み `columns` が利用でき、**サブクエリ・UNION 枝・物理 records GET・DML mutation より前**に拒否できる。

### 8.5 `=` も対象に含める

**0 件は正しい空集合ではなく、不存在列を空文字として評価した誤結果**である。
B78 / B79 の「**エラー化しても正しい結果を失わない**」基準がそのまま使える。

### 8.6 既存テストへの影響は 0 件（静的監査）

既にエラーを期待する materialized JOIN-key テストが 2 件あり、**非回帰対象**として維持する。

### 8.7 残る限界＝`rows=[] && columns=[]`

**0 行かつ列が復元できない状態**では、`x` と `missing` を区別できない。
R1 は **JOIN なしの 0 行読み出しに限定して既存挙動を維持**し、
**JOIN 利用は取得前に schema-unavailable error** とする。
完全解消には **B2 の schema 復元拡張**が別途必要（追加 0.75〜1.5 人日）。
→ **[B88](ksql_b88_empty_wildcard_schema_restore_issue.md) として正式起票**（2026-07-28）。列順は実測で解消済みだが **[B87](ksql_b87_field_metadata_cache_staleness_issue.md) が前提条件**。
→ **[B88] で解消済み（未リリース・2026-07-28）**。空の実体化テーブルを JOIN 入力に使う形は通るようになり、**不存在列の参照はむしろ拒否できるようになった**（従来は schema が無く素通ししていた）。

### 8.8 `defs.length === 0` の抜け道は持ち込まない

**`MaterializedTable.columns` が非空なら、mock metadata に関係なく検証する。**
物理側の skip をコピーすると、**検証があるつもりで無い**状態を作る。

### 8.9 見積もりの改定

起票時 1.0〜1.75 人日 → **2.25〜3.25 人日**（`columns=[]` の完全復元まで含めるなら さらに 0.75〜1.5）。
**書き込み経路と混在 JOIN が加わったため。**

## 9. 【実装レビュー・2026-07-28】完了

### 独立検証（envelope の中身で判定）

| 形 | 結果 | POST |
|---|---|---:|
| `LIKE 不存在列` | `unknown field code(s): 存在しない (#t)` | **0** |
| `= 不存在列` | 同上 | **0** |
| **`INSERT ... SELECT 不存在列`** | **拒否** | **0** |
| 混在 JOIN・**物理側** | `... (APP200)` | **0** |
| 正しい形 | 成功 | — |

**エラーが発生源を名指しする**（`#t` / `APP200`）ので、どのソースの列が無いかがすぐ分かる。
**混在 JOIN で物理側の検証も復活**している。

> `executeBatch` は throw せず envelope を返すため、**最初のレビューで判定を誤った**。
> `ok` と文別 status を見て判定し直している。

### 仕様との差＝既存テスト影響は 0 件ではなかった

仕様の静的監査では「既存テスト影響 0 件」だったが、**実際は 1 件あった**。
空 temp の `SELECT *, extra` を**成功として固定していた**テストで、
保存列が `a,b` なのに `extra` を許す **B86 対象そのもの**だった。error 期待へ更新済み。

**テストが誤った挙動を正しいものとして固定していた**例であり、
静的監査だけでは見つからない。**実行して初めて分かる**類である。
