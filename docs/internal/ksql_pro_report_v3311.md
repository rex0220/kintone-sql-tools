## 1. ⚠ v3.31.0 には回帰があります。**v3.31.1 を取り込んでください**

**v3.31.0 では、変数を算術に使うバッチを `explainQuery` に通すと必ず失敗していました。**

```
SET @total = (SELECT SUM(売上) FROM #g);
SELECT (売上 * 100) / @total AS 構成比 FROM #g
→ ArgumentError: variable @total is not numeric and cannot be used in arithmetic.
```

**ご依頼①（`explainQuery` のバッチ対応）とご依頼②（変数の直接算術）が噛み合った結果**です。

- 設定画面は **`explainQuery` で構文チェック**（①で複文対応したばかり）
- そこへ流すのは **構成比のバッチ**（②で書けるようにしたばかり）

**両方を同時にお使いになる、まさにその形で必ずエラーになります。**
**v3.30.0 まで動いていた `ROUND(算術式, ...)` の形も巻き添え**になっていました。

**v3.31.1 で修正済みです。v3.31.0 は取り込まずに飛ばしてください。**

### なぜ起きたか

`EXPLAIN` は変数を評価しないため、**名前をプレースホルダーとして保持**します。
②で追加した「非数値ならエラー」の検査が、**それを文字列変数と誤認**していました。

②のレビューで「変数は計画生成の前に解決される」ことは確認していたのですが、
**そこで渡されるのが実値ではなくプレースホルダーである**ところまで見ていませんでした。
**受入条件に `EXPLAIN` 経路が 1 件もありませんでした。**

**リリース後の実機確認で見つけました。**していなければ、そちらが最初に踏んでいたことになります。
検証項目の抜けで、申し訳ありません。

## 2. ①`explainQuery` のバッチ対応

**受理する文の集合を `runBatch` と揃えました。**
`CREATE TEMP TABLE` / `SET` / `DECLARE` / `VALIDATE` / `SHOW APPS` / `DESCRIBE` / `ASSERT` を
含むバッチが検証できます。**単文の `VALIDATE APPn` も通ります。**

複文の計画は `lines` に `[n] TYPE` の見出し付きで返します。**単文の出力は変わりません。**
公開型も変えていません。

### 実装中に、こちらの既存の穴が 2 つ見つかりました

**(a) 静的検証エラーに文の情報が載っていませんでした。**

前回の返信で「エラー時の文の特定は既に手当て済み」とお伝えしましたが、**正確ではありませんでした。**
v3.29.0 で追加した文別診断は**実行時の失敗にしか届いておらず**、
**入力中の構文エラー（＝そちらが最も必要とする場面）には載っていませんでした。**

**`runBatch` でも同じ**でしたので、両方に入れています。
**静的検証エラーにも `statementIndex` と `statementType` が載ります。**

**(b) `runBatch` が `EXPLAIN UPDATE` を受理していました。**

read-only ガードが `EXPLAIN` を展開せず、外側の文型で判定していたためです。
**`EXPLAIN <DML>` を拒否するようにしました**（§4）。

## 3. ②変数の直接算術

```sql
SET @total = (SELECT SUM(売上) FROM #g);
SELECT 提案商品, 売上, (売上 * 100) / @total AS 構成比 FROM #g
```

**`ROUND()` で包む必要がなくなりました。**

**式の文法が 2 系統あり、関数引数の側だけが変数に対応していた**のが原因でした。
変数は計画・実行の前にリテラルへ解決されるため、**押し下げの判定には手を入れていません。**

---

## 4. ⚠ `EXPLAIN <DML>` を拒否します（**純加法ではありません**）

**`runBatch` が `EXPLAIN UPDATE` / `EXPLAIN DELETE` / `EXPLAIN INSERT` / `EXPLAIN UPSERT` を
受理していたのを拒否するようにしました。**受理範囲が 1 形だけ狭まります。

**`EXPLAIN SELECT` は従来どおり通ります。**

そう判断した理由です。

- **engine ライブラリは read-only が契約**で、read-only API で DML の計画を出せること自体が
  意図されていませんでした
- **`EXPLAIN` は計画のみで書き込みは起きない**ため、**誤った結果を得ていた方はいません**
- **`explainQuery` は元から拒否**しており、そちらが意図された姿でした

read-only ライブラリで DML を explain される使い方は無いと見込んでいますが、
**該当があればお知らせください。**

---

## 5. ⚠ 非数値の変数を算術に使うと停止します（**ご依頼の範囲を超えます**）

**文字列の変数を算術に使うと `ArgumentError` で停止するようになりました。**

```
修正前: DECLARE @phase = '受注'; SELECT ROUND(売上 * 100 / @phase, 1) FROM APPn  → NaN
修正後: variable @phase is not numeric and cannot be used in arithmetic. で停止
```

**新しい直接算術だけでなく、従来から動いていた `ROUND()` などの関数経路も対象**です。
**エラーは変数名を含み、レコード取得の前に停止します。**

**ご依頼は「直接算術を許可してほしい」だけで、既存経路の挙動変更は含まれていませんでした。**
それでも揃えた理由は、**同じ誤りに 2 つの結果が生まれる**のを避けるためです。

**従来の `NaN` は正しい結果ではない**ため、エラー化によって正しい結果が失われることはありません
（`>= 5000000` や不存在列のときと同じ判断基準です）。**数値変数の結果は変わりません。**
