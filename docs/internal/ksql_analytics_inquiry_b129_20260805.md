## 2. 現状（実測 v3.47.0）

**同じ文面で 3 形とも止まります。** 違うのはトークン位置だけです。

```
> SELECT 製品名, ROUND(SUM(個数) OVER (), 1) AS a FROM APP4228
ウィンドウ関数の結果を式に含めることはできません。CTE で一度実体化してください（位置 12、トークン: 「ROUND」）

> SELECT 製品名, SUM(個数) OVER () * 2 AS a FROM APP4228
… （位置 28、トークン: 「*」）

> SELECT 製品名, CASE WHEN SUM(個数) OVER () > 0 THEN 1 ELSE 0 END AS a FROM APP4228
… （位置 12、トークン: 「CASE」）
```

**3 段にすれば通ります。** CTE でも一時テーブルでも通ることを実データで確認しました
（どちらも構成比＝牛乳 34.7% / 食パン 27.3% / トマト缶 12%）。

```sql
-- CTE 版
WITH base AS (SELECT 製品名, SUM(個数) AS 出庫量 FROM APP4228 WHERE 入出庫区分 = '出庫' GROUP BY 製品名),
     ranked AS (SELECT 製品名, 出庫量, SUM(出庫量) OVER () AS 総計 FROM base)
SELECT 製品名, 出庫量, ROUND(出庫量 * 100.0 / 総計, 1) AS 構成比 FROM ranked

-- 一時テーブル版（同じ結果）
CREATE TEMP TABLE #base AS SELECT 製品名, SUM(個数) AS 出庫量 FROM APP4228 WHERE 入出庫区分 = '出庫' GROUP BY 製品名;
CREATE TEMP TABLE #ranked AS SELECT 製品名, 出庫量, SUM(出庫量) OVER () AS 総計 FROM #base;
SELECT 製品名, 出庫量, ROUND(出庫量 * 100.0 / 総計, 1) AS 構成比 FROM #ranked
```

> **現在の診断は「CTE で一度実体化してください」と CTE だけを案内しています。**
> 一時テーブルでも同じことができるので、**既存の文面が回避策を狭く見せています。**
> 中間結果を再利用したい・検算したい・段数が増える場合は一時テーブルのほうが向きます。

## 3. 2 つの案

### 案 A: ウィンドウ結果を同一 SELECT の式で使えるようにする

```sql
-- これが書けるようになる
WITH base AS (SELECT 製品名, SUM(個数) AS 出庫量 FROM APP4228 GROUP BY 製品名)
SELECT 製品名, 出庫量, ROUND(出庫量 * 100.0 / SUM(出庫量) OVER (), 1) AS 構成比
FROM base
```

**費用は高い**です。現在の実行順は「集計 → HAVING → ウィンドウ → DISTINCT → ORDER BY」で、
**ウィンドウの後にスカラー式を評価する段がありません**。ここを足すことになり、
B125 Phase 1 で固めた契約（FULL_SCAN 強制・完全入力・型メタの伝播）に触れます。

### 案 B: 診断文に「次の一手」を足す（安い）

```
ウィンドウ関数の結果を式に含めることはできません。
総計は SUM(x) OVER () として別の列に出し、割り算は次段の CTE
（または一時テーブル）で行ってください。
```

文言だけなので**すぐ入ります**。

## 4. 聞きたいこと

### Q2. 実際に詰まったのはどの形ですか

上の 3 形（関数で包む / 算術式 / `CASE` の中）のうち、**実際に書いて止まったもの**を
教えてください。**案 B の文面は「次に何を書くか」を示すものなので、
形によって次の一手が違うなら文面を分ける必要があります。**

- 関数で包む（`ROUND(... OVER (), 1)`）→ 次の一手は「CTE で実体化してから `ROUND`」
- 算術式（`... OVER () * 2`、割り算）→ 次の一手は「総計を列に出して次段で割る」
- `CASE` の中 → 次の一手は？

### Q3. 3 段 CTE では書けない形はありますか

案 A が本当に要るのは「**回避策が存在しない**」ときです。
3 段にしても書けなかった形があれば、それが案 A の根拠になります。

### Q4. 案 B の文面はこれで伝わりますか

上の文面案（§3 案 B）を見て、**それを読んだ人が 3 段構成を書けるか**を判断してください。
足すべき情報（具体例を含めるか、`SUM(x) OVER ()` の書き方まで示すか）があれば教えてください。

### Q5. 一時テーブルは選択肢として使えていますか

現在の診断は **CTE だけ**を案内していますが、**一時テーブルでも書けます**（§2）。

- そちらでは一時テーブルを使っていますか。それとも CTE だけですか
- **診断文で両方を示すべきですか**、それとも CTE だけのほうが迷わないですか

> **関連して 1 つ制約が見つかりました。** **保存クエリ（`ksql_save_query`）は現在 1 文しか
> 受け付けない**ため、**一時テーブルを使った多段は保存クエリにできません**（CTE 一択になる）。
> これは安全のための制約ではなく実装上の暫定ガードだったので、
> **解除を [B133](ksql_b133_saved_query_batch_issue.md) として起票しました。**
> 解除されると `DECLARE @x = ...; SELECT ...` も保存クエリに持てるようになります。
> **そちらで保存クエリを多段にしたい場面はありますか。** あれば B133 の優先度を上げます。

## 5. 補足: ③（B128）を保留にした理由

依頼③で挙げていただいた「7 日移動平均」ですが、**`ROWS` の行数指定では満たせない**ことが
仕様レビューで分かりました。

- `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` は**行数**で数えます
- **同日に複数行があったり、取引の無い日があると、直近 7 行 ≠ 直近 7 日**です
- 現行のウィンドウ評価はソート後の配列 index を走査しており、日付差を見ていません

満たすには次のどちらかが要ります。

- **日次集約 CTE と組み合わせる**（1 製品 1 日 1 行にしてから `ROWS`）— 現行機能でも書けます
- **値指定 `RANGE`**（`RANGE BETWEEN INTERVAL 6 DAY PRECEDING`）を実装する — 大幅に重い

**そちらの「7 日移動平均」は、日次集約してから 7 行で足りますか。**
それとも日付範囲そのもの（取引の無い日を 0 として扱う）が必要ですか。
ここで③のスコープが変わるので、あわせて教えてください。

なお `LAG` / `LEAD`（前月比）は行数指定で素直に書けるため、
**③を `LAG` 先行に組み替える案**もあります。
