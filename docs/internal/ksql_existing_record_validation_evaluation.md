## 1. 背景・目的

**kintone のフォーム制約は過去データに効かない**（フィールド定義変更後、旧レコードは制約違反のまま残る）。参考記事の Chrome 拡張は、既存レコードの **必須・数値上下限（minValue/maxValue）・文字数（minLength/maxLength）・サブテーブル行**の違反を一括検出し、違反を CSV（レコードID/フィールド/エラー内容/現在値）で出力する。

本 B41 は、これを kSQL の機能として取り込む：**既存レコードを、①アプリの組み込み制約（フォーム定義由来）＋②カスタムチェック（B37 構文）で監査し、違反を報告する読み取り操作**。

## 2. B37 との関係（書込み時 ⇄ 既存監査）

| | B37（実装済み・v3.4.0） | B41（本評価） |
|---|---|---|
| 対象 | **書き込む行**（INSERT/UPSERT/UPDATE） | **既存レコード**（読み取り監査） |
| 目的 | 悪いデータを**入れない** | 既存の**悪いデータを見つける** |
| 検証 | 組み込み＋`CHECK`＋`#err` 隔離 | 組み込み＋`CHECK`＋違反報告 |

→ **B41 は B37 の読み取り版**。「今後をきれいに保つ（B37）＋既存の汚れを洗い出す（B41）」で対を成す。

## 3. 現状 kSQL の隙間

- **組み込み検証は「書き込む値」専用**（`validateAndNormalizeDmlValue`・[dmlValidation.ts](../../src/core/dmlValidation.ts)）。既存レコードを監査する経路がない。
- `SELECT … FROM app WHERE <違反条件>` で**カスタム条件の違反は探せる**が、**組み込み制約（必須/上下限/文字数）はフィールドごとに手書きが必要**（値を知らないと書けない＝記事の「フォーム定義から自動導出」ができない）。
- 記事の Chrome 拡張はプラグイン面のみ。kSQL 化すれば **WHERE 絞り込み・カスタムチェック・SQL 出力（CSV/JSON）・全面（CLI/MCP/プラグイン）**が乗る。

## 4. 実現性（高：既存機構の再利用度が大きい）

記事の制約は **kSQL に既に実装済み**（書込み経路で使用中）：
- `validateAndNormalizeDmlValue`（[dmlValidation.ts:50-97](../../src/core/dmlValidation.ts)）が **必須（ERR_REQUIRED）・数値上下限（ERR_RANGE_MIN/MAX）・文字数（ERR_LENGTH_MIN/MAX）・選択肢（ERR_CHOICE_INVALID）** を検証。
- `KintoneFieldInfo`（[execute.ts:160](../../src/execute.ts)）に `required/minValue/maxValue/minLength/maxLength`。
- フォーム定義は `getFieldsCached` で取得済み。B29 の数値桁検証・B37 の `CHECK` 評価器も流用可。

→ **新規部分は「既存レコードを fetch して、書込み値でなくレコード値に同じ検証をかけ、違反を報告する読み取り経路」だけ**。検証ロジック・型解決・`CHECK`・fetch は既存流用。**B37 より軽い**見込み。engine 側＝全面同一。

## 5. 設計スケッチ（v1）

```sql
-- 既存レコードを組み込み制約＋カスタムチェックで監査（読み取り・書込みなし）
VALIDATE APP4221 [ ( 金額, 顧客コード ) ]        -- 任意: 対象フィールド（省略=全フィールド）
[ WHERE 作成日時 >= '2026-01-01' ]              -- 任意: 監査対象の絞り込み
CHECK                                           -- 任意: カスタムチェック（B37 構文）
  WHEN 数値1 > 数値2 THEN '数値1 > 数値2'
[ INTO #err ];                                  -- 任意: 違反を一時テーブルへ（複文で再利用）
```

- **読み取り操作**（書込みなし）：MCP は `ksql_query`・CLI は `--allow-dml` 不要・プラグインは確認ダイアログなし（B12 VALIDATE ONLY と同じ read-only 扱い）。
- **組み込み制約は自動導出**（フォーム定義から required/min-max/length/choice）。対象フィールド省略時は全フィールド。
- **カスタムチェック**は B37 の `CHECK WHEN … THEN …`（グループ先勝ち・メッセージ補間 `||`/`CONCAT`）を既存レコードに適用。
- **出力**：違反の結果集合＝`$id`（レコード）・`$err_field`・`$err_code`・`$err_message`・**現在値**（記事の CSV 列に対応）。`INTO #err` で複文再利用、CLI は `--format csv` で記事同等の CSV 出力。
- **サブテーブル**：記事同様、サブテーブル行の違反を行番号付きで報告（v1 で対応するか要判断＝B37 はサブテーブル非対応なので整合を検討）。

## 6. 確定すべき設計論点

- **構文**：`VALIDATE <app>`（読み取り監査の新文）か、`SELECT … FROM app VALIDATE` か、`CHECK <app>` か（`VALIDATE ONLY` は DML サフィックスで別物）。B37 の `CHECK` 語との整合。
- **対象制約**：必須/数値上下限/文字数/選択肢（＝既存検証の全部）＋B29 数値桁。ユニークは kintone 側強制のため対象外か。
- **出力スキーマ**：`$id`＋`$err_field`/`$err_code`/`$err_message`＋現在値。1 レコード複数違反＝複数行（B37 と同じモデル）。
- **サブテーブル**：v1 で対応するか（記事は対応）。B37 非対応との整合・行番号表現。
- **絞り込み**：`WHERE` で監査対象を限定（大アプリの部分監査）。取得は既存 fetch（Cursor 含む）・上限は既存 maxRecords/fail-closed。
- **面**：全面 engine 側。CLI の CSV 出力で記事の運用を代替。

## 7. 実需

- **記事のとおり実需は明確**（ユーザー自身が Chrome 拡張を作成＝現実の痛み「フォーム制約が過去データに効かない」）。
- kSQL 化の追加価値＝WHERE 絞り込み・カスタムチェック（業務ルール）・SQL/CSV 出力・全面・複文で `#err` を後段利用（GROUP_CONCAT で集計等）。

## 8. 総合評価・提言

| 項目 | 評価 |
|---|---|
| 実需 | **明確**（既存ツールあり・kintone の既知の痛み） |
| 実現性 | **高**：組み込み検証・型解決・`CHECK`・fetch を**既存流用**。新規は「既存レコードへの検証適用＋出力」経路のみ |
| 実装規模 | **B37 より軽い見込み**（検証ロジックは既存・新文法と読み取り経路が主） |
| B37 との整合 | **強い**（書込み時 B37 の読み取り版・機構共有） |
| 面 | 全面 engine 側・配管不要 |

**提言**：**実装を推奨**。実需が明確で既存機構の再利用度が高く、B37 と対を成す。B40（グラフ・大規模投資・探索的需要）と対照的に、**小さく確実に価値を出せる題材**。
