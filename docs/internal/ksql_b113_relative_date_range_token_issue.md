# B113 `RELATIVE_DATE` 変数への範囲トークン（任意区間の単一変数対応）

- 起票: 2026-08-02
- ステータス: ❌ **クローズ（見送り・2026-08-02 オーナー判断）**＝理由は §4
- 出典: [Pro の相談 2026-08-02d](../../../ksql-dashboard-pro/docs/internal/kSQLエンジンへの連絡-20260802d-送付版.md)（K-6・**急ぎではない・代替手段あり**）
- 関連: [B111](ksql_b111_relative_date_variable_issue.md)（v3.39.0）

## 1. 依頼

`RELATIVE_DATE` 変数の値に**範囲トークン**（例 `DATE_RANGE('2026-07-01','2026-07-10')`）を許可し、
`WHERE 受注予定日 = @period` の単一変数形のまま任意区間を扱えるようにしてほしい。

Pro の理由＝**フィールド型に応じた境界（DATE は日付リテラル、DATETIME は日の終わりまで）を
正しく作れるのは型を知っているエンジンだけ**。Pro 側でのテキスト変換は B107 以来の
「エンジンの構文解釈を Pro で再実装しない」線引きに反するため採らない。

## 2. 実測（2026-08-02）— 前提が 1 つ成り立たない

### 2.1 kSQL に「展開機構」は無い

`= THIS_MONTH()` は **kintone へそのまま素通し**され、範囲として解釈するのは kintone 側。

```
kintone query: 受注予定日 = THIS_MONTH()
```

**kintone に範囲関数は無い**ため、`DATE_RANGE` はエンジンが**述語の形そのものを書き換える**
（`= @p` → `>= a AND < b'`）ことになる。B111 は値ノードの差し替えだったので、
**これは kSQL 側で初めての述語書き換え**であり、同じ機構には乗らない。

### 2.2 境界は「日の終わり」ではなく**半開区間**が正解（実データ 20 件・APP4149）

```
>= '2026-07-14' AND <= '2026-07-14'    → 0 件   （両端とも 0:00 ＝空区間）
>= '2026-07-14' AND <  '2026-07-15'    → 2 件   （正しい）
>= ...T00:00:00Z AND <= ...T23:59:59Z  → 2 件   （この環境では動く）
```

**半開区間は TZ を知らなくても正しくなる**——kintone が両端の日付リテラルを同じ規則で
解決するため、区間が kintone 自身の「1 日」と一致する。
RFC3339 の `T23:59:59Z` は kintone 側の TZ 解決に依存する
（別の実測で、この環境の日付リテラルは **UTC 0:00** として解決された＝
`作成日時 <= '2026-04-08'` が `2026-04-07T22:07:00Z` の 16 行を含んだ）。

### 2.3 実装上の制約 — 変数解決はメタデータ解決より前

実行計画の表示は `runtime plan timing: variables/subqueries resolved -> metadata resolved`。
**差し替え時点でフィールド型が分からない**ため、依頼の狙い（型に応じた境界）を満たすには
展開を後段へ回すか遅延させる必要がある。**B111 より作業は大きい。**

## 3. 設計メモ（再起票時の出発点）

- 配置は **`field = @var` の比較 leaf に限る**（`BETWEEN` 境界・`>=` / `!=` に範囲トークンを
  置く意味がない）。B111 の配置規則より狭い
- 展開形は **DATE = `>= a AND <= b`／DATETIME = `>= a AND < b+1日`**（§2.2）。
  RFC3339 の end-of-day は採らない
- 引数検証は B111 と同じく **API 呼び出し前の名前入りエラー**
- DML は `RELATIVE_DATE` ごと拒否の現行のままでよい（Pro も同意）

## 4. 見送りの理由（2026-08-02 オーナー判断）

- **correctness の問題は engine 変更なしで消える**＝Pro は範囲形の上端を
  「終了日の翌日」にするだけで、DATE / DATETIME を同じ書き方で扱える（§2.2）。
  依頼の動機のうち「`_to_end`（RFC3339）の使い分けが復活する」は**これで解消**する
- 残るのは**「書き方が 2 系統」という説明上の価値**で、Pro 自身も
  「急ぎではない・代替手段あり」と明記している
- 一方コストは**新機構（述語書き換え）＋フェーズ順序の変更**で、B111 より重い。
  WHERE の書き換え経路に触れるため、影響範囲も広い

**再起票の条件**＝①Pro のリリース後に「2 系統」が実際の混乱として報告されたとき
②任意区間を単一変数で扱いたい別の実需が出たとき。そのときは §3 の設計メモから始める。

## 5. 副産物（本件と独立に価値がある）

**言語リファレンスの「日時フィールドの境界」の記述を、RFC3339 から半開区間へ改める価値がある。**
v3.39.0（B111）で追記した現行の案内は誤りではないが、`T23:59:59Z` は kintone の TZ 解決に
依存する。半開区間ならその依存が消える。

**→ 2026-08-02・オーナー承認で実施済み**（`docs/ksql_language_reference.md` の
「日時フィールドの境界」を半開区間の推奨へ書き換え。RFC3339 も使える旨は残した）。
**次のリリースに同梱される。**
