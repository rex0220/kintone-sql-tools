## 1. `SELECT COUNT(*)` が 1 リクエストになりました — **取得上限を適用しません**

**ご報告の「実件数 10,228 のアプリで `COUNT(*)` が 10000 を返す」は、v3.32.0 では起きません。**

kintone REST の `totalCount` を使い、**レコードを 1 件も取得せずに件数を返します。**

```
SELECT COUNT(*) FROM APP4147     maxRecords=5  →  18（正しい総件数）
```

**レコード本体を取得しないので、`maxRecords` / `onLimitReached` を適用する理由がありません。**
そのため **`"truncate"` のままでも誤った件数は返りません。**

### 1.1 従来は往復が多く、上限を超えると失敗していました

従来は `$id` を**全件取得して数えて**いました。10 万件なら **200 回以上**の往復です。
さらに **`maxRecords` を超えると `FetchAllLimitError` で失敗**していました。

**MCP の既定 `maxRecords` は 500 なので、500 件を超えるアプリの件数は MCP から取得できませんでした。**
これも解消しています。

### 1.2 **適用されるのは「WHERE が完全に押し下がる」場合だけです**

**ここが一番大事なところです。**

kSQL は `LIKE` を JS 評価に統一しています（v2.0.0）。**そういう WHERE では kintone が返す件数と
実際の結果件数が違う**ため、**`totalCount` を使うと誤った件数になります。**

**押し下げが完全でない場合は、従来どおり全件取得します。**

```
WHERE 顧客No > 5          → 単発 GET（押し下がる）
WHERE 顧客No LIKE '%1%'   → 従来どおり全件取得（JS 評価が必要）
```

**この判定は新しく作っていません。**エンジンが以前から持っている押し下げ判定
（`EXACT_PUSHDOWN`）をそのまま使っています。**しかも実行時に確定した結果**で判断します。
計画時の見込みで決めると、実行時に候補が外れた場合に誤った件数を返すためです。

**適用外**（従来どおり全件取得）:
`GROUP BY` / `HAVING` / `DISTINCT` / window / JOIN / CTE / 一時テーブル / サブテーブル /
`LIMIT` / `OFFSET`、**`COUNT(列)`**（空セルを除外する意味なのでレコード件数とは違う）。

### 1.3 自前クライアントの扱い

**`getRecords` の応答に `totalCount` が無い、または非負整数の文字列でない場合は、
`0` と推測せず従来の全件取得へ落とします。**

engine ライブラリの型に**任意プロパティ**を足しました。純加法です。

```ts
interface ReadonlyGetRecordsParams { /* … */ totalCount?: boolean }
interface ReadonlyGetRecordsResult { /* … */ totalCount?: string }
```

**対応は任意です。**`params.totalCount === true` のときに `totalCount=true` を kintone へ渡し、
応答の `totalCount` をそのまま返していただければ、この最適化が効きます。
**渡さなくても従来どおり正しく動きます**（全件取得になるだけです）。

### 1.4 検索打ち切りは fail-closed です

kintone の検索が 10 万件で打ち切られた応答は、**`SearchAbortedError` で停止**します。
**部分集合の件数を「総件数」として返しません。**

## 2. 依頼④ — `metrics.limitReached` で打ち切りを判別できます

**ご要望どおり、`boolean` とアプリ ID の配列の両方を返します。**

```ts
interface QueryMetrics {
  recordGetCalls: number;
  fetchedRows: number;
  elapsedMs: number;
  cursorRecordsScanned: number;
  limitReached?: boolean;              // 追加
  limitReachedApps?: readonly number[]; // 追加
}
```

```ts
if (result.metrics.limitReached) {
  // 結果は全件ではない
}
```

### 2.1 **判定に使うのは `limitReached` のほうです**

`limitReachedApps` は「APP912 が上限に達しました」とメッセージに出すための補助です。

**配列が空であることを「打ち切られていない」の判定に使わないでください。**
今は両者が必ず一致しますが、**将来アプリ ID を伴わない打ち切り経路が増えたときに、
`limitReached` のほうだけが正しくあり続ける**ようにしています。

### 2.2 **`fetchedRows` では判定できません**（ご指摘のとおりでした）

打ち切りは**アプリごと**に判定されます。**実機で確認した例**です。

```
APP4148（215 件）LEFT JOIN APP4147（18 件）   maxRecords = 230

fetchedRows  : 233   ← 上限を超えている
limitReached : false ← どちらのアプリも上限に達していない
```

**合計が上限を超えても打ち切られていない**——この形があるため、`fetchedRows` での判定は
誤検知します。

### 2.3 **どちらも任意プロパティです**

**既存のコードは変更不要です。**

`QueryResult` を**そちらのコードで構築している箇所があっても型エラーになりません**。
実装中に、こちらのテストがまさにその形で `QueryResult` を構築していることに気づき、
**必須プロパティにすると破壊的変更になる**と分かったためです。

**エンジンは常に値を入れます**（打ち切りが無ければ `false` と空配列）。
`undefined` になるのは**旧版のエンジンが返した結果**だけです。したがって

```ts
if (result.metrics.limitReached) { … }
```

は**旧版でも新版でも同じに書けます**（旧版は `undefined`、新版の非打ち切りは `false`。どちらも falsy）。

### 2.4 バッチでの扱い

`runBatch` では、**他の metrics と同じくバッチ全体の集計値**を返します（文別には分かれません）。

### 2.5 変えていないもの

- **打ち切りの判定そのもの**
- **警告の文言**
- **`onLimitReached: "error"` の挙動**

## 3. 「打ち切られた入力の集計をエラーにする」案は**今回は入れていません**

ご報告を受けて、**集計が誤った数を返す範囲を実測しました。**

```
APP4147（18 件）へ maxRecords=5・truncate
SELECT COUNT(*) AS 件数, SUM(顧客No) AS 合計, AVG(顧客No) AS 平均 FROM APP4147
```

| | 打ち切りあり | 実際 |
|---|---:|---:|
| 件数 | **5** | 18 |
| 合計 | **17** | 51 |
| 平均 | **3.4** | 2.83… |

**`COUNT` / `SUM` / `AVG` の 3 つとも誤った値を返します**（警告は 1 行だけ）。
**平均が特に危ういと見ています。**件数と合計は「少ないな」と気づく余地がありますが、
**平均は値域が変わらないため見た目に違和感がありません。**

**これを fail-closed にする案は見送りました。**
**`"truncate"` はそちらが明示的に選んだ設定**であり、選んだ挙動を勝手にエラーへ変えるのは
別の問題を作ると判断したためです。**§2 で分岐できるようになったので、まずはそちらでご対応ください。**

**要望をいただければ実装します。**「集計だけエラー・明細は行＋警告」をエンジン側で
やってほしい、という形であれば検討します。

なお、**統計系（`STDDEV` / `VAR` / `MEDIAN` / `MODE`）は従来から fail-closed**です。
打ち切られた入力では意味を成さないためです。

## 4. `getFields` のエラー文面を直しました（先日の切り分けを受けて）

**先日「エンジンの回帰では」と報告されて双方が調査に時間を使った件**ですが、
**こちらの伝え方に問題がありました。**

```
（従来）InternalError: ... policy is not defined ...
```

**このコードベースで `InternalError:` は「到達しないはずの不変条件が破れた＝エンジンのバグ」に
使う接頭辞**です。**client 由来の入力に使っていたのが誤り**でした。
**エンジンの不具合に見えて当然の文面**を出していました。フィールドコードも出ていませんでした。

```
（v3.32.0）
ArgumentError: getFields returned unknown fieldType "__ID__" for field "$id".
  getFields must return only the fields from /k/v1/app/form/fields.json;
  $id and $revision are synthesized by the engine and must not be added.
```

**`code` は `EXECUTION_ERROR` のままです**（エラー種別を `code` で判定する分岐は変わりません）。

あわせて、**ドキュメントに `getFields()` の契約を「渡すもの」と「渡さないもの」の対で
書きました**（`docs/ksql_engine_library.md`）。従来は**渡すべきものしか書いておらず**、
**足してはいけないものが読み取れませんでした。**
