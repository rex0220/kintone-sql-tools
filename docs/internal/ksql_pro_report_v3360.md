# 本文（送付版）

## 【連絡】v3.36.0 — `UNION` の件数クエリが既定設定で動くようになりました

```
npm i @rex0220/kintone-sql-tools@3.36.0
```

**Pro 側の対応は不要です。取り込むだけで、該当する SQL が速く・確実になります。**

---

## 1. 何が変わったか（B105）

**`UNION` / `UNION ALL` の各枝の `SELECT COUNT(*)` が、単体と同じく
`totalCount` の単発 GET になりました。ラベル列（リテラル）との併用も対象です。**

```sql
SELECT '顧客管理' AS アプリ, COUNT(*) AS 件数 FROM APP100
UNION ALL SELECT '案件管理', COUNT(*) FROM APP200
```

**従来、この形は各枝が全件取得に落ちていました。**
単体の `COUNT(*)` は v3.32.0（B94）から単発 GET でしたが、**`UNION` の枝と
ラベル列の併用には適用されていませんでした**。そのため既定の `maxRecords` を
超えるアプリを含むと「完全な候補集合が必要です」のエラーで停止していました。

**実測**（12 アプリ・合計 10,675 件の件数一覧）:

| | 従来 | v3.36.0 |
|---|---|---|
| 既定 `maxRecords` | **エラー** | **約 5 秒で 12 行** |
| kintone への GET | 約 32 回（`$id` 全件） | **12 回**（各枝 1 回） |

### 1.1 対象の判定

| 枝の形 | v3.36.0 |
|---|---|
| `COUNT(*)` だけ | **単発 GET** |
| `'ラベル' AS 列名` ＋ `COUNT(*)`（順序・別名は自由） | **単発 GET** |
| フィールド参照・算術・文字列関数・`CASE` が混ざる | 従来どおり全件取得 |
| `COUNT(列)`・`GROUP BY` つき | 従来どおり全件取得 |

**枝ごとに個別に判定**されるので、同じ `UNION` の中で混在しても構いません。

### 1.2 挙動変更の向き

**従来エラーだった形が成功するようになる方向だけです。**
**返る値が変わるクエリはありません。**単発 GET の経路とフォールバック経路
（`totalCount` を返さない client での全件取得）の結果が完全に一致することを
テストで固定しています。検索の 10 万件打ち切りは従来どおり fail-closed です。

> **BYO client への影響**——`getRecords()` が `totalCount` を返さない場合は
> 従来どおり全件取得へフォールバックします。**v3.33.0 の B96 でお願いした
> 「応答をそのまま返す」が守られていれば、何もする必要はありません。**

## 2. 文書の更新（挙動の変更なし）

- **`PRIMARY_ORGANIZATION()` の言語リファレンスに `SELECT` 側の注意を明記しました。**
  優先組織が未設定の利用者では条件が無視されて全件が返り、エンジンからも画面からも
  判別できない——**そちらが閲覧側の警告で対応された、まさにその内容**です。
  従来は DML 拒否しか書かれていませんでした。根拠も「公式の記述＋実機で再現を確認」へ
  更新しています（そちらの `5 = 5` の実測を受けたものです）
- SELECT 基本構文に `KORDER BY` を追記、kintone クエリ関数の性能上の意味を追記
