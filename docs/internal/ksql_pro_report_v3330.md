# 本文（送付版）

## 【連絡】v3.33.0 — **`"truncate"` へ戻していただけます**（K-37 の前提が解けました）

**ご依頼の「集計だけ fail-closed」を実装しました。**

**K-37 に書かれていた依存関係**——「明細ペインのために `"truncate"` へ戻すなら、
集計側の fail-closed がエンジンにあることが前提」——**が解けます。**

```
npm i @rex0220/kintone-sql-tools@3.33.0
```

---

## 1. `"truncate"` のまま、集計だけがエラーになります

**ご要望の線引きそのものです。**

| 形 | v3.33.0 |
|---|---|
| 集計 / `GROUP BY` / `DISTINCT` / `UNION`（`ALL` なし） | **エラー**（`FetchAllLimitError`） |
| **素の明細** / `UNION ALL` | **打ち切り + 警告**（従来どおり） |

**実機で確認しました**（`APP4147` 18 件・`maxRecords=3` / `truncate`）。

```
SELECT COUNT(*) FROM APP4147 WHERE 顧客No LIKE '%6%'
  v3.32.0 → 0        （真の値は 3。該当は 4 件目以降で、先頭 3 件だけを数えていた）
  v3.33.0 → FetchAllLimitError

SELECT 顧客No FROM APP4147
  v3.33.0 → 3 行 ＋「取得上限（3 件）に達したため…」    ← 従来どおり
```

**明細ペインは今までどおり行を出せます。**これが要件の本体と受け取りました。

### 1.1 エラー文面

```
集計の正しい結果には完全な候補集合が必要です。complete input reason: AGGREGATE。
onLimit=truncateは使用できません。取得件数が上限（3 件）を超えました。
WHERE 句で絞り込むか、maxRecords を引き上げてください。
```

**理由・上書きの明示・元の文言の 3 段**です。`reason` は
`AGGREGATE` / `GROUP_BY` / `DISTINCT` のいずれか（複数のこともあります）。

**`code` は `FETCH_LIMIT_EXCEEDED` のまま**です。エラー種別を `code` で判定している
分岐は変わりません。

## 2. **新しいモードは足していません**（ご提案と違う形になりました）

ご依頼では `onLimitReached: "error-if-incomplete"` のような**モード追加**を前提に
書かれていましたが、**実装前に調べたところ、その必要がありませんでした。**

**エンジンには既に「完全な入力が必要」という仕組みがあり、
`truncate` を `error` へ差し替える配管まで完成していました。**

**ローカル `ORDER BY`・window 関数・統計集計（`STDDEV` など）・小計総計は、
従来から `truncate` でもエラー**になっていました。**足りなかったのは対象だけ**です。

さらに、**その非対称は意図的に残されたもの**でした。統計集計を fail-closed 化した際の
社内仕様書に、こう書かれていました。

> 既存 `SUM` / `AVG` 等の truncate 契約を互換性のため変更せず、
> **既存集計の完全入力化を別課題とし、新旧非対称は意図的**とする。

**今回がその「別課題」です。**

### 2.1 モードを足さないほうが良い理由

- **判定・配管・エラー文面をすべて既存のものが使えます。**
  新しい判定を書くと、それ自体が誤った結果の原因になり得ます
- **モードを足すと、既存の `ORDER BY` 等（モード非依存で常にエラー）との一貫性を
  改めて決め直す必要が出ます。**「`ORDER BY` は新モードでなくてもエラーなのに、
  集計は新モードのときだけ？」という説明の難しい状態になります

**結果として、`"truncate"` を選ぶだけでご要望の線引きが得られます。**

## 3. ⚠ これは挙動の変更です

**`"truncate"` を選んでいる利用者の集計クエリが、上限到達時にエラーになります。**

**ただし、失われる正しい結果はありません。**
**現在成功して見えるクエリも、返しているのは部分集合を畳んだ誤った値**です。

**`0` が返る形が最も危ういと考えています。**そちらが APP912 で観測された値です。

| 返る値 | 気づけるか |
|---|---|
| `COUNT` 5 / `SUM` 17 / `AVG` 3.4 | 「今月これだけ？」と**疑う余地がある** |
| **`0`** | **「該当なし」という完結した答えに読める。しかもダッシュボードで `0` は平常の値** |

**「平均が特に危うい」というこちらの見立てに `0` を並べたい、というご指摘のとおりでした。**
**平均は桁が変わらないので気づけず、`0` はそもそも異常に見えません。**

### 3.1 対象と対象外

**対象**（上限到達時にエラー）:
`COUNT` / `SUM` / `AVG` / `MIN` / `MAX` などの集計、plain `GROUP BY`、
`SELECT DISTINCT`、`UNION`（`ALL` なし）。

> **`UNION` を含めたのは、枝をまたいで重複を畳むためです。**
> 含めないと「`SELECT DISTINCT x FROM A` はエラーだが
> `SELECT x FROM A UNION SELECT x FROM B` は通る」という説明できない差が残ります。

**対象外**（従来どおり行と警告）:
**素の明細**、**`UNION ALL`**。**行そのものは本物**で、件数が足りないだけです。

**対象外**（そもそも取得上限を使わない）:
**完全に押し下がる `COUNT(*)` の単発取得**（v3.32.0 の B94）。
**実機で確認済み**——`maxRecords=3` でも正しい `18` を返します。

**`JOIN` は対象外**です。行を畳んでいないためです。
**LEFT JOIN で右側が打ち切られると `NULL` が入る**という別の問題は認識しており、
**別課題として残しています。**

### 3.2 移行方法

- **`WHERE` で候補を絞る**か、**`maxRecords` を引き上げる**
- **`onLimitReached: "error"` を選んでいる場合、挙動は変わりません**

### 3.3 EXPLAIN に出ます

集計・`GROUP BY`・`DISTINCT` を含むクエリの計画に、**完全入力の要求とその理由**が
表示されるようになりました。**実行前に分かります。**

```
  complete input: required (onLimit=truncate disabled)
  complete input reason: AGGREGATE
  onLimit=truncate: disabled
```

## 4. `getRecords()` の応答契約を文書化しました（ご共有ありがとうございます）

**ラッパーが `totalCount` と `searchAborted` を落としていた件、共有していただいて
助かりました。**とくに **`searchAborted` のほうが危険**というご指摘が的確でした。

**こちらでも確認しました。エンジン側では検出できません。**
**`false` と「そもそも入っていない」を区別する手段が無く、
打ち切りが無ければ省略するのが正常な実装**だからです。

| 落ちたもの | 影響 | エンジン側 |
|---|---|---|
| `totalCount` | 遅くなる／上限でエラー | ✅ **自分で塞ぐ**（全件取得へフォールバック） |
| **`searchAborted`** | **打ち切られた結果を完全な結果として扱う** | ❌ **塞げない** |

**ご提案どおり、`getFields()` と同じ形で文書に書きました**
（`docs/ksql_engine_library.md` の `getRecords() の契約`）。

- **「必ず残す」＝`searchAborted`**（正しさ）／**「残すと速い」＝`totalCount`**（性能）
  と**危険度の差**が読めるようにしました
- **ラッパーの注意を独立させました。**`createReadonlyKintoneClient()` を使っていても
  踏むため、「自前クライアントを書く人向け」の文脈に埋めていません
- **`getRecords()` だけが脆いことも書きました**——`ReadonlyCursorPage.next` と
  `ReadonlyCursorHandle.totalCount` は**必須なので型で防げます**。
  **追加項目が任意プロパティである応答は `getRecords()` だけ**です

**型を必須化する案は採りませんでした。**破壊的変更になり、
`records` だけを返す既存のラッパーがすべてコンパイルエラーになるためです。
