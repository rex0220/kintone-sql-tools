# B137 列数の違う `UNION` をエラーにする 仕様（R2）

- ステータス: ✅ **v3.50.0 でリリース**（2026-08-06） → [レビュー](ksql_b137_codex_review_1.md)（高 2・中 4 を**全件反映**）
- 起票: [B137](ksql_b137_union_column_count_issue.md)（コード確認済み・方向確定＝案 A）

> **R1 の誤り 3 件（うち 1 件はオーナー指摘、2 件はレビュー）**
>
> 1. **「静的検出は不可能」は偽**（オーナー指摘＋レビュー H2）。**`DESCRIBE` の列数は版内で固定**（`execute.ts` の literal）、**`SHOW APPS` も 3 列固定**、**`SELECT *` はアプリ定義から項目数が分かる**。さらに**両枝が wildcard を含まなければ AST の `columns.length` で判定できる**。→ §0.1 を訂正
> 2. **「C まで到達しない」は誤り**（レビュー H1）。`executeUnion` は `Promise.all` で**左の入れ子全体と右を同時に開始する**ため、**不一致でも全枝が実行される**。→ §2.3・§3.3 を訂正
> 3. **「padding に依存する既存テストは無い」は現時点では偽**（レビュー M4）。**B130 で自分が現状挙動を固定するテストを書いた**ため、そのテストは落ちる。→ §4 を訂正

## 0. 確定事項（コード確認・調査で裏取り済み）

| 事実 | 根拠 |
|---|---|
| **remap は 2 か所にある**（通常経路と CTE 経路）。**同じ 1 行** | `execute.ts:4908` / `:5022` |
| **右辺を左辺の列名へ位置対応でリマップし、`?? ""` で埋めている** | 同上 |
| **`A UNION B UNION C` は左結合の木**（`UNION(UNION(A,B), C)`） | `parser.ts:1273-1274` の `tryParseUnionChain` |
| 列名は**左辺から取る**（`columns: leftCols`）。**MySQL と同じ**なので変えない | `execute.ts:4922` / `:5031` |
| **主要 4 実装（MySQL / PostgreSQL / SQLite / SQL Server）はすべてエラー** | 起票 §4.1 |
| **B130 実装時の実測では padding 依存テストは 0 件**（列数検査を入れた状態で 225 suites / 5,426 tests 全通）。**ただしその後こちらが現状挙動を固定するテストを 1 本追加した**ので、本件でエラー期待へ変える | B130 実装時の実測 / `b130DescribeFlags.test.ts` |
| `INSERT ... SELECT` は既に**列数一致を要求**している | `execute.ts:7842-7847` |
| `deduplicateRows` は `leftCols` だけを見る | `execute.ts:4930` |

### 0.1 静的判定は「不可能」ではない。**しない**という設計判断にする（R1 から訂正）

**R1 は「kSQL では静的に弾けない」と書いたが誤り。** 次の形は実行前に列数が分かる。

| 形 | 静的に分かるか | 根拠 |
|---|---|---|
| 両枝とも列を明示（wildcard 無し） | **分かる** | `SelectColumn` 1 つが 1 出力位置。`columns.length` で足りる |
| `DESCRIBE` | **分かる** | 列は `executeDescribe` の literal で**版内では固定**（v3.49.0 は 7 列） |
| `SHOW APPS` | **分かる** | 同じく 3 列固定 |
| `SELECT *`（物理アプリ） | **算出できる** | フォーム定義から項目数が出る（`EXPLAIN` は既に metadata を読む） |
| `SELECT *`（JOIN 後・サブテーブル展開後） | **要注意** | 非修飾キーと修飾キーが両方載るため、単純な項目数とは一致しない（`process.ts:103-105`） |

**それでも B137 では実体化後の共通検査だけにする。** 理由は「できないから」ではない。

- **形ごとにエラーの時機と優先順位が分岐する**。静的に弾ける形だけ早く落ちると、
  **未知フィールドエラーとの優先順位が形によって変わる**（observable contract の分岐）
- **1 つの意味論で通す方が、利用者にもテストにも説明しやすい**

> **API 節約のための静的 fast-fail は別課題にする。** wildcard の展開規則・
> エラー優先順位・`EXPLAIN` / validate との整合を独立に決める必要があるため
> （レビュー H2 の提案どおり）。**着想はオーナー指摘（`DESCRIBE` は版内固定、
> `SELECT *` はアプリ定義から分かる）。**

### 0.2 判定は実体化後の `columns.length` で行う

**両枝を実行し終えてから比べる。** MySQL のような prepare 時エラーにはしない（§0.1）。

## 1. スコープ

| 区分 | 内容 |
|---|---|
| **対象** | `UNION` / `UNION ALL` の**左右で列数が違うときエラーにする**（2 か所とも） |
| **非対象** | **列名の一致**（左辺から取る現行仕様を維持。MySQL と同じ） |
| **非対象** | **型の互換性**（kSQL は全値文字列なので概念が無い） |
| **非対象** | `INSERT ... SELECT`（既に列数一致を要求している） |
| **非対象** | 事前（静的）検出。**可能だが本件ではやらない**（§0.1・別課題） |

## 2. 変更内容

### 2.1 判定

```
左辺の columns.length !== 右辺の columns.length → エラー
```

**`UNION` と `UNION ALL` で扱いを変えない。** 標準 SQL も 4 実装も区別しない。

### 2.2 適用箇所

**2 か所とも**（`execute.ts:4902-4910` と `:5018-5023`）。
**共通ヘルパー 1 本**にして、片方だけ直す事故を防ぐ。

### 2.3 3 段以上の連鎖

パーサが**左結合の木**を作る（`UNION(UNION(A,B), C)`）ため、
**各ノードで「そこまでの結果」と右辺を比べる**形になり、
**結果的に最左の `SELECT` の列数が基準**になる。**MySQL と同じ。**

`A(3列) UNION B(3列) UNION C(5列)` は **外側ノードで落ちる**。
`A(3列) UNION B(5列) UNION C(3列)` は **内側ノードで落ちる**。

> **【R1 から訂正・レビュー H1】「C まで到達しない」は誤り。**
> `executeUnion` は **`Promise.all` で左の入れ子全体と右を同時に開始する**ため、
> **内側が不一致でも C の実行は始まっている**。
> **どの段で落ちても、全枝ぶんの API を消費する。** 受入にもこれを入れる（§3.3）。

### 2.4 エラーメッセージ

```
ArgumentError: UNION の左右で列数が一致しません（左 3 列 / 右 7 列）。
UNION は列を位置で対応させるため、両辺の列数を揃えてください
```

- **`ArgumentError`** を使う（既存の列関連エラーと同じ扱い）
- **左右の実際の列数を出す**（どちらを直すか判断できる）
- **次の一手を書く**（B129 の教訓＝診断は「なぜ止まったか」だけでなく「次に何を書くか」）

> **列名まで出すかは論点**（→ §6-2）。`DESCRIBE` の 7 列は名前が長く、
> エラーが読みにくくなる可能性がある。

**ヘルパーは `readonly string[]` の左右 `columns` を受け取る**（レビュー M2）。
必要なのは長さだけで、行・warnings・メタを渡す理由がない。

## 3. 受入条件

### 3.1 エラーになること

**代表 SQL は実在アプリで書く**（`APP100` / `APP200`。**過去に 5 回、実行していないサンプルを書いた**）。

| 入力 | 期待 |
|---|---|
| `SELECT a, b FROM APP100 UNION SELECT c FROM APP200`（右が少ない） | **エラー**（従来は空文字で埋めていた） |
| `SELECT a FROM APP100 UNION SELECT b, c FROM APP200`（右が多い） | **エラー**（従来は黙って捨てていた） |
| `UNION ALL` でも同じ | **エラー** |
| **CTE 内の `UNION`**（`executeQueryWithCte` 経路） | **エラー**（2 か所とも直すこと） |
| `CREATE TEMP TABLE #t AS <列数の違う UNION>` | **エラー**（実体化時に止まる） |
| `WITH d AS (DESCRIBE APP100) SELECT * FROM d UNION ALL SELECT 'a','b','c'` | **エラー**（7 列 vs 3 列） |
| **3 段の連鎖で内側が不一致** | **内側ノードで落ちる**（ただし**全枝が実行される**・§2.3） |
| **3 段の連鎖で外側が不一致** | **外側ノードで落ちる** |
| **engine ライブラリ `runQuery` / `runBatch` 経由** | 同じエラー（公開 surface・レビュー M2） |

> **`INSERT ... SELECT` / `UPSERT ... SELECT` のソースに直接 `UNION` は書けない**（構文非対応）。
> **一時テーブル経由の場合は `UNION` の実体化時に止まる**（レビュー M2）。

### 3.2 従来どおり通ること（回帰）

1. **列数が一致する `UNION` / `UNION ALL`** がすべて従来どおり
2. **列名が違っても列数が同じなら通る**（左辺の名前になる。現行仕様）
3. `FROM` なしの `SELECT ... UNION ALL SELECT ...`（レシピ R7 の形）
4. `UNION` の重複排除（`deduplicateRows`）が不変
5. **`SHOW APPS` / `DESCRIBE` を含む `UNION`** で列数が合っていれば通る

### 3.3 エラーの出方

1. **両辺を実行したうえで落ちる**（§0.1）。**片側だけ実行して落ちる形にしない**
   （現行は `Promise.all` で両辺を並行実行しており、その形を変えない）
1b. **3 段以上でも全枝が実行される。** 内側が不一致でも外側の右枝は開始済みなので、
   **「途中で止まるから API を節約できる」とは書かない**（レビュー H1）
2. **メッセージに左右の列数が入る**
3. `ArgumentError` として扱われる（MCP の error envelope に載る）

### 3.4 `EXPLAIN` は従来どおり計画を返す（R1 で未確定だった・レビュー M1）

**現行の `EXPLAIN <UNION>` は `executeUnion` を通らず、枝ごとの計画を集めるだけ**なので、
**列数が違っても計画を返す**。**この挙動を変えない。**

- **`EXPLAIN` は行を取らない**ので、そもそも列が実体化されない
- **`EXPLAIN` の役割は「どう実行されるか」を見せること**であり、実行時エラーの先取りではない
- 静的に弾く話は §0.1 のとおり別課題

**受入に「`EXPLAIN` は列数が違っても成功する」を入れる**（変えていないことを固定するため）。

### 3.5 差し戻したコードを使う

B130 の実装時に codex が書いた `assertUnionColumnCount` が**そのまま使える**
（`docs/internal/ksql_b130_codex_impl_report.md` に経緯）。
**ただし当時のテストは 1 本だけ**だったので、§3.1 / §3.2 を満たすまで足す。

## 5. 移行案内（CHANGELOG に書く）

**従来は列数が違っても通っていた。** 空文字で埋めるか、余りを捨てていた。

```
修正前  SELECT 製品名, 仕入先 FROM APP4228 UNION SELECT 製品名 FROM APP4229
        → 仕入先 が空文字の行が混ざる
修正後  同じ SQL → エラー
```

**直し方**＝両辺の列数を揃える。足りない側にリテラルを足す。

```sql
SELECT 製品名, 仕入先 FROM APP4228 UNION SELECT 製品名, '' FROM APP4229
```

**この移行後の形は `ksql_validate` を通して確認済み**（2026-08-06）。
