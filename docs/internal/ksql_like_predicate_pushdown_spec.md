# 仕様案: LIKE を含む SELECT の述語分割プレフィルタ（性能緩和）

- 作成日: 2026-07-15
- ステータス: **仕様案（レビュー前・実装可否判断用）**
- 分担: Claude=仕様/観点、Codex=実装/テスト
- 背景: CHANGELOG v2.0.0 が「安全な AND 述語だけをプレフィルタとして押し下げる最適化は、包含性を検証してから v2.x で別途追加する」と予告した宿題。
- 関連コード: `src/converter/selectToKintone.ts`（`whereRequiresJsEval` / `selectToFetchAllParams`）、`src/core/optimization/wherePredicatePushdown.ts`（`extractTableCondition`）、`src/execute.ts`（`executeFullScanSelect` / `fetchTableRecordsForFullScan`）

## 0. 用語（誤解を避ける）

- **述語分割プレフィルタ**は **LIKE を kintone に押し下げる最適化ではない**。LIKE は**従来どおり JS 評価**のまま。
- LIKE と **AND で並ぶ「他の安全な条件」だけ**を kintone クエリに渡して**取得件数を絞り**、その縮小集合に対して JS で **WHERE 全体（LIKE 含む）を再評価**する。
- したがって kintone の `like`（単語検索・全角半角正規化・トークン化）の仕様を**再現する必要はない**。論点は「押し下げる**他の条件**が正しく働くか」だけ。

## 1. 目的と現状

### 目的
LIKE（や関数・サブクエリ等 JS 評価が必要な要素）を含む SELECT は現状 **WHERE 全体が FULL_SCAN**（全件取得）になる。LIKE と併記された**数値・日付などの絞り込み条件を kintone 側プレフィルタ**にして取得件数を減らし、`maxRecords` 到達や実行時間を緩和する。

### 現状（コードで裏取り済み）
- **FULL_SCAN 判定**: `whereRequiresJsEval`（[selectToKintone.ts:81](../../src/converter/selectToKintone.ts#L81)）が WHERE 内に LIKE / 左辺関数 / 右辺式 / サブクエリ / EXISTS のいずれかを見つけると true → `resolveSelectMode` が FULL_SCAN。
- **押し下げ基盤は既に存在**: `extractTableCondition`（[wherePredicatePushdown.ts](../../src/core/optimization/wherePredicatePushdown.ts)）が **AND を分解して各テーブルの押し下げ条件を抽出**し、**LIKE は除外**（[:17](../../src/core/optimization/wherePredicatePushdown.ts#L17)）。`executeFullScanSelect`（[execute.ts:1082-1096](../../src/execute.ts#L1082)）が各テーブル（メイン含む）にこれを適用し、`fetchTableRecordsForFullScan` が `(baseQuery) and (pushQuery)` で kintone に渡す（[:1540](../../src/execute.ts#L1540)）。EXPLAIN にも反映（[:3194](../../src/execute.ts#L3194)）。
- **ただし押し下げは「エイリアス付きフィールド」に限定**: `extractTableCondition` は `isSingleTableField`（`field.tableAlias === tableAlias`）で判定し、`executeFullScanSelect` は `if (stmt.from.alias)` でのみ計算する。→ **`FROM APP100 WHERE 売上 >= 1000000 AND 会社名 LIKE '%A%'`（無エイリアス・JOIN なし）は押し下げ対象がなく全件取得**になる。これが本課題の主対象。
- **FULL_SCAN では `selectToFetchAllParams` は WHERE を出さない**（[:162](../../src/converter/selectToKintone.ts#L162) の `!whereRequiresJsEval` ガードで false）ため、メインの `baseQuery` は空。押し下げは `pushQuery` のみが担う。
- **現状すでにテキスト `=` / `in` を押し下げ対象にしている**: `isPushDownableRight`（[wherePredicatePushdown.ts:53](../../src/core/optimization/wherePredicatePushdown.ts#L53)）は `STRING` / `NUMBER` / `KINTONE_FUNC` / `IN_LIST` を許可。演算子は `!=` / `<` 等も区別なく押し下げる（右辺型のみで判定）。

## 2. 正しさモデル（超集合性 = この最適化の生命線）

押し下げる条件 `P` について、**「kintone が `P` で返す集合」が「JS が `P` を真とする集合」を包含（⊇）**していなければならない。

- 縮小集合に対し JS が WHERE 全体（`P ∧ 残差`）を再評価するため、最終結果は `{ kintone-P } ∩ { JS: P ∧ 残差 }`。
- これが押し下げ無し（`{ JS: P ∧ 残差 }`）と一致する条件は **`{JS-P} ⊆ {kintone-P}`**。
- **kintone-P が JS-P より狭い（取りこぼす）と、正しい行が fetch されず結果から静かに欠落**する（サイレント不具合）。逆に kintone-P が広い分には JS 再評価が捨てるので無害。

→ **「kintone の P 評価が JS の P 評価より狭くならない」と保証できる述語だけ**を押し下げてよい。

## 3. 述語型ごとの安全性評価

| 述語 | 例 | 超集合性 | 判定 |
|---|---|---|---|
| 数値 `= < > <= >=` | `売上 >= 1000000` | kintone 数値比較と JS 数値比較は一致。空/非数値レコードは kintone 側で当該条件から自然に外れ、JS でも NaN 除外 → 取りこぼしなし（要確認: 空セルの `>=` 挙動） | **安全（推奨）** |
| 日付・日時の範囲 `< > <= >=` | `作成日時 >= '2026-07-01'` | 概ね安全。ただし**タイムゾーン**・**日時の分精度丸め**・境界（`=` の端）で kintone と JS の解釈差が出得る | **条件付き安全（境界要検証）** |
| レコード番号 `$id` | `$id >= 1000` | 完全一致・数値。安全 | **安全（推奨）** |
| 選択系 `in`（オプションコード） | `ステータス IN ('完了')` | オプションコードの完全一致。kintone `in` と JS の集合一致が期待できる（要確認: 表記ゆれのない前提） | **条件付き安全** |
| テキスト `=` / `in` | `会社名 = 'ABC'` | **不確実**。kintone のテキスト照合は全角半角・大小・トークン化の**正規化**が絡む（詳細非公開）。正規化は通常 kintone を**広く**する（`ABC` が `ＡＢＣ` にも一致＝超集合性は保たれる方向）が、**狭くする端（末尾空白・結合文字・特定記号）を排除できない** | **要実機検証（既定は非押し下げ）** |
| `!=` / `<>` / `NOT` | `会社名 != 'ABC'` | **否定は超集合性が反転しやすい**。kintone-`=` が広いと kintone-`!=` は**狭く**なり取りこぼす。テキスト否定は特に危険。数値 `!=` も NULL/空の扱いで差が出る | **非押し下げ（除外）** |
| `IS NULL` / `IS NOT NULL` | `顧客コード IS NULL` | kintone の空判定と JS の空文字判定の一致要確認。フィールド型で挙動差 | **要確認（既定は非押し下げ）** |
| OR をまたぐ条件 | `A OR B` | 片側が押し下げ不可（LIKE 等）だと OR 全体を落とすしかない。`extractTableCondition` は「全体が単一テーブル参照かつ押し下げ可能」時のみ OR を押す | 現状維持（AND 分解が主対象） |

> **重要**: 現状コードは既に**テキスト `=`/`in` と `!=` を押し下げている**（エイリアス付き / JOIN 経路）。本仕様で安全ホワイトリストを厳格化するなら、**新規（単一テーブル）経路だけ厳格にするか、既存経路も揃えて厳格化するか**を決める必要がある（§5-B）。

## 4. 提案（2 つの独立した変更）

### A. 単一テーブル（JOIN なし・無エイリアス）への押し下げを有効化【本命・低リスク】

- `extractTableCondition` の**単一テーブル版**（エイリアス不問）を追加する。あるいは `executeFullScanSelect` のメインフェッチで、**JOIN が無い**場合は「テーブル修飾の有無に関わらず安全述語を抽出」して `pushQuery` に使う。
- 抽出は既存ロジック（AND 分解・LIKE 除外）を再利用。フィールドは単一テーブルなので曖昧さなし。
- 効果: `FROM APP100 WHERE 売上 >= 1000000 AND 会社名 LIKE '%A%'` が `売上 >= 1000000` でプレフィルタされ、取得件数が激減。

### B. 安全述語ホワイトリストの確定【正しさの核心・要判断】

`isPushDownableRight`（右辺型のみ）に加え、**演算子とフィールド型（＝左辺の種類）で押し下げ可否を制御**する。推奨は段階導入:

- **第 1 段（超保守・すぐ入れられる）**: 押し下げてよいのは
  - 数値比較（`= < > <= >=`、右辺 NUMBER）
  - 日付・日時の範囲比較（`< > <= >=`、右辺 STRING/KINTONE_FUNC の日付）※境界の実機検証を通すまでは `>=`/`<=`/`>`/`<` のみ、`=` は除外
  - `$id` 比較
  - 選択系 `in`（右辺 IN_LIST・オプションコード）
  - **除外**: テキスト `=`/`!=`/`in`、あらゆる `!=`/`<>`/`NOT`、`IS (NOT) NULL`（新規経路では押し下げない）
- **第 2 段（実機検証後）**: テキスト `=`/`in` の超集合性を実機で確認できたら押し下げ対象に追加。

> フィールドが数値か日付かテキストかは、kSQL は**アプリのフィールド定義を持たない**（実行時に型情報が乏しい）。そのため「右辺リテラルの型」と「演算子」から**保守的に**判定する（例: 右辺 NUMBER なら数値比較とみなす／右辺 STRING で `=` は「テキスト等値の可能性」があるため第 1 段では押し下げない）。この近似の妥当性は §7 で要検証。

### EXPLAIN
- 「プレフィルタ押し下げ: `売上 >= 1000000`／JS 評価: `会社名 LIKE '%A%'`（＋ push 分）」のように、**何を押し下げ・何を JS 評価したか**を明示する（現状の EXPLAIN 表示を拡張）。取得削減効果がユーザに見える。

## 5. 判断が要る論点（レビューで決める）

- **B の適用範囲**: 新規（単一テーブル）経路のみ厳格化するか、既存（JOIN / エイリアス）経路も同じホワイトリストに揃えるか。後者は既存のテキスト `=`/`!=` 押し下げ挙動を**変える**（安全側だが、これまで速かった JOIN クエリが全件取得に戻り得る）。
- **右辺型からの型近似の是非**: 「右辺 NUMBER＝数値フィールド」と見なしてよいか（文字列フィールドに数値を書くケースの扱い）。
- **日時の境界**: タイムゾーン・分精度で `>=` の端が kintone と JS でずれないか（実機検証項目）。

## 6. 非対象・限界

- LIKE 単独、またはテキスト条件だけと AND した SELECT は**押し下げ対象がなく無効果**（従来どおり全件取得）。効果は「LIKE ＋ 数値/日付/id/選択in」の併記時に限られる**条件付き**。
- サブテーブル仮想テーブルは親レコード取得のため、押し下げ設計は別途（本仕様はメイン/親アプリの通常フィールドを対象）。

## 7. 正しさ担保テスト（実機必須・超集合性の検証）

「**押し下げ後の結果 == 全件 JS 評価の結果**」を、超集合性を壊しやすいケースで固定する:

- 数値 `>=` ＋ LIKE: 件数と行が一致。空セル・0・負値を含める。
- 日時 `>=` の**境界**（分丸め・TZ 端）＋ LIKE: 一致。
- 選択系 `in` ＋ LIKE: 一致。
- **テキスト `=`（全角半角・末尾空白・大小）**: 押し下げた場合に**取りこぼしが出ないこと**を実データで確認（→ 出るなら第 1 段どおり非押し下げが正しい）。
- `!=` / `IS NULL`: 非押し下げ（JS 評価に残る）であることをユニットで固定。
- 回帰: 既存の JOIN 押し下げ結果が不変（B の適用範囲次第）。
- 単体: `extractTableConditionForSingleTable`（新規）が LIKE / 関数 / `!=` / テキスト `=` を抽出しない、数値/日付/id/選択in を抽出する。

## 8. 効果評価（実装可否の材料）

| 観点 | 評価 |
|---|---|
| 実装コスト | **A は小**（既存 `extractTableCondition` の単一テーブル版＋メインフェッチ結線）。**B は中**（型近似・ホワイトリスト・EXPLAIN・既存経路との整合） |
| 正しさリスク | **B が核心**。誤って狭い述語を押し下げるとサイレント欠落。第 1 段の超保守ホワイトリストと実機超集合性テストで管理 |
| 効果 | 条件付き（LIKE ＋ 数値/日付/id/選択in）。該当する大規模アプリのクエリでは**取得件数を桁で削減**し得る |
| 段階性 | A＋B 第 1 段（数値/日付/id/選択in、テキスト・否定は除外）で**安全に価値を出せる**。テキストは実機検証後に第 2 段で追加 |

## 9. 結論（推奨）

- **実装は可能**。基盤（AND 分解・LIKE 除外・per-table 押し下げ・EXPLAIN）が既にあり、本命の A は既存資産の再利用で小さい。
- **B のホワイトリストを超保守（数値・日付範囲・`$id`・選択in のみ、テキスト等値と否定と NULL 判定は除外）から始める**のが安全。ユーザ懸念（テキストの全角半角・単語切り分け）は**テキスト述語を押し下げない**ことで原理的に回避する。
- 既存の JOIN 経路がテキスト `=`/`!=` を押し下げている件は、**別途「既存押し下げの超集合性」実機検証**として切り出し、危険なら揃えて厳格化する。
