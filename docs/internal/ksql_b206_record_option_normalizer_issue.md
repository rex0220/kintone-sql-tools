## 1. なぜ必要か

B205 で **SQL は言語に依らず書ける**ようになった（既定の名称を書けばよい）。
ところが依頼元のプラグインには**もう 1 つの口＝計算式**がある。
ボタンの表示条件・実行条件・SQL のパラメーター・結果メッセージを独自の式で書け、
評価に渡すのは **kintone がブラウザーに渡したレコード**（`kintone.app.record.get()` /
`event.record`）で、**エンジンを通らない**。

そのレコードの選択肢とステータスは**表示名**なので、利用者は同じ設定の中で

- SQL には**既定の名称**（`WHERE ラジオボタン = 'sample1'`）
- 計算式には**表示名**（`ラジオボタン = "サンプル１"`）

という **2 つの規則**を使い分けることになり、しかも計算式の側は**押した人の言語で値が変わる**ので
**どの言語の人にも当たる式が書けない**（設定はアプリに 1 本しか無い）。

**今のうちに直さないと破壊的変更になる**＝利用者が表示名で書いた設定が、直したときに壊れる。
依頼元は Ver.1 のリリースをこれを待つ判断にしている。

## 2. 入れたもの

```ts
const normalize = await client.createRecordNormalizer(appId);  // 準備（通信 3 回）
const canonical = normalize(record);                           // 以降は同期・通信なし
```

| # | 決めたこと | 中身 |
|---|---|---|
| 1 | **`FlowKintoneClient` は変えない** | 同梱のクライアントの型だけ分けた（`BundledKintoneClient`）。自作のクライアントは型も動きも不変＝純加法。B205 の「自作のクライアントでは `canonical` を使えない」決定も崩さない |
| 2 | **作るところだけ非同期・変換は同期** | 依頼元は同期の `filter` と行ごとのループで評価する。`await` が入ると件数ぶん待つ |
| 3 | 向きは**表示名 → 既定名だけ** | 逆は出さない（画面に出す文は依頼元の共通の文で出す設計） |
| 4 | **入力を書き換えない** | `mapRecordOptionValues` の性質そのまま（変わらなければ同じ参照）。渡るのは画面のレコード**そのもの**なので、その場で書き換えると画面が壊れる |
| 5 | **ステータスは `type` で見つける** | 項目コードはアプリの言語で `ステータス` / `Status` と変わる。レコードの中で `type === "STATUS"` のキーを対応表に結びつけるので、**1 項目だけのレコードでも当たる**（依頼元の `@_status` / `@_prev_status` の正規化）。**前提: `STATUS` はアプリに 1 つだけ**（プロセス管理の状態。サブテーブルの項目にもならない）＝レコードの中で `type === "STATUS"` のキーは**最大 1 つ**なので、1 つ見つけて結びつければ取り違えは起こらない（2026-11-07 Takashi） |
| 6 | 一意に決まらない対応表は **`ArgumentError`** | `createRecordNormalizer` の時点（レコードを 1 件も触る前）。`optionNames: "canonical"` と同じ判定・同じ例外 |
| 7 | 恒等のアプリは**素通しの関数** | `identity` のときは入力をそのまま返す（変換の経路を 1 行も通らない） |
| 8 | **キャッシュしない** | 寿命は呼び側。アプリの設定が変わったら作り直す |

**コアは 1 行も変えていない**＝`buildAppOptionNameMap`（対応表と検査）と
`mapRecordOptionValues`（再帰の変換）をそのまま使う。**写しを作らないのが依頼の主旨**だった。

## 3. 代案を採らなかった理由（依頼の §4-3）

依頼元は「対応表をこちらに渡して純粋な関数で変換する」代案も示していたが、**採らなかった**。

- 代案は `getOptionNames` の**返りの形を公開の型として固定**することになる。
  あの形は**内部の都合**（コアが既定名の側と `index` で検算するための生のメタデータ）で、
  依頼元が自分で見つけたとおり **`semantics.optionOrder` が空で上位の `optionOrder` が正本**という
  「同じ名前で意味の違う入れ物」が入っている。**公開して固定したくない**。
- 本命なら対応表が境目を越えないので、その区別そのものが要らない。
- 実装量はどちらも 30 行ほどで、**軽さでは差が付かない**。差が付くのは公開面の固定だけ。

## 4. 試験（`src/flow-library/__tests__/b206RecordNormalizer.test.ts` 13 件）

依頼元の受入基準（KJ-10 §6）をそのまま固定した。**モックは実 API の形に寄せた**＝
プロセス管理が有効なアプリは `form/fields` が `STATUS` / `STATUS_ASSIGNEE` / `CATEGORY` を返し、
言語ごとの表示名を設定した項目は `lang=user` で**選択肢のキーごと変わる**
（B205 で「モックが本物より甘い」ことが原因の不具合を 3 回出した）。

| # | 固定したこと |
|---|---|
| AC1 | `サンプル１` → `sample1`・`みしょり` → `未処理` |
| AC2 | 表示名を設定していない `処理状況` は不変。**その選択肢の `未処理` がステータスの表と混ざらない**（同じ文字列） |
| AC3 | 選択肢に無い値（`サンプル３`）はそのまま |
| AC4 | サブテーブルの**単値**（`明細区分`）と**配列**（`明細印`）の両方。行の `id` も保つ |
| AC5 | 入力を書き換えない・触らない項目は同じ参照 |
| AC6 | **ステータスに同じ名称**を付けたアプリは `ArgumentError`（`status.json` のキーは既定名なので実機で起こり得る形）／**選択肢に同じ表示名**を付けたアプリも `ArgumentError`（`lang=user` の `options` が 1 つに潰れて返るので件数が合わない） |
| 追加 | `type` でステータスを見つける（`Status`・キー名 `s`・1 項目だけ）／`STATUS_ASSIGNEE` と `CATEGORY` は素通し／恒等のアプリは同じ参照／`null`・数値・`{ code }` の配列を触らない／通信は 3 回／**返りは渡した型のまま** |

**AC6 の形を実機の形に直した**のが実装中の発見。はじめ「表示名が重複した `lang=user` の `options`」を
モックで作ろうとしたが、**`options` のキーは表示名なので重複できない**（実機では 1 つに潰れて返る）。
ありえない形で試験を書いていたので、起こり得る 2 つ（ステータスの名称の重複・選択肢の潰れ）に直した。

## 4.1 実装レビュー（2026-11-07。Codex。BLOCKER 0 / MAJOR 2 / MINOR 3）

記録は `kintone-plugin/work-link/codex-review-ksql-b206-2026-11-07.md`。

**MAJOR 1（直した。ただし原因の読みは変えた）＝ステータスの判断が「キーの名前」で再帰全体に効いていた。**
レビューは「トップに `STATUS` が複数あると取り違える」「サブテーブルの子だけ `type: "STATUS"` だと効かない」など
**実アプリでは起こらない形**も根拠に挙げていた（**`STATUS` はアプリに 1 つだけ**。2026-11-07 Takashi。
資料でも**ステータス・作業者・カテゴリーは項目として追加できない**ことを確認＝
[フィールドを追加する](https://cybozu.dev/ja/kintone/docs/rest-api/apps/form/add-form-fields/) の「制限事項」）。
**残っていた本当の穴は 1 つ**で、**サブテーブルの子がステータスの項目コードと同じ名前**のとき、
子の `type` に関係なくステータスの表で変換していた（`map.fields` がステータスをその項目コードで持ち、
再帰は深さを知らないため）。実アプリではその名前は空かないが、**公開の口は任意のレコードを受ける**ので閉じた。

- 直し方: **選択肢の表からステータスを外す**（`choiceFields`）。ステータスは
  **トップの項目だけ**を `type === "STATUS"` で見て直す（`type` の無いレコードのときだけ項目コードで補う）。
  これで資料の「ステータスは `type` で見つけます」が**実装そのまま**になった（レビューの MINOR も同時に解消）。
- **コアは依然 1 行も変えていない**（レビューの案は `mapRecordOptionValues` に `fieldType` と深さを渡す形だったが、
  B205 の読み書きの包みと共有している関数なので、**呼ぶ側で表を分ける**ほうが影響が小さい）。

**MAJOR 2（直した）＝`<T>(record: T) => T` は型が嘘になる。**
`as const` で書いた文字列リテラル型が残るのに、実行時は別の文字列になる。
さらに `Record<string, …>` の制約だと**索引シグネチャの無い名前付きの型**（kintone の型生成で作った
レコードの型）を**受け取れない**（レビューがコンパイラ API で確認）。

- 直し方: 制約を `T extends Record<keyof T, NormalizableRecordValue>` に、戻りを
  `NormalizedRecord<T>`（キーは保ち、値の文字列リテラル型を `string` へ広げる。配列とサブテーブルの行も辿る）に変えた。
- `NormalizableRecordValue` と既存の `KintoneRecordValue` を分ける判断は**妥当**と評価された。
  紛らわしいので JSDoc に「あちらは書き込みの DTO・こちらは読んだレコード」と書いた。

**MINOR（全部対応）**

| 指摘 | 直したこと |
|---|---|
| 試験に実レコードの形が足りない | 追加画面の `null`・行の `id` 欠落・**カテゴリーの非空配列**・ルックアップの値・**プロセス管理が無効な実 API の形**・**入力の deep-freeze** を足した（試験 13 → 21 件） |
| `getOptionNames!` の非 null 断言 | `client` の外に**名前付きの内部関数**として出して断言を消した |
| 資料の言い方 | 「変わらなければ同じ参照」→「**変更があった階層だけ**新しいオブジェクト」。ステータスの契約は実装に合わせた（上）。README に**通信 3 回・キャッシュなし・物理 appId** を足した |

**問題なしと評価された観点**: 入力の不変性・サブテーブルと配列と `{ code }` と `null` の素通し・
公開面の拡張が構造的に純加法であること・spread で能力が落ちていないこと・通信回数・キャッシュしないこと・
fail-closed の位置・**代案を採らなかった判断**・物理 appId の記述。
