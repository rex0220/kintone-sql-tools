## 1. 何ができないか（実測・2026-08-08・v3.62.0）

`GENERATE_SERIES` が埋められるのは 1 軸だけ。**「日付 × 製品」の歯抜けない格子**を作る手段がない:

```
FROM s CROSS JOIN APP4229 AS m            → ParseError: 「ON」が必要です
FROM s INNER JOIN APP4229 AS m ON 1 = 1   → ParseError: フィールド名またはテーブル名が必要です
FROM s, APP4229 AS m                      → ParseError: 文の区切りには ; が必要です（カンマ結合も不可）
```

`JOIN ON` は等値 1 本・両辺とも列のため、直積の標準 3 形（`CROSS JOIN`・`ON 1=1`・カンマ結合）が
すべて構文レベルで閉じている。開けるならどれを公式の入口にするかが構文論点
（カンマ結合は SQL-92 非推奨形式で `;` 忘れの誤記とも衝突するため、明示 `CROSS JOIN` が本命）。

## 2. なぜ効くか（依頼元の分析・当方も同意）

1. **B128 Phase 2a（移動フレーム）の前提**＝製品別の 7 日移動平均には 2 軸の 0 埋めが必須。
   これが無いと 2a を出しても「直近 7 行 ≠ 直近 7 日」が製品別で残る（B134 の再来）
2. **2a 抜きでも単独で効く**＝直積があれば既存の固定境界ウィンドウ（v3.45.0）だけで
   「製品別・暦日ごとの残高推移」（依頼元 R17）が書ける。**ウィンドウ本体（レビュー高 9 の対象）に
   触らない**文法＋実行計画の話

## 3. 設計論点（評価時に決める）

- 構文＝`CROSS JOIN` を許すか、`GENERATE_SERIES` の 2 軸版か、`ON TRUE` 形か
- **行数ガード必須**＝直積は掛け算で増える。`GENERATE_SERIES` の 10,000 行ガードと同じ形
  （依頼元の規模は 365×8=2,920 行）。`EXPLAIN` に生成行数を出す（`row guard:` の前例に乗る）
- 完全入力・FULL_SCAN との関係、CTE/一時テーブル/物理の 3 経路

## 4. 依頼元の実需

製品別 7 日移動平均（需要ペースの平滑化）・欠品日の可視化・R17 の製品別暦日化。
**急ぎなし・止まっている作業なし**（意見であり要望ではないと明言）。
