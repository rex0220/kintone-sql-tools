# B215 結合キーで JOIN 先を絞るとき（B150）、前の外部結合が空文字で埋めた行のキーを数えず、当たる行を黙って取り落とす

- 起票: 2026-11-11（**B214 の Codex レビューの BLOCKER** から。KJ-12 の続き）
- ステータス: 🚧 **実装済み（枝 `b214-join-on-empty-physical` の PR・リリース待ち）**。**B214 と同じ版（v3.96.0）で出す**（2026-11-11 Takashi「1」）
- 種別: バグ（正しさ・**fail-open＝黙って誤った結果**）**※ 結果が変わります**
- 関連: B150（結合キーによる取得範囲の絞り込み）／B153（空の結合キーは空文字どうしで一致）／[B214](ksql_b214_join_on_rowless_physical_issue.md)
- 確かめのスクリプト: `kintone-plugin/work-link/ksql-kj12-codex-check.mjs`（模擬の client）

## 1. 実測（v3.95.0）

APP3 に `{ コード: "", 値: "empty-match" }` が 1 件。

```sql
SELECT o.明細キー, p.値 FROM APP1 AS t
RIGHT JOIN APP2 AS o ON t.キー = o.明細キー     -- APP1 に当たらない行 Q、APP2 に Z
INNER JOIN APP3 AS p ON t.キー = p.コード;      -- RIGHT JOIN で埋めた t.キー = "" と p.コード = "" は当たるはず
```

| 形 | v3.95.0 |
|---|---|
| 上の `RIGHT → INNER` | **0 行**（APP3 を `コード in ("Q")` で読み、空のキーの行を取らない） |
| 同じで最後を `LEFT JOIN` にした形 | 1 行（`["Z","empty-match"]`）＝メモリ上の結合は空文字どうしで当てる |
| `FROM APP1 LEFT JOIN #o（一時テーブル）… INNER JOIN APP3 ON o.明細キー = p.コード` | **当たる行を落とす**（`#o` の行のキーだけで絞る） |

同じ SQL で、最後の JOIN が `INNER` か `LEFT` かで行が変わる（`INNER` は `LEFT` の部分集合のはずなのに、`LEFT` で出る行が `INNER` で消える）。
エラーにならず、**黙って誤る**。

## 2. 原因

B150 の `tryFetchJoinRecordsBySourceKeys` は、結合キーの一覧を**元の表の行**（`tables.get(sourceAlias)`）から作る。
前の外部結合で一致しなかった行は、メモリ上の結合でその表の列が空文字に埋められ（`LEFT JOIN` の右・`RIGHT JOIN` の左）、
B153 の意味論で JOIN 先の空のキーと一致する。ところが元の表の行にはその空文字が無いので、`in (...)` に `""` が入らず、
JOIN 先の空のキーの行を読まない。元の表が 0 件なら `EMPTY_SOURCE` で JOIN 先を 1 件も読まない。

B150 は「取得を減らす最適化で、結果は変えない（取った後のメモリ上の照合が正）」という約束だが、取る範囲が答えを含まなかった。
元の表が**前の JOIN の物理 APP**のときは、JOIN 先の取得を並べて始めるので元の表がまだ `tables` に入っておらず、
絞り込みを使わずに全件を読む（誤らない）。誤るのは、元の表が **FROM の表**か、**前の JOIN の一時テーブル・CTE**のとき。

## 3. 直し方（実装済み）

`joinKeySourceMayBeNullExtended`（`execute.ts`）が「この JOIN より前の外部結合で元の表が空文字に埋められ、
その行がこの JOIN まで残りうるか」を SQL と分かっている件数から決める:

- 前の `LEFT JOIN` の右の表は、その JOIN までに行が残りうるなら埋められうる。前の `RIGHT JOIN` より左の表は、
  その `RIGHT JOIN` の右に行がありうるなら埋められうる。
- 件数が分かる表（取得済み・実体化済み）が 0 件なら、その JOIN までの行は残らない（`INNER` / `CROSS` の相手、`RIGHT JOIN` の右）。
  そこで「埋められうる」をいったん消す（後ろの `RIGHT JOIN` で行が戻れば、また埋められうる）。
- 件数が分からない表（並べて取得している物理 APP・EXPLAIN の物理 APP）は「行がありうる」とみなす（結果を誤らない側）。

埋められうるなら:

- キーの一覧に `""` を足し、空値ありとして扱う。`in ("")` を受ける型（`SINGLE_LINE_TEXT` など B150 の表のとおり）は
  `in (…, "")` で絞り込みを続け、それ以外の型（`$id`・日付など）は全件取得に落とす（B150 の既存の規則）。
- `""` も重複を除いた 1 キーとして 300 の上限に数える（空でないキーが 300 個なら 301 個になり、全件取得と警告になる。
  すでに空のキーを含む 300 個なら 300 個のまま）。
- 元の表が 0 件でも `EMPTY_SOURCE` にしない（埋められた行が残るため）。
- **EXPLAIN も同じ関数を使い**、静的な実体化の元（`GENERATE_SERIES` など）で表示する `in (...)` に `""` を足す（計画と実行を一致させる）。
  EXPLAIN は物理 APP の件数を知らないので、前に 0 件の物理 APP があっても「行がありうる」として `""` を足した形を表示する
  （実行時はその物理 APP が 0 件なら足さない＝実行のほうが狭い）。

**変わるもの**: 外部結合の後の `INNER JOIN` で、JOIN 先に空のキーの行があるとき、その行が結果に出る（今までは落ちていた）。
埋められうるときは JOIN 先の空のキーの行も読む。空値を受けない型のキーと、空でないキーがちょうど 300 個のときは、JOIN 先を全件読む
（読む量が増え、`maxRecords` に当たることがある）。
**変わらないもの**: 前に外部結合が無い JOIN の絞り込み（`in (...)` の中身も同じ）、外部結合の後に 0 件と分かっている表で行が消える形
（Codex レビュー 2 回目の反例。v3.95.0 と同じく JOIN 先を読まない）、JOIN 先に空のキーの行が無いときの結果の行。

## 4. 受入条件と試験

`src/__tests__/b214JoinOnRowlessPhysical.test.ts` の「B215」の 11 件:

1. `RIGHT → INNER`（APP1 が 0 件／当たらない行あり）が 1 行を返し、`RIGHT → LEFT` と同じ。
2. `LEFT → INNER`（真ん中が一時テーブル）で、APP3 への問い合わせが `コード in ("Z","")`。
3. 前に外部結合が無ければ `in (...)` に `""` を足さない（従来どおり。比べ役）。
4. 外部結合の後に空の `CROSS JOIN` で行が消えたら `""` を足さず、JOIN 先（`$id`）を読まない（`maxRecords: 1` でも止まらない）。
5. 空の `CROSS JOIN` の後に `RIGHT JOIN` で行が戻れば `""` を足して当てる（`コード in ("")`）。
6. `in ("")` を受けない型（`$id`）は全件取得（問い合わせに `in (` が無い）。
7. 空でないキー 300 個＋`""` は 301 個として全件取得と警告。299 個＋空のキーは 300 個のまま `in` で絞る。
8. EXPLAIN が静的な元で `コード in ("1","2","")` を表示し、物理 APP の元では `JOIN_KEY_VALUES_RUNTIME` のまま（どちらも records API 0 回）。

直す前の本体で通るのは、v3.95.0 と同じ動きを確かめる 4 件（3、4、7 の 299 個の形、8 の物理 APP の形）だけで、ほかの 7 件は落ちる。
4 は Codex レビュー 2 回目の反例で、1 回目の直し（件数を見ない判定）では落ちることを確かめた。B150・B153・B155・B167 の既存の試験は変わらない。
