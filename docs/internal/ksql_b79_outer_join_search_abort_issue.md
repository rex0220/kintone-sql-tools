# B79 外部結合＋検索打ち切りで誤った値を返す（silent wrong result）

- 起票: 2026-07-27（B76 Phase A Step 4 のレビュー中に発見）
- ステータス: ✅ **方針決定済み（2026-07-27 オーナー決定＝案 A: 外部結合の `searchAborted` を fail-closed）**。実装未着手。
- 関連: [B76 Phase A 仕様 §16](ksql_b76_join_pushdown_phase_a_spec.md) / B7（プラグイン検索打ち切り検出・v3.10.0）

## 1. 事象

kintone の検索が 10 万件で打ち切られた（`searchAborted: true`）とき、
**`LEFT` / `RIGHT JOIN` は「行が減る」のではなく「値が間違う」。**

### 1.1 実測

右表（APP200）だけ打ち切りが起き、結合相手の行が取得できなかった状況を模擬した。

| | 結果 | 性質 |
|---|---|---|
| **INNER JOIN** | `rows=[]` ＋ 警告 | **行の欠落**（返る行は正しい） |
| **LEFT JOIN** | `rows=[{"$id":"1","目標金額":""}]` ＋ 警告 | **誤った値**（正しくは `300`） |

正常時は両者とも `rows=[{"$id":"1","目標金額":"300"}]` を返す。

**LEFT JOIN では、結合相手が取得できなかっただけなのに null 拡張され、
「該当なし」という嘘の値が返る。**

### 1.2 警告文が実態を伝えていない

```
検索が 10 万件で打ち切られ、結果が欠落した可能性があります。
```

「**欠落**」としか言っておらず、**値が誤り得ること**を伝えていない。
利用者は「件数が減っているかもしれない」とは読むが、
「表示されている `目標金額` が実際とは違う」とは読み取れない。

## 2. なぜ危険か

- **行が減る**のは、利用者が警告を見れば「不完全な結果だ」と判断できる。
- **値が間違う**のは、**その行自体は正しく見える**ため判断できない。
  集計に使えば合計・平均が静かにずれる。
- B78（ユーザー系フィールドへの `=` が黙って0件）と同じ **silent wrong result** の class。

## 3. 現状の挙動の一覧

| ケース | 検索打ち切り時 | 性質 |
|---|---|---|
| 単一表 | 警告＋部分結果 | 行の欠落 |
| INNER JOIN | 警告＋部分結果 | 行の欠落 |
| **LEFT / RIGHT JOIN** | **警告＋部分結果** | **誤った値** |

**最も危険なケースが、最も軽い扱いを受けている。**

## 3.5 オーナー決定（2026-07-27）＝案 A

**外部結合で `searchAborted` が起きたら fail-closed（エラー）とする。**

- 判断基準は B78 と同じ＝**現在成功して見えるクエリは実際には誤った値を返しているので、
  エラー化しても正しい結果を失わない**。
- **案 B（警告文の是正）は案 A と併せて実施する**。§4 に「いずれの案でも必要」と記載のとおり。
  「結果が**欠落**した可能性」では、**値が誤り得る**ことが伝わらない。
- **INNER JOIN と単一表は対象外**（行の欠落であり警告で足りる）。
- B79 は **B80 と同一リリース**で出す（テーマ＝「失敗時の挙動を正直にする」）。
  **破壊的変更を含む**ため移行案内を CHANGELOG・言語リファレンス・`release/README.txt` の3箇所へ。

### 実装時の注意

- B76 Phase A で INNER JOIN のみ fail-closed にして**危険度と逆向き**になり撤回した経緯がある
  （B76 spec §16）。**同じ轍を踏まないこと**＝対象は**外部結合のみ**で、
  INNER JOIN・単一表の警告経路は変えない。
- B76 で `"joinPlan" in pushdownPlan` という**plan オブジェクトの存在だけ**で判定して
  「押し下げが1件も起きていないクエリまでエラー」にしてしまった。
  **判定条件は「外部結合であること」に紐づけ、plan の有無に依存させないこと。**
- **B6（KLIKE 外部結合 非 nullable 側の押し下げ解禁・却下）**の記録を着手時に確認すること。

## 4. 方針案（決定済み・記録として保持）

| 案 | 内容 | 影響 |
|---|---|---|
| **A** | **外部結合で `searchAborted` が起きたら fail-closed**（エラー） | 誤値を根絶。破壊的変更だが、現状は誤った値を返しているので「正しい結果を失わない」 |
| B | 警告文を「値が誤り得る」旨へ是正するのみ | 非破壊。ただし silent wrong result は残る |
| C | 非 nullable 側（駆動表）の打ち切りは警告、null 生成側の打ち切りは fail-closed | 精密だが、どちら側が打ち切られたかの追跡が要る |

**Claude の推奨は A**。B78 で「黙って0件」をエラー化したのと同じ判断基準
（**現在成功して見えるクエリは実際には誤りなので、エラー化しても正しい結果を失わない**）が
そのまま当てはまる。ただし B の警告文是正は**いずれの案でも必要**。

## 5. スコープの論点

- **INNER JOIN と単一表は対象外**（行の欠落であり、警告で足りる）。
  B76 Phase A で INNER のみ fail-closed にしたが、危険度と逆向きだったため撤回した（B76 §16）。
- 外部結合の null 生成側という概念は **B6（KLIKE 外部結合 非 nullable 側の押し下げ解禁・却下）**
  と同じ領域に触れる。着手時に B6 の却下記録を確認すること。
- 検索打ち切りの検出自体は **B7（v3.10.0）**で実装済み。本課題は「検出後にどう振る舞うか」。

## 6. 補足

B76 Phase A の変更が原因ではなく、**B7 以来の既存挙動**である。
B76 Step 4 のレビュー中、「JOIN は本当に単一表より危険か」を検証する過程で発見した。
