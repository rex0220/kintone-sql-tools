## 1. 決まっていること（変更しない・方針論に戻らない）

- **Phase 1 の対象は整数と日付（`DATE`）**（オーナー判断 2026-08-07）。
  **小数 step・`DATETIME` / `TIME` 系列は Phase 1 に入れない**（Phase 線引きに理由を書く）
- **名前は `GENERATE_SERIES`**（PG 互換名。「最初に書かれる形」で選ぶ——起票 §2）
- **挙動の基準は PostgreSQL**（起票 §1 の表を正とする）＝
  生成値は `stop` を**超えない**／`start > stop` で step 正（逆も同じ）は**エラーにならず 0 行**／
  **`step = 0` はエラー**
- **kSQL に NULL は無い。** 引数が空文字・非数値・非日付なら **`ArgumentError`**
  （B124 の `@変数` と同じ整理。`NaN` や空行にしない）
- **構文の第一候補は文 CTE 形**＝`WITH s AS (GENERATE_SERIES(1, 5)) SELECT ... FROM s`
  （`WITH d AS (DESCRIBE APP100)` の前例に乗る）。**`FROM` 直置きは Phase 1 に入れない。**
  コードを読んで文 CTE 形に重大な障害があれば、**採用せず「代替案」として明記**すること
- **`INTERVAL` 型は導入しない。** 日付 step の表現はあなたが設計する
  （第一候補は PG に近い `'1 day'` 形式の文字列。**対応する単位を仕様で列挙**すること。
  `day` は必須。`week` / `month` / `year` は要否を判断し、**入れるなら月末規則を明記**する）
- **行数上限のガードは必須**（無から行を作る初の機能。既存の行数上限との関係を仕様で決める）
- **価値の本体は「系列を左辺にした `LEFT JOIN` の 0 埋め」**（B134）。
  受入条件に必ずこのシナリオを含める

## 2. 確定している事実（再導出せず、そのまま使うこと）

- **FROM なし `SELECT ... UNION ALL` で無から行を作れる**（B134 で実測済み。レシピ R7 が同形）。
  「kSQL は無から行を作れない」という前提は既に崩れている
- **文 CTE の前例**＝`DESCRIBE` / `SHOW APPS` は `WITH` の中で文として使える
  （v3.49.0 / v3.56.0 の移行例が `WITH d AS (DESCRIBE APP100) SELECT ...`）
- **CTE 実体化後の CTE 間 JOIN は動く**（B51 / B52 で修正済みの経路）
- **空文字は算術では 0 になるが、比較では 0 と等しくない**（横断仕様参照）
- **値参照ウィンドウ（v3.51.0 の `LAG` / `LEAD`）は引数の型メタデータを引き継ぎ、
  CTE の次段でも数値順・日付順を維持する**——生成列の型メタ設計の先行例

## 3. R1 に必ず含めること

1. **構文**（完全な文法。引数の型と省略規則、文 CTE としての位置づけ、複数 CTE との併用）
2. **規則**（整数系列・日付系列それぞれの生成規則。境界値の表＝
   `stop` ちょうど／超える直前／0 行になる 4 象限／`step` 省略時）
3. **生成列の仕様**＝既定の列名（1 つに固定）・`AS` での改名可否・
   **型メタ**（生成列が数値／日付としての比較・ソート・`ORDER BY` 規則を持つこと。
   `LAG` / `LEAD` の型メタ引き継ぎと同じ整理でよいかを明示）
4. **エラー診断**＝`step = 0`・非数値/非日付/空文字引数・引数の型不一致
   （整数 start + 日付 stop 等）・上限超過。**Phase 1 対象外の形
   （小数 step・`DATETIME`・`FROM` 直置き）を書いたときの診断も含める**
   （静かに 0 行や誤値を返す形を作らない）。人間向け本文に内部語を出さない（B148 の整理を踏襲）
5. **行数上限ガード**＝上限値の根拠・既存上限との関係・超過時のエラー文
6. **`EXPLAIN` の表示**（生成系列はレコード API を呼ばないこと、計画にどう出すか）
7. **適用単位**（`WITH` の中だけか。`UNION` の arm・サブクエリ・一時テーブル source・
   `INSERT ... SELECT` source からの参照可否を明示）
8. **負ステップの扱い**＝入れるか外すかをあなたが判断し、**どちらでも理由と診断を明記**
9. **受入条件**＝**通るもの／エラーになるもの／adversarial／回帰**。
   **完全な SQL で書き、公開結果（結果オブジェクト・送出される例外・
   mock client のレコード API 呼び出し回数）で観測できる形にすること。**
   **境界値は桁を変えて両方向**（B119〜B122 の教訓＝桁が揃うと文字列比較でも正答する）。
   **`LEFT JOIN` 0 埋め（取引の無い日が 0 で並ぶ）を必ず含める**
10. **Phase の線引き**（Phase 1 に入れないものと、その理由）
