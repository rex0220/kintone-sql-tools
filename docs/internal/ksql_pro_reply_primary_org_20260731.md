# 本文（送付版）

## 【返信】再現していただき、ありがとうございます — こちらの文書の穴も見つかりました

**`5 = 5` の実測、こちらでは出せなかったものです。**

## 1. 実測の受け取り

| 利用者 | 結果 |
|---|---|
| 優先組織あり | 正しく絞られる（3 / 全 5 件） |
| 優先組織なし | **条件ごと無視され全件（5 = 5）** |

**公式の記述どおりでした。**
**こちらに欠けていたのは「優先組織を持たないユーザー」だけで、
挙動の理解そのものは合っていたことになります。**

**判定式（`in` と `not in` の突き合わせ）については、`in = 全件` の側が確認されました。**
**`not in` 側は測られていないので、判定式全体としてはまだ半分です。**
**必要になったときの参考まで。**

## 2. **この報告で、こちらの文書の穴が見つかりました**

**言語リファレンスの `PRIMARY_ORGANIZATION()` の説明は、2 箇所とも
「DML を拒否する」しか書いていませんでした。**

**`SELECT` で黙って全件になることが、どこにも書かれていませんでした。**

**CHANGELOG・`release/README.txt`・GitHub Release には書いたのに、
利用者が SQL を書きながら参照する文書に無い**——という状態でした。

### 2.1 直した内容

- **`SELECT` と DML で扱いが分かれることを、表で示した**
- **`SELECT` では画面から区別がつかず、警告も出せないことを明記した**
- **ダッシュボードのように結果だけを見せる用途では、
  利用者側での案内を検討すべきと書いた**——**まさに今回そちらが実装された形です**
- **根拠を「公式の記述」から「公式の記述＋2026-07-31 実機で再現を確認」へ更新した**

**注意書きを実装された判断が、結果としてこちらの文書を直しました。**

## 3. 実装について

**閲覧側に置く形、`getOrganizations()` を 1 画面 1 回、
判定できない環境では何も出さない**——いずれも妥当だと思います。

**とくに「誤警告は無警告より悪い」という線引き**は、
こちらが `SELECT` を素通しにした理由と同じ考え方です。
**判別できないときに何かを言うと、言われた側は判断を誤ります。**

**関数を使うペインにだけ出る**のも、そのとおりだと思います。

> **こちらの課題（B102）では、この検出をエンジン側へ持つ案を保留にしていました。**
> **プラグイン面だけで実装できる一方、MCP や CLI では同じことができず、
> 面によって挙動が変わるためです。**
> **そちらの層で解決されたので、エンジン側で持つ必要は当面ありません。**
