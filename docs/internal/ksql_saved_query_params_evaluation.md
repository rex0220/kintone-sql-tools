## 1. 目的（何をする機能か）

現行の保存クエリは SQL 文字列をそのまま保存するため、条件値も SQL に固定される。

```sql
-- 現状: 値がハードコードされ、用途が同じでも値ごとに別クエリを量産する
SELECT * FROM APP100 WHERE 登録日 >= '2026-01-01'
```

名前付きパラメータを導入し、同じテンプレートへ実行時の値だけを安全に渡せるようにする。

```sql
-- 導入後: 構造・文型・対象アプリは固定し、値だけを実行ごとに差す
SELECT * FROM APP100 WHERE 登録日 >= :since AND 状態 IN (:statuses) LIMIT :limit
```

主利用者は MCP クライアント（AI）で、`ksql_run_saved_query(name, params)` で値だけを渡す運用を想定する。

## 2. 仕様案サマリ（R2）

仕様の詳細・更新履歴・テスト計画・受け入れ条件は [仕様本体](./ksql_saved_query_params_spec.md) を正とする。ここでは設計の骨子のみ。

### 2.1 設計原則

1. パラメータは**値位置だけ**で使用可。テーブル名・フィールド名・alias・演算子・SQL キーワードは動的化しない。
2. **生の文字列置換はしない**。lexer/parser が `ParamRef` を認識し、専用バインドフェーズで既存リテラル AST（`STRING`/`NUMBER`/`IN_LIST`）へ解決する。
3. バインド後の AST に `ParamRef` を残さない。既存の検証・WHERE pushdown・評価器・kintone query 変換は既存リテラルだけを受け取る。
4. 保存時・実行時の双方で、SQL 内の参照とパラメータ宣言の整合を検証する。
5. 未指定・余剰・型不一致・使用位置不一致は暗黙補正せずエラーにする。

### 2.2 初回スコープ

**含める:** `ksql_run_saved_query` の `params` 入力／`:name` 記法／scalar（`string`/`number`/`integer`）と list（`string[]`/`number[]`）／`IN (:list)` 限定のリスト展開／宣言（名前・型・必須・default・説明）／`list_queries`・`get_query` での宣言提示／SELECT と DML 保存クエリ（既存 DML 承認ガード維持）。

**含めない:** `ksql_query`/`ksql_mutate` 等の直接 `params`／位置パラメータ `?`／識別子・テーブル・profile・演算子のパラメータ化／式・scalar subquery の注入／CLI・プラグイン UI／SQL 結果キャッシュ／**複文（バッチ）**（save・run とも既存どおり単文限定）／**任意フィルタ**（値未指定で述語ごと省略する挙動）。

### 2.3 主要な設計判断

| 論点 | 決定 |
|---|---|
| バインド方式 | AST バインドフェーズ（parse 後・実行前に既存リテラル AST へ解決。`evalWhere`/`whereToKintone` へ `params` を配管しない） |
| 記法 | `:name`（lexer 未使用の `:` を安全に追加。ISO 標準ではなく慣用記法） |
| パースモード | lexer は常に `PARAM` token を生成、parser の `allowParams` モードで受理/拒否（字句・構文の二重実装を回避） |
| optional の穴 | `required: false` は **default 必須**。optional かつ default なしは禁止（未解決 ParamRef を原理的に排除） |
| カタログ version | 条件付き v2 移行。全 param 空の間は v1 維持、初回 param 保存時のみ v2 化、自動降格なし |
| 単文限定 | save・run とも `requireSingleStatement` を通す既存仕様を維持 |

## 3. 効果評価（確定版）

### 3.1 中核価値

**この機能の最大価値は「既存機能の安全性向上」ではなく、動的値を必要とする保存クエリを、生 SQL 生成や危険な文字列置換へ逃げず、安全な構造制約の下で導入できること。**

固定値の保存クエリはそもそも外部入力を持たないため、「固定 SQL より安全になる」という比較は成り立たない。価値は比較軸ごとに評価する。

| 比較対象 | 効果 |
|---|---|
| 固定 SQL 保存クエリ | 再利用性は上がるが、外部入力が新たに増える（安全性が上がるわけではない） |
| 文字列置換方式 | AST bind により**大幅に安全** |
| AI が毎回生 SQL を生成 | 保存後の各実行では値だけを bind できるため、毎回生 SQL を渡す場合より**構造を限定できる**（ただし AI が `save_query` でテンプレートを更新できる権限モデルは別途考慮が必要。§3.3 参照） |

### 3.2 集約効果

**SQL 構造が同一でリテラル値だけが異なる保存クエリを、1 テンプレートへ集約できる。** 効果の大きさは利用パターン依存で、実測根拠のない「N 倍減」は仮説に留める。SELECT 列・JOIN・並び順が違えば統合できない点に注意。

- 定型レポートを日付・状態・担当だけ変えて繰り返す運用 → 効果大
- その都度違う分析を書き捨てる運用 → 効果小

### 3.3 安全性の担保（信頼境界の正確な表現）

安全性を担保するのは「人間が固定した信頼済みテンプレート」ではなく、**事前に検証・保存された SQL 構造**という事実と、次の仕組みである。

- 保存時・実行時の構文検証
- readOnly / DML 分類
- **DML 実行時の明示的な確認入力（`confirmText`）と影響行数上限（`dmlMaxRows`）。人間承認になるかは MCP ホスト側の tool confirmation 運用に依存する**（`allowDml`/`confirmText`/`dmlMaxRows` は AI 自身が値を指定できるため、コード上は「明示的な実行条件」であって人間承認そのものではない）
- 値位置限定の bind

> **重要:** `ksql_save_query` は MCP ツールとして公開されており（`src/mcp/index.ts`）、`upsertSavedQuery` は既存名を上書きする（`src/mcp/savedQueries.ts`）。したがって **AI クライアント自身がテンプレートを新規作成・更新できる**。「人間が固定した信頼テンプレート」という運用は現行の権限モデルからは導けない。

「人間承認済みテンプレート」を本当に保証したいなら、本仕様のスコープ外として別途以下が必要：保存/更新ツールの実行環境での無効化・provenance（保存者記録）・immutable/承認済みフラグ・更新権限の分離。

### 3.4 AI エージェントへの副次効果

`get_query`/`list_queries` がパラメータ宣言（名前・型・必須・説明）を返すため、AI は全 SQL を読まずにテンプレートの要求を判断でき、選択精度が上がる。ただし**一覧の宣言量が増えるため、トークン効率はクエリ数次第**（無条件の改善ではない）。

### 3.5 コスト・リスク（効果を割り引く要因）

- **実装コスト中〜大**: lexer（PARAM token）・parser（`allowParams`）・新 AST ノード・バインドフェーズ・AST 入口共有・カタログ v2 移行・MCP メタデータ同期。言語コアに触る。
- **一方向ドア**: 初回パラメータ保存で catalog が v2 化し、ダウングレードで全保存クエリが使えなくなる（条件付き移行で緩和済みだが残存）。
- **機能の穴**: 任意フィルタ（値があれば絞る／なければ述語省略）が非対応 → 効果の上限を規定する。
- **MCP 限定**: 初回は CLI/プラグイン非対応。CLI 主体ユーザーには効果が届かない。

## 4. 結論 — 条件付きで実装推奨

**動的値を必要とする保存クエリを、生 SQL 生成や文字列置換へ逃げず、安全な構造制約の下で導入できる。着手には AST 入口共有と version 2 移行手順の確定が必要。**

### 4.1 着手条件（3 点）

1. 同一 SQL 構造で値だけ変える**繰り返し発生する具体的な実需**が確認できる（機械的な件数ではなく、反復性のある実需かで判断する）
2. **バインド済み AST を文字列化せず実行できる AST 入口**を設計する
3. **catalog v2 移行時のバックアップ・rollback 手順**を確定する

### 4.2 判定

| 状況 | 判定 |
|---|---|
| MCP で「同じクエリに値だけ変えて繰り返し実行」している実需がある | **実装推奨** |
| 「将来使いそう」という段階（実需未確認） | **保留** |

理由は、単なる省力化ではなく、動的値を扱う際に AI の生 SQL 生成や危険な文字列置換を避けられるため。MCP から保存クエリを繰り返し実行する製品方針とも合う。

一方、実需が未確認なら即実装は非推奨。言語コア・実行経路・カタログ移行まで触る中〜大規模変更であり、固定 SQL だけで足りる状況では費用が先行する。

## 5. レビュー来歴

- 設計評価（初版）: 用途の確認（保存クエリのパラメータ化）→ 方式B・値限定・段階リリースを提示
- codex 効果外レビュー → キャッシュ論点撤回・readOnly→DML 化の根拠修正・AST 伝播をバインドフェーズへ
- 仕様 R1（自己レビュー）: 単文スコープ／NULL・任意フィルタの穴／v2 全滅リスク／パースモード二重化を指摘（うち単文の save 側ガードは自己誤読を後に訂正）
- 仕様 R2: R1 の3点を反映（optional は default 必須／条件付き v2／lexer 共通化＋`allowParams`）。単文制約は新規の制約ではなく、save・run とも `requireSingleStatement` を通す既存仕様の確認として補足（R1 の save 側ガード欠如という指摘は自己誤読で、後に訂正）
- 効果評価 → codex 効果レビュー: 比較軸の限定・信頼境界の訂正（AI がテンプレートを作成/更新可）・集約効果は仮説・リスク抑制は時期尚早、を反映
- 効果レビュー最終補正: DML の「明示承認」→「明示的な確認入力と影響行数上限。人間承認は MCP ホストの tool confirmation 運用依存」に表現修正

裏取りした事実:
- `:` は現行 lexer の演算子として未使用（`tryReadOperator` に分岐なし）→ 既存 token との直接的な構文衝突は確認されていない（parser 全経路・エラー位置への影響は実装検証が必要）
- `buildCacheContext` は profile/APP binding のメタデータキャッシュキーであり SQL 結果キャッシュではない → バインド値は含めない
- `ksql_save_query`・`ksql_run_saved_query` とも `requireSingleStatement` を通す → 単文限定
- `parseSavedQueryCatalog` は `version !== 1` を厳格拒否し既知フィールドのみ再構築 → version 決定と条件付き移行の根拠
- `ksql_save_query` は MCP 登録ツール（`index.ts`）＋ `upsertSavedQuery` は既存名上書き → AI がテンプレートを作成/更新可能
