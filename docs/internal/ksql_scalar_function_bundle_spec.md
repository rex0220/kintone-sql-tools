第2部は「**文書どおりに書くと必ず失敗する**」「**不正入力が黙って別の結果になる**」ものを含み、関数追加より**優先度が高い**。§6.4 でリリース順の選択肢を示す。

## 1. 選定方針: 「関数ファミリーを欠けたまま出さない」

追加候補は「主要 RDB にあるから」ではなく、**既存関数との対称性**と**代替不能性**で選ぶ。

| ファミリー | 既存 | 欠け | 判断 |
|---|---|---|---|
| 丸め | `ROUND` `FLOOR` `CEIL`/`CEILING` | **`TRUNCATE`** | **追加**（切り捨てだけ無い＋`FLOOR` で代替不能・§2.1） |
| 部分文字列 | `SUBSTRING`/`SUBSTR` | **`LEFT` `RIGHT`** | **両方追加**（`RIGHT` は代替不能・`LEFT` は対称性・§2.2） |
| 文字列検索 | `LIKE`（有無のみ） | **`INSTR`**（位置） | **追加**（代替なし） |
| 最大最小 | 集約の `MAX`/`MIN` | **`GREATEST`/`LEAST`**（行内） | **追加**（`CASE` は3列以上で著しく冗長） |
| 桁揃え | なし | **`LPAD`/`RPAD`** | **追加**（伝票番号の 0 埋め・kintone 実務で頻出） |
| 日付 | `YEAR` `MONTH` `DAY` `DATE_ADD` `DATEDIFF` `DATE_FORMAT` | **`LAST_DAY`** | **追加**（月末日・式が煩雑） |
| 日付加減算 | `DATE_ADD` | ~~`DATE_SUB`~~ | **追加しない**（§2.6・実機で負数が動く） |

### 1.1 除外したもの

| 関数 | 理由 |
|---|---|
| **`DATE_SUB`** | `DATE_ADD(x, -1, 'DAY')` が**実機で正しく動く**（§2.6）。kSQL の `DATE_ADD` は `INTERVAL` 構文ではなく**3 引数で符号を内包**するため、`DATE_SUB` は単なる言い換えで対称性の問題も起きない |
| `EXTRACT` | `YEAR`/`MONTH`/`DAY` で足りる。`EXTRACT(HOUR …)` の需要が立証されてから |
| `POSITION` | `POSITION(sub IN str)` は **`IN` 演算子と構文衝突**する。MySQL 系の `INSTR` に統一（kSQL は `LIMIT`/`DATE_FORMAT` など MySQL 寄り） |
| `SIGN` `LOG`/`LN`/`EXP` `REVERSE` `REPEAT` `TRUNC` 以外の数学関数 | 需要が薄い。**関数名は予約語になる**ため、同名フィールドを壊すリスクに見合わない |
| `LEN` `NVL` `IFNULL` `GETDATE` `DATEADD` `TO_CHAR` | **別名だけの追加**。`LENGTH`/`ISNULL(a,b)`/`NOW()`/`DATE_ADD`/`DATE_FORMAT` が既にある。予約語を増やす価値なし |

> **`ISNULL(a, b)` は既に `NVL`/`IFNULL` 相当**（2 引数・SQL Server 系）。ただし**言語リファレンスに未記載だった**ため v2.14.1 で追記済み。

## 2. 追加する関数（実機で代替不能性を確認済み）

### 2.1 `TRUNCATE(x, n)` / `TRUNC(x, n)` — 切り捨て

- `n` 省略時は 0 桁（整数へ切り捨て）。負数 `n` は 10^n 単位（`ROUND`/`FLOOR`/`CEIL` の既存規則に合わせる）。
- **`FLOOR` では代替できない**。負数で結果が異なる:

| 式 | 結果 |
|---|---|
| `FLOOR(-1.5)` | `-2`（負の無限大方向） |
| `TRUNCATE(-1.5)` | `-1`（0 方向） |

金額の端数処理で実害が出る。`TRUNC` は別名。

### 2.2 `LEFT(x, n)` / `RIGHT(x, n)` — 先頭/末尾 n 文字

**両方を追加する**。

- **`RIGHT` は現状のどの式でも代替できない**（実機確認・§2.2.1）。
- **`LEFT` は `SUBSTRING(x, 1, n)` で代替できるが追加する**。理由:
  - **対称性**。`RIGHT` だけあって `LEFT` が無いのは利用者を迷わせる（どの RDB でも対）
  - **新規予約語がゼロ**（`LEFT`/`RIGHT` は `LEFT JOIN`/`RIGHT JOIN` で既にトークン登録済み）
  - パーサの曖昧性解消（`(` の先読み）は**両方で同じ処理**＝片方だけより実装が素直
  - 本プロジェクト自身が `CEIL`/`CEILING`・`POWER`/`POW`・`SUBSTRING`/`SUBSTR` と**親しみやすさを優先する前例**を持つ

#### 2.2.1 `RIGHT` が代替不能である根拠（実機実測・`会社名` = `株式会社サイボウズ商事`／11 文字）

| 式 | 結果 | 判定 |
|---|---|---|
| `SUBSTRING(会社名, 1, 4)` | `株式会社` | ✅ `LEFT(x,4)` 相当は書ける |
| `SUBSTRING(会社名, LENGTH(会社名))` | `事` | ✅ **関数は引数に渡せる** |
| `SUBSTRING(会社名, LENGTH(会社名) - 3, 4)` | ❌ **ParseError**（`-`） | **引数に算術が書けない** |
| `SUBSTRING(会社名, -4)` | `株式会社サイボウズ商事`（全文） | **負数開始が末尾切り出しにならない** |

→ `RIGHT` に必要な `SUBSTRING(x, LENGTH(x) - n + 1, n)` は**2 つの理由で書けない**。

> **`SUBSTRING` の引数に算術式を許す**案（`SUBSTRING(x, LENGTH(x)-3, 4)`）は、全関数の引数へ波及するため**別課題**（§7）。本仕様は `RIGHT` の追加で解決する。

### 2.3 `INSTR(str, sub)` — 部分文字列の位置

- 1-indexed。見つからなければ `0`（MySQL 準拠）。`SUBSTRING` が 1-indexed なので整合する。
- **代替なし**。`LIKE` は有無しか判らない。
- `POSITION` は採用しない（`IN` と構文衝突・§1.1）。

### 2.4 `GREATEST(a, b, …)` / `LEAST(a, b, …)` — 行内の最大/最小

- 可変長引数（`CONCAT`/`COALESCE` と同じ）。
- **集約の `MAX`/`MIN`（列方向）とは別物**であることを言語リファレンスで明示する（混同しやすい）。
- **比較規則は §3 に従う**（kSQL は型メタ非依存のスカラー評価のため、値ベース判定になる）。

### 2.5 `LPAD(x, n, pad)` / `RPAD(x, n, pad)` — 桁揃え

- `pad` 省略時は半角スペース（MySQL 準拠）。
- `x` の長さが `n` 以上なら**先頭 n 文字へ切り詰める**（MySQL 準拠）。
- 主用途は**伝票番号・コードの 0 埋め**（`LPAD(顧客No, 5, '0')` → `00007`）。kintone は数値フィールドを `"7"` の文字列で返すため需要が高い。

### 2.6 `DATE_SUB` を追加しない根拠（実機実測）

```sql
SELECT DATE_ADD(日付, -1, 'DAY') AS 前日, DATE_ADD(日付, -1, 'MONTH') AS 前月 FROM APP4221;
-- 日付 2026-07-15 → 前日 2026-07-14 / 前月 2026-06-15   ✅ 負数が正しく動く
```

kSQL の `DATE_ADD` は **`INTERVAL` 構文ではなく 3 引数**（`applyDateAdd(dateStr, n, unit)`）で**符号を内包**する。`INTERVAL n UNIT` 構文なら `DATE_SUB` に意味があるが、本形では単なる言い換え。→ **追加しない**（§1 の「ファミリーの欠け」にも当たらない）。

### 2.7 `LAST_DAY(d)` — 月末日

- 月次バッチの定番。現状は式が煩雑で実質書けない。
- 返却は `YYYY-MM-DD`（`DATE_ADD` と同じ形式）。

## 3. 共通の意味論

| 規則 | 内容 |
|---|---|
| **文字数の単位** | 既存 `LENGTH`/`SUBSTRING` と**同じ単位**に揃える（実装を共有する）。受入条件で既存関数との一致を固定する |
| **1-indexed** | `INSTR` の戻り値・`LEFT`/`RIGHT` の n は既存 `SUBSTRING` に合わせる |
| **数値化** | 数値引数は既存関数と同じく `Number()` 化。非数値は `NaN` 伝播（既存 `ROUND` 等と同じ） |
| **比較** | `GREATEST`/`LEAST` は **引数集合でモードを 1 回決めてから**最大/最小を取る（§3.1）。判定規則は `compareScalarValues` と同一だが、**そのまま畳み込まない**（推移律が無い） |
| **空文字** | **関数ごとに規定**する（§3.2）。「一律に空文字を返す」とはしない |

### 3.1 `GREATEST` / `LEAST` の比較規則（R4 で確定）

> **R1 の誤り**: 「`compareSortKeys` の自動判定と同じ規則」＋「空文字は辞書順で最小」と書いたが**両立しない**。`Number("") === 0` のため、`compareSortKeys` の自動判定では `GREATEST('', '-1')` が `''`（0 として `-1` より大きい）になり、「辞書順で最小」と矛盾する。

> **R2 の誤り（R3 で修正）**: 「`compareScalarValues` をそのまま畳み込む」としたが、**`compareScalarValues` は全順序ではない**（推移律が成り立たない）。`GREATEST` は畳み込みなので、順序が定まらないと**引数順で結果が変わる**。

#### なぜ畳み込めないか（推移律の破れ・R3 で追加）

`compareScalarValues` は**比較する 2 値ごと**にモードを決める（[scalarCompare.ts:26](../../src/core/scalarCompare.ts#L26) の `numeric = !isNaN(leftNum) && !isNaN(rightNum)`）。このため**非空値だけでも循環する**:

| 比較 | モード | 結果 |
|---|---|---|
| `'2' < '10'` | 両方数値 → **数値比較** | ✅ true（2 < 10） |
| `'10' < '1a'` | `Number('1a')` = NaN → **文字列比較** | ✅ true（`'0'`(0x30) < `'a'`(0x61)） |
| `'1a' < '2'` | 同上 → **文字列比較** | ✅ true（`'1'` < `'2'`） |

→ **`2 < 10 < 1a < 2`**。`GREATEST('2','10','1a')` は畳み込み順で `'1a'` / `'10'` / `'2'` の**いずれにもなる**。

> **§3.1 の「空文字は先に処理」では防げない**。循環は**非空値の間**で起きる。

#### 確定する規則: **引数集合でモードを 1 回だけ決める**

```
GREATEST(args):
  1. 全引数が "" なら "" を返す
  2. nonEmpty = 空文字を除いた引数          ← 空文字は常に最小（GREATEST では勝たない）
  3. numeric = nonEmpty が全て数値か        ← 集合単位で 1 回だけ判定
  4. numeric ? 複合キー (Number(x), x) で最大 : 文字列で最大   ← 二次キーは §3.1.1

LEAST(args):
  1. 引数に "" が 1 つでもあれば "" を返す   ← 空文字は常に最小
  2. numeric = args が全て数値か
  3. numeric ? 複合キー (Number(x), x) で最小 : 文字列で最小
```

- 「数値か」の判定は **`!Number.isNaN(Number(x))`**（`compareScalarValues:26` と同じ規則）。
- **モードが集合で 1 つに固まるため全順序になり、引数順に依存しない**。

#### 3.1.1 数値が同値な異表記の tie-break（R4 で追加）

集合モードだけでは**まだ引数順に依存する**。`'1'` / `'01'` / `'1.0'` は **`Number` が全て `1`** で、単純に畳み込むと「同値なら現在値を維持」となり**先頭の引数がそのまま残る**（実測: 6 順列で `'1'` / `'01'` / `'1.0'` と割れる）。kSQL の関数結果は**文字列**なので、数値が等しくても**観測可能な差**になる。

**確定する規則**: 数値モードでは **`(Number(x), x)` の複合キー**で比較する（数値が同値なら**元の文字列を辞書順で二次比較**）。

| 案 | 結果 | 判定 |
|---|---|---|
| (a) 数値結果を `String(最大値)` へ正規化 | `GREATEST('007','008')` = **`'8'`** | ❌ **採らない**。元の桁揃えが失われる。`LPAD` で 0 埋めする用途（§2.5）と正面から衝突し、**入力の情報を捨てる**（B1/B16 と同じ理由） |
| **(b) 数値同値なら元文字列で二次比較** | `GREATEST('007','008')` = **`'008'`** | ✅ **採用**。全順序かつ**元の表記を保持** |

`(Number(x), x)` は**辞書式順序**なので全順序＝引数順に依存しない（実測で全順列一致を確認）。

| 式（全順列で同一） | 結果 |
|---|---|
| `GREATEST('1','01','1.0')` | `'1.0'`（数値は同値 → 文字列で最大） |
| `LEAST('1','01','1.0')` | `'01'`（同 → 文字列で最小） |
| `GREATEST('0','-0')` | `'0'`（`0 === -0` → 文字列で `'-0' < '0'`） |
| `LEAST('0','-0')` | `'-0'` |
| `GREATEST('007','008')` | `'008'`（数値が異なるので二次キーは効かない・**桁揃えを保持**） |

#### `compareScalarValues` との関係（R3 で明確化）

**モード判定は `compareScalarValues` の n 項への自然な一般化**であり、別規則ではない。ただし**一致するのは「2 引数がどちらも非空、かつ数値同値でない」場合に限る**（R4 で限定）。

| 条件 | `compareScalarValues` との関係 |
|---|---|
| **非空 2 引数・数値同値でない** | **完全に一致**。`compareScalarValues` の `numeric` フラグ（両オペランドが数値）は **2 項における「集合が全て数値」そのもの**。→ `WHERE a > b` との整合が保たれる |
| **空文字を含む** | **一致しない**。本仕様の「空文字は常に最小」が優先する（§3.1・下記） |
| **3 引数以上の混在** | **一致しない**（集合モードが優先）。ただし `compareScalarValues` の畳み込み自体が**循環して答えを持たない**領域なので失うものは無い |
| **数値が同値な異表記** | `compareScalarValues` は `>`/`<` とも false（同値）で**勝者を決められない**。本仕様は §3.1.1 の二次キーで確定させる |

#### 空文字を含む場合に一致しない理由（R4 で明記）

`compareScalarValues` の空文字規則は**左辺が空のときだけ発火**するため**非対称**で、そのままでは −∞ の意図を満たさない（実測）:

| 呼び出し | 結果 | 本仕様 |
|---|---|---|
| `compareScalarValues('>', '', '-1')` | `false`（空は −∞ → 正しい） | `GREATEST('', '-1')` = `'-1'` |
| `compareScalarValues('>', '-1', '')` | **`false`**（左辺が空でないので −∞ 規則が発火せず `Number('') = 0` と比較して `-1 > 0` が false） | 同上 = `'-1'` |
| `compareScalarValues('<', '-1', '')` | **`true`**（`-1 < 0`） | `LEAST('-1', '')` = **`''`** |

→ **`compareScalarValues` は「`-1` の方が小さい」と言うが、v2.2.0 の意図は「空セルが −∞（最小）」**。本仕様は**その意図を対称化した先行規則**（空文字は常に最小）を優先する。**これは comparator の非対称性を正す方向**であり、v2.2.0 の意味論と矛盾しない。

例: `GREATEST('2','10','1a')` = **`'2'`**（`'1a'` が非数値 → 集合全体を文字列比較 → `'2' > '1a' > '10'`）。

理由:

- **非空かつ数値同値でない 2 項では `WHERE a > b` と同じ規則**（上記の表のとおり `compareScalarValues` と一致。空文字・数値同値は本仕様の規則が優先する）。
- **v2.2.0 で決めた空セル意味論をそのまま引き継ぐ**（空文字は最小＝ −∞ 相当）。独自規則を作らない。
- **既に `core/` にある leaf モジュール**の判定規則を流用するため §3.3 の循環参照が起きない。

#### なぜ空文字を「先に」処理するのか（集合モードだけでは足りない）

上の手順 1〜2 で空文字を先に確定させるのは、**集合モードに空文字を混ぜると −∞ 意味論が壊れる**ため:

- `GREATEST('', '-1')` を集合モードにかけると、`Number('') = 0`・`Number('-1') = -1` でどちらも数値 → 数値比較 → `max(0, -1) = 0` → **`''` が返る**（0 として `-1` に勝ってしまう）。
- v2.2.0 の空セル意味論では**空文字は最小**（−∞ 相当）。よって**空文字は比較に参加させず先に確定**させる。

これは `compareScalarValues` の 2 分岐とも結論が一致する:

- `'' vs 有限数` → −∞ 規則で空文字が小さい ✅
- `'' vs 非数値文字列` → 文字列比較で `'' < 'a'` ✅

確定する挙動（**受入条件に固定**）:

| 式 | 結果 |
|---|---|
| `LEAST('', '5')` / `LEAST('5', '')` | `''`（順序非依存） |
| `GREATEST('', '5')` / `GREATEST('5', '')` | `'5'`（順序非依存） |
| `GREATEST('', '-1')` / `GREATEST('-1', '')` | `'-1'`（順序非依存。空文字を先に除くため 0 として勝たない） |
| `LEAST('', 'a')` | `''` |
| `GREATEST('', '')` | `''` |
| **`GREATEST('2','10','1a')`**（全 6 順列） | **`'2'`**（非数値が 1 つでもあれば集合全体を文字列比較） |
| **`LEAST('2','10','1a')`**（全 6 順列） | **`'10'`**（同上） |
| `GREATEST('2','10')` | `'10'`（全て数値 → 数値比較） |

### 3.2 空文字の扱い（関数ごとに規定・R2 で追加）

「空文字入力は空文字を返す」という一律規則は**採らない**（`LPAD('', 3, '0')` や `INSTR('', '')` で一般的な意味論と衝突するため）。

| 関数 | 空文字の扱い | 期待結果 |
|---|---|---|
| `LPAD('', 3, '0')` | **パディング対象として扱う**（空文字を返さない） | `'000'` |
| `RPAD('', 3, '0')` | 同上 | `'000'` |
| `LEFT('', 3)` / `RIGHT('', 3)` | 切り出し元が空 | `''` |
| `INSTR('', 'a')` | 見つからない | `0` |
| `INSTR('abc', '')` | **空文字は先頭で見つかる**（MySQL 準拠） | `1` |
| `INSTR('', '')` | 同上 | `1` |
| `GREATEST`/`LEAST` の空文字引数 | §3.1 の比較規則に従う（スキップしない） | 上表 |
| `TRUNCATE('', n)` | 既存 `ROUND('')` と同じ（`Number('') = 0`） | `0`（既存関数と一致させる） |
| `LAST_DAY('')` | 既存 `DATE_ADD('')` と同じ（`dateStr.length < 10` で入力をそのまま返す） | `''` |

> `TRUNCATE`/`LAST_DAY` は**既存の同系関数と挙動を揃える**ことを優先する（新規則を作らない）。受入条件で既存関数との一致を固定する。

### 3.3 比較ロジックの共有と循環参照（R2 で追加・R4 で更新）

**`compareSortKeys` を `evalFunc` から呼んではいけない**。

- `compareSortKeys` は **`process.ts:594` の非 export 関数**（R1 の `process.ts:559` は誤り）。
- import の向きは **`process.ts` → `evalFunc.ts`** および **`evalWhere.ts` → `evalFunc.ts`**（`evalFunc` が最下層）。`evalFunc` から `process` を import すると**循環参照**になる。

**解決**: 新規抽出は不要。**既存の `core/scalarCompare.ts` を使う**（`core/` は leaf で、`evalWhere.ts` / `execute.ts` が既に import 済み）。`evalFunc.ts` から追加で import しても循環しない。

**`compareSortKeys` と統合しない理由**（規則が違ってよい根拠）:

| | 入力 | 使えるメタ |
|---|---|---|
| `compareSortKeys`（ORDER BY） | **フィールド参照**のソートキー | `optionOrders`（選択肢の定義順）・`sortKinds`（型メタ） |
| `GREATEST`/`LEAST` | **値**（式の評価結果） | **なし** |

`GREATEST` は値しか受け取らないため**選択肢の定義順を使いようがない**。両者の差は**メタの有無という本質的なもの**であり、無理に統合すると ORDER BY 側の最適化（キー前計算）まで巻き込む。→ **統合しない**方針を明記する。

### 3.4 引数の個数と境界値（R2 で確定）

#### 3.4.1 現状: **arity は一切検証されていない**（実機実測）

```sql
SUBSTRING(会社名)        -- → 株式会社サイボウズ商事（引数不足でも全文が返る）
ROUND(顧客No, 1, 99)     -- → 1（過剰引数は黙って無視）
LENGTH(会社名, 'x')      -- → 11（同上）
```

評価器が `args[0] ?? ""` の形で既定値を補うため、**仕様を書かないと実装ごとに結果が割れる**。

#### 3.4.2 方針: **本仕様の追加関数は arity を検証する**

既存関数の arity 検証は**本仕様では変更しない**（挙動変更の範囲を最小化）。追加分のみ**実行時 `ArgumentError`** とする（§6.2 と同じエラー方式に統一）。

| 関数 | 許容 arity | 不正時 |
|---|---|---|
| `TRUNCATE(x [, n])` / `TRUNC` | 1〜2 | `ArgumentError` |
| `LEFT(x, n)` / `RIGHT(x, n)` | **2 のみ** | `ArgumentError` |
| `INSTR(str, sub)` | **2 のみ** | `ArgumentError` |
| `GREATEST(a, b, …)` / `LEAST` | **2 以上**（可変長） | 0〜1 引数は `ArgumentError` |
| `LPAD(x, n [, pad])` / `RPAD` | 2〜3 | `ArgumentError` |
| `LAST_DAY(d)` | **1 のみ** | `ArgumentError` |

> `GREATEST` の 1 引数を「その値を返す」としない理由: 引数の書き忘れを静かに通すため。`COALESCE`/`CONCAT` は 1 引数を許すが、あちらは「先頭の非空値」「連結」という意味が 1 引数でも成立する。`GREATEST(a)` は**意味を成さない**。

#### 3.4.3 数値引数の境界値

| ケース | 規定 | 根拠 |
|---|---|---|
| `LEFT(x, 0)` / `RIGHT(x, 0)` | `''` | 0 文字の切り出し |
| **`LEFT(x, -1)` / `RIGHT(x, -1)`** | **`''`**（エラーにしない） | `SUBSTRING(x, 1, -1)` 相当。負の長さは空 |
| **`LEFT(x, 2.7)`** | **`2` 文字**（`Math.trunc` で切り捨て） | 既存 `SUBSTRING` の小数引数と揃える（受入条件で一致を固定） |
| `LEFT(x, n)`（n ≥ 長さ） | 全文 | |
| **`LPAD(x, 0, '0')`** | `''` | 長さ 0 |
| **`LPAD(x, -1, '0')`** | **`''`**（エラーにしない） | MySQL は NULL だが kSQL に NULL は無い |
| **`LPAD('7', 5, '')`**（空 pad） | **`'7'`**（パディング不能なので原文） | **MySQL は空文字を返す**が、**入力を失う方が有害**なので採らない（B1 の「暗黙のデータ欠落を作らない」と同じ判断）。受入条件に明記 |
| `LPAD('12345', 3, '0')` | `'123'` | 長い場合は**先頭 n 文字へ切り詰め**（MySQL 準拠） |
| `TRUNCATE(x, 2.7)` | 既存 `ROUND(x, 2.7)` と同じ | 既存関数と揃える（新規則を作らない） |
| `INSTR` の n | — | 位置指定の第3引数は**持たない**（MySQL の `INSTR` も 2 引数） |

> **`LPAD('7', 5, '')` の判断**: MySQL 準拠なら `''`（入力が消える）。本プロジェクトは B1 で「暗黙の部分書き込み」を排し、B16 で「暗黙の切り捨て」を排した。**入力を黙って捨てる方向は採らない**ため、パディング不能時は原文を返す。

### 4.1 `LEFT` / `RIGHT` の曖昧性解消（実装上の注意）

`LEFT` / `RIGHT` は**既に `LEFT JOIN` / `RIGHT JOIN` の予約語**。関数化すると次を区別する必要がある:

```sql
SELECT LEFT(会社名, 4) FROM APP100 LEFT JOIN APP200 ON …
--     ^^^^ 関数（次が「(」）        ^^^^ JOIN 修飾子（次が JOIN）
```

- **`(` が続く場合のみ関数**として解釈する（1 トークン先読み）。それ以外は従来どおり JOIN 修飾子。
- **受入条件で両方を同一クエリに含めて固定**する（§5）。
- 他の追加関数にこの問題は無い（新規予約語のため）。

## 5. 受入条件（第1部）

- [ ] `TRUNCATE(123.456, 1)` = `123.4`／`TRUNCATE(123.456)` = `123`／`TRUNCATE(1234.5, -2)` = `1200`。
- [ ] **`TRUNCATE(-1.5)` = `-1` かつ `FLOOR(-1.5)` = `-2`**（負数で挙動が分かれることを固定）。`TRUNC` は同値。
- [ ] `LEFT('Database', 4)` = `'Data'`／`RIGHT('Database', 4)` = `'base'`。
- [ ] **`SELECT LEFT(x, 2) … FROM a LEFT JOIN b ON …` が動く**（関数と JOIN 修飾子の共存・§4.1）。`RIGHT` も同様。
- [ ] `INSTR('A-B-C', '-')` = `2`／見つからなければ `0`。
- [ ] `GREATEST(1, 5, 3)` = `5`／`LEAST('b','a')` = `'a'`／**集約 `MAX` と混同しない**（同一 SELECT で併用しても別物として動く）。
- [ ] `LPAD('7', 5, '0')` = `'00007'`／`RPAD('7', 3)` = `'7  '`（既定は空白）／`LPAD('12345', 3, '0')` = `'123'`（長い場合は切り詰め）。
- [ ] `LAST_DAY('2026-02-10')` = `'2026-02-28'`（うるう年 `2024-02-10` → `2024-02-29`）。
- [ ] **文字数の単位が既存 `LENGTH`/`SUBSTRING` と一致**（サロゲートペアを含む文字列で `LEFT`/`RIGHT`/`LPAD` が既存関数と矛盾しない）。
- [ ] 追加関数が**予約語**であること、および `` `TRUNCATE` `` 等バッククォートで同名フィールドを参照できること。
- [ ] 既存関数（`ROUND`/`FLOOR`/`CEIL`/`SUBSTRING`/`LENGTH`/`DATE_ADD` 等）に回帰なし。

### 5.1 空文字（§3.2）

- [ ] `LPAD('', 3, '0')` = `'000'`／`RPAD('', 3, '0')` = `'000'`（**空文字を返さない**）。
- [ ] `LEFT('', 3)` = `''`／`RIGHT('', 3)` = `''`。
- [ ] `INSTR('', 'a')` = `0`／**`INSTR('abc', '')` = `1`**／`INSTR('', '')` = `1`。
- [ ] `TRUNCATE('', 1)` が**既存 `ROUND('', 1)` と一致**／`LAST_DAY('')` が**既存 `DATE_ADD('', 1, 'DAY')` と一致**（新規則を作らない）。

### 5.2 `GREATEST` / `LEAST` の比較（§3.1）

- [ ] **順序非依存（空文字）**: `GREATEST('', '-1')` = `GREATEST('-1', '')` = `'-1'`／`LEAST('', '5')` = `LEAST('5', '')` = `''`。
- [ ] `GREATEST('', '5')` = `'5'`／`LEAST('', 'a')` = `''`／`GREATEST('', '')` = `''`。
- [ ] **順序非依存（数値・非数値の混在）＝推移律の破れの回帰テスト**: **`GREATEST('2','10','1a')` が全 6 順列で `'2'`**／**`LEAST('2','10','1a')` が全 6 順列で `'10'`**（集合単位でモードを決めるため）。
  - この 3 値は `compareScalarValues` の**ペア判定では循環する**（`'2'<'10'` は数値・`'10'<'1a'` と `'1a'<'2'` は文字列）。畳み込み実装では順列ごとに `'1a'`/`'10'`/`'2'` と割れるため、**この 3 値を必ずテストに含める**。
- [ ] **順序非依存（数値が同値な異表記）＝ tie-break の回帰テスト**（§3.1.1）: **`GREATEST('1','01','1.0')` が全 6 順列で `'1.0'`**／**`LEAST('1','01','1.0')` が全 6 順列で `'01'`**／`GREATEST('0','-0')` = `'0'`・`LEAST('0','-0')` = `'-0'`（両順序で）。
  - この 3 値は `Number` が全て `1` で、二次キーが無いと**先頭引数がそのまま残り**順列ごとに `'1'`/`'01'`/`'1.0'` と割れる。**必ずテストに含める**。
- [ ] **元の表記を保持する**: `GREATEST('007','008')` = `'008'`（`'8'` にしない＝`String(数値)` へ正規化しない・§3.1.1）。
- [ ] **非空かつ数値同値でない 2 引数では `WHERE a > b` と結論が一致**する（`compareScalarValues` と同じ規則）。**空文字を含む場合・3 引数以上の混在・数値同値**では本仕様の規則が優先する（§3.1）。
- [ ] 全て数値なら数値比較（`GREATEST('9', '10')` = `'10'`）／1 つでも非数値なら**全体を**文字列比較（`GREATEST('a', 'b')` = `'b'`）。

### 5.3 引数の個数・境界値（§3.4）

- [ ] **arity 違反が `ArgumentError`**: `LEFT('x')`／`LEFT('x',1,2)`／`INSTR('x')`／`GREATEST('a')`／`GREATEST()`／`LAST_DAY()`／`LPAD('x')`。
- [ ] `LEFT(x, 0)` = `''`／**`LEFT(x, -1)` = `''`**（エラーにしない）／**`LEFT(x, 2.7)` が既存 `SUBSTRING` の小数扱いと一致**。
- [ ] `LPAD(x, -1, '0')` = `''`／**`LPAD('7', 5, '')` = `'7'`**（空 pad は原文を返す。**入力を捨てない**）。
- [ ] `TRUNCATE(x, 2.7)` が**既存 `ROUND(x, 2.7)` と同じ小数扱い**。

- [ ] **`DATE_ADD` の不正単位が実行時 `ArgumentError`**（メッセージに `YEAR, MONTH, or DAY` を含む）: `'HOUR'`／`'WEEK'`／`'xxx'`。

## 6. 第2部: 既存関数の文書誤り・静かな誤動作（実機で発見）

### 6.1 🐞 `DATE_ADD` の構文が文書と実装で食い違う（**最優先**）

| | 内容 |
|---|---|
| **言語リファレンス §5 の記載** | `DATE_ADD(フィールド, INTERVAL n UNIT)` |
| **実機** | ❌ **`ParseError`**（`INTERVAL` は**トークンとして存在しない**・実測で 0 件） |
| **正しい構文** | ✅ **`DATE_ADD(日付, -1, 'MONTH')`**（3 引数。`applyDateAdd(dateStr, n, unit)`・[evalFunc.ts:215](../../src/engine/evalFunc.ts#L215)） |

**文書どおりに書くと必ず失敗する**。`NULLIF`/`ISNULL` の「未記載」（気づけないだけ）より悪く、利用者を確実に誤らせる。

→ **言語リファレンスを 3 引数形へ修正**する。実装は変更しない（`INTERVAL` 構文の追加は §7）。

### 6.2 🐞 `DATE_ADD` の不正な単位が**黙って `DAY`** になる

```sql
DATE_ADD('2026-07-15', 1, 'HOUR')  -- → 2026-07-16 ← DAY として処理されている
DATE_ADD('2026-07-15', 1, 'WEEK')  -- → 2026-07-16
DATE_ADD('2026-07-15', 1, 'xxx')   -- → 2026-07-16 ← 完全な誤字でも通る
```

原因は `applyDateAdd` の `switch` が **`default:` で DAY に落ちる**（[evalFunc.ts:219-223](../../src/engine/evalFunc.ts#L219)）:

```ts
switch (unit) {
  case "YEAR":  …
  case "MONTH": …
  default:      dt.setUTCDate(dt.getUTCDate() + n); break; // DAY
}
```

**サポートするのは `YEAR`/`MONTH`/`DAY` のみ**（実装コメントにも明記）だが、`'HOUR'` と書いた利用者は**日単位で加算された結果を正しいと誤認する**。

**修正方針（R2 で確定・実行時エラーに統一）**: `YEAR`/`MONTH`/`DAY` 以外は **実行時 `ArgumentError`** とする。

> **R1 の「`ParseError`（または実行時エラー）」は受入条件が一意にならないため撤回。**

**なぜ parse 時でなく実行時か**:

第 3 引数は**文字列リテラルとは限らない**。`StringFuncArg` はフィールド参照・式も取れるため、`DATE_ADD(日付, 1, 単位フィールド)` のように**パーサが単位を確定できない**ケースがある。リテラルのときだけ parse 時に弾くと**二重仕様**（同じ誤りがリテラルなら ParseError・フィールドなら別扱い）になり、利用者にもテストにも一貫しない。

→ **すべて実行時に検証する 1 本の規則**にする:

```
ArgumentError: DATE_ADD unit must be YEAR, MONTH, or DAY.
```

- **大文字小文字は不問**（実装コメントの「大文字・小文字不問」を維持。`'day'` / `'Day'` は有効）。
- **SemVer: 挙動変更**（従来「通っていた」`DATE_ADD(x, 1, 'HOUR')` がエラーになる）。ただし**その結果は誤り**（HOUR 加算になっていない・日単位で加算されている）であり、**誤った成功を失敗へ変える**方向。B1（`truncate` の暗黙部分書き込みを `error` 固定）と同じ判断。
- **受入条件にエラー型・メッセージ・小文字許容を固定**（§5）。

### 6.3 🐞 `SUBSTRING` の負数・0 開始が MySQL と異なる（**文書のみ**）

| 式（`会社名` = `株式会社サイボウズ商事`） | kSQL | MySQL |
|---|---|---|
| `SUBSTRING(x, -4)` | `株式会社サイボウズ商事`（**全文**） | `ズ商事`（末尾 4 文字） |
| `SUBSTRING(x, 0)` | `株式会社サイボウズ商事`（全文） | `''`（空） |
| `SUBSTRING(x, 0, 4)` | `株式会社` | `''` |
| `SUBSTRING(x, 99)` | `''` | `''` |

**エラーでも末尾切り出しでもなく黙って全文**を返すため、MySQL 経験者は気づきにくい。

**修正方針**: **挙動は変更せず**、言語リファレンスに「**開始位置は 1 以上。0 以下は 1 と同じ（先頭から）。MySQL のような負数＝末尾からの切り出しには非対応**」と明記する。
- 挙動変更（負数を末尾切り出しにする）は**既存の動作を壊す**ため採らない。末尾切り出しは §2.2 の `RIGHT` で提供する。

### 6.4 リリース順の選択肢

第2部（§6.1・§6.3 の文書修正、§6.2 の実装修正）は**バグ相当**で、第1部より優先度が高い。

| 案 | 内容 |
|---|---|
| **A（推奨）** | 第1部＋第2部を **v2.17.0 で一括**。文書修正だけ先に出しても、利用者は結局 `RIGHT` 等が無くて困るため、まとめて 1 回の実機確認で出す |

## 7. スコープ外・後続

- **`SUBSTRING` の引数に算術式を許す**（`SUBSTRING(x, LENGTH(x)-3, 4)`）: 全関数の引数へ波及する言語機能。`RIGHT` の追加で当面の需要は満たせるため別課題。
- **`DATE_ADD` の `INTERVAL n UNIT` 構文**: MySQL 互換の別記法。`INTERVAL` の予約語追加と単位トークン化が要る。3 引数形が動く以上、優先度は低い（§6.1 は文書を実装に合わせる方針）。
- `EXTRACT` / `SIGN` / `LOG` / `REVERSE` / `REPEAT` / 別名（`LEN`/`NVL`/`IFNULL`）: §1.1 のとおり見送り。
- **`DATE_ADD` の時刻単位**（`HOUR`/`MINUTE`）: `DATETIME` フィールドへの加算需要が立証されてから。§6.2 でエラー化するため、追加する場合は別途仕様化する。
