# 課題: 切り出し・桁揃え関数がサロゲートペアを分割する（B22）

- 作成日: 2026-07-17
- 位置づけ: B20（正規表現関数）の仕様検討中、`u` フラグの扱いを調べる過程で発見。**B20 / B21 とは独立した既存の欠陥**。
- ステータス: **課題 R4 実装済み・実機確認済み（2026-07-18・[実機記録](evidence/b22_surrogate_slice_smoke.md)）・v3.2.0 リリース待ち。**
- 横断契約: 文字数・切り出し単位・4 面の一貫性に関する事実と原則は [文字列の扱い](ksql_string_semantics.md) §§1–3 を正とする。本書は B22 固有の再現、境界規則、受入条件だけを定める。
- 分担: Claude=仕様/観点、Codex=実装/テスト
- 台帳: [ksql_issue_tracker.md](../ksql_issue_tracker.md)

---

## 0. 要約

**`LEFT` / `RIGHT` / `SUBSTRING` / `LPAD` / `RPAD` が、サロゲートペアを途中で割って孤立サロゲート（不正な文字）を返す。**

```
LEFT('𩸽あ😀', 1)      = "\ud867"     ← 孤立した上位サロゲート
RIGHT('𩸽あ😀', 1)     = "\ude00"     ← 孤立した下位サロゲート
SUBSTRING('𩸽あ😀', 1, 1) = "\ud867"
LPAD('😀😀', 3, '0')   = "😀\ud83d"   ← 切り詰めで割れる
LPAD('7', 4, '😀')     = "😀\ud83d7"  ← 埋め文字列そのものが割れる
RPAD('7', 4, '😀')     = "7😀\ud83d"
```

**採用する対策は「指定されたコードユニット予算内で、入力中のサロゲートペアを割らない最大の部分列を返す」（§3 案 C）。** 「切り出しは UTF-16」という曖昧な表現は使わない。区間の予算はコードユニットだが、境界は安全な側へ縮める（横断仕様 原則4）。

---

## 1. 現象（実機実測）

`𩸽`（U+29E3D）と `😀`（U+1F600）はサロゲートペア（各 2 コードユニット）。`'𩸽あ😀'` は **5 コードユニット / 3 文字**。

| 式 | 結果 | 問題 |
|---|---|---|
| `LEFT('𩸽あ😀', 1)` | `"\ud867"` | 上位サロゲート単独＝文字として不正 |
| `RIGHT('𩸽あ😀', 1)` | `"\ude00"` | 下位サロゲート単独 |
| `SUBSTRING('𩸽あ😀', 1, 1)` | `"\ud867"` | 同上 |
| `LPAD('😀😀', 3, '0')` | `"😀\ud83d"` | `str.length >= n` の切り詰め（`evalFunc.ts`）が割る |
| `LPAD('7', 4, '😀')` | `"😀\ud83d7"` | **`padStart` が埋め文字列を 3 ユニットに切って割る** |
| `RPAD('7', 4, '😀')` | `"7😀\ud83d"` | 同上 |

**`LPAD` / `RPAD` は 2 経路で壊れる**（切り詰めと埋め）。**どちらも B19（v2.17.0）で追加したばかりの関数**であり、`LPAD` は「桁揃え・0 埋め」という**書き込み前提の用途**で入れたため、壊れた値が kintone へ流れ得る。

**B19 の受入条件は `LEFT`/`RIGHT`/`SUBSTRING` の文字単位が相互に一致することは確認したが、サロゲートを割ること自体の是非は見ていなかった**（`process.test.ts` の「B19 の文字数単位は LENGTH / SUBSTRING と一致する」）。

### 1.1 横断契約との関係

`LENGTH`、kintone の `maxLength`、`LIKE '_'` が使う単位と、その実測経路は横断仕様 §§2–3.5 を参照。本課題はそれらの一般則を再掲せず、**コードユニット予算を守る切り出しが新しい孤立サロゲートを作る**という B22 固有の欠陥だけを扱う。

## 3. 対策案の比較（R1 で確定）

### 3.1 案 A: コードポイント単位にする（`[...str]`）— **却下**

`[...str]` / `for...of` はコードポイント単位のイテレータを使うため、サロゲートペアを割らない。**JS の対処としては正しい**が、kSQL では 2 つ壊れる。

**① `LENGTH` と単位が食い違う**

```
LEFT('𩸽あ😀', 1) = '𩸽'  → LENGTH(結果) = 2   ← 1 を頼んだのに 2
LEFT('😀😀😀', 2) = '😀😀' → LENGTH(結果) = 4   ← 2 を頼んだのに 4
```

**② 決定的: 「フィールド上限に収める」が壊れる**

```
maxLength = 64 の欄へ LEFT(x, 64) で詰める（x = 😀×40 = 80 ユニット）
  コードポイント版 → 結果は 80 ユニット → ERR_LENGTH_MAX で拒否される
```

**kintone で `LEFT` / `SUBSTRING` を使う第一の用途は「上限に収める切り詰め」**である。横断仕様 §2 の保存予算は変えられないため、`LEFT` だけコードポイント数を長さ引数の意味にすると **切り詰めた結果が kSQL 自身の検証に弾かれる**という別の壊れ方になる。

### 3.2 案 B: 書記素クラスター単位にする（`Intl.Segmenter`）— **却下**

`Intl.Segmenter` なら結合文字・ZWJ 絵文字・国旗・異体字セレクタまで 1 文字として扱える（Node で実測: `👨‍👩‍👧‍👦` は 11 ユニット / 7 コードポイント / **1 書記素**）。**「人間の見た目の文字数」としては最も正しい。**

**却下理由:**

| # | 理由 |
|---|---|
| 1 | **ホストエンジン依存**。`Intl.Segmenter` は **Firefox 125（2024 年 4 月）でようやく対応**した。**プラグインは利用者のブラウザで動く**ため、Firefox ESR 115 等では `TypeError` になる。B20 仕様 §3.1 で「最も重い残存リスク」とした問題と同型で、**そちらは回避不能だから受け入れたのに対し、本件は案 C を選べば回避できる** |
| 2 | **locale 依存**。`new Intl.Segmenter('ja', …)` の第 1 引数で結果が変わり得る。kSQL の他の関数に locale 依存は無い |
| 3 | **`LENGTH` との乖離が案 A より大きい**。`👨‍👩‍👧‍👦` を kintone は 11 と数えるのに 1 と数える単位を混ぜると、①の用途がさらに壊れる |

**ただし将来の別関数としては有力**（§6）。

### 3.3 案 C: コードユニット予算内で、安全な境界へ縮める — **採用**

> **結果は常に「n コードユニット以下」かつ「入力中で対になっていたペアを割らない」。**

#### 判定は「上位かつ下位」の両方を見る（R1 の初稿を訂正）

**初稿は「`x[n-1]` が上位サロゲートなら手前で切る」としていたが、誤りだった。** 入力に**既に孤立サロゲートがある**場合（過去の本欠陥で壊れた値が保存されている可能性がある）に、割るペアが無いのに短くしてしまう:

```
入力 "あ\ud83dい"（孤立上位。ペアではない）
  初稿版 LEFT(_, 2) = "あ"          ← 割るペアが無いのに短くしている
  確定版 LEFT(_, 2) = "あ\ud83d"    ← 正しい
```

**確定する判定:**

```ts
// 位置 i で切ると「入力中で対になっているペア」を割るか
const splitsPair = (x, i) =>
  i > 0 && i < x.length && isHigh(x.charCodeAt(i - 1)) && isLow(x.charCodeAt(i));
```

**上位サロゲートの直後に下位サロゲートが続くときだけ**ペアである。片方だけでは判定できない。

#### 各関数の規則

```
LEFT(x, n)  : splitsPair(x, n) なら n-1 で切る
RIGHT(x, n) : s = len-n。splitsPair(x, s) なら s+1 から取る
SUBSTRING   : 開始・終了の両方に同じ調整（終了は e-1、開始は s+1）
LPAD/RPAD   : 切り詰め（x.length >= n）は LEFT と同じ。
              埋めは埋め文字列を繰り返してから LEFT で gap ユニットへ整える
              （＝残りが埋め文字 1 つ分に満たなければ埋めずに終える。結果は n 未満）
```

#### 網羅検証（プロトタイプ・13,905 ケース pass）

**入力 18 種**（BMP のみ / 日本語 BMP / ペア 1 つ / **連続ペア×3・×10・×40** / ペア+BMP 交互 / BMP+ペア交互 / 先頭のみ / 末尾のみ / 中間のみ / 異なるペア混在 / **孤立上位を含む入力** / **孤立下位を含む入力** / **孤立が隣接** / 空文字 / 長文）× **全境界**（`LEFT`/`RIGHT` は n=0〜len+2、`SUBSTRING` は開始 1〜len+1 × 長さ 0〜len+1 と省略、`LPAD`/`RPAD` は n=0〜len+8 × 埋め文字列 4 種 `'0'` / `'😀'` / `'a😀'` / `'😀b'`）。

**検査した性質:**

1. `LENGTH(結果) <= n`（`SUBSTRING` は長さ指定時）
2. 結果が入力の前方一致（`LEFT`）/ 後方一致（`RIGHT`）/ 部分文字列（`SUBSTRING`）
3. **入力中で対になっていたペアを割っていない**（元々入力にあった孤立サロゲートは差し引いて数える）
4. **最大性**（`LEFT`）— もう 1 ユニット足すと n 超過かペア分割になる＝不必要に短くしていない

**全 13,905 ケース pass。** 性質 4 が初稿の誤りを捕捉した。

| | `LENGTH` と同単位 | 上限に必ず収まる | 割れない | ホスト依存なし |
|---|---|---|---|---|
| 現状 | ✅ | ✅ | ❌ | ✅ |
| 案 A コードポイント | ❌ | ❌ | ✅ | ✅ |
| 案 B 書記素 | ❌❌ | ❌ | ✅ | **❌** |
| **案 C 境界調整** | ✅ | ✅ | ✅ | ✅ |

#### 案 C で受け入れる違和感

```
LEFT('𩸽あ😀', 1)  = ''      （'𩸽' は 2 ユニットなので 1 ユニットには収まらない）
RIGHT('𩸽あ😀', 1) = ''
LPAD('7', 4, '😀') = '😀7'   （3 ユニット。残り 1 ユニットに '😀' は入らない）
```

**「1 コードユニットに収まる安全な先頭部分は空文字だけ」という答え**であり、壊れた半分を返すより良い。横断仕様 原則1・4に従う。

**リファレンスに明記する**: 「長さ引数はコードユニット予算。サロゲートペアを割る境界では安全な側へ縮める。結果は必ず指定予算以下になる」。

## 4. SemVer

**minor**。

- **挙動変更を含む**（孤立サロゲートを返していた式が、より短い正しい値を返すようになる）
- ただし**変わるのは「壊れた値を返していたケース」だけ**であり、**誤った成功を正しい結果へ変える**方向。B19 の `DATE_ADD` 不正単位（黙って DAY → `ArgumentError`）と同じ判断
- サロゲートペアを含まない値（ほぼ全ての実データ）の挙動は**完全に不変**

## 6. 将来候補: `Intl.Segmenter` による書記素対応

`LENGTH_GRAPHEME(x)` のような**別関数**として足せば、既存の単位を壊さずに「人間の見た目の文字数」を提供できる。

**設計上の注意**:

- **ホスト依存を fail-closed にする**。`typeof Intl.Segmenter === 'undefined'` なら `ArgumentError`（Firefox ESR 等で黙って別の値を返さない）
- locale を固定するか、引数で明示させる
- **`LENGTH` を置き換えてはならない**（kintone の計数と乖離する）

## 7. 受入条件

- [x] **性質テストにすること**（個別の期待値を並べるのではなく、入力×境界を回して性質を検査する。§3.3 の 13,905 ケースのプロトタイプと同じ形）:
  - [x] `LENGTH(結果) <= n`
  - [x] 結果が入力の前方一致（`LEFT`）/ 後方一致（`RIGHT`）/ 部分文字列（`SUBSTRING`）
  - [x] **入力中で対になっていたペアを割らない**（**元々入力にあった孤立サロゲートは差し引いて数える**こと。さもないと「孤立を含む入力」のケースで偽陽性になる）
  - [x] **最大性**: もう 1 ユニット足すと n 超過かペア分割になる＝**不必要に短くしていない**（**この性質が §3.3 の初稿の誤りを捕捉した**ため必須）
- [x] **入力の形を網羅すること**（**1 種類では足りない**。§3.3 の 18 種を最低限とする）:
  - [x] BMP のみ（`'ABCDE'` / `'東京都千代田区'`）＝ 非回帰
  - [x] **連続ペア**（`'😀😀😀'` / `'😀'×10` / **`'😀'×40`**）
  - [x] ペアと BMP の交互（`'😀あ😀い😀う'` / `'あ😀い😀う😀'`）
  - [x] 先頭のみ / 末尾のみ / 中間のみペア
  - [x] 異なるペアの混在（`'𩸽😀𩸽😀'`）
  - [x] **既に孤立サロゲートを含む入力**（`'あ\ud83dい'` / `'あ\ude00い'` / `'\ud83d\ud83dあ'`）＝**本欠陥で壊れた値が既に保存されている可能性があるため必須**
  - [x] 空文字
- [x] **境界を全数で回すこと**: `LEFT` / `RIGHT` は n = 0〜len+2、`SUBSTRING` は開始 1〜len+1 × 長さ 0〜len+1 と長さ省略
- [x] **`LPAD` / `RPAD` の 2 経路**: ①切り詰め `LPAD('😀😀', 3, '0')` が `"😀\ud83d"` にならない ②**埋め文字列** `LPAD('7', 4, '😀')` が `"😀\ud83d7"` にならない
- [x] **`LPAD` / `RPAD` は埋め文字列も網羅**: `'0'`（1 ユニット）/ `'😀'`（2 ユニット）/ **`'a😀'`・`'😀b'`（混在・奇数境界が出る）** × n = 0〜len+8
- [x] **上限に収まる**: `LEFT('😀'×40, 64)` が **64 コードユニット以下**（実測 64・現状は孤立サロゲートを含む 64）
- [x] **上限に収まる（書き込み経路）**: `maxLength = n` のフィールドへ `LEFT(x, n)` の結果が**必ず `VALIDATE ONLY` を通る**。`n` は検証に使うフィールドの実際の `maxLength` と一致させること（**R1 初稿は `LEFT(…, 64)` の結果を `maxLength = 10` の欄で検証するという不整合な条件だった**）
- [x] **最大性は全関数で**: `LEFT` だけでなく **`RIGHT` / `SUBSTRING` / `LPAD`・`RPAD` の切り詰めと埋め**にも「不必要に短くしない」を性質として定義する（R1 初稿は `LEFT` のみ）
- [x] **非回帰**: サロゲートペアを含まない値（`'ABCDE'` / `'東京都千代田区'`）で B19 の既存テストが全て pass。特に `LEFT(s,2)` = `SUBSTRING(s,1,2)` の相互一致
- [x] **`LENGTH` は非回帰**: `LENGTH('😀')` = `2`（根拠は横断仕様 §2）
- [x] **`LIKE` は不変**: `'😀' LIKE '_'` は引き続き一致（§5・本課題の対象外）
- [x] **`INSTR` は不変**: コードユニット位置を返す
- [x] **書き込み経路**: `CREATE TEMP TABLE … AS SELECT LEFT(…)` → `UPDATE … FROM` で、孤立サロゲートが kintone へ流れない
