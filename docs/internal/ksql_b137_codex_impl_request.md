## 罠（レビューとオーナー指摘で直った点）

1. **「静的に弾ける形だけ先に落とす」をやらない。**
   **静的判定は可能**（両枝が明示列なら AST で分かる／`DESCRIBE` は版内固定 7 列／
   `SHOW APPS` は 3 列／`SELECT *` はアプリ定義から算出可）。
   **それでも本件は実体化後の共通検査だけにする**——形ごとにエラーの時機と優先順位が
   分岐し、**未知フィールドエラーとの順序が形によって変わる**ため。
   **これは最適化の見送りではなく意味論の統一。** 勝手に fast-fail を足さないこと。

2. **「途中で止まるから API を節約できる」と書かない・作らない。**
   `executeUnion` は **`Promise.all` で左の入れ子全体と右を同時に開始する**ので、
   **内側が不一致でも全枝が実行される**。**現行の並列実行の形を変えないこと。**

3. **`EXPLAIN` は従来どおり計画を返す。**
   現行の `EXPLAIN <UNION>` は `executeUnion` を通らず枝ごとの計画を集めるだけで、
   **列数が違っても成功する**。**この挙動を変えない。**
   **「変えていないこと」を受入で固定すること。**

4. **判定は 2 か所とも**（`execute.ts:4902-4910` の通常経路と `:5018-5023` の CTE 経路）。
   **共通ヘルパー 1 本**に寄せる。**引数は `readonly string[]` の左右 `columns`**
   （長さしか要らないので `SelectResult` を渡さない）。

5. **列名は左辺から取る現行仕様を変えない**（MySQL と同じ）。
   **列名の一致も型の互換性も本件の対象外。**

6. **`b130DescribeFlags.test.ts` に、こちらが書いた characterization test が 1 本ある**
   （「B137 で別途」とコメント済み）。**これはエラー期待へ変えてよい唯一の既存テスト。**
   **意味の変更なので報告に明記すること。**

7. **代表 SQL は実在アプリの形で書く**（`APP100` / `APP200` 等）。
   **過去に 5 回、パースできないサンプルを書いている。**

## 受入・回帰

R2 §3 のとおり。落とさないでほしいもの:

- **§3.1** 右が少ない／右が多い／`UNION ALL`／**CTE 内 `UNION`**／
  **`CREATE TEMP TABLE #t AS <列数の違う UNION>`**／`DESCRIBE` を含む形／
  **3 段連鎖（内側・外側それぞれ）**／**engine ライブラリ `runQuery` / `runBatch` 経由**
- **§3.2** 列数が一致する `UNION` / `UNION ALL` は不変／**列名が違っても列数が同じなら通る**／
  `FROM` なしの `SELECT ... UNION ALL SELECT ...`（レシピ R7 の形）／
  `deduplicateRows` が不変／`SHOW APPS` / `DESCRIBE` を含む形で列数が合えば通る
- **§3.3** 両辺を実行したうえで落ちる／**3 段以上でも全枝が実行される**／
  メッセージに左右の列数が入る／`ArgumentError` として扱われる
- **§3.4** **`EXPLAIN` は列数が違っても成功する**
