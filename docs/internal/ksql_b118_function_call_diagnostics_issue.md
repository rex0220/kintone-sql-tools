# B118 関数呼び出しの診断が弱い（引数の数を黙認する／未知の関数名で無関係なエラー）

- 起票: 2026-08-04
- ステータス: ✅ **完了（v3.43.0 でリリース）**（2026-08-04・受入 §4.3 を新規ビルドの MCP で実測確認。**codex の停止 1 回**＝FORMAT の既存テスト、**レビューで差し戻し 1 回**＝案内メッセージの位置情報が二重）＝仕様は §4（②）・§5（①）
- 出典: [Pro の報告 2026-08-04d](../../../ksql-dashboard-pro/docs/internal/kSQLエンジンへの連絡-20260804d-送付版.md) §5 の反省
  （「**構文エラーを機能の非対応と読み替えていた**」）を読み、原因を実測して発見
- 関連: [B117](ksql_b117_date_add_month_end_issue.md)（同じ「静かに間違う」形）/ `src/engine/evalFunc.ts:489`（`assertArity`）

## 1. 経緯

Pro は `DATE_ADD` を「非対応（検証済み）」と文書に書いていた。原因は MySQL の書式
（`DATE_ADD(d, INTERVAL 1 MONTH)`）で試し、`ParseError` を「機能が無い」と読んだこと。
**その読み替えを招いたのはこちらのエラーメッセージ**である。

Pro の誤記 → こちらの訂正 → Pro が実際に動かす → **月末の欠陥（B117）を発見** という
連鎖だったため、**診断が弱いことは実際に欠陥の発見を 1 往復ぶん遅らせた**。

## 2. 症状（実測 2026-08-04）

### 2.1 ② 引数の数の誤りを黙認し、誤った値を返す（本体）

```
DATE_ADD(受注予定日, 1)   → 2026-08-13   ← 単位が無いのに通る（DAY 扱い）
ROUND(売上, 1, 2)         → 5200000      ← 余分な引数が黙って無視される
```

**`ksql_validate` も通る。**実行しても警告が出ない。

### 2.2 ① 未知の関数名・誤った引数構文で、無関係なメッセージ

```
DATE_SUB(受注予定日, 1, 'MONTH')
  → ParseError: 文の区切りには ; が必要です（位置 15、トークン: 「(」）

DATE_ADD(受注予定日, INTERVAL 1 MONTH)
  → ParseError: 「)」が必要です（位置 32、トークン: 「1」）
```

**どちらも「関数が無い」「書式が違う」と読めない。**

## 3. 原因

**設計の欠落ではなく適用漏れ。**`assertArity`（`src/engine/evalFunc.ts:489`）は既にあり、
`LEFT` / `RIGHT` / `INSTR` / `REGEXP_*` などでは使われている。

```
assertArity の呼び出し: 16 箇所   /   関数の case 分岐: 65
```

`DATE_ADD` / `ROUND` などは素通しで、**既定値が書き間違いを正当化している**。

```ts
case "DATE_ADD":
  return applyDateAdd(args[0] ?? "", Number(args[1] ?? "0"), (args[2] ?? "DAY").toUpperCase());
```

①はパーサの診断で、関数名を識別子として読んだあと `(` で構文が壊れているため、
メッセージが原因を指していない。

## 4. ② の仕様（本体）

### 4.1 変更点

**すべての関数分岐で引数の数を検証する。**

- **引数の数の正本は `docs/ksql_language_reference.md` の関数表の「構文」列**
  （`UPPER(フィールド)` / `DATE_ADD(列, n, '単位')` など・85 行）。
  **構文列から一意に読み取れない関数があれば、止めて報告すること**
- 検証は既存の `assertArity` を使う（**新しい仕組みを作らない**）
- **文書上「省略可能」と書かれている引数は、引き続き省略可能**（例 `REGEXP_LIKE` の第 3 引数）。
  省略可能でない引数の `?? 既定値` による黙認はやめる
- **正しい呼び出しの結果は完全に不変**

### 4.2 破壊的変更

**いま通っている「引数の数が誤った呼び出し」はエラーになる。**
ただしそれらは**単位や引数を書き忘れた SQL** であり、現状も意図しない値を返している。

**実装は、挙動が変わる形をすべて列挙して報告すること**（移行案内に載せるため）。

### 4.3 受入条件

1. `DATE_ADD(列, 1)` が `ArgumentError`（単位が必要である旨）
2. `ROUND(列, 1, 2)` が `ArgumentError`
3. **正しい呼び出しの結果が完全に不変**（既存テスト全 green）
4. `ksql_validate` でも同じ検出ができること（**実行前に分かる**のが望ましい。
   静的に検出できない設計なら、その理由とともに報告）
5. snapshot 22 不変・語数予算 exact 不変・declaration snapshot 差分 0

## 5. ① の仕様（同梱・自然な縫い目がなければ報告）

**関数呼び出しに見える形で失敗したとき、原因を名指しする。**

| 入力 | 期待するメッセージの趣旨 |
|---|---|
| `DATE_SUB(...)`（**未知の関数名**） | 「`DATE_SUB` という関数はありません」と**名前を出す**（可能なら「`DATE_ADD` に負数を指定してください」まで） |
| `DATE_ADD(d, INTERVAL 1 MONTH)`（**既知の関数・引数の構文が不正**） | 「`DATE_ADD` の構文は `DATE_ADD(列, n, '単位')` です」と**期待する書式を出す** |

- 判定は**識別子の直後に `(` が来た形**を対象にする
- **関数名の一覧は既存の定義を単一ソースとして使う**（`src/mcp/docsResources.ts` の
  `KSQL_FUNCTION_CATALOG` は MCP 層なので、パーサから参照するのが不自然なら別の場所を選ぶ。
  **新しい一覧を二重に持たないこと**）
- **自然な縫い目が無いと判断したら、黙って広げず止めて報告すること。**
  ②だけ先に出す判断もありうる

## 6. やらないこと

- 関数の追加・削除・改名
- 引数の**型**変換規則の変更（数値化・文字列化の既存挙動は不変）
- 押し下げ・`WHERE` での扱いの変更
- `DATE_SUB` / `INTERVAL` 構文の実装（**メッセージで案内するだけ**）
- `KSQL_MCP_INSTRUCTIONS` の変更（語数予算 exact 不変）

**中〜高。**②は **B117 と同じ「静かに間違う」形**で、B117 を「その形は残さない」という
理由で直した直後に同種を残すのは一貫しない。①は今回の誤読の直接原因。

**minor＋移行案内**（B117 と同じ扱い）。
