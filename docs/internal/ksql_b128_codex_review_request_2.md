## 特に見てほしい点（コードで真偽が決まるもの）

### 1. 【最優先】前回の「高」4 件は本当に潰せているか

R1 §3.1〜§3.3・§2.3。

- **`isRankingWindow` の positive discriminator 化**（§3.1）で、
  **他に壊れる呼び出し元が無いか**。`isRankingWindow` の全利用者を挙げてほしい
- **required-field 収集**（§3.2）＝`VALUE` で `walkAggregateArg` を通すだけで足りるか。
  **`LAG` の引数に書ける式の範囲**（算術・文字列関数・`CASE`・連結・変数）を
  現行 walker がすべて拾えるか
- **型メタの 6 箇所**（§3.3）＝**過不足が無いか**。ほかに同期が要る箇所は無いか
- **`default` を取らない判断**（§2.3）で、**利用者が本当に困らないか**
  （「次の段で `CASE`」が実際に書けるか。**ウィンドウ結果を式に含められない制約**と矛盾しないか）

### 2. 代表 SQL は実際にパースできるか

R1 §1.1。**前回の R1 は代表 SQL が現行パーサで拒否された**（同じ轍を踏みたくない）。

- `WITH ... GROUP BY ... ` の CTE の外側で `LAG(...) OVER (ORDER BY ...)` が書けるか
- **`GROUP BY` を含む CTE の結果に対してウィンドウを使う形**は現行で通るか
- 「次の段で前月比」の 3 段目まで含めて、**実行可能な完全形**を示せるか

### 3. `applyWindow` の 3 分岐と `LAG` の実装位置

R1 §3.1・§5。

- **`applyValueWindow` を新設する**のが素直か、既存の順位系ループに相乗りすべきか
- **ソート結果（`sortDecoratedRows`）の共有**は B125 と同じ形でよいか
- **同じ SELECT に順位系・集計窓・`LAG` を混在**させたとき、
  **パーティション分割とソートが何回走るか**（性能・正しさの両面）

### 4. `offset` の扱い

R1 §2.2。非負の safe integer リテラルのみ。

- **`0` を自分自身とする**のは現行の実装と整合するか
- **パーティション長を超える `offset`**（→ 空文字）で問題が無いか
- 変数（`@n`）を将来許す余地を残す書き方になっているか

### 5. 非全順序 `ORDER BY` の決定性

R1 §2.4・§6-2。**B127 の判定器を再利用できるか**をコードで確認してほしい。
再利用できないなら、その理由と代替案。

### 6. 受入条件の穴

R1 §4。**B130 / B137 で受入条件の書き方を誤って実装者を誤らせた**ので、
**要求とも確認ともとれる文が無いか**を見てほしい。

- §4.2 の型の受入は、**§3.3 の 6 箇所を本当に検出できるか**
  （とくに **4 番のロードゲート**。direct APP の `LAG(選択肢列)`）
- §4.3 の「引数にしか現れないフィールド」の受入は、**漏れを確実に検出する形か**

### 7. `LAG` / `LEAD` を soft keyword にするか

R1 §6-1。**既存フィールド名と衝突し得る**（`LAG` という名前のフィールドがあり得る）。
現行パーサの soft keyword の扱いを踏まえて方針を出してほしい。
