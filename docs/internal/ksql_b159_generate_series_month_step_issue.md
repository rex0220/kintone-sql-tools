# B159 GENERATE_SERIES に month / year step が無く、月次の LAG を 0 埋めで守れない

- 起票: 2026-08-08（[依頼元の B128 Phase 2 意見 §4](../../../ksql-analytics/docs/internal/kSQLエンジンへの意見-20260808-B128Phase2再開ライン.md)・実測裏取り済み）
- ステータス: ✅ **v3.63.0 リリース（2026-08-08・[仕様 R1](ksql_b159_generate_series_month_step_spec_r1.md)どおり実装・空月直後の LAG=0 を実データ確認）**
- 関連: [B149](ksql_b149_generate_series_issue.md)（日付 step は day/days のみで出荷）／
  [B128 2b LAG/LEAD](ksql_b128_lag_lead_spec.md)（v3.51.0）

## 1. 穴の構造

- **B128 2b（`LAG`）が先行できた根拠は「依頼元の月次履歴 13 か月に歯抜けが無い」**＝
  データの性質であって保証ではない
- 日次は `GENERATE_SERIES` の 0 埋めで守れるが、**月次は守れない**:

```
GENERATE_SERIES('2025-08-01', '2026-08-01', '1 month')
→ ArgumentError: GENERATE_SERIES の日付 step は day または days のみ対応しています。
```

（実測・2026-08-08・v3.62.0）

- 結果、**レコードが 1 件も無い月があると `LAG` は静かに 2 か月前と比べる**。
  エラーも警告も出ない（「静かに間違う」クラス）。休業月・新設アプリ初期で現実に起こる形

## 2. 依頼元の現状回避

`inventory_monthly_outflow_mom.sql` のヘッダに「使う前に月の連続性を確かめる」を追記
（規約で受けているだけで仕組みでは止まっていない、と自認）。

## 3. 方針案

- **month / year step の追加**（`'1 month'` / `'1 year'`）。案 B（値指定 RANGE）より遥かに小さく、
  新機能ではなく**出荷済み機能（LAG）の穴を塞ぐ側**
- **月末丸めの整理（2026-08-08 オーナー問いで最終形に確定）**:
  - **系列は月初アンカー限定のままでよい。月末が欲しい場合は既存の式で変換する**
    （オーナー案）＝`LAST_DAY(月初)`。**`LAST_DAY` / `DATE_ADD(日付, n, 'MONTH')` は既存**
    （言語リファレンス §5）で、合成も動作する（実測 2026-08-08・v3.62.0）
  - よって**アンカー方式の系列開放という将来段階も不要**。丸め規則の選択問題は
    「系列に月末起点を持ち込まない」ことで消滅する
  - **言語内の先例も確認済み**＝`DATE_ADD` の MONTH 加算は**アンカー方式＋月末丸め**を
    既に実装している（実測: `'2025-01-31' +1M → 02-28`・**`+2M → 03-31`**（累積でない）・
    うるう年 `'2024-01-31' +1M → 02-29`）。万一将来任意日起点を開くなら規則は
    **DATE_ADD 準拠**の一択（PG の `generate_series` の累積ドリフトは、PG 自身の
    単発 interval 加算とも食い違う実装アーティファクトであり、追随しない）
- 出力形は `DATE`（YYYY-MM-01）か `YYYY-MM` 文字列かも評価時に決める
  （依頼元の月次キーは `DATE_FORMAT(日付,'%Y-%m')` の文字列）
