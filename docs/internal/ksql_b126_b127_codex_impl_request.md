## 罠（R1→R4 で 4 回訂正した箇所。同じ穴に落ちないこと）

1. **正規化を `classifyWhereCapability` の中で行わない**（R4 §2.0）。
   同関数は capability しか返さず、**converter / JOIN planner / COUNT / KORDER /
   ローカル再評価は別途 `stmt.where` を読む**。分類関数内で書き換えると
   **分類結果と実際に使われる述語が分離する**。
   **schema resolver 構築後**に純粋な正規化 API を置き、
   `{ normalizedWhere, rewrites }` を返して**実行と `EXPLAIN` が同じ結果を使う**。

2. **判定は各 `BINARY` leaf 単位**（R4 §2.1）。WHERE 全体の capability で見ると、
   `AND` の中の 1 つだけが residual のとき全体は `SUPERSET_PREFILTER` になり
   **正規化が漏れる**。

3. **`!=` も対象**（R4 §2.5）。R3 では「`not in` は部分集合になり得る」として
   除外していたが**根拠が誤りだった**。実データでも `!= '出庫'` = `NOT IN ('出庫')` = 95。

4. **`EXPLAIN` の計画は変わってよい**（R4 §4.3）。正規化が効けば `mode` / `fetch` /
   `reason` / COUNT・KORDER の判定は変わる。**それが効果そのもの。**
   受入は「**`IN` / `NOT IN` と書いた場合と完全一致**」で固定する。
   **`metrics.fetchedRows` の厳密減少は受入にしない**（Cursor 経路を数えず、減らない形もある）。

### 絶対に壊してはいけないもの

- **`= '存在しない値'` は今 0 行で正常終了する。** `IN ('存在しない値')` は `GAIA_IQ10` エラー
  （実測・`ksql_language_reference.md:447` に文書化された既存挙動）。
  **`optionOrder` で実在を確認できたときだけ正規化する。** 実在しなければ従来どおり residual。
- **空文字は対象外**（`= ''`）。押し下げ経路ごとに `IN ('')` の扱いが違う
- **複数値型は対象外。** `LOCAL_SCALAR_TYPES` に属する型だけ
  （`USER_SELECT` / `ORGANIZATION_SELECT` / `GROUP_SELECT` 等は `IN` が集合 overlap で意味が変わる）
- `CHECK_BOX` / `MULTI_SELECT` / `CREATOR` / `MODIFIER` の `=` は
  `LOCAL_VALID_OPERATORS` で手前から `UNSUPPORTED`。**その挙動を変えない**
