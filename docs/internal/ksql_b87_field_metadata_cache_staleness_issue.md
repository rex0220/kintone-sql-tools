# B87 アプリ定義キャッシュが無効化されず、追加した項目が「存在しない」と拒否される

- 起票: 2026-07-28
- ステータス: ✅ **実装済み（未リリース）**（2026-07-28）。→ [実装仕様](ksql_b87_metadata_cache_spec.md)
- 出典: B2 schema 復元拡張の事前検証（実 kintone・オーナー指摘「あとから項目を追加したケース」）
- 関連: [B86 実体化ソースの不存在列](ksql_b86_materialized_unknown_column_issue.md) / [B85 VALIDATE の制約検証](ksql_b85_library_validate_constraints_issue.md) / [B2 schema 復元拡張](ksql_empty_select_wildcard_pipeline_spec.md)

## 1. 事象

**kintone に項目を追加してデプロイしても、ksql は「存在しない」と拒否する。**

同一プロセス・同一アプリ・同一の項目で、`SELECT *` は見えているのに名指しすると落ちる。

```sql
SELECT レコード番号, B2確認C FROM APP423
-- → ArgumentError: unknown field code(s): B2確認C (APP423)

SELECT * FROM APP423
-- → …更新日時, B2確認C, 日時W…        ← 同じプロセスで見えている
```

`ksql_describe_app` も追加項目を返さない。一方 `ksql_app_metadata`（raw GET）は返す。

利用者から見た症状は **「項目を追加したのに ksql から使えない。VSCode を再起動すると直る」**。

## 2. 原因＝プロセス生存期間のキャッシュに無効化が無い

[`execute.ts:5034-5040`](../../src/execute.ts#L5034) のモジュール変数。**TTL も明示的な無効化も無い。**

```ts
const fieldTypeCache       = new Map<string, Map<number, FieldTypeMap>>();
const optionOrderCache     = new Map<...>();
const sortKindCache        = new Map<...>();
const fieldInfoCache       = new Map<string, Map<number, Promise<KintoneFieldInfo[]>>>();
const processStatusCache   = new Map<...>();
const numberPrecisionCache = new Map<...>();
```

`cacheContext` は [`buildCacheContext`](../../src/node/appProfiles.ts#L395) が生成する**内容由来の文字列**（`apps:M423=physical:APP423@dev`）で、プロセスごとに変わらない。
したがって**同じアプリを参照する限り、最初に取得した定義を最後まで使い続ける**。

**レコードは常に最新**（`getRecords` はキャッシュしない）。この非対称が §1 の内部矛盾を生む。

## 3. 影響範囲

| 面 | プロセス寿命 | 影響 |
|---|---|---|
| **MCP サーバー** | セッション中ずっと | ❌ **該当**（実測で確認） |
| **engine ライブラリ** | ホスト側が決める | ❌ **該当**（Pro のダッシュボードは常駐） |
| CLI | 1 実行 1 プロセス | ✅ 実害なし |
| プラグイン | 画面ごと | ✅ 実害なし |

**古くなるのは項目の追加だけではない。**上記6キャッシュすべてが対象で、少なくとも次が古いまま使われる。

- **選択肢の増減**（`optionOrderCache`）＝ IN 押し下げの `optionOrder` 実在検証が古い集合で判定する
- **プロセス管理の有効化／無効化**（`processStatusCache`）＝ `STATUS` 押し下げの可否が変わる
- **数値精度設定**（`numberPrecisionCache`）＝ VALIDATE の整数桁検証が古い設定で通る
- **必須・文字数・上下限**（`fieldInfoCache`）＝ **v3.30.0 の B85 で公開した制約検証**が、管理者が制約を厳しくしても古い条件で「エラーなし」と返す

## 4. 実測（2026-07-28・実 kintone APP423）

検証用アプリに項目を追加 → デプロイ → 確認 → 削除 → デプロイで**元の定義へ復元済み**。

| 操作 | `ksql_app_metadata`（raw GET） | `ksql_describe_app`（キャッシュ経由） | `SELECT *`（レコード由来） |
|---|---|---|---|
| 追加前 | 31 項目 | 31 項目 | 25 列 |
| **追加後** | **33 項目**（新項目あり） | **31 項目**（古いまま） | **27 列**（新項目あり） |

**`SELECT <新項目>` は `ArgumentError: unknown field code(s)` で拒否**。

## 5. なぜ今まで表面化しなかったか

- **CLI とプラグインでは起きない**（プロセスが短命）
- MCP でも **VSCode を再読み込みすれば直る**ため、利用者が原因に到達しにくい
- **fail-closed 側の誤検知**なので、誤った結果ではなくエラーとして出る（B78・B79・B86 のような silent wrong result ではない）

ただし **B86（v3.30.0）で不存在列の検証を強化した結果、この誤検知が届く範囲は広がっている。**
従来は素通ししていた実体化ソース経路でも、古い定義に基づいて拒否するようになった。

## 6. 対応案

### 6.1 案 A — アプリ設定リビジョンで無効化する（**却下**）

kintone の `revision` はアプリ設定を変更するたびに上がる（実測: 183 → 184 → 185 → 186）。
`cacheContext` に revision を含めるか、取得時に revision を照合して差があれば捨てる。

- **正確**（変更があったときだけ捨てる）
- ただし **revision を知るために 1 回 API を撃つ**必要があり、キャッシュの意味が薄れる箇所がある

### 6.2 案 B — TTL を入れる

例えば 60 秒。単純で追加 API が要らない。
**「追加した項目がしばらく使えない」は残る**が、再起動なしで必ず直る。

### 6.3 案 C — 明示的な無効化手段を公開する

MCP ツールまたはライブラリ API に「キャッシュを捨てる」操作を足す。
利用者が能動的に直せるが、**原因に到達できて初めて使える**ので単独では弱い。

### 6.4 案 D — 不存在列エラーのときだけ再取得して再判定する

`unknown field code(s)` を返す直前に 1 回だけ取り直し、実在すれば通す。

- **誤検知だけを狙って潰せる**（正常系のキャッシュ効果は無傷）
- 押し下げ・VALIDATE 側の陳腐化（§3）は直らない

**当初は案 A ＋ 案 D の併用を本命としたが、実コード確認で撤回した。**

**案 A は成立しない**＝`KintoneClient` にリビジョン取得の口が無く、追加すれば **B85 で判明した Pro の自前クライアントが壊れる**（必須メソッドの追加は破壊的変更）。
しかも**リビジョン取得自体が 1 API** なので、下記 案 E とコストが変わらない。**より複雑で、より壊れやすく、同じコスト**である。

### 6.5 案 E — キャッシュを実行単位スコープにする（採用）

内容由来の `cacheContext`（プロファイル分離＝正しさの役割）は残し、**実行ごとに一意な識別子を連結**して
実行終了時に破棄する。**案 D は不要になる**（陳腐化そのものが消えるため誤検知が起きない）。

**実測したコスト**＝増分は「1 実行 × 1 アプリあたり 1 回」だけ。
**1 実行内の重複排除（2 アプリ JOIN で 2 回・バッチ 4 文で 2 回）は完全に維持される**ため、
キャッシュ本来の価値は失われない。→ [実装仕様](ksql_b87_metadata_cache_spec.md)

## 7. B2 との関係＝**B2 の前提条件**

[B2 schema 復元拡張](ksql_empty_select_wildcard_pipeline_spec.md)（0 行 `SELECT *` の列復元）は
`getFields` から列を作る設計だが、**その `getFields` が古いままだと、修正自体が列数のブレを生む。**

| | 列の出所 | 追加項目 |
|---|---|---|
| データがある日 | レコード（常に最新） | 含む |
| データが無い日 | **キャッシュ（古い）** | **含まない** |

**B2 が避けようとしている「空の日だけ違う」を、B2 が作り出すことになる。**
したがって **B87 を先に片付けてから B2 に着手する。**

なお **B2 の列順の懸念（①）は解決済み**＝実 kintone 5 アプリで `getFields` の順序と
`SELECT *` の列順が完全一致することを確認した。**後から追加した項目は末尾ではなく途中に入る**
（APP423 では 6・8 番目）が、**その予測不能な位置まで両者は一致する。**

## 9. 優先度の根拠

**実害は出ているが、誤った結果ではなくエラーである**ため B86 ほどの緊急性は無い。
一方で **Pro のダッシュボードは常駐プロセス**であり、**B85 で公開したばかりの制約検証が古い条件で
「エラーなし」を返す**点は、v3.30.0 で Pro に案内した内容と整合しない。

**B2 の前提条件**でもあるため、B2 に着手するなら先に必要。
