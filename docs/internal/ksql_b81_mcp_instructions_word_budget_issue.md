# B81 MCP instructions の語数予算が構造的に枯渇する

- 起票: 2026-07-27
- ステータス: ✅ **実装済み（未リリース）**（2026-07-27）。案 D（散文とカタログで予算を分ける）を実装。
- 出典: B76 Phase B（v3.28.0）Step 5 で instructions が **552 語**となり guard に一度失敗。短縮して 548 語で通した。
- 関連: [B60 syntax hints](ksql_b60_mcp_syntax_hints_spec.md) / [B62 AI visibility](ksql_b62_ai_visibility_notes_issue.md) / [B67 実装計画](ksql_b67_impl_plan.md)

## 1. 事象

`KSQL_MCP_INSTRUCTIONS` の語数上限 **550 語**に対し、現在 **548 語**。**余裕は 2 語**。

`src/mcp/__tests__/metadataTools.test.ts`:

```ts
expect(instructionWords).toBe(548);           // 実測値の exact 固定（fail-loud）
expect(instructionWords).toBeLessThanOrEqual(550);
```

B76 Phase B で docs ポインタを 1 文追加しただけで **552 語**となり guard に失敗した。
既存記述を圧縮して 548 語に収めたが、**次に 3 語以上増える変更はそのままでは入らない**。

## 2. 推移＝単調増加であり偶発ではない

| 時点 | 語数 | 契機 |
|---|---:|---|
| B60（上限設定時） | — | **目安 ≤500 語・550 超は再圧縮**と定義 |
| B62 | 502 → **525** | AI 可視性ノート追加 |
| B67 | 529 → **541** | **相対日付 12 関数を catalog へ追加** |
| B76 Phase B | 552 → **548** | JOIN 対応の docs ポインタ（圧縮して収めた） |

**機能を足すたびに増える。**下げる力が働いていない。

## 3. 原因＝語数の測り方が「散文の冗長さ」と「カタログの規模」を混同している

段落ごとの実測（合計 548 語）:

| 段落 | 語数 | 比率 | 内容 | 生成元 |
|---|---:|---:|---|---|
| P1 | 27 | 5% | kSQL とは何か | 手書き |
| P2 | 39 | 7% | Key rules | 手書き |
| P3 | 50 | 9% | ツール使用手順 | 手書き |
| **P4** | **273** | **50%** | **Statement templates** | **`STATEMENT_SYNTAX_CATALOG` から生成** |
| **P5** | **159** | **29%** | **Complete function catalog** | **`KSQL_FUNCTION_CATALOG` から生成** |

**P4＋P5 で 79%** を占め、**どちらもカタログから自動生成**される。

語数は空白区切りで数えるため、**関数を 1 つ増やすと 1 語増える**
（`KSQL_FUNCTION_CATALOG.scalar.join(" ")` の各要素が 1 語）。
B67 で 12 関数を足したときに +12 語増えたのはこの構造による。

### 3.1 これは削ってはいけない部分である

カタログ列挙は **AI クライアントにとって最も価値が高い部分**である。

- 「この一覧が完全であり `IFNULL` のような他方言の関数は存在しない」と明示することで
  **存在しない関数の捏造を防いでいる**（B62 の目的そのもの）
- statement templates は **構文の推測を防ぐ**

つまり **上限に近づけているのは、instructions の中で最も効いている部分**である。
一方、上限 550 の趣旨（B60 の「目安 ≤500」）は **散文が冗長になるのを防ぐ**ことだった。

**測っているものと、抑えたいものがずれている。**

## 4. 方針案

| 案 | 内容 | 評価 |
|---|---|---|
| **A** | 既存重複文をさらに圧縮する | **一時しのぎ**。B60 当初の方針だが、B62・B67・B76 と3回連続で効かなくなっている。次の関数追加でまた埋まる |
| **B** | カタログを instructions から外し `ksql_docs` / resource へ委譲 | 構造的だが **B62 の目的（初回可視性）と正面衝突**。resource を読まないクライアントで捏造が復活する |
| **C** | 上限を 550 → 650 等へ引き上げる | 根拠が要る。**目安 500 の趣旨（簡潔さ）が失われ**、次も同じ理由で引き上げることになる |
| **D（推奨）** | **語数予算を「散文」と「カタログ列挙」で分けて計上する** | 抑えたいもの（散文の冗長さ）だけを抑える。カタログは機能追加に比例して増えて当然なので別枠にする |

### 4.1 案 D の具体化

```ts
// 散文（手書き部分）＝ 抑制対象
expect(proseWords).toBeLessThanOrEqual(200);     // P1-P3 ＋ P4/P5 の説明文
// カタログ列挙（自動生成）＝ 記録のみ、上限は緩く
expect(catalogWords).toBeLessThanOrEqual(450);
// 総量にも上限は残す（青天井にしない）
expect(totalWords).toBeLessThanOrEqual(650);
```

- **散文の上限を厳しく**することで B60 の趣旨（簡潔さ）を守る
- **カタログは機能追加で増えて当然**なので別枠にし、増加自体は失敗にしない
- **総量上限も残す**ことで青天井を防ぐ

分割の実装は `KSQL_MCP_INSTRUCTIONS` を組み立てる時点で
散文部分とカタログ部分を別の定数として保持すれば足りる（現在も `STATEMENT_SYNTAX_PARAGRAPH` /
`FUNCTION_CATALOG_PARAGRAPH` として分かれている）。

### 4.2 検討事項

- **exact 固定（`toBe(548)`）は維持する。** 意図しない増減を fail-loud に捕まえる仕組みで、
  B76 Phase B でも実際に機能した（552 語で止まった）
- 上限の根拠は「MCP クライアントの制約」ではなく **kSQL 自身が置いた予算**である。
  外部制約でない以上、**根拠を再定義してよい**
- 散文 200 語などの具体値は、実測（現在 P1〜P3 で 116 語）を見て決めること

## 5. 影響・規模

- **公開挙動の変更なし**（テストの計上方法を変えるだけ）
- **想定 0.25〜0.5 人日**
- ただし **着手しないと次の MCP instructions 変更がブロックされる**

## 6. 優先度の根拠

単独では小さいが、**次に MCP instructions へ 3 語以上足す課題が来た時点で必ず踏む**。
その課題の作業中に「まず圧縮から」となると、本来の課題の見積もりが崩れる。
**先に片付けておく類のもの**であり、B70（版同期ガード）と同じ性質である。

なお **B73（エラーの構造化・多言語）が instructions へ追記を伴う可能性が高い**ため、
B73 に着手するなら本課題を先に処理しておくのが望ましい。


## 【実装・2026-07-27】案 D を実装した

`src/mcp/instructionsBudget.ts` を新設し、`measureInstructionsWordBudget()` が
`{ total, catalog, prose }` を返すようにした。**カタログ由来の語数は文面ではなく元データ**
（`KSQL_FUNCTION_CATALOG` / `STATEMENT_SYNTAX_CATALOG` / CHECKS / CONTROL）から数える。

### 起票時の見積もりを訂正

起票時に「散文は P1〜P3 の 116 語」と書いたが**誤り**だった。
**P4/P5 の説明文（`STATEMENT_SYNTAX_COMMON_NOTES` や function catalog の注記）も散文**なので、
実測は次のとおり。

| 区分 | 語数 |
|---|---:|
| total | 548 |
| catalog（機能追加に比例） | **258** |
| prose（抑制対象） | **290** |

そのため §4.1 に書いた「散文 200 語」は実態に合わない。閾値は実測に合わせて設定した。

### 閾値

```ts
expect(budget).toEqual({ total: 548, catalog: 258, prose: 290 }); // exact 固定は維持
expect(budget.prose).toBeLessThanOrEqual(320);    // 抑制対象
expect(budget.catalog).toBeLessThanOrEqual(420);  // 増えて当然・青天井は防ぐ
expect(budget.total).toBeLessThanOrEqual(700);
```

### 破壊テストで肝心の性質を確認した

関数を5個追加して再測定した結果:

| | before | after |
|---|---:|---:|
| total | 548 | 553 |
| catalog | 258 | **263** |
| prose | 290 | **290（不変）** |

**旧ルールでは total 553 で上限 550 を突破**していた。新ルールでは catalog 枠が動くだけで、
**機能追加が散文の予算を食わない**。これが本課題の目的である。

exact 固定は残しているので、この変更自体はテスト更新を要求する（意図した fail-loud）。
