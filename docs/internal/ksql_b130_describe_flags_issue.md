## 1. 何が起きるか

`ksql_describe_app` は**フィールドコード・ラベル・タイプの 3 列だけ**を返す（実測・APP4228）。

```
{"フィールドコード":"製品名","ラベル":"製品名","タイプ":"SINGLE_LINE_TEXT"}
{"フィールドコード":"仕入先","ラベル":"仕入先","タイプ":"SINGLE_LINE_TEXT"}
```

**この 2 行は describe 上で見分けが付かない。** 実際には次のように違う（`ksql_app_metadata` 実測）。

| フィールド | 実体 |
|---|---|
| `製品名` | **ルックアップ**（`relatedApp: 4229` / `relatedKeyField: 製品名` / `fieldMappings: 仕入先`） |
| `仕入先` | 素の文字列。ただし**ルックアップがコピーしてくる先**（`fieldMappings` の宛先） |

**型からは推測できないが、推測がしばしば当たる。** 当たっている限り誰も気づかず、
外れたときだけ静かに間違う。

### 実際に踏んだ

記事レビュー（2026-08-05）で、履歴側の `製品名` を「表示用の素の文字列」と推測し
**「結合キーが無い」**と書いた。実際はマスタを引くルックアップで、マスタ側は `unique: true` だった。
**結論（改称で在庫が割れる）は正しく、理由が誤っていた。**

## 2. 実測（2026-08-05・v3.48.0）

### 2.1 `unique` は「型に付いている」のではなくフィールドごと

| アプリ | フィールド | 型 | `unique` |
|---|---|---|---|
| APP4229 | `製品名` | SINGLE_LINE_TEXT | **`true`** |
| APP4229 | `製品番号` | SINGLE_LINE_TEXT | `false` |
| APP4228 | `仕入先` | SINGLE_LINE_TEXT | `false` |

**同じ型・同じアプリでも値が違う。** `製品番号` を名寄せキーに使えないことは
`unique: false` を見ないと分からない（見た目は「番号」なので使えそうに見える）。

### 2.2 **ルックアップのフィールドには `unique` プロパティが存在しない**

APP4228 の `製品名`（ルックアップ）の property には `unique` キーがそもそも無い。
`minLength` / `maxLength` / `expression` も無く、代わりに `lookup` オブジェクトが入る。

```json
"製品名": { "type": "SINGLE_LINE_TEXT", "code": "製品名", "label": "製品名",
            "required": false,
            "lookup": { "relatedApp": {"app":"4229"}, "relatedKeyField": "製品名",
                        "fieldMappings": [{"field":"仕入先","relatedField":"仕入先"}] } }
```

**したがって `unique` フラグは「`unique === true`」で判定する必要がある**（`!== false` ではない）。
プロパティ非在を「不明」として別扱いするかは仕様で決める（→ R1 の論点）。

### 2.3 **`expression` は CALC 以外の型にも存在する（空文字で）**

APP4228 の `仕入先`（素の SINGLE_LINE_TEXT）:

```json
"仕入先": { "type": "SINGLE_LINE_TEXT", ..., "expression": "", "hideExpression": false, "unique": false }
```

`個数_在庫計算用`（CALC）:

```json
"個数_在庫計算用": { "type": "CALC", ..., "expression": "IF ( 入出庫区分 = \"出庫\" , -個数 , 個数 )" }
```

**「`expression` プロパティを持つか」で判定すると、素の文字列まで CALC 扱いになる。**
非空かどうかで見る必要がある。

**逆に、非空なら型が CALC でなくても計算列**である（kintone の SINGLE_LINE_TEXT / NUMBER は
自動計算を設定できる）。**この形こそ「型からは分からない」の典型**で、
`calc` フラグを型ではなく `expression` の非空で決める根拠になる。
※ この環境に実例は無い（実測した 2 アプリでは CALC 型以外の `expression` はすべて空）。**未確認**。

## 3. 依頼側の案（採用）

**値の中身は要らない。フラグ 3 つだけ。**

| フラグ | 意味 |
|---|---|
| `lookup` | ルックアップか |
| `unique` | 重複禁止が付いているか |
| `calc` | 計算式が入っているか |

> **【2026-08-06 訂正】「1 ビットあれば `ksql_app_metadata` を引く判断ができる」は誤り。**
> **上の `仕入先` はルックアップのコピー先で、3 フラグはすべて空になる**（素の文字列と区別が付かない）。
> **つまり「3 つとも空なら metadata 不要」とは判断できない。**
> しかも現行の正規化は**その差を既に `writable` として持っている**（`formFieldInfo.ts:72,86-97`）。
> **§1 で「見分けが付かない」と書いた 2 行のうち、片方はこの改善でも見分けが付かない。**
>
> → 目的は「**lookup / unique / 計算式の有無を直接示す**」に狭める（[仕様 R2](ksql_b130_describe_flags_spec.md) §1.1）。
> それでも価値があるのは、この 3 つが**JOIN の正しさ・名寄せキーの可否・数値の意味**に直結し、
> **外したときの誤りが静かに通る**ため。

### なぜ 3 つで打ち止めか

**停止規則が明確**なため。「便利そうなものを足す」を始めると
`required` / `enabled` / `maxLength` / `options` / `defaultValue` と際限が無くなり、
それは `ksql_app_metadata` の仕事になる。**describe は「引くべきか」を判断させる面**に徹する。

> **Qiita 下書きで私は「説明文ではなく出力に 1 行足す」案を推したが、依頼側の案に差し替えた。**
> 依頼側の案のほうが停止規則が明確で、行動（`ksql_app_metadata` を引く / 引かない）に直結する。

## 4. 論点（R1 で決める）

1. **出力の形。** `DESCRIBE` は `type: "SELECT"` で `columns` を返す**行返し文**である。
   列を 3 本足すか、1 本（`制約` などのまとめ列）にするか。**下流（CTE 経由の SELECT）への影響**を測ること
2. **`unique` プロパティ非在の表現。** ルックアップには `unique` が無い。`false` と同じ扱いでよいか
3. **`calc` の判定条件。** 型 `CALC` か、`expression` 非空か、両方か
4. **既存の列名・並びを変えないこと**（回帰）。列の追加が破壊的変更にならないか
5. **サブテーブル・システムフィールド**の扱い（`RECORD_NUMBER` / `STATUS` などにフラグは付かない）
6. **CLI / プラグイン側の DESCRIBE 表示**に波及するか
