## 2. 差し戻し③ `MIN` / `MAX` が GROUP BY 無しで文字列比較のまま

`MAX(売上)` = **7,200,000**（`SELECT MAX(売上) FROM APP4149` で確認）に対して:

| SQL | 期待 | 実測 | 文字列比較なら |
|---|---|---|---|
| `CASE WHEN MAX(売上) > 9 THEN '大' ELSE '小' END` | 大 | **小** | `"7200000" > "9"` → `'7'<'9'` → false → 小 |
| `CASE WHEN MAX(売上) > 100000000 THEN '大' ELSE '小' END` | 小 | **大** | `"7200000" > "100000000"` → `'7'>'1'` → true → 大 |

**両方向で文字列比較と一致する。** 一方、次は正しい:

| SQL | 期待 | 実測 |
|---|---|---|
| `CASE WHEN AVG(売上) > 9 ...`（GROUP BY 無し） | 大 | **大** ○ |
| GROUP BY 有り `CASE WHEN MAX(売上) > 9 ...`（5,400,000 の会社） | 大 | **大** ○ |

つまり **`MIN` / `MAX` × GROUP BY 無し**の組み合わせだけが残っている。
`COUNT` / `SUM` / `AVG` は GROUP BY の有無を問わず数値、`MIN` / `MAX` は GROUP BY 有りなら数値。

### 原因の見立て

`MIN` / `MAX` の比較意味論は引数の型メタ（`resolveAggregateArgSemantics` /
`AggregateSortKindResolver`）から決まる。**GROUP BY 無しの全件集計経路で、この型リゾルバが
CASE 側へ渡っていない**ため、安全側のコードポイント順にフォールバックしていると見られる。
GROUP BY 有りの経路では渡っているので正しく動く。**その差分を追えば特定できるはず。**

## 3. テストの穴（2 回連続で同じ形）

`npm test` 5277 通過でも③は素通りした。1 回目に渡した観点では
「GROUP BY 有り・無しの両方で通す」と書いたが、**集計関数の種類を網羅していなかった**。
次は下の組み合わせを機械的に埋めること。

**{GROUP BY 有り / 無し} × {`COUNT` `SUM` `AVG` `MIN` `MAX` `GROUP_CONCAT` `MODE`}**

各セルで、**文字列比較なら必ず落ちる境界**を使う。桁が揃った値では文字列比較でも通るため無意味。

- 数値集計: `> 9`（値は 7 桁）と `> 100000000`（値は 7 桁）の**両方向**を入れる
  — 片方だけだと、たまたま一致して通る
- 文字列集計（`GROUP_CONCAT` / `MODE`）: 文字列比較のままであることを固定する
- `MIN` / `MAX`: **数値フィールドと文字列フィールドの両方**を引数にした形
