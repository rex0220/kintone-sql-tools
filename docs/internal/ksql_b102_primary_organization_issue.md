## 1. 何を足すのか

**kintone のクエリ関数 `PRIMARY_ORGANIZATION()` を kSQL の WHERE で使えるようにする。**

```sql
SELECT 案件名 FROM APPn WHERE 担当組織 IN (PRIMARY_ORGANIZATION())
```

**「API を実行したユーザーの優先する組織」**を指す。

### 1.1 用途（オーナー指示）

**LOGINUSER() と同様に、ダッシュボードで自組織のデータを抽出するために使う。**

**これは §4.2 の危険が最も効く使い方でもある。**
**ダッシュボードの読み手は、絞り込みが効いているかどうかを画面から判断できない。**
**「自組織の実績」のつもりの数字が全社の数字になっていても、そう見える。**

**同時に、用途が SELECT に閉じていることも意味する。**
**DML を fail-closed にしても、この用途は何も失わない。**

## 2. kintone 側の仕様（[公式](https://cybozu.dev/ja/kintone/docs/overview/query/) 実測 2026-07-29）

| | |
|---|---|
| **使える型** | **組織選択（`ORGANIZATION_SELECT`）のみ** |
| **使える演算子** | **`in` / `not in` のみ** |
| **意味** | API を実行したユーザーの優先する組織 |

### 2.1 **⚠ 優先組織が未設定だと、条件が無視されて全件返る**

> **API を実行したユーザーに優先する組織が設定されていない場合、
> `組織 in (PRIMARY_ORGANIZATION())` の条件は無視され、
> それ以外の絞り込み条件を満たすすべてのレコードが取得されます。**（公式・原文）

**これが本課題の中心である。**

**kintone 自身が fail-open する。**
**しかも「無視された」ことは応答から分からない。**

**`LOGINUSER()` とは向きが逆である。**

| 関数 | 文脈が解決できないとき |
|---|---|
| `LOGINUSER()` | **該当なしへ閉じる**（0 件） |
| **`PRIMARY_ORGANIZATION()`** | **全件へ開く**（条件が消える） |

## 4. なぜ素通しにできないか

**kSQL は B78 → B79 → B86 → B90 → B94 → B97 → B98 と、
「黙って誤った結果を返す」形を一貫して潰してきた。**

**`PRIMARY_ORGANIZATION()` の fail-open は、その典型そのものである。**

### 4.1 DML では致命的

**WHERE が押し下げられる DML で条件が消えると、対象が全件になる。**

```sql
DELETE FROM APPn WHERE 担当組織 IN (PRIMARY_ORGANIZATION())
-- 優先組織が未設定 → 条件が無視される → アプリ全件が対象
```

**これは「誤った結果」ではなく「誤った書き込み」である。**

### 4.2 SELECT では「誤った結果」（権限昇格ではない）

**kintone のレコード閲覧権限は引き続き効く。**
**取れるのは「そのユーザーが元から見られるレコード」の全部**であって、
**見えないはずのレコードが見えるようになるわけではない。**

**それでも、「自分の組織の案件」のつもりで書いた集計が
全社の集計になる**——**黙って誤る**という性質は変わらない。

## 5. 案

### 案 A: `LOGINUSER()` と同じ扱いで素通しする

- **最小の実装。**関数名を 1 つ足し、直列化で素通しするだけ
- **fail-open をそのまま製品に持ち込む。**§4 と正面から衝突する
- **DML の危険が残る**

### 案 B: **SELECT は許可（警告付き）・DML は fail-closed**

- **DML の WHERE に現れたら拒否する**（`whereToKintone` の中央ガードは LIKE で前例がある）
- **SELECT では通し、「優先組織が未設定の場合は条件が無視される」旨を警告に出す**
- **実装は現実的。**ただし**SELECT の「黙って誤る」は残る**（警告は出るが、誤りが起きたかは分からない）

### 案 B': **条件が落ちたことを実測で検出する**（**User API 不要の fail-closed**）

**in と not in の両方を数えれば、条件が無視されたかどうかが分かる。**


正常（優先組織あり）  in = X 件 / not in = Y 件   → X も Y も全件より小さい
                      （X + Y ≤ 全件。空セルはどちらにも入らない）

落ちた（優先組織なし）in = 全件 / not in = 全件     ← 両方が全件になるのは、この場合だけ


**判定式**


全件 > 0 かつ COUNT(組織 in (PRIMARY_ORGANIZATION()))     == 全件
            かつ COUNT(組織 not in (PRIMARY_ORGANIZATION())) == 全件
  → 条件が無視された → エラー


| | |
|---|---|
| **誤検知しないこと** | 正常時に in が全件になるのは**全レコードが自組織**のときで、そのとき not in は **0 件**になる（全件 > 0 なら一致しない） |
| **見逃す場合** | **全件 = 0 のときだけ**判定できない。**そのとき結果も空なので害が無い** |
| **費用** | COUNT(*) 2 回。**[B94](../ksql_issue_tracker.md) の単発取得（totalCount）が効けば 2 GET** |
| **B54 が要らない** | **User API を引き込まずに fail-closed にできる**——これが案 C との決定的な差 |

> **判定しているのは「実行ユーザーに優先組織があるか」であって、クエリの内容ではない。**
> **1 実行につき 1 回測れば足りる**（同一実行内で使い回せる）。

**限界**——**プローブ自体もレコード取得なので、レコード 0 件のアプリでは判定できない。**
**また、プローブと本体の間に優先組織が変わると理屈上ずれる**（現実には無視できる）。

### 案 C: **優先組織の有無を先に確かめ、無ければエラー**（**本来の fail-closed**）

- **実行ユーザーの優先組織を取得できれば、fail-open を完全に潰せる**
- **User API（[B54](../ksql_issue_tracker.md)）が要る**＝**B67 が予見していた相乗**
- **API トークン認証では実行ユーザーが存在しない**ため、**その面では常に拒否**になる可能性がある
- **費用が最も大きい**

### 案 D: 実装しない

- **`LOGINUSER()` と違い、安全に通せる保証が無い**
- **実需が出ていない**（今回はオーナー指示による起票で、利用者からの要望ではない）

## 6. 実装前の測定（**実施済み 2026-07-29**）

**検証アプリ APP4227（`名前` / `担当組織`＝`ORGANIZATION_SELECT`）を作り、
組織を未設定にしたレコードを 3 件入れて測った。**

**生の kintone クエリが要るため、`ksql.config.json` の認証情報で REST を直接叩いた。**

### 6.1 結果

```
全件（条件なし）                                  → 3 件
担当組織 in (PRIMARY_ORGANIZATION())              → 0 件
担当組織 not in (PRIMARY_ORGANIZATION())          → 3 件
名前 like "組織なし"（対照）                      → 3 件
名前 like "組織なし" and 担当組織 in (PRIMARY_...) → 0 件
```

| プロファイル | 結果 |
|---|---|
| `dev` | `all=3 in=0 notIn=3` → **条件は適用された** |
| `guest` | `all=3 in=0 notIn=3` → **条件は適用された** |
| `prod` / `pguest1` | 別環境で APP4227 に到達できず（`GAIA_AP01`） |

### 6.2 **分かったこと**

**① 正常系は期待どおり動く。**
**組織が未設定のレコードは `in` に入らず `not in` に入る。**
**`in` と `not in` が全件を分割する**（3 = 0 + 3）。

**② fail-open は再現できなかった。**
**アクセスできたユーザーは、いずれも優先組織を持っていた。**
**「優先組織が未設定のユーザー」をこの環境で用意できない**（ユーザー管理の変更が要る）。

**③ 案 B' の判定式の前提は成り立っていた。**
**正常時に `in` と `not in` が両方とも全件になることは無い**（§5 案 B'）。

| **トークン認証面** | 4 プロファイルすべてパスワード認証のため未測定 |
| **プラグイン面** | 未測定（ブラウザのログインユーザー文脈） |

## 7. 現時点の見立て（R2）

**`LOGINUSER()` と同じ形で入れる。加えて DML だけ fail-closed にする。**

### 7.1 実装は `LOGINUSER()` と同じでよい

**初版は fail-open を重く見すぎた。**

**違うのは 1 点だけ**である。
**それ以外——カタログ・サーバ専用扱い・押し下げの直列化・ローカル評価不可・
型×演算子の制約——はすべて `LOGINUSER()` と同じ経路に乗る。**
**型の側（`ORGANIZATION_SELECT` × `in` / `not in`）は既にある**（§3）。

**fail-open が起きる条件も、測ると狭い。**

| 当初の想定 | 実際 |
|---|---|
| **トークン認証では実行ユーザーが無く、常に fail-open** | **現に使われている 4 プロファイルはすべてパスワード認証**。プラグインもログインユーザー（§6-2） |
| いつでも起こりうる | **「実在するユーザーだが、優先組織が未設定」のときだけ** |

### 7.2 それでも DML だけは fail-closed にする

**用途はダッシュボードでの抽出＝SELECT に閉じている**（§1.1）。
**DML を拒否しても、この用途は何も失わない。**
**一方、DML で条件が落ちれば全件 UPDATE / DELETE になる**（§4.1）。

**失うものが無く、防ぐものが大きい。ここだけは入れる。**

### 7.3 SELECT は素通しでよい

- **kintone 自身がそう振る舞う。**kintone の一覧の絞り込みでも同じことが起きる
- **KLIKE の前例**＝**kintone のネイティブ挙動へ素通しする**と決めた判断と同じ筋
- **代わりに fail-open を文書へ明記する**（言語リファレンス・MCP instructions・関数カタログ）

### 7.4 案 B' は「必要になったら」

**`in` と `not in` の突き合わせで検出できること自体は成り立つ**（§5 案 B'）。
**ただし `COUNT(*)` 2 回の常時追加は、狭い条件のために払う費用としては重い。**

**§6-1 を測り、実運用で踏みうると分かった時点で上積みする。**

### 7.5 優先度

**中。**用途がはっきりしており（§1.1）、実装は `LOGINUSER()` の写しで済む。

**§6 は測り終えた。**
**正常系は期待どおりで、fail-open は再現できなかった**（優先組織を持たないユーザーを用意できない）。

**したがって文書には「公式の記述による」と明記して書く。**
**「実測した」とは書かない。**

## 8. 対象外

| | 理由 |
|---|---|
| **`ORGANIZATION_SELECT` 以外の型での使用** | **kintone が受け付けない**（§2）。取得前に拒否する |
| **`in` / `not in` 以外の演算子** | 同上 |
| **ローカル評価（FULL_SCAN 対応）** | **サーバ側のユーザー文脈が要る**ため再現できない。`LOGINUSER` と同じ扱い |
| **`ORDER BY` での使用** | kintone のクエリ関数は WHERE 用 |
| **B54 User API の実装そのもの** | **案 C を採る場合に改めて判断する** |

## 9. 実装とリリース（v3.35.0・2026-07-29）

**`LOGINUSER()` と同じ経路に足し、DML だけ fail-closed にした。**
**codex の停止は 0 回。**経路を全部たどってから仕様を書いたことが効いた。

### 9.1 レビューで独立に確かめた 5 点

| | 結果 |
|---|---|
| 押し下げ | `kintone query: 担当組織 in (PRIMARY_ORGANIZATION())`・`EXACT_PUSHDOWN`・**client 評価 0** |
| 実機 | `in`=0 / `not in`=3 — **§6 の REST 直叩きと完全一致** |
| DML 拒否 | `DELETE` / `UPDATE` とも拒否し、**レコードは 3 件のまま残った** |
| `LOGINUSER()` | **無傷**（押し下げも `--allow-dml` の DML も従来どおり） |
| 型・演算子・混在 | `ORGANIZATION_SELECT` 以外／`=` 演算子／`IN` リスト混在の 3 つとも取得前に拒否 |

### 9.2 語数予算

**予想と完全一致**＝`{ total: 554, catalog: 259, prose: 295 }`（`catalog` だけ +1・段落数 6 のまま）。

### 9.3 気づいた点

**`--allow-dml` を付けずに DML を書くと、新ガードが先に立つ。**

```
DELETE ... PRIMARY_ORGANIZATION()  → 「PRIMARY_ORGANIZATION() は DML の WHERE では使用できません」
                                     （「DML is disabled」より先に出る）
```

**既存文には影響しない**（この関数は従来パースすらできなかった）。
**より具体的な理由が出るので、このままとする。**

### 9.4 **文書に書いたこと**

**DML を拒否するだけでは片手落ちになる。**
**`SELECT` でも、優先組織が未設定の利用者では絞り込みが効かない。**

**CHANGELOG・`release/README.txt`・GitHub Release の 3 つすべてに、
「エンジンからは判別できないのでそのまま返す。kintone の一覧の絞り込みと同じ挙動」
と明記した。**

**fail-open は一貫して「kintone 公式の記述による」とし、「実測した」とは書いていない**（§6.3）。
