## 0. 実測（v3.56.3・APP4228・**3 か所すべてで通る**）

### 0.1 `GROUP BY` あり

```sql
SELECT 製品名, 個数, 日付, SUM(個数) AS 合計, COUNT(*) AS 件数
FROM APP4228 GROUP BY 製品名
  → 食パン / 646 / 2025-08-05 / 23429 / 件数 220
```

**`個数` と `日付` はグループの先頭レコードの値**（素の `SELECT ... LIMIT 3` の 1 行目と一致）。

### 0.2 **`GROUP BY` 無し（集計だけ）** — **いちばん危ない**

```sql
SELECT 製品名, 個数, SUM(個数) AS 合計, COUNT(*) AS 件数 FROM APP4228
  → 食パン / 646 / 85438 / 件数 1000     （1 行）
```

**1000 件が 1 行に畳まれ、`製品名` と `個数` は先頭レコードの値。**
**`GROUP BY` を書いていないので、集計したつもりが無い人ほど踏む。**
**見た目は明細行と区別が付かない。**

### 0.3 `HAVING`

```sql
SELECT 製品名, SUM(個数) AS 合計 FROM APP4228 GROUP BY 製品名 HAVING 個数 > 0
  → エラーにならず 3 行返る
```

**いずれも警告なし・文書の規定なし。**

## 1. 規則（標準 SQL）

**集計を含むクエリでは、列参照は次のいずれかでなければならない。**

1. **`GROUP BY` に現れている**（フィールド名、または `GROUP BY` と構文的に一致する式）
2. **集計関数の引数の中にある**

**満たさない参照はエラー。** `GROUP BY` の有無に関わらず適用する
（**`GROUP BY` の無い集計クエリは「全体で 1 グループ」**なので、同じ規則が効く）。

**適用箇所は 3 つ**＝**`SELECT` 句 / `HAVING` 句 / `ORDER BY` 句**。

> **`ORDER BY` は §5-1。** `GROUP BY` 無し集計での `ORDER BY` は 1 行しか無いので実害が薄く、
> **`ORDER BY` を Phase 1 に入れるかは論点として残す。**

## 2. 「集計を含むクエリ」の判定

**`SELECT` / `HAVING` のいずれかに集計関数があるか、`GROUP BY` があるとき。**
**集計もグループ化も無い素の `SELECT` には一切影響しない**（本件で最も守るべき回帰）。

## 3. `GROUP BY` との対応づけ

**[B147](ksql_b147_aggregate_alias_shadows_key_input_issue.md) と同じ罠を踏まないため、名前一致で済ませない。**

- **フィールド参照**＝`GROUP BY` の解決結果（物理フィールド／別名／システム列）と**同じ実体**を指すこと。
  **言語リファレンス §8 の解決順**（**同名フィールドがあればフィールド優先**、無いときだけ SELECT 別名）に従う
- **式**＝`GROUP BY DATE_FORMAT(日付,'%Y-%m')` に対し
  `SELECT DATE_FORMAT(日付,'%Y-%m')` は**構文的に一致すれば許可**する。
  **正規化の方法は §5-2**（AST の構造比較で足りるか、別名経由に限るか）
- **別名経由**＝`SELECT DATE_FORMAT(...) AS 年月 ... GROUP BY 年月` は
  **現行の主用途**であり、**必ず通ること**（受入 §4.1）

## 4. 受入条件

### 4.1 通り続けるもの（**回帰。ここが壊れたら出さない**）

| 入力 | 期待 |
|---|---|
| `SELECT 製品名, SUM(個数) FROM APP4228 GROUP BY 製品名` | 通る |
| `SELECT DATE_FORMAT(日付,'%Y-%m') AS 年月, SUM(個数) … GROUP BY 年月` | **通る**（主用途） |
| `SELECT DATE_FORMAT(日付,'%Y-%m'), SUM(個数) … GROUP BY DATE_FORMAT(日付,'%Y-%m')` | 通る（式の一致） |
| `SELECT SUM(個数) FROM APP4228`（集計だけ） | 通る |
| `SELECT 製品名, 個数 FROM APP4228`（**集計もグループ化も無い**） | **通る**。素の SELECT に影響しない |
| `GROUP BY ROLLUP(...)` の grouping item | 通る |
| レシピ R13 / R15 / R16 / R17 の掲載 SQL | **通る**（測って該当なしを確認済み） |

### 4.2 エラーになるもの

| 入力 | 期待 |
|---|---|
| §0.1（`GROUP BY` あり・非集計列） | エラー |
| §0.2（**`GROUP BY` 無し・集計と素の列の混在**） | エラー |
| §0.3（`HAVING` の非集計列） | エラー |
| `GROUP BY a` に対し `SELECT b`（`b` は別のフィールド） | エラー |
| `GROUP BY DATE_FORMAT(x,'%Y')` に対し `SELECT DATE_FORMAT(x,'%m')` | エラー（式が違う） |

### 4.3 エラー文（**事前照会をしないので、これが唯一の案内**）

| 要件 | なぜ |
|---|---|
| **どの列かを名指しする** | 列が多い SELECT で探させない |
| **「存在しない」と読めないこと** | **その列は存在する**。[v3.56.1](ksql_b145_describe_subtable_field_issue.md) で `unknown field code(s)` が「そんな項目は無い」と読まれ、誤った結論へ誘導した |
| **書き換え後の形を 2 つ示す** | `MIN(<列>)` と `GROUP BY` への追加。**意味が変わるので利用者が選ぶ** |
| **示した形が実際に動くこと** | **[B140](ksql_b140_cte_groupby_total_order_issue.md) と [B145](ksql_b145_describe_subtable_field_issue.md) で「従うと壊れる助言」を 3 回出している。**実測してから載せる |
| **`GROUP BY` 無しの形でも通じること** | §0.2 は「`GROUP BY` に足す」が的外れに読める。**文面を分けるか要検討**（§5-3） |

**骨子**（実装時に実測して確定）

```
ArgumentError: 個数 は集計もグループ化もされていません（APP4228）。
GROUP BY 製品名 のもとでは、グループ内のどの行の値を返すか決まりません。
  グループごとに 1 つに決まる値なら  →  MIN(個数) AS 個数
  行を分けたいなら                  →  GROUP BY 製品名, 個数
```

**「なぜ決まらないか」を書く**のは、[v3.56.2](ksql_b145_describe_subtable_field_issue.md) で
**症状だけ書くと別の入口から来た人に通じない**と学んだため。

### 4.4 位置と副作用

- **レコード取得前にエラー**（§8 が既に持つ「レコード取得前にエラーになります」の一覧に並べる）。
  **取りに行ってから落ちるのは無駄な API 消費**
- **通るクエリの値・並び・列は一切変えない**
- **`EXPLAIN` / `ksql_validate` でも同じエラーになること**
  （**依頼元は実行前に `ksql_explain` まで通す運用**。→ [B143](ksql_b143_explain_warnings_issue.md)）

## 5. 未確定（実装前に決める）

1. **`ORDER BY` を Phase 1 に含めるか**（§1 の注記）
2. **式の一致をどう判定するか**（AST の構造比較か、別名経由に限るか）。
   **緩すぎると偽陰性、厳しすぎると既存クエリを落とす**
3. **`GROUP BY` 無しの形のエラー文**（§4.3 の最終行）
4. **CTE・一時テーブル・JOIN 経由**で同じ判定が効くか。**効かないなら穴が残る**
5. **`$id` / `レコード番号` で `GROUP BY` した場合**＝標準 SQL は**一意キーへの関数従属**を認めるので
   他の列を許してよい。**Phase 1 では許さない**（`MIN()` で書ける）が、
   **[B140](ksql_b140_cte_groupby_total_order_issue.md) の候補キーが入れば自然に解ける**。**そちらと合流させる**

## 6. 関連

### 6.1 破壊的変更

**`SELECT *` の列数を変えた [v3.56.0](ksql_b145_describe_subtable_field_issue.md)、
拡張 grouping をエラーにした v3.56.1 と同じ扱い。**
**リリースノートに移行案内を明記する。**

**依頼元（`ksql-analytics`）の資産は該当なし**（オーナーが把握）。
**測れないのは保存クエリとプラグイン利用者だけ。**

### 6.2 [B140](ksql_b140_cte_groupby_total_order_issue.md) との交差

**§5-5 の関数従属は、B140 の「候補キー」と同じ概念。**
**B140 が relation レベルの候補キーを持てば、本件の Phase 2 はそれを使える。**
**Phase 1 で「候補キーを持たない」形に閉じておけば、B140 の道を塞がない。**

## 7. [B147](ksql_b147_aggregate_alias_shadows_key_input_issue.md) との区別（**別の欠陥・本仕様では直らない**）

**B147 は「集計の別名が、別の列の式が参照するフィールドを上書きする」**（`年月` が空になる）。
**本件の規則を入れても直らない**——B147 の `DATE_FORMAT(日付,…) AS 年月` は
**`GROUP BY 年月` のキーそのもの**なので、§1 の規則を満たしてしまう。

**ただし方針は共通にできる**＝**標準 SQL では、SELECT 句の別名は
同じ SELECT 句の他の式からは見えない。** **B147 も「標準 SQL に合わせる」で直る。**
**B147 の仕様を書くときに、この原則を出発点にする。**
