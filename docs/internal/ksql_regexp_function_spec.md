## 0. 結論の要約

**関数の追加自体は容易で、本仕様の本体は ReDoS（破滅的バックトラック）対策である。**

- kSQL は既に評価ホットパスで `RegExp` を使っており（`evalWhere.ts:370`）、`evalFunc.ts` は leaf。追加は機械的。
- 文字列リテラルはバックスラッシュを素通しするため、`'\d+'` がそのまま届く（**MySQL のような二重エスケープが不要**）。
- **しかし利用者が正規表現を直接書けるようになると、1 行あたり 14 秒 CPU を占有する式が書けてしまう**（§4 実測）。kSQL のタイムアウトはこれを止められない。プラグインはブラウザで動くため kintone の画面ごと固まる。
- したがって **v1 は「ReDoS を構文的に起こせない安全部分集合」に限定する**（§4.3）。
- **R2 で追加**: 方言は `new RegExp` を呼ぶ以上 **ホストエンジン依存**であり、プラグイン（ブラウザ）と CLI/MCP（Node）で結果が変わり得る（§3.1）。**v2.0.0 の「同じ SQL は実行モードによらず同じ結果」という原則に構造的に反する最初の機能**になる。回避不能かつ fail-closed 側に倒れるため受け入れるが、**文書での注意喚起が唯一の対策**。

## 1. 実需

kintone の運用で、現状の `LIKE` / `REPLACE` / `SUBSTRING` では届かないもの:

| 用途 | 現状 | 正規表現なら |
|---|---|---|
| 書式検証（郵便番号・電話番号・社内コード） | **原理的に不可能**。`LIKE '___-____'` は桁数しか見られない（**実機: `abc-defg` にも `１０３-６０２７` にも一致**。§4.5.0） | `REGEXP_LIKE(郵便番号, '^[0-9]{3}-[0-9]{4}$')` |
| フリーテキストからの抽出 | 不可能。`SUBSTRING` は固定位置のみ、`INSTR` と組んでも可変長に追随できない | `REGEXP_SUBSTR(メモ, '[A-Z]{2}-[0-9]{6}')` |
| **数字以外を除去**・文字範囲の検出・連続空白の圧縮 | **原理的に不可能**。`REPLACE` はリテラル置換で「数字以外の全て」を列挙できない（§4.5.0） | `REGEXP_REPLACE(電話番号, '[^0-9]', '')` |
| 異体字の正規化（`（株）`/`(株)`/**`（株)`**/**`(株）`**/`㈱`） | **実務上は代替困難**。`REPLACE` は「開き × 閉じ × 会社種」の**積**を人手で列挙する必要があり（株＋有で **10 段**）、**列挙漏れは黙って非変換**になる（§4.5.0・実機実測） | `REGEXP_REPLACE(会社名, '[（(]株[）)]｜㈱', '株式会社')` — **1 パターンで 4 通りの括弧＋合字** |

いずれも「B12 の事前検証で弾く前に、そもそも不正な値を検出・修正したい」という B12〜B19 の弧の延長にある。

## 2. 追加する関数

主要 RDB の共通集合は `REGEXP_LIKE` / `REGEXP_REPLACE` / `REGEXP_SUBSTR` / `REGEXP_INSTR` の 4 つ（§9 の比較表）。

| 関数 | 構文 | 戻り値 |
|---|---|---|
| `REGEXP_LIKE` | `REGEXP_LIKE(値, パターン [, フラグ])` | 一致すれば `'1'`、しなければ `'0'` |
| `REGEXP_REPLACE` | `REGEXP_REPLACE(値, パターン, 置換 [, フラグ])` | 置換後の文字列（**全件置換**） |
| `REGEXP_SUBSTR` | `REGEXP_SUBSTR(値, パターン [, フラグ])` | 最初の一致文字列。非一致は空文字 |

**`REGEXP_INSTR` は v1 で追加しない。** B19 の「ファミリーを欠けたまま出さない」原則に反するように見えるが、B19 の対称性は **`LEFT`/`RIGHT`・`GREATEST`/`LEAST`・`LPAD`/`RPAD` のような対（かたわれが欠けると利用者が迷う組）**についての原則だった。`REGEXP_INSTR` は対の相方ではなく独立した 4 つ目で、`INSTR`（B19）が非正規表現の位置検索を既に埋めている。需要が出た時点で追加する。§10 に将来候補として記載する。

### 2.1 `REGEXP_LIKE` が真偽値でなく `'1'`/`'0'` を返す理由

kSQL の `evalStringFunc` は `string` を返す設計で、真偽型が無い。既存の同型は無いが、`IF(cond, a, b)` の `cond` は WHERE 式であって関数戻り値ではない。したがって:

```sql
-- ✓ 想定する書き方
SELECT * FROM APP100 WHERE REGEXP_LIKE(郵便番号, '^[0-9]{3}-[0-9]{4}$') = '1'
SELECT 会社名, REGEXP_LIKE(電話番号, '^0[0-9-]+$') AS 電話書式OK FROM APP100
```

**Oracle の `REGEXP_LIKE` は条件（condition）であって関数ではなく、`WHERE REGEXP_LIKE(x, p)` と裸で書ける。MySQL / PostgreSQL は真偽を返す関数なので同じく裸で書ける。kSQL は `= '1'` が要る点で 3 者いずれとも異なる。**

これは kSQL の型設計上の制約であり、回避するには WHERE の述語として `REGEXP_LIKE` を特別扱いする（`isLike` のような専用 AST ノードにする）必要がある。**R1 では関数として素直に足す案を提示するが、`= '1'` の見た目の悪さは実用上の欠点であり、レビューで判断を仰ぎたい**（§11 の論点 1）。

### 2.2 フラグ（R2 で確定）

#### 経緯: 「JS のフラグをそのまま通す」案の検討（R2）

R1 は `i`/`m`/`s` の allowlist を根拠薄く提示していた。レビューで **「JS の正規表現のオプションそのままではどうか」** という指摘があり、再検討した。

指摘の直感 —「JS が既に定義しているものを kSQL が再発明するな」— は**構文については完全に正しく、R1 も既にそうしている**（§3: ECMAScript 採用・POSIX ではない）。**フラグで話が変わるのは、JS の 6 つのフラグのうち半分が「何が一致するか」を決めていないため**である。

| フラグ | 性質 | 判断 |
|---|---|---|
| `i` `m` `s` | **意味**（何が一致するか） | **そのまま通す**。kSQL が再発明する理由がない |
| `u` | **意味だが、kSQL が既に決めてしまっている** | **常に強制**（§2.2.1） |
| `g` `y` | **`RegExp` オブジェクトの駆動方法**（`lastIndex` という状態） | **拒否**（§2.2.2） |
| `d` | マッチ結果オブジェクトの形 | **拒否**。kSQL はマッチオブジェクトを露出しない |
| `v` | **エンジン版依存**（ES2024・Node 20+/Chrome 112+/Safari 17+） | **拒否**（§3.1） |

**結論: `i` / `m` / `s` のみ受理し、`u` を常に付与する。** 未知のフラグ文字は実行時 `ArgumentError`。

結果として R1 と同じ allowlist になったが、**根拠が変わった**。「安全そうな 3 つを選んだ」のではなく、**「意味に関わるフラグはすべて通し、意味に関わらない 3 つ（`g`/`y`/`d`）と、エンジン版に依存する 1 つ（`v`）を落とした」**である。

#### 2.2.1 `u` は利用者が選べる options ではない（R2 で追加・実機実測）

kSQL には**既に文字単位の不整合がある**:

```
LENGTH('😀')  = 2          ← UTF-16 コードユニット
LEFT('😀', 1) = "\ud83d"   ← 壊れた孤立サロゲート
'😀' LIKE '_' = 一致       ← u フラグ＝1 コードポイント扱い
'ab'  LIKE '_' = 不一致    （対照・正常）
```

`matchLike`（`evalWhere.ts:370`）が `"u"` を付けているため `LIKE '_'` は**コードポイント**単位、`LENGTH`/`LEFT`/`SUBSTRING` は**コードユニット**単位。

**ここで利用者に `u` を選ばせると、1 つの SQL に 3 種類の文字単位が混在する。** 正規表現の隣人は `LIKE`（同じパターンマッチ）であり `LENGTH`/`LEFT`（位置・長さ演算）ではないため、**`u` 固定で `LIKE` に揃える**。

副作用として、`u` は一部の記法を `SyntaxError` にする（`{,3}` を非 `u` はリテラル扱いするが `u` はエラー）。**kSQL が厳しくなる方向であり、黙って別解釈するより良い**（B19 の `DATE_ADD` 不正単位と同じ判断）。

**`LEFT('😀',1)` が孤立サロゲートを返すのは B20 とは独立した既存欠陥**（§11 の論点 5）。

#### 2.2.2 `g` / `y` を拒否する理由（R2 で強化）

**これらは「オプション」ではなく「駆動方法」の指定であり、駆動するのは kSQL であって利用者ではない。**

`g`/`y` 付きの `RegExp` は `lastIndex` という**状態**を持つ。kSQL は行ごとに評価し、コンパイル結果を**キャッシュして使い回す**（§6.2）。したがって:

> **前の行の `lastIndex` が次の行へ漏れ、同じ式が行ごとに違う結果を返す。**

利用者の意図と無関係な壊れ方であり、`REGEXP_LIKE`/`REGEXP_SUBSTR` では `g` に意味もない。`REGEXP_REPLACE` の全件置換は kSQL 内部で行う（§2.3・§6.2）。

**トレードオフ**: `g` を拒否する結果、**「最初の 1 件だけ置換」が書けなくなる**。MySQL/Oracle は `occurrence` 引数で指定できる。v1 では実需が薄いと判断して落とすが、§10 に将来候補として記載する。

### 2.3 `REGEXP_REPLACE` は既定で全件置換

| 実装 | 既定 |
|---|---|
| MySQL 8.0 | **全件**（occurrence=0） |
| Oracle | **全件**（occurrence=0） |
| PostgreSQL | **最初の 1 件のみ**（`g` フラグで全件） |
| **kSQL（本仕様）** | **全件** |

多数派（MySQL/Oracle）に合わせる。加えて **kSQL 自身の `REPLACE` が全件置換である**ことを実機で確認済み（`REPLACE('a-b-c-d','-','/')` = `'a/b/c/d'`、`REPLACE('aaa','a','X')` = `'XXX'`）。同名の非正規表現版と既定が食い違う方が有害。

置換文字列の `$1`〜`$9`（後方参照）は **§4.3 でパターン側の後方参照 `\1` を禁止するのとは別**で、置換側の `$1` は**許可する**（ReDoS と無関係。抽出→再構成の実需が大きい）。

```sql
-- 電話番号を 03-1234-5678 形式へ再構成
REGEXP_REPLACE(電話, '^(0[0-9])([0-9]{4})([0-9]{4})$', '$1-$2-$3')
```

JS の `String.replace` は `$&`（一致全体）・`$$`（`$` 自身）・`` $` ``・`$'` も解釈する。**`` $` `` と `$'` は禁止する**（前後文字列の挿入は実需が無く、意図しない展開の温床）。実装は置換文字列を走査して拒否する。

## 3. 正規表現の方言は ECMAScript とする

**合わせるべき「標準」が存在しない。**

| 実装 | 方言 |
|---|---|
| MySQL 8.0 | ICU |
| Oracle | POSIX ERE + Perl 拡張 |
| PostgreSQL | POSIX ARE |
| SQL Server 2025 | 独自（長年 regex 自体が無く、SQLCLR 回避策が定番だった） |
| SQL 標準（SQL:2016 `LIKE_REGEX` 等） | XQuery 正規表現。**ほぼ誰も実装しなかった** |

主要 RDB 間ですら移植性が無い以上、**kSQL が ECMAScript 正規表現を採用しても準拠を外すことにはならない**。むしろ kSQL は JS 実行基盤（ブラウザ／Node）そのものなので、ECMAScript が唯一の自然な選択。

**言語リファレンスに「ECMAScript（JavaScript）の正規表現であり、POSIX ERE ではない」と明記する。** 具体的に効く差:

- POSIX の文字クラス `[[:alpha:]]` `[[:digit:]]` は**使えない**（`[a-zA-Z]` `\d` を使う）
- `\d` `\w` `\s` は ECMAScript の定義（`u` フラグ下では ASCII のみ。`\d` は全角数字に一致しない）

最後の点は kintone で実害が出やすいため、リファレンスに例示する。

### 3.1 方言はホストエンジン依存であり、kSQL は制御できない（R2 で新設）

**§2.2 の検討中に判明した、本仕様で最も重い残存リスク。**

パターンは `new RegExp(利用者の文字列)` として**実行時にホストエンジンが解釈する**。esbuild の `target` はこれを変換しない（`build.mjs` は `platform: "browser"` / `target: ["es2020"]`、`build-cli.mjs` / `build-mcp.mjs` は `target: ["node18"]` だが、**いずれもビルド時の話であり、パターン文字列の解釈は実行時のホスト任せ**）。

したがって:

| 実行経路 | 正規表現エンジン |
|---|---|
| プラグイン | **利用者のブラウザ**（Chrome / Safari / Firefox、任意のバージョン） |
| CLI / MCP | 利用者の Node（V8） |

具体的に効く例:

```sql
REGEXP_LIKE(x, '(?<=ab)c')   -- 後読み
  → Chrome (62+)       ✓
  → Node               ✓
  → Safari 16.4 未満   ✗ SyntaxError（後読み対応は 2023 年 3 月）
```

**同じ SQL・同じアプリで、利用者のブラウザによって結果が変わる。**

**これは v2.0.0 が major version を切ってまで潰した「LIKE のモード不一致」と同じ種類のバグである**（`docs/internal/ksql_where_rhs_field_and_like_mode_divergence_issue.md`）。kSQL の設計原則は「同じ SQL は実行モードによらず同じ結果」であり、本仕様はその原則に**構造的に反する最初の機能**になる。

#### なぜ受け入れるか

- **回避不能**。自前の正規表現エンジンを書く以外に手段がない（§4.3 で RE2 差し替えを却下したのと同じ理由: ブラウザで動かせない）
- **影響範囲が限定的**。差が出るのは新しい構文（後読み・`\p{...}`・名前付きグループ）を使った場合のみ。§4.3 の実需パターン 8 種はいずれも 20 年前から全エンジンで動く記法
- **fail-closed 側に倒れる**。非対応エンジンは黙って別解釈せず `SyntaxError` を投げ、§6.4 で `ArgumentError` に包まれる。**静かに違う結果を返すのではなく、明示的に落ちる**

#### したがって取る対策

1. **言語リファレンスに明記する**: 「正規表現の解釈は実行環境（ブラウザ / Node）に依存する。プラグインで動く記法が CLI で動かない、あるいはその逆があり得る。**新しい構文（後読み・Unicode プロパティ・名前付きグループ）は避け、基本的な記法に留めること**」
2. **制御できるフラグ側は絞る**（§2.2）。`v` を拒否する理由はこれ。フラグはエンジン版差が最も出やすく、かつ kSQL が唯一制御できる箇所
3. **§12 の受入条件に含めない**（CI は Node のみで走るため、ブラウザ差はテストで捕捉できない）。**文書での注意喚起が唯一の手段**であることを明示する

## 4. ReDoS 対策（本仕様の本体）

### 4.1 危険度の実測

Node で計測（1 行あたりの同期 CPU 時間）:

```
安全: LIKE 相当 '%緊急%' → /^.*緊急.*$/    入力長 40 →      0.1 ms
危険: /^(a+)+$/                            入力長 29 → 14,214.1 ms
危険: /^(\w+\s?)*$/                        入力長 27 →  4,738.8 ms

入力長 vs 時間 — /^(a+)+$/:
  22 → 27.3 ms   24 → 120.8 ms   26 → 438.2 ms   28 → 1,777.4 ms   （1 文字ごとに約 2 倍＝指数）
```

**29 文字は会社名・住所としてごく普通。** `^(\w+\s?)*$` は「前後の空白を許容する検証」としてネット上に無数にあるコピペ元がある形。

**しかもこれは 1 行あたり。** FULL_SCAN で 10,000 行なら 14 秒 × 10,000 = 約 39 時間。

### 4.2 kSQL のタイムアウトはこれを止められない

- `execute.ts:665` — 期限判定は **文と文の間**（`if (deadline !== null && Date.now() >= deadline)`）
- `execute.ts:910` — `setTimeout(() => reject(new BatchTimeoutError()), remainingMs)` は **Promise race**。同期的に回っている `RegExp.test` を中断できない

**プラグインはブラウザで動くため、kintone の画面ごとフリーズする。** CLI/MCP でも Ctrl-C 以外に止める手段が無い。

**これは kSQL にとって新種のリスクである。** 既存の `LIKE` も内部で `RegExp` を使うが（`evalWhere.ts:370`）、**機械生成なので安全**:

```ts
// evalWhere.ts:366 — 利用者の文字は全てエスケープされる
regexStr += ch.replace(/[.+*?^${}()|[\]\\]/g, "\\$&");
// 挿入されるのは % → ".*" と _ → "." のみ
```

利用者の文字が全てエスケープされ、挿入されるのが `.*` と `.` だけである以上、**入れ子量化子が構文的に生成され得ない**。利用者が正規表現を直接書けるようになると、この保証が消える。

### 4.3 対策: 安全部分集合（parse できるものを構文的に制限する）

#### 検討して却下した案

| 案 | 判定 |
|---|---|
| ステップ/時間制限（MySQL の `regexp_time_limit` 方式） | **不可**。MySQL は ICU がステップを数えられるから可能。**JS の `RegExp` は中断もステップ計数もできない** |
| RE2 等のバックトラックしないエンジンへ差し替え | **不可**。`re2` はネイティブ addon で**ブラウザプラグインで動かない**。純 JS 実装は巨大な依存で、kSQL の無依存方針に反する |
| Worker で隔離して kill | 1 関数群のためにプラグイン/CLI/MCP 全体のアーキテクチャを変える。費用が釣り合わない |
| `safe-regex` 等のライブラリで静的判定 | 依存追加。かつ偽陰性が知られており、fail-closed にならない |

#### 採用する規則

ReDoS（指数時間）は本質的に**量化子の入れ子または量化されたグループ内の曖昧な選択**を要する。したがって:

> **R-1. 量化子（`*` `+` `?` `{n}` `{n,}` `{n,m}`）が付いたグループの本体に、量化子または選択（`|`）を含んではならない。**
>
> **R-2. 後方参照（`\1`〜`\9`、`\k<name>`）を含んではならない。**

違反は **`ArgumentError`**（§4.4 で検証時期を規定）。

グループには丸括弧のすべて（捕獲 `(...)`、非捕獲 `(?:...)`、先読み `(?=...)` `(?!...)`、後読み `(?<=...)` `(?<!...)`、名前付き `(?<n>...)`）を含む。

#### 実需パターンが通るかの検証

| パターン | 判定 | 理由 |
|---|---|---|
| `^[0-9]{3}-[0-9]{4}$`（郵便番号） | ✅ | 量化子は文字クラスに付いている。グループ無し |
| `^\d{2,4}-\d{2,4}-\d{4}$`（電話） | ✅ | 同上 |
| `[^0-9]`（数字以外を除去） | ✅ | 量化子すら無い |
| `^[A-Z]{2}-[0-9]{6}$`（社内コード） | ✅ | |
| `^(0[0-9])([0-9]{4})([0-9]{4})$`（分解） | ✅ | **グループに量化子が付いていない**。中身の `{4}` は無関係 |
| `(株式会社\|有限会社)` | ✅ | 選択を含むが**グループが量化されていない** |
| `^(?=.*[A-Z])(?=.*[0-9]).*$`（複合条件） | ✅ | 先読みは量化されていない |
| `(abc)+` | ✅ | 量化されたグループだが本体に量化子も選択も無い＝曖昧性なし |
| `^(\w+\s?)*$` | ❌ | **量化されたグループの本体に `+` と `?`** ＝ 4.1 の実測対象 |
| `(a+)+` | ❌ | 同上 |
| `(a\|ab)+` | ❌ | 量化されたグループの本体に選択（重複する選択肢＝指数の典型） |

**実需パターンはすべて通る。**

#### 保守的すぎる（偽陽性）ケースと回避策

`(a|b)+` は選択肢が互いに素なので実際には安全だが、R-1 は拒否する。**判定を「選択肢が互いに素か」まで踏み込ませない**のは意図的で、その判定こそ誤りやすいため。回避策は自明:

```sql
-- ✗ 拒否される
REGEXP_LIKE(x, '^(a|b)+$')
-- ✓ 等価で通る
REGEXP_LIKE(x, '^[ab]+$')
```

リファレンスに「量化するグループは単純に保ち、選択は文字クラスへ」と明記する。

#### 多項式時間（`.*.*` 等）は許容する

`\d+\d+` や `.*a.*b.*` は多項式時間で、指数ではない。65,535 文字の `MULTI_LINE_TEXT` に対しては秒単位になり得るが:

- **`LIKE '%a%b%c%'` が既に `^.*a.*b.*c.*$` を生成して出荷済み**（`evalWhere.ts:361`）。同じ形を今さら禁止するのは筋が通らない
- R-1 で禁止すると `.*` の連続すら書けなくなり、実用に耐えない

**v1 は指数のみを塞ぎ、多項式は既存 `LIKE` と同じ扱い（許容）とする。** この線引きをリファレンスに明記する。

### 4.4 検証の時期: 実行時（B19 `DATE_ADD` と同じ判断）

パターン引数は**リテラルとは限らない**。`REGEXP_LIKE(x, パターン列)` や `REGEXP_LIKE(x, CONCAT('^', 接頭辞, '$'))` が書ける（B19 で `DATE_ADD(x, 1, CONCAT('MON','TH'))` が動くことを実機確認済み）。

したがって **R-1/R-2 の検証は実行時**とし、parse 時には行わない。B19 の `DATE_ADD` の単位検証と同じ判断で、理由も同じ:「parse 時検証にすると、リテラルは parse 時・式は実行時という**二重仕様**になる」。

**ただし本件は `DATE_ADD` と一点だけ事情が違う**: 不正なパターンは 1 行目の評価で throw するため、**10,000 件を fetch した後に失敗する**。無駄ではあるが read-only であり、害はない。**リテラルパターンに限り parse 時にも同じ関数を呼んで早期に落とす案**は、実装が 1 つの関数で両所から呼ぶ形なら「二重仕様」にはならない。**§11 の論点 2 としてレビューで判断を仰ぐ。**

### 4.5.0 代替不能性の測り方（R2 で追加・実機実測）

**B19 で `RIGHT` の代替不能性を実機で確かめたのと同じ厳密さで測る。** パターンによって「原理的に不可能」と「書けるが破綻する」が分かれ、**看板に据えるべきは前者**である。

#### 原理的に不可能（`REGEXP_*` でしか書けない）

| 用途 | なぜ不可能か（実機実測） |
|---|---|
| **書式検証** | `LIKE '___-____'` は**桁数しか見られない**。実機: `103-6027` に一致するが **`abc-defg` にも `１０３-６０２７` にも一致してしまう**。`_` は「任意の 1 文字」であり数字性を検査できない |
| **数字以外を除去** `[^0-9]` | `REPLACE` はリテラル置換。**「数字以外の全て」を列挙できない**（何が入っているか事前に分からない） |
| **文字範囲の検出** `[ｦ-ﾟ]`（半角カナ） | 同上。範囲を列挙できない |
| **連続空白を 1 つへ** `[ 　]+` → `' '` | `REPLACE` は「2 個を 1 個」なら書けるが、**個数が不定**だと書けない |

#### 書けるが実務では破綻する（`（株）` → `株式会社`）

**R2 の初稿はここで測り方を誤った。** 「`REPLACE` の入れ子で書ける」として簡潔さの改善に格下げしたが、**検証が `（株）` と `(株)` の一貫した 2 形しか見ておらず、混在形を試していなかった**。実データには括弧の全角・半角が混ざった形がある。

**実機実測（`REPLACE` 2 段）**:

```
（株）A → 株式会社A   ✓
(株)B  → 株式会社B   ✓
（株)C → （株)C      ✗ 変換されない（全角開き + 半角閉じ）
(株）D → (株）D      ✗ 変換されない（半角開き + 全角閉じ）
```

**混在形はエラーにならず黙って素通りする。** 正規化のつもりで実行して 4 通りのうち 2 通りだけ直る＝**静かに壊れる**側の失敗であり、実務上これは「書ける」とは言い難い。

**正規表現の文字クラスは積として効く**。`[（(]株[）)]` は **2 開き × 2 閉じ = 4 通り**を 1 パターンで覆う（実測）:

```
[（(]株[）)]|㈱  →  （株）A / (株)B / （株)C / (株）D / ㈱E / F（株) / G㈱
                    すべて 株式会社 へ変換される（前株・後株・混在・合字とも）
```

**必要な段数の比較（実測）**:

| 対応範囲 | `REPLACE` の入れ子 | `REGEXP_REPLACE` |
|---|---|---|
| `株` の括弧 4 通り | 4 段 | **1 回** |
| ＋ 合字 `㈱` | 5 段 | 1 回（同じパターン） |
| ＋ `有` の括弧 4 通り＋合字 `㈲` | **10 段** | **2 回** |

**`REPLACE` は「括弧の開き × 閉じ × 会社種」の積を人手で列挙する必要があり、正規表現は会社種の数だけで済む。** 段数が積で増えるのに対し、パターン数は線形。**列挙漏れが静かな非変換になる**ため、異体字が増えるほど誤りが入り込む。

**したがって §4.5.1 の `（株）` 例は「実務上は代替困難」として提示してよい。** ただし「4 段書けば `REPLACE` でも可能」であることは事実なので、**`RIGHT`（B19・実機で構文的に不可能を確認）のような「原理的に不可能」とは区別して記載する。**

#### 看板レシピの題材（§8）

**「書式検証 → 隔離 → 正規化」とする。** 検証部分（`REGEXP_LIKE`）が原理的に不可能な側（§4.5.0 の 1 つ目の表）であり、B12（`ON ERROR SKIP`）・B16（`GROUP_CONCAT`）・B11（`UPDATE … FROM`）と繋がって弧が閉じる。**`（株）` の正規化はその中の「正規化」段の題材として使う**（混在形が 1 パターンで拾えることを示せるため説明力が高い）。

### 4.5.1 置換（`REGEXP_REPLACE`）

| 用途 | パターン | 置換 | 例 |
|---|---|---|---|
| **（株）→ 株式会社**<br>（**括弧 4 通り**・合字・前株・後株を 1 パターンで） | `[（(]株[）)]｜㈱` | `株式会社` | `（株）A`→`株式会社A`／`(株)B`→`株式会社B`<br>**`（株)C`→`株式会社C`／`(株）D`→`株式会社D`**（混在）<br>`㈱E`→`株式会社E`／`F（株)`→`F株式会社`（後株） |
| （有）→ 有限会社 | `[（(]有[）)]｜㈲` | `有限会社` | `（有）山田商店` → `有限会社山田商店` |
| 電話のハイフン等を除去 | `[^0-9]` | （空） | `03-1234-5678` → `0312345678` |
| ハイフンの表記ゆれを統一 | `[‐‑‒–—―－ー]` | `-` | `03ー1234－5678` → `03-1234-5678` |
| 空白除去（全角・半角） | `[\s　]` | （空） | `東京都 千代田区　1-1` → `東京都千代田区1-1` |
| 連続空白を 1 つへ | `[ 　]+` | `' '` | `山田　　太郎` → `山田 太郎` |
| 郵便記号を除去 | `^〒\s*` | （空） | `〒 103-6027` → `103-6027` |
| 携帯番号を再構成 | `^(0[789]0)(\d{4})(\d{4})$` | `$1-$2-$3` | `09012345678` → `090-1234-5678` |
| 東京 23 区の固定を再構成 | `^(03)(\d{4})(\d{4})$` | `$1-$2-$3` | `0312345678` → `03-1234-5678` |

**`（株）` の 1 パターンが前株・後株の両方を正しく処理する**のが要点。位置を指定せずトークンだけを置換するため、`^`/`$` を付けないこと。`㈱`（機種依存文字）も同じ文字クラスの選択肢に入れて 1 回で拾う。

> 表中の `｜` は Markdown の表を壊さないための表記で、**実際のパターンでは半角の `|`** を使う。

#### 電話番号の再構成は市外局番が可変長なので難しい（R2 で追加・実測）

**R2 の初稿で `^(0\d{1,3})(\d{2,4})(\d{4})$` → `$1-$2-$3` を例に挙げたが、検証したところ間違っていた**:

```
'0312345678' → '0312-34-5678'    ← 期待は '03-1234-5678'
```

`0\d{1,3}` が貪欲に `0312` を取るため。**日本の市外局番は 1〜4 桁で、桁数だけからは一意に決まらない**（`03` = 東京、`0312` は存在しない、しかし `0166` = 旭川は 4 桁）。正規表現だけでは解けない。

**したがってリファレンスには「市外局番が確定している場合のみ」の形（`^(03)(\d{4})(\d{4})$`・`^(0[789]0)(\d{4})(\d{4})$`）を載せ、汎用の再構成は載せない。**

**この誤りは「レシピの公開 SQL は実行して確かめる」（B18 の教訓）が仕様の例にも当てはまることを示している。** 本仕様の全パターンは実際に動かして確認した。

### 4.5.2 チェック（`REGEXP_LIKE`）

| 用途 | パターン | 一致する | 一致しない |
|---|---|---|---|
| 郵便番号 | `^\d{3}-\d{4}$` | `103-6027` | `1036027` / **`１０３-６０２７`** |
| 電話番号 | `^0\d{1,4}-\d{1,4}-\d{4}$` | `03-1234-5678` / `090-1234-5678` | `1234` |
| メール | `^[^@\s]+@[^@\s]+\.[^@\s]+$` | `a@b.co.jp` | `a@b` |
| 全角カタカナのみ | `^[ァ-ヶー]+$` | `サイボウズ` | `ｻｲﾎﾞｳｽﾞ` / `さいぼうず` |
| ひらがなのみ | `^[ぁ-んー]+$` | `やまだ` | `ヤマダ` |
| 半角英数のみ | `^[0-9A-Za-z]+$` | `ABC123` | `ＡＢＣ` |
| 社内コード | `^[A-Z]{2}-\d{6}$` | `AB-123456` | `ab-123456` |
| **半角カナを含む**（kintone で嫌われる） | `[ｦ-ﾟ]` | `ｻｲﾎﾞｳｽﾞ` | `サイボウズ` |
| **絵文字を含む**（`u` フラグが要る） | `[\u{1F300}-\u{1FAFF}]` | `進捗😀` | `進捗` |
| 数字以外を含む（検出） | `[^0-9]` | `03-1234` | `031234` |
| 英大文字と数字を両方含む | `^(?=.*[A-Z])(?=.*[0-9]).+$` | `AB12` | `abcd` |

**`\d` が全角数字に一致しない（§3）ことは、検証用途ではむしろ利点**: `^\d{3}-\d{4}$` が `１０３-６０２７` を弾き、全角混入を検出できる。**リファレンスに「仕様であり利点でもある」と明記する。**

`[\u{1F300}-\u{1FAFF}]` は **`u` フラグ下でのみ有効**（§2.2.1 で `u` を強制する理由の 1 つ）。

### 4.5.3 正規表現では解けないもの（R2 で追加）

| 用途 | なぜ無理か |
|---|---|
| **全角英数 → 半角**（`ＡＢＣ` → `ABC`） | 正規表現は**文字の写像ができない**。1 対 1 変換には Oracle の `TRANSLATE` 相当が要る。**kSQL には無く、MySQL にも無い**（`CONVERT` は文字コード変換で別物） |
| **半角カナ → 全角カナ**（`ｻｲﾎﾞｳｽﾞ` → `サイボウズ`） | 同上。加えて濁点の合成（`ﾎﾞ` = 2 文字 → `ボ` = 1 文字）が要り、写像ですら足りない |

**`REGEXP_LIKE` で「検出」はできるが「変換」はできない**、という非対称をリファレンスに明記する。検出して `#err` へ隔離する（B12）か、`GROUP_CONCAT` で一覧化する（B16）のが kSQL での現実的な運用。

**`TRANSLATE` 相当の追加は §10 の将来候補に記載する。**

### 4.5.4 判定器プロトタイプで見つかった実装の落とし穴（R2 で追加）

§4.3 の R-1/R-2 を実装して全パターンを流したところ、**プロトタイプ自身に 2 件のバグが出た**。codex の実装で同じ罠を踏まないよう記録する:

1. **エスケープの直後の量化子を登録し損ねる**。`\w` を `i += 2` で読み飛ばして `continue` すると、続く `+` が「このグループは量化子を含む」の記録から漏れる。結果 **`^(\w+\s?)*$` が安全と誤判定される**（§4.1 の 14 秒の実測対象そのもの）。**エスケープ・文字クラス・グループ閉じ・通常文字のすべてで、直後の量化子を同じ経路で処理すること。**
2. **`\u{...}` を 1 つのエスケープとして読む**必要がある。`\u` の 2 文字だけ進めると `{1F300}` が量化子 `{...}` と誤解される。

**受入条件に `^(\w+\s?)*$` と `^(\d+)*$` の両方を入れる**（後者も同じ根本原因で漏れる）。

## 5. 実行モードと DML の扱い（実機で確認済み）

### 5.1 常に FULL_SCAN

kintone のクエリ API に正規表現は無いため、押し下げは原理的に不可能。`REGEXP_*` を WHERE に含む SELECT は FULL_SCAN。**v2.0.0 で `LIKE` を JS 評価へ統一した判断と同じ**で、新しい概念は持ち込まない。

安全リーフのプレフィルタ（`extractSafePushdownLeaves`）は従来どおり効く。B19 の実機確認で、`WHERE LEFT(郵便番号,3)='100' AND 顧客No > 200` が `pushdown candidate: 顧客No > 200` を維持することを確認済み。`REGEXP_*` でも同じ。

### 5.2 親 DML の WHERE では**既存機構が自動的に拒否する**（新規則不要）

当初「`LIKE` が親 DML で拒否されるのと同じ理由で `REGEXP_LIKE` も拒否すべき」と考えたが、**実機で確認したところ新しい規則は要らない**:

```
UPDATE APP4148 SET 建物名 = 'x' WHERE LEFT(郵便番号, 3) = '100'
→ KintoneQueryError: WHERE 句の関数（LEFT）は kintone クエリに変換できません
```

**親 DML の WHERE は文字列関数を既に一律拒否している**（`whereToKintone.ts` に `STRING_FUNC` のケースが無く fail-closed）。`REGEXP_*` は `STRING_FUNC` として実装されるため、この機構にそのまま乗る。**追加のガードを書くと二重になる。**

受入条件には「`UPDATE ... WHERE REGEXP_LIKE(...)` が `KintoneQueryError` になること」を**既存機構の回帰テストとして**入れる。

### 5.3 `UPDATE SET` では使えない（重要な制限）

```
UPDATE APP4148 SET 建物名 = UPPER(建物名) WHERE 顧客No IN (1)
→ ParseError: SET の値にはリテラル・算術式を指定してください（フィールド参照のみは不可）
```

**kSQL の `UPDATE SET` は文字列関数を直接受け付けない。** つまり `REGEXP_REPLACE` の最大の用途である「その場での一括正規化」は**直接は書けない**。

#### R2 初稿の誤りを訂正（`* 1` の「罠」は存在しない）

**R2 の初稿は「SET は算術式を受けるため `* 1` を付けると通ってしまい、静かに数値化される罠がある」と記載していたが、誤りだった。** EXPLAIN が計画を表示するのを見て、**実行せずに書いた**のが原因:

```
EXPLAIN UPDATE APP4148 SET 建物名 = LENGTH(建物名) * 1 WHERE 顧客No IN (1)
→ ok。 set type: 算術 SET（現在値を取得して計算）      ← 通るように見える

実行   → DmlConvertError: UPDATE SET の算術式では文字列関数はサポートされていません
```

**実際は `resolveArithOperand`（`dmlToKintone.ts:407`）が fail-closed で拒否する。罠は存在しない。**

**これは §11 論点 4（EXPLAIN が実行不能な計画を `ok` で表示する）の 2 例目**でもある。

#### `CASE WHEN` で包むと書ける（B21 として起票）

```
UPDATE APP4148 SET 建物名 = CASE WHEN 顧客No IN (1) THEN CONCAT(建物名, '★') ELSE 建物名 END
WHERE 顧客No IN (1)
→ ok: updatedCount = 1（実書き込みで確認・文字列として正しく書かれ、検証後に復元済み）
```

**同じ式が `CASE WHEN` の中では書けるのに、直接書くと `ParseError` になる。** 評価機構は既に完成しており（`dmlToKintone.ts:539` が `evalStringFunc` を呼ぶ）、parser の accept list から `STRING_FUNC` が漏れているだけに見える。

**[B21](ksql_update_set_string_func_issue.md) として独立に起票した。** B20 とは独立の既存欠陥で、`UPPER`/`REPLACE`/`CONCAT` および B19 の `LPAD`/`LEFT`/`RIGHT` 等**既存の全文字列関数に効く**ため、**B20 より優先度が高い**（台帳の優先ルール「正しさ/安全性 > 機能」）。

**ただし B21 が入っても B20 のレシピは 1 文にならない**: 親 DML の `WHERE` は文字列関数を一律拒否するため（§5.2）、対象の絞り込みができない。**B20 の書き戻しは B21 の有無にかかわらず §5.4 の temp + `UPDATE … FROM` を使う。**

**リファレンスには「`REGEXP_REPLACE` は `UPDATE SET` で直接は使えない（B21 で解消予定）。書き戻しは §5.4 のレシピを使う」と記載する。**

### 5.4 書き戻しは temp テーブル + `UPDATE … FROM`（実機で検証済み）

§5.3 の制限があっても書き戻し経路は存在する。B11/B12 の資産に素直に乗る:

```sql
CREATE TEMP TABLE #norm AS
  SELECT $id AS 対象id, REGEXP_REPLACE(電話番号, '[^0-9]', '') AS 正規化
  FROM APP100 WHERE REGEXP_LIKE(電話番号, '[^0-9-]') = '1';
UPDATE APP100 SET 電話番号 = n.正規化 FROM #norm AS n WHERE APP100.$id = n.対象id;
```

**実機で同型（`REPLACE` 版）を `VALIDATE ONLY` まで通して確認済み**: `validatedRows: 1, validRows: 1, invalidRows: 0`。temp テーブル側は文字列のまま保持される（`REPLACE(REPLACE(郵便番号,'-',''),' ','')` = `"1036027"`）。

**したがって `REGEXP_REPLACE` は表示専用ではない。** レシピ集（`ksql_batch_recipes.md`）に R7 として追加する（§8）。

**注意**: `UPDATE … FROM` の結合キーに `RECORD_NUMBER` 型は使えない（実機: `ArgumentError: UPDATE ... FROM does not support target join field type RECORD_NUMBER (顧客No)`）。`$id` 結合を使う。レシピにも明記する。

**`core/regexSafety.ts` を新設する理由**: B19 で `core/scalarCompare.ts` を leaf として使った前例と同じ。`evalFunc.ts` は最下層（`process.ts → evalFunc`、`evalWhere.ts → evalFunc`）なので、`evalFunc` から `evalWhere` の何かを import すると循環する。安全判定は `evalFunc` からも（将来 parser からも）呼べる leaf に置く。

### 6.2 コンパイルキャッシュ

`evalWhere.ts:345` の `likeRegexCache` と同型:

```ts
const regexCache = new Map<string, RegExp>();   // key = `${pattern} ${flags}`
const REGEX_CACHE_MAX = 200;
```

**キーはパターンとフラグの組**にすること。パターンだけをキーにすると `'i'` 付きと無しが混ざる。

**`g` フラグを受理しない理由がここにも効く**: `g` 付き `RegExp` は `lastIndex` を持ち、**キャッシュで使い回すと前回の位置から探し始める**。行ごとに結果が変わる典型的なバグになる。`REGEXP_REPLACE` の全件置換は `String.replaceAll` 相当を使うか、置換時のみ `g` 付きの別インスタンスを生成する（キャッシュしない、あるいは `lastIndex` を毎回 0 に戻す）。**実装契約として明記する。**

### 6.3 arity

B19 の `assertArity` を再利用。

| 関数 | min | max |
|---|---|---|
| `REGEXP_LIKE` | 2 | 3 |
| `REGEXP_REPLACE` | 3 | 4 |
| `REGEXP_SUBSTR` | 2 | 3 |

### 6.4 不正な正規表現そのもの

`new RegExp('[')` は `SyntaxError` を投げる。**`ArgumentError` へ包み直す**（`SyntaxError` が生で MCP まで漏れると `toErrorPayload`（`mcp/tools.ts:324`）の `/^([A-Za-z]+Error):/` に一致せず `code: "Error"` になる）。

### 6.5 空文字の扱い

B19 §3.2 に倣い関数ごとに規定する。

| 式 | 結果 | 理由 |
|---|---|---|
| `REGEXP_LIKE('', '^$')` | `'1'` | 空文字は正規表現の対象として正当 |
| `REGEXP_LIKE('', 'a')` | `'0'` | |
| `REGEXP_LIKE(x, '')` | `'1'` | 空パターンは全てに一致（JS の `//` と同じ） |
| `REGEXP_REPLACE('', 'a', 'b')` | `''` | |
| `REGEXP_SUBSTR(x, 'a')`（非一致） | `''` | kSQL の NULL 相当は空文字 |

**`REGEXP_SUBSTR` の非一致が空文字である結果、「一致したが空文字」と「非一致」が区別できない。** MySQL/Oracle は非一致に NULL を返すため区別できる。kSQL には NULL が無いため原理的に不可避。**リファレンスに明記し、区別が要る場合は `REGEXP_LIKE` と併用するよう案内する。**

## 7. 予約語と SemVer

`REGEXP_LIKE` / `REGEXP_REPLACE` / `REGEXP_SUBSTR` は**新しい予約語**。同名フィールドはバッククォートで参照する。

**`REGEXP` / `RLIKE` 演算子は追加しない。** MySQL は `expr REGEXP pat`、PostgreSQL は `~` を持つが、kSQL は既に `LIKE`（JS 評価）と `KLIKE`（kintone ネイティブ検索）の 2 本立てで、3 本目の一致演算子は混乱を増やすだけ。関数のみに限定する。

### 7.1 経緯: JS 由来の命名（`TEST` など）を採らない根拠（R2 で追加）

R2 のレビューで **「`TEST` など JS の命名ではどうか」** という案が出た。`RegExp.prototype.test()` に倣う発想で、§2.2 の「JS が定義済みのものを再発明するな」と同じ直感に基づく。

**採らない。** 根拠を重い順に:

| # | 根拠 |
|---|---|
| 1 | **予約語として最悪の部類**。`TEST` は kintone のフィールドコードとして**極めてありそう**（テスト用フィールド）。B19 で新規予約語が既存クエリを壊すことを実証済み（`SELECT LEAST FROM APP100` → `ParseError`）。`REGEXP_LIKE` がフィールド名である可能性はほぼ無い。**8 語を追加した B19 の中で最も危険だった `LEAST` より、`TEST` はさらに危険** |
| 2 | **`MATCH` は SQL 予約語**。SQL 標準の `MATCH`（外部キー）・MySQL の `MATCH … AGAINST`（全文検索）と衝突する。kintone ネイティブ検索（`KLIKE`）を将来伸ばす際に名前を失う |
| 3 | **kSQL は SQL 方言であり、全関数が SQL 名**。`UPPER`≠`toUpperCase`、`LENGTH`≠`length`、`SUBSTRING`≠`slice`、`CONCAT`≠`+`。ここだけ JS 名にすると一貫性が崩れる |
| 4 | **B19 の選定方針と矛盾**。B19 は「関数名は一般的なもので」という方針で `LEN`/`NVL`/`GETDATE` のような別名を却下した。`REGEXP_LIKE` は MySQL / Oracle / PostgreSQL / SQL Server 2025 の**共通名**（§9） |
| 5 | **§11 論点 1（`= '1'` の見た目）を解決しない**。`TEST(x, 'p')` の戻り値も `string` であり、改名で真偽型は生えない |

**この案の直感が正しく効くのは構文の側**であり、そこは §3 で既に採用している（ECMAScript・POSIX ではない）。**命名はホスト言語ではなく利用者の言語（SQL）に合わせる**、というのが本仕様の立場。

**SemVer は minor**（v2.18.0 想定）。厳密には予約語追加で構文互換性リスクがあるが、`KLIKE`（v2.8.0）・`GROUP_CONCAT`（v2.15.0）・B19 の 8 語（v2.17.0）と同じ方針。B19 でバッククォート回避が全経路（SELECT/WHERE/GROUP BY/ORDER BY）で機能することを実機確認済み。

| | チェック | 置換 | 抽出 | 位置 | 個数 | 方言 | ReDoS 対策 |
|---|---|---|---|---|---|---|---|
| MySQL 8.0 | `REGEXP_LIKE`／`REGEXP`・`RLIKE` 演算子 | `REGEXP_REPLACE` | `REGEXP_SUBSTR` | `REGEXP_INSTR` | **なし** | ICU | **`regexp_time_limit` / `regexp_stack_limit`** |

2. **PostgreSQL の `regexp_replace` だけが既定で初回のみ。** kSQL は多数派＋自身の `REPLACE` に合わせて全件（§2.3）。

## 11. レビューで判断を仰ぎたい論点

### 論点 1: `REGEXP_LIKE(...) = '1'` の見た目

主要 RDB はすべて `WHERE REGEXP_LIKE(x, p)` と裸で書ける。kSQL は関数戻り値が `string` のため `= '1'` が要る（§2.1）。

- **案 A（本仕様）**: 関数として素直に足す。`= '1'` を許容し、リファレンスで案内する。実装が小さく、`SELECT` 列としても使える
- **案 B**: WHERE 述語として専用 AST ノードにする（`isLike` と同型）。裸で書けるが、`SELECT REGEXP_LIKE(...) AS 判定` が書けなくなるか、両方実装して二重になる

**私は案 A を推す**が、`= '1'` は利用者の学習コストとして無視できないため、レビューの判断を仰ぎたい。

### 論点 2: 安全部分集合の検証を parse 時にも行うか

§4.4 のとおり実行時が必須。加えてリテラルパターンに限り parse 時にも**同じ関数を呼ぶ**案がある。

- **利点**: `ksql_validate` で捕捉できる（「`ksql_validate` は実行可否を保証しない」という B18 の教訓に対し、数少ない改善機会）。10,000 件 fetch 前に落ちる
- **欠点**: B19 の `DATE_ADD` は「二重仕様になる」として parse 時検証を却下した。同じ関数を 2 箇所から呼ぶだけなら二重仕様ではない、という整理が成り立つかどうか

### 論点 3: `UPDATE SET` の文字列関数 → **B21 として起票済み（R2 で解決）**

§5.3 で判明した件は **[B21](ksql_update_set_string_func_issue.md) として独立に起票した**。

**R2 で内容が変わった**: 初稿の「`* 1` を付けると通ってしまい静かに数値化される罠」は**誤り**で、実際は `DmlConvertError` で fail-closed に拒否される（§5.3）。真の問題は **「同じ式が `CASE WHEN` の中では書けるのに直接書くと `ParseError`」という一貫性の欠如**で、評価機構は既に完成している（parser の accept list からの漏れ）。

**B21 は本仕様とは別 PR で先行させる。** 根拠:

- **台帳の優先ルール**「正しさ/安全性 > 機能 > 性能」。B21 = 一貫性（正しさ寄り）、B20 = 機能
- **B20 を待たずに価値が出る**。`UPPER`/`REPLACE`/`SUBSTRING`/`CONCAT` および B19 で追加した `LPAD`/`TRUNCATE`/`LEFT`/`RIGHT` **すべてに効く**
- **差分が小さいと見込まれる**（書き込み経路は対応済み）
- B20 は ReDoS・ホスト依存性（§3.1）という**重い未決論点を抱えており、着手までに時間がかかる**

### 論点 4: EXPLAIN が実行不能な計画を表示する（B20 の対象外）

§5.2 の調査中に発見:

```
EXPLAIN UPDATE APP4148 SET 建物名 = 'x' WHERE LEFT(郵便番号, 3) = '100'
→ ok。 kintone query: (JS 評価が必要なため kintone クエリに変換不可)
        api: GET /k/v1/records.json → PUT /k/v1/records.json
実行     → KintoneQueryError（必ず失敗する）
```

**EXPLAIN が「GET して PUT する」計画を表示するが、実行すると必ず失敗する。** memory にある B12 レシピの発見（`ksql_validate` が `ok` を返すのに実行時 `KintoneQueryError`）と同型で、別課題として起票候補。

### 論点 5: `LEFT` / `SUBSTRING` がサロゲートペアを割る（B20 の対象外・R2 で追加）

§2.2.1 の調査中に発見:

```
LENGTH('😀')  = 2
LEFT('😀', 1) = "\ud83d"   ← 孤立サロゲート。文字として壊れている
'😀' LIKE '_' = 一致        ← LIKE だけコードポイント単位
```

**B19 は `LEFT`/`RIGHT`/`SUBSTRING` の文字単位が相互に一致することは受入条件で確認した**（`process.test.ts` の「B19 の文字数単位は LENGTH / SUBSTRING と一致する」で `LEFT(s,2)` = `SUBSTRING(s,1,2)` = `😀`）**が、サロゲートを割ること自体の是非は見ていない**。UTF-16 計数は B12-A で kintone 実測に基づき採用した方針（`minLength`/`maxLength` は UTF-16 code units）と整合しており、**長さ検証としては正しい**。壊れるのは**切り出し**（`LEFT`/`RIGHT`/`SUBSTRING`）のみ。

B20 とは独立した既存欠陥として **B22 起票候補**。判断が要る点:

- kintone 自身が `maxLength` を UTF-16 で数える以上、`LENGTH` を変えるべきではない
- `LEFT`/`RIGHT`/`SUBSTRING` だけをコードポイント単位にすると `LENGTH` と食い違う（`LENGTH('😀')=2` なのに `LEFT('😀',2)` が `'😀'` 全体を返す等）
- 何もしないと孤立サロゲートが `#err` や書き込み値へ流れ得る
