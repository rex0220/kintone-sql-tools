# 本文（送付版）

## 【返信】K-6 範囲トークン — 今回は見送ります。代わりに「半開区間」をお使いください

バー連携まで同日に実装いただき、ありがとうございます。
**範囲トークンは見送らせてください。**ただし、**ご相談の痛みの半分は今日なくせます。**

## 1. 先に、いま効く話 — 上端を「終了日の翌日」にしてください

```sql
WHERE 受注予定日 >= @period_from AND 受注予定日 < @period_to_next
```

**`<= 終了日` をやめて `< 終了日の翌日` にすると、DATE でも DATETIME でも同じ書き方になります。**
`_to_end`（RFC3339）の使い分けは不要です。実データで測りました:

```
>= '2026-07-14' AND <= '2026-07-14'    → 0 件   （両端とも 0:00 なので空区間）
>= '2026-07-14' AND <  '2026-07-15'    → 2 件   （正しい）
```

**この形は kintone のタイムゾーン設定を知らなくても正しくなります。**両端の日付リテラルを
kintone が同じ規則で解決するため、区間が kintone 自身の「1 日」と一致するからです。
RFC3339 の `T23:59:59Z` は kintone 側の TZ 解決に依存するので、**半開区間のほうが安全**です
（v3.39.0 で当方のリファレンスに書いた RFC3339 の案内も、この形へ改める予定です）。

## 2. 見送りの理由 — 前提が 1 つ違っていて、費用が想定より大きくなります

**「既存の相対日付関数の展開機構にそのまま乗る」という点です。**
実は **kSQL に展開機構はありません。**

```
kintone query: 受注予定日 = THIS_MONTH()      ← 展開せず、そのまま kintone へ渡している
```

`= THIS_MONTH()` を「月の範囲内」と解釈しているのは **kintone 側**です。
kintone に範囲関数は無いので、`DATE_RANGE(a, b)` は**エンジンが述語の形そのものを
書き換える**（`= @p` → `>= a AND < b'`）ことになります。B111 は「値の差し替え」でしたが、
これは **kSQL 側で初めての述語書き換え**になります。

さらに、**変数の解決はフィールド型を読むより前**に走ります
（実行計画にも `variables/subqueries resolved -> metadata resolved` と出ます）。
**ご指摘のとおり型を知っているのはエンジンだけ**なのですが、**その型を知る前の段階で
差し替えている**ため、順序から作り直す必要があります。

**そのうえで、§1 の半開区間で correctness の問題は消えます。**
残るのは「書き方が 2 系統」という説明上の問題で、費用と釣り合わないと判断しました。

## 3. 再起票の条件

**閉じたまま忘れることはしません。**次のどちらかが出たら再検討します。

- リリース後に「**2 系統の書き方が実際の混乱を生んだ**」という報告
- 任意区間を単一変数で扱いたい**別の実需**

設計メモ（展開形は DATE=`>= a AND <= b` / DATETIME=`>= a AND < b+1日`、配置は
`列 = @変数` の比較 leaf のみ、引数不正は API 前に fail-closed）は残してあるので、
そのときは設計から始められます。
