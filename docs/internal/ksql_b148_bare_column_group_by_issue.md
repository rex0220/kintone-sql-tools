## 1. 実測（v3.56.3・APP4228）

```sql
SELECT 製品名, 個数, 日付, SUM(個数) AS 合計, COUNT(*) AS 件数
FROM APP4228 GROUP BY 製品名
```

| 製品名 | 個数 | 日付 | 合計 | 件数 |
|---|---|---|---|---|
| 食パン | **646** | **2025-08-05** | 23429 | **220** |
| 牛乳 | **706** | **2025-08-05** | 29351 | **200** |

**`個数` と `日付` は集計もキーもされていない。** それでも値が返る。

**その値は、グループの先頭レコードのもの**である。

```sql
SELECT 製品名, 個数, 日付 FROM APP4228 LIMIT 3
  → 食パン / 646 / 2025-08-05
    牛乳   / 706 / 2025-08-05
```

**完全に一致する。**

- **エラーも警告も出ない**（`warnings: []`）
- **220 件のうち 1 件の `個数` が「食パンの個数」として出ている**
- **式でも同じ**＝`個数 * 2 AS 倍` は**先頭行の 2 倍**を返す（1292 = 646 × 2）

### 1.1 **`GROUP BY` 無しでも起きる（いちばん危ない）**

```sql
SELECT 製品名, 個数, SUM(個数) AS 合計, COUNT(*) AS 件数 FROM APP4228
  → 食パン / 646 / 85438 / 件数 1000     （1 行）
```

**1000 件が 1 行に畳まれ、`製品名` と `個数` は先頭レコードの値。**
**`GROUP BY` を書いていないので、集計したつもりが無い人ほど踏む。**
**見た目が明細行と区別が付かない。**

### 1.2 `HAVING` でも通る

```sql
SELECT 製品名, SUM(個数) AS 合計 FROM APP4228 GROUP BY 製品名 HAVING 個数 > 0
  → エラーにならず 3 行返る
```

## 2. なぜ重いか

**踏む形が普通に書かれる。**

```sql
SELECT 製品名, 個数, SUM(個数) AS 合計 FROM APP4228 GROUP BY 製品名
```

**「製品・数量・合計」と読める。** `個数` を意味のある値として受け取るのが自然だが、
**実際は任意の 1 件の値**である。

**集計し忘れは最も普通の書き間違い**で、**標準 SQL も MySQL の既定（`ONLY_FULL_GROUP_BY`）も
これをエラーにする**のは、まさにそのためである。

**[B147](ksql_b147_aggregate_alias_shadows_key_input_issue.md) より踏みやすい**＝
B147 は別名の衝突という珍しい条件が要るが、**本件は「集計を書き忘れる」だけ**で起きる。

| **実装** | **ordinary `GROUP BY` にはガードが無い**が、**拡張 grouping には B65 の依存検査が既にある**（[レビュー 1 §6](ksql_b148_codex_review_1.md) の実測で判明。**起票時の「検査は存在しない」は誤り**） |
| **既存テスト** | ordinary については**意図として固定しているものは見つからなかった**（拡張 grouping 側にはある） |

**【2026-08-06 追記】この節は起票時の初期観測である。**
**その後の実測で、同じ規則が拡張 grouping の経路には既にあると判明した**（[レビュー 1 §6](ksql_b148_codex_review_1.md)）。

**それなら文書に書かれているはず**である（§8 は別名解決を細かく書いている）。

## 4. 案

- **案 A＝エラーにする**（標準 SQL・MySQL 既定と同じ）。**破壊的**。**本命**（§4.1）
- 案 B＝警告を出す。値は変えない
- 案 C＝文書化のみ（「先頭行の値を返す」と明記）
- 案 D＝何もしない

### 4.1 **案 A（エラー）を推す**（2026-08-06・オーナー指摘で見立てを改めた）

**起票時は「案 B → 様子を見て案 A」と書いた。弱腰だった。改める。**

**理由 1＝警告では届かない。**
**[B145](ksql_b145_describe_subtable_field_issue.md) の `HAVING`（v3.56.2）は、警告が出ていたのに
「0 行」を見た人に届かなかった。** **[B140](ksql_b140_cte_groupby_total_order_issue.md) は警告疲れそのもの。**
**警告疲れを起こしている系に、意味のない値を守るための警告をもう 1 本足すのは筋が通らない。**

**理由 2＝返る値に正しい読みが 1 つも無い。**
**220 件のうち任意の 1 件**であって、近似でも代表値でもない。
**[B145 の v3.56.1](ksql_b145_describe_subtable_field_issue.md)（拡張 grouping をエラーにした）と同じ判断基準**
——**静かに返る値が無意味なら、破壊的でもエラーにする。**

**理由 3＝正当な用途には、既に正しい綴りがある。**

**唯一の正当な用途は関数従属**である。

```sql
SELECT 製品名, 仕入先, SUM(個数) AS 合計 FROM APP4228 GROUP BY 製品名
```

**`仕入先` が製品ごとに 1 つに決まるなら、この列は意味を持つ。**
**MySQL 5.7 が `ONLY_FULL_GROUP_BY` を既定にしつつ、検出できる関数従属だけ許した**のはこの用途のため。
**kSQL は kintone の上なので関数従属を検出する手立てが無い。**

**しかし移行先が既にある。**

```sql
SELECT 製品名, MIN(仕入先) AS 仕入先, SUM(個数) AS 合計 FROM APP4228 GROUP BY 製品名
```

**定数列に対する `MIN` はその定数。** MySQL が `ANY_VALUE()` を足したのと同じ役割を
**`MIN` / `MAX` が既に果たす**（`ANY_VALUE` を新設する必要は無い）。

**したがって案 A の代償は「機能が失われる」ではなく「書き方が変わる」だけ。**

### 4.4 **測れない利用者にはエラー文が唯一の案内になる**（2026-08-06）

**依頼元は該当なしと分かっている**ので、[B145 の v3.56.1](ksql_b145_describe_subtable_field_issue.md)
のような事前照会は不要。**残るのは保存クエリとプラグイン利用者**で、**こちらは測る手立てが無い。**

**帰結を明記しておく**＝**該当クエリを持っている人は、次に実行して落ちたときに初めて知る。**
**そのとき、エラー文だけで自力回復できなければならない。**

**したがってエラー文は次を満たすこと**（受入条件に含める）。

| 要件 | なぜ |
|---|---|
| **どの列が問題かを名指しする** | 列が多い SELECT で「どれか」を探させない |
| **「存在しない」と読めないこと** | **その列は存在する**。[B145 v3.56.1](ksql_b145_describe_subtable_field_issue.md) で
`unknown field code(s)` が「そんな項目は無い」と読まれ、誤った結論へ誘導した |
| **書き換え後の形をそのまま示す** | `MIN(<列>)` へ。**`GROUP BY` に足す**という選択肢も併記する（意味が変わるので利用者が選ぶ） |
| **示した形が実際に動くこと** | **[B140](ksql_b140_cte_groupby_total_order_issue.md) と [B145](ksql_b145_describe_subtable_field_issue.md) で
「従うと壊れる助言」を 3 回出している。**実測で確かめてから載せる |

**文面の骨子**（実装時に実測して確定する）

```
ArgumentError: 個数 は集計もグループ化もされていません（APP4228）。
GROUP BY 製品名 のもとでは、グループ内のどの行の値を返すか決まりません。
  グループごとに 1 つに決まる値なら  →  MIN(個数) AS 個数
  行を分けたいなら                  →  GROUP BY 製品名, 個数
```

**「なぜ決まらないか」を書く**のは、[v3.56.2](ksql_b145_describe_subtable_field_issue.md) で
**症状だけ書くと別の入口から来た人に通じない**と学んだため。

## 5. B147 との区別

**別の欠陥である。** 混同しないこと。

| | 条件 | 症状 |
|---|---|---|
| **B147** | **集計の別名**が、別の列の式が参照するフィールド名と衝突する | **その列が空になる**（キー列でも起きる） |
| **B148** | 列を**集計もキーもしていない** | **先頭行の値が返る** |

**B147 は先頭行の値ですらない**（`年月=""`）。**先頭行を評価していれば正しい値が出るはず**なので、
**B147 は投影時の上書きが原因**という §2 の見立てと整合する。

## 6. 次に開くとき必要なもの

1. **`ORDER BY` / `HAVING` / ウィンドウの引数**でも同じ「先頭行」が使われるか
2. **JOIN を含む場合**の挙動
3. **CTE・一時テーブル経由**でも同じか
4. **レシピや文書の掲載 SQL に、この形が無いか**（あれば掲載 SQL 側も直す。→ [B141](ksql_b141_doc_sql_unverified_issue.md)）
5. **「先頭行」が安定しているか**（取得順・並列取得・押し下げの有無で変わるなら、
   **同じクエリが日によって違う値を返す**ことになり、さらに重い）

## 9. 依頼元の全数確認（2026-08-07）

**[v3.57.0 の返信](../../../ksql-analytics/docs/internal/kSQLエンジンへの返信-20260807-v3570.md)。**

| 対象 | 本数 | 結果 |
|---|---:|---|
| `sql/`（運用資産） | 12 | **全通** |
| 独立ラン 1 / 2 / 3 | 17 | **全通** |
| **CSV 差分** | 3 本 | **ゼロ** |

**偽陽性ゼロ。** **`GROUP BY` 無しの集計も資産・その場の MCP 呼び出しとも該当なし。**

**「該当無しと申告されていても、版が変わったら機械的に通し直す」という規約が効いた**＝
**こちらの申告を信じずに測るのは、こちらが把握を誤っていたときに唯一気づける手段。**

**理由の観察が興味深い**＝**`SELECT *` を書かない習慣（鉄則 1）が、
結果として「明細列を混ぜる」形を作りにくくしていた**。
**規約が別の規約の穴を塞いでいた**（意図しない相互作用の良い側）。

**`ksql_explain` で同じ診断が出ることが効く**とも書かれている＝
**「集計・ウィンドウを含む本番クエリは必ず `ksql_explain` を通す」運用**なので、
**レコード取得前に規約違反が機械的に落ちる。**
**「規約は読まれないと効かない」という弱点が、ここだけ消えた。**

### 9.1 手順に取り込んだ 2 件

**① 直したら隣の経路も測る**（依頼元 §4）

> **2 回とも「片方を直した直後の確認」で見つかった。
> 「直したついでに、隣の経路も同じ形か確かめる」手順が入れば、2 度目は 1 度目と同時に見つかっていた。**

**そのとおり。v3.56.1 で拡張 grouping を直した直後に plain 側を測っていれば、
B148 はそのとき見つかっていた**＝**1 週間、静かに間違う実装を出荷し続けた。**

**② 助言を出す機能には、助言をそのまま実行するテストを 1 本**（依頼元 §5）

**4 度目を止めたのがレビューではなく実測だったこと**が要点。
**文面は正しく見えていた**（`APP4233` は実在し `MIN(数値_0)` も正しい）が、
**実行して初めて `_pid` が親アプリに無いと分かった。**

**どちらも auto-memory へ記録した。**
