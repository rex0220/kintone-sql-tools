## 1. 実測結果（v3.58.0）

### 1.1 §12.7 の周辺機構は現行版でそのまま動く ○

系列部分だけ手書き（FROM なし `UNION ALL`）に置き換えた完全 SQL を実行した。

```sql
WITH 日付系列 AS (
  SELECT '2025-08-04' AS 日付 UNION ALL SELECT '2025-08-05' UNION ALL SELECT '2025-08-06'
),
日別 AS (
  SELECT 日付, SUM(個数) AS 合計 FROM APP4228
  WHERE 日付 >= '2025-08-04' AND 日付 <= '2025-08-06' GROUP BY 日付
)
SELECT s.日付, CASE WHEN d.合計 = '' THEN 0 ELSE d.合計 END AS 合計
FROM 日付系列 AS s LEFT JOIN 日別 AS d ON s.日付 = d.日付
ORDER BY s.日付
```

```json
{"columns":["日付","合計"],"rows":[
  {"日付":"2025-08-04","合計":"0"},
  {"日付":"2025-08-05","合計":"1750"},
  {"日付":"2025-08-06","合計":"552"}],"rowCount":3,"warnings":[]}
```

**取引の無い 08-04 が "0" で出る。** CTE 間 LEFT JOIN・修飾参照・`CASE` の空文字ガード・
列名まで §12.7 の期待と同形。**新規部分は系列生成だけ**で、周辺リスクは小さい。

### 1.2 `DECLARE` は `=` のみ・変数名は英字/`_` 開始のみ ✗（仕様の例が壊れている）

```
DECLARE @start DEFAULT 1;   → ParseError: 「=」が必要です（位置 15、トークン: 「DEFAULT」）
DECLARE @開始 = 1;          → LexError: 「@」 の直後には英字または _ で始まる変数名が必要です
DECLARE @d = '2025-08-05'; WITH t AS (...WHERE 日付 = @d...) SELECT ... → 成功（バッチ 2 文）
```

### 1.3 CTE 上のウィンドウは、一意でも「全順序でない」警告が出る（仕様が沈黙）

```sql
WITH s AS (SELECT '1' AS n UNION ALL SELECT '2' UNION ALL SELECT '3'),
w AS (SELECT n, LAG(n) OVER (ORDER BY n) AS 前 FROM s)
SELECT n, 前 FROM w ORDER BY n
```

値は正しいが `warnings` に「`前` の ORDER BY は全順序でないため…すでに一意な場合も
この警告が出ます…」が出る。**仕様 R1 の受入 M4 / M5（生成系列 + LAG / LEAD）は
この警告が出るか出ないかを書いていない。**

## 2. 指摘

### R1-1【Must】`DECLARE` の例が二重に壊れている（§2.4・§12.10 X7）

`DECLARE @開始 DEFAULT 1` は **`DEFAULT` で ParseError、`@開始` で LexError**（§1.2 実測）。
B141 で 5 回踏んだ「従うと壊れる例」と同じ形。**全例を `DECLARE @start = 1;` 形へ**。
§15.8 の実測項目一覧も同じ前提で読み直すこと。

### R1-2【High】生成系列上のウィンドウ警告の扱いを決める（§6.5・§12.5 M4/M5）

実測 §1.3 のとおり、**本命の使い方（系列 + `LAG`）で現行の警告機構が発火する**。
生成列は**構築により厳密単調**＝一意性が推論ではなく構成で保証される初のケース。

- **案 a（推奨）**: ウィンドウ `ORDER BY` が生成系列列を含むとき、この警告を出さない。
  警告文自身が「一意でも**証明できないため**出る」と言っており、証明できる場合に
  出し続けると文と矛盾する。抑止条件は「生成 CTE 由来の列」に限定（B140 で閉じた
  「集約キーからの一意性証明」とは別物＝推論不要・構成保証）
- **案 b**: Phase 1 は警告を許容し、受入 M4/M5 に**期待警告文を明記**＋言語リファレンスに
  「この警告は無視してよい」と書く（B140 と同じ手当て）

**どちらを採るかはオーナー判断。いずれでも M4 / M5 に `warnings` の期待値を書くこと**
（書かないと、警告ノイズ付きで受入が通る）。

### R1-3【Medium】`ksql_validate`（静的検証）の契約が未規定

B148 R3 は「二段階契約（AST-only / schema-aware）」を明記していた。B149 は
**どのエラーが `ksql_validate` で捕まるか未定義**。リテラル引数の
型不一致・step 0・`FROM` 直置き・（リテラルなら）上限超過は静的に決まる。
**validate で出すもの／実行時（変数解決後）に回るものを表で明記**すること。

### R1-4【Medium】相対日付変数（`TODAY()` 等）の扱いが一言で流されている（§2.4）

日次 0 埋めの実需は「**今日を終端にする**」形が最初に書かれるはず:

```sql
DECLARE @today = TODAY();
WITH d AS (GENERATE_SERIES(@from, @today)) ...
```

§2.4 の「相対日付変数は既存の変数エラー規則に従う」では**許可か拒否か読めない**。
`TODAY()` は実行時に具体日付へ解決されるため**許可を推奨**。拒否するなら診断文まで明記。
いずれでも受入条件に 1 本入れること。

### R1-5【Low】保存クエリ（v3.48.0 read-only 複文）との関係が未記載

read-only 判定が新文型（`GENERATE_SERIES` 文 CTE）を **read-only として分類**することを
仕様に 1 行明記（分類漏れだと保存クエリで使えない）。§15.10 の surface 列挙に
`ksql_run_saved_query` 経路を追加。

### R1-6【Low】step の `+` 符号の可否が曖昧（§3.3）

`<signed-nonzero-integer>` が `'+1 day'` / 整数 step `+1` を含むか不明確。
可否どちらでもよいが、診断の一貫性のため明記。
