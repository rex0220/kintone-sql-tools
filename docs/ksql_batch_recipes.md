# kSQL バッチ設計レシピ集

kSQL の現行機能（バッチ実行・一時テーブル・ASSERT・UPSERT・バッチ変数）だけで、**リラン可能で安全な差分更新バッチ**を組むためのレシピ集です。新機能ではなく、既存機能の組み合わせ方をまとめています。

- 対象: CLI（`-e` / `-f` / `--console`）と MCP（`ksql_mutate` 等）。プラグイン UI もバッチ対応（DML は文ごとの確認ダイアログ）。
- 参照: 言語リファレンス [§25 バッチ実行と一時テーブル](ksql_language_reference.md#25-バッチ実行と一時テーブル) / [§26 ASSERT](ksql_language_reference.md#26-assert) / [§17 UPSERT](ksql_language_reference.md#17-upsert)。
- 例のアプリ/フィールドは説明用です。`APP100`（差分アプリ）・`APP200`（マスタアプリ）等はご自身の物理アプリ ID・フィールドコードに置き換えてください。

> **前提バージョン**: 本レシピはバッチ変数を使うため **v2.1.0 以降**を前提とします。主な機能の追加バージョン — バッチ実行・一時テーブル `v1.4.0`／ASSERT `v1.10.0`／プラグインの DML バッチ `v1.9.0`／`tempTableMaxRows` `v1.11.0`／バッチ変数 `SET @var`・IN リストの変数 `v2.1.0`。変数を使わない R2・R3 は v1.10.0（ASSERT）以降で動きます。

---

## 設計原則（リラン可能バッチ）

kSQL バッチは**トランザクションを持たず非アトミック**です（途中失敗時は前半のみ反映され得る）。そこで、いつ失敗しても**先頭からのリランだけで正しく回復できる**（＝冪等・判断分岐なし）設計にします。

1. **ステータス駆動**: 対象を「未処理 → 処理済」のステータスで管理し、毎回「未処理」だけを拾う。
2. **マスタ更新 → ステータス更新の順**: 本処理（マスタへの書き込み）を先に行い、**成功した対象だけを「処理済」にする**。逆順にすると、マスタ更新前に失敗した対象が「処理済」で取り残される。
3. **件数ゲート**: 想定外の件数（0 件・過大）は**書き込み前に ASSERT で止める**。
4. **冪等**: `UPSERT`（キー一致で更新・なければ挿入）を使い、リランで二重登録が起きないようにする。**ただしキーがソース・マスタ双方で一意であることが前提**（R1 の 2') 参照）。
5. **時刻・バッチ ID の固定**: `SET @now = NOW()` でバッチ内時刻を固定し、事後検証を完全一致で書けるようにする。

## R1. 差分更新バッチの全体像（リラン可能・冪等）

```sql
SET @now = NOW();          -- バッチ内で時刻を固定
SET @batch_id = NOW();     -- 実行識別子（事後検証・トレース用）

-- 1) 未処理の差分を一時テーブルへ確定（以降はこのスナップショットで処理）
CREATE TEMP TABLE #tgt AS
SELECT $id AS 差分ID, 顧客コード, 顧客名
FROM APP100
WHERE 処理ステータス = '未処理';

-- 2) 件数ゲート（0 件や過大なら書き込み前に停止）
ASSERT (SELECT COUNT(*) FROM #tgt) BETWEEN 1 AND 10000;

-- 2') キー一意ゲート（後述の冪等性の前提）: ソース内にキー重複があれば停止
ASSERT (SELECT COUNT(*) FROM #tgt) = (SELECT COUNT(DISTINCT 顧客コード) FROM #tgt);

-- 3) 本処理: マスタへ UPSERT（キー一致で更新・なければ挿入）
UPSERT INTO APP200 (顧客コード, 顧客名)
SELECT 顧客コード, 顧客名 FROM #tgt
ON DUPLICATE (顧客コード);

-- 4) 成功した対象だけを「処理済」に（時刻・バッチ ID を付与）
UPDATE APP100
SET 処理ステータス = '処理済', 処理日時 = @now, バッチID = @batch_id
WHERE $id IN (SELECT 差分ID FROM #tgt);
```

> **冪等性の前提（重要）**: UPSERT の「キー一致で更新・なければ挿入」が冪等になるのは、**`ON DUPLICATE` キーがソース `#tgt` 内でもマスタ `APP200` 側でも一意**であるときだけです。
> - **ソース内にキー重複があると重複登録される**: 現行の UPSERT はソース各行を独立に判定するため、`#tgt` に未登録の同一 `顧客コード` が複数あると、そのぶんマスタへ**新規レコードが複数作成**されます（初回実行で重複登録される。次回以降は既存キーとして更新に回るので INSERT が無限に増えるわけではないが、一度できた重複は残り、**以後の正しい回復も保証できなくなる**）。上の **2') のキー一意 ASSERT** で書き込み前に止めるか、`#tgt` 作成時に `GROUP BY 顧客コード` 等で集約してください。
> - **マスタ側にキー重複があると 1 件しか更新されない**: 既存マスタに同キーが複数あると、更新は最大 `$id` の 1 件のみで、他は残ります。マスタのキー一意性を前提にします。

- **途中失敗時**: 上記の一意性が満たされていれば、3) まで済んで 4) で失敗しても、次回リランで同じ差分を再度 UPSERT（キー一致で更新＝冪等）し、4) を再実行して「処理済」にできる。取り残し・重複は起きない。
- `#tgt` にスナップショットしてから処理するため、実行中に新しく増えた「未処理」は次回に回る（対象が処理中にぶれない）。

## R2. 事前ゲート（件数チェック・inserts/updates 内訳）

書き込み前に「何件を新規作成し、何件を更新するか」を読み取り専用で確認します（現行機能のみ・書き込みなし）。

```sql
CREATE TEMP TABLE #tgt AS
SELECT 顧客コード, 顧客名 FROM APP100 WHERE 処理ステータス = '未処理';

-- inserts（マスタ未存在）と updates（マスタ存在）を 1 結果セットで
--   LEFT JOIN + COUNT(m.顧客コード)：COUNT(field) は空文字（未マッチ）をスキップして数える
SELECT
  COUNT(*)                       AS 対象件数,
  COUNT(m.顧客コード)             AS updates,
  COUNT(*) - COUNT(m.顧客コード)  AS inserts
FROM #tgt t LEFT JOIN APP200 m ON t.顧客コード = m.顧客コード;

-- 想定外件数なら停止
ASSERT (SELECT COUNT(*) FROM #tgt) BETWEEN 1 AND 10000;
```

> **1 結果セットにまとめる理由**: プラグイン UI は**最後に結果を返した文だけ**を表示するため、`SELECT COUNT(*)` を 2 本並べると両方を同時に見られません。上のように LEFT JOIN で 1 行にまとめると全入口で同じ見え方になります。
>
> **確認手段の役割分担**（混同しやすい点）:
> - **構文・静的検査**（temp table 依存・未定義参照など）: `ksql_validate` / CLI の validate。
> - **実行計画のみ**（SIMPLE/FULL_SCAN・書き込み先）: `ksql_explain` / CLI `--dry-run`。**`--dry-run` は kintone にアクセスせず、実データの件数は出ません**。
> - **実データの件数**: 上の R2 を `ksql_query` / CLI で**実際に実行**（read-only なので書き込みなし）。

## R3. 更新前スナップショット（`#before`）

上書きされる前のマスタの値を一時テーブルに退避し、結果に含めます（差分の記録・目視確認用）。

```sql
CREATE TEMP TABLE #tgt AS
SELECT 顧客コード, 顧客名 FROM APP100 WHERE 処理ステータス = '未処理';

-- 更新対象の「更新前の値」を退避
CREATE TEMP TABLE #before AS
SELECT $id, 顧客コード, 顧客名 FROM APP200
WHERE 顧客コード IN (SELECT 顧客コード FROM #tgt);

-- 本処理
UPSERT INTO APP200 (顧客コード, 顧客名)
SELECT 顧客コード, 顧客名 FROM #tgt
ON DUPLICATE (顧客コード);

-- 退避した更新前の値を確認（バッチは最後の結果セットを表示）
SELECT * FROM #before;
```

一時テーブルはバッチ内スコープ（呼び出し終了で破棄）なので、恒久保存が要る場合は別途アプリへ INSERT します。

## R4. 実行結果の識別・件数突合（バッチ ID）

`SET @batch_id` を全書き込みに付与しておくと、**その実行で書き込んだ対象を完全一致で特定**でき、事後検証が近似条件（`処理日時 >= TODAY()`）不要になります。さらに、対象件数を退避しておけば**処理漏れの突合**まで書けます。

```sql
SET @batch_id = NOW();

-- 対象を退避（突合の基準にする）
CREATE TEMP TABLE #tgt AS
SELECT $id AS 差分ID FROM APP100 WHERE 処理ステータス = '未処理';

UPDATE APP100
SET 処理ステータス = '処理済', バッチID = @batch_id
WHERE $id IN (SELECT 差分ID FROM #tgt);

-- 突合: バッチ ID で更新された件数が、対象件数と一致することを検証
ASSERT (SELECT COUNT(*) FROM APP100 WHERE バッチID = @batch_id)
     = (SELECT COUNT(*) FROM #tgt);

-- 実行結果の識別・件数確認
SELECT COUNT(*) AS 更新件数 FROM APP100 WHERE バッチID = @batch_id;
```

> - `#tgt` で対象件数を退避せず `SELECT COUNT(*) ... WHERE バッチID = @batch_id` を出すだけだと、**その実行の対象を識別・件数表示できる**が、**「予定件数どおり漏れなく処理できたか」の突合にはならない**（上の `ASSERT` で突合になる）。
> - `@batch_id = NOW()` は追跡・識別に便利ですが、**厳密に一意な ID を保証するものではありません**（同一ミリ秒の同時実行等）。厳密な一意性が要る場合は呼び出し側（ジョブ制御）で一意 ID を採番して渡してください（保存クエリのパラメータ化＝将来対応）。
> - `SET @cnt = (SELECT COUNT(*) ...)`（サブクエリを変数へ代入）は現時点で非対応です。件数チェックは **ASSERT にスカラーサブクエリを直接**書きます（R1/R2/R4）。

## R5. バッチ変数の活用（v2.1.0）

- **時刻固定**: `SET @now = NOW();` … 以降のすべての文で同じ時刻（`NOW()` を文ごとに評価すると値がぶれる）。
- **条件値の DRY 化**: 対象日付・ステータス値を 1 か所で定義。
  ```sql
  SET @cutoff = TODAY();
  DELETE FROM APP100 WHERE 作成日時 < @cutoff AND 処理ステータス = '処理済';
  ```
- **チェックボックス/複数選択フィールド**: `=` を使えないフィールドは `IN (@変数)` で（v2.1.0）。
  ```sql
  SET @a = 'A'; SET @b = 'B';
  SELECT 顧客No FROM APP100 WHERE 顧客ランク IN (@a, @b);
  ```

変数の詳細・制約は言語リファレンス [§25 バッチ変数](ksql_language_reference.md#25-バッチ実行と一時テーブル) を参照。

## 適用限界（スケール指針）

判断基準は総レコード数ではなく **「日次の実変更件数が API 制限と実行時間に収まるか」** です。

| 実行あたり処理件数 | 判断 |
|---|---|
| 〜数千件（差分型の日次バッチ） | **本設計の主戦場**。読み取り数リクエスト＋書き込み 100 件単位で、1 日の API 上限のごく一部で収まる |
| 〜数万件 | 成立。ただし後述の各種上限・タイムアウトの調整、または日付範囲での分割実行が必要 |
| 数十万件〜 | **機能では解けない領域**。インメモリモデル・API 上限・実行時間の 3 制約が同時に立つ。上流での差分抽出（CDC 化）や連携方式の見直しを先に検討 |

- **API 上限はコース差あり**: 1 日あたりの API リクエスト上限は**スタンダードコース 10,000 / ワイドコース 100,000（/アプリ）**（[kintone REST API 共通仕様](https://cybozu.dev/ja/kintone/docs/rest-api/overview/kintone-rest-api-overview/)）。同時アクセス数（ドメインあたり）の制約もあります。
- **数千〜数万件で調整対象になる項目**（入口ごと）:
  - 取得上限 `maxRecords`（CLI `KSQL_MAX_RECORDS` / profile `query.maxRecords`。既定 500）
  - 一時テーブル行数 `tempTableMaxRows`（既定 10,000）
  - MCP の影響行数ガード `dmlMaxRows`（文ごと）/ `dmlTotalMaxRows`（合計）
  - 実行タイムアウト
- マスタが 10 万件でも**日次差分が数百件なら問題ありません**（判断は総件数でなく日次の実変更件数）。

## 注意

- **トランザクションはありません**。バッチは非アトミックで、途中失敗時に前半のみ反映された状態が起こり得ます（だからこそ R1 の「冪等・リラン可能」設計にします）。
- 一時テーブルは**同時 16 個・1 個あたり既定 10,000 行**（`tempTableMaxRows` で変更可）。バッチは**最大 20 文**。
- DML バッチは常に **fail-fast**（`ASSERT` 失敗・エラーで停止）。`continueOnError` は read-only バッチのみ。
