# kSQL バッチ設計レシピ集

kSQL の現行機能（バッチ実行・一時テーブル・ASSERT・UPSERT・バッチ変数）だけで、**リラン可能で安全な差分更新バッチ**を組むためのレシピ集です。新機能ではなく、既存機能の組み合わせ方をまとめています。

- 対象: CLI（`-e` / `-f` / `--console`）と MCP（`ksql_mutate` 等）。プラグイン UI もバッチ対応（DML は文ごとの確認ダイアログ）。
- 参照: 言語リファレンス [§25 バッチ実行と一時テーブル](ksql_language_reference.md#25-バッチ実行と一時テーブル) / [§26 ASSERT](ksql_language_reference.md#26-assert) / [§17 UPSERT](ksql_language_reference.md#17-upsert)。
- 例のアプリ/フィールドは説明用です。`APP100`（差分アプリ）・`APP200`（マスタアプリ）等はご自身の物理アプリ ID・フィールドコードに置き換えてください。**`バッチID` は文字列（1行）フィールドにしてください**（下記）。

> **前提バージョン**: 本レシピはバッチ変数を使うため **v2.1.0 以降**を前提とします。主な機能の追加バージョン — バッチ実行・一時テーブル `v1.4.0`／ASSERT `v1.10.0`／プラグインの DML バッチ `v1.9.0`／`tempTableMaxRows` `v1.11.0`／バッチ変数 `SET @var`・IN リストの変数 `v2.1.0`。

> **`バッチID` は文字列フィールドにする（重要）**: `NOW()` は**ミリ秒付き ISO 文字列**（`2026-07-14T12:34:56.789Z`）です。kintone の**日時フィールドは分精度**で秒・ミリ秒が丸められるため、`バッチID` を日時フィールドにすると `WHERE バッチID = @now` が一致せず（0 件）、後述の確保・突合が成立しません。**`バッチID` は文字列（1行）フィールド**にして ISO 文字列をそのまま保存・完全一致させます（`処理日時` は日時フィールドで可。丸めは無害）。

> **一時テーブルを参照できる DML は `INSERT … SELECT` / `UPSERT … SELECT` だけ**（v1.7.0）。`UPDATE … WHERE $id IN (SELECT … FROM #tmp)` のように**一時テーブルをサブクエリ参照する UPDATE / DELETE は実行前に拒否**されます。そのため「処理した対象だけを後で更新する」には、**先にバッチ ID で対象を確保**し、**その直接条件（`WHERE バッチID = @now`）で更新**します（R1）。

---

## 設計原則（リラン可能バッチ）

kSQL バッチは**トランザクションを持たず非アトミック**です（途中失敗時は前半のみ反映され得る）。いつ失敗しても**先頭からのリランだけで正しく回復できる**（＝冪等・判断分岐なし）設計にします。

1. **ステータス駆動**: 対象を「未処理 → 処理中 → 処理済」で管理する。
2. **確保 → 本処理 → 完了 の順（fail-fast）**: まず対象を自分のバッチ ID で「処理中」に確保し、本処理（マスタ書き込み）を行い、最後に「処理済」にする。DML バッチは fail-fast なので、途中で失敗すれば後段に進まない。※ 部分成功を検出して差分だけ更新する仕組みではなく、「後段に進まない＋冪等でリラン復旧」で正しさを担保する。
3. **件数ゲートは書き込みの前**: 想定外の件数（0 件・過大）は、確保の UPDATE より**前**に ASSERT で止める。
4. **冪等**: `UPSERT`（キー一致で更新・なければ挿入）を使う。ただし**キーがソース・マスタ双方で一意**であることが前提（R1 のキー一意 ASSERT 参照）。
5. **時刻・バッチ ID の固定**: `SET @now = NOW()` で 1 回だけ評価し、確保・完了・突合で使い回す。`バッチID` は文字列フィールド（上記）。

## R1. 差分更新バッチ（確保 → 処理 → 完了）

一時テーブル参照 UPDATE が使えないため、**対象をバッチ ID で確保してから、その直接条件で完了**させます。この「確保」は、実行中に増えた未処理を混ぜない・多重起動を緩和する役割も兼ねます。

```sql
SET @now = NOW();          -- 1 回だけ評価し、確保・完了・突合で使い回す

-- 1) 件数ゲート（確保の前に。0 件や過大なら停止）
ASSERT (SELECT COUNT(*) FROM APP100 WHERE 処理ステータス = '未処理') BETWEEN 1 AND 10000;

-- 2) 確保: 未処理を自分のバッチ ID で「処理中」に（直接条件・一時テーブル不使用）
UPDATE APP100
SET 処理ステータス = '処理中', バッチID = @now
WHERE 処理ステータス = '未処理';

-- 3) 確保した分をスナップショット（以降はこの集合で処理）
CREATE TEMP TABLE #tgt AS
SELECT 顧客コード, 顧客名 FROM APP100 WHERE バッチID = @now;

-- 4) キー一意ゲート（冪等性の前提。ソース内にキー重複があれば停止）
ASSERT (SELECT COUNT(*) FROM #tgt) = (SELECT COUNT(DISTINCT 顧客コード) FROM #tgt);

-- 5) 本処理: マスタへ UPSERT（UPSERT … SELECT は一時テーブル参照可）
UPSERT INTO APP200 (顧客コード, 顧客名)
SELECT 顧客コード, 顧客名 FROM #tgt
ON DUPLICATE (顧客コード);

-- 6) 完了: 確保した分を「処理済」に（直接条件・一時テーブル不使用）
UPDATE APP100
SET 処理ステータス = '処理済', 処理日時 = @now
WHERE バッチID = @now AND 処理ステータス = '処理中';

-- 7) 事後突合（任意）: 処理済にした件数が確保件数と一致することを検証
ASSERT (SELECT COUNT(*) FROM APP100 WHERE バッチID = @now AND 処理ステータス = '処理済')
     = (SELECT COUNT(*) FROM #tgt);
```

**なぜこの形か**
- **確保（2）と完了（6）は直接条件**（`WHERE 処理ステータス=…` / `WHERE バッチID=@now`）で、一時テーブルをサブクエリ参照しない → 実行拒否を避ける。本処理（5）だけが `UPSERT … SELECT FROM #tgt`（許可）。
- **実行中に増えた未処理は混ざらない**: 2) の時点の未処理だけをバッチ ID で確保し、以降はその集合（3 のスナップショット）で処理する。
- **多重起動の緩和**: 2) で対象を「処理中」に確保するため、別実行が同じ「未処理」を二重に拾いにくくなる（ただし kintone にレコードロックは無く、確保 UPDATE 自体は競合し得る＝**完全な排他ではない**。厳密な排他はジョブ制御側で保証）。

**冪等性・リランの注意**
- **キー一意が前提**: `#tgt` 内・`APP200` 側の双方で `顧客コード` が一意のときだけ UPSERT が冪等。ソース内にキー重複があると**初回に重複登録**され（次回以降は既存キーとして更新に回るので無限には増えないが、できた重複は残り**正しい回復も保証できなくなる**）、上の 4) で止める。マスタ側に重複があると更新は最大 `$id` の 1 件のみ。
- **事後突合（7）は書き込み後の検知**: 失敗した時点で書き込みは済んでいる。「ASSERT で止まれば守られる」ではなく「異常を検知して**リランで回復する**（冪等なので安全）」ための番人。
- **処理中のまま止まった対象の復旧**: 途中失敗で「処理中」に残った行は、次回リランで拾えるよう、別途「一定時間経過した処理中 → 未処理」に戻す運用を用意すると自動化できる。

## R2. 事前ゲート（件数チェック・inserts/updates 内訳）

書き込み前に「何件を新規作成し、何件を更新するか」を読み取り専用で確認します（書き込みなし）。

```sql
CREATE TEMP TABLE #tgt AS
SELECT 顧客コード, 顧客名 FROM APP100 WHERE 処理ステータス = '未処理';

-- 想定外件数なら停止（ゲートは先頭に）
ASSERT (SELECT COUNT(*) FROM #tgt) BETWEEN 1 AND 10000;

-- inserts（マスタ未存在）と updates（マスタ存在）を 1 結果セットで
--   COUNT(フィールド) は空文字・NULL（＝LEFT JOIN 未マッチ）をスキップして数える（§8）
SELECT
  COUNT(*)                       AS 対象件数,
  COUNT(m.顧客コード)             AS updates,
  COUNT(*) - COUNT(m.顧客コード)  AS inserts
FROM #tgt t LEFT JOIN APP200 m ON t.顧客コード = m.顧客コード;
```

> **1 結果セットにまとめる理由**: プラグイン UI は**最後に結果を返した文だけ**を表示するため、`SELECT COUNT(*)` を 2 本並べると両方を同時に見られません。LEFT JOIN で 1 行にまとめると全入口で同じ見え方になります。`COUNT(m.顧客コード)` が「マスタにマッチした件数（＝updates）」になるのは [§8 集計関数](ksql_language_reference.md#8-group-by--集計関数) の「`COUNT(フィールド)` は空文字・NULL をスキップ」仕様によります。
>
> **確認手段の役割分担**（混同しやすい点）:
> - **構文・静的検査**（temp table 依存・未定義参照など）: `ksql_validate` / CLI の validate。
> - **実行計画のみ**（SIMPLE/FULL_SCAN・書き込み先）: `ksql_explain` / CLI `--dry-run`。**`--dry-run` は kintone にアクセスせず、実データの件数は出ません**。
> - **実データの件数**: 上の R2 を `ksql_query` / CLI で**実際に実行**（read-only なので書き込みなし）。

## R3. 更新前スナップショット（`#before`）

上書きされる前のマスタの値を一時テーブルに退避し、結果に含めます（差分の記録・目視確認用）。

```sql
CREATE TEMP TABLE #tgt AS
SELECT 顧客コード, 顧客名 FROM APP100 WHERE 処理ステータス = '未処理';

-- 更新対象の「更新前の値」を退避（$ 始まりの列はエイリアスを付ける）
CREATE TEMP TABLE #before AS
SELECT $id AS レコードID, 顧客コード, 顧客名 FROM APP200
WHERE 顧客コード IN (SELECT 顧客コード FROM #tgt);

-- 本処理（UPSERT … SELECT は一時テーブル参照可）
UPSERT INTO APP200 (顧客コード, 顧客名)
SELECT 顧客コード, 顧客名 FROM #tgt
ON DUPLICATE (顧客コード);

-- 退避した更新前の値を確認（バッチは最後の結果セットを表示）
SELECT * FROM #before;
```

一時テーブルはバッチ内スコープ（呼び出し終了で破棄）なので、恒久保存が要る場合は別途アプリへ INSERT します。R1 に組み込む場合は、確保（R1 の 2）の後・UPSERT の前に `#before` を作ります。

## R4. バッチ変数の活用（v2.1.0）

- **時刻固定**: `SET @now = NOW();` … 以降のすべての文で同じ時刻（`NOW()` を文ごとに評価すると値がぶれる）。**1a では変数から変数への代入（`SET @b = @a`）はできない**ため、同じ値を複数の用途に使いたい場合は同じ `@now` を使い回します。
- **条件値の DRY 化**: 対象日付・ステータス値を 1 か所で定義。
  ```sql
  SET @cutoff = TODAY();
  DELETE FROM APP100 WHERE 作成日時 < @cutoff AND 処理ステータス = '処理済';
  ```
  この DELETE は**同一実行の中では冪等**です（`@cutoff` はその実行で固定され、消える対象がぶれない）。ただし `TODAY()` はバッチごとに再評価されるため、**翌日のリランでは対象範囲が 1 日広がります**（同じ cutoff に対しては冪等だが、日をまたいで同じ対象集合を保証するものではない）。厳密に同じ対象を再現したい場合は固定の日付リテラルを使ってください。
- **チェックボックス/複数選択フィールド**: `=` を使えないフィールドは `IN (@変数)` で（v2.1.0）。
  ```sql
  SET @a = 'A'; SET @b = 'B';
  SELECT 顧客No FROM APP100 WHERE 顧客ランク IN (@a, @b);
  ```

変数の詳細・制約は言語リファレンス [§25 バッチ変数](ksql_language_reference.md#25-バッチ実行と一時テーブル) を参照。

## 適用限界（スケール指針）

判断基準は総レコード数ではなく **「日次の実変更件数が API 制限と実行時間に収まるか」** です。

| 実行あたり処理件数 | 判断 |
|---|---|
| 〜数千件（差分型の日次バッチ） | **本設計の主戦場**。読み取り数リクエスト＋書き込み 100 件単位で、1 日の API 上限のごく一部で収まる |
| 〜数万件 | 成立。ただし後述の各種上限・タイムアウトの調整、または日付範囲での分割実行が必要 |
| 数十万件〜 | **機能では解けない領域**。インメモリモデル・API 上限・実行時間の 3 制約が同時に立つ。上流での差分抽出（CDC 化）や連携方式の見直しを先に検討 |

- **API 上限はコース差あり**: 1 日あたりの API リクエスト上限は**スタンダードコース 10,000 / ワイドコース 100,000（/アプリ）**（[kintone REST API 共通仕様](https://cybozu.dev/ja/kintone/docs/rest-api/overview/kintone-rest-api-overview/)）。同時アクセス数（ドメインあたり）の制約もあります。
- **数千〜数万件で調整対象になる項目**（入口ごと）: 取得上限 `maxRecords`（CLI `KSQL_MAX_RECORDS` / profile `query.maxRecords`。既定 500）／一時テーブル行数 `tempTableMaxRows`（既定 10,000）／MCP の影響行数ガード `dmlMaxRows`（文ごと）・`dmlTotalMaxRows`（合計）／実行タイムアウト。
- マスタが 10 万件でも**日次差分が数百件なら問題ありません**（判断は総件数でなく日次の実変更件数）。

## 注意

- **トランザクションはありません**。バッチは非アトミックで、途中失敗時に前半のみ反映された状態が起こり得ます（だからこそ R1 の「確保・冪等・リラン可能」設計にします）。
- 一時テーブルは**同時 16 個・1 個あたり既定 10,000 行**（`tempTableMaxRows` で変更可）。バッチは**最大 20 文**。
- DML バッチは常に **fail-fast**（`ASSERT` 失敗・エラーで停止）。`continueOnError` は read-only バッチのみ。
- **一時テーブルを参照できる DML は `INSERT … SELECT` / `UPSERT … SELECT` のみ**。`UPDATE` / `DELETE` から一時テーブルをサブクエリ参照すると実行前に拒否されます（R1 の直接条件で回避）。
