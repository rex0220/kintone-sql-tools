# kSQL サブテーブル仮想テーブル仕様

**バージョン:** 0.3（ドラフト）  
**更新日:** 2026-04-03  
**ステータス:** 詳細設計（AST → kintone API 変換）

---

## 1. 目的

kintone のサブテーブル値はレコード上では JSON 構造として保持されるため、そのままでは SQL で扱いにくい。  
本仕様では、サブテーブルを「通常テーブル相当の仮想テーブル」として公開し、SELECT/UPDATE/DELETE/INSERT を一貫した SQL 操作で扱えるようにする。

---

## 2. スコープ

- 対象:
  - サブテーブルの読み取り（SELECT）
  - サブテーブル行の追加/更新/削除（INSERT/UPDATE/DELETE）
  - 親テーブル・他サブテーブルとの JOIN
- 非対象（本仕様外）:
  - 複数親レコードにまたがる 1 文での高効率一括更新最適化
  - トランザクション制御
  - サブテーブルの列定義変更（メタ変更）

---

## 3. 論理データモデル

### 3.1 仮想テーブル命名

- 親アプリ: `APP100`
- サブテーブル: `APP100$<サブテーブルフィールドコード>`
  - 例: `APP100$明細`
  - 例: `APP100$履歴`

`1サブテーブル = 1仮想テーブル` として扱う。

### 3.2 列構成

仮想テーブルは以下で構成する。

- 親レコード由来のシステム列
  - `_pid`（親 `$id`）
- サブテーブル行由来のシステム列
  - `_rid`（kintone サブテーブル行 `id`）
  - `_idx`（親レコード内の行順、0-based）
- サブテーブル内の各フィールド列
  - 例: `商品コード`, `数量`, `単価`
- 親項目の参照列（読み取り専用）
  - `_p.<親フィールドコード>`
  - 例: `_p.案件名`, `_p.顧客コード`

注:
- 公開列名は `_rid` を正式採用する。
- 将来互換のため、旧名 `_subtable_rid` は当面エイリアスとして受理してよい（非推奨扱い）。
- 互換のため `_parent.<親フィールドコード>` も当面受理してよい（非推奨）。

### 3.3 一意性

推奨主キー（論理キー）:

- `(_pid, _rid)`

`_rid` 単独でも多くのケースで特定できるが、実装上は複合キーを標準とする。

## 4. SELECT 仕様

### 4.1 基本取得

```sql
SELECT * FROM APP100$明細;
SELECT _p.案件名, 商品コード, 数量 FROM APP100$明細 WHERE 数量 > 0;
```

### 4.2 親項目ショートカット（`_p`）

- `_p.<親フィールドコード>` で親項目を直接参照できる
- `_p` はサブテーブル仮想テーブル内でのみ有効
- `_parent.<親フィールドコード>` は互換エイリアス（非推奨）

例:

```sql
SELECT _p.案件名, _p.担当者, 商品コード, 数量
FROM APP100$明細
WHERE _p.案件名 LIKE 'A%';
```

### 4.3 親項目一括展開（`_p.*`）

- `SELECT _p.*` で親項目を一括展開する
- 展開時の列名は `_p.<親フィールドコード>` とする
- `SELECT *` には `_p.*` を暗黙追加しない（行サイズ肥大化を避ける）

例:

```sql
SELECT _p.*, 商品コード, 数量
FROM APP100$明細
WHERE 数量 > 0;
```

### 4.4 親との JOIN

```sql
SELECT p.案件名, d.商品コード, d.数量
FROM APP100 p
INNER JOIN APP100$明細 d
  ON p.$id = d._pid;
```

`_p.<項目>` が使えるため、親JOINは必須ではない。  
親側で追加条件が必要な場合のみ JOIN を使用する。

### 4.5 複数サブテーブル JOIN

```sql
SELECT d.商品コード, h.変更区分
FROM APP100$明細 d
INNER JOIN APP100$履歴 h
  ON d._pid = h._pid;
```

注意:
- 異なるサブテーブル同士を親IDのみで結合すると `N x M` で行数が増える。
- 実行計画では可能な限り `WHERE` を先行適用し、展開後の件数を抑制する。

## 5. DML 仕様（行追加/更新/削除）

サブテーブル DML は内部的に「親レコード更新（PUT /k/v1/record.json）」へ変換する。

共通フロー:

1. 対象親レコードを取得
2. サブテーブル配列をメモリ上で編集
3. `revision` を指定して親レコードを更新

### 5.1 行追加（INSERT）

```sql
INSERT INTO APP100$明細 (_pid, 商品コード, 数量, 単価)
VALUES (123, 'A-001', 2, 1500);
```

- `_rid` は指定不要（新規行のため未採番）
- 変換時は対象親レコードのサブテーブル末尾に新規行を追加する

拡張候補（将来）:
- `INSERT ... POSITION n` による挿入位置制御

### 5.2 行更新（UPDATE）

```sql
UPDATE APP100$明細
SET 数量 = 5, 単価 = 1200
WHERE _pid = 123
  AND _rid = '67890';
```

- 対象行の特定は `_rid` を優先する
- `row_index` のみでの更新は誤更新リスクが高いため非推奨

### 5.3 行削除（DELETE）

```sql
DELETE FROM APP100$明細
WHERE _pid = 123
  AND _rid = '67890';
```

- 対象行をサブテーブル配列から除外して親レコード更新を行う

### 5.4 行並び替え（REORDER）

```sql
REORDER APP100$明細
BY 商品コード ASC, 納期 DESC
WHERE _pid = 123;
```

- 対象親レコード内のサブテーブル配列を `BY` キーで再ソートする
- `_idx` は更新不可（参照専用）とし、並び替えは `REORDER` でのみ行う
- 並び替え後の配列を親レコード更新で保存する
- 更新時はサブテーブル行 `id` のみ送信し、行値は再送しない（ルックアップ再評価影響を抑制）

`WHERE` なし:
- デフォルトはエラー（誤操作防止）
- 全件実行したい場合は `REORDER ALL ...` を使用する

```sql
REORDER ALL APP100$明細
BY 商品コード ASC, 納期 DESC;
```

- `REORDER ALL` では `WHERE` を併用できない
- 実行前確認を必須化する

## 6. 安全制約

### 6.1 WHERE 制約

- `UPDATE APPxxx$...` / `DELETE FROM APPxxx$...` は WHERE 必須
- `REORDER APPxxx$...` は WHERE 必須（`REORDER ALL` を除く）
- 安全モードでは `_rid` 条件を必須化してよい
  - 例: `_rid = '...'`
  - または `_pid + _rid` の複合条件

### 6.2 競合制御

- 親レコード更新時に `revision` を必ず指定（楽観ロック）
- `revision` 不一致時は競合エラーとして返却

### 6.3 更新マージ

- サブテーブル更新時は、非対象行・非対象列を保持したまま更新データを組み立てる
- 部分列のみ送信で既存値を欠落させないよう、内部で明示的にマージする

---

## 7. AST → API 変換ポリシー

### 7.1 テーブル解決

- `APP\d+` は親テーブル
- `APP\d+\$...` はサブテーブル仮想テーブルとして解決

### 7.2 条件式解決

- `_rid` は kintone サブテーブル行 `id` にマップ
- `_pid` は親 `$id` にマップ
- `_p.<親項目>` は親レコードの同名フィールドにマップ
- `_p.*` は親フィールド一覧へ展開

### 7.3 実行単位

- 1 親レコードに対するサブテーブル編集を最小更新単位とする
- 複数親レコード対象の UPDATE/DELETE は親単位で順次更新

---

## 8. エラー仕様

- `_rid` 未指定で複数行に影響する UPDATE/DELETE（安全モード時）
  - `ERR_SUBTABLE_WHERE_ROW_ID_REQUIRED`
- 指定 `_rid` が親レコード内に存在しない
  - `ERR_SUBTABLE_ROW_NOT_FOUND`
- `revision` 競合
  - `ERR_RECORD_REVISION_CONFLICT`
- サブテーブル仮想テーブル名が不正
  - `ERR_SUBTABLE_TABLE_NAME_INVALID`
- `REORDER` で WHERE 省略
  - `ERR_SUBTABLE_REORDER_WHERE_REQUIRED`
- `UPDATE ... SET _idx = ...` のようなシステム列更新
  - `ERR_SUBTABLE_SYSTEM_COLUMN_UPDATE_FORBIDDEN`

---

## 9. 段階導入計画（推奨）

1. Phase 1: SELECT（単一サブテーブル）
2. Phase 2: INSERT/UPDATE/DELETE（`_rid` 条件の安全制約付き）
3. Phase 3: 複数サブテーブル JOIN 最適化（件数抑制）
4. Phase 4: REORDER（親単位の一括並び替え）
5. Phase 5: 互換エイリアス縮退（`_subtable_rid` の非推奨化案内）
