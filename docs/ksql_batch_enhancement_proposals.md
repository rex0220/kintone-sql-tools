## 1. 目的

v1.4.0〜v1.9.0 でバッチ実行の基盤(`;` 区切り複文・一時テーブル・validate-all-first・多層 DML ガード・バッチ EXPLAIN)は完成した。本書は、その先にバッチ処理の実用性・安全性を高める追加機能を列挙し、実装可能性を評価する。

評価記号: **◎** 容易(既存構造にそのまま乗る) / **○** 可能(設計判断が必要) / **△** 条件付き(前提基盤や設計原則との調整が必要) / **×** 非推奨

## 2. 安全性系

### 2.1 ASSERT 文 — 評価: ◎

```sql
CREATE TEMP TABLE #targets AS
SELECT $id FROM APP100 WHERE 売上 > 1000000;

ASSERT (SELECT COUNT(*) FROM #targets) BETWEEN 1 AND 500;

UPDATE APP100 SET 状態 = '対象' WHERE ...;
```

- 条件が false ならその文で `error` となり fail-fast 停止する(DML 実行前の業務条件ガード)
- `dmlMaxRows` が「実行時の影響行数上限ガード」なのに対し、ASSERT は「業務条件の事前検証」で役割が補完的
- 実装: 新 statementType `ASSERT` を1つ追加。read-only 扱いで validate-all-first / fail-fast / `statements[]` エンベロープにそのまま乗る。実装コストは全提案中で最小
- **真値の定義(初期版)**: 曖昧さを避けるため `ASSERT <比較式>` に限定する
  - スカラーサブクエリは**必ず 1行1列**を要求(複数行・複数列・0行は `AssertError`。0行を暗黙 NULL 扱いにしない)
  - 比較結果が false または NULL 相当なら `AssertError`(`0` / 空文字の truthy 判定のような暗黙変換は導入しない)
  - 比較式以外(裸の値・式のみ)は `ParseError`
- エラーコードは `AssertError` を新設(fail-fast の停止理由が `ArgumentError` 等と区別できるように)

### 2.2 bulkRequest 対応(M5 再掲)— 評価: ○〜△(実装難度は重い)

- DML バッチの連続する書き込みを kintone `/k/v1/bulkRequest.json` に集約し、**擬似アトミック化**(all-or-nothing)する。§10 の「トランザクションは無い」制限への実質的な回答
- kintone 側制約:
  - 最大 20 リクエスト / bulkRequest(バッチ文数上限 20 と偶然一致するが、1文が複数リクエストに分割される場合がある点に注意)
  - 対象はレコードの add / update / delete のみ。**REORDER は不可**(API 上はステータス更新も bulk 可能だが、kSQL 現行はプロセス管理ステータス更新を対象外としているため、将来その構文が入る場合のみ関係する)
  - **UPSERT は事前照合(読み取り)が別呼び出し**になるため、照合〜書き込み間の変動は防げない(書き込み部分のみアトミック)
- 実装方針案: 対象文種(INSERT / UPDATE / DELETE のみで構成されるバッチ)に限定した opt-in オプション(例: MCP `atomic: true` / CLI `--bulk`)。適用不能な文種が混在する場合は validate 段階で ArgumentError
- **実装難度の注意**: 現在の `KintoneClient` は `postRecords` / `putRecords` / `deleteRecords` の即時実行単位であり、bulk 化には API メソッドの追加だけでなく「**DML 文を実行せずリクエスト計画に変換する層**」の新設が必要。また 100 レコード超の文は1文が複数リクエストに分割され 20 リクエスト上限を圧迫するため、適用条件(文数 × 行数)は validate 段階でかなり絞る必要がある
- ステータス: v1.4.0 時点で「実機スパイクとセットで v1.5 以降に判断」と保留済みの項目

### 2.3 Undo ログ生成 — 評価: ○

- UPDATE / DELETE の実行前に対象行の pre-image を JSONL で保存し、復元用 SQL(または復元コマンド)を生成する
- UPDATE / DELETE は対象行の特定クエリを実行済みのため**そのクエリは流用できる**が、現行は `$id` のみ取得しており、pre-image の保存には**追加フィールド取得が必要**(取得フィールドの拡張 or 追加読み取り1回)
- CLI: `--undo-log <path>` で容易。MCP: ファイルパスを結果に含める形ならステートレス設計と両立可(サーバー内に状態は持たない)
- 制約の明示が必要: 復元は「pre-image の再書き込み」であり、他ユーザーの後続更新と競合し得る(真のロールバックではない)

## 3. 運用系(cron / CI バッチ実行向け)

### 3.1 リトライ / レート制御の設定公開 — 評価: ◎(新規機能ではなく既存基盤の公開)

- **基盤は実装済み**: `requestGate`(P0-1、`src/api/requestGate.ts`)がセマフォ(同時リクエスト上限、既定 10)と GET 系リトライ(408/429/502/503/504 + ネットワーク一時エラーを指数バックオフ + ジッタで再試行、既定 3 回)を提供している
- **書き込み系(POST/PUT/DELETE)は原則リトライしない**(応答喪失時の二重実行を避けるため。セマフォのみ適用)— この方針を公開仕様として明文化する
- 残タスク:
  - CLI / config からの調整公開(例: `--max-concurrent` / `--retry <n>` / `--retry-backoff <ms>`)
  - 言語リファレンス or CLI 仕様への「書き込み非リトライ」方針の追記
- 文レベル並列実行(§4.4)の前提基盤は既に存在することになるため、§4.4 の再評価条件は「設定公開 + 実運用での挙動確認」に読み替える

### 3.2 バッチ結果の構造化出力(CLI)— 評価: ◎(優先度高)

- 現状: CLI バッチは SELECT 結果のみ stdout に出力し、文ごとのサマリは stderr に流している(`src/cli/index.ts` `writeBatchOutput`)。機械可読なバッチ全体の結果が stdout から得られない
- 提案: MCP と同じ `statements[]` エンベロープ(バッチ仕様 §6.2)を `--format json` 時に stdout へ返す
- exit code: **`2` は既存の `ArgumentError` / DML キャンセルで使用済みのため部分失敗に割り当てない**。部分失敗(`continue-on-error` 時)は `1` のまま JSON の `ok: false` / `statements[]` で判定するのを基本とし、CI で exit code のみで区別したい需要が出たら未使用の `4` 等を新設する
- 実装: 既存エンベロープの再利用のみ。CI 用途での効果が大きく、コスト対効果は ASSERT に次ぐ

### 3.3 失敗時 Webhook 通知 — 評価: ◎

- バッチ失敗時に指定 URL へ結果サマリを POST(cron 運用での監視・アラート)
- 実装は小さいが、kintone 通知アプリや Slack 連携と組み合わせると cron 用途で効果が大きい
- 論点: 通知ペイロードに含める情報の範囲(SQL 全文を含めるとトークン等の秘匿情報混入リスク。文タイプ + アプリ ID + エラーコードに限定が安全)

### 3.4 チェックポイント / リジューム — 評価: △(優先度低)

- 途中失敗したバッチを文 N から再開する機能
- MCP のステートレス設計と衝突するため CLI 限定 + 状態ファイル方式になるが、一時テーブルはバッチ終了で破棄されるため**再開時に再実体化が必要**で、「再開」の意味が薄い
- 代替: fail-fast + 文ごとの影響件数レポート(実装済み)を見て、残りの文だけの SQL ファイルを作り直す運用で実用上足りる

## 4. 利便性系

### 4.1 パラメータバインド — 評価: ○

```bash
ksql -f monthly_report.sql --param month=2026-07 --param dept=営業部
```

```sql
SELECT * FROM APP100 WHERE 対象月 = :month AND 部署 = :dept;
```

- 定型バッチ(cron / CI)のテンプレート化に必須級。保存クエリ(`ksql_save_query` / `ksql_run_saved_query`)への引数対応と合わせると MCP 側でも効く
- 実装: レキサに `:name` トークン追加 + パース後の **AST レベルでの型付き置換**(文字列結合ではないためインジェクション懸念なし)
- 論点: 置換を許す位置(リテラル位置のみに限定。テーブル名・フィールドコードへの置換は不可とする)

### 4.2 保存クエリのバッチ対応 — 評価: ○

- `ksql_save_query` にバッチ SQL を保存可能にし、`ksql_run_saved_query` で実行(§4.1 のパラメータと組み合わせて定型処理のライブラリ化)
- 現状: 両ツールは `requireSingleStatement` ガード(`src/mcp/tools.ts`)で**明示的に単文限定**。バッチ対応時はこのガードを外すだけで、実装自体は小さい
- **安全設計を先に確定させる**: DML バッチを保存クエリとして「ワンタッチ実行」できることになるため、ガードは保存時ではなく**実行時**に `allowDml + confirmText + dmlMaxRows` を必須とする現方針を維持する(保存済みであることが実行時確認の省略理由にならない)

### 4.3 一時テーブルのエクスポート(CLI)— 評価: ○

```sql
CREATE TEMP TABLE #result AS SELECT ...;
EXPORT #result TO './result.csv';
```

- 中間結果のファイル保存。CLI は `--output` の機構を流用でき容易
- MCP は「最終 SELECT の結果を返す」で代替可能なうえ、サーバーからのファイル書き込みは権限設計が必要になるため**対象外(CLI 限定)**とするのが妥当

### 4.4 文レベル並列実行 — 評価: △

- 依存関係のない文(異なるアプリへの独立した SELECT 等)の並列実行
- 一時テーブルの依存グラフは validate-all-first で静的解決済みのため、**DAG 化自体は既存情報で可能**
- レート制御基盤(`requestGate`)は実装済みのため、§3.1 の設定公開 + 実運用での挙動確認後に別仕様として再評価
- DML 文は直列維持(並列 DML は途中失敗セマンティクスが複雑化しすぎる)

### 4.5 INSERT INTO #t / CREATE OR REPLACE — 評価: ○(需要待ち)

- 本仕様で「需要が確認できたら再検討」と保留済みの2項目。技術的にはいずれも容易
- バッチ内で一時テーブルを段階的に組み立てる需要(複数ソースの UNION では書きにくいケース)が実際に出た時点で着手

### 4.6 IF / ループ等の制御構文 — 評価: ×(非推奨)

- 手続き型言語化は設計原則「決定的処理と AI 解釈の分離」に反する
- 分岐が必要なケースは (a) AI クライアント側で結果を見て次の呼び出しを組み立てる、(b) ASSERT(§2.1)+ 呼び出し分割、のいずれかで足りる
- kSQL は宣言的なバッチ言語に留めることを明示的な設計判断とする

## 5. 推奨優先順位

| 順位 | 機能 | 理由 |
|---|---|---|
| 1 | ASSERT 文(§2.1) | 実装コスト最小で DML バッチの安全性が一段上がる。既存設計との整合が最良 |
| 2 | CLI バッチ JSON 出力 + exit code 整理(§3.2) | 既存エンベロープの流用のみで CI 用途に直結 |
| 3 | パラメータバインド(§4.1) | 定型バッチ運用(cron / CI)の要 |
| 4 | 保存クエリのバッチ対応(§4.2) | 実装は小さいが、実行時ガード維持の安全設計を先に確定 |
| 5 | bulkRequest(§2.2) | 価値は高いがリクエスト計画変換層の新設が必要で重い |
| 6 | Undo ログ(§2.3) | 追加読み取りコストなしの安全網。設計は独立して進められる |
| 7 | Webhook 通知(§3.3) | 小コストだが外部依存を持つため後回しで可 |

- **リトライ / レート制御(§3.1)は上表から除外** — 新規機能ではなく既存 `requestGate` の設定公開 + 仕様明文化として、上記と並行して随時実施
- §4.3〜§4.5 は需要・前提基盤の確認後に判断。§3.4・§4.6 は見送り
