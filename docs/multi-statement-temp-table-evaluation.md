kSQL に「複数SQLの順次実行・並列実行」と「一時テーブル」を追加する案について、現行実装のコード調査に基づいて評価する。並列実行は本改訂で**対象外**とした(§3)。

---

## 結論(TLDR)

| 案 | 評価 | 要約 |
|---|---|---|
| 一時テーブル | ◎ 採用推奨 | CTE実体化機構がほぼそのまま流用でき、費用対効果が3案中で最も高い |
| 順次実行 | ○ 条件付き採用推奨 | 一時テーブルとセットで初めて価値が出る。本丸はパーサではなくMCP層の安全設計の再設計 |
| 並列実行 | ✕ 対象外 | レート制御基盤が無く実利も薄い。本仕様から切り離し、基盤整備後に別仕様として再評価 |

推奨ロードマップ:

0. 先行基盤(独立改善): グローバルレートリミッタ + 429/5xx リトライ、フィールド定義キャッシュ TTL、`bulkRequest` 技術検証
1. バッチスコープ一時テーブル + read-only バッチ(順次)
2. DML を含むバッチ(`bulkRequest` によるアトミック化を含めて検討)

並列実行は本仕様の対象外とする(基盤整備後に別仕様として再評価)。

## 前提: 現状実装の確認結果

評価の根拠となる事実。

### 単文前提はパーサ1箇所にハードコード

`Parser.parse()`(`src/parser/parser.ts:112-118`)が「1文 + 任意の `;` + EOF」を強制している。

```ts
parse(): Statement {
  const stmt = this.parseStatement();
  // セミコロンは任意
  if (this.peek().kind === TokenKind.SEMICOLON) this.advance();
  this.expect(TokenKind.EOF);
  return stmt;
}
```

レキサは既に `;` を `TokenKind.SEMICOLON` としてトークン化済み(`src/lexer/tokens.ts:163`, `src/lexer/lexer.ts:198`)のため、複文分割自体は `parseStatements()` のループ追加だけで済む。公開パースAPIは `parseSqlStatement`(`src/core/sql.ts:5-8`)のみで、戻り値は単一 `Statement`。

### MCP層は隅々まで単文前提

- `validate()` が返す `ValidationResult`(`src/mcp/tools.ts:78-92`)はスカラー構造(1つの `statementType`・`hasWhere`・`insertValuesCount`・`appIds`・`cacheContext`)
- DMLガードの `dmlMaxRows` と `confirm` コールバックは単一操作前提(`src/mcp/tools.ts:215-231`, `:374-379`)
- 結果整形も単一ペイロード(`toSelectPayload` `:153` / `toMutationPayload` `:164`)
- 入力スキーマは `sql: z.string().min(1)`(`src/mcp/schemas.ts`)

**複文対応の実装コストの大半はパーサではなくこの層にある。**

### CTEは既に「文内一時テーブル」として実装済み

`executeWith`(`src/execute.ts:649-680`)が CTE 結果を `Map<string, ProcessRow[]>` に実体化し、`processRowToKintoneRecord`(`src/execute.ts:917`)で擬似テーブルとして FULL_SCAN エンジンに注入している。一時テーブルは「この寿命を文単位からバッチ単位に延ばしたもの」に相当する。

### トランザクションは無い

kintone API の制約により非対応(言語リファレンス「制限事項」に明記)。DML 書き込みは 100件/リクエストの逐次チャンク(`src/converter/dmlToKintone.ts`)で、既に非アトミック。

### 並列制御はページ取得層のみ

- `fetchParallel`(1〜10)は `fetchAll` 内の `Promise.all` を制御するだけ(`src/api/fetchAll.ts:141-145`)。既定値は CLI/MCP runtime 経由では 3(`src/node/runtime.ts:76-79`)、`fetchAll` 単体では 1 = 直列(`src/api/fetchAll.ts:47`)
- サブクエリ解決・JOIN の複数テーブル取得・UNION の枝は既に `Promise.all` で並列(`src/execute.ts:479,560,607`)
- **グローバルなレートリミッタ・リクエストキュー・429/5xx リトライは存在しない**(リトライは `CB_IL02` の1ケースのみ、`src/cli/nodeKintoneClient.ts:85-136`)
- `bulkRequest` API は未使用

### MCPサーバーはコール毎にruntime/clientを生成するステートレス設計

`createKsqlRuntime`(`src/node/runtime.ts:61`)がコール毎に profile 別クライアントを構築。例外はプロセス寿命のフィールド定義キャッシュ(`src/execute.ts:1203-1206`、TTL・無効化なし、メタデータのみ)。

## 個別評価

## 1. 一時テーブル — ◎ 採用推奨

### 価値: 高い

- MCP 経由の利用では中間結果を LLM のコンテキストに往復させるしかなく、件数制限(MCP 既定 500件)とトークンコストの両方で不利。`CREATE TEMP TABLE t AS SELECT ...` → 後続文で `t` を参照、がサーバー内で完結すれば解消する
- 相関サブクエリ非対応・UPDATE に JOIN 非対応という現行制限の実用的な回避策になる
- 現在 MCP で拒否している `INSERT_SELECT` の安全な解禁経路になる: `ksql_query` で件数をプレビューして承認判断し、`ksql_mutate` の**同一バッチ内**で「実体化 → 書き込み」を行う2段階 DML フローが組める(一時テーブルはバッチスコープのため本実行側で再実体化する)。書き込み前に行数が確定するため `dmlMaxRows` ガードと自然に整合する

### 実装コスト: 中〜小

`ProcessRow[]` の行モデル、`Map` によるテーブル格納、エンジンへの注入ブリッジまで全て既存。新規に必要なのは:

- `CREATE TEMP TABLE ... AS SELECT` / `DROP TEMP TABLE` のパース(AST 追加)
- バッチ実行器に `Map<string, ProcessRow[]>` のストアを1つ通す(`cteCache` の寿命延長版)
- `parseTableRef` の名前解決拡張(現行の `Parser.cteNames` 機構を流用、`src/parser/parser.ts:104,842`)
- `APPxxx` と衝突しない命名規則 — `#temp` 接頭辞を推奨。ただし現行レキサは `#` を読めないため小規模なレキサ・パーサ変更を伴う(詳細は「仕様化が必要な追加論点」(4))
- 行数上限(既存 `maxRecords` に準拠)とメモリ保護

### 設計上の分岐点: スコープ

| スコープ | 評価 |
|---|---|
| **バッチ内**(1回のツール/CLI呼び出し内) | **推奨。** ステートレス設計を維持でき、クリーンアップも自明(呼び出し終了=破棄) |
| セッション/プロセス | 非推奨。MCP のステートレス原則を壊し、TTL 無しキャッシュの前例をデータにまで広げることになる。profile 混在時の取り違えリスクも生む。やるなら TTL + 総量上限 + 明示 DROP 必須が最低条件 |

## 2. 複数SQLの順次実行 — ○ 条件付き採用推奨

### 価値: 一時テーブルとセットなら高い

単独では「複数回ツールを呼べば済む」ため価値が薄いが、一時テーブルの寿命を定義する器として必須。CLI の `-f file.sql` も現状は実質1文のため、バッチ実行は CLI 側の自然な拡張にもなる。

### 最大の論点: 安全設計3本柱との整合

本プロダクトの差別化は「read-only/DML のツール分離・validate-first・多層 DML ガード」であり、複文対応でこれを緩めたら本末転倒。整合させる設計:

- **validate-all-first**: 実行前に全文をパース・分類し、1文でも不正なら全体拒否。validate-first の自然な拡張
- **ツール境界の維持**: バッチ内に DML が1つでもあれば `ksql_mutate`(またはバッチ専用ツール)でのみ受理。`ksql_query` は read-only 文のみのバッチを受ける
- **ガードの複数形化**: `dmlMaxRows` は「文ごと適用 + バッチ合計上限」の2段。`insertValuesCount`・`hasWhere` チェックも文ごとに適用
- **失敗セマンティクスの明示**: トランザクションが無い以上、**途中失敗時に前半の DML だけ反映された状態は避けられない**。ロールバック風の実装は試みず、「fail-fast(既定)/ continue-on-error(opt-in)」を選ばせ、結果ペイロードに文ごとの成否・影響件数を返す。なお kintone の `bulkRequest` API(最大20リクエストをアトミック実行、失敗時は全体ロールバック)は現在未使用であり、小規模 DML バッチの原子性確保に使える可能性がある(→「独立して先行すべき基盤仕様」(b))
- `EXPLAIN` のバッチ版(全文のプラン一括表示)があると dry-run 運用と噛み合う

### 実装コスト: 中〜大

| 層 | コスト | 内容 |
|---|---|---|
| パーサ | 小 | `parseStatements()` のループ化 |
| 実行器 | 中 | `executeStatement` のループ + 一時テーブルストアの受け渡し |
| MCP層 | 大 | `ValidationResult` の配列化、ガードの複数形化、結果エンベロープ、スキーマ拡張 |

テスト資産は充実(計404ケース / 17ファイル)。`src/__tests__/execute.test.ts`(94ケース)はモッククライアント注入型のため、ネットワーク無しでバッチ実行をテスト可能。主に触るのは parser(67)・execute(94)・process(80)・mcp/tools(23)。

## 3. 並列実行 — ✕ 対象外

本仕様の対象外とする。理由は以下の通り。

### 実利が想定より薄い

並列化で速くなるのは「独立した複数アプリからの取得」だが、これは既にサブクエリ解決・JOIN の複数テーブル取得・UNION の枝で `Promise.all` により並列化されている。実際のボトルネックであるページ取得にも `fetchParallel` が既にある。文レベル並列が新たに稼げる時間は限定的。

### リスクは具体的

- **レート制限に無防備**: 文レベル並列 × `fetchParallel`(最大10)で同時リクエスト数が乗算されるが、グローバルセマフォも 429 バックオフリトライも無い。kintone の同時接続制限に当たると即エラーで倒れる。**並列機能より先にこの基盤が必要**であり、それは独立した(先にやる価値のある)改善
- **DML 並列は安全設計と真っ向から矛盾**: 順序保証なし・同一アプリへの並列書き込みでのリビジョン衝突・失敗時状態の予測不能化。「曖昧さを残さない」という設計思想と両立しない
- **一時テーブル導入と相性が悪い**: 一時テーブルは文間に依存関係を生むため、自動並列化には依存グラフ解析が必要になる。明示構文(並列ブロック)にしても、MCP 経由では LLM が誤用する余地が増えるだけ

### 再評価の条件

将来の再評価余地は残す。条件: read-only 文のみ・明示 opt-in・グローバル同時実行上限つき、かつレートリミッタ + 429/5xx リトライの基盤整備後。その場合も本仕様の拡張ではなく**別仕様として起こす**。

## 仕様化が必要な追加論点

フェーズ1〜2を実装に落とす前に決めておくべき仕様。上記の個別評価では未定義の項目。

### (1) 複数結果セットの返却仕様

バッチ内に SELECT が複数あるとき、全結果を返すか・最後の SELECT のみ返すかが未定義。MCP では `DEFAULT_MAX_RECORDS = 500`(`src/mcp/tools.ts:94`)が文ごとに掛かるのか合計なのかも決める必要がある。一時テーブルの狙いが「中間結果を LLM のコンテキストに返さない」ことにある以上、**既定は「一時テーブルへ格納した SELECT の結果は返さず、素の SELECT のみ結果セットとして返す」**を推奨。`maxRecords` は「文ごと適用 + バッチ合計上限」の2段とする(`dmlMaxRows` と同じ構造)。

### (2) 一時テーブル自体への DML の可否

上記の個別評価は `CREATE TEMP TABLE ... AS SELECT` / `DROP TEMP TABLE` しか定義していない。`INSERT INTO #t` / `UPDATE #t` / `DELETE FROM #t` は kintone に書き込まないため「read-only バッチ」に含められる理屈だが、そうすると `ksql_query` が DML 構文を受理することになり、ツール分離(read-only/DML)の説明が濁る。**フェーズ1では非対応(エラー)と明示する。** 需要が確認できたらフェーズ2以降で再検討。

### (3) 一時テーブルのメタデータ解決

一時テーブルは CTE と同様に `ProcessRow[]` を FULL_SCAN エンジンに注入して参照する設計のため(`src/execute.ts:828-861,917`)、**REST API への WHERE プッシュダウンは構造的に発生しない(参照は常にインメモリ FULL_SCAN)**。列型情報が必要になるのは、検証・`ksql_describe_app` 相当の内省・ORDER BY / 比較演算の意味づけである。仕様化する事項:

- SELECT 結果からの列型導出規則(集計列・演算列・NULL のみの列の型)
- 一時テーブル参照文に対する `EXPLAIN` の表示内容(FULL_SCAN である旨、実体化前は行数不明である旨)

### (4) 命名規則の詳細

**注意: `#` は現行レキサでは読めない。** 識別子の先頭文字は ASCII英字・`_`・`$`・日本語のみ(`src/lexer/lexer.ts:279-288`)で、`#` は演算子表にも無いため `LexError` になる。`#temp` を採用する場合はレキサ・トークン・パーサの小規模な変更(識別子先頭としての `#` の受理と `parseIdentifier` の対応、`src/parser/parser.ts:1710`)が必要。代替の `TEMP_` 接頭辞は既存トークンのまま使えるが、実テーブル・CTE 名との衝突を構造的には防げない(命名規約頼みになる)。

推奨: 衝突を構造的に防げる `#temp` を採用し、レキサ変更をフェーズ1の作業項目に含める。その他仕様として決める事項:

- 同名 `CREATE` の再定義可否 — まずはエラーを推奨(`OR REPLACE` は需要が出てから)
- 名前の大文字小文字の扱い(既存のテーブル名解決と揃える)
- `@profile` 付与不可の明示(`#t@dev` はエラー)

### (5) 実行時失敗時の依存スキップ

validate-all-first が弾けるのは構文エラー・分類違反のみ。`CREATE TEMP TABLE` が実行時エラー(429等)で失敗した場合、continue-on-error モードでもそのテーブルを参照する後続文は必然的に失敗する。**依存先が失敗した文は実行せず `skipped` として報告する**仕様とし、結果エンベロープの文ごと成否を「success / error / skipped」の3値にする。

### (6) バッチのタイムアウトとキャンセル

現在の `timeout` はコール単位(`src/node/runtime.ts:87-89`)。バッチでは合計タイムアウトとして扱い、到達時に「どの文まで実行済みか」を結果に含める。DML 混在バッチの途中キャンセル時も同様に、文ごとの確定状態(反映済み/未実行)を返す。

### (7) CLI コンソールの複文入力方式

ロードマップの「`--console` の複文入力」には UI 仕様が別途必要。改行=実行の現行方式に対し、**`;` が来るまで継続入力する方式**を推奨(入力途中の破棄方法などの細部も定義する)。

## 独立して先行すべき基盤仕様

本提案とは独立に価値があり、先行して仕様化・実装すべきもの。

### (a) グローバルレートリミッタ + 429/5xx リトライ — 最優先

並列実行の前提としてではなく、**現行実装が既に無防備**であるため。サブクエリ解決・JOIN・UNION の `Promise.all` × `fetchParallel`(最大10)の乗算は現行機能だけで発生する(`src/execute.ts:479,560,607` × `src/api/fetchAll.ts:141-145`)。バッチ化はこの露出をさらに広げるため、フェーズ1の前に独立仕様として切り出す。

### (b) `bulkRequest` API の採用検討

kintone の `bulkRequest` は最大20リクエストをアトミックに実行し、失敗時は全体がロールバックされる。現在未使用(`src/converter/dmlToKintone.ts` は 100件/リクエストの逐次チャンク)。採用すれば ①小規模 DML の原子性確保、②リクエスト数削減、③フェーズ2の「途中失敗で前半だけ反映」問題の部分的緩和、が得られる。フェーズ2の失敗セマンティクス設計とセットで検討する。

### (c) フィールド定義キャッシュの TTL・無効化

プロセス寿命のフィールド定義キャッシュに TTL・無効化が無い(`src/execute.ts:1203-1206`)。長寿命 MCP プロセスでスキーマ変更が反映されない問題は一時テーブルとは独立に存在し、改修も小さいため先行できる。

## 推奨ロードマップ

### フェーズ0: 先行基盤(独立改善)

- グローバルレートリミッタ + 429/5xx リトライ
- フィールド定義キャッシュの TTL・無効化
- `bulkRequest` 採用の技術検証(フェーズ2の設計入力)

### フェーズ1: read-only バッチ + バッチスコープ一時テーブル

- 「仕様化が必要な追加論点」(1)〜(7)の決定
- 一時テーブル名 `#` 接頭辞のレキサ・トークン・パーサ対応
- 複文パース(`parseStatements`)
- read-only バッチ順次実行
- `CREATE TEMP TABLE ... AS SELECT` / `DROP TEMP TABLE`(バッチ内スコープ、一時テーブルへの DML は非対応)
- MCP: `ksql_query` の拡張または `ksql_batch` 新設
- CLI: `-f` の複文対応と `--console` の複文入力(`;` 区切り)

### フェーズ2: DML を含むバッチ

- `ksql_mutate` 側でのバッチ受理
- 文ごと + 合計の `dmlMaxRows`、fail-fast 既定、文ごと結果レポート(success / error / skipped)
- バッチ EXPLAIN(dry-run)
- 一時テーブル経由の `INSERT_SELECT` 解禁
- `bulkRequest` によるアトミック化の適用判断(フェーズ0の検証結果を反映)

### 対象外: 並列実行

本仕様の対象外(§3)。レートリミッタ + 429/5xx リトライの基盤整備後、read-only 限定・明示 opt-in で**別仕様として**再評価する。

---

## まとめ

この案の価値の源泉は**一時テーブル**であり、**順次実行はその器**である。**並列実行は本仕様の対象外**とし、レート制御基盤の整備後に別仕様として再評価する。実装に着手する前に「仕様化が必要な追加論点」(1)〜(7)を確定させ、基盤仕様 (a)〜(c) はフェーズ0として本提案と独立に進める。
