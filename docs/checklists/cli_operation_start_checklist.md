# kSQL CLI 実運用開始チェックリスト

- 作成日: 2026-04-07
- 対象: kSQL CLI Ver.1

## 1. 運用開始前（必須）

1. ビルド確認
- `npm run build:cli` が成功する
- `node dist-cli/ksql.js --help` が表示できる

2. 接続確認（本番相当環境）
- `token` 認証で `SELECT` が成功する
- `userpass` 認証で `SELECT` が成功する
- `--debug-url` で実HTTPリクエストURLを確認できる

3. DML 安全ガード確認
- 変更系コマンドは `--allow-dml` 必須運用にする
- `--dml-max-rows` を必ず設定する（例: 100）
- `--allow-without-where` は本番で原則禁止にする
- 非対話実行時は `--yes` の利用条件をチームで明文化する

4. 権限・対象アプリ確認
- APIトークンに対象アプリ権限がある
- 実行対象アプリIDを運用手順書に固定化する
- 本番トークンは設定ファイルに平文保存しない

## 2. 運用中（日次/都度）

1. 実行ログを残す
- 実行SQL
- 実行時刻
- 対象環境（base-url / app）
- 成否
- 失敗時エラー本文

2. 変更系実行時のルール
- 初回は必ず小件数（WHERE + `--dml-max-rows`）で実施
- 件数見積りと実件数が乖離したら即中断
- 大量更新は段階実行（分割）を原則にする

3. 失敗時の記録
- `--debug-url` 出力
- `--debug-headers` 出力（機密値はマスク）
- APIエラーコード（例: `CB_IL02`）

## 3. 障害時対応（簡易）

1. まず止める
- 同一コマンドの再実行を停止
- 影響範囲（対象アプリ / レコード件数）を確認

2. 事実を集める
- 実行SQLとCLIオプション
- 実行ユーザー/認証方式
- エラー全文とリクエストURL

3. 復旧を判断する
- 再実行で復旧可能か
- 手動修正が必要か
- ロールバック相当の修正SQLが必要か

## 4. 週次レビュー（推奨）

1. エラー上位3件を確認する
2. 遅いクエリ上位3件を確認する
3. 操作ミス/分かりにくさを3件まで洗い出す
4. 次週の改善タスクを1〜2件に絞る

## 5. GO / NO-GO 判定

### GO 条件
- 接続確認（token/userpass）が成功している
- DML安全ガード運用ルールが合意済み
- ログ保存手順が決まっている

### NO-GO 条件
- 本番で `--allow-without-where` を常用している
- `--dml-max-rows` 未設定でDMLを実行している
- 失敗時ログが残らず原因追跡できない
