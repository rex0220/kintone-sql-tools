改善 (B141 fetch は同じ WHERE でもクエリの形で変わる) ★本リリースの要点:
- fetch: の節に、形で値が変わることを追記しました。
    SELECT COUNT(*) FROM APP100 WHERE 担当者 in ('user1')
      → COUNT_ONLY  (押し下げは効いているが、走査しないので COUNT_ONLY が優先)
    SELECT 区分, COUNT(*) FROM APP100 WHERE 担当者 in ('user1') GROUP BY 区分
      → PREFILTERED (同じ WHERE・同じ押し下げ。走査するので PREFILTERED)
- 押し下げが効いているかを比べるときは、すべて同じ形で測ってください。
  形を混ぜた表を作ると、押し下げの差ではなく形の差を読んでしまいます。
- 分類表そのものは定義表なので誤りはありませんでしたが、「同じ WHERE でも
  形で変わる」がどこにも書かれていませんでした。

改善 (B141 挙動を写した表に「実測した版」を刻む):
- 挙動を写した表に (実測・vX.Y.Z) を刻むようにしました
  (除数ガードの表・空集合の戻り値の表)。
- この文書は MCP リソースとして配られ、利用側のドキュメントへ複製されます。
  刻印があれば、複製先は「どの版の観測を写したか」を一緒に持ち帰れます。
- エンジンの変更はありません。

挙動が変わります (B142 値が無いときの MIN / MAX が 0 から空文字へ) (v3.54.0):
- 集計する値が 1 つも無いときの MIN / MAX が、0 ではなく空文字を返します。
    SELECT MIN(製品名) FROM APP100 WHERE 分類 = '存在しない分類'
      旧 "0" (長さ 1 の文字列。= '' をすり抜ける)   新 ""
- 同じ状況が形によって割れていたためです。空セルは MIN / MAX では値として
  保持されるため、値が 1 個なら空文字、0 個なら 0 になっていました。
    LEFT JOIN で一致しないグループ (空セル 1 個)  ""   従来から
    WHERE が全部落ちる (値 0 個)                  "0"  ← 変わった
    CASE に ELSE が無く全行が非一致 (値 0 個)     "0"  ← 変わった
- MODE / MEDIAN / 統計集約は以前から空文字でした。標準 SQL も MIN / MAX の
  空集合は型に依らず NULL です。COUNT / SUM / AVG は変わりません。
- 移行: MIN / MAX の結果を 0 件かどうかの判定に使っている場合は影響します。
  DML では書き込む値が変わります。
    UPDATE APP88 SET 上限費用 = (SELECT MAX(合計費用) FROM APP88) WHERE ...
    サブクエリが 0 件のとき、書き込む値が 0 から空になります。
  該当が無いのに「最大値は 0」と書くのは事実に反するための変更ですが、
  対象が必須フィールドなら、これまで通っていた UPDATE が失敗します。
  既に 0 が書き込まれているレコードは遡って変わりません。

改善 (B141 除数のガードが要る形を絞り込む) (v3.54.1 で修正):
- 「除数には常に = '' OR = 0」ではなく、どの除数にガードが要るかを表にしました。
    SUM / COUNT / AVG を通した値  該当が無いと 0     = 0 で足りる
    MIN / MAX を通した値          該当が無いと空文字 = '' OR = 0
    素の列として渡ってきた値      該当が無いと空文字 = '' OR = 0
- 「集計を通したから安全」ではありません。MIN / MAX は空文字を返します。
- 空文字は「値が無かった」ことから生まれます (LEFT JOIN 不一致、LAG / LEAD の
  端、NULLIF、対象が 0 件の MIN / MAX)。
- 空集合の戻り値も関数ごとに表で示しました。
- v3.54.0 ではこの表が MIN / MAX を「集計を通した値」に含めており、同じ版で
  変えた挙動に追随していませんでした。v3.54.1 で直しています。

新機能 (B128 LAG / LEAD) (v3.51.0):
- 前月比・前年同月比を SQL 側で書けるようになりました。
    LAG(expr [, offset])  OVER (PARTITION BY ... ORDER BY ...)
    LEAD(expr [, offset]) OVER (PARTITION BY ... ORDER BY ...)
- 前後の行がパーティションの外なら空文字を返します。offset は省略時 1 で、
  非負の整数リテラルだけを受け付けます。第 3 引数 (既定値) は未対応です。
- 引数の型を引き継ぎます。CTE や一時テーブルの次の段でも、数値順・日付順・
  選択肢の定義順など元の列の比較規則を保ちます。
- 前月比は 3 段で書きます (ウィンドウ結果を同じ SELECT の式に含める形は
  従来どおり拒否されます)。書き方は ksql_docs の recipes/r16 にあります。
- ORDER BY が全順序と判定できないときは警告が出ます。値は正しく、
  同順の行があるときの前後関係が未規定であることの注意です。

修正 (B137 列数の違う UNION / UNION ALL をエラーにする) (v3.50.0):
- UNION / UNION ALL の左右で列数が違う場合、エラーで停止するようになりました。
  従来は右辺の列が足りないと空文字で埋め、余ると黙って捨てていたため、
  成功しても意図しない結果になり得ました。
    修正前  SELECT 製品名, 仕入先 FROM APP4228 UNION SELECT 製品名 FROM APP4229
            → 右辺由来の行では 仕入先 が空文字になっていた
    移行後  SELECT 製品名, 仕入先 FROM APP4228 UNION SELECT 製品名, '' FROM APP4229
- 足りない側へリテラルを追加して列数を揃えてください。
- 列名は従来どおり左辺から取り、左右の列を位置で対応させます。列名の一致と
  型の互換性は検査しません。
- EXPLAIN は従来どおり計画を返します (行を取らないため列が実体化されません)。
- 言語リファレンスは以前から「両辺の列数が一致しない場合はエラー」と書いていました。
  文書が正しく、実装がその契約を守っていませんでした。挙動の追加ではなく、
  文書どおりに直したものです。
